# 规则治理（测试轨）

> **读取级别：参考**（维护/改规则时读；运行时规则以 `global-rules.md` 为准）。

> 目的：防止规则膨胀、重复、冲突、无执行载体。维护/改规则时读；业务任务不读。
> 原则：一条规则一个 owner；能脚本检查的不写长文；**优先吸收/改写既有条文**；完全未覆盖才新增；禁「缺一加一」堆清单。
> 优化目标：生成一次到位（深度够、oracle 可判）+ 执行判定正确 + **同路径旁证问题能发现**（不限于本条断言面）。

## 1. 预算

| 对象 | 上限（估算 tokens） | 说明 |
| --- | ---: | --- |
| `cold-start.md`（开局一次整文件读） | ≤ 1,200 | 只放启动/续跑/回执 |
| `global-rules.md`（每步整文件读） | ≤ 6,000 | 全局规则唯一出处；每步读并逐条过；未读不得写 `global=ok` |
| `AGENTS.md` §0 + 指针 | ≤ 2,500 | 分级表+指针；硬约束不重复 global-rules |
| `AGENTS.md` 全文（含口令表） | 不计入每任务预算 | 口令表仅路由未定/首次命中时读 |
| 参考手册 / `rules/special/` / 按节读规则 | 不设整文件上限 | 头部标 `读取级别：参考` 或 `读取时机` + 节索引；只读当前节；不得为凑短删质量内容 |
| `skills/<name>/SKILL.md` | 不设 token 上限 | 按 §6 **整卡读取**（必做 → 方法/判定 → 反模式/DoD）；单步预算计整卡；主文件 ≤500 行（结构上限，超长拆 `references/`） |
| 模板 | 不设 token 上限 | 只复制/填写，不作为规则通读 |
| 单步读取总量（步骤包 + §6 整卡） | 轻 ≤8,000｜标准 ≤12,000｜重 ≤22,000 | 不含每步 `global-rules`；核心来源按命中读；重步允许；超 22,000 才拆包或拆技能。预算约束长度，不截断技能，也不是砍质量的借口 |

估算：CJK 字符约 1 token/字；ASCII 约 4 字符/token。整文件 token 只约束 `AGENTS.md` / `cold-start.md` / `global-rules.md` 这类“开局或每步整文件读”的文件；`gates.md`、`routing.md`、`doc-quality.md`、`doc-governance.md` 等按节读规则，不按整文件限长。`Test-DocHygiene.ps1` 检查上述整文件预算、模板索引与结构；按节读文档不报整文件长度。

**读法分级**：
- **开局**：新会话精读 `cold-start.md`。
- **每步必读**：`global-rules.md`（按 §7 重读分级）+ 当前步骤包（`packet=`）；未按 §7 复核不得写 `global=ok`。
- **主从**：步骤包=本步目的/门槛/门；技能/模板=方法与壳；`global-rules`=跨步场规则；`core|defects|collaboration` 具名索引按步骤包点名再读。禁技能另造平行流程。
- **参考 / 技能 / 模板**：按命中读当前节；不通读库。

## 2. 单一出处

- 每条规则只在一个文件定义；其他位置只放指针 + 规则 ID。
- 高频重复（证据可追溯、P0 不通过、阻塞从严、一次一问）必须合并。
- 阻断路径统一 `必须/禁止/不得`；`可/建议/按需` 只用于非阻断能力。
- 新增前先问：① 能否并入既有不变量/深度档/判定语义？② 能否脚本检查？③ 能否删改旧句代替新增？任一「能」则不得新开条目。  
- 对照外源defects/事故改规则时：先映射到现有特征行与 §3.0 判定；只补**通用维度**，禁贴场景清单；同一主题多处正文 → 留一处 SSOT，其余改指针。

## 2.0 补强闸门（防堆积 · 硬）

```text
发现缺口 / 反复失误
  → Q1 现有 global-rules / cold-start / gates / skill 必做 / verify / multi-track 是否已覆盖？
       是 → 改那一处（增强）→ 删其它副本 → 跑 eval/自检
  → Q2 能否用脚本/门检查代替长文？ → 是则加机检，不写新散文
  → Q3 是否同一错误反复（有证据）？ → 否：只记洞见，不入库
  → Q4 完全未覆盖？ → 才新开：优先扩现有 owner；须单一职责、预算内、有载体、有降级；并删除被替代正文
```

- workflow step `notes`：**≤3 行指针**；方法进 skills / must_read / special 当前节；禁止 notes 复述门/准出口径全文。
- 能力体检方法：`rules/special/skill-audit.md`（仅 skill-audit 链点名读）。

## 2.1 自适应规则写法（防过拟合）

规则写“判断维度、不变量、升级条件、失败回退”，不写“具体场景清单/固定口令/固定文件数/固定角色名”。示例只作校准，最多 2～3 个，并标“示例，非穷尽”。三层写法：**不变量（硬，必须/禁止）→ 判断维度（柔，按影响/风险/协调面）→ 示例（参考，非穷尽）**；禁止把示例写成不变量。

- 一条规则只回答：什么目标、看哪些信号、何时取轻/取重、何时停、失败怎么办。
- 能用门/脚本/检查表判定的，不写成长篇叙述；不能机器判定的，给“判断问题”而非“标准答案”。
- 新规则必须写“不适用/降级”路径；否则不得新增。
- **路径/产物未列尽**：优先靠执行契约 §1.3 归类；禁为单次落盘困惑新增专条路径清单。
- 同一规则不在 AGENTS/技能/模板重复正文；只留指针。
- 维护时删除“只为某个项目/某次事故写死”的条款；必须保留的，标为项目适配并登记。
- 评审规则时问：换一个团队/产品/规模，这条还成立吗？不成立就改成维度或降为示例。

## 3. 规则 ID 与条件

- 格式：`TEST-<域>-<序号>`，如 `TEST-VER-02`。
- 每个 ID 对应：一句话不变量、执行载体（gate/script/human）、适用 step。
- 门语义只认 `gates.md`；新增确认门须有 YAML 载体 + `gates.md` 词条；能用门禁/检查表判定的不靠追问。
- 条件门由外部事实优先；模型自评不确定按触发处理。**T2/T3、发布前、外部文档输入：禁止用恒假条件跳过高风险门；跳过须写理由。**

## 4. 规则卫生（维护时）

```powershell

powershell -ExecutionPolicy Bypass -File "wf-testing/rules/tools/Test-DocHygiene.ps1"

```

检查：引用/锚点、YAML、workflows→agents、版本单点、AGENTS/规则行数、孤立模板。
后续可加：token 预算、重复句、同范围“必须/可跳过”冲突、孤儿规则；未实现前人工核对。

## 5. 规则 eval（改规则时）

1. 台账 18/20、报告 20/20 → 门必须 FAIL。
2. P0 失败但报告写“整体通过” → 门必须 FAIL。
3. 失败用例证据路径不存在 → 门必须 FAIL。
4. 阻塞未写已尝试/恢复条件 → 门必须 FAIL。
5. 交平台无回执仍写“已回写” → 门必须 BLOCKED。
6. 用户只要解释结果/覆盖/趋势、未要求执行 → 必须走只读分析，不得强制生成/执行/报告；未执行不得写“已通过”。
7. 低风险只读/单点任务被强制升级版本级全量/评审 → 视为过度流程，规则判定失败。
8. 新增规则只列具体场景/固定口令，无判断维度/降级路径 → 规则卫生检查失败。
9. 口令表/专模列表/类型码写成穷尽白名单（未标「示例非穷尽」）→ 规则卫生检查失败。
10. 与「内容优先·包按需」冲突的「必须整包 HO」死句 → 规则卫生检查失败。
11. 「待探查/推断」未升格写入基线 §3 真值，或未排除错入口就把契约错码开成实现缺陷 → 规则卫生/评审 FAIL（对照 `doc-quality` §1 第 2.1 条、`classification` §0）。
12. 口令表/`entry_points` 指向不存在的 step，或链图缺当前状态 → 规则卫生检查失败。
13. 来源盘点声明 N 项、§1.2/§1.3/§2.1.1 实际行数不足 N → 覆盖闸必须 FAIL。
14. 执行记录 §3 声明多个意图通过、场景表只跑其中一部分 → 报告门必须 FAIL（无场景不算执行）。
15. 分析 §2.1 为 P0、执行记录优先级写成 P2 且 P0 失败 → 报告门必须 FAIL，`-Claim` 必须 DENIED。
16. 轻量计划声明 `版本准出=是`，或计划 §0 计数与分析不一致 → 覆盖闸必须 FAIL。
17. 执行记录每场景只写原文单源、缺互补源 → 执行门必须 FAIL（或单源+理由+接受人）。
18. 把「分析 §2.1」写成互补源，或用分析 Oracle 替代原文断言 → 执行门必须 FAIL。
19. 计划 §2 接口/探索/发布前 纳入=是，但 §3.1 无对应批次 → 覆盖闸/执行门必须 FAIL。

## 6. 变更流程

1. 说明问题与现有规则冲突/冗余；
2. 优先合并/删除，再新增；
3. 改一处 owner；
4. 跑规则卫生 + 本节 eval；
5. 更新包 `AGENTS.md` `template_version`。**业务项目会话禁止**改项目根 `CHANGELOG.md`。仅在 **AIWorkflow 母版仓**维护、且有对使用者可见的包能力变化时，由母版维护会话用产品语言记入母版根 CHANGELOG（通常开发轨落笔）；纯内部措辞收紧可不记；
6. 旧规则删除或归档；现行文档遵守「当前有效状态」（见 `doc-quality.md` §1 第9条）：不留“旧方案/已废弃/不要再用”等删后说明。
