# 文档质量标准（测试轨）

> **读取级别：参考**（交付质量检查时读；通用文档纪律以 `global-rules.md` 为准）。

> **定位**：测试轨所有文档的**通用合格线**。模板只提供结构；本文件判断“这份文档能不能用、能不能准出”。
> **适用**：环境基线、用户版业务变化说明、测试计划、意图台账、执行记录、测试报告、缺陷详单/文案、锚点清单、交接包、复盘、工作日志。
> **原则**：按文档位置定内容；测试计划不写成测试报告，测试报告不复述计划，缺陷单不写开发方案。

## 0. 冲突优先级

覆盖顺序只认 `global-rules.md` §11。

模板与本文件冲突：**先出拟改/原因/影响 → 用户确认后改本包模板并升版本 → 自检**；不按旧模板产出。

## 0.1 模板 / 实例适配

- **包内标准**：不写具体项目环境、端口、账号、组织、版本等实例事实。
- **可按项目适配**：发现模板 / 规则 / 技能不匹配或更好做法 → 先出拟改/原因/影响，用户确认后改本包并登记。
- **适配留痕**：确认后在环境基线或本地适配记录登记（文件/原因/日期/确认人）。
- **模板是骨架、标准是底线**：按项目裁剪；不适用写不适用+理由；能靠产出文档解决的优先改产出。
- **不匹配时先改产出**：优先修改当前项目生成的文档（测试计划/报告/缺陷单等），使其贴合实际并可验收。

## 1. 通用硬门槛（任一不满足 = 不合格）

1. **目的与读者明确**：开头能看出“给谁、解决什么、用来做什么决定”。
2. **事实有来源**：环境 URL/端口/IP、构建/提交、账号、日期、执行结果、通过/失败数、缺陷号、准出结论必须来自配置/台账/证据/用户确认；未验证写「未verify/待确认」，禁止猜测或把假设写成事实。
2.1 **证据成熟度 · 禁升格（硬）**：探查/短表/分析中的「待探查｜推断｜假设｜旁路试探」**不得**写入确定态载体（环境基线 §3 真值行、正式执行记录、执行记录 PASS 终态、缺陷「实现缺陷」定性等），直至升格条件满足：**写操作**＝同动作 UI 或同源 Network 成功捕获（或主读原文 + 现网成功实测）；**只读**＝契约/现网成功路径实测；或用户书面确认。**否定一条错路径 ≠ 默认真路径挂到邻口。** 未升格只留过程档（`.draft`、分析「口径待探查」列）；正式正文对该项写「待探查」或整行省略。细则指针：基线模板 §3、`tracks/api.md` 红线、`classification.md` §0。  
2.2 **证据终态制（硬）**：`evidence/` 正式树只收断言终态叶（通过关键绿证；失败终态 `字段=值` 和/或钉点截图）。中间 save/repub/试连/半成品 JSON 进 `.draft/`，**禁止**以「多叶」冒充可复核。执行记录证据列只链正式叶。
3. **范围有边界**：in/out、覆盖/未覆盖、依赖/排除分开；out 标来源/理由/确认人。
4. **可执行/可判定**：步骤、数据、预期、判定标准可被他人复现；禁“测试完成/基本正常”等空话。
5. **证据可核对**：命令/截图/日志/报告/执行记录可打开；结论必须能回到证据。
6. **一致与追溯**：需求/AC/场景/执行/defects/报告数字同口径；不出现两套统计。
7. **状态与变更**：版本/构建/日期/负责人/状态/变更记录齐；旧版归档。
8. **安全与合规**：无密钥/凭据/真实 PII；测试数据脱敏；环境/权限边界写清。
9. **当前有效状态（硬）**：正式文档以当前最终状态为唯一事实来源。
   1. 只描述当前存在的功能、流程、规则和约束。
   2. 删除后直接移除相关表述；不追加「已删除 / 已废弃 / 不要再用xxx / 禁止xxx（因旧物）」等说明。现行仍生效的约束可写（如安全红线），那是现行规则，不是删后留痕。
   3. 不记录历史修改过程、原因、旧方案和已取消内容。
   4. 不为防误解而引入当前不存在的概念或对照物。
   5. 改完以最终状态落笔，保持简洁准确。
   6. 对用户的文档/结论输出写现行结论，不复述用户需求原文，不写「本次改了什么」。
   7. 禁止在正式正文记录变更原因与废弃史；留痕仅限变更/CR / **测试分析 §0** / 工作日志 / 复盘 等允许载体，且不回流执行记录正文。
   8. 不把未采纳的修改方案、对比草案写入正式文档。
   9. **常青格同属正式正文**：环境基线、测试计划/报告现行档、 `inbound/INDEX.md`现行行等只写当前落点与角色；接入/迁移/归档等事件进工作日志或归档清单；回写覆盖终态，不追加过程句。

> **说明性输出的例外**：用户明确要求“变更说明/版本对比/复盘/handoff/培训”时，可按时间线写“此前→当前”的差异；该文本是说明材料，不是正式资产。必须标注来源/时点，不回流 PRD/方案/场景/报告等正式正文；正式资产仍只写现行状态。

10. **语言克制**：禁辩解式/对比式/冗余括注、未经确认的“应该/可能”。
11. **准出匹配证据**：PASS/CONDITIONAL/FAIL/BLOCKED 有判定依据；不替产品/开发做业务决策。

## 2. 测试文档类型矩阵

| 文档 | 位置/作用 | 必须具备 | 不应包含 | 合格判据 |
| --- | --- | --- | --- | --- |
| 环境基线 | 测试前置事实 | 环境/入口/账号/数据/版本/依赖/访问方式 | 测试结论 | 可复现、可核对 |
| 用户版业务变化说明 | 用户可读变化说明（plan） | 30 秒摘要/变化清单/业务全景/角色任务/不变与边界/FAQ/AI 索引 | 内部阶段门、缺陷号、任务 ID、内部路径、TP/AC 编号堆砌；替代测试分析/AC | 业务用户能直接看懂；AI 可定位来源；与正式依据一致 |
| 测试计划 | 版本级测试控制面 | 范围/策略/类型/入口/出口/排期/角色/风险/数据 | 测试结果、缺陷结论 | 测试可按计划执行 |
| 测试执行记录 | 执行最小单元与实际事实 | 场景/3～7步（带核对点）/预期/结果/证据/构建环境/轮次/缺陷/追溯 | 大段方案、预填“通过” | 他人可复核、可判定、与证据一致 |
| 测试报告 | 给开发/产品/协作方的准出报告 | 版本/环境/范围/结果/缺陷/未测风险/建议/证据 | 测试内部用例号/意图号/门禁名/测试数据编号；计划复述、猜测数据 | 开发/产品能直接读懂并决策；数字与执行记录一致 |
| 缺陷详单/文案 | 缺陷交接 | 复现/预期/实际/环境/构建/证据/严重度/影响 AC | 未确认的技术方案 | 开发可复现、产品可决策 |
| 缺陷台账 | 本版本缺陷记录/回归索引 | 平台单号/标题/严重度/类型/状态/发现记录/修复构建/回归结论/负责人/下一步 | 平台正文复制、内部用例号堆砌 | 回归按单号定位；状态/结论可追溯 |
| 冒烟清单 | 快速准入 | 关键路径/最少步骤/阈值/证据 | 全量回归 | 可在短时间内判定 |
| 交接单文档（默认） | 跨角色外发 | 先择优形态；介绍+对方动作清晰；按需事实；结果合格线；禁外印流程元数据 | 整表套模、考卷体风险清单、密钥、见 `{workroot}/…` 代正文 | 只拿本文即可懂情况并知道自己做什么 |
| 交接包 | 升包快照 | 00/01/必带快照；回执文件可空白；正式签收才填 | 密钥、未过门草稿、未命中触发却发包 | 接收方可独立核对 |
| 复盘 | 改进闭环 | 事实/根因/行动项/负责人/截止/验证 | 追责、空泛口号 | 行动项可验收 |
| 根 CHANGELOG | 项目发版史（仅开发维护） | — | 本包写入/补链/创建 | 本包不写；无开发包则不建 |
| 工作日志 | 本岗里程碑 | 日期/事件/结论/产出/遗留 | 根 CHANGELOG、场景/证据全文 | 可扫；含接入/治理/准出；≠发版史；可供发版核对 |

## 3. 检查清单（交付前逐项过）

- [ ] 目的/读者/范围一句话能说清
- [ ] 环境/构建/账号/数据/执行结果有来源
- [ ] 无「待探查/推断」被升格进基线真值、成功契约或实现缺陷定性（§1 第 2.1 条）
- [ ] out/未覆盖有来源/理由/确认人
- [ ] 意图/AC 可追溯到需求或提测单
- [ ] 执行结果与台账/证据一致
- [ ] 通过率/P0/P1/缺陷数同口径
- [ ] 已知问题含影响/是否阻塞/规避/计划
- [ ] 状态/版本/负责人/变更记录齐
- [ ] 无密钥/PII；链接/路径可打开
- [ ] 当前有效状态：无「已删除/已废弃/不要再用」留痕；无历史过程/旧方案/未采纳草案；结论只写现行
- [ ] 不替开发/产品下结论

## 5. 版本与构建标识（所有文档）

- **四个标识分开**：产品/测试版本（如 `{版本}`）、构建/制品（tag/commit/构建号/镜像 digest）、部署版本（build-manifest/`.deploy-rev`）、文档版本（文档自身）。**提测单只写实际部署版本**，不写文档版本/commit/tag/`.deploy-rev`；测试只认实际部署版本；代码 commit 是开发内部追溯。
- **版本节奏**：按项目版本策略（A 发布候选/B 连续迭代）；测试只记录版本与构建，不自行升版。
- **项目内可查**：项目/URL 必须提供版本查看方式（页脚、`/version`、`/health`、构建清单）；没有就补，不能靠文档 HEAD。
- **文档提交不改变构建**：禁止把 HEAD、文档 commit、文档 rev 当构建版本；代码不变，文档怎么提交都不影响被测版本。
- **提测单冻结**：起草可滚动；交接冻结为 `提测单-{版本}.md` 或 `releases/{版本}/提测单.md`；交接后改动出下一个版本/候选，不覆盖。
- **构建/发布不可变**：一次构建、同一制品晋级；变更出新版本；参考 12-Factor build/release/run、GitHub immutable releases。
- **证据**：测试报告记录部署版本、环境、版本查看证据；构建/commit 由开发在部署记录中维护，测试无需读取本地文件。

## 6. 维护

- 新增/修改模板时，同步更新本文件 §2 类型矩阵与模板索引。
- 发现“模板有结构但产出不可用” → 先修模板/标准，再修单份文档。
- 版本随包 `template_version` 更新；本文件不单独设版本号。
