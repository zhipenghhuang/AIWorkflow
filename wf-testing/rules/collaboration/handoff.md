# 协作与交接（测试轨）

> **读取级别：参考**（按节读取；按当前状态与链图只读命中节，禁止通读全本）。

> **目的**：把“产品/开发 → 测试、测试 → 开发/产品、变更 → 所有角色”的交接，从口头约定变成**可复制、可追踪**的交付（默认自洽主文档；按需标准包；回执可选）。
> **独立性**：本包可单独使用；接收方可以是本仓角色、用户本人或外部团队。交付物须自洽详实，文件夹/ZIP 即可传递。回执默认可选，仅正式签收时再填。本侧收到外部材料走资料入站（T1～T9）与 `test-basis-analysis` 等理解吸收；结构化 HO 可另走 `handoff.receive` 签收，与通用入站不互斥。
> **单一出处**：交接意图、单文档默认、包触发、回执策略、变更分级以本文为准。  
> **模板**：默认按 `handoff-note-template.md` 做**择优写法**（先分析再选形态，禁止整表填空）；升包用说明/清单/回执/台账。交付目的对等既有专模质量义务时用专模；无对等专模则五问合格线。
> **读取时机**：`handoff.*`、`testing.plan/execute/report`、`defect.*` 的handoff/变更节；不需要每次开工通读。

## 1. 角色与决策权

| 角色 | 决策权 | 主要交接责任 |
| --- | --- | --- |
| 测试负责人（A/R） | 测试策略、范围、准出建议 | 测试计划/用例、缺陷、报告、发布后验证 |
| 开发负责人（C） | 实现、修复、构建 | 提测、修复/回归、影响面、构建/环境 |
| 产品负责人（C/A） | 业务范围、AC、优先级、发布 | PRD/AC/原型/变更/验收口径 |
| 用户/业务（A/C） | 目标、预算、风险接受 | 确认范围/准出/发布 |
| 运维/SRE（C/I） | 环境、部署、监控 | 环境/数据/发布/回滚 |

**原则**：一个交付物只有一个 A；R 做、C 咨询、I 知会。测试不替产品改业务口径、不替开发改代码；oracle 必须有来源。

| --- | --- | --- | --- | --- |

| 缺陷交接 | 执行失败/发现产品缺陷 | 测试 + 开发/产品 | **有平台→只交平台**；**无平台/点名→本批统一导出**（见 §3.1.1） | 门3/计划授权 |

## 3. 交接矩阵（测试轨）

### 3.0 总策略（内容优先 · 包按需 · 与产品/开发同口径）

> **三层并存，按目的选用**（不按文档名白名单拒做）：  
> ① **专模质量底线**——对方结果对等既有专模的质量义务（计划确认、准出结论、缺陷入库、变更冻结等）→ 用该专模，字段标准照旧；示例非穷尽。  
> ② **HO 标准包**——包触发、先问后发、齐套照旧。  
> ③ **通用择优单文档**——无对等专模时走五问 + A/B/C 合格线；**禁止**用通用菜单稀释①的质量义务；也**禁止**因「表上没有场景名」拒交接。

**选用判定（必做）**：① 对方要什么结果（计划确认 / 准出结论 / 验收证据 / 知会 / 拍板）② 协调面与风险 ③ 是否正式签收。结果对等专模 → 专模；否则 → 择优单文档；仅包触发才升 HO。

| 层 | 默认交付（必产、自洽） | HO 交接包（按需） |
| --- | --- | --- |
| **任意跨角色（无对等专模）** | **择优单文档** A/B/C（五问选形态） | 仅命中包触发 |
| 计划（计划确认） | `{workroot}/{ver}/test-plan.md` 专模（含意图/风险/轮次/准出） | `PLAN`：多文件/点名要包/仓外 |
| 准出（准出结论） | `{workroot}/{ver}/test-report.md` 专模（报告门过） | `TEST`：同上 |
| 缺陷 | **有平台→只平台单**；无平台→本批统一一份详单 | `BUG`：仅无平台/`export`/点名；**一批一包**（禁逐条目录）；`FIX` 按需 |
| 变更（冻结） | CR 正文 | `CHG`：点名要包/仓外 |

**包触发**：① 多文件证据 ② 正式签收且要标准包 ③ 仓外 ZIP ④ 同发多主文档 ⑤ 明确要 HO。口语「交接」≠要包。禁止静默发包、报告完成≠必须发包、**禁止用通用模板整表顶替对等专模的质量义务**。

**回执（三包统一）**：默认不需要；正式签收或 C2/C3/发布才要；不得外印回执策略。无平台 BUG 不强制回执。

### 3.0.0 意图与择优（与开发/产品同口径）

五问 → 按目的判专模或形态 A/B/C/D → 仅触发升 HO。意图编码不印成对方章节。知会用 A；要对方确认用 B；多选项用 C。未列意图靠五问选形态，勿因「没有编码」升 HO 或硬套大表。

### 3.0.1 交付形态与合格线

**单文档合格线（结果导向）**：情况介绍清楚、对方动作清楚（或仅知悉）、判断所需事实够用；无密钥；无内部路径代结论；未强迫回执。

**交付质量**：目的对等专模用专模｜否则择优｜不偏科｜正文自洽｜外发禁内部路径与流程元数据。

### 3.1 测试发出（**先择优单文档 · 升包另闸**）

> **默认**：先判意图（澄清 80）→ 有歧义则完整【意图理解】确认；意图已清则一行回执 → 五问→形态或专模 → 落盘；**不**需 HO。含糊口令禁止直接成文。  
> **落盘**：专模真源仍写 `{workroot}/{ver}/`（如 `test-report.md`）；同轮**实拷**到 `{workroot}/handoff/outbound/{category}/`。无对等专模可直接落对应出站类别。  
> **升包**：命中触发 + 用户确认【拟发包】的**类型/接收方/必带摘要**（`confirm_handoff`）后才落盘到 `handoff/outbound/{category}/{HO-ID}/`；仅说「要包/生成/交接包」不算确认。业务门过 ≠ 发包授权。

| 时机 | 类型 | 接收方 | 最小必带（包内） | 前置 |
| --- | --- | --- | --- | --- |
| 依据澄清 | `CLAR` | 产品/开发 | 问题+原文引用+影响+建议+拍板项（正文自洽） | 按需触发 + 用户确认 |
| 计划通报 | `PLAN` | 产品、开发 | 计划关键节快照（范围/准出/缺陷策略等） | 计划门后按需 + 确认 |
| 阶段状态 | `DEC` | 产品、开发 | 阶段/范围/阻塞/预计 | 按需 + 确认 |
| 缺陷（无平台/点名） | `BUG` | 开发/产品 | 本批一份十段详单（可含多条）+ 共享证据；不依赖平台号 | §3.1.1 + 确认 |
| 回归 | `FIX` | 开发 | 原单/构建/范围/结果/证据 | 有平台写回≠自动发包；按需+确认 |
| 报告/准出 | `TEST` | 产品、开发 | 报告快照+准出摘要 | 报告门过；**默认只交报告**；包按需+确认 |
| 发布后验证 | `REL` | 产品/开发/运维 | 验证结果+证据+回滚建议 | 按需+确认 |
| 复盘 | `RETRO` | 产品、开发 | 复盘+行动项 | 按需+确认 |
| 变更 | `CHG` | 产品/开发 | CR+影响矩阵+截止 | C1+ 按需+确认 |
| 其它（无对等常用码） | `OTHER` / 项目扩展码 | 按 `00` 列明 | `00` 用自然语言写清类型意图 + 最小必带 | 按需+确认；示例非穷尽 |

### 3.1.1 缺陷通道（平台优先 · 导出统一 · 互斥）

> **现行口径**：有可用缺陷平台 → **只完整交平台**；无平台且用户确认导出 → **本批统一一份**。二者互斥，禁止并行、禁止拆成多个文件夹。

| 协作方式 | 主通道 | 本地导出 / HO | 台账 |
| --- | --- | --- | --- |
| **有平台**且本轮 `api`/`browser`（含「提交禅道/平台」） | **平台单**（十段齐 + 附件 + 指派 + 回查） | **零导出**：禁 BUG HO、禁出站实拷详单、禁「提交包」旁路、禁一缺陷一目录 | 回写平台号到执行记录；`handoff-ledger` 可记一行「平台已交 #{id}」（可选，非包） |
| **无平台** / 用户确认 `export` / 点名「缺陷交接包」「发给开发」 | **本批统一提交包** | **适用**；先问后发；确认后**只需一个**落点（见下「统一形态」） | 状态=`已发送`；条目用本地键 `BUG-…` |
| 先导出后补平台 | 先统一包，后补平台号 | 平台号只回写台账；**不**再为同批重导出（除非 C2/C3 级内容变更） | 回写平台号到台账备注 |

**统一形态（仅无平台/`export` 路径）**

- **默认**：`{workroot}/handoff/outbound/defects/缺陷提交包-{yyyyMMdd-HHmm}.md`（**一份文件含本批全部条目**；证据路径写绝对/相对引用，能指向轨内 `evidence/` 则不复制）。  
- **仅当**同批必须附多文件证据且无法外链时：才需**一个**目录 `…/defects/EXPORT-{yyyyMMdd-HHmm}/`（内含上述一份详单 + 可选共享 `evidence/`）。  
- **禁止**：一缺陷一 `HO-*` 目录、一批多个导出目录、交平台成功/进行中仍落任何导出。  
- 用户点名「标准 HO」→ 仍**本批一个** `HO-*-BUG-*`，齐套 `00～04`；不得按条拆 HO。

**硬规则**

1. **互斥**：平台已交或本轮走平台 → **不得**再生成任何缺陷导出/HO/出站详单副本。  
2. **完整交平台即完成**：标题前缀 + 十段 + 附件挂载回查 + 指派 + 台账单号；不要求本地再留「提交包」。  
3. **自包含（仅导出路径）**：读者假定没有禅道/Jira；业务语言写清复现/预期/实际/证据；禁把平台单号当唯一索引。  
4. **同源**：导出正文 = 台账终态十段（与平台 `steps` 同构）；禁「拟提交」稿、禁只贴执行记录充数。  
5. **口令**：「提交到平台/提交禅道」→ **只**平台 + writeback，**零导出**；「缺陷交接包/发给开发/无平台交接/仅导出」→ 出示【拟统一导出】摘要（条数/落点/是否带证据目录），确认后再落盘。  
6. **禁自动 / 禁静默**：报告完成、计划门、批末交平台、回归写回、平台提交成功等节点 **不得**直接生成导出；最多口头建议「是否统一导出（无平台时）」。  
7. **基线不全**：先问补 §1.3 直提 vs 本批统一导出；确认前零落盘（见 `collaboration.md` 81）。

### 3.2.1 提测接收 → 装填（测试侧映射）

- **消费字段**：提测单 §2.6（或等价）**影响面追溯 / 回归范围** → 测试侧写入分析 §2/§3、计划 §2 轨道/§3 轮次 + `suite`（通常 module；发版可 full）。
- **术语隔离**：不要求开发填写 Core/Domain/Delta、suite、装填等内部词；业务表述（改了哪些模块/接口/是否需回归）即可。
- **可选加速**：对方在 `activeContext` 同步一行影响面可加速映射，**非必填**。  
- **无提测单**：测试仍须用主读/CR/测试分析表自行补齐**直接+邻接+回归**影响面并写入 §2/§5；**禁**因无提测单跳过邻接影响面。

## 4. 交接目录与包规范

### 4.0 总目录（outbound / inbound）

> **`{workroot}/handoff/`** = 出站托盘 + 入站收件箱。真源在 `{workroot}/`；出站对报告/计划等按需实拷；**缺陷有平台时禁止**为交平台而实拷详单（§3.1.1）；`handoff/inbound/` **不作**主入口。

```text
{workroot}/handoff/
├─ handoff-ledger.md
├─ outbound/
│  ├─ 报告/ | 计划/ | 缺陷/ | 回归/ | 澄清/ | 发布/ | 变更/ | 复盘/ | 确认/
│  │  ├─ {可转发实文件}.md
│  │  └─ {HO-ID}/
│  └─ _archive/…
└─ inbound/
   ├─ 需求/ | 设计/ | 计划/ | 提测/ | 报告/ | 回归/ | 澄清/ | 发布/ | 变更/ | 缺陷/ | 复盘/ | 确认/ | 待分拣/
   │  ├─ {投放件：格式不限}
   │  └─ {HO-ID}/
   └─ _archive/…
```

**outbound 类别**：`报告`←TEST；`计划`←PLAN；`缺陷`←BUG；`回归`←FIX；`澄清`←CLAR；`发布`←REL；`变更`←CHG；`复盘`←RETRO；`确认`←DEC/OTHER。  
**inbound**：按内容归类；打开→分析→吸收→同步。与 `docs/`：原件主副本固定 `inbound/{ver|topic}`；交接工作副本进 `handoff/inbound/{category}/`；定稿进 `docs/materials/`。同仓直读对方 outbound。

### 4.1 标准包（HO）

路径：`{workroot}/handoff/outbound/{category}/{HO-ID}/`（`00`～`04`；回执模板首行可标空白未签收）。BUG 包 `02` 须十段详单。其余 ID/快照/安全同前。

### 4.2 生成步骤（`handoff.send`）

先问后发 → 落 `handoff/outbound/{category}/{HO-ID}/` 并刷新出站散文件 → validate → 台账已发送 → 同仓直读该路径（禁转发）/仓外 ZIP。输出路径须含 `outbound/{category}/`。

### 4.3 接收、分析与吸收（`handoff.receive` + 文档治理）

硬：禁止只投放。通用材料走文档治理 + materials / `test-basis-analysis`；标准 HO 签收后仍 T9+吸收。多包同仓直读对方 outbound；仓外原件主副本 `inbound/{ver|topic}` + 工作副本 `{workroot}/handoff/inbound/{category}/`。正式签收才称已接收。

**时限（正式签收）**：普通 1 工作日；阻断/提测/发布 4 小时。

## 5. 交接完成判定

| 状态 | 含义 | 能否进入下游 |
| --- | --- | --- |
| `已投放` | 入站仅落盘未分析 | 否 |
| `已分析` | 已出【入站分析】待吸收确认 | 否（除非仅 R0） |
| `已吸收` | 已吸收且同步完成 | 是（日常；≠正式签收） |
| `草稿` | 出站包未生成完/未自检 | 否 |
| `已发送` | 已生成并交给对方（回执未填或未收回） | 本侧可继续准备；不得称「已接收」 |
| `已接收` | 正式回执=接受，清单齐 | 是（正式签收完成） |
| `有条件接收` | 正式回执=有条件，非阻断缺口有主/截止 | 是，条件进计划风险 |
| `退回` | 正式回执=退回，阻断缺口未解 | 否；补件后发新版本 |
| `已取代` | 有新版本包 | 否；以新版本为准 |
| `已关闭` | 下游工作完成/验收关闭 | 是（作为历史） |

**硬规则**：日常外发以包生成/`已发送`为准，可继续本侧准备，**不得**用「须等回执」阻塞日常。**正式签收**（用户点名要回执，或发布/重大变更 C2/C3）才要求回执后标 `已接收/有条件接收`；不得用「已接收」冒充未签收。提测包日常以核对清单/准入结论为准开跑；用户点名正式签收时再填回执。

## 7. 计划回写与状态

- **计划是状态唯一入口**：`{workroot}/{ver}/test-plan.md` §0 写当前阶段/门/下一动作/待回执/健康度；§6 写执行日志；交接摘要进计划，详细在台账。
- **每次发送/接收/回执/变更**：更新 `handoff-ledger.md` → 测试计划 §0/§6 → {workroot}/INDEX.md → `activeContext.md`。四者同轮，不得只改一处。
- **计划状态**：`草稿` → `已确认` → `执行中` → `变更中` → `待关闭` → `已关闭`。
- **健康度**：绿=无阻断，且**须回执项**已齐（无回执要求不计入）；黄=有非阻断缺口/正式签收待回执/数据环境风险但可恢复；红=阻断缺口/关键门未过/准出风险。红色必须在 §0 写升级对象与下一步。
- **禁止**：用“已发送”冒充“已接收”；用“计划写了”冒充“已执行”；正式签收场景用聊天结论替代回执/变更单。

## 8. 禁止事项

1. 未过计划门就改范围/准出；清单/准入未核对就开跑。
2. 交接包无清单、无版本；或包内缺 `04-回执/` 空白模板文件（模板必带，不要求默认已填写）。
3. 正式签收场景下发送方替对方签收；用「已接收」冒充未签收。日常外发不以「未写回执」当作阻断。
4. 口头变更、先试后补单、边试边改 oracle。
5. 把密钥/凭据/真实 PII 放进交接包。
6. 用旧版本包继续执行；有新版本仍引用旧包。
7. 交接包内容与主副本不一致；包内文档被接收方修改后当主副本。
8. 变更后不更新计划/台账/索引，导致下一角色按旧口径执行。
9. 多包同仓仍要求用户把包拷/转到对方 `handoff/inbound/` 或 `handoff/inbound`（应同仓直读对方出站）。
10. 入站只投放不打开分析吸收；或把 `handoff/inbound` 当永久主副本替代原件根 `inbound/`。
