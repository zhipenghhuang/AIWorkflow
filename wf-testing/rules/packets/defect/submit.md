## 1. 元信息

- **包轨**：测试轨
- **workflow**：`defect`
- **step**：`submit`（提交或回写）
- **packet**：`rules/packets/defect/submit.md`
- **条件步** `when=defect_submit_required`：条件不满足则跳过本步（不打开本包）。
- 低风险档（L0/P0/T0）按 AGENTS 分级表可跳过未命中步骤；本包仅在执行本步时适用。

## 2. 本步目标

- **目标**：提交或回写
- **产出**：平台单号（或待确认后的统一导出路径）· 备注与状态同轮 · 可复制汇总块（collaboration.md §5.2）

## 3. 本步硬约束

- **继承开局卡**：本会话已读 `cold-start` 的八条硬约束仍全部生效（此处不复述，避免冲淡本步）。
- **本步只读**：本文 +（若 §6 列出）**一个模板**；禁止通读 rules / read-index / playbook / 未嵌入 skill。
- **完成声称**：本步有完成类 gate 时，无 `CLAIM: ALLOWED` 不得写完成/通过/可提测。
- **回执**：`reads=` 必须含本 packet 路径。

### 本步专有

- remark_writeback＝拟关/激/解决/标重复/补充澄清/回归写回备注；先出 id+备注全文再执行。 platform_submit＝计划 为批末/阶段末/收尾确认且本轮拟新建单时触发；执行批 ID 与计划 对齐；修复批可另立 `B-FIX-xx` 并在计划 登记；细则见 `rules/defects/collaboration.md` /（分流：本地消化/盯办/缺陷；待实现进缺陷清单；测本地消化不开单；外力盯办须实机类型+指派匹配或问用户）。 补充澄清用 ；回归未通过用 ；新问题用 ；非修复处置用 ；产品判定回流用 ；写后按 回查。 产品缺陷：提交后直接指派产品负责人，不经开发；产品判定非问题/重复/信息不足 → 指派回测试，按 / 处理。 建单标题：`[V版本?][测试类型]`+正文（已确认迭代版本才加 `[V…]`；类型必加；）。 列表/仅查重展示/仅建单（无状态回写）→ 跳过 remark 门；拟新建单仍按 platform_submit 门；列表子类可跳过本步直 wrap。 回写内容由编排集中生成；子代理只提供事实素材，不写平台、不改状态。 **缺陷通道（）**：`api`/`browser`/「提交禅道|平台」→ **完整交平台即完成**（writeback 回执 + 台账单号）；**禁止**同轮导出包、BUG HO、出站实拷详单、一缺陷一目录。 无平台/`export`/点名「缺陷交接包|发给开发|仅导出」→ **先问后发**：出示【拟统一导出】（条数/单文件或单 EXPORT 目录）；确认后本批**只落一份**（见 handoff ；禁「拟提交」充数；禁逐条文件夹）。 基线 不全 → 先问补适配直提 vs 统一导出；确认前零落盘。 更新台账/计划平台号；仅导出路径才更新 `handoff-ledger.md`；未回执不得写“开发/产品已接收”。

## 4. 本步门

- **HITL `confirm_remark`**：拟关/激/解决/标重复/补充澄清/回归写回 → 先列 id+结论+备注全文；确认后执行
- **HITL `confirm_platform`**：有拟入库、须问交平台/新建缺陷单/回写 → STOP（交平台用专用确认句）；**≠** git；否则跳过
- **GATE `writeback-receipt` when=remark_writeback**：运行对应 verify；未过不得宣称完成。
