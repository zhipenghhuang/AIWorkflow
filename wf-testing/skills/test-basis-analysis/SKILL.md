# 测试依据分析（技能 · 随包生效）

> 用于：`testing.plan`；分析必做，先于计划。  
> 目标：先回答“要守护什么承诺、怎么算对”，再回答“怎么测”；产出**意图台账（§2.1 SSOT）+ 风险清单 + Oracle + 待确认**，**完整覆盖方案每一个应测细节**（功能 + UI/布局/文案等），为正确检出缺陷服务。  
> 边界：本技能不写计划排期、不写执行记录；计划/执行由 `test-analysis-and-plan`、`testcase-design` 接。  
> **硬顺序**：先以方案原文逐段盘点 → 建 §2.1 具体 INT 台账（含 Oracle）→ 再让设计点/章节/矩阵回指台账；禁「只有设计点列表、无台账行」；禁「主功能齐了、UI/文案以后再说」。

## 0. 必做（按顺序）

1. **定主读**：用户点名 > 唯一正式版 > 计划已登记；未定且多候选 → 一问 + 推荐。已点名仍要做对账。
2. **多源对照**：至少读主读 + 1 个互补源（原型/接口/代码/现网/历史缺陷）；不能只看单一文档。冲突按「用户裁决/AC/PRD/契约 > 设计/原型/接口 > 代码/现网事实」；代码/现网只证明现状，不改写需求。
3. **建来源盘点（方案全细节）**：按目录逐项列——章节/标题、F/R/AC/A/N、字段、状态与非法跃迁、权限、关键异常、入口/菜单、配置/开关、NFR，以及 **UI 结构/布局/分区/组件、交互态（禁用/加载/空态）、文案/标题/按钮/校验提示/空态说明/徽标**；写清总数/已映射/N/A/缺口（可核对等式）。同步填 **章节回执**、**依据覆盖**；每个可验收单元最终须有意图或 N/A+接受人。**已映射/总数必须能被 §1.2/§1.3/§2.1.1 的实际行数支撑；空表或只写汇总=覆盖缺口（门会查）。** 方案有页面/原型/UI 描述时，§1.1 必须有「UI/布局/组件」「文案/提示/空态」行，不得整类省略。
4. **抽意图（台账 SSOT）**：每条可独立判定“过/不过”的承诺一行**具体** `INT-<域>-<短名>`（禁簇名当行）；写来源、条件→动作→可观察结果、**可观测 Oracle**（禁「通过/正常」；P0/关键须**点名字段/码/文案/计数**，禁仅「状态正确/有原因/已联动」）、优先级 P0/P1/P2、不可接受失败、处置、接受人。同义用两字段/两载体表达时，Oracle 写清**对账点**。P0/P1/P2 都必须执行；N/A 必须有接受人。本轮 `处置=测` 的项必须先落本表，再被设计点引用。UI/文案类同样要有可观察 Oracle（可见文案/布局区/控件态）。
4.1 **AC/设计点账本**：每个 AC/F/R/N/设计点，以及方案写出的 UI 布局/组件/文案/提示/空态，至少一行；意图列只填 §2.1 **已存在**的具体 INT；禁只写簇名；禁台账外 ID。设计点=方案条目→台账映射，不是第二套意图库。
5. **铺覆盖矩阵**：模块/流程 × 13 面（主路径/状态/边界/权限/并发/审计/通知/迁移/非功能/视觉/集成/计算/负向）逐格 `INT/场景` 或 `N/A+依据`；空格=缺口；有 UI 时「视觉/UI」不得无依据整格 N/A。
6. **铺质量特性 + 方法矩阵**：先过 ISO 25010 八类（功能/性能/兼容/易用/可靠/安全/维护/可移植）标适用/方法族/意图或 N/A+依据；再按 P0/关键规则 × 常用方法（等价/边界/判定/状态/场景/算例）+「其他方法」列逐格有落点或 N/A+依据；P0 至少两种方法或写「单方法足够+依据」。只测主路径不算完整。
7. **过细节维**：D01–D13 + S6/S7/S11 逐维适用/意图/判定面/依据；有 UI 时 D05/D08/S6/S7/S11 默认适用，须有 INT 或业务依据；S6/S7/S11 是功能收口探针，不是可选建议。
8. **扫风险**：逐类过资金/对账、状态、幂等/并发、异步/回调、权限/数据域、迁移/回滚、外部依赖、历史事故、空值/业务语义、可观测/假成功、UX/可访问性；命中写 `RISK-*`。
9. **定 Oracle**：需求原文 > AC > 契约 > 业务规则 > 用户裁决；现网实现只能作现状，不能自动当预期；未写死写「以本构建实现值为准」，执行前先读口径。方案声明的追溯字段（规则/计算/来源版本、来源对象等）写入 Oracle；失败/降级类写「用户可读原因」，原始异常文本不作合格标准。
10. **标隐式**：推断项标 `[隐式]`，必须确认后升格；未确认不得写确定断言。
11. **关缺口**：无来源/Oracle 的意图标 GAP；交付缺口（范围内应有入口/能力未交付）单独标，执行转 `待实现`/`fail`+缺陷，不当观察。
12. **画影响面**：直接/邻接/上游/下游/共享数据/事件/回归逐层有模块/依据/意图/覆盖/责任人；无提测单也自建。
13. **列核心链路**：每条用户能办结的主链，入口/关键步骤/意图/P0 冒烟；初版全量，迭代覆盖受影响主链+上下游回归。
14. **回写**：分析文件是源头；计划引用计数与摘要，不重复大表。

## 1. 来源怎么读（多源对照）

> 至少读主读 + 一个互补源（原型/接口/代码/现网/历史缺陷）；不能只看单一文档，也不能只看分析。冲突按「用户裁决/AC/PRD/契约 > 设计/原型/接口 > 代码/现网事实」；代码/现网只证明现状，不改写需求。

**第一遍：结构与 ID**
- 文档类型/版本/状态/owner/日期/适用范围；主读与对照。
- 目录/章节/AC 编号；先建“来源盘点”，不急着写意图。
- 变更记录：本版相对上版增/改/删；旧版是否仍被引用。

**第二遍：语义 + UI/文案**
- 名词（对象/字段）→ 动词（动作/状态变化）→ 规则（约束/口径/计算）→ 异常（失败/边界/权限）→ **界面（布局/组件/文案/提示/空态）**。
- 每个 `must/must not/禁止/不得/仅/至少/不超过` 都要有反向或边界意图。
- 每个状态：合法迁移 + 非法迁移；每个权限：正例 + 拒绝；每个字段：必填/格式/范围/默认/计算；每个入口：可达 + 缺省/无权限；每个配置：生不生效；**每个「须关联/绑定/挂接」**：配置面可达（入口/字段/API）须有意图，不得只靠下游检查兜底。
- 每个写出的页面/区：结构与关键控件在；每个写出的文案/提示/空态/按钮名：可观察一致或进入偏差择优（执行阶段判定）；每个交互态：禁用原因/加载/失败下一步诚实。
- 含糊形容词（快/稳定/友好/合理/尽量）→ 问出可判定值，或标 GAP。

## 2. 意图卡片（最小字段）

```text
INT-012-IDEM
来源：PRD §7.3 / AC-05
意图：同一订单重复提交支付请求时，只扣款一次并返回首次结果
Oracle：支付流水 1 条；订单状态=原态；响应幂等键=首次；同键异体→拒绝+冲突说明
风险：P0
不可接受失败：二次扣款/状态错乱/同键异体仍成功
处置：测（API+脚本）
```

- 一条意图只表达一个可判定承诺；不要把多个无关规则塞一行。
- **配置契约与结果门禁分列**：同句既写「须能关联/绑定/挂接」又写「缺失须阻断/不得当成功」→ **至少两条** INT（配置面可达+字段/键；消费端读入或阻断定位）；禁只留门禁吞掉配置面。
- 一个意图可有多个场景；场景不是意图，不写进台账的“意图”列。
- 计算类：公式/输入/精度/最小分母集/期望值；分母 0/缺维单列。
- 负向类：写“本该发生的仍发生、本不该出现的未出现”，不只抄条款。
- **Oracle 自检**：第三人只看台账行能否判过/不过；不能→改写到字段级再往下排。

## 3. 风险怎么设计（人确认，AI 提议）

1. AI 按 §0 第 8 步逐类给候选；每类写“适用/不适用+依据”，不留空。
2. 人确认“不可接受的失败”与优先级；P0必须有 Oracle 和深度要求。
3. 风险 → 意图映射；一个风险可对多意图，一个意图可挂多风险。
4. 历史事故/线上问题：有则逐条转意图/锚点；无则写「无历史输入」并说明。
5. P0未确认 → 计划门不过；低风险可用默认清单 + 明确“无额外风险”。

## 4. 歧义 / 冲突 / GAP

| 类 | 处理 |
| --- | --- |
| 时间/边界/数值含否 | 问起算点、端点、取整、时区；问不到写假设+GAP |
| 规则冲突/术语不一致 | 列双方原文+位置；默认不选边；用户裁决后写 SSOT |
| 异步/并发/顺序 | 问判定时限、谁先谁后、重试/补偿；无时限=不可测 |
| 部分成功/部分失败 | 问按比例/全额、负数/欠额、逐条结果 |
| NFR 无指标 | 问吞吐/并发/响应/兼容基线；或书面“本版不验证” |
| AC 不可观测 | 问可观察结果；问不到标 GAP，不写“正常/成功” |
| 交付缺口 | 范围内菜单/路由/关键能力缺失，或有入口 404/500/空壳 → 执行 `待实现`/`fail`+缺陷 |

> 关键 GAP 未关 → 禁写确定断言/禁宣称准出；N/A 必须有人接受。

## 5. 输出检查

- [ ] 来源盘点无缺口；含 UI/文案类（方案有 UI 时）；章节回执、依据覆盖无未解释缺口。
- [ ] §2.1 台账：每条具体 INT + 来源 + 可观测 Oracle + 优先级 + 处置 + 接受人；P0 有不可接受失败；无簇名行；UI/文案类有可观察断言。
- [ ] 「须关联/绑定」与「缺失须阻断」已分列意图（或 N/A+依据）；无门禁吞配置面。
- [ ] §2.1.1 设计点：每条方案可验收单元有行（含 UI/文案）；意图列只映射台账已有 ID。
- [ ] 质量特性八类有适用/依据；模块×面（含视觉/UI）、方法×规则（含其他方法）、D01–D13 + S6/S7/S11 无未解释空格；有 UI 时 D05/D08 等不得无依据整否。
- [ ] 风险逐类有结论；历史事故已考虑。
- [ ] 影响面直接/邻接/上游/下游/共享数据/事件/回归有落点或 N/A+依据+接受人。
- [ ] 核心链路每条有意图/P0 冒烟或 N/A+依据。
- [ ] 隐式项已确认或标待确认。
- [ ] 负向/计算/权限/状态类有可观测断言。
- [ ] `-Mode coverage` 可 PASS（结构完整）后再写计划/开跑。

## 6. 常见坑

| 坑 | 纠正 |
| --- | --- |
| 只读 PRD 不读原型/接口/代码 | 至少读主读 + 对照；冲突列原文 |
| 把“文档没写”当“不用测” | 标 GAP/问；行为仍要验证 |
| 把现网实现当预期 | Oracle 来自需求/AC/契约/裁决；现网只作现状 |
| 把交付缺口写成观察/GAP | 范围内未交付→待实现/失败+缺陷 |
| 只写模块名/页面名 | 每行是可判定承诺，不是清单标题 |
| 推断当规格 | 标 `[隐式]`，确认后升格 |
| 只测主路径 | P0按深度补负向/状态/权限/幂等/恢复 |
| 只有设计点/簇索引无台账 | 先建 §2.1 具体 INT+Oracle；设计点只回指 |
| 用簇名 INT-240 当台账行 | 拆成 INT-240-CHK 等具体行 |

## 7. 参考

- ISTQB 测试分析（test conditions）、ISO/IEC/IEEE 29119-3。
- 企业 RTM：需求/AC → 意图 → 场景 → 结果 → 缺陷。
- 方法内化：来源对账、Oracle 分离、风险驱动、证据闭环。

## 8. 常见合理化与反驳

| 合理化 | 现实 |
| --- | --- |
| “文档没写就是不用测” | 未写≠免测；标 GAP/问，行为仍要验证。 |
| “现网就是这样，按现网写预期” | 现网是现状，不是需求；Oracle 来自原文/AC/契约/裁决。 |
| “先写用例再补分析” | 先有意图/风险，场景才有依据。 |
| “风险让 AI 想就行” | 人必须确认“什么失败不可接受”；否则漏隐含规则。 |
| “细节太多，先测主路径” | P0细节缺失=覆盖缺口；按风险补深度。 |
| “UI/文案执行时再看” | 否；分析阶段就必须盘进 §1.1/§1.3/§2.1.1；执行只对照与择优判定。 |
| “视觉/文案整行 N/A 省事” | 方案有页面/文案时禁止无依据整类 N/A。 |
| “交付缺口记观察就行” | 范围内未交付→待实现/失败+缺陷。 |
| “设计点表写满了就算覆盖方案” | 否；闸只认 §2.1；无 Oracle 的映射不算可测意图。 |
| “Oracle 写『状态正确/有失败原因』就行” | 否；须字段/码/文案可复核；同义多表要对账；SQL/堆栈原文≠合格原因。 |
| “大方案先用簇 ID，台账以后补” | 本轮要测的 INT 必须先有台账行；覆盖闸不过不得开跑。 |
| “先粗计划，细节执行时再分析” | 违规；方案每一个应测细节须本步入账；执行自主不回补空账。 |
