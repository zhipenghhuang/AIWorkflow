## 1. 元信息

- **workflow / step**：`defect` / `apply`（联动与评审）
- **packet**：`rules/packets/defect/apply.md`
- **角色**：`pm-lead`（交付编排与变更处置（排期/跟进/受理/变更/缺陷平台/UAT/发布/复盘/展示））。统一受理需求与问题 → 分诊定性 → 影响评估 → 处置确认 → 联动更新 → 验证关闭；平台缺陷可拉取、分析并回写；本步只做该角色职责；越界交回或升级。

- **后续**：`review`（进 `review` 前的 `when=substantive_change`）
- **失败去向**：回 decide；非产品缺陷只产处置单，不改 PRD/AC/计划

## 5. 本步动作

> **本节 = 本步编排与门槛**（顺序、产出、门、禁做）。
> **方法质量在技能**：§6 列为必开/条件开的 skill 必须按闭环执行，**禁止**把技能正文粘进本包替代实读；**禁止**为省事跳过必开技能。

- **本步必开技能（质量不降）**：`change-management` → 见 §6 闭环。

### 本步动作清单

- **仅在 decide 确认后执行**。
- 纯拉取/只读分析止于 analyze，不落处置单。
- **产品缺陷才更新 PRD/AC/计划/UAT**。
- 实现缺陷/非问题/重复/信息不足只产缺陷处置单与回执，不进入 PRD/AC 更新。
- 即使无需联动，也至少落缺陷处置单/受理单回执。
- 不适用项写原因。
- 按 `change.apply` 规则更新 PRD/AC/原型/交付计划/产品计划/需求池/UAT/发布检查。
- 已有受理单（pull 建档）就地更新，不重复建档。
- 同一缺陷多轮处理只留一份现行受理单。
- 产品缺陷确认 → 产出 `{workroot}/{ver}/30-changes/缺陷处置-{BUG-ID}-{主题}-{yyyyMMdd}.md` （模板 `rules/templates/30-review-change/product-defect-disposition-template.md`），写清判定、依据、新口径、对开发要求、验收标准、指派对象。
- 实现缺陷/非问题/重复/信息不足也产出缺陷处置单（说明+下一步+指派），不要求 PRD 变更。
- 实质变更 → 走 review 步（产品视角：是否解决原问题/AC 影响/范围/风险；不评价技术实现细节）。
- 生成回写附件：缺陷处置单/受理单/变更单/评审意见/PRD 变更摘要（按需）。
- 不修改代码或技术方案。
- **缺陷双通道**：平台已回写（`defect.writeback`）→ **不**再强制 `BUG` 整包。
- 无平台/`export`/用户点名「缺陷交接包」→ **先问后发**，确认后 `handoff.send` 自包含处置详单。
- 平台附件与包内口径同源，禁重复造口径。
- 联动审计（子代理编排 ）：≥4 份受影响文档 → 单写手完成后派 verifier-agent 只读核验（受理单 ＋改动产物），返回未更新/旧口径/待补 ≤30 行。
- 三包独立：产品文档落本包目录，附件上传平台。
- 不引用开发/测试包内部路径。
- 平台附件/开发评估单/新产品文档：先按 文档治理规则（工作根/原件根/索引/关版整夹） 【入站分析】（多为 T6）。
- 确认后落 `inbound/{ver|topic}/`，同步处置结论到工作区。
- S1/S2/S3 同批进 `inbound/_archive/`。

### 本步规则卡：文档治理

- 外部输入先入站：落 `inbound/{ver|topic}/` 或 `_common/`；登记 `inbound/INDEX.md`；确认后才改名/归档；不把原件迁出 inbound。
- 迭代关账：确认后将迭代绑定文档迁入 `{workroot}/_archive/{yyyyMMdd}-{ver}/`；主档关闭时快照、主档不移动；「并行不关」只落新资料、不归档现行主档。
- 清理只删已知临时/缓存/未引用失败产物；不确定移 `_archive/_pending-cleanup/{yyyyMMdd}/` 并写清单。
