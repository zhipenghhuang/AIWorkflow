## 5. 做法

### 技能 `prd-writing`

# PRD 撰写（技能 · 随包生效）

> 用于：prd 步。按 `rules/templates/10-planning/prd-template.md` 落盘；本技能=把 PRD 写到**可开发、可测试、可追溯**。  
> **写前门槛**：须已完成理解+方案双确认（受理单/澄清记录/需求池确认列）；澄清程序**按 澄清纪律（一次一问、候选答案、未确认不升格）。**未双确认不得**写正式 PRD / 称可开发（可出标「待确认」草稿）。每条 F/R/AC 必须能指到来源；无来源列 `Q-xx`；未确认推断标「假设」。禁止把单个客户/竞品做法/领导偏好写成市场需求。

## 1. 写作顺序（16 节）

元数据 → 摘要 → 背景/依据 → 用户/场景 → 范围/边界 → 功能 F-xx → 业务流程图 → 状态机 → 权限矩阵 → 数据/字段来源 → 校验规则 R-xx → 异常/边界 → NFR N-xx → 埋点/指标 → 验收 A-xx/AC-xx → 追溯矩阵 → 待确认/决策 Q/C → 评审误区/依赖/风险/里程碑/变更。

## 2. 图（Mermaid 必填）

- **主流程**：`flowchart TD`，判断出线标“是/否”；异常/补偿路径可见；复杂流程加子流程。
- **状态机**：`stateDiagram-v2`，状态×事件；每个非法跃迁写拒绝表现；终态重入必须定义。
- 图与文字同源：图中每个节点在功能/rules/验收中有对应；不做“装饰图”。

## 3. ID 与追溯（企业级核心）

- `F-xx` 功能、`R-xx` 校验规则、`A-xx` 验收场景、`AC-xx` 验收标准、`N-xx` 非功能、`Q-xx/C-xx` 待确认/已确认。
- 每个 F 至少 1 条 AC；每个 R 至少 1 个 A；追溯矩阵 F→R→A→AC→原型→测试→版本不能空。
- 测试用例后续用这些 ID 反查；改名/删除 ID 必须同步矩阵与测试。

## 4. 三个最容易漏的结构

- **状态机**：状态×事件矩阵；非法跃迁；终态重入。
- **权限矩阵**：角色×操作×数据域（本人/部门/全部）；未定义标「待确认 + 责任人」。
- **字段来源**：字段/类型/必填/范围/默认/来源/校验；表结构归开发。

## 5. 校验规则（R-xx）

- 完整性、一致性、门槛、唯一性、金额/数量/日期口径；每条写比较对象、失败表现、阻断/提示。
- 不允许“系统自动校验”一句话；写清比较什么、失败怎么办。

## 6. 验收标准写法

- 公式：**条件 + 动作 + 可观测结果**；
- 好：`已登录管理员在X页点[保存]后，列表新增一行且状态=待处理，重复保存不新增`；
- 坏：`保存功能正常`；
- 每条 F ≥1 AC；异常/边界各 ≥1；A-xx 用 Given/When/Then 或步骤+预期。
- 验收矩阵每行补 `优先级 / 类型 / owner / 执行阶段`；类型按 `DEV-AC / QA-AC / REL-AC` 分层。
- 验收矩阵是验收资产，不是开发任务；开发只承接 `DEV-AC`，`QA-AC/REL-AC` 交测试/UAT。
- 独立执行记录用固定列：场景 ID / 构建环境 / 角色及数据单号 / 执行时间 / 实际结果 / 结论 / 证据/缺陷号；结论只能是“通过/失败/未执行”。

## 7. NFR / 指标

- NFR 只写目标/约束 + 验收方式 + 待确认；不写实现。
- 指标：事件/触发/属性/指标/观测窗口/基线；无埋点写「不适用 + 原因」。

## 8. 引用、待定、技术边界

- 引用「来源 + 日期」，可回查；查不到写「待验证」。
- 待定：责任人 + 期限 + 影响；未标注 TBD 不允许。
- 技术边界：产品不写架构/技术栈/DB/API/部署；需要可行性列问题交开发/用户。

### 8.1 AI 产品需求补充（如适用）

- **任务与失败成本**：用户要完成什么；错误输出的后果；哪些场景必须人工确认/转人工。
- **可接受/不可接受输出**：事实错误、越权、泄露、危险建议、格式破坏等；写成可判定验收。
- **数据边界**：哪些数据可输入/可保留/可出境；PII/密钥/商业机密；供应商条款由开发/法务确认。
- **兜底与透明度**：低置信/超时/模型不可用时的行为；是否标注 AI 生成；是否可编辑/撤销。
- **质量度量**：评测集/通过阈值/红队/线上反馈；不只写“准确率≥90%”，要写口径与样本。
### 技能 `analytics-and-experimentation`

# 指标、埋点与实验（技能 · 随包生效）

> 用于：PRD 的指标/埋点节、发布度量、功能验证、增长实验、复盘归因。  
> 定位：**先有决策问题，再有指标；先有口径，再有数据**。指标不是“上线后看看”，而是验收的一部分。  
> 边界：数据平台/SQL/BI 属开发/数据侧；本技能定义产品口径与验收方法。  
> 不适用：无用户/无数据决策的内部工具；写「不适用 + 原因」，不硬造指标。

## 1. 从决策问题到指标

- 先写：**要做什么决策？**（继续/停止/加投/改方案/放量）——没有决策的指标不采集。
- 指标树：北极星（用户价值）→ 输入指标（可影响）→ 护栏指标（不能被伤害）→ 诊断指标（排障）。
- 一个指标一个定义：名称、口径、公式、分子/分母、时间窗、过滤条件、数据源、owner。
- 分群：新/老、角色、租户、渠道、版本；避免整体平均掩盖局部恶化。
- 反虚荣：注册数/页面浏览量/总时长单独看不算成功；要连到激活、留存、转化、任务完成。

## 2. 事件字典（埋点单一出处）

| 字段 | 要求 |
| --- | --- |
| 事件名 | `{对象}_{动作}`，过去式/稳定语义；禁止 `click1`、`test` |
| 触发时机 | 成功/失败/提交前/响应后，写清唯一时点 |
| 属性 | 名称、类型、必填、枚举、示例、隐私级别 |
| 身份 | 匿名/登录/租户；id 变更与合并规则 |
| 来源 | 客户端/服务端；以哪端为真 |
| 版本 | 事件 schema 版本；废弃/重命名迁移 |
| owner | {workroot}/数据/开发责任人 |

- 客户端事件易丢/易重复；关键业务以服务端为准，客户端只补交互。
- 命名、属性、枚举一次定清；上线后改名=破坏历史数据，必须走版本/双写/迁移。
- 埋点与功能同批交付；无埋点写「不适用 + 原因」，不事后补。

## 3. 漏斗、留存、 cohort

- 漏斗：步骤、时间窗、是否允许回退/重复、分母是谁；每步流失要能解释。
- 留存：次日/7 日/30 日口径；新用户定义、激活定义、时区；避免幸存者偏差。
- cohort：按首次使用/版本/渠道分组；对比同口径，不拿不同窗口硬比。
- 归因：区分相关与因果；多渠道/自然流量/内部流量要标注。
- 数据质量：空值/重复/时区/机器人/测试账号；上线前做事件校验与对数。

## 4. A/B 与灰度实验

- 假设：`因为…，如果…，则…指标会…`；先写主指标、护栏指标、最小可检测效应。
- 单元：用户/租户/会话；避免同一用户跨组；随机化与分流比例可复现。
- 样本与时长：按基线/方差/效应算样本量；不要“跑两天看看”；避免提前偷看（peeking）。
- 护栏：错误率、延迟、投诉、退款、取消率；护栏恶化立即停。
- 分析：意向治疗（ITT）、SRM 检查、置信区间、多重比较校正；统计显著 ≠ 业务显著。
- 决策规则：上线/回滚/继续/扩大样本，实验前写清；事后不改假设。
- 不能做随机实验时：准实验/前后对比/匹配，明确混杂因素与局限，不冒充因果。

## 5. 隐私与合规

- 最小化：只采决策必需字段；不采敏感个人信息；自由文本慎采。
- 同意/告知：按地区与业务要求；拒绝追踪时仍保证核心功能。
- 保留/删除：期限、聚合、导出/删除路径；跨境与供应商条款。
- 权限：看板/原始数据按角色脱敏；小样本防重识别。
- 参考：PIPL/GDPR（按适用）、公司数据分级；不把“匿名化”当口号，验证可重识别风险。

## 6. 发布与验收

- 发布前：事件字典、埋点实现、数据校验、看板/告警、基线值、决策规则齐。

### 技能 `customer-needs-discovery`

# 客户需求发现与确认（技能 · 随包生效）

> 用于：`change.intake` / `prd.discover` / `prd.prioritize` / `new-product.discover` / `plan.goals`。  
> **产品职责**：多问、问准，把「谁/场景/问题」与「怎么做（方案要点）」问清楚，并拿到用户明确确认；不替用户拍板，不省问偷跑。  
> 目标：先回答“**谁、在什么场景、遇到什么问题、现在怎么解决、代价多大、要达成什么结果**”，再与用户确认“**推荐方案要点是否按此做**”，最后才谈排期与写 PRD。  
> 边界：本技能不写全量 PRD、不定最终优先级数字；不把单个说法当市场结论。澄清格式唯一出处：澄清纪律（一次一问、候选答案、未确认不升格）。

## 1. 角色地图（先分清谁是谁）

| 角色 | 要问 | 为什么 |
| --- | --- | --- |
| 使用者 | 谁每天用？在什么场景？ | 决定真实流程与痛点 |
| 付费人/决策人 | 谁批准预算？谁签字？ | 决定价值口径与采购约束 |
| 影响者 | 谁提建议/反对？ | 决定采用阻力 |
| 阻塞者 | 谁能让项目停？ | 合规/安全/IT/法务 |
| 现有替代 | 现在用什么？Excel/人工/竞品？ | 决定切换成本与真实需求强度 |

- 一个“客户”可能同时是使用者/付费人/决策人；分开记录，不合并。
- 角色不明 → 先问“谁最痛、谁付钱、谁拍板”，一次一问；可多轮直到清楚。

## 2. 证据分层（每条结论都要能回查）

| 等级 | 证据 | 可信度 | 用法 |
| --- | --- | --- | --- |
| E1 | 直接观察/现场跟岗/行为数据 | 高 | 可作需求依据 |
| E2 | 一对一访谈（过去行为+具体案例） | 较高 | 需交叉验证 |
| E3 | 工单/客服记录/反馈原文 | 中 | 看频次与样本 |
| E4 | 问卷/销售转述/领导意见 | 较低 | 标样本与偏差 |
| E5 | 竞品/行业报告/最佳实践 | 参考 | 不能直接当客户需求 |

- 记录：来源 + 日期 + 样本量 + 原话（脱敏）；无来源写“待验证”。
- 单个客户/单次访谈 ≠ 市场需求；至少交叉 2 个来源，或显式标“单点证据”。
- 竞品做法只能证明“有人这样做”，不能证明“你的客户需要”。系统拆竞品/学习模仿走 `skills/competitive-intelligence-and-learning/SKILL.md`（S/P 两档）；本技能只负责把借鉴回绑到「谁/场景/问题」。

## 3. 访谈法（Mom Test 精神）

- 问**过去的行为**与具体案例，不问“你会不会用/你觉得好不好”。
- 一次只问一个问题；追问“上次遇到是什么时候、当时怎么解决、花了多少时间/钱、最后结果如何”。
- 不问引导性问题（“如果有个功能能…你会用吗”）；不问假设性问题。
- 记录原话，不把推测写成用户结论；对方用“应该/通常/最佳实践”时，追问具体场景与代价。
- 可反问：**“如果不用向任何人交代，你真正想要的是什么？”**
- **承诺信号**：愿不愿试点、预付、介绍同事、占用日历；“听起来不错”不算承诺。
- 访谈对象不足/无法访谈 → 用现有工单/数据/行为证据，标缺口，不编访谈；对**产品决策用户**仍须按 澄清纪律（一次一问、候选答案、未确认不升格）。
- 需要正式访谈时：用模板 `rules/templates/10-planning/interview-guide-template.md`；综合用 `rules/templates/10-planning/insight-synthesis-template.md`。

## 4. 问题定义（先问题，后方案）

```text
谁（角色）：
在什么场景/触发条件：
遇到什么问题：
现在怎么绕过/替代：
代价（时间/成本/风险/机会）：
频率与严重度：
期望结果（不是功能）：
怎么算成功：
明确不做什么：
```

- 用“问题陈述”而不是“功能清单”开头；功能是候选解，不是需求。
### 技能 `requirement-discovery-and-prioritization`

## 常见合理化与反驳

| 合理化 | 现实 |
| --- | --- |
| 「先排进版本再澄清」 | 理解→方案双确认未过不得入池承诺。 |
| 「客户喊得响=优先级高」 | 用价值/风险/成本矩阵；嗓门不是 RICE。 |
| 「范围可以边做边定」 | 无边界=无 AC；未定义完禁评审通过。 |
| 「竞品有的我们都要」 | 对标是输入不是清单照搬；写非目标。 |
### 技能 `competitive-intelligence-and-learning`

# 竞品情报与学习模仿（技能 · 随包生效）

> 用于：`prd.discover`（口令「竞品分析」/0→1 市场验证）、`prd.benchmark`（口令「竞品对标」）、`new-product.discover`、`prototype.context`（设计借鉴时）。  
> **目标**：把同类竞品拆清楚，并把可学习点变成**可验证的本产品决策**——不是抄功能清单，也不是无视市场。  
> **边界**：不写全量 PRD；不替用户定差异化终裁；澄清格式仍认 澄清纪律（一次一问、候选答案、未确认不升格）。  
> **与相邻技能**：问题还原先 `customer-needs-discovery`；入池/优先级用 `requirement-discovery-and-prioritization`；0→1 立项用 `zero-to-one-product-definition`；体验借鉴用 `prototype-and-interaction` / `ui-visual-design-system`。

## 0. 两档模式（强制先选）

| 档 | 何时用 | 口令/入口 | 产出 | 入池纪律 |
| --- | --- | --- | --- | --- |
| **S 选择性学习** | 0→1、战略、新品定位、点名「竞品分析」 | `prd.discover` / `new-product.discover` | `竞品分析-*.md` | 借鉴项须回绑本产品问题；验证后才承诺版本；**不得**把竞品功能直接当客户需求 |
| **P 对标跟进** | 已有产品线迭代、点名「竞品对标」/功能差距/parity | `prd.benchmark` | `竞品对标-*.md` | 差距项可进需求池**候选项**（来源=`竞品对标`）；排进版本仍须价值/成本初判 + 用户确认范围；证据可只用公开资料+日期 |

- 分不清 → 有产品线且要「我们也要有/对一下功能」→ **P**；空白新品/要定位差异化/Go 决策 → **S**。  
- 同会话可先 S 再 P，不得混成一份无模式标注的文档。

## 1. 对象清单（开拆前）

| 项 | 要求 |
| --- | --- |
| 本产品定位一句话 | 谁 / 什么场景 / 什么结果（可来自档案/计划/用户确认） |
| 竞品集合 | 直接竞品 2～5 + 替代方案（Excel/人工/外包）≥1；写选取理由 |
| 资料来源 | 官网/定价页/帮助中心/试用/应用商店评/公开案例；每条 **链接+日期**；禁凭印象 |
| 能力 | `browser-mcp` 已装则打开页面取证；未装=用户粘贴/截图/链接，不阻塞 |

**扇出**（`rules/collaboration/subagents.md` §2）：≥4 独立竞品/来源 → 按来源只读扇出，返回证据表 ≤30 行；定位/借不借/对标结论**集中**由主 agent 写。

## 2. 模式 S — 选择性学习（分析 → 借/改编/不借 → 验证）

### 2.1 拆解维度（按需全做；缺维写「未覆盖+原因」）

| 维 | 看什么 | 记什么 |
| --- | --- | --- |
| 定位 | 声称服务谁、解决什么 | 一句话 + 证据链接 |
| 用户与场景 | 公开案例/评价里的真实用法 | 场景摘要 |
| 核心流程 | 完成关键任务的步骤数/门槛 | 流程要点 / 摩擦点 |
| 功能簇 | 模块级能力（非按钮级流水账） | 有/弱/无 + 备注 |
| 体验 | 密度、引导、空态、移动/打印 | 可借鉴交互模式 |
| 定价/包装 | 套餐、限免、增购 | 价格带（来源+日期） |
| 获客/信任 | 渠道、社会证明、合规宣称 | 可观察事实 |
| 明显短板 | 差评/缺失/过度复杂 | 机会点 |

### 2.2 学习决策表（每条必填）

| ID | 观察（竞品做法） | 决策 | 对本产品的改编 | 回绑的问题/机会 | 验证方式 | 入池建议 |
| --- | --- | --- | --- | --- | --- | --- |
| L-01 | `{…}` | **借** / **改编** / **不借** | `{怎么用在本产品}` | `{谁/场景/问题}` | `{访谈/原型/数据/试用}` | 入池候补 / 仅设计参考 / 丢弃 |

- **借**：交互/信息结构可近似复用；仍须写「为何适合本用户」。  
- **改编**：学意图不学外形；写清改哪几处。  
- **不借**：写原因（不合定位/合规/成本/已有更好替代）。  
- 禁止空表「全面对标后抄齐」；S 档至少产出 **3 条**学习决策（可含不借）。

### 2.3 差异化一句话

- 相对直接竞品：我们**坚持**什么、**放弃**什么、**独特**什么（各 ≤1 句）。  
- 无差异化也可：写「效率工具，优先一致可预测」+ 依据。  
- 差异化主张进立项书 §3 / 产品计划，**须用户确认**后才当已定定位。

### 编排备忘

skills_required: prd-writing｜skills_optional: analytics-and-experimentation（有指标/埋点/实验才读） 前置：产品计划已确认，或单需求范围已经 `confirm_scope` 批准；两者都无 → 先补一行范围确认（一次），不直接写全量 PRD。 已在需求池/立项书/计划范围内 → 直接写；未定性新输入 → 先走 `workflows/change.yaml` intake，不跳过受理。 **写前先读**：确认的客户需求理解/受理单/需求池/证据；每条 F/R/AC 必须能追溯到来源（访谈/工单/数据/文档/裁决），无来源列 `Q-xx` 待确认，不臆造；未确认的推断标「假设」。 理解门先行：`confirm_understanding` 按 `rules/core/clarification.md` 出示理解复述+方案要点；**未双确认不得**落正式 PRD（可出草稿并标待确认）。 P2+ 且开发/测试角色可得时，按 `rules/collaboration/handoff.md` 做需求澄清（Three Amigos）：产品讲问题/AC，开发讲可行性/影响，测试讲可测性/oracle；产出澄清记录（问题/示例/AC/待决，可并入 PRD 的变更记录节或评审记录）并回写 PRD；角色不可得则跳过，不阻塞。 技能：`skills/prd-writing/SKILL.md`（先读再写）+ `skills/analytics-and-experimentation/SKILL.md`（指标/埋点/实验，可选）；自检清单与 `skills/review-and-finalize/SKILL.md` 同源。 要素齐：背景/目标与指标/用户场景/功能清单/流程/状态机/权限矩阵/字段rules/异常边界/非功能/埋点/验收标准/范围排除/依赖风险/里程碑； **多需求/版本级**：用 `rules/templates/10-planning/iteration-plan-template.md` 汇总范围、功能覆盖、验收矩阵、执行记录与发布条件；PRD 保留单需求明细。验收矩阵先标 `DEV-AC/QA-AC/REL-AC`，不得原样转开发任务。 写不出验收标准 = 需求未定义完；禁臆造用户反馈与数据（引用可回查）。 **级别**：P0/普通 P1 → 轻量模板；**P1↑**（权限/资金/隐私/不可逆数据/主数据规则）→ 作者自检按 P2，可用轻量壳但须补权限/rules/异常/AC；P2+ → 全量模板。 **作者侧硬纪律**：完稿必须产出【完稿自检摘要】（见 prd-writing ）；`gate_when: prd_structure_required` → 跑 `-Mode prd`（`gate: product-prd`）。BLOCKED → 不得进评审/定稿；DRAFT → 可审不可定稿；进定稿/交开发前 P2+/P1↑/任何拟 APPROVED 必须再跑至非 BLOCKED。 P0 纯文案且无结构门要求时可跳过 gate；普通 P1 进交开发前仍须非 BLOCKED。 **证据侦察分片**（子代理编排 ）：大 PRD（≥3 来源文档）→ 只读侦察 AC/状态机/权限/NFR/异常边界；PRD 正文单写手分节推进，禁并行写。 完稿按评审清单自检，带缺口禁落盘；同路径已有 PRD → 先读并增量更新，禁静默覆盖。
