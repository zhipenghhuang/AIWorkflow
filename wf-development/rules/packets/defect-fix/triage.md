## 1. 元信息

- **workflow / step**：`defect-fix` / `triage`（分类与处置）
- **packet**：`rules/packets/defect-fix/triage.md`
- **角色**：`defect-fixer`（缺陷修复编排）。平台拉取 → 分类 → 红证修复或产品评估 → 门禁 → 菜单 → 按 YAML hitl 提交/部署/回写 → 发布后验证；本步只做该角色职责；越界交回或升级。
- **上游**：`pull`（取其产出为本步输入；该步被 `when` 跳过则记 `skip=`，不因缺上游阻塞，除非本步硬依赖其产出）
- **后续**：`assess_product`（进 `assess_product` 前的 `when=product_defect`）
- **失败去向**：停在本步，按 §4 门与 §5 规则补齐或升级；不得静默跳过。
- **轻量路径**：纯文档/无行为/无 UI/未命中时，可将预检、前端硬门标 `na`（一句理由）；**必开技能与 Claim/HITL 不降**。

## 5. 本步动作

> **本节 = 本步编排与门槛**（顺序、产出、门、禁做）。
> **方法质量在技能**：§6 列为必开/条件开的 skill 必须按闭环执行，**禁止**把技能正文粘进本包替代实读；**禁止**为省事跳过必开技能。

- **条件技能**：`cross-layer-consistency`（命中权限/状态/数据基数/多表面） → 命中则同样走 §6 闭环。

### 本步动作清单

- **§4.0 门禁**：本步必产出【分类表】（≥2 单逐行：单号|处置|依据一句|下一步）。
- 未出表禁进 fix/禁改业务代码。
- 禁「多为实现缺陷」代替逐单。
- 子代理不可用→mode=直做|单写手 + deviation=…，仍须出表。
- 按 rules/defects/fix-collaboration.md 分类： 实现缺陷→implementation_required。
- 产品缺陷/需求缺口/设计口径不明→product_defect。
- 信息不足/无法复现/环境数据不一致/预期不明/重复/设计如此/非defects/外部/已在其它构建修复→need_clarification。
- 延期/不修复须产品/项目确认，不得开发单方关闭。
- 产品缺陷不得先写完整技术方案，只写评估单。
- 口径存疑但实现路径清晰 → 出评审版修复方案（solution-template 裁剪，落 20-design/BUG优化修复方案/），评估单与评审版方案二选一，不重复出。
- 混批含产品缺陷+实现缺陷：两轨并行——实现项照常 fix（可先提交），产品项出评估单/评审版方案并 AWAIT_PRODUCT。
- 仅当实现项依赖产品结论时该实现项等待，不整批阻塞。
- pull 已标「待产品」→ 直接输出 AWAIT_PRODUCT，不重新评估/不重复 handoff。
- 分类结论须引用原单 steps/数据/环境/设计依据，禁只看标题。
- 批量时以侦察回执为输入，**分类/五选一/处置集中**，不采信子代理终态。
- 拟标 product_defect 前须完成实现核对（相关代码路径与/或接口行为），只凭页面观感不得判产品缺陷。
- 测试无设计文档默认实现缺陷属正确。
- 开发改判需求缺口须写明并交产品终审，不与测试争默认。
- 不挡主路径且无合规/资金/数据风险的体验类 → 不硬推 product_defect。
- 点名要改走产品 change/需求池。
- 每条实现缺陷同时记「根因层（需求/设计/数据模型/实现/测试/契约/文档）+ 同类路径候选（同模型写入口/同谓词消费方/同权限端点/同状态表面）+ 规则缺口」。
- 按 §6 `cross-layer-consistency` 取矩阵，不只修表面现象。
- 内部处置码只用于路由，不写进平台备注。

本步无前端硬门。不改界面、不做界面验收 → 不跑 capture / parity。
