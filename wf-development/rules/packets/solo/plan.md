## 5. 做法

### 技能 `product-shaping`

# 产品定义与收敛（技能 · 随包生效）

> 用于：`solo.frame`、`solo.plan` 前段；也可在 `change.clarify` 遇到「只有一个想法、没有 PRD」时按需加载。
> 目标：先判断**值不值得做、做多大**，再进入方案；不把一句「我想要 X」直接变成代码。
> 边界：本技能不写技术架构、不写完整 PRD、不做市场调研；技术方案归 `solution-design`，完整 PRD 归产品包或 `requirements-and-spec` 的完整档。
> 口径：`rules/core/lightweight.md` §0 / §3.1；**免盘问 ≠ 免验收字段**。

## 1. 适用 / 不适用

**适用**

- 只有一个想法、目标用户/场景/成功标准还没说清。
- 新项目/新产品/新模块，需要先定 MVP 与不做什么。
- 多个需求抢资源，需要快速判断先后。
- 方案卡需要补「产品判断」一节。

**不适用**

- 已确认的 PRD/需求基线，直接走 `product-doc-analysis` + `requirements-and-spec`。
- 纯技术重构、依赖升级、文案错字等无产品决策的小改（仍须 ≥1 条可观察验收，见工程自测）。
- 用户明确说「不做产品判断，直接按我说的做」——**不展开盘问**，但仍须输出 §3.1 五字段（可全标 `[假设]`），在 `confirm_spec` 一并签收；**无 AC 不得实施**。字段说不清或与体量冲突 → 推荐 + 一问确认。

## 2. 先判断「要不要做」

按顺序回答，答不出就标「未知」，不要编：

| 问题 | 要得到什么 | 不合格信号 |
| --- | --- | --- |
| 谁在什么场景遇到什么问题？ | 具体角色 + 触发场景 + 现状 | 「所有人」「随时」「不方便」 |
| 现在怎么解决？代价多大？ | 现有替代（人工/表格/竞品/不做） | 说不出现有做法 |
| 做了之后什么会变好？ | 一个主成功标准 + 一个护栏 | 「体验更好」「更先进」 |
| 最小可用是什么？ | 1～3 个必须能力 | 一上来就是完整平台 |
| 明确不做什么？ | 非目标 + 理由 | 「以后再说」但没有边界 |

**判断口径**

- **值得做**：问题真实、发生频率/代价可说明、最小版本能独立交付、成功可观察。
- **先验证**：问题真实但方案不确定 → 先做人工/假门/小样本，不写全量功能。
- **不值得做**：问题是假设、没有目标用户、收益无法观察、维护成本明显高于价值。
- **必须现在做**：合规/安全/阻断主链路/明确承诺；按高风险处理。

> 结论不是「做/不做」二选一；可以是「先做哪一小块」「先验证什么」「用什么最小实现」。

## 3.0 产品最小硬门槛（任何档；实施前）

进入方案确认 / 写代码前必须齐（快档写在方案卡 §0/§1；标准档可在产品定义卡）：

| 字段 | 最低要求 | 不合格 |
| --- | --- | --- |
| 谁 | 具体角色 | 「所有人」「用户」无场景 |
| 问题 | 场景 + 现状代价 | 只有解决方案没有问题 |
| 成功标准 | 条件 + 动作 + 可观测结果 | 「更好用」「体验提升」 |
| 非目标 | ≥1 条明确不做 | 空白或「以后再说」无边界 |
| AC | ≥1 条可被完成门读取 | 「按我说的做」无检查点 |

拿不准用户要「只做方案」还是「直接做」→ 一问确认；拿不准是否升级完整档 → 按 `lightweight.md` §2 推荐升级并一问。

### 技能 `solution-design`

## 0.1 架构与质量属性（S2 必答）

- **质量属性场景**：性能（峰值/延迟）、可用性（故障/降级）、安全、可修改性、可观测、成本；写成“刺激→响应→度量”。
- **架构视图**：上下文/容器/组件/部署（C4 或等价）；模块边界、依赖方向、数据流。
- **取舍**：至少 2 个候选（除非事实标准）；写优点/代价/风险/改回条件；架构级进 ADR。
- **技术选型**：按 02A 的约束→候选→矩阵→POC→ADR，不拍脑袋。
- **非功能**：容量/性能/安全/兼容/可观测/回滚；不适用写「不适用」。性能按 02F 给基线/瓶颈/容量/降级；可观测按 SLO/信号/告警给最小集。
- **测试策略**：单测/集成/契约/E2E/性能/安全/兼容；不可自验项单列。

## 常见合理化与反驳

| 合理化 | 现实 |
| --- | --- |
| 「先选流行栈」 | 选型对照约束/团队/运维；无 ADR 依据不拍板。 |
| 「架构一次画完所有层」 | 按变更面加载子技能；未命中面不灌水。 |
| 「跨层不一致以后补」 | 权限/状态/数据基数命中须四维矩阵进方案。 |

### 技能 `engineering-quality`

# 工程质量（技能 · 随包生效）

> 用于：`change.design` / `change.implement` / `change.review`（iterate 同名步骤同样适用）。  
> 定位：**质量条与证据的单一出处**；不替代 `solution-design`（方案结构）、`implementation-and-selftest`（实现方法）、`code-review`（评审方法）。  
> 原则：**先约束与质量属性，再结构；先最小可行，再演进；每条质量主张都要有证据。**  
> 冲突：`AGENTS.md`/`rules/` 的红线与门优先；项目档案 §7/§8 的项目约束优先于本技能默认值。

### 1.1 三维体验（所有变更）

| 维度 | 谁 | 目标 | 不可接受 | 证据 |
| --- | --- | --- | --- | --- |
| UX 用户体验 | 最终用户 | 任务更短、更清楚、更少出错；状态与下一步可见；文案只留决策所需 | 用大段说明/标签弥补布局；关键状态或风险文案缺失 | 截图/走查/可用性记录 |
| DX 开发体验 | {workroot}/维护者 | 边界清楚、可局部改、可测、可调试、命令可跑、少魔法 | 为未来造抽象；隐式耦合；跑不起来/无法定位 | diff/测试命令/评审 |
| AX AI Agent 体验 | 执行本仓的 AI | 入口/路径/命令/完成标准明确；单一出处；结构化可解析；上下文可承受 | 需要猜路径/命令；同一规则多处复制；长文迷宫 | 读取索引/门回执/报告链接 |

- 默认三者同向提升且不破坏现有功能/验收；任一不得净退化。无法同向 → 方案/收尾写取舍、补偿、确认；不得静默牺牲。
- L0 一句话说明三维影响；L1+ 在方案/任务卡/评审写；L2+ 设计/评审必写；无证据的维度标「未验证」。
- 反模式：UX 靠加说明文字；DX 靠加抽象/兼容层；AX 靠加重复rules/长文档。

### 1.2 开发阶段：不背旧数据

- 触发：`project-profile.md` §1 `项目阶段=开发`（未上线/无真实存量）且用户未要求兼容。
- 允许：直接改 schema/接口/枚举/配置；删除本次变更涉及的旧字段/旧表/旧数据；重建 seed/夹具/测试数据；用新数据重跑受影响测试。
- 禁止：为旧字段/旧记录/旧客户端加兼容分支、双写、回填、版本分支、`if legacy`；禁止保留“以后可能用到”的旧结构/死代码。
- 必须：明确丢弃范围与不可逆影响；用户要求保留时先备份；更新契约/文档/种子/夹具；不留悬空迁移脚本。
- 恢复兼容：上线/试运行/真实数据/外部公开契约/用户明确要求 → 按生产标准做兼容与迁移；不得以“开发阶段”为由删生产数据。
- 项目阶段未标或不确定 → 按生产保守处理；接入时必须在档案 §1 标清。

### 1.3 AI/LLM 变更附加质量条

- **先定失败成本**：建议/草稿、辅助决策、自动执行三级；自动执行且不可逆/对外/资金/权限 → 必须人工确认/二次授权 + 审计 + 回滚。
- **可评测**：有代表性评测集、通过阈值、失败样本；提示词/模型/检索/工具变更必须回归同一套。
- **可控制**：提示词与模型版本化；结构化输出服务端校验；工具白名单/最小权限/步数与预算上限。
- **可兜底**：超时/限流/低置信/模型不可用有明确降级或转人工，不静默失败。
- **可观测且不泄露**：记录模型/提示词版本、token、延迟、检索/工具调用、护栏触发；日志不落完整敏感 prompt/PII。
- **可合规**：数据边界、供应商条款、保留/删除、跨境按适用法规；高风险场景上线前做红队。
- 方法与测试分别见 `skills/ai-application-engineering/SKILL.md`、`skills/threat-modeling/SKILL.md`；本表只定质量条。
