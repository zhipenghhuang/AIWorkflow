# 验证与完成（开发轨）

> **读取级别：参考**（核对状态语义时读；门与回执以 `verify/README.md` + `gates.md` 为准）。

> **单一出处**：验收清单、证据、完成状态、报告措辞。`AGENTS.md` 只留指针；`verify/README.md` 是操作入口；`verify/checks.yaml` 是策略表。
> **定位**：验证是**兜底与证明**——证明落地与 SC/AC 一致；**不替代** `implementation-quality.md` DEV-IQ-12 的抽全与忠实编码。理解/语义错误应在 plan/implement 消掉，不得指望本步「捞回」。
> **读取时机**：`clarify`/`plan` 定验收；`implement` 收尾、`verify`、`closeout` 前；`review` 只读证据标准，不读门回执（门在 verify/gates 跑）。维护时读 `rules/core/rule-governance.md`。

## 1. 不变量（带 ID）

| ID | 不变量 |
| --- | --- |
| DEV-VER-01 | 先理解后执行：需求理解包/验收清单未确认，不写基线/方案/清单/代码。 |

| DEV-VER-03 | 证据先于结论：结论必须引用本轮检查、退出码、证据路径；聊天文本/子代理自述不算证据。 |
| DEV-VER-04 | 失败不声称完成；工具/环境缺失记 `BLOCKED`，不得降级为“人工清单已过”。 |
| DEV-VER-05 | 风险不降级：L0～L3 由变更事实判定；前端行为/布局变化最低 L1。 |
| DEV-VER-06 | 实施者不自证：L1+ 前端/API 变更由 fresh-context verifier 抽核；L1+ 用户可见 UI 命中前端硬门 A 级、**L1 命中安全/性能/并发/数据面**、L2+、L3、高风险/大改/破坏性变更必须独立评审；L0 或确实低风险/单点且未命中 A 级/安全/性能/并发/数据面的 L1 可免独立评审，但须记录理由与风险接受人。 |
| DEV-VER-07 | 前端必须浏览器验证：状态、视口、console、network、**桌面+移动截图**，并与同类页面/原型对照（导航层级/文案、复用组件、列/区块、空态/错误态）；无证据不报完成。浏览器/MCP/截图不可用 → 前端项 `BLOCKED`/`UNVERIFIED`，不得口头放行；**接口 200、DOM 文本、class 名正确不能替代视觉完成证据**。单 HTML 原型须先解码 `data:`/base64 模块再核对（DEV-IQ-13），原始文本搜索无结果不能作为“原型无此页”的依据。 |

| DEV-VER-09 | 读 `.gate/wf-development/completion.json` 前核对 `package=wf-development`、`mode`、`task_id`、`diff_hash`/`timestamp`；旧任务/其它包/空 diff = 未验证。review 步不读门回执，门统一在 verify/gates 跑。 |
| DEV-VER-10 | 免审不免自检：L0 纯文档核相对链接/未认领占位；代码或配置至少 L1，必须有本轮测试/冒烟/证据（定向或全仓，以 profile 为准）。多波次先选“每波独立评审+过门”或“只 S5 全量评审”，不得混用。 |
| DEV-VER-11 | 实施质量对账：有行为变化须核对 `implement_preflight`；命中取重时另核 SC 追溯、跨层、基线冒烟、债项；重要面命中须有同批硬补证据。缺项不得报全覆盖「通过/完成」。细则只认 `implementation-quality.md`（§8）。 |
| DEV-VER-12 | 验收分层：产品验收矩阵先分 `DEV-AC / QA-AC / REL-AC`；只有 `DEV-AC` 进入开发任务与 S5 门禁；`QA-AC` 由测试在 S6/S7 执行，`REL-AC` 由 UAT/发布在 S8 执行。 |
| DEV-VER-13 | 禁止直接转任务：不得把 PRD/方案验收矩阵原样拆成开发实现任务；验收矩阵保留为测试资产，开发任务只抽取 `DEV-AC` 子集。 |
| DEV-VER-14 | **测试证据保真**：全量/定向测试必须单实例串行；日志记录命令、起止时间、耗时、退出码、测试数；报告数字从本轮日志提取，禁止手填/沿用旧轮次。中断、并发、超时、无 traceback 的退出 = `未验证`，不得写“绿/通过”。 |
| DEV-VER-15 | **证据指纹与新鲜度**：截图/报告必须记录 `base_commit`、生成时间、路由、视口、文件哈希；同一截图哈希被多路由复用、截图早于本轮、文件名与路由不符、报告无路由 = 无效证据。评审必须引用证据路径 + 哈希/时间。 |
| DEV-VER-16 | **评审独立性**：复审必须实际运行最小复现/断言（至少 1 条能证伪该修复的检查）；不得以实施方自述、未断言该修复的测试、或“已信任”关闭阻断。未运行 = `未验证`，阻断保持 OPEN；评审报告须列命令/退出码/证据。 |
| DEV-VER-17 | **S5 附条件分流**：S5/评审列出的每个“附条件/重要项”必须归入 `DEV`（开发未实现/缺陷，阻塞 S6）、`QA`（测试执行/验证，进 S6 提测单）、`PRODUCT`（范围/AC 决策，需书面确认）之一；`DEV` 项不得改写成“测试条件/QA-AC”绕过。S6 前 `DEV` 项清零或书面裁剪并落债项；`QA` 项必须在提测单有入口/数据/预期；`PRODUCT` 项必须有关闭记录。 |
| DEV-VER-18 | **实施即验证**：功能实施必须先完成需求/AC/边界与「不做」的理解，再按最小改动实现；提交前按变更面完成本地验证（L0 纯文档核链接/占位；代码或配置至少 L1，按 L1 跑构建/lint/测试/冒烟；有行为变化加定向/单测与接口/页面走查，前端含桌面+移动），证据齐全方可提交/推送/部署。缺陷修复按 `fix-collaboration` §4.5（本地硬验；测环境依赖时验证站相关模块轻验）。未验证不得提交。 |
| DEV-VER-19 | **非功能证据（命中即写）**：L2+ 验收清单须写 `nfr.security` / `nfr.performance`，值为 `done: <证据>`（存在的路径、可复跑命令或可量化指标）或 `na: <理由>`；L1 及 L2+ 命中可靠性/数据/成本/供应链面时在验收清单写短句+证据或债项（不新增门禁字段）；性能敏感另须预算/基准/回归证据，安全敏感另须负面用例或扫描证据，并发敏感另须并发/重复/冲突探针或债项；禁止只写“已关注/无风险”。 |

## 2. 验收清单

- **L0**：纯文档/文案/注释；不强制验收清单；门核 `docs-links`/`docs-placeholders`；空 diff=`NOT_VERIFIED`，不得报完成。
- **L1**：写在任务卡/开发卡里的验收表（至少含 `AC | 判定 | 检查 | 证据`）；`change` 单点用开发卡（模板 `rules/templates/30-planning-tasks/dev-card-lite-template.md`），`iterate` 用任务清单。运行门时用 `-Acceptance <开发卡/任务清单>` 显式传入；不传且无 `.gate/acceptance.yaml` → BLOCKED。
- **L2+**：落 `.gate/acceptance.yaml`（含 `task_id`/`level`/`process.review`/`nfr.security`/`nfr.performance`；有代码须含 `scope_files`；L3 另含 `security`/`rollback`），确认后冻结；变更走变更记录。`task_id` 须与 `.gate/task.json` 一致，缺失或不一致 → BLOCKED；`.gate/plan-coverage.md` 同样须含本轮 `task_id`；L2+ 缺独立评审记录或非功能结论 → BLOCKED。
- **门禁字段**（模板见 `verify/templates/acceptance.yaml`）：L1+ 有代码必填 `implement_preflight`、`sc_trace`（done/na+理由；Markdown 可用「实施预检」行 + SC 表）；命中 profile `shared_globs` 另须 `impact_map`（调用方/依赖模块 + 回归集）；取重另含 `cross_layer`、`baseline_smoke`、`debts`。缺或 `missing` → **BLOCKED**（见实施质量门 §8）。
- **来源可打开（硬）**：SC 来源文件须存在、`§x` 须在目标文档有同名编号标题；方案 §4.1 设计要点 `D-xx` 须逐条被 SC 引用；任务清单 §4.1 须覆盖总表全部 `R-xx`。由 `validate_tasklist.py` 机检，解析不到即 FAIL。
- 每行必须能判定（条件+动作+可观测结果），检查可复跑，证据有落点；AC/SC 预期来自方案，不来自现网实现（DEV-IQ-02）。
- 写不出 AC = 需求未定义完；不得进入实施。
- 确认后不重复问；新增/变更 AC 走变更记录。
- **规范包只读**：`wf-development/verify/` 仅工具与模板；运行态（验收清单、证据、project-profile、截图）一律写项目根 `.gate/`，禁止写入包内。

## 2.1 验收分层（防职责错位）

> 产品方案/PRD 中的验收矩阵是**验收资产**，不是开发任务清单。任务拆解前必须先分层；未分层不得拆单。

| 类型 | owner | 执行阶段 | 典型内容 | 门禁用途 |
| --- | --- | --- | --- | --- |
| `DEV-AC` | {workroot}/verifier | S4/S5 | 单测、集成、契约、核心冒烟、权限/越权反例、幂等/并发、迁移回滚；**写入口契约负面**（批量混合结果、上传正式态门禁等，见下） | 写入 `.gate/acceptance*.yaml`，作为完成门输入 |
| `QA-AC` | 测试/QA | S6/S7 | 业务验收矩阵、**全量组合/长链路**异常与回归、缺陷复验、测试报告 | 不进入 S5；作为提测/测试通过证据 |
| `REL-AC` | 产品/业务/测试 | S8 | UAT、发布准入、遗留接受、回滚/监控确认 | 不进入 S5；作为发布评审输入 |

> **勿误读**：上表 QA「异常」指全量组合矩阵与长链路异常，**不是**「凡边界/负面一律甩 QA」。模块写入口的契约负面（权限/幂等/批量分条或整批失败定位/上传正式态门禁）属 DEV 必留面。

**规则**：

1. 产品方案/PRD 的每条验收场景标注 `DEV-AC / QA-AC / REL-AC`。
2. **DEV-AC 必留（触发链 · 对称硬句）**：同时满足下列三项时，**至少 1 条**可复跑检查必须标 `DEV-AC` 并进开发任务/S5——不得仅因场景号落在产品验收矩阵、或「原文未标类型」就整条划为 `QA-AC`：
   1. 本期**新增或改写**的对象生命周期起点（创建草稿 / 生成任务 / 下发请求 / 首次写库可见态等；示例非穷尽）；
   2. 方案/AC 写明的**业务触发链**（A 发生 → 产生或更新 B），而非仅「打开已有对象再查询/展示」；
   3. 失败会**阻断同模块后续 P0**（无草稿则无下发；无快照则无延期/统计分母等）。
3. **DEV-AC 必留（横切写契约 · 或然硬句）**：本期任务**实现或改写**下列任一类写入口时，须各至少 1 条可复跑 `DEV-AC`（混合/负面样例），**不得**以「在产品验收矩阵里」整包划为 `QA-AC`：
   1. **批量写/批处理**：方案要求分条返回或整批阻断时，合法+非法/已终结混合 → 结果可区分、不得静默漏项却报全部成功；
   2. **上传/附件进正式可下载态**：方案写危险/损坏/类型上限不得进正式版时 → 拒入或故障可见；
   3. **权限/幂等/版本冲突**反例（与实施质量门重要面同向）。
4. **仍可为 `QA-AC`/`REL-AC`**：全量组合矩阵、多角色长链路、全站/逐页视觉、真实双连与故障注入、跨版本大数据回归、UAT 业务签字等（示例非穷尽）。
5. **未标注默认**：先按第 2～3 条「必留」判定；**判不中**再默认 `QA-AC` 记入待确认/测试交接，**不得**把必留项默认塞给 QA，也**不得**把非必留矩阵整包塞给开发。
6. 任务清单只承接 `DEV-AC`；`QA-AC/REL-AC` 进入测试计划、UAT 计划或交接项，不建开发实现任务。
7. `QA-AC` 未执行不阻断 S5；它阻断的是 S6 提测准入/S7 测试通过/S8 发布评审。
8. `DEV-AC` 必须有本轮可复跑检查（证据保真见 `implementation-quality.md` DEV-IQ-02 / §5）；`QA-AC/REL-AC` 必须有执行记录和证据，不以“代码完成”替代。
9. S5 评审只评 `DEV-AC` + 代码/CI/安全/回滚；不得用未执行的 `QA-AC/REL-AC` 否定开发完成门。

## 2.2 S5 附条件分流（硬）

> 目的：防止把“开发没做完”写成“测试条件”，也防止把“测试应执行的验证”误当开发阻断。

| 分类 | 判定 | 处理 | S6 关系 |
| --- | --- | --- | --- |
| `DEV` | 功能未实现、接口/页面缺失、数据/权限/迁移缺陷、开发可复跑断言失败 | 建开发任务/缺陷；写文件/AC/测试/负责人/截止 | **阻塞 S6**，清完或书面裁剪+债项 |
| `QA` | 已有实现，需测试执行组合/长链路/全量回归/多角色/视口/真实样本 | 写入提测单测试范围、入口、数据、预期 | **进 S6**，由 QA 执行；不得写成开发阻断 |
| `PRODUCT` | 范围/AC/优先级/验收口径未定，或需加字段/改承诺 | 出选项、影响、推荐；书面确认/决策记录 | 未确认前不得按“已交付”验收 |

**分流规则**：

1. S5 结论不得只写“通过（附条件）”；必须附本表，逐项写出分类、依据、负责人、关闭证据。
2. `DEV` 项禁止出现在“测试范围/已知条件”里冒充 `QA`；若实现不存在，测试无法验，必须回开发或由产品书面裁剪。
3. `QA` 项不得作为 S6 阻断（除非缺环境/数据/入口导致不可测）；提测单必须能直接执行。
4. `PRODUCT` 项未关闭时，相关 AC 只能标“待确认/裁剪”，不得计入全通过。
5. S6 提测前复核：`DEV` 清零、`QA` 已入提测单、`PRODUCT` 有关闭记录；缺一不得标“可提测”。
6. **本表是内部门禁产物，不写入测试提测单**；提测单只写测试可执行的条件（入口/数据/样本/预期/是否阻断），不得出现 `DEV/QA/PRODUCT` 标签、开发任务号、门禁名、内部路径或测试命令。

## 3. 证据

- 门自己跑关键检查并写 `completion.json`；不信任“已通过”文本。
- 证据类型：命令+退出码、测试报告、Playwright trace/截图、console/network 日志、设计 QA、评审记录。
- 前端证据与矩阵：按**当前步骤包内「前端硬门」**（含每路由桌面+移动截图、`evidence.json`、console/network、design-qa）；L2+ 另按该节计划覆盖项提供 `verify/templates/plan-coverage.md`。截图必须晚于本轮验收清单，否则视为旧证据。维护真源仍为 `rules/core/frontend-gate.md`。
- **证据新鲜度**：截图/报告必须晚于本轮源码变更（含未提交工作区），不能只比 `base_commit`；源码改动后必须重拍受影响路由并更新哈希。
- **证据复用**：同一任务、同一源码 diff 的已通过证据可直接引用，不重复执行；代码变更后只重跑受影响集、重拍受影响路由；全量回归同一 diff 至多一次，再次全量须记录变更与理由。门禁实例的 `test`/`capture`/`e2e` 不得对同一路由重复全量执行。
- 原始测试日志落 `.gate/logs/`（命令、起止、耗时、退出码、测试数）；对话只放 ≤30 行摘要；报告数字必须与本轮日志一致。
- 独立评审/复审记录必须落 `{workroot}/50-verification/` 并在报告内引用本轮命令/退出码/证据；只留在会话记录、未回写文档的复审结论不算关闭依据。
- 缺陷修复另需：原单口径红证（修复前失败）+ 修复后同入口实测 + 验证站冒烟/相关模块轻验记录（条件见 `fix-collaboration` §4.5）；平台回写按 §6.1 备注并带 commit/版本；未验证只写“待验证”，不得 resolved。
- 证据不夹带密钥/PII；路径用相对路径。

## 4. 完成状态

| 状态 | 条件 | 报告措辞 |
| --- | --- | --- |
| `COMPLETE` | 验收全覆盖；必跑检查通过；证据可打开 | 完成/通过/已修复 |
| `PARTIAL` | 核心通过；有非阻断缺口/跳过项 | 部分完成/部分验证；列缺口 |
| `BLOCKED` | 检查失败/缺环境/缺证据/验收未覆盖 | 未完成/阻塞/未验证 |
| `NOT_VERIFIED` | 未跑门 | 未verify/待验证 |

> 中文回执映射：通过=COMPLETE｜部分通过=PARTIAL｜阻塞=BLOCKED｜未验证=NOT_VERIFIED。报告写中文，机器对账仍读 JSON 英文值。
> **`PARTIAL` 不是完成**：`-Claim` 只认 `COMPLETE`；前端 parity/矩阵/截图未过 = `BLOCKED`，不得写“通过（附条件）”；附条件中的前端项按 `DEV` 回开发。

## 5. 前端分级

> 前端分级、必产物与命令只认 `rules/core/frontend-gate.md` §2.1（A/B/C）与 §3；本节不另立第二套分档。

- L1+ 前端必须过 `verify/tools/frontend_parity.py`（parity-matrix + route-coverage + 截图哈希/新鲜度）；未通过 = `BLOCKED`。

## 6. 报告契约

```text
【验证回执】结论=通过/部分通过/阻塞/未验证 | 校验=开发计划校验（dev-plan-validator） | 检查=8/8 | 未验证=0
```

- 回执在【任务收尾】第 1 点之前；`verify/Test-Report.ps1` 对账 `.gate/wf-development/completion.json`。
- 数字与 `completion.json` 一致；未验证项显式列出；`校验=` 必须含本轮 `gate_id`（commit-diffHash），可写“中文名（机器代号）”。
- 提交/部署/回写门仍按 YAML `hitl` 独立确认；门不替代提交授权。

## 7. 成本纪律

- 定向仅当 profile 配 `*_scoped`（`{files}`）；否则 `project-*` 全仓，勿假称受影响。全量回归留给发布/L3。
- **L1 不全量（硬）**：L1 代码/配置未配 `test_scoped` 且已有 `smoke` → 跑 smoke + 验收证据，不跑全仓 test；全量 test 只在 L2+/发布/L3。未配 smoke 才回退全仓 test。L1 未配 `e2e_scoped` → 不跑全量 e2e，前端证据（截图/parity/design-qa/console）不降。
- **失败重试（硬）**：同一检查连续失败 2 次 → 停，换路径/请人确认；`-ResetAttempts` 仅换路径后用。build/test 失败时门跳过 e2e/capture/integration/perf/security，避免空转。
- **定向覆盖（硬）**：`*_scoped` 必须覆盖本轮改动模块及新增/修改的测试模块；配置遗漏 → 补映射或改跑全量，不得因映射缺失漏测。新增测试模块默认加入日常定向集。
- **升全量（硬）**：仅发布/L3、破坏性结构变更（如设置/依赖锁/破坏性迁移），或映射无法覆盖且已记理由。业务模块默认进映射表，不因「曾改过某文件」整仓。升全量须在日志打印命中路径/条件；工作区夹带无关变更 → 先收窄任务窗口或排除路径，**禁止静默升全量**。
- 全量测试只跑一个实例，禁止并发/中途重启；日志落 `.gate/logs/`（命令/起止/耗时/退出码/测试数），中断即 `未验证`，不得用旧数字补报告。
- **环境隔离（硬）**：重型测试/capture 前停掉本机后台写入（worker/daemon）或改用独立库/端口；由锁、端口、并发导致的失败按未验证处理并重跑，不得写通过。
- `-StartTask` 冻结 `base_commit`；门按 base..工作区计 diff（防中途 commit 空门）。截图新鲜度 = max(本轮代码 mtime, task `started_at`)；截图哈希跨路由复用 = 无效。
- 不复用旧 `completion.json`；高价值低成本默认做（见 `verify/checks.yaml`）。
- 不为 L0/L1 新增文档；不每个任务通读rules/技能。
