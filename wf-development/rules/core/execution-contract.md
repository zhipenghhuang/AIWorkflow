# 执行契约（开发轨）

> **定位**：把「按规则执行」变成「按目标 + 事实 + 证据判断」。规则是下限，不是百科全书；未覆盖时允许合理自主，但必须留痕。
> **冲突与覆盖**：默认按rules/红线；冲突时先说明风险与替代，用户再次明确选择按原指令 → 以用户选择为准。无冲突：用户明确指令 > 项目根 `AGENTS.md` > 本包 `AGENTS.md` > 本文件 > 当前 agent 契约 > 项目档案技术要点（若有）。拟改与现行代码或 CI 稳定口径冲突时，先指出依据与影响再改，禁止静默覆盖。细则见本包 `AGENTS.md` §0 第 5 条。
> **读取时机**：开工判定模式时读 §1～§2；写/改 workflow 时读 §3；收尾前读 §4/§6；长会话中段心跳只认 `rules/core/rule-anchor.md`（不每步通读本文）。

## 1.0 需求/意图确认与动作前分析（硬）

### 1.0.1 任务开工：先输出【需求与意图理解】，确认后再做

任何**任务**（分析/实施/测试/评审/变更/交付/对外）开工前，先输出：

1. **你的字面要求**：原文要点，不改写。
2. **我理解的目标/意图**：要解决什么、为什么、成功是什么。
3. **范围/非目标**：本次做/不做。
4. **依据/约束**：需求/方案/原型/规则/环境/权限。
5. **验收/交付物**：怎么算完成、落到哪里。
6. **歧义/缺口**：0～3 个；有则给默认建议并等确认。

- **未确认前禁止**：写/改文件、跑改库/部署/提交/推送命令、对外发送、下“通过/准出/完成”结论。
- **纯只读问答**（解释/查询/对比，无交付物、无写入）可一句话复述理解后直接回答；一旦涉及判断/建议/方案取舍/实施，仍按本段确认。
- 用户已明确“按此执行/确认/继续”且理解无歧义 → 记 `intent=confirmed`，进入 `execute`，不重复问；范围/AC/目标变化 → 重新确认。

| 场景 | 开工 `confirm_task_intent` | 动作前分析 |
| --- | --- | --- |
| 新开交付 / 歧义 / 外发 | 完整六段【需求与意图理解】 | 写/门/外发/提交：六字段 |
| 计划内续跑 / 意图已清 | 一行回执即可 | 同批可合并一行 |
| 纯只读 | 一句话复述即可 | 免 |

> `confirm_intent`（澄清 §0，`intent_needs_confirm`）与开工门分离：意图已清可跳过 `confirm_intent`，**不**豁免新开交付的完整六段开工门。

### 1.0.2 动作前分析：每个实质动作先分析，再执行

**实质动作**=写/改文件、执行命令/测试、过门、改状态、对外发送、提交/推送/部署、下结论。执行前必须先分析并在回复/工作记录中给出：

`【动作前分析】目标｜依据｜现状/已核对｜方法/步骤｜影响/风险/回退｜验证`

- 只读 / 可逆本地小改：至少写“目标/依据/验证”一行（续跑可同批合并）。
- 写入/门/不可逆/对外/跨包/提交：六项齐全；缺关键事实 → 停问 0～1 个问题，不猜。
- 分析发现方案不适配/风险高 → 先说明依据+主推方案，再确认；禁静默照做。
- **禁止先做后补分析**；禁止用“规则没写/来不及”跳过分析。
- **禁止仪式空转**：与上轮无增量时，勿重复贴满六字段长文；按上表合并一行即可（档位不降级）。

## 1. 判断模式（先判后做）

| 模式 | 条件 | 行为 |
| --- | --- | --- |
| `execute` | 目标/范围/AC/风险清楚，事实可查 | 直接做到产出/门；不再问 |
| `analyze` | 信息不足但可查（代码/文档/数据/命令） | 先查 1～3 个来源，给「理解 + 建议 + 0～1 问」 |
| `stop` | 影响范围/AC/风险/不可逆/权限/资金/合规，且查不到 | 停下问 1 个关键问题；同时给默认建议与影响 |

> `execute` 的前提是 §1.0 已确认（`intent=confirmed`）；未确认不得以“目标清楚”直接执行。

- **禁止为流程而流程**：低价值步骤可合并/省略；`output`/`gate`/证据/红线默认不可省（用户按冲突与覆盖选择除外）；跳过要写理由。
- **模板是下限不是剧本**：收尾/表单按通用占位填**本项目事实**；禁照抄示例；未列尽字段按目标+证据补全并留痕。
- **禁止为自主而自主**：不得自行改范围/AC/优先级/风险接受/发布结论（用户按冲突与覆盖明确选择除外）。
- **规则缺口**：按「最近规则 + 项目事实 + 最小可验证路径」处理；产物/路径/例外未列尽 → §1.3；收尾 `deviation=` 按实际情况如实记录取舍。
- **失败纪律**：同一方案无效 2 次换路径；连续 3 轮无新信息收敛范围或给推荐方案，不继续盘问。
- **方案择优**：发现用户方案不适配项目或明显更差 → 先说明依据与影响 + 主推（可附 1 备选），再确认或按覆盖继续；禁止静默执行劣解。低风险措辞差异不抬杠。

## 1.1 最小充分（自适应深度）

不按“场景清单”选流程，按四个维度判断：

| 维度 | 问什么 | 取轻 | 取重 |
| --- | --- | --- | --- |
| 决策影响 | 结论会影响钱、权限、合规、发布、多人协作吗？ | 不影响 | 影响 |
| 不可逆性 | 做错后能否低成本回退？ | 可逆 | 不可逆/高代价 |
| 协调面 | 需要几个角色/包/外部确认？ | 单点/单包 | 跨角色/跨包/外部 |
| 证据强度 | 结论用于解释/草稿，还是对外承诺/准出/审计？ | 解释/建议/草稿 | 承诺/准出/发布/审计 |

- 默认取“能支撑当前决策的最小深度”，不是默认最高档。
- 命中任一取重：不可逆、权限/资金/迁移/安全/合规、对外承诺、跨包契约、真实 PII、生产变更。
- 低风险/只读/可逆：允许合并步骤、减少文档、直接给结论；事实来源、未验证声明、红线不可省。
- 拿不准：先给“推荐档位 + 一句理由”；只有档位改变范围/验收/是否实施时才问 1 问，否则按推荐档执行并记 `deviation=`。
- 升级/降级都要写 `reason=` 或 `deviation=`；禁止用“规则没写”当不做的理由。

## 1.2 只读分析（解释/对比/诊断/复盘）

触发：用户要理解现状、变更、方案权衡、历史对比、数据解释；不要求改文件、过门或对外承诺。

- 不进入交付链，不写计划/索引/台账；仅允许按 `rules/core/context-memory.md` 记录用户明确偏好/要求与工作记忆（一句话回执），不更新任务状态。
- 先定范围与来源；事实、推断、未知分开；引用可核对来源；不把文档分析说成门禁验证。
- 输出深度由问题决定：默认 3～5 段；用户要“详细/全面/对比”时展开，不受只读简报 2～3 行限制。
- 发现需要实施/决策/对外承诺时，停下来给“下一步入口 + 影响”，不擅自转实施。
- 结论只对“本轮读到的材料”负责；未跑门/未执行测试要明说。

## 1.3 未列尽归类（规则缺口择优）

> 规则不枚举全部产物、路径与例外。**未写明 ≠ 可随意堆放，也 ≠ 停工等新规则**；按目的归类就近落位，禁为补漏加百科条目。

1. **先定角色**（择一主角色）：控制面（开发计划 / 任务清单 / INDEX）｜模块常青主档｜轮次·阶段件｜过程（`.draft/`）｜归档。
2. **就近归位**：并入已有 SSOT 或工作流约定目录；能改正文就不新建同题文件；能写进计划/任务行就不另起全局总览。
3. **禁方便堆**：不得因「规则没写路径」把控制面/轮次件塞进模块夹根或工作根；不得把仍有效主档丢进归档；不得另造替代计划 §0 / INDEX 的全局索引。
4. **留痕档**：路径非显而易见或与习惯不同 → 收尾 `deviation=` 写「归类=角色→路径」一句；改范围/AC/风险接受/发布结论仍须先说明再确认（§2 必须停）。

## 2. 自主边界

**可自主**：探查顺序、实现路径、工具选择、拆分粒度、措辞、是否派子代理、验证命令、文档结构、**未列尽产物按 §1.3 归类落盘**（模板是下限）。

**必须停（首轮）**：意图含糊/外发交接未对齐却拟落盘（见澄清 §0.1）；范围/AC/优先级变化；跨系统契约/数据迁移/权限资金/破坏性变更；发布/回滚/提交/推送/回写；风险接受；用户指令与规则冲突（先说明再等选择）；规则与事实冲突且无法判定。用户按冲突与覆盖再次明确选择后，按用户选择继续。

**冻结/停工（硬）**：用户说“停 / 冻结 / 先别改 / 先分析” → 立即停止编辑、测试、提交、部署；只输出冻结记录（`git status`、diff stat、未验证文件清单、当前结论、恢复条件）。未验证改动不得混入提交；恢复须用户明确指令。用户报一个前端缺陷 → 先按 DEV-IQ-18 做同波次全量审计，禁止只修被点名处。

**续跑/接管（硬）**：接手既有计划、波次或“已通过”状态时，必须先核对源需求/方案/原型的关键页、字段、路由与状态，产出「继承基线核对」；不得用 `activeContext`、旧评审、旧截图代替源文档。发现继承缺口 → 停，回退状态，补分析后再实施。

**必须记录**：自主取舍、跳过步骤及理由、假设与验证方式、未验证项、影响面。

## 3. 步骤契约

产出型/决策型 step 至少具备：

| 字段 | 含义 | 缺失处理 |
| --- | --- | --- |
| `agent` | 唯一执行角色 | 必填 |
| `input`（notes 首段或 `reads`） | 读什么 | 必填（可写「无」） |
| `skills`（notes 中路径） | 方法：skills/rules/模板 | 产出型必填 |
| `output` | 落盘路径/形态 | 产出型必填；内部步用 `internal: true` + `reason` |
| `verify` / `gate` | 门/检查/证据 | 产出型必填；无机器门用 `gate_type: checklist` |
| `precondition` | 进入本步前必须已成立的前置状态 | 关键步必填（可写「无」）；不通过 → `on_fail` |
| `on_fail` | 失败回退/阻塞 | 关键产出/决策步必填（可写「回上一步/停下问」） |
| `escalate_to` | 升级对象 | 影响范围/风险时必填 |

- `gate_type: machine` 才可声称「机器过门」；`checklist` 必须给检查方法/证据，不得假装自动。
- `chain: full` 终点必须有 `output` + 可核验终点（`verify`、`gate` 或收尾骨架 §2）；空终点不得标 full。
- `next` 只用于有意短链（如 report→handoff），不得用来绕过门。
- 禁止新增「只写 gate、无检查方法」的空门；新增门必须同时写 `gate_type` 与证据来源。
- **适用范围**：关键产出/决策步（影响门、交付、外部承诺、基线、发布/回滚/回写）必须齐；纯内部转换/只读步可用 notes 说明，不强制补空 `gate`/`on_fail`。高风险的实施、发布、回滚、回写步不可省 `on_fail`。

## 4. 计划同步（同轮）

| 事件 | 最小同步集 |
| --- | --- |
| 任务开始/状态变化/阻塞/收尾 | **开工先读**：`activeContext` 总览 + 本包 `### 进行中`（含 `rule_card`）+ 本包 `### 生效中的偏好`（项目/包，≤3 行）+ 有则 `project-profile.md` §1+§2 表（身份短读，见 `AGENTS.md` §0）。回写：`### 进行中`（任务 ID/状态/最后动作/未提交文件/下一步口令/待确认/`rule_card`）；只读分析除外（§1.2）。**若本轮使阶段/门/焦点/下一动作语义变化** → 另加开发计划 §0（阶段变则 §1 对应行）+ `{workroot}/INDEX.md` |
| 用户偏好/要求 | 本包 `### 生效中的偏好` 1 行 + 一句话回执；影响当前任务则同步进行中/计划；范围/期限/强度与升级见 `rules/core/context-memory.md` §3；与门/红线冲突先说明 |
| 任务收尾/复盘/计划关闭 | 按 `rules/core/context-memory.md` §4 五问评估：记 1 行 / 升级 / 不记；`待归位` 清零；【任务收尾】写「工作记忆」行 |
| 新需求/变更 | 开发计划 §0/§8/§10 + 变更记录 + {workroot}/INDEX.md + `activeContext.md` |
| 范围/AC/里程碑 | §1/§3/§4/§13 + 任务清单 + 测试计划（如启用）+ handoff-ledger.md |
| 进度/阻塞 | §0/§12 + {workroot}/INDEX.md + `activeContext.md` + 工作日志（里程碑）+ handoff-ledger.md |
| 缺陷 | 缺陷台账 + §7 + 测试报告（如启用）+ **开发计划 §0（实质进入/处于 S7 时）+ {workroot}/INDEX.md + `activeContext.md`** |
| 交接 | handoff-ledger.md + §0/§12 + {workroot}/INDEX.md + `activeContext.md` |
| 发布 | §0/§10 + 发布说明 + 根 `CHANGELOG.md`（仅开发；多包输入见文档治理版本记录）+ 工作日志 + **门面同步**（`doc-facade-sync.md`） |
| 回滚/事故 | §9/§10 + 复盘 + 发布记录 |
| 版本 bump / 迭代关闭 / 对外可见事实变 | 最小集见上表相关行；**另**按 `rules/core/doc-facade-sync.md`（轻量对应句；禁全扫 README） |

**规则**：

0. **只读 / 最小充分档**不强制触达上表全量计划矩阵；只同步当前决策所需最小集。**仅当阶段/门/焦点/下一动作语义未变**时，可只更 `activeContext`「进行中」或口头结论；语义已变却只改热层 = 违规。
1. 先列「受影响文档清单」，改完逐项标 `已更新/不适用/待补`；未标不得收尾。
2. 计划是控制面：任何「下一步」必须能从 §0 读出；读不出先修计划。
3. **单包**只改本包；**多包**只改本包分节 + 跨包同步一行；共用原件根 `inbound/`；不自动跑他包。
4. 变更 C2/C3：先重基线再实施；禁止拆成 C0/C1 绕过。
5. 收尾对比「计划下一步 vs 实际下一步」，不一致先修。
6. **进行中=跨会话快照**：任务开始、状态变化、阻塞、收尾前必须更新本包 `### 进行中`；不能只在收尾写。收尾时状态=已完成/待确认/阻塞，未提交文件写实际，下一步口令写下一条。**总览**须保持项目一句话定位（已接入禁止长期「无」）；与档案 §1 冲突以档案为准并同轮改总览。
7. **状态与导航（硬）**：**有 `development-plan`（L2+ 或计划已存在）** → 状态唯一权威＝开发计划 §0（阶段变则含 §1 对应行）；`activeContext` 是热快照；`{workroot}/INDEX.md` 只写入口/清单/版本——**不重复阶段/门/状态**。**齐改触发**：阶段/门/焦点/下一动作**语义变化**时同轮改计划 §0 + 索引入口 + `activeContext`；语义未变可只更新「进行中」。收尾前对账：§0 与索引入口不一致 → **先修计划再收尾**。正式门未签但实质已进入下一阶段 → §0 写「进行中（正式门待补）」，**禁止**热层领先 §0。`sync=` 须含 `triad=aligned` 或 `triad=deferred:<原因>`。**无 `development-plan`（L0/L1/solo）** → 状态 SSOT=`activeContext` 本包进行中；`triad=na` 合法；有计划才三处同拍。禁只写 `activeContext` 冒充「有计划时」同步完成。
8. **项目身份短读**：每新会话开工一次（见 `AGENTS.md` §0）；同会话文件未变不重读；日常优先档案 §1+§2 表，不预防性通读根 README。
9. **资料不足升级（硬）**：身份/地图空壳、占位、与代码冲突、命令不可用、或缺支撑本任务的关键事实 → 入口判定 §5：有 README 则按实际结构择要，不够则探查仓库实情 → **同轮必回写**档案/`activeContext`（真源）→ 有缺口则按 `doc-facade-sync.md` 补已核实句（无缺口=`facade=na`）→ 收尾【资料补强】。死守空资料继续执行=违规；升级读取计入 `reads=`。
10. **门面同步（硬·事件触发）**：版本 bump、迭代关闭、发布/上线、或本轮核实的对外可见事实变化 → 只认 `rules/core/doc-facade-sync.md`；未命中不扫 README。`sync=` 须含 `facade=aligned|na|deferred:<原因>`（与 `triad=` 并列；只读可 `facade=na`）。

## 5. 时间 / Token 纪律

- 单步默认核心 ≤3～4 个来源（命中才读）、≤8k tokens；开工另计身份短读（通常很小）；资料不足升级另计有界探查（仍守总量）；复杂可至 5；先读标题/当前节，够用即停。
- 同一文件不重读；后续 delta-only；大文件只读当前节。
- 不预防性通读rules/skills/模板；不复制正文；用路径引用。
- 超预算：只读当前节 + 收尾说明，**不得**为省预算跳过门/证据/红线。

## 6. 遵守自检（收尾必写）

```text
【遵守自检】route=workflow:step | mode=execute/analyze/stop | packet=rules/packets/<wf>/<step>.md | skills=name=done|na,... | reads=... | gates=... | confirm=gate=approved@yyyy-MM-dd HH:mm,...|无 | sync=... | skip=... | deviation=...
```

- `packet` 必须是本轮实际步骤包；`skills` 列必开/条件开技能结果；`confirm` 列本轮确认门 `gate=结论@时间`（无则写无）。
- `route` 必须是实际执行入口；`reads` 列实际读过的文件；`gates` 列门 id/结果；`sync` 列更新的计划/索引/台账，**且须含** `triad=aligned|deferred:<原因>`（§4 规则 7；只读或无 `development-plan` 可写 `triad=na`）与 `facade=aligned|na|deferred:<原因>`（§4 规则 10）；`skip` 列跳过步骤 + 理由；`deviation` 按实际情况如实记录取舍（无则写无）。
- 缺此项 = 未完成收尾；不得只写「已完成」。

## 7. 规则心跳（中段重锚）

- 格式/触发/与 §0 关系：**只认** `rules/core/rule-anchor.md`。
- 切 step、过门前后：输出一行【规则心跳】（必做）；同一步长会话可选（建议约每 5～8 轮）。`rule_card=refresh` 时同轮写回 `activeContext` 进行中。
- 心跳只重锚身份与当前步约束，**禁止**借此通读全书或全本 `AGENTS.md` §0。
