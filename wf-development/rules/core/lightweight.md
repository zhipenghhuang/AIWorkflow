# 自包含完整链（solo）

> **定位**：无正式迭代/正式协作时，由开发包自包含完成**产品分析 → 方案 → 完整开发 → 测试**的完整链；不是只开发，也不依赖产品/测试包。
> **单一出处**：轨道判定、产品/测试切片、文档最小集、测试覆盖集（按风险完整）、门策略、本包产品/测试职责边界、不降标口径。`AGENTS.md`、`workflows/solo.yaml`、模板只引用本文，不复制阈值。
> **读取时机**：命中 `solo` 入口、准备产品分析/方案/测试报告、无 QA 自验、收尾前；改「不阻塞/降级」语义时也读。

## 0. 本包产品/测试职责边界（硬）

开发包**以工程交付为主**；无正式迭代/正式协作时，开发包自包含完成产品判断、方案、完整开发、测试，标准不因「个人项目 / 无多职责分工」降低。有正式迭代/产品/测试产物时，开发只消费对方产物，不重复产品分析与测试设计。

| 本包负责（自包含链切片） | 本包不负责（归他包或正式流程） |
| --- | --- |
| 值不值得做 / MVP / 非目标 / 可观察成功标准 | 需求池、路线图、立项 Go-Hold-Kill、客户访谈 |
| 理解 PRD/原型 → 冲突表 / GAP / AC 可验收 | 写完整 PRD、原型/IA/视觉体系、GTM |
| 方案卡/需求基线里的产品行为 + 验收表 | 产品变更单作业务 SSOT |
| 按风险完整覆盖实测 + **开发测试/自验**报告 | 测试计划库、用例库、覆盖三闸、**版本准出** |
| 有 QA 时提测单；无 QA 时自验结论可交付 | 替测试判准出、替产品改业务口径 |

**口径分离（禁混用）**

- **开发测试/自验** verdict：`PASS` / `CONDITIONAL` / `FAIL` → 回答「本轮改动能不能用」。
- **版本准出**：仅测试包 / 正式测试负责人结论 → 回答「版本能不能出」；本包不得写「已准出」。
- **可选输入不阻塞**：缺他包产物（PRD/测试报告/UAT）→ 一句缺口，用本包模板补或用户提供；**不**等于可省 AC、产品分析、完成门、测试证据。
- **自包含**：裁剪文档厚度与角色分工；**不**裁剪产品分析、AC、证据、P0、完成门、红线。

**不确定时**：先按 §1 判轨；轨道拿不准（是否正式协作）只问 1 个关键问题，不静默降为只开发。

## 1. 轨道判定（只看正式协作，不看体量/风险）

`solo` 是**自包含完整链**（产品分析 → 方案 → 完整开发 → 测试），不是「只开发」，也不是「小改动专用」。先按事实判轨：

| 事实 | 轨道 |
| --- | --- |
| 团队/正式协作：有正式迭代方案/原型/PRD/开发计划/测试排期，或产品/测试已按迭代/版本正式介入本轮交付 | 完整开发链（`change`/`iterate`）；开发消费产品/测试产物，不重复 |
| 无正式迭代/正式协作（单人或团队，含大改动/高风险） | `solo` 自包含完整链：产品分析 → 方案 → 完整开发 → 测试；大改动/高风险按 §2 提高严谨度 |
| 需要正式发布/QA/UAT/交接/团队流程 | 完整链 + 对应正式步骤；不塞 solo，不冒充准出 |

- **文档数量/页数不判轨**：单个 PRD/原型不自动等于正式迭代；看它是否本轮正式迭代/版本依据、产品/测试是否按迭代·版本正式介入。拿不准只问 1 问；首条 `reason=` 写轨道依据（正式协作/正式介入/无正式协作）。

`solo` 只有一条路径（不按体量/风险分档）：

```text
frame（方向不清/新产品时）
  → plan（产品分析与方案）
  → confirm_spec
  → build（完整开发）
  → test（完整测试）
  → completion-gate
  → closeout
```

- **产品切片**：frame 做产品定义；plan 做产品行为/AC/影响面/风险；输入含文档/原型 → `product-doc-analysis`；一句话输入用五字段 + 假设。产品分析不是只开发。
- **开发切片**：与正式协作同一要求（iq 预检、StartTask、前端硬门、completion-gate、Claim 不降）。
- **测试切片**：`test-design-and-execution` 做设计 → 执行 → 报告；AC 走查、P0/P1、覆盖、证据、缺口；L1+ 前端/API 独立 verifier；大改动/高风险按 §2 全节 + 回归/安全/回滚证据。
- 新产品/方向不清：先 frame；单人/无正式协作也走本链。
- **体量/风险不换链**：>3 文件、多模块、接口/数据/权限/迁移/安全等，仍在 solo 内提高产品分析与测试证据（§2）；只有正式协作/正式流程才转 `change`/`iterate`。
- 口令「轻量开发 / 自包含开发 / 我有个想法 / 小项目」只影响入口；「做个/快速做」按 `routing.md` 判轨，命中正式协作/迭代才转完整链。
- **正式协作 ≠ 必须完整链**：只有产品/测试按迭代/版本正式介入本轮交付才转完整链；团队里有产品/测试同事、但本轮未正式介入的无正式迭代任务，仍走 solo 自包含链。

## 2. 严谨度（不换链）与转链条件

**转链只看正式协作/正式流程**（不是体量/风险）：

1. **团队正式迭代/版本**：本轮属于迭代方案、版本计划、原型/PRD、开发计划或测试排期；产品/测试已按迭代/版本正式介入本轮交付。→ 完整链；开发消费对方产物，不重复。
2. **正式发布/QA/UAT/交接/团队流程**：需要正式评审、提测、发布审批、回滚演练、交接包/回执。→ 完整链/正式步骤；solo 不冒充准出。
3. **用户明确要求完整流程 / 写 PRD / 出测试计划 / 按团队流程** → 完整链。

**大改动/高风险不换链，在 solo 内提高严谨度**：

- **产品**：frame + 方案卡 §0/§1 全节；含用户/场景/替代/价值/成功标准/非目标/AC 追溯/影响面/风险/假设；有文档/原型 → `product-doc-analysis`；方向 ≥2 个互斥选择 → 列选项 + 推荐，仍只停一次。
- **开发**：iq 预检、StartTask、前端硬门、completion-gate 全数；>3 文件/多模块按任务拆分；破坏性变更先停；独立 verifier。
- **测试**：报告全节（AC 走查、P0/P1、主路径 + 边界 + 异常 + 权限/数据 + 回归、证据、缺陷、缺口、verdict）；命中安全/权限/迁移/回滚 → 补对应证据；P0 未过 = FAIL。
- 需要正式评审/发布/QA/UAT/交接 → 按上面转链；**不把「大」当转链理由**。

**其他**：

- P0 失败根因涉及产品范围/架构 → 在 solo 内回 frame/plan 补产品分析/方案修正；不自动换链。
- 价值/成功标准说不清 → frame/`product-doc-analysis` + 方案卡列选项；不自动换链。
- 轨道拿不准（是否正式协作）→ 只问 1 个关键问题；不静默降为只开发。

## 3. 文档最小集

| 必产 | 可并入 | 不产 |
| --- | --- | --- |
| 方案卡（一页为目标；含产品分析/技术/任务/验收/测试策略/**测试结果**） | 产品定义卡（仅新想法/方向不清时加）；测试结果可写在方案卡内；大改动/高风险可用附录 | 独立 PRD、需求基线、用例库、提测单；测试计划可并入方案卡测试策略（大改动/高风险须全节） |

- 方案卡落 `{workroot}/20-design/方案卡-{主题}-{yyyyMMdd}.md`；产品定义卡落 `{workroot}/10-requirements/产品定义-{主题}-{yyyyMMdd}.md`；需要独立报告时落 `{workroot}/50-verification/测试报告-{主题}-{yyyyMMdd}.md`。
- 一页为目标，不为凑节写空话；超出用附录，不另起一套文档。
- 方案卡必须含可被 `completion-gate` 读取的验收表：`ID | 验收标准 | 检查 | 证据`；每条证据是路径或可复跑命令。

### 3.1 产品最小硬门槛（实施前必齐；免盘问不免字段）

无论是否写产品定义卡、用户是否说「不做产品判断」，进入 `confirm_spec` / 写代码前必须齐：

| 字段 | 最低要求 |
| --- | --- |
| 谁 | 具体角色（禁「所有人」空写） |
| 问题 | 场景 + 现状代价（可标假设） |
| 成功标准 | 条件 + 动作 + 可观测结果 |
| 非目标 | ≥1 条明确不做 |
| AC | ≥1 条可被完成门读取 |

用户豁免「产品盘问」→ 仍输出上述五字段（假设标 `[假设]`），在方案卡确认时一并签收；**不得**无 AC 开工。大改动/高风险：除五字段外，方案卡 §0/§1 全节 + 影响面/替代/非目标/AC 追溯/风险；仍只停一次 `confirm_spec`。

## 4. 测试覆盖集（开发测试/自验 · 按风险完整，不是只跑一条）

| 变更 | 必测 | 证据 |
| --- | --- | --- |
| 纯文档/文案/注释 | 相对链接 + 未认领占位 | `docs-links` / `docs-placeholders` |
| 纯样式/文案 | 受影响页面 + console 无 error | 截图（桌面/移动按需） |
| 前端行为 | 主路径 + 1 边界 + 1 异常 + 受影响回归；状态/视口/console/network | 截图 + network 摘要 |
| 后端/接口 | 主路径 + 1 边界 + 1 错误码/权限 + 受影响回归 | 命令/响应/日志 |
| 数据/迁移 | 上述 + 迁移前后核对 + 回滚路径 | 查询结果/脚本输出 |
| 高风险 | 本表全节 + 回归/安全/回滚证据 + 独立 verifier；不换链 | 现有证据/报告 |

- **自验证据块（硬）**：即使完成门未触发（如单独「测试」入口），也必须写清 `范围 | 检查/用例 | 结果 | 证据 | 缺口`；缺一项不得写「通过」。大改动/高风险：报告全节，P0/P1 全列，安全/权限/迁移/回滚按命中补证据。
- **AC 走查**：方案卡/基线每条 AC 至少对应一次检查结果（通过/失败/未测+理由）；未走查不得写 PASS。
- P0 未过 = 整体 FAIL；不得用「有条件通过」掩盖 P0。
- 有条件通过仅限 P0 全过、缺口非 P0、用户明确接受并记录。
- 未测项必须列缺口；不得写「应该没问题」。
- 能脚本的稳定回归优先脚本；一次性/探索式用 AI + 浏览器/API；同一失败修复后跑「原用例 + 冒烟 + 影响面」。
- 结论用语写「开发自验 / 可交付（有条件）」；禁写「版本准出 / 测试通过可发布」（后者归测试包）。

### 4.1 完整链无 QA 时（`change` / `iterate`）

- **跳过 `deliver`（无提测单）≠ 跳过自验**。
- 代码/配置改动触及用户路径 / 交互 / 业务规则 / 接口行为 → verify/gates **必须**产出轻量测试报告（或方案卡/验收附录含完整 verdict/P0/缺口/证据）；仅 build/lint/单测绿不算功能自验完成。
- 纯文档核链接与占位；代码/配置按 L1 覆盖集验证；无用户路径可不强制独立报告，但收尾须写自验依据。
- 有测试包且本轮已有正式测试报告 → 引用，不重复造轻量报告；不以开发自验替代准出。

## 5. 门策略

- 只保留三个确认点：`confirm_spec`（方案卡批准）、`completion-gate`（完成门）、`confirm_commit`（拟提交）。
- 产品定义不单独设门：方向不清在方案卡里列选项一次性确认；需要正式产品评审 → 转正式协作/完整链；solo 内仍列选项 + 推荐。
- **completion-gate 仍必须过**；轻量不等于免验证。门命令未配置/不可用 → 记 `BLOCKED`/`未验证`，不得写通过。
- 不单独走 `select_review_mode`、`confirm_requirements`、`confirm_backlog`；这些在完整链使用。
- 需要正式代码评审 → 转 `change.review`；solo 内用独立 verifier 核测试证据，不冒充已评审。
- 单独「测试/验收」入口未触发完成门时，仍按 §4 强制证据块，结论只能是 `PASS/CONDITIONAL/FAIL/未验证` 之一。
- 测试报告未落盘/无 verdict/证据不存在 → 不得收尾为完成。

## 6. 反模式

- 把「自包含 / 个人项目 / 无 QA」当「不测试/不verify/无 AC」。
- 把 solo 当只开发，跳过产品分析/测试；或把大改动/高风险当必须换完整链，忽略 solo 自包含完整链。
- 把「可选输入不阻塞」读成「可以没有验收标准」。
- 一个想法直接写代码，跳过方案卡与确认。
- 小改也生成 16 节 PRD、18 节测试计划、用例库。
- 方案卡只有技术，没有产品判断/AC/测试点。
- 测试只跑 build，不跑用户路径。
- 发现 P0 还写「基本可用」；把开发测试 PASS 写成「已准出」。
- 用 solo 绕过正式评审/准出；solo 内仍按风险补证据。
- 「做个/快速做」死板塞 solo，忽略正式协作/正式流程（§2）。
- 单独「测试」只给诊断结论，不写范围/结果/证据/缺口。

## 7. DoD

- 产品最小硬门槛五字段齐；大改动/高风险：产品分析全节 + 测试报告全节；方案卡已确认；范围/非目标/AC/测试点/风险齐。
- 验收表每条有检查与证据；证据路径存在；AC 走查完成。
- 测试有 verdict、P0 结论、缺口；失败项已修/已接受/已转正式流程；用语为开发测试/自验非准出。
- `completion.json=COMPLETE`（本轮 task_id/diff_hash 匹配）；未触发门时写「未验证」。
- 收尾写清未verify/阻塞/升级项；无 QA 时含【开发自验】段；提交按 `confirm_commit`。
