# 规则治理（开发轨）

> 目的：防止规则越写越多、互相冲突、没有执行载体。维护/改规则时读；业务任务不读。
> 原则：**规则不是越多越稳；一条规则一个 owner；能被脚本检查的，不写成长文。**

## 1. 预算

| 对象 | 上限（估算 tokens） | 说明 |
| --- | ---: | --- |
| `cold-start.md`（每任务常驻） | ≤ 1,200 | **开局唯一常驻正文**；超预算必须再拆命令表 |
| `AGENTS.md` §0 + 指针 | ≤ 2,500 | 分级表+指针；硬约束不重复开局卡 |
| `AGENTS.md` 全文（含口令表） | 不计入每任务预算 | 口令表仅未路由时读 |
| 常驻/必读规则 | ≤ 3,000 | 含 cold-start；超了拆节或移 playbook |
| 参考手册/playbook | ≤ 10,000 | **必须**在头部标 `读取级别：参考` + 节索引；只读当前节，禁止通读 |
| 单个 `skills/<name>/SKILL.md` | ≤ 4,500 | 技能按步加载；超了拆 `references/` 或脚本 |
| 模板 | 不设 token 上限 | 只复制/填写，不作为规则通读 |
| 单步读取总量 | 轻 ≤6,000｜标准 ≤8,000｜重 ≤12,000 | 核心 ≤3～4 来源（命中才读）；重步默认允许；超 12,000 才拆包或把技能拆 `references/`。预算是指示线，不是砍质量的借口 |

估算：CJK 字符约 1 token/字；ASCII 约 4 字符/token。`Test-DocHygiene.ps1` 检查常驻规则、参考手册、AGENTS、技能；模板不报预算。

**读法分级**：
- **常驻**：新会话精读 `cold-start.md`；其后心跳 + `rule_card` + 当前步骤包（`packet=`）。read-index/playbook 仅当前步骤包点名时按节读。  
- **参考**：`implementation-quality.md`（词典）、`workflow.md`、handoff/缺陷长文；只读当前节。`frontend-gate` / `iq-checklist` 为命中必读短卡，不算百科。
- **技能**：命中步才读，不命中不读。
- **模板**：只读当前要填的一份，不通读模板库。

## 2. 单一出处

- 每条规则只在一个文件定义；其他位置只放“指针 + 规则 ID”。
- 高频重复规则（一次一问、证据先于结论、文档现行有效、子代理边界）必须合并。
- 阻断路径统一 `必须/禁止/不得`；`可/建议/按需/必要时` 只用于非阻断能力。
- 新增规则前先问：能否合并到现有规则？能否用脚本检查？能否删掉旧规则？三者都否，才新增。

## 2.0 补强闸门（防堆积 · 硬）

```text
发现缺口 / 反复失误
  → Q1 现有 cold-start / 短硬卡 / gates / skill 必做 / verify 是否已覆盖？
       是 → 改那一处（增强）→ 删其它副本 → 跑 eval/自检
  → Q2 能否用脚本/门检查代替长文？ → 是则加机检，不写新散文
  → Q3 是否同一错误反复（有证据）？ → 否：只记洞见，不入库
  → Q4 完全未覆盖？ → 才新开：优先扩现有 owner；须单一职责、预算内、有载体、有降级；并删除被替代正文
```

- workflow step `notes`：**≤3 行指针**；方法进 skills / must_read；禁止 notes 复述门/完成口径全文。
- `playbooks/`：内容须已进入 read-index 或 skill 后才可删文件；业务步默认不读，仅当前步骤包点名时按节读。

## 2.1 自适应规则写法（防过拟合）

规则写“判断维度、不变量、升级条件、失败回退”，不写“具体场景清单/固定口令/固定文件数/固定角色名”。示例只作校准，最多 2～3 个，并标“示例，非穷尽”。三层写法：**不变量（硬，必须/禁止）→ 判断维度（柔，按影响/风险/协调面）→ 示例（参考，非穷尽）**；禁止把示例写成不变量。

- 一条规则只回答：什么目标、看哪些信号、何时取轻/取重、何时停、失败怎么办。
- 能用门/脚本/检查表判定的，不写成长篇叙述；不能机器判定的，给“判断问题”而非“标准答案”。
- 新规则必须写“不适用/降级”路径；否则不得新增。
- **路径/产物未列尽**：优先靠执行契约 §1.3 归类；禁为单次落盘困惑新增专条路径清单。
- 同一规则不在 AGENTS/skills/模板重复正文；只留指针。
- 维护时删除“只为某个项目/某次事故写死”的条款；必须保留的，标为项目适配并登记。
- 评审规则时问：换一个团队/产品/规模，这条还成立吗？不成立就改成维度或降为示例。

## 3. 规则 ID

- 格式：`DEV-<域>-<序号>`，如 `DEV-VER-03`。
- 每个 ID 对应：一句话不变量、执行载体（gate/script/human）、适用 step。
- 报告/gate 输出引用 ID；无法引用 ID 的规则视为“无执行载体”，应删除或改写。

## 4. 条件门

- **只认** workflow 步上 `hitl` / `hitl_when` / `gate_when`；语义见 `rules/gates.md`；专规不另造门。`hitl_when` 用于按事实条件开门/跳过，**合法且应保留**。
- L2+、外部文档输入、前端行为变化：默认开门；**禁止用条件把 L2+ 高风险门跳过**（不得写使高风险门恒假的条件）。
- L0/L1 才允许用条件跳过低风险门；跳过必须记录理由。
- 条件由外部事实/脚本判定优先；模型自评只作建议，不确定按触发处理。

## 5. 规则卫生检查（维护时）

```powershell
powershell -ExecutionPolicy Bypass -File "wf-development/rules/tools/Test-DocHygiene.ps1"
powershell -ExecutionPolicy Bypass -File "wf-development/rules/tools/Test-Template.ps1"
python "wf-development/rules/tools/validate_workflow.py" "wf-development"
```

检查：引用/锚点、YAML、workflows→agents、版本单点、AGENTS/规则行数、读取索引挂载、孤立模板。
新增检查（后续）：token 预算、重复句、同范围“必须/可跳过”冲突、孤儿规则。未实现前由维护者人工核对。

## 6. 规则 eval（改规则时）

1. 没跑测试就写“完成” → 报告 lint 必须失败。
2. 前端只测 happy path → gate 必须 BLOCKED（缺状态/截图）。
3. console 有 error 仍报通过 → gate 必须 BLOCKED。
4. UI 改动被降级为 L0 → 风险分级必须升到 L1。
5. 验收清单缺证据 → gate 必须 BLOCKED。
6. 空 diff / dry-run → 必须 `NOT_VERIFIED` / `DRY_RUN`，不得 `COMPLETE`。
7. 包内 `.state`/包内 `project-profile.json` 存在 → 不得被读取；旧截图/旧验收 → BLOCKED。
8. 用户只要解释/对比、未要求改文件 → 必须走只读分析，不得强制任务收尾/计划更新；未跑门不得写“完成”。
9. 低风险只读/单点任务被强制升级完整链/独立评审 → 视为过度流程，规则判定失败。
10. 新增规则只列具体场景/固定口令，无判断维度/降级路径 → 规则卫生检查失败。
11. 口令表/专模列表/类型码写成穷尽白名单（未标「示例非穷尽」）→ 规则卫生检查失败。
12. 与「内容优先·包按需」冲突的「必须整包 HO」死句 → 规则卫生检查失败。
13. 方案有 Then/异常分支但任务无 `SC-xx` 仍声称可实施 → DEV-IQ-01 失败。
14. 自测断言与方案/AC 相反仍报绿 → DEV-IQ-02 失败（禁刷绿）。
15. 跨层命中但无矩阵/无第二次写或角色正反证据仍报完成 → DEV-IQ-03 失败。
16. 「本期不做」仅口头、无债项/提测限制声明 → DEV-IQ-05 失败。
17. 增量提测声明沿用基线却无基线冒烟证据（且未写不适用）→ DEV-IQ-06 失败。
18. 有行为变化却无【实施预检】/`implement_preflight` 仍动手或报完成 → DEV-IQ-09 失败。
19. 预检命中重要面却只做主路径、无同批防护/负面自测/债项 → DEV-IQ-10 失败。
20. 命中 §2.1「DEV 必留」的触发链 AC，仅用合成行/mock 插入/只读打开预置对象即报 COMPLETE → DEV-IQ-02 / DEV-VER-12 失败。
21. 方案写「生成/创建/下发时」却 SC 落点只写查询补齐、或先旁路后接写入口且无债项 → DEV-IQ-01 / DEV-IQ-09 写路径失败。
22. 口令表/`entry_points` 指向不存在的 step，或 `read-index` 缺当前 step 行 → 规则卫生检查失败。
23. 任务声明覆盖某组通用条款/场景族，但 AC/SC 未覆盖组内「必须/不得」却标完成 → DEV-IQ-12 §4.1#10 失败。
24. 实现批量写却对合法+非法混合返回空成功/静默漏项；或方案写危险不得进正式可下载却仅做令牌/hash 仍进正式态 → DEV-IQ-10/12 失败。
25. 把写入口契约负面（批量混合、上传正式态门禁）仅因落在产品验收矩阵就整包划 `QA-AC` → DEV-VER-12 第 3 条失败。

eval 通过才算规则改好；不通过先修rules/脚本，不加新规则。

## 7. 变更流程

1. 说明要解决的问题与现有规则冲突/冗余；
2. 优先合并/删除，再新增；
3. 改 workflow/agent/rules/skills/模板中的一处 owner；
4. 跑规则卫生检查 + 本节 eval；
5. 更新包 `AGENTS.md` `template_version`。**仅 AIWorkflow 母版仓**维护会话、且有对使用者可见的包能力变化时，用产品语言更新母版根 `CHANGELOG.md`（禁接入/文档树/过程项）；**业务项目会话禁止**为「改规范包」去改项目根 CHANGELOG。纯内部措辞收紧可不记；
6. 旧规则删除或归档；现行文档遵守「当前有效状态」（见 `doc-quality.md` §1 第9条）：不留“旧方案/已废弃/不要再用”等删后说明。
