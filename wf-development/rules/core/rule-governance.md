# 规则治理（开发轨）

> **读取级别：参考**（维护/改规则时读；运行时规则以 `global-rules.md` 为准）。

> 目的：防止规则越写越多、互相冲突、没有执行载体。维护/改规则时读；业务任务不读。
> 原则：**规则不是越多越稳；一条规则一个 owner；能被脚本检查的，不写成长文。**

## 1. 预算

| 对象 | 上限（估算 tokens） | 说明 |
| --- | ---: | --- |
| `cold-start.md`（开局一次整文件读） | ≤ 1,200 | 只放启动/续跑/回执 |
| `global-rules.md`（每步整文件读） | ≤ 6,000 | 全局规则唯一出处；每步读并逐条过；未读不得写 `global=ok` |
| `AGENTS.md` §0 + 指针 | ≤ 2,500 | 分级表+指针；硬约束不重复 global-rules |
| `AGENTS.md` 全文（含口令表） | 不计入每任务预算 | 口令表仅路由未定/首次命中时读 |
| 参考手册 / `rules/special/` / 按节读规则 | 不设整文件上限 | 头部标 `读取级别：参考` 或 `读取时机` + 节索引；只读当前节；不得为凑短删质量内容 |
| `skills/<name>/SKILL.md` | 不设 token 上限 | 按 §6 **整卡读取**（必做 → 方法/判定 → 反模式/DoD）；单步预算计整卡；主文件 ≤500 行（结构上限，超长拆 `references/`） |
| 模板 | 不设 token 上限 | 只复制/填写，不作为规则通读 |
| 单步读取总量（步骤包 + §6 整卡） | 轻 ≤8,000｜标准 ≤12,000｜重 ≤22,000 | 不含每步 `global-rules`；核心来源按命中读；重步允许；超 22,000 才拆包或拆技能。预算约束长度，不截断技能，也不是砍质量的借口 |

估算：CJK 字符约 1 token/字；ASCII 约 4 字符/token。整文件 token 只约束 `AGENTS.md` / `cold-start.md` / `global-rules.md` 这类“开局或每步整文件读”的文件；`gates.md`、`routing.md`、`doc-quality.md`、`doc-governance.md` 等按节读规则，不按整文件限长。`Test-DocHygiene.ps1` 检查上述整文件预算、模板索引与结构；按节读文档不报整文件长度。

**读法分级**：
- **开局**：新会话精读 `cold-start.md`。  
- **每步必读**：`global-rules.md`（按 §7 重读分级）+ 当前步骤包（`packet=`）；未按 §7 复核不得写 `global=ok`；其后心跳 + 运行状态。`special` 仅点名时按节读。  
- **主从**：步骤包=本步目的/门槛/门；技能/模板=方法与壳；`global-rules`=跨步场规则；`core|defects|collaboration` 具名索引按步骤包点名再读。禁技能另造平行流程。
- **参考**：`implementation-quality.md`（词典）、`workflow.md`、handoff/缺陷长文；只读当前节。`frontend-gate` / `iq-checklist` 为命中必读短卡，不算百科。
- **技能**：命中步**整卡读**，不命中不读；`references/` 只按正文点名再开。
- **模板**：只读当前要填的一份，不通读模板库。

## 2. 单一出处

- 每条规则只在一个文件定义；其他位置只放“指针 + 规则 ID”。
- 高频重复规则（一次一问、证据先于结论、文档现行有效、子代理边界）必须合并。
- 阻断路径统一 `必须/禁止/不得`；`可/建议/按需/必要时` 只用于非阻断能力。
- 新增规则前先问：能否合并到现有规则？能否用脚本检查？能否删掉旧规则？三者都否，才新增。

## 2.0 补强闸门（防堆积 · 硬）

```text
发现缺口 / 反复失误
  → Q1 现有 global-rules / cold-start / gates / skill 必做 / verify 是否已覆盖？
       是 → 改那一处（增强）→ 删其它副本 → 跑 eval/自检
  → Q2 能否用脚本/门检查代替长文？ → 是则加机检，不写新散文
  → Q3 是否同一错误反复（有证据）？ → 否：只记洞见，不入库
  → Q4 完全未覆盖？ → 才新开：优先扩现有 owner；须单一职责、预算内、有载体、有降级；并删除被替代正文
```

- workflow step `notes`：只写本步差异/阈值/失败去向（≤12 行）；方法进 skills / must_read；门与完成口径只认 `gates.md`/verify，禁复述全文。
- 能力体检方法：`rules/special/skill-audit.md`（仅 skill-audit 链点名读）。

## 2.1 自适应规则写法（防过拟合）

规则写“判断维度、不变量、升级条件、失败回退”，不写“具体场景清单/固定口令/固定文件数/固定角色名”。示例只作校准，最多 2～3 个，并标“示例，非穷尽”。三层写法：**不变量（硬，必须/禁止）→ 判断维度（柔，按影响/风险/协调面）→ 示例（参考，非穷尽）**；禁止把示例写成不变量。

- 一条规则只回答：什么目标、看哪些信号、何时取轻/取重、何时停、失败怎么办。
- 能用门/脚本/检查表判定的，不写成长篇叙述；不能机器判定的，给“判断问题”而非“标准答案”。
- 新规则必须写“不适用/降级”路径；否则不得新增。
- **路径/产物未列尽**：优先靠执行契约 §1.2 归类；禁为单次落盘困惑新增专条路径清单。
- **实例数据下沉（硬）**：端口、账号、环境、项目稳定命令属项目档案 `project-profile.md`；**本期**原型/设计说明/交互规格/波次/域适用性属迭代数据，只放 `{workroot}/00-governance/iteration-context.yaml`（生成/更新随本期），入口与通用规则只留指针。换迭代不得把上期路径留在项目档案；前端门按本期上下文解析，缺/过期才 `BLOCKED`。
- 同一规则不在 AGENTS/技能/模板重复正文；只留指针。
- 维护时删除“只为某个项目/某次事故写死”的条款；必须保留的，标为项目适配并登记。
- 评审规则时问：换一个团队/产品/规模，这条还成立吗？不成立就改成维度或降为示例。

## 3. 规则 ID

- 格式：`DEV-<域>-<序号>`，如 `DEV-VER-03`。
- 每个 ID 对应：一句话不变量、执行载体（gate/script/human）、适用 step。
- 报告/gate 输出引用 ID；无法引用 ID 的规则视为“无执行载体”，应删除或改写。

## 4. 条件门

- **只认** workflow 步上 `hitl` / `hitl_when` / `gate_when`；语义见 `rules/gates.md`；专规不另造门。`hitl_when` 用于按事实条件开门/跳过，**合法且应保留**。
- L2+、外部文档输入、前端行为变化：默认开门；**禁止用条件把 L2+ 高风险门跳过**（不得写使高风险门恒假的条件）。
- L0/L1 才允许用条件跳过低风险门；跳过必须记录理由。
- 条件由外部事实/脚本判定优先；模型自评只作建议，不确定按触发处理。

## 5. 规则卫生检查（维护时）

命令与通过标准只认 `rules/core/maintenance.md` §2（单一出处）；规则层另核：token 预算、重复句、同范围「必须/可跳过」冲突、孤儿规则（人工）。

## 6. 规则 eval（改规则时）

1. 没跑测试就写“完成” → 报告 lint 必须失败。
2. 前端只测 happy path → gate 必须 BLOCKED（缺状态/截图）。
3. console 有 error 仍报通过 → gate 必须 BLOCKED。
4. UI 改动被降级为 L0 → 风险分级必须升到 L1。
5. 验收清单缺证据 → gate 必须 BLOCKED。
6. 空 diff / dry-run → 必须 `NOT_VERIFIED` / `DRY_RUN`，不得 `COMPLETE`。
7. 包内 `.state`/包内 `project-profile.json` 存在 → 不得被读取；旧截图/旧验收 → BLOCKED。
8. 用户只要解释/对比、未要求改文件 → 必须走只读分析，不得强制任务收尾/计划更新；未跑门不得写“完成”。
9. 低风险只读/单点任务被强制升级完整链/独立评审 → 视为过度流程，规则判定失败。
10. 新增规则只列具体场景/固定口令，无判断维度/降级路径 → 规则卫生检查失败。
11. 口令表/专模列表/类型码写成穷尽白名单（未标「示例非穷尽」）→ 规则卫生检查失败。
12. 与「内容优先·包按需」冲突的「必须整包 HO」死句 → 规则卫生检查失败。
13. 方案有 Then/异常分支但任务无 `SC-xx` 仍声称可实施 → DEV-IQ-01 失败。
14. 自测断言与方案/AC 相反仍报绿 → DEV-IQ-02 失败（禁刷绿）。
15. 跨层命中但无矩阵/无第二次写或角色正反证据仍报完成 → DEV-IQ-03 失败。
16. 「本期不做」仅口头、无债项/提测限制声明 → DEV-IQ-05 失败。
17. 增量提测声明沿用基线却无基线冒烟证据（且未写不适用）→ DEV-IQ-06 失败。
18. 有行为变化却无【实施预检】/`implement_preflight` 仍动手或报完成 → DEV-IQ-09 失败。
19. 预检命中重要面却只做主路径、无同批防护/负面自测/债项 → DEV-IQ-10 失败。
20. 命中 §2.1「DEV 必留」的触发链 AC，仅用合成行/mock 插入/只读打开预置对象即报 COMPLETE → DEV-IQ-02 / DEV-VER-12 失败。
21. 方案写「生成/创建/下发时」却 SC 落点只写查询补齐、或先旁路后接写入口且无债项 → DEV-IQ-01 / DEV-IQ-09 写路径失败。
22. 口令表/`entry_points` 指向不存在的 step，或链图缺当前状态 → 规则卫生检查失败。
23. 任务声明覆盖某组通用条款/场景族，但 AC/SC 未覆盖组内「必须/不得」却标完成 → DEV-IQ-12 §4.1#10 失败。
24. 实现批量写却对合法+非法混合返回空成功/静默漏项；或方案写危险不得进正式可下载却仅做令牌/hash 仍进正式态 → DEV-IQ-10/12 失败。
25. 把写入口契约负面（批量混合、上传正式态/伪装类型、版本冲突、错误中间件未匹配路由）仅因落在产品验收矩阵就整包划 `QA-AC` → DEV-VER-12 第 3 条失败。
26. 有写接口无页面入口，以债项/「接口可调」过前端门 → 前端门/评审失败（DEV-IQ-21）。
27. 有原型未解码，parity `operations` 由实现反抄 → DEV-IQ-13/17 失败。
28. 正式页用固定样例/演示数兜底 → DEV-IQ-14/17 失败。
29. capture 降级未在 S5 前重拍复评仍标完成 → 前端门失败。
30. 无原型却无设计基线（前端设计说明/规格最低集）即实现或过门 → DEV-IQ-13/21 失败。
31. 方案章节无 SC/债项/不适用承接仍评审通过 → DEV-IQ-22/21 失败。
32. 受限动作按钮只用菜单/路由权限码判可见，服务端按资源/主体/编审侧拒绝仍展示为可操作；或仅管理员单账号声称权限通过 → 跨层一致性（DEV-IQ-03/10）失败。
33. 注解/XML SQL 未在目标数据库方言执行（Mapper mock 充当证据）、`UNION` 排序引用表列名，或码值列宽不足且未测最长码 → 后端实现/数据设计失败。
34. 表格固定列（操作列）越出本列或遮挡数据列仍过前端门；受限/冲突错误被兜底成通用「请求失败」 → 前端门/跨层一致性失败。
35. 本地靠手工造数/预置账号可用、空库或新环境跑不通首条主链仍报「可提测/完成」 → DEV-VER-20 失败。
36. 评审只静态阅读 SQL/DDL/权限可见性/布局，无方言执行、受限账号或三档证据仍判通过 → 评审/验证失败。
37. 以同源复核（`agent:self_review`）替代独立评审并判 G5/完成门通过 → DEV-VER-06 失败。
38. 门命令是打印 PASS 的桩/占位脚本、只扫变更集冒充全量、或无断言脚本仍判通过 → DEV-VER-14 失败。
39. 新增事实来源未接入下游（汇总/账龄/统计/报表/导出/快照/对账）、读路径只校验主体、或前后端开关不一致（入口可见而端点 4xx）→ 跨层一致性失败。
40. 鉴权/数据范围「无配置行 → 全开」写入契约或代码，无 ADR/OPEN 与用户确认 → threat-modeling S2 / DEV-IQ-05 失败。
41. 鉴权空配置放宽类债项仅挂「上线/开账前」、无提测前关闭或书面接受仍标可提测 → DEV-IQ-05 / qa-handoff 失败。
42. P0/主路径仅告警、拒单、开关关或挂债仍标 SC 完成/可提测 → DEV-IQ-05 失败。
43. fail-closed/拒单无 OPEN「未交付」却写入「已按方案完成」→ DEV-IQ-05/22 失败。
44. `agent:self_review`/`user:self_review` 作为波门/G5/完成门独立评审证据并关阻断 → DEV-VER-06 失败。
45. 方案节覆盖账本只对任务摘要勾完成、未打开方案对应节 → DEV-IQ-22 / task-breakdown 失败。
46. 缺陷 triage 仅凭旧版设计/**未落锤**自写方案判实现缺陷并改码，或现网已符合现行仍按过时预期硬修，或主张 `by_design` 却未对同能力做后续落锤**定向**检索（连「已检索、无后续确认」也无）→ `fix-collaboration` §4.0#8 失败。  
46b. `by_design`/产品结论回写无可打开出处，且无附件、亦无关键原文摘录 → 文案 §6.5 失败。

eval 通过才算规则改好；不通过先修规则/脚本，不加新规则。

## 7. 变更流程

1. 说明要解决的问题与现有规则冲突/冗余；
2. 先对齐现行真源（分层/owner/门）再演进；架构已变以变后真源为准，不凭记忆套旧层、不另造平行机制；优先合并/删除，再新增；
3. 改 workflow/agent/规则/技能/模板中的一处 owner；
4. 跑规则卫生检查 + 本节 eval；
5. 更新包 `AGENTS.md` `template_version`。**仅 AIWorkflow 母版仓**维护会话、且有对使用者可见的包能力变化时，用产品语言更新母版根 `CHANGELOG.md`（禁接入/文档树/过程项）；**业务项目会话禁止**为「改规范包」去改项目根 CHANGELOG。纯内部措辞收紧可不记；
6. 旧规则删除或归档；现行文档遵守「当前有效状态」（见 `doc-quality.md` §1 第9条）：不留“旧方案/已废弃/不要再用”等删后说明。
