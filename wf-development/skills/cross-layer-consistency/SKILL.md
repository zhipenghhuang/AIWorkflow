# 跨层一致性与覆盖矩阵（技能 · 随包生效）

> 用于：L2+/L3；任何涉及权限、状态、数据基数、唯一约束、多表面（列表/详情/预览/打印/归档）或跨层（UI/API/DB）的变更与缺陷。
> 不用于：纯文案/样式、单文件且无行为变化（L0）；不适用时一句话说明，不硬套矩阵。
> 与相邻技能：需求用 `requirements-and-spec`；方案用 `solution-design`；数据用 `database-design`；接口用 `api-design`；实现用 `frontend-implementation`/`backend-implementation`；开发自测用 `implementation-and-selftest`；评审用 `code-review`。独立测试轨不在本技能范围。本技能只回答一件事：**同一业务事实，是否在所有层说同一种话、走同一个判定、被同一组开发自测证明。**

## 1. 先判是否命中

- 命中任一条：角色/权限/数据域；状态/水印/可归档；附件/明细/多页/多份；唯一约束/幂等/重复提交；同一事实在 UI/API/DB/文档多处出现；缺陷现象跨层。
- 未命中：在方案/任务卡写「不适用 + 理由」；不要用矩阵替代真正的设计。

## 2. 四张矩阵（L2+ 必须落；L1 命中项至少落 1 张）

### 2.1 需求追溯矩阵

| 需求点/Then | 来源 | 方案 | 任务 | 自测 | 证据 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| US-xx / AC-xx | 文档路径§ | 方案§ | T-xx | 用例/命令 | 路径/输出 | 未开始/完成 |

- 每个 `Then`、每个异常分支、每个「可补充/重新上传/重复/空列表/非法跃迁」都要有一行。
- 每行必须有自测与证据；没有自测的 `Then` 不得标完成。
- 自测预期来自方案/AC，不来自现网实现；自测与方案冲突时停下报告，不改预期迁就代码。

### 2.2 角色/权限矩阵

| 角色 | 能力 | 数据范围 | UI 入口 | API | 允许/拒绝 | 自测 |
| --- | --- | --- | --- | --- | --- | --- |
| admin/clerk/leader | 查看/新建/编辑/归档 | 全局/本人/关联 | 显示/隐藏/禁用 | 方法+路径 | 200/403/404 | 正向 + 反向 |

- 每个角色至少一条「允许」和一条「拒绝」；只测管理员或只测拒绝都不算覆盖。
- UI 可见动作必须有同权限 API；API 拒绝时 UI 不得继续展示为可操作；只在 UI 隐藏不算覆盖。
- **判定源同源（硬）**：前端「可见/可用」必须复用服务端同一判定的只读投影（同一权限码 + 同一资源/主体范围 + 同一编审侧/金额阈值）；禁止只用菜单/路由权限码近似资源级授权；服务端判定含主体、编审侧、金额或范围时，前端须有对应授权查询接口或等价能力。
- 权限判断只允许一个服务端策略层；禁止各视图各写一套 `assert_*`。
- 403/404 语义明确；业务冲突用 409/业务码，不用 500。

### 2.3 状态/表面矩阵

| 状态 | 列表 | 详情 | 预览/打印 | 归档/导出 | 标签/水印 | 允许动作 |
| --- | --- | --- | --- | --- | --- | --- |
| draft/formal/archived | … | … | … | … | … | … |

- 同一状态在列表、详情、预览、打印、归档中不得出现互相矛盾的标签/水印/可操作项。
- 每个状态至少一条正向和一条非法跃迁；终态重入要明确。
- 「正式」由单一谓词决定，不能一个页面看 `status`、另一个页面看 `summary.pass`。
- **时间口径（硬）**：日期时间格式化单一源；列表/详情/**导出·打印·归档·文件元信息**同 TZ/口径；只改读接口或只改页面展示不算齐。

### 2.4 数据形状/写路径矩阵

| 对象 | 0 | 1 | N | 首次写 | 第二次写 | 重复/并发 | 既有行但缓存空 | 约束/错误码 | 自测 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 附件/明细/结算单/审批 | … | … | … | … | … | … | … | … | … |

- 多值对象必须覆盖 0/1/N；只测「第一次成功」不算多值。
- 唯一约束/索引就是业务规则：写清「一个槽位代表什么、谁分配下一个槽位、冲突怎么处理」。
- **含删占用（硬）**：若物理唯一键在逻辑删除/归档后仍占用槽位，序号分配与查重必须计入含删/全量占用集（或等价策略）；只扫存活集 → 视为未覆盖冲突路径。
- **精度/校验谓词**：金额/数量等跨单据或多写入口共用同一拒绝谓词；禁只修一个入口、他入口静默 round/超精度入库。
- 必须测：第二次写、并发写、重试、既有行但 JSON/缓存列表为空、同内容不同文件名；有软删时另测「删后再建同槽」。
- 关系行与 JSON 旁路只能有一个事实源；否则必须写对账/修复机制并自测。

## 3. 单一判定谓词（Single Predicate）

1. 每个业务判定只定义一个服务端谓词/函数，例如 `is_formal(settlement)`、`can_archive(review)`、`can_view_customer(user, customer)`。
2. 列出所有消费方：列表、详情、预览、打印、归档、导出（含文件元信息）、统计、通知；全部调用同一个谓词（含时区/精度/就绪态）。
3. 谓词名必须带范围：`trade` / `settlement` / `review` / `version`；禁止用交易级结论代替单据级结论。
4. 同一 fixture 下逐个消费方断言结果一致；范围不同则写清边界并各测一次。
5. 发现第二个判定入口 → 先合并，再改功能；不得让两个入口长期并存。

**反例**：生成前检查按「本张结算单引用范围」过滤，预览/归档却用「交易全量核对」的 `summary.pass`；结果生成成功、预览显示草稿、归档 409。

## 4. UI / API / DB 契约

- **UI 可见即可用**：页面/菜单/按钮/字段可见 → 对应 API 必须允许；不允许时隐藏或禁用并说明原因。前端隐藏不是授权。
- **服务端为准**：资源级权限、数据范围、状态校验都在服务端；前端只做体验。
- **错误语义**：唯一约束/重复写/状态/版本冲突 → 客户端可消费的冲突响应（稳定业务码 + 可读文案，常见 409）；不得把约束异常或乐观锁失败直接漏成裸 5xx。对外 API 的未捕获异常若仍返回 5xx，亦须有稳定信封/可读提示（禁仅状态码无文案）；**未匹配路径/方法**同构信封，禁框架 HTML/URLconf；前端不得静默吞掉。
- **错误文案不吞码（硬）**：受限/冲突类错误前端必须保留业务码与可读原因；后端已给业务码时禁降级为通用「请求失败/操作失败」。
- **同一状态同一文案**：`draft/formal/archived` 等标签、水印、页脚由同一映射产生；禁止各页面各写一套。
- **同一事实一个来源**：JSON 列表与关系表并存时，明确主源；另一侧只做缓存/展示，并提供对账或重建。
- **契约自测**：角色正反、状态正反、第二次写、空缓存+既有行，至少各一条；有软删唯一键时含「删后再建」。

## 5. 缺陷根因与同类路径

修复前按层归因，禁止只写「代码写错了」：

| 层 | 要回答 |
| --- | --- |
| 需求/AC | 方案是否写了该分支？开发是否抽成 `SC-xx` 条款清单？验收是否覆盖？ |
| 设计 | 是否缺少单一谓词/权限矩阵/状态矩阵/数据基数？ |
| 数据模型 | 唯一约束/索引/归属/生命周期是否与业务语义一致？ |
| 实现 | 是否绕过既有模式、复用错层、异常未转换？ |
| 开发自测 | 是否只验 happy path、自测预期是否抄实现？ |
| 文档/治理 | 继承需求是否漏进当前迭代验收？ |

**同类路径扫描（强制）**：

- 同一模型的其他写入口（例如单据附件 vs 盖章附件）。
- 同一谓词的其他消费方（预览/打印/归档/统计）。
- 同一权限策略的其他端点/菜单。
- 同一状态的其它表面（列表/详情/导出）。
- 原单期望写明「统一错误/同类入口」时，把同类写入口、统一错误信封、**错误中间件/全局 404·405**纳入扫描，不得只修标题主路径。
- 用 grep/搜索列出命中；逐条判断「同缺陷/已正确/不适用」，不能只修原单。

**回归**：原缺陷用例 + 每个同类路径各一条；缺陷单内部记录「根因层 / 同类路径 / 规则缺口 / 回归证据」。

## 6. 判定 / DoD（硬门 · 对齐 DEV-IQ-03）

> 命中本技能时，下列未勾不得标任务「完成」、不得报完成门全覆盖通过（可 `PARTIAL` 并列缺口）。细则 `rules/core/implementation-quality.md`。

- [ ] 四张矩阵已填（或逐项写不适用+理由）；每行有自测/证据。
- [ ] 每个 `Then`/异常/角色正反/第二次写/空缓存+既有行都有用例。
- [ ] 单一谓词已命名，消费方列全；无平行判定入口。
- [ ] UI 可见动作与 API 权限一致；403/404/409 语义正确。
- [ ] 受限动作按钮判定源与服务端同源（非菜单码近似），有受限账号「禁用/拒绝」+ 授权账号「可用」各 1 条证据。
- [ ] 唯一约束/多值对象的 0/1/N 与冲突路径已测。
- [ ] 缺陷已做同类路径扫描，原单+同类路径均有回归。
- [ ] 自测预期能指回方案/AC；不存在「自测断言与方案相反」。
- [ ] 以上证据写入任务卡/评审记录/缺陷记录，不只在对话里说。
- [ ] 验收清单/任务卡已标 `cross_layer: done|na`（取重时不可空）。

## 7. 反合理化

| 常见说法 | 现实 |
| --- | --- |
| 「主路径跑通就行」 | 权限、状态、第二次写、空缓存往往才是缺陷所在。 |
| 「UI 已经隐藏了」 | 隐藏不是授权；API 必须独立校验并测拒绝路径。 |
| 「唯一约束是数据库的事」 | 约束就是业务槽位规则；写入路径必须知道如何分配/冲突处理。 |
| 「软删了就不会撞唯一」 | 物理唯一仍占用则分配/查重必须计入含删集；否则删后再建必崩。 |
| 「第二次上传是边缘场景」 | 方案写了「可补充/重新上传」，它就是主路径。 |
| 「冲突变 500 先顶住」 | 约束/状态/版本冲突须业务码；裸 5xx 与无文案信封都算契约缺口。 |
| 「列表时区对了就行」 | 导出/元信息/打印同口径；只改一表面不算齐。 |
| 「自测过了就说明需求对」 | 自测可能把错误实现固化成预期；先对方案再对代码。 |
| 「方案没写就不用做」 | 方案写了目标/Then，就要补出可验收分支；缺分支是方案/分析缺口，不是不做。 |
| 「这是历史代码，不是本轮」 | 本轮声称交付/验收，就要对继承能力的当前行为负责。 |

## 8. 红旗

- 自测断言与需求/方案相反，或自测名写着「不能」但方案说「可以」。
- 同一状态在列表显示正式、预览显示草稿、归档又报失效。
- UI 显示按钮，API 返回 403/500；或只测管理员。
- 第二次上传/第二次提交/并发写/版本冲突直接 500；或约束冲突无稳定业务码。
- 软删后同槽再建撞唯一/500，分配只扫存活集。
- API 未匹配路由返回框架 HTML/URLconf；或只修列表时区、导出元信息仍偏。
- 关系表已有行，JSON/缓存列表为空，代码却假设「没有」。
- 只修原单，不搜索同一模型/谓词/权限/状态的其他入口；或原单写了统一错误却未扫同类入口。
- 方案/任务卡没有矩阵，却在收尾写「已覆盖全部 AC」。

## 9. 输出

- 矩阵落点（方案/任务清单/验收清单/缺陷记录）与行数。
- 单一谓词名称、消费方清单、一致性自测命令。
- 角色/状态/数据形状/第二次写的自测结果与证据路径。
- 同类路径扫描结果：命中文件/入口、判定、回归证据。
- 规则缺口：哪条规则/技能没拦住，建议改本包何处（先拟改/原因/影响，用户确认后改）。
