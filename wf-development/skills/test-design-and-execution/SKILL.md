# 测试设计与执行（开发自包含链 · 随包生效）

> 用于：`solo.test`；`solo.test_plan`（测试分析与计划）；`change.verify` / `iterate.gates` 在无 QA、且触及用户路径/业务规则/接口行为时**必用**（见 `lightweight.md` §4.1）。
> **思想（对齐完整测试轨 · 轻量）**：真源 = **意图 INT + 可观测 Oracle**；计划不预生成全量用例表；执行时按意图对照原文生成场景并落报告；**以意图终态为准**，不以场景条数/通过率替代。
> 目标：按风险完整做**开发测试/自验**——回答「这次改动能不能用」；大改动/高风险全节；不是堆用例数量，也不是版本准出。
> 边界：不替代完整测试包的测试计划库/用例库/覆盖三闸/准出门；结论用语写「开发测试/自验 / 可交付」，禁写「已准出」。
> 口径：`rules/core/lightweight.md` §4～§4.1；门禁与证据见 `verify/README.md`；P0 意图未过不得判整体通过。
> 不确定「是否要正式测 / 是否够自验」→ 推荐路径 + 一问确认，不静默跳过用户路径。

## 0. 只测已实现（硬）

- 测试对象必须是已部署、可操作的行为；功能未实现/接口未接/页面缺失 → 不写“待测条件”，直接退回 `DEV` 或产品书面裁剪（见 `verification.md` §2.2）。
- 不得把开发缺口写成「条件通过」；测试无法验证不存在的能力。
- `DEV` 清零或已裁剪+债项后，才按本技能设计/执行测试。

## 0.1 AC 走查（硬）

先按 AC 来源回指打开**方案对应段**，再合看原型/接口/现有实现；理解包/任务卡摘要只作索引补漏（不替代方案完整覆盖）：每条 AC → 通过 / 失败 / 未测+理由；未走查不得写 PASS。不只依赖分析或单一来源；走查可与意图台账合并，但 AC ID 必须可对账。派生文档与方案不一致 → 记实现缺陷或停工确认，不以派生文档改预期。方案示例/死边界/旧数据只作意图锚点，按当前环境择优并记偏离；判不了且影响验收 → 一问，不照抄死脚本（DEV-IQ-22）。

## 0.2 术语

| 词 | 含义 |
| --- | --- |
| **意图 INT** | 可独立判定的测试承诺（用户能… / 系统须…）；可独立证伪的规则默认分列 |
| **Oracle** | 可观测终态（界面/响应/状态/日志可见事实）；**禁主题句**充数 |
| **场景** | 执行时按意图对照原文生成的一次验证；不必预写全表 |
| **意图终态** | 通过 / 失败 / 阻塞 / 未测；**准绳**；场景结果只服务意图结论 |

## 1. 先建测试卡（5～10 行）

在测试分析与计划、方案卡「测试」节或报告开头写清：

| 项 | 内容 |
| --- | --- |
| 变更点 | 改了什么（文件/接口/页面/规则） |
| 影响面 | 直接受影响 + 邻接（谁调用、谁展示、谁依赖） |
| 风险 | 主链路阻断 / 数据 / 权限 / 资金 / 兼容 / 性能 / 安全 |
| P0 意图 | 不过就不能交付的 1～5 条 INT（含 Oracle） |
| P1/P2 意图 | 重要/按风险；处置=测均须终态 |
| 覆盖摘要 | 主路径/边界/异常/权限（适用）是否有 INT；不预写逐步脚本 |
| 环境/数据 | 构建、URL、账号、测试数据、清理方式 |
| 不测 | 明确不测项 + 理由 + 接受人 |

**P0 判定**

- 主业务链走不通、数据错/丢、越权、资金错、核心页面打不开 → P0。
- 拿不准向上一档；P0 不因「实现简单」降级。

## 2. 意图台账（计划真源 · 不预写全量用例）

`solo.test_plan` 按模板落盘：AC 账本 → **意图台账（INT + Oracle）** → 影响面/风险/覆盖摘要 → 执行总排。

**硬规则**

1. 每条 AC ≥1 条意图；可独立证伪的规则默认分列，禁为「少行数」合并。
2. 每条意图必须有可观测 Oracle；无 Oracle = 不合格意图。
3. **禁**：预写逐步用例脚本表、用「测试点/TC」代替意图、主题句 Oracle。
4. 口径/预期变更 → **先改意图台账 Oracle**（记变更），再执行；禁按过时预期判过。
5. P0/P1/P2 均为覆盖义务（处置=测须有终态）；P0 未过不得整体通过。
6. 不预生成全量用例 **≠** 可浅测：执行仍须按风险生成足够场景证伪意图。

**执行时场景生成（按顺序展开，不跳）**

1. **主路径**：用户从入口到结果的完整故事，至少 1 条成功场景。
2. **规则/状态**：合法状态迁移抽样；有状态对象至少 1 条非法跃迁。
3. **边界**：数字/长度/时间/金额/分页取 `min-1 / min / max / max+1` 代表值。
4. **权限/数据域**：跨角色/租户至少 1 条；文档未声明时做角色冒烟，不假装已覆盖。
5. **异常/失败**：空值、重复提交、网络失败、超时、脏数据、依赖不可用。
6. **写操作**：失败或写后回查 + 清理（可并入主场景）。
7. **UI/体验**：布局、遮挡、截断、空态/加载/错误提示、按钮状态、文案；截图同帧检查。
8. **回归**：原失败意图 + 冒烟子集 + 影响面；稳定主链路优先脚本。

**技法速用**（生成场景时用，不是预写库）

- 等价类 / 边界值 / 判定表 / 状态迁移 / 场景法 / 错误推测——同前；不穷举同类。

**最小覆盖（与变更类型匹配 · 落为意图+执行场景）**

| 变更 | 至少覆盖 |
| --- | --- |
| 纯文案/样式 | 受影响页面 + console 无 error |
| 前端行为 | 主路径 + 1 边界 + 1 异常 + 受影响回归 |
| 后端/接口 | 主路径 + 1 边界 + 1 错误码/权限 + 受影响回归 |
| 数据/迁移 | 上述 + 迁移前后核对 + 回滚路径 |
| 高风险 | 本表全节 + 回归/安全/回滚证据 + 独立 verifier；不换链 |

## 3. 执行

**前置**

- 构建/环境可访问；账号/数据就绪；知道本次构建对应的提交。
- 先读方案卡 AC 与**本轮意图台账**；按 AC/意图来源回指原文；Oracle 来自原文/AC/契约/用户裁决，不按现网实现或派生摘要改预期。
- **判定对账**：每条 AC/意图落结果前打开来源对应段；验收「判定」只认可观测结果（对照 Oracle/AC Then），禁「看起来正常/无报错」；入口自身失败≠前置阻塞（有界穷尽后才阻塞）。
- 记录开始时间；截图/证据必须晚于任务开始。

**顺序**

1. 先冒烟：P0 主链路能不能通；不通先停下报 P0，不继续铺量。
2. 再按处置=测意图生成场景：主路径 → 状态/规则 → 边界 → 权限 → 异常。
3. UI 变更先看页面，再看 Network；不猜未见 API，不拿别的接口替代。
4. 写操作查回显/列表/详情/状态；结束后清理测试数据。
5. 前端看 console error、失败请求、关键响应、桌面/移动视口、空态/错误态。
6. 发现意图外的问题（布局/console/network/文案）记额外发现，不静默忽略。
7. 每个意图给终态；报告以意图表为准绳，场景表为摘录。

**证据**

- 失败：截图钉住断言面 + 最小复现步骤 + 环境/账号/时间；能取日志/响应就取。
- 通过：至少一条可复核证据（命令输出/响应/截图路径）；不写「已验证」了事。
- 证据路径必须存在；聊天里说「测过了」不算。
- 真实 PII/密钥不入证据；测试数据用合成数据并清理。

## 4. 失败分类

| 分类 | 判定 | 处置 |
| --- | --- | --- |
| 实现缺陷 | 需求清楚，代码行为不符 | 修代码；修后回归 |
| 产品问题 | 需求冲突/缺失/不可行 | 停下问用户；不按现网实现改预期 |
| 环境/数据 | 环境不可用、数据错、依赖缺失 | 修复环境/换数据；记录阻塞 |
| 测试问题 | 步骤/Oracle/数据写错或过时 | 刷新意图台账后重跑；不计产品缺陷 |
| 待定 | 证据不足/偶发 | 有界复现 2 次；仍不确定记频率与缺口，不硬判 |

**严重度**

- S1 阻断/数据错/越权/资金错；S2 主功能受损但有绕过；S3 一般；S4 文案/体验。
- 拿不准一问；不把 S1 写成「小问题」。

## 5. 修复与回归

- 每个失败修复后立即跑：原失败意图 + 冒烟子集 + 影响面组；不等批末。
- 同一方案无效 2 次 → 换路径或升级，不继续重试刷绿。
- 回归结果就地覆盖，只留最新；报告写轮次与遗留。
- 已脚本化的稳定回归优先脚本；脚本失败先分诊（产品/环境/数据/脚本），不直接判产品缺陷。
- 不手改结果表、不跳测试、不禁告警凑绿；豁免须用户批准并记录。

## 6. 报告

计划用 `rules/templates/40-delivery/solo-test-plan-template.md`；报告用 `rules/templates/40-delivery/lite-test-report-template.md`。

报告最少：

- 范围/环境/构建/测试时间；AC 走查；
- **意图终态表**（准绳）+ 本轮场景摘录；
- P0/P1/P2 意图汇总；失败项分类/处置/回归；
- 未测项/缺口/风险接受；
- `verdict: PASS | CONDITIONAL | FAIL`。

**判定（开发自验）**

- `PASS`：P0 意图全过，AC 走查齐，P1 无阻断，证据可打开，缺口已列。
- `CONDITIONAL`：P0 全过，剩余缺口非 P0，用户明确接受并记录接受人/期限。
- `FAIL`：任一 P0 意图未过、AC 未走查、证据缺失、关键路径未测且无法说明。
- 非 PASS 禁用「全部通过/可发布/没问题/已准出」；只能写「开发自验未通过/有条件可交付/阻塞」。
- 同项目已有测试包正式报告/准出 → 引用对方结论，本技能不冒充准出。

## 7. 反合理化

| 常见说法 | 现实 |
| --- | --- |
| 「build 过了就算测过」 | 构建只证明能编译，不证明用户路径能用。 |
| 「主路径没问题，边界不用测」 | 小项目的返工常来自空值/重复提交/权限/超长。 |
| 「先写全量用例表再测」 | solo/开发自验以意图+Oracle 为真源；场景执行时生成；不预写库。 |
| 「场景全绿 = 意图过」 | 须给意图终态；场景通过率不能替代意图结论。 |
| 「这个 API 肯定存在」 | 未见/未调用的接口不能当已验证；先看 Network/文档/代码。 |
| 「重跑一次过了就算过」 | 偶发要看频率与分诊；一次通过可能是偶然。 |
| 「失败不重要，先交付」 | 要记录缺口/风险接受；P0 不得带病通过。 |
| 「AI 说通过了」 | 结论要有证据路径；自述不算证据。 |
| 「测试报告太麻烦，写收尾里」 | 至少写 verdict/P0 意图/缺口；否则无法对账。 |
| 「无 QA / 个人项目不用测」 | 跳过提测单 ≠ 跳过自验；L1+ 用户路径仍须按风险完整。 |
| 「build 绿 + 自验 PASS = 已准出」 | 自验只证本轮可用；版本准出归测试包/测试负责人。 |
| 「看起来正常就算通过」 | 须对照原文/Oracle 可观测断言 + 证据；禁口头通过。 |
| 「预期变了按现网改过」 | 先刷新意图台账 Oracle，再判；不按现网改预期。 |

## 8. 红旗

- 只跑 build/lint，没有用户路径。
- 计划只有「测试点/TC」表、无 INT+Oracle 台账。
- 测试没有环境/构建/账号信息，无法复现。
- 失败没有截图/响应/日志，只有「有问题」。
- 把产品冲突当实现缺陷直接改代码。
- P0 意图未过仍写「基本可用/有条件通过」。
- 测试数据含真实 PII/密钥，或写操作后不清理。
- 报告数字与证据/意图终态不一致。

## 9. 验证 / DoD

- [ ] 测试卡有变更点/影响面/P0～P2 意图/环境/不测项。
- [ ] 意图台账：AC 映射齐；每条有可观测 Oracle；无预写全量用例表冒充计划。
- [ ] AC 走查齐；主路径、边界、异常、权限（适用时）、回归至少各一条场景。
- [ ] 处置=测意图均有终态；失败有证据与分类；修复后已回归。
- [ ] P0 意图全过；非 P0 缺口已列并有人接受。
- [ ] 报告 verdict 与意图终态一致；证据路径存在；用语为开发自验。
- [ ] 未测项显式列出，没有「应该没问题」。
- [ ] 需要正式测试计划库/准出时，已提示转测试包，不在本技能内冒充。

## solo 用法

`solo.test_plan` 写测试分析与计划（AC 账本、**意图台账 INT+Oracle**、影响面/覆盖摘要、执行总排、不测、回归锚点）；**不**预写全量用例表。  
`solo.test` 报告只写执行结果（AC 走查、意图终态、场景摘录、证据、verdict），不重复计划。  
`change`/`iterate` 无 QA 自验仍按本技能 §1～§6；思想同为意图+Oracle，不回退到旧用例表准出。
