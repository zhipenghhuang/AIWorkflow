# AGENTS.md

> **用途**：开发协作 AI 入口。先读本文 → 命中口令打开对应 `workflows/*.yaml` → 当前步只加载 `agents/*.yaml` 与 `技能/`。  
> **位置**：`开发规范/`。与项目根 `AGENTS.md` 冲突时，以项目根为准。  
> **template_version**：`2026.10.21.4`（单点：包内版本以本文为准）。  
> **架构**：Workflow 定义（YAML）+ Agent 契约 + 规则红线（`规则/`）+ 内置专业技能（`技能/`：随包生效、命中步必用）+ 可选能力层（`能力/` 注册表：本机可用即自动使用、不可用降级）+ 文档治理（`规则/工作流.md` §5：落位/命名/归档/根目录白名单）+ **开发计划**（`{文档事实源目录}/开发计划.md`：开发阶段/门/状态/下一步的控制面，L2+ 默认启用）；执行宿主（任意支持 AGENTS 入口与所需能力的 AI 编码工具；要求见 README「宿主适配」节）为执行器。步骤**怎么做**交 AI，不另开规划回合。

## 0. 开工（每任务）

1. **中文**：对话与结论使用中文；输出写现行结论。  
2. **activeContext + 开发计划**：任务前读项目根 `activeContext.md`（2～3 句报备焦点/下一步）；L2+ 项目同时读 `{文档事实源目录}/开发计划.md`，报备当前阶段/门/下一步。无 activeContext 按模板初始化；无开发计划且 L2+ → 按 `技能/development-plan/SKILL.md` + 模板创建（或走 `workflows/control.yaml` init）。稳定真值仍在项目档案与开发计划/正式产物。  
3. **接入状态（一次判定 · 禁止每任务自检）**：  
   - 读 `activeContext.md`：若已有 `开发规范接入：已完成` → **跳过**落地检查，直接按 §3 路由执行。  
   - 无该标记 → 按 `agents/onboard-agent.yaml` **接入清单**判定一次：已具备（`项目档案.md` 已填实、`activeContext.md` 含「当前焦点」或旧版 A/B 节、无占位符残留、文档索引存在）→ **静默**写入接入标记后直接执行；不具备 → 走 `workflows/onboard.yaml`，核验通过后写入标记，再继续原任务。  
   - `规则/tools/Test-Template.ps1` **仅**在：改本包后、用户点名自检时运行；**禁止**每会话/每任务例行开工自检。  
4. **独立判断**：不迎合；先查错误前提、逻辑跳跃与信息缺失；数字/结论/人物尽量核实来源（代码、门禁或文档）；用户有误直接指出依据与风险；主动提示被忽略的变量、成本、偏差与依赖。  
5. **冲突优先级**：用户明确指令 > 项目根 `AGENTS.md` > 本文 > 当前 agent 契约 > 命中专规红线 > 项目规范要点（`项目档案.md` §7）。  
6. **精读预算**：

| 口令类 | 默读 |
| --- | --- |
| 任意已路由 | 本文 → 命中 `workflows/*.yaml` → **当前步** `agents/*.yaml`（禁通读全部 agent）；按步注加载 `技能/` 对应专业技能（随包生效、必用） |
| 护栏细节 | 需要时点开 `规则/` 对应专规（红线/输出骨架）；本轨关键节**读够**——**禁**为省读砍专规（漏约束的返工成本更高） |
| 前后端/交付细节 | 接入后 `项目档案.md` §7（项目规范）、§8（交付治理）、§9（文档归档） |
| 文档治理 | `规则/工作流.md` §5（落位/命名/归档/根目录白名单） |
| 维护 / 查询 | 本文 + 点名 |

同一会话内文件未变不重读；后续步骤 **delta-only**（禁重贴已读稳定规则全文）；探查限定目录/关键词，大范围调查派子代理。

### 0.1 任务分级与最小流程（防过度/不足）

| 级别 | 典型 | 必走 | 可跳过 | 主要产物 |
| --- | --- | --- | --- | --- |
| **L0 微改** | 单文件、无契约/数据/权限/安全影响、≤约 30 分钟 | clarify → implement → verify →（有变更）commit | requirements / design / plan / review / deliver / release | 【任务收尾】六段；必要时轻量需求卡 |
| **L1 常规** | 多文件但范围收敛、无跨系统契约 | clarify →（轻量需求卡）→ implement →（review 按风险）→ verify →（有 QA）deliver → commit | 全量 PRD/ADR/单独计划（多文件时建议轻量清单） | 需求卡/提测单（如交接） |
| **L2 功能/迭代** | 新功能、跨模块、接口/数据变更、多任务 | requirements → design（条件）→ plan → implement → review（按风险）→ verify → deliver → commit → release_handoff（含部署） | 无 | 需求基线/方案/任务清单/提测单/发布说明 |
| **L3 高风险** | 权限/资金/数据迁移/公共 API/安全合规/破坏性 | L2 全链 + 独立评审 + 安全/隐私检查 + 回滚演练 + 发布审批 + 发布后观察 + 复盘 | 无 | L2 + 上线检查单/发布记录/复盘 |
| **缺陷** | 平台缺陷/指派/修复# | `defect-fix`：preflight → pull → fix → gates → menu → close → postrelease | 无平台→change | 总结菜单/备注/发布记录（含部署） |

分级由 AI 在 clarify 步判断并写入首条路由；不确定按高一档。**L0 不强制文档，但证据/提交确认/密钥红线不可省**。  
**L2+ 默认启用《开发计划》**（总览/控制面）；L0/L1 可写「不适用」或轻量开发卡。计划路径：`{文档事实源目录}/开发计划.md`；阶段表/门/证据/下一步必须随进展更新。  
命名：**开发计划=总览全文**（类似《测试计划》）；S3 叫**任务与排期**（任务清单/依赖/估算/DoR/DoD/检查点），是计划里的一个阶段，不单独叫“开发计划”。  
术语：**RP**=Requirement Point（要求点，编号 `R-xx`）；**AC**=验收标准；**DoR**=开工条件；**DoD**=完成定义。

### 0.2 确认门 · 澄清 · 直跑

| 类型 | 规则 |
| --- | --- |
| 确认门 | **只认**当前 workflow 步上的 `hitl:`——标量（条件 `hitl_when`）或列表（各项 `name`+`when`）；条件不满足则跳过该门。专规只提供输出骨架，**禁止**另造确认门 |
| 防重复 | 同一确认点只问一次；同批信息只展示一次（跨步复用已有输出）。固定骨架/菜单/拟提交清单**不得**以「简洁/直跑/不追问」省略或改字段；禁用长文复述规则代替开跑或确认提问 |
| 澄清 | 目标/范围/验收不明或多解 → **一次只问一个**，按回答继续追问至 **≥95%** 再实施；判据＝能复述「谁 / 什么场景 / 做什么 / 系统怎么响应 / 怎么算对」；已唯一 → 1～2 句复述；确认门是授权，不是澄清 |
| 可跳过连续追问 | 三要素已唯一 → 动手前 1～2 句复述即可 |
| 直跑 | 口令命中 workflow → 立即 `route=workflow:<id> | step=… | level=… | next_action=…`；步内条件 hitl 仍执行 |
| 预授权 | 「一次性 / 直接跑完 / 中途不停」＝预授权：默认**只到任务本身完成**，**不含**提交/推送/部署/回写；收到后**声明默认界并直接执行**，仅当口令同时提到后续动作且范围不明时一问；只免**等待**、不免**输出**（§0.8） |
| 少问 | 只问会改变范围/验收/风险的问题；可由档案/代码/计划推断的先按现行值推进并记「假设」，不把确认门当澄清 |

> **实质确认 vs 输出门**：开发计划/版本范围 = `confirm_plan`（首次或范围·版本·里程碑实质变更）；架构级「先方案后实施」的批准 = `change` 设计步 `confirm_spec`；需求基线 = `confirm_requirements`；清单/节奏 = `confirm_backlog`；工程部署 = `confirm_deploy`（若项目另有业务发布决策流程/产品包 `confirm_release`，按其执行，不强制）；验收 = `confirm_acceptance`；回滚 = `confirm_rollback`。其余输出型门（提交/回写/菜单/入库等）一律以步上 `hitl` 为准。  

**可选输入不阻塞**：某步所需资料（PRD/方案/提测单/测试报告/UAT/缺陷单等）不存在 → 一句话说明缺口 → 由用户提供/选择只用已有资料/本包模板补一份；**禁**因缺其它包而阻塞，**禁**擅自启用其它包或强制引用。  
**新输入先吸收**：用户发新文档/聊天变更/确认项 → 走 `workflows/intake.yaml`（收件/分类/影响/局部更新/报告）；**不直接改基线**，不把新文档当完整 PRD。  
**缺陷分流（本包）**：指派给我/我的待修 → `defect-fix`（编号只许平台拉；档案 provider=「无」→ 降级 `change`）；仅 `#数字` 或 `修复#…` → 点名进 `defect-fix`；只描述现象、无平台编号 → `change`。  
**与测试轨分工**（落地通常只启用本包）：提交缺陷/查重/回归验证 → 测试包（若未装则提示换会话/或按现有资料处理）；开发侧提测单可作为测试计划的可选输入（不强制）。  
**可选输入（不强制）**：项目已有 PRD/需求文档（无论来自产品包、文档目录还是用户提供）→ `requirements` 步可引用，只补技术验收/差距，不重写需求；没有则按本包需求卡/用户输入。UAT/业务发布决策若已由其它流程完成 → 引用其结论；没有则本包按需补；`release` 只做工程部署审批。复盘可与已有复盘合并引用。

### 0.3 硬红线（易疏忽 · 准确度）

1. 证据先于结论；未验证不声称完成。  
2. 缺陷：修前红证；**禁修复后回退补红证**；无根因不修；未验证不回写；产品缺陷**先方案评审、确认后才实施**（见 `规则/缺陷修复协作.md` §5）。  
3. **最小改动**；密钥零入库；正式文档只写现行有效状态（§0.9）；旧版归档不堆“最终版”。  
4. 禁刷绿跳过门禁；禁先实现后补测冒充验收；禁改断言/跳过测试/禁用告警凑绿（豁免须用户批准）；git 前拟提交确认（无文件变更可跳过）。  
5. 子代理禁 commit/push/改平台/改确认门；编排核验后再结论；**高风险/大改/破坏性变更：核验者≠实施者**（派独立核验子代理；核验不替代机器门禁）。  
6. 平台备注按专规写全（版式：行间 `<br>`；禁每行 `<p>`/行间空行，见 `规则/缺陷修复协作.md` §6）；备注与状态同轮。  
7. 遇错先析因；同方案无效 **2** 次换路径（**换根因假设或验证手段，禁同命令空重跑**）；缺陷闭环 **3** 次回根因。  
8. **文档不落根**：方案/清单/报告/截图/临时文件进标准目录；根目录只留白名单（§5）；无法分类先问，不擅自删。  
9. **发布不跳门**：未过上线检查单/审批不得部署；验证失败按回滚预案，不恋战。

### 0.4 执行中（效率）

1. 多解需拍板 → 一句权衡再建议；路径唯一则直接做。  
2. 跑命令前确认环境与依赖。  
3. 动手前说明拟改文件；优先直接编辑；仅批量/重复性操作才生成脚本；系统操作优先简单稳定方案。  
4. **增强能力首缺提示（每能力一次）**：命中步骤要用增强能力（清单见 `能力/00-能力注册表.md` §3）而本机缺失 → 该步附一句提示（例：未装 X，已按降级执行；启用说「装配能力」）并记入 `项目档案.md` §6（状态记「未安装（已提示）」）；已安装/已提示 → 静默。  
5. **文档/开发计划同步**：任务产出的需求/方案/清单/提测/发布/UAT/复盘在收尾前落位并更新 `{文档事实源目录}/文档索引.md`；L2+ 同时更新《开发计划》§0（计划状态/当前门/下一动作）、§1（阶段/状态/产出/证据/下一步）、§12（执行日志），见 `技能/development-plan/SKILL.md`。不要留一批未提交文档在根目录。

### 0.5 工程红线

1. 可测逻辑同步补测（无测点除外）。  
2. 不引入未声明依赖；新增依赖看版本/许可证/维护状态。  
3. 外部输入校验；防注入/越权；接口鉴权按接口自校（不假定调用方已鉴权）；外部调用设超时与错误处理；错误不回传敏感信息。  
4. 不改已评审契约；破坏性变更先文档+确认（含回退思路）。  
5. 不动生产数据；破坏性操作先确认；迁移脚本幂等、可回滚/前滚。  
6. 个人信息最小化/脱敏；证据不夹带真实 PII/密钥。  
7. 高风险变更用开关/降级/可回滚路径；发布前有回滚预案。

### 0.6 框架固定 · 局部自主

- **不可让**：口令→workflow 映射、步上 `hitl`/`hitl_when`、专规输出骨架、预授权界（§0.8）、证据/红绿、密钥、子代理边界、接入标记语义、能力注册表取用与降级（**已安装即启用**；未安装=降级路径，禁阻塞或硬编）、文档落位/根目录白名单、文档现行有效（§0.9）。  
- **应交 AI**：步内实现路径、探查顺序、是否派子代理、验证命令、文档措辞、任务拆分粒度（按 `技能/task-breakdown/SKILL.md` 方法）——**禁止**把默认可完成动作写成逐步检查表；**禁止**另造确认门或预防性通读。  
- **规则未覆盖或冲突**：以用户目标、代码事实与既有门禁为先，选最小成本可验证路径；在收尾「假设与未决项」记录取舍，不新增门、不跳红线。  
- **成本**：择优在推理中完成，不另开规划回合、不输出分析长文、不因此增加默读；计划/评审/发布等条件步只在触发时执行。

### 0.7 `hitl` / `gate` / `when` 枚举（YAML 用）

| 标记 | 含义 | 必须行为 |
| --- | --- | --- |
| `hitl:` | 确认门声明 | 标量（单门）或列表（多门；各项 `name` + 可选 `when`）；**未写 `when` 视为无条件** |
| `hitl_when:` | 标量门的条件 | 条件不满足 → **跳过**该门，不算违例 |
| `gate_when:` | 门禁条件 | 条件不满足 → **跳过该 gate**（步骤不跳过）；用于同一 step 跨场景复用 |
| `confirm_change` | 变更吸收/影响 | 出示变更类型/影响矩阵/待更新文档/待确认项；实质变更确认后才更新基线 |
| `confirm_requirements` | 需求基线/范围 | 出示范围/AC/NFR/非目标/未决，确认后冻结；未签收不进设计/排期 |
| `confirm_spec` | 方案评审 | 出示方案要点（范围/接口/兼容与回滚/验收），批准后才实施 |
| `confirm_plan` | 开发计划/版本范围 | 首次创建或范围·版本·里程碑实质变更，出示阶段/门/范围/下一步；确认后计划状态=已确认 |  
| `confirm_backlog` | 迭代清单与节奏 | 出示任务数/RP 覆盖/依赖/风险 + 节奏三选，确认后才实施 |
| `confirm_commit` | 拟提交/推送 | 输出【拟提交】块（见 `规则/工作流.md` §2），等确认后才执行 |
| `confirm_deploy` | 工程部署审批 | 出示版本/窗口/影响面/回滚决策人；未批准不部署；若项目已有业务发布决策，只确认工程侧 |
| `confirm_rollback` | 回滚 | 出示触发信号/步骤/数据影响/预计时长，确认后执行 |
| `confirm_acceptance` | UAT/业务验收 | 出示 AC 覆盖/失败项/遗留风险/发布建议，确认后进审批 |
| `confirm_actions` | 复盘行动项 | 出示行动项/负责人/截止/验收，确认后落盘 |
| `confirm_remark` | 回写前备注 | 出示 §6 备注全文，确认后回写 |
| `confirm_gitignore` | 入库策略 | 四选一确认并写档案、改 `.gitignore` |
| `confirm_docs_migration` | 文档搬迁/整理 | 出示拟搬迁清单与目标，确认后执行；不擅自删 |
| `select_menu` | 缺陷批末菜单 | 输出总结+【用户选择菜单】，精确执行选项 |
| `gate: project-gates` | 项目门禁 | 按 `项目档案.md`「质量门禁命令」跑最小充分集；失败不声称完成 |
| `gate: dev-plan` | 开发计划检查 | L2+ 开发计划存在，阶段表/门/证据/下一步完整；缺项不过 |
| `gate: release-readiness` | 发布就绪 | 按上线检查单逐项核；硬项不过 → NO-GO |

**步骤条件 `when` 词汇**：`new_feature_or_scope_change_or_requested`｜`new_feature_or_architecture_or_breaking_change_or_requested`｜`new_feature_or_architecture_or_breaking_change_or_high_risk_or_requested`｜`architecture_or_breaking_change_or_requested`｜`multi_file_or_new_feature_or_requested`｜`multi_file_or_new_feature_or_high_risk_or_requested`｜`high_risk_or_requested`｜`has_qa_or_deploy_or_requested`｜`has_deploy`｜`has_uat`｜`release_verification_failed`｜`release_failed`｜`release_ready`｜`release_ready_and_acceptance_passed`｜`release_approved`｜`has_deployed`｜`iteration_done_or_incident`｜`recurring_defect_or_incident`｜`incident_or_major_release`｜`docs_migration_needed`｜`requirements_need_confirm`｜`change_is_substantive`｜`backlog_or_pace_changed`｜`plan_needs_confirm`｜`has_pending_commit`｜`code_changed_or_requested`｜`implementation_required`｜`menu_includes_commit`｜`menu_includes_writeback`｜`menu_includes_deploy`。条件不满足 → 跳过该步（及其 hitl）；不确定按触发处理。`release_failed` = 部署失败或发布验证失败/触发回滚条件；`release_ready` = 上线检查单结论 GO；`release_ready_and_acceptance_passed` = 上线检查单 GO 且 UAT/验收通过或不需要；`release_approved` = `confirm_deploy` 已批准；`implementation_required` = 非「只出任务清单」且清单已确认。

### 0.8 预授权与「一次性」界

- **界**：「一次性 / 直接跑完 / 中途不停」等说法为**预授权**，默认只到**任务本身完成**——需求/方案/实现/门禁＋固定输出骨架（如总结/菜单）；**不含**提交、推送、部署、回写、发布审批等后续流程。
- **默认界声明**：收到该类口令，回执中声明「按默认界：只到任务完成，不含提交/推送/部署/回写」并直接执行；**仅当口令同时提到后续动作（提交/部署/回写/发布）且范围不明**时一次一问。按确认后的界执行，不再逐门重复询问。
- **只免等待、不免输出**：固定骨架（清单/总结/菜单/拟提交/回写备注全文/汇报）照常输出；已覆盖的确认门在对应位置附一行【已预授权执行：<组合>】代替等待；未覆盖的门仍按步上 `hitl` 执行。
- **未确认前**：按默认界执行到「做完任务」并输出菜单/总结（`AWAIT_CONFIRM`），**禁**静默连跑提交/推送/部署/发布/回写。

### 0.9 文档现行有效（正式产物 · 不可让）

1. 只描述当前存在的功能、流程、规则与约束；以当前最终状态为唯一事实源，保持简洁准确。  
2. 删除内容后直接移除，不增加「禁止 / 不要 / 已废弃 / 旧方案」等说明。  
3. 不记录历史修改过程、变更原因、取消内容与废弃概念。  
4. 不引入不存在的概念；不确定的写「待确认」，不猜造。  
5. 结论性输出不复述用户原话、修改过程或方案草稿；不把修改方案写入正式产物，正式产物按各自模板写业务内容。  
6. **例外**：变更记录/CR/待决项/DEC/执行日志/复盘等治理留痕可记录变更前后与原因；但不得把“已废弃/旧方案”等历史说明回写到需求基线、方案、任务清单、发布说明等正式产物。

## 2. 收尾

**触发**：工作流末步（含 `wrap` / `commit` / `verify`）、计划驱动全部阶段（S0～S9）结束、或用户点名「收尾 / 总结」时，必须输出本骨架。阶段中途只出 ≤3 行简报，不替代最终收尾；极短只读任务可压缩为 2～3 行，但 6 个字段标签保留。收尾前更新任务清单/文档索引/activeContext/开发计划（有实质进展时）。

**唯一骨架**：迭代交付 / 缺陷修复 / 评审 / 提测 / 发布等专规总结只填第 1 点，不得另起编号或省略第 2～6 点。第 1 点的「可直接复制汇报」给业务 / 上级看：业务语言、量化、结论先行，禁过程词、工具名、commit hash 与内部路径。

```text
【任务收尾】
1. 完成了什么：{一句话结论}
   可直接复制汇报（整段复制）：
   {版本/主题}已完成{功能/修复/交付}共{N}项（完成 {n} 项，{P%}）；{关键链路/接口/页面}已{通过门禁/自测/评审}；{缺陷/遗留/风险一句}。结论：{可提测/可发布/待验证/已交付}。
2. 改了哪些文件：{路径；无改动写「无」}；拟提交：{短列表或「无」}；.gitignore / 文档归档：{一句}
3. 如何验证：{命令+结果 / 门禁摘要 / 评审结论；未验证须明示}
4. 假设与未决项：{列表或「无」}
5. 还存在什么问题或风险：{列表或「无」}
6. 下一步值得做什么：{建议或「无」}
```

- **第 1 点**：数字须与任务清单 / 门禁 / 评审 / 测试记录一致；无问题写「未发现阻断问题」；不写「先…后…」与调试过程。按任务类型取数：实现=任务/RP 数；评审=审阅文件数/缺口数；提测/发布=版本/检查项数；答疑=答复问题数。  
- **第 2 点**：列实际新增 / 修改 / 删除的文件；拟提交、`.gitignore`、文档归档同点；未提交须说明。  
- **第 3 点**：验证＝可复跑的命令 / 门禁＋结果，或「评审通过 / 单测 N 条通过」；未验证不得写完成。  
- **第 4 / 5 点**：假设与风险分开；无则写「无」，不留空。  
- **第 6 点**：给可执行下一步（提测 / 发布 / 回归 / 补文档），不写空泛建议。  
- 门3（提交 / 部署 / 回写）按 YAML 步上 `hitl` 独立确认，不并入 6 点；骨架第 2 点如实写「拟提交 / 已提交 hash / 未提交」。  
- **收尾自检（输出前逐项过）**：① 标题【任务收尾】；② 1～6 字段标签齐；③ 第 1 点含可复制汇报且数字与任务清单/门禁一致；④ 未验证项明示；⑤ 拟提交/部署/回写门按 YAML 独立确认，不并入 6 点。

## 5. 文档治理（摘要 · 细则 `规则/工作流.md` §5）

- **根目录白名单**：代码/构建文件、`README.md`、`产品档案.md`（如启用产品包）、`项目档案.md`、`activeContext.md`、`开发规范/`、`{文档事实源目录}/`、`产品/`（如启用产品包）、`测试/`（测试包）、`.gitignore`。  
- **标准树**：`开发计划.md / 文档索引.md / 资料/（项目文档 + 原始素材 + 资料索引） / 00-项目治理 / 01-需求基线 / 02-设计基线 / 03-计划与状态 / 04-测试与验收 / 05-发布与交付 / 06-复盘与改进 / _归档`；根索引为 `{文档事实源目录}/文档索引.md`；L2+ 开发计划在 `{文档事实源目录}/开发计划.md`（旧项目可在 `00-项目治理/开发计划.md`）；无内容不建空目录。  
- **资料 vs 工作文档**：`资料/项目文档/` 放外部 PRD/方案/设计稿；`资料/原始素材/` 放收件箱/截图/附件；00～06 为工作文档。    
- **命名**：`{类别}-{主题}-{版本或yyyyMMdd}.md`；发布说明一版一档；任务清单确认后冻结；旧版/迭代快照移 `_归档/{yyyyMMdd}-{版本}/`（旧项目可用 `历史/`）。  
- **索引**：`{文档事实源目录}/文档索引.md` 随需求/方案/清单/提测/发布/UAT/复盘更新；只导航不复制正文。  
- **禁止**：方案/清单/报告/截图/临时文件堆根；“最终版/最终版2”并列；覆盖历史发布说明。  
- **接入整理**：onboard `docs` 步一次性归位；既有分类按映射，不强行搬迁；无法判断先问，不擅自删。
