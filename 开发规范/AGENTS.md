# AGENTS.md

> **用途**：开发协作 AI 入口。常驻最小集；命中口令 → `workflows/*.yaml` 当前 step → `规则/读取索引.md` 当前行 → 当前 `agents/*.yaml`。
> **位置**：`开发规范/`。与项目根 `AGENTS.md` 冲突时，以项目根为准；与用户指令冲突时见 §0 第 5 条（可覆盖）。
> **template_version**：`2026.10.30.25`（单点：包内版本以本文为准；与产品/测试交接口径对齐）。
> **架构**：Workflow + Agent + 规则/门/读取索引 + 技能/能力 + 验证层 + 开发计划控制面；落地文档 `review-docs` + `select_review_mode`（自行｜AI，仅完整档），代码审仍走 `review`。

## 0. 开工（每任务）

1. **中文**：对话与结论用中文；写现行结论。
2. **activeContext + 开发计划**：任务前读 `activeContext.md` 总览 + `## 开发` 的 `### 进行中` + 跨包同步；先按 `进行中` 报备任务/状态/下一步（2～3 句），无则按模板补建（只建本包节）。任务开始/状态变化/阻塞/收尾时更新本包 `### 进行中`（只读解释/分析除外，见 `规则/核心/执行契约.md` §1.2）；收尾只改本包分节。多包时禁止改他包分节/他包接入行。L2+ 同时读 `开发/开发计划.md`，报备阶段/门/下一步。
3. **接入状态（一次判定）**：`activeContext.md` 运行时有 `开发规范接入：已完成` → 跳过落地检查；无标记 → 按 `agents/onboard-agent.yaml` 判定一次，具备则静默打标，不具备则走 `workflows/onboard.yaml`。`Test-Template.ps1` 只在改包/点名时跑。
4. **独立判断**：不迎合；先查错误前提/逻辑跳跃/信息缺失；数字/结论尽量核实来源；用户有误直接指出依据与风险；主动提醒用户忽略的变量、成本与偏差。
5. **冲突与覆盖**：默认按本包规则与红线执行。用户指令与规则/红线冲突时：①先不执行冲突项；②说明冲突点、风险与合规替代；③用户再次明确选择按原指令 → **以用户选择为准**并执行。收尾【遵守自检】`deviation=` 按实际情况如实记录取舍（无则写无）。无冲突时：用户明确指令 > 项目根 `AGENTS.md` > 本文 > 当前 agent 契约 > 项目规范要点。红线是默认护栏，可被用户二次明确选择覆盖。
6. **读取协议**：

| 场景 | 读什么 |
| --- | --- |
| 任意已路由 | 本文 **§0 硬节** → workflow 当前 step 块 → 读取索引当前行 → 当前 agent/产物（口令表仅路由未定/首次命中时读） |
| 路由未定/首条 | 本文 §3 口令表或 `规则/核心/入口判定.md` → 再按上行走已路由 |
| 有门/写 YAML | `规则/门.md` 当前行；不通读全表 |
| 验证/收尾 | `验证/README.md` + `规则/核心/验证规则.md` + 检查矩阵 + 验收清单/证据 |
| 交接/变更 | `规则/协作/协作与交接.md` 当前节 + **默认**`通用交接单文档模板.md`（升包才读交接包说明）+ `交接台账.md`；变更按 C0～C3 |
| 前后端/交付 | `项目档案.md` §7/§8/§9；技能按步读 |
| 维护/查询 | 本文 + `规则/核心/维护.md` + 点名 |

同一会话文件未变不重读；后续 delta-only；探查限定目录/关键词。**workflow 文件只读当前 step 块（当前 `- name:` 至下一个），不整文件通读。** **规则阅读不是越多越稳**：读全本会稀释当前步约束。**读取预算（目标，非硬上限）：核心 ≤3～4 个来源（命中才读）+ ≤8k tokens；复杂可至 5；确需更多时只读当前节并在收尾说明，不得为省预算跳过门/证据/红线。** 标 `读取级别：参考` 的大文件只读当前节。

7. **执行契约**：判断模式（execute/analyze/stop）、自主边界、步骤契约、计划同步见 `规则/核心/执行契约.md`。规则是下限不是百科全书；低价值步骤可合并/省略；输出/门/证据/红线默认不可省（用户按第 5 条选择覆盖除外）；跳过与取舍写收尾【遵守自检】，不静默偏离。只读解释/对比/诊断按 `规则/核心/执行契约.md` §1.2，不强行进入交付链；用户要详细时用分析说明，不受只读简报 2～3 行限制。

### 0.0 事实与文档（硬规则）

- 环境/构建/账号/日期/结果/缺陷号/发布窗口/审批结论等事实字段，必须来自配置、命令输出、权威文档或用户确认；未核实写「待确认」并问，禁止用默认/示例/历史值补。
- 生成后回查关键字段；同一事实只保留一个来源；**当前有效状态**：只写当前存在的功能/流程/规则/约束；删除即移除，不追加「已删除/已废弃/不要再用」；不写历史过程、旧方案、变更原因、未采纳方案；对用户输出结论性现行状态，不复述需求与「本次改了什么」。细则见 `规则/核心/文档质量标准.md` §1 第9条；结构完整≠合格。
- 模板/规则/技能可按项目实际适配：发现不匹配或更好做法 → 先出拟改/原因/影响，用户确认后改本包并登记。
- 模板是骨架、标准是底线：按项目裁剪；不适用写不适用+理由；能靠产出文档解决的优先改产出。
- **版本标识分离**：产品/测试版本、构建/制品、部署版本、文档版本分开；测试只认实际部署版本；文档提交不改变项目版本；项目必须暴露版本查看方式（页脚/接口/清单）。**模式/矩阵/环境边界见 `规则/核心/版本策略.md`；项目只写事实与例外。**

### 0.1 任务分级（防过度/不足）

| 级别 | 典型 | 必走 | 可跳过 |
| --- | --- | --- | --- |
| L0 微改 | 单文件/文案/配置；无行为/契约/权限/数据变化 | clarify → implement → verify → commit | requirements/design/review-docs/plan/review/deliver/release |
| L1 常规 | 多文件、范围收敛、无跨系统契约 | clarify →（轻量卡）→ implement →（代码 review 按风险）→ verify →（有 QA）deliver → commit | 全量 PRD/ADR；有新方案则问 A/B |
| L2 功能/迭代 | 新功能、跨模块、接口/数据变更、多任务 | requirements → design（条件）→ **review-docs（A/B）** → plan → implement → review → verify → deliver → release_handoff（条件）→ retro（条件）→ wrap → commit | 无 |
| L3 高风险 | 权限/资金/迁移/公共 API/安全/破坏性 | L2 + 文档/代码独立审 + 安全/隐私 + 回滚演练 + 发布审批 + 观察 + 复盘 | 无 |
| 缺陷 | 平台缺陷/指派/修复#/产品评估/产品回复 | defect-fix：preflight → pull → triage →（fix/assess→handoff→await→decision→align/clarify）→ gates → menu → close → postrelease | 无平台→change |

分级在 clarify 判断并写入首条路由；不确定先按最小充分，高风险/不可逆/跨包再高一档。L0 不强制文档，但证据/提交确认/密钥红线不可省；L0 也不得跳过理解回执（纯机械操作除外）。L2+ 默认启用《开发计划》；路径 `开发/开发计划.md`。

**轻量档**：小项目默认 `solo`；完整档走 `change`/`iterate`。轻量=裁文档厚度，**不**裁 AC/完成门/开发自验；「做个/快速做」仍按体量升级（`规则/核心/轻量交付.md` §0～§2）。拿不准档位 → 推荐高一档 + 一问确认。

**评审分级**：独立代码评审不是每阶段一律强制。L0、以及 L1 中确实低风险/单点的改动可免独立评审；**L2+、L3、权限/资金/迁移/公共 API/破坏性变更不可免**。免审必须在计划/任务清单记录理由与风险接受人；**免审不免自检**——测试/冒烟/证据仍按级别执行（有 `*_scoped` 则定向，否则全仓）。不得把 L2+ 说成“阶段简单”绕过评审；若确实简单，先重定级并记录。

### 0.2 确认门 · 澄清 · 直跑

- **只认 YAML 步上 `hitl`/`hitl_when`/`gate_when`**；档位/语义/何时停 **只认** `规则/门.md`（本处不复述 approve 清单）。条件不满足则跳过；专规不另造门。
- **意图确认择优（硬）**：有歧义/跨角色外发/新开交付 → 先【意图理解】等确认再落盘；意图已清或任务内续跑 → 一行回执即做或免示，**不**凡落盘必停。门=`confirm_intent`（`intent_needs_confirm`）；细则 `规则/核心/澄清.md` §0。禁止含糊口令直接写交接单。
- **澄清（SSOT）**：程序/停止条件只认 `规则/核心/澄清.md`；硬句：不确定项先标 **P/D/S**（§1.1）→**S**/阻塞 **P** 未关闭不实施；「由开发确认」归 **D**。
- **产品资料先解析**：PRD/方案/原型/技术文档 → `技能/product-doc-analysis/SKILL.md`；理解包 **§0 Brief+本期差量表必填**；冲突/方案缺陷入【待确认单】，不反推后端、不静默选边；无 §0 不得拆单/实施。
- **直跑/预授权**：只到任务完成，不含提交/推送/部署/回写；只免等待不免输出；意图门按 §0 择优，不与预授权互相顶替。
- **可选输入不阻塞（≠ 降标）**：他包产物**可选**；缺则一句缺口，**不强制装他包、不阻塞本包**；**不可省** AC 硬门槛/完成门/自验证据（`轻量交付.md` §0）。
- **档位/准出不确定**：solo vs 完整档/是否升级/是否准出 → 推荐 + 只问 1 问，不静默降档或冒充准出。
- **自主边界 SSOT**：必须停/可自主见 `规则/核心/执行契约.md`；本处硬红线与框架固定句为摘要。

### 0.3 硬红线（易疏忽）

1. 证据先于结论；未验证不称完成。
2. 缺陷：修前红证；禁回退补红证；无根因不修；未验证不回写；产品缺陷先评估单/产品确认。
3. 最小改动；密钥零入库；文档只写现行；旧版确认后同批归档；新输入先按 `规则/文档治理.md` §3 分流。
4. 禁刷绿（改断言/跳测试/关告警）；git 前拟提交确认；分支/推送/PR 按 `规则/工作流.md` §2。
5. 子代理禁 git/平台/改门；核验后再结论；高风险/破坏性核验者≠实施者。
6. 文档不落根；发布不跳门；失败按回滚预案。
7. 需求理解先于方案；全局体验（界面减法/UX-DX-AX 不净退化）。
8. **跨层一致**：L2+/L3 或触及权限/状态/数据基数/唯一约束/多表面 → 按 `技能/cross-layer-consistency/SKILL.md` 过四张矩阵；同一业务判定只允许一个服务端谓词；UI 可见动作必须有同权限 API；第二次写/空缓存+既有行/同类路径必须有开发自测与证据。
9. **实施质量（DEV-IQ）**：细则只认 `规则/核心/实施质量门.md`。硬摘要——`SC-xx` 先于代码；**动手前自主【实施预检】（DEV-IQ-09）**；重要面命中同批硬补（DEV-IQ-10）；自测只认方案/AC（禁刷绿）；跨层矩阵未齐不得完成；冲突先 `OPEN`；裁剪债项化；沿用须基线冒烟；异步同批契约；同族缺陷回流。

### 0.4 验证与汇报（硬约束）

1. **完成只认门**：`-StartTask` → `验证/Invoke-Gate.ps1` → `.gate/开发规范/completion.json` 本轮 `COMPLETE`；空窗口/`DRY_RUN` 不算完成；非 COMPLETE 禁用“完成/通过/已修复”。
2. **证据先于结论**；子代理自述不算证据；前端须浏览器验证。
3. **程序 SSOT**：落地文档 A/B、评审分级、成本纪律见 `规则/核心/验证规则.md` + `验证/README.md`（solo/L0 不走文档 A/B；L2+/L3 不可免代码审）。本处不复述流程表。
4. **质量门对账**：有行为变化须对上 `implement_preflight`；取重时另对 SC 追溯、跨层、基线冒烟、债项；缺项不得声称全覆盖完成（细则 `实施质量门.md` §8）。

### 0.5 工程与执行

- **质量条**：`技能/engineering-quality/SKILL.md` + `规则/工作流.md` §3.4；不可省：可测逻辑补测、密钥零入库、外部输入校验、破坏性变更先确认、回滚/降级路径。
- **方案落地**：`实施质量门.md` DEV-IQ-01/02/09/10——抽 `SC-xx`；动手前【实施预检】；重要面同批硬补；自测只认方案/AC。
- **执行**：多解先权衡；跑命令前确认环境与依赖；失败先析因，同方案 2 次无效换路径；动手前说明拟改文件；最小改动；先工具后子代理；不预防性通读；改动面超预期先停。
- **改法**：文件修改优先直接编辑，保持最终内容准确；仅批量或重复性操作才生成脚本；系统操作优先简单稳定方案。
- **框架固定/局部自主**：口令→workflow、步上 hitl、输出骨架、证据/红绿、密钥、子代理边界、git 纪律、文档落位**默认**不可让（用户按第 5 条选择覆盖除外）；实现路径/顺序/工具/拆分/措辞可自主。规则未覆盖时按目标+事实+最小可验证路径，收尾记录取舍。

### 0.6 协作与交接（硬约束）

> 细则见 `规则/协作/协作与交接.md` 当前节；此处只留硬句。

1. 内容优先、包按需、正文自洽；**默认择优单文档**（五问→知会/确认一页纸/决策简报/专模，禁整表套模）；compose 有歧义才 `confirm_intent`，意图已清可直写；回执默认否；外发禁内部路径与流程元数据；HO 仅触发命中且先问后发；有平台不重复 BUG/FIX 整包。细则 `规则/协作/协作与交接.md` §3.0。
2. **仅升级 HO 包时** 00说明+01清单+02快照齐套缺一不发；提测包须 `COMPLETE`，发布包须 `confirm_deploy`；接收=入站/`intake` + 可选签收。**正式签收**时三选一并回执；正式签收/C2·C3/发布须回执；仅通知/同仓/代收 →「已发送」+用户确认可关。
3. C2/C3 必须重基线过门；交接后更新台账 → 开发计划 §0/§1/§12 → 索引 → `activeContext`。

### 0.7 提交、推送、部署（硬约束）

> 本地提交（可逆）｜推送（远程可见）｜部署（环境变更）三件事分开；默认只提交。

- **git（有 `.git` 时，每任务强制）**：完整任务收尾必须检查——当前分支与跟踪、未提交分类（本任务/前序/无关）、`.gitignore` 是否覆盖密钥·凭据·依赖目录·构建产物·运行时数据等；结论只写入【任务收尾】第 2 点（统一字段 + 本轨多分账/建议动作/文档归档）；拟改 ignore 列入第 4 点表（确认后同轮落地）；禁止收尾外另造 git 块；完整清单仅【拟提交】一次（≠第 2 点摘要）。无 `.git` 时第 2 点写「无仓库」。细则见 `规则/工作流.md` §2。
- 任务前有前序未提交 → 【基线检查】；完成自测/评审后 → 【提交检查】+【拟提交】；会话结束 → 【提交提醒】；>20 文件或 >500 行先拆分/说明。
- 发布只从干净工作区、已提交/已打 tag 的版本构建；`COMPLETE` + `confirm_deploy` 才部署；回滚单独 `confirm_rollback`。生产发布必须是正式版；test/staging 不触发 S8，版本按项目模式；详见 `规则/核心/版本策略.md`。
- 一任务/一逻辑一次提交；禁 `git add -A` 混前序；无关文件/生成物/密钥不入库；用户说「直接跑完」也不自动提交/推送/部署。

## 1. 接入

实例：`项目档案.md`（§1/§7/§8/§9）+ `activeContext.md`；工作根必须有 `开发/`；原始资料根推荐 `docs/`（其它名可）；占位符未换=未接入。交接 `开发/交接/{HO-ID}/` + `交接台账.md`（唯一登记）；多包同仓直读，仓外包在用户放置处读。
口令「接入/重新接入/档案/文档树」→ `onboard.yaml`；必须建索引+标准树+原始资料根+本包 `资料/`+根 `CHANGELOG.md`+`开发/工作日志.md`；L2+ 另建开发计划/变更记录/待决项/决策记录/需求台账。

## 2. 收尾

触发：工作流末步、计划结束、点名「收尾/总结」。**对照** `规则/模板/90-交接与收尾/收尾骨架.md` §2。**必须含【遵守自检】**，缺项=未收尾。提交/推送/部署/回写门按 YAML `hitl` 独立确认；完整【拟提交】在 commit 只展示一次（第 2 点仅「待提交摘要」）；默认仅提交，推送单独确认；未提交默认不得开始下一任务（例外=基线检查选项 C/D 且用户确认）。

## 3. 口令 → Workflow（命中即停）

> **描述**：表内是常见口令示例（非穷尽），同义表述按五元组路由，不要求逐字匹配；命中优先执行。未命中或任意描述句 → 必读 `规则/核心/入口判定.md`：抽五元组（动作/对象/结果/连续/体量）→ 意图类 A～L → 项目状态修正；首条必写 `reason=`（可附 `intent=`）。不抠固定措辞；路由后按步加载技能，不另造 workflow。

**部署歧义（硬规则）**：裸说「部署/推服务器」先判环境，不默认 S8：test/staging/UAT → S7 环境部署（版本按项目模式，只记录+冒烟，不触发 `confirm_deploy`）；prod/生产/正式 → `release`/S8；无法判断只问一次目标。提交/推送 ≠ 部署。
**复合口令**：「提交推送部署更新服务器」= commit→push→环境更新；唯一 test 环境按 S7，多环境问一次；不得默认 S8。

**入口直达**：单步口令（代码评审/提测/下一步/回滚/澄清）只执行该 step 到产出完成即停；`change`/`iterate`/`release` 按各自链路继续到下一个门或收尾；「只出任务清单」到 wrap + commit 确认即止。`workflow.chain: full`（如 onboard）例外，必须走到 verify/打标。单步入口仍按 `规则/模板/90-交接与收尾/收尾骨架.md` 输出。
**互斥**：「落地…#编号…优化方案」=缺陷；「落地迭代方案」=迭代；无 `#` 又无「迭代」→ 一问。未命中 1～5 的改代码/改配置实施类 → `change`；发布/回滚/复盘各自独立。有开发计划且续跑语义（下一步/继续开发计划/当前状态）→ 优先 `control`。
**无口令**：口语未命中上表 → `规则/核心/入口判定.md`（通用意图类，非口令同义词表）。
**首条**：`route=workflow:<id> | step=<id> | level=<L0-L3> | mode=... | reason=... | reads=<读取索引行> | next_action=…`；有输入加 `input=<diff/路径>`。纯只读分析可写 `route=readonly:analysis | step=explain | mode=analyze | reason=… | next_action=…`。

## 4. 维护

改不变量/路由/读取协议 → 本文；改无口令路由 → `规则/核心/入口判定.md`；改步骤 → `workflows/`；改角色 → `agents/`；改红线/门 → `规则/`；改澄清 → `规则/核心/澄清.md`；改协作/交接/变更分级 → `规则/协作/协作与交接.md` + `workflows/handoff.yaml`；改模板 → `规则/模板/`；改技能 → `技能/`；改能力 → `能力/`；改文档树/归档 → `规则/文档治理.md`；改子代理 → `规则/协作/子代理编排.md`；改读取索引 → `规则/读取索引.md`；改轻量档 → `规则/核心/轻量交付.md` + `workflows/solo.yaml`。自检见 `规则/核心/维护.md` §2。

## 5. 文档治理（摘要）

- 工作文档根固定 `产品/` · `开发/` · `测试/`。原始资料根推荐 `docs/`（认根：用户指定优先，否则判定表，不定则问）；`keep`/`mix`/`replace` 只管原树结构，仍可索引/复制/吸收。根白名单含登记的原始资料根。
- 原夹文件一律不迁出；中途存量**全索引**，按任务/版本按需复制或 R0～R2 吸收；可仅索引。细则 `规则/文档治理.md` §2。
- **换迭代=关版本**：新迭代/换代/换主题（可不发版）→ 同会话按文档治理 §7；不确定 → `confirm_iteration_close`；确认后 §7.1 完整归档清理。根 `CHANGELOG.md`=发版史；`开发/工作日志.md`=岗位里程碑；发布说明按版本。

## 6. 技能与能力（按步加载）

- **角色边界**：谁负责/能定/何时停/向谁升级见 `规则/协作/角色契约.md`；冲突先查表。
- **技能**：`技能/<name>/SKILL.md` 命中步必用；阶段→技能见 `技能/README.md`；新增/大改按末节质量标准（description 含中文触发词、≤500 行、超长拆 references）。
- **能力**：`能力/00-能力注册表.md` 已装即用、未装降级；「装配能力」=安装，「体检能力」=诊断+优化（`skill-audit.yaml`）。业务会话最多 1 条有证据的建议，禁推销。

## 7. 多包（自动探测）

- **口令表节号**：本包与产品 §3；测试 §2（勿跨包按节号直译）。
- **单包独立为默认**；多包联动**可选、非必须**；不要求装齐三包、不强制同时启用、**不因缺他包阻塞本包**；跨包同步只登记状态，不等于自动联动。**联动=交付物字段+同仓直读，≠共安装、≠自动跑对方、≠强制引用他包路径。**
- ≥2 个包目录=多包；共用原始资料根（推荐 `docs/`）、根 `activeContext.md`（总览→各包分节→跨包同步→运行时）。
- 各包只改本分节/本包接入行/相关跨包同步一行；禁整文件覆盖或改他包分节；一次会话只跑一个包 workflow；跨包默认自洽交付物/同仓直读，**仅升包时**用 `{HO-ID}` 整包；不复制正文、不自动跑对方。
