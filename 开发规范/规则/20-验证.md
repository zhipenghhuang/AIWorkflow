# 验证与完成（开发轨）

> **单一出处**：验收清单、证据、完成状态、报告措辞。`AGENTS.md` 只留指针；`验证/README.md` 是操作入口；`验证/检查矩阵.yaml` 是策略表。
> **读取时机**：`clarify`/`plan` 定验收；`implement` 收尾、`verify`、`wrap` 前；`review` 只读证据标准，不读门回执（门在 verify/gates 跑）。维护时读 `30-规则治理.md`。

## 1. 不变量（带 ID）

| ID | 不变量 |
| --- | --- |
| DEV-VER-01 | 先理解后执行：需求理解包/验收清单未确认，不写基线/方案/清单/代码。 |
| DEV-VER-02 | 完成只认门：没有 `completion.json` 的 `COMPLETE`，只能报“未验证/阻塞/部分完成”。 |
| DEV-VER-03 | 证据先于结论：结论必须引用本轮检查、退出码、证据路径；聊天文本/子代理自述不算证据。 |
| DEV-VER-04 | 失败不声称完成；工具/环境缺失记 `BLOCKED`，不得降级为“人工清单已过”。 |
| DEV-VER-05 | 风险不降级：L0～L3 由变更事实判定；前端行为/布局变化最低 L1。 |
| DEV-VER-06 | 实施者不自证：L1+ 前端/API 变更由 fresh-context verifier 抽核；L2+ 独立评审。 |
| DEV-VER-07 | 前端必须浏览器验证：状态、视口、console、network、截图；无证据不报完成。 |
| DEV-VER-08 | 报告先写 verdict，再写完成内容；非 COMPLETE 禁用“完成/通过/已修复/正常”。 |
| DEV-VER-09 | 读 `.gate/completion.json` 前核对 `package=开发规范` 与本轮 `mode/timestamp`；被其它包覆盖或非本轮=未验证。review 步不读门回执，门统一在 verify/gates 跑。 |

## 2. 验收清单

- **L0/L1**：写在任务卡/开发卡里的 `## 验收清单` 表；至少含 `AC | 判定 | 检查 | 证据`。L1 非纯文档改动无可解析清单 → 门 BLOCKED。
- **L2+**：落 `.gate/acceptance.yaml`，确认后冻结；变更走变更记录；多任务清单的验收表会被聚合核对。
- 每行必须能判定（条件+动作+可观测结果），检查可复跑，证据有落点。
- 写不出 AC = 需求未定义完；不得进入实施。
- 确认后不重复问；新增/变更 AC 走变更记录。
- **规范包只读**：`开发规范/验证/` 仅工具与模板；运行态（验收清单、证据、project-profile、截图）一律写项目根 `.gate/`，禁止写入包内。

## 3. 证据

- 门自己跑关键检查并写 `completion.json`；不信任“已通过”文本。
- 证据类型：命令+退出码、测试报告、Playwright trace/截图、console/network 日志、设计 QA、评审记录。
- 前端证据落 `.gate/frontend/`；至少桌面+移动截图；从 `验证/frontend/design-qa.md` 复制到 `.gate/frontend/design-qa.md` 后填满 15 项结果/证据且结论非「不通过」。
- 原始日志落 `.gate/logs/`；对话只放 ≤30 行摘要。
- 证据不夹带密钥/PII；路径用相对路径。

## 4. 完成状态

| 状态 | 条件 | 报告措辞 |
| --- | --- | --- |
| `COMPLETE` | 验收全覆盖；必跑检查通过；证据可打开 | 完成/通过/已修复 |
| `PARTIAL` | 核心通过；有非阻断缺口/跳过项 | 部分完成/部分验证；列缺口 |
| `BLOCKED` | 检查失败/缺环境/缺证据/验收未覆盖 | 未完成/阻塞/未验证 |
| `NOT_VERIFIED` | 未跑门 | 未验证/待验证 |

## 5. 前端分级

| 变更 | 必做 |
| --- | --- |
| 纯文案/配置 | build + 受影响页面截图 + console 无 error |
| 普通 UI 改动 | 上述 + 状态（loading/empty/error/permission）+ 360/768/1280 截图 + 键盘/焦点基础 |
| 布局/交互/表单/权限 | 上述 + E2E 主链路 + network 4xx/5xx + 独立目检 |
| 高风险/品牌页 | 上述 + 视觉基线/diff + a11y 扫描 + 深度设计评审 |

设计合理性由 `验证/frontend/验收清单.md` 15 项 + 独立目检判断；不追求每页像素级 diff。
产品设计不完整 → 先出 1 页前端设计说明（布局/层级/tokens/状态），确认后再写代码。

## 6. 报告契约

```text
【验证回执】verdict=COMPLETE | gate=<commit/diffHash> | checks=8/8 | unverified=0
```

- 回执在【任务收尾】第 1 点之前；`验证/Test-Report.ps1` 对账。
- 数字与 `completion.json` 一致；未验证项显式列出。
- 提交/部署/回写门仍按 YAML `hitl` 独立确认；门不替代提交授权。

## 7. 成本纪律

- 只跑受影响范围；全量回归只留给发布/L3。
- 门每次按当前 diff/验收清单重跑；不复用旧回执（避免旧 `completion.json` 假绿）。
- 高价值低成本默认做；高价值中成本按风险；低价值高成本不做（见 `验证/检查矩阵.yaml`）。
- 不为 L0/L1 新增文档；不每个任务通读规则/技能。
