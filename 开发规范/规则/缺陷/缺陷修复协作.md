# 缺陷修复协作

> **读取级别：参考**（按节读取；按 `读取索引` 只读当前 step 节，禁止通读全本）。

> **步骤顺序**以 `../workflows/defect-fix.yaml` 为准；角色契约见 `../agents/defect-fixer.yaml`。  
> 本文定分类、产品缺陷评估与流程；平台见 `规则/缺陷/缺陷平台适配.md`，备注骨架见 `规则/模板/40-交付与发布/缺陷文案模板.md`。本文中 `§3` 指平台文件，`§6.x` 指文案文件同名节。  
> 读取：只读当前步节 + 对应分文件节；不要通读。  
> 真值：`项目档案.md`。确认门**只认**步上 `hitl` 列表：`select_menu` / `confirm_commit`（含提交时）/ `confirm_deploy`（含部署时）/ `confirm_remark`（含回写时）；本文不另造门。  
> **三包独立**：不假设产品包/测试包与本包同目录；跨包交接只认平台单号、备注、附件、状态/指派；产品包存在时可选联动，不作为前置。  
> **备注受众**：平台备注是给测试/产品看的，不是开发日志。测试只看结论、复现差异、请补充事项、下一步；产品只看判定依据、相符证明、方案选项、影响、待确认。开发内部处置码、类名、命令、仓库路径、红绿证据只进内部记录/总结，**不进平台备注**。

## 1. 口令

| 形态 | 范围 |
| --- | --- |
| 指派给我 / 我的待修… | 批量未解决且指派给我 |
| 修复…#123 / 仅 #123 | 点名 |
| 落地…#123 优化方案 | §5 |
| 拉取产品回复 / 产品回复 / 产品退回 / 继续缺陷 | 从 `product_decision` 进入（已有产品回复或退回） |
| 一次性 / 直接跑完 / 中途不停 | 预授权：声明**默认只到做完任务**（分类＋修复/评估＋门禁＋总结菜单），直接执行；仅当口令同时提到后续（提交/推送/部署/回写）且范围不明时一问；只免等待不免输出（`../AGENTS.md` §0.2） |
| 菜单编号或执行提交/推送/… | 精确执行 |

编号只来自平台 API；空清单摘要后收尾。无平台编号、只描述现象 → `workflow:change`。  
**产品缺陷分支**：开发只出评估单，不直接写完整技术方案；产品确认后才实施。产品回复可能改变分类/范围，按 §5.2/§5.3 处理。

## 2. 前置

档案缺陷配置已填（provider、提交方式、平台适配）；凭据可取不入库。缺失一问补齐。  
**provider=「无」或未配置**：立即降级 `workflow:change`（`defect-fix.yaml` preflight），禁索要编号、禁空转拉平台。  
**平台/工具暂不可用**（含 MCP/登录/网络）：先输出启动回执与阻塞说明，再排障；恢复后回 `pull` 补出清单摘要——禁静默排障取代输出门。  
**三包独立**：产品/测试文档不放在本包目录内；收到产品文档按 §5.4 落 `资料/{版本或主题}/` 或 `_通用/`（按 `规则/文档治理.md` 意图分析/对照，保持原名）并登记 `资料/资料索引.md`；不引用其它包内部路径。

## 4. 主流程（顺序以 YAML 为准）

```text
preflight → pull → triage
  ├─ 实现缺陷 → fix → gates → menu → close → postrelease?
  ├─ 产品缺陷 → assess_product → handoff_product（备注+附件+指派产品）→ await_product
  │      → product_decision → align →（认可/改判实现/新方案）→ fix → gates → menu → close
  └─ 无法确认/信息不足/无法复现/重复/设计如此/非缺陷/外部 → clarify → STOP（等测试补充；必要时 wrap）
```

先读全单（原单提交信息＋历史备注/附件）再动手；复现与写回按原单口径对齐（§6）。修前红证；无根因不修；未自验通过不进可提交项、不回写。无效换路径 / 回根因见 `../AGENTS.md` §0.3-7。  
**产品缺陷期间不改代码**：评估单提交后停，等产品结论；产品未回复不得按自己的方案实施。  
**子代理**：按 `规则/协作/子代理编排.md` §2 取档——**≥5 单且读单成本高**（多备注/附件/评估单）或合计 ≥20k token 才逐单只读侦察（分类候选/证据缺口/查重键）；**≥3 单且文件不重叠**才修复分片（默认串行）；提示含 bugId/路径/红证/验收；禁 commit/push/回写；**返回 ≤30 行，须为可直填 §6 备注各节的事实素材**，禁「已修复」空壳；编排核验差异与红绿证据后再写入总结；同文件集合并组勿多代理并行覆盖。高风险/大改：核验者≠实施者，只给原单＋diff＋红绿命令。  
**合并组**：同根因或同文件集可合并；产品缺陷初次/无法确认不入组。组内一次实施、逐条红绿、一次门禁与提交、逐条回写。

### 4.1 分类与内部处置码

> 处置码仅开发内部使用，用于路由与平台字段映射；**不得写进平台备注正文**。

| 内部处置码 | 中文结论 | 开发动作 | 改代码 | 平台动作（按 §6.9） |
| --- | --- | --- | --- | --- |
| `fixed` | 实现缺陷，已修复 | 红证→根因→修复→自验 | 是 | `resolution=fixed`；`resolvedBuild`；指派测试 |
| `product_defect` | 产品缺陷/需求缺口/设计口径不明 | 写评估单→上传→指派产品 | 否 | 保持待确认；`resolution` 空；指派产品 |
| `need_info` | 信息不足，暂无法确认 | 列缺什么、谁补、截止 | 否 | 保持 active；指派提交人/测试 |
| `not_repro` | 按原单无法复现 | 记录尝试与频率；请测试复核 | 否 | `resolution=notrepro`；指派提交人确认 |
| `env_mismatch` | 环境/版本/构建/数据不一致 | 指定可复现环境/构建；请换环境复测 | 否 | 保持 active；指派测试 |
| `expected_unclear` | 预期不明确/无验收口径 | 请产品/设计确认预期 | 否 | 保持 active；指派产品/测试 |
| `duplicate` | 重复 | 关联主单；说明重复点 | 否 | `resolution=duplicate`；`duplicateBug=主单` |
| `by_design` | 设计如此/非缺陷 | 引用设计/需求原文；说明理由 | 否 | `resolution=bydesign`；指派测试 |
| `external` | 外部原因 | 给证据与责任方 | 否 | `resolution=external`；指派责任方/测试 |
| `deferred` | 延期/下版 | 需产品/项目确认；记录目标版本 | 否 | `resolution=postponed`；指派产品/项目 |
| `wontfix` | 不修复 | 需产品/项目确认；记录风险接受人 | 否 | `resolution=willnotfix`；关闭/指派 |
| `already_fixed` | 已在其它构建修复 | 给构建号；请测试验证 | 否 | `resolution=fixed`；`resolvedBuild=构建` |

- `duplicate/by_design/external` 有确凿依据才可关闭；`deferred/wontfix` **不得开发单方决定**，须产品/项目确认并留痕。  
- 产品缺陷被产品改判为实现缺陷 → 处置码转 `fixed`，按 §5.2 继续修；产品判定非问题 → 按产品指派关闭/回执或退回测试，不自行改代码。  
- 平台备注只写“中文结论”，例如“结论：信息不足，暂无法确认”“结论：按原单无法复现”，**不写 `need_info/not_repro` 等英文码**。  
- **混批拆分**：同一批既有产品缺陷又有实现缺陷 → 先处理产品缺陷（评估/交接）并 `AWAIT_PRODUCT`；实现项标「待下一批」，不静默丢、不先提交半批；用户继续后再按实现缺陷走 `fix`。

### 4.2 产品缺陷流转状态

```text
待开发确认
  → 待产品评审（开发评估单已上传、已指派产品）
  → 产品已认可 / 产品修改后认可 / 产品判定实现缺陷 / 产品判定非问题 / 产品要求补充
  → 待开发实施（仅认可/改判实现/修改后认可）
  → 待测试回归
  → 关闭
```

- **待产品评审**：开发不改代码、不提交、不部署；只维护评估单与平台回执。  
- **产品已认可/修改后认可**：开发先按 §5.3 对齐文档，再实施。  
- **产品判定实现缺陷**：开发按产品说明修复，备注引用产品结论。  
- **产品判定非问题**：开发按产品指派关闭/回执或退回测试，不自行改成实现缺陷。  
- **产品要求补充**：开发一次列清缺什么，保持待产品评审。

## 5. 产品缺陷评估与落地

### 5.1 开发判定为产品缺陷（首次评估）

开发认为测试提交的是产品缺陷、设计口径问题或需求缺口时：

1. 先按 §6 读全单，确认原单步骤/数据/环境/版本；不凭标题判定。  
   > 测试侧无设计文档时默认实现缺陷；开发复核若判断为需求缺口/设计口径问题，可按本轨改判产品缺陷，评估单写「无设计文档·现网依据」+业务影响，由产品最终定性。  
2. 按 `规则/模板/20-设计与技术/产品缺陷评估模板.md` 写 **产品缺陷评估单**，落 `开发/00-项目治理/缺陷评估/`，文件名 `缺陷评估-{BUG-ID}-{主题}-{yyyyMMdd}.md`。  
3. 评估单只写：判定依据、问题与影响、方案选项 A/B/C、推荐、影响面、待产品确认；**不写代码实现细节、不拆开发任务、不排开发排期**。  
4. **不要**把评估单写成正常迭代方案 `方案-{主题}-…`；也不要放进 `04-计划与任务/`。评估单是产品决策输入，不是实施计划。  
5. 上传评估单为缺陷附件；备注按 §6.2；指派产品经理；状态按档案映射置「待产品确认/待评审」。  
6. **停**：不改代码、不提交、不部署；等待产品回复。若产品长期不回复，按 §5.2 的时限升级。  
7. **提交分离**：评估单可独立提交；代码修复另提交，不把评估单与代码混在一个提交里（文档随提交规则见 `规则/工作流.md` §2）。

评估单必须能回答产品四个问题：**是不是产品问题、依据是什么、建议怎么处置、影响多大**。  
产品确认后如实施复杂，再按 `规则/模板/20-设计与技术/方案模板.md` 展开技术方案，文件名 `方案-BUG-{id}-{主题}-{yyyyMMdd}.md`，落 `02-方案设计/`；简单修复不强制。

### 5.2 产品确认后执行

产品回复按以下五类处理；**先读全附件/备注，再动手**：

| 产品回复 | 开发动作 |
| --- | --- |
| **认可方案** | 按评估单方案实施；更新受影响文档/计划（§5.3）；复杂实施补技术方案；修复后回写。 |
| **修改后认可** | 以产品新文档/备注为准（较新附件 > 备注 > 原评估单）；按 §5.3 对齐后实施；备注写明与原评估差异。 |
| **判定实现缺陷** | 产品说明依据；开发按实现缺陷修复；备注引用产品结论，不写成产品口径调整。 |
| **判定非问题** | 产品说明依据；按产品指派处理：指派测试则退回测试，指派开发则由开发关闭/回执；开发不改代码，不把非问题写成已修复。 |
| **要求补充信息** | 一次列清缺什么、谁补、截止；保持待产品评审；补充后回 `product_decision`。 |

- **产品确认方式**：平台回派/备注/评审附件/新产品文档；以平台最新有效记录为准。仅“回派”无备注/附件说明 → 视为未确认，回 `product_decision` 请产品补结论。  
- **确认三源**：回派（须带明确备注）、评审附件、新产品文档；三者皆无 → 向用户确认一次，仍无 → 停，不按未确认方案实施。  
- **优先级**：较新评审附件 > 历史备注 > 本地评估/原方案；冲突点写「调整项摘要」，产品未裁决不实施。  
- **未确认不实施**：只有“待产品评审/补充信息”状态，不得进入 `fix`。  
- **分类争议**：开发对产品判定有异议 → 不反复回派；在平台备注列事实与依据，请产品经理与开发负责人 1 个工作日内裁决；仍不一致升级项目负责人，留决策记录。  
- **时限**：S1/S2 产品确认目标 4 小时/1 个工作日；S3 3 个工作日；S4 下一版本。超期在总结标「待产品超期」并升级，不静默等待。

### 5.3 产品退回 / 新方案对齐

产品给出新文档、修改说明或改判后，开发必须先对齐再实施：

1. **读全**：平台标题/steps/状态/解决码/指派、全部备注、附件、关联需求/PRD/AC；评审类文档必须下载读全文（禁只列文件名）；`solutionChannel=manual` 读不全 → 请用户补关键附件/备注，禁只看标题。  
2. **落资料**：产品新文档（PRD/设计/处置单/变更单）原件落 `资料/{版本或主题}/` 或 `_通用/`，保持原文件名（或确认后用 `需求-缺陷处置-{BUG-ID}-{主题}-{yyyyMMdd}.md`），先按 `规则/文档治理.md` §3～§4 意图分析/收取/对照，登记 `资料/资料索引.md`。  
3. **判变更**：产品新文档若构成需求/范围/AC/接口/数据实质变更 → 按 `../workflows/intake.yaml` 与 `规则/工作流.md` §0.1 做影响分析/CR；纯缺陷修复口径变更也至少记 `00-项目治理/变更记录.md`。  
4. **核对**：逐项对照开发评估单/原方案，列出「一致/差异/新增/删除」；差异点写入对齐记录，不静默吸收。  
5. **更新开发资料**（按影响取用，不适用写原因）：

| 检查项 | 更新对象 | 证据 |
| --- | --- | --- |

6. **再实施**：对齐完成后再 `fix`；复杂实施按方案模板展开；简单修复在任务清单/备注记差异。  
7. **回写**：按 §6.3 写「产品处置·已对齐」，点名产品文档/附件、已更新文档、差异点、回归范围。  
8. **禁止**：未读附件就实施、只改代码不改文档、把产品新文档丢在收件箱、用旧 PRD/AC 继续开发。

### 5.4 三包独立交接

- 不假设 `产品/`、`测试/` 与本包同目录；不引用其它包内部路径/模板。  
- 交接只认平台：缺陷号、备注、附件、状态/指派；产品/测试文档作为外部输入落 `资料/{版本或主题}/` 或 `_通用/`（类型写索引，禁强制类型前缀）。  
- 产品包存在时：可引用其受理单/变更单编号，但不作为前置；不存在时按平台附件/用户提供继续。  
- 测试包存在时：提测单/测试报告可作为可选输入；不存在时按本包 UAT/回归记录继续。  
- 对外交付物只写本包路径；跨包引用写「平台附件名/单号」，不写对方绝对路径。

## 7. 分类

- 实现缺陷 → 修+自验+回写已修复。
- 产品缺陷 → **评估单 + 上传附件 + 指派产品经理**；产品确认后才实施（§5）。测试直提产品缺陷若误指派开发 → 按本条出评估单并转产品，不在开发侧直接修。
- 产品判定实现缺陷 → 按产品说明修，备注引用产品结论。
- 产品判定非问题 → 按产品指派关闭/回执或退回测试，不改代码。
- 信息不足/无法复现/环境数据不一致/预期不明 → 【无法确认·待澄清】（§6.4），不改代码。
- 重复/设计如此/非缺陷/外部 → 有依据才关；延期/不修复 → 产品/项目确认后关（§6.5）。
