# 协作与交接（开发轨）

> **读取级别：参考**（按节读取；按 `读取索引` 只读当前 step 节，禁止通读全本）。

> **目的**：把“产品 → 开发、开发 → 测试/产品、变更 → 所有角色”的交接，从口头约定变成**可复制、可追踪**的交接包（回执可选）。
> **独立性**：本包可单独使用；接收方可以是产品/测试角色、用户本人或外部团队，**不要求对方安装同套包**。交接包自包含（00～04）；对方未装包时按普通文档阅读即可。回执默认可选，仅正式签收时再填模板。
> **单一出处**：交接包结构、回执、变更分级、重规划触发以本文为准；模板见 `规则/模板/90-交接与收尾/交接包说明模板.md`、`规则/模板/90-交接与收尾/交接清单模板.md`、`规则/模板/90-交接与收尾/接收回执模板.md`、`规则/模板/90-交接与收尾/交接台账模板.md`。
> **读取时机**：`handoff.*`、`change.*`、`iterate.*`、`release.*`、`defect-fix.*` 的交接/变更节；不需要每次开工通读。

## 1. 角色与决策权

| 角色 | 决策权 | 主要交接责任 |
| --- | --- | --- |
| 开发负责人（A/R） | 技术方案、任务拆分、实现、提测 | 需求澄清、技术方案/影响、提测、修复/回归、发布结果 |
| 产品负责人（A/C） | 业务范围、AC、优先级、UAT/发布 | PRD/AC/原型/变更/验收口径；答复开发澄清 |
| 测试负责人（C） | 测试策略、oracle、准出建议 | 测试计划/用例、缺陷、测试报告、回归结果 |
| 用户/业务（A/C） | 目标、预算、风险接受 | 确认范围/优先级/发布 |
| 运维/SRE（C/I） | 部署、监控、回滚 | 发布/回滚/观察交接 |

**原则**：一个交付物只有一个 A；R 做、C 咨询、I 知会。技术决策写 ADR/方案，业务决策写变更单/决策记录；开发不替产品改业务口径，不替测试判准出。

## 2. 协作节奏（什么时候必须拉齐）

| 节点 | 触发 | 参与 | 必须产出 | 门 |
| --- | --- | --- | --- | --- |
| 需求澄清（Three Amigos） | 收到 PRD/迭代方案后、方案前 | 开发 + 产品 + 测试（可缺省） | 理解包、冲突/GAP、可测性/接口影响、待决 | `confirm_understanding` |
| 方案评审 | 方案/ADR 完成 | 开发 + 产品 + 测试 | 方案、接口/数据、兼容/回滚、测试策略 | `confirm_spec` |
| 任务对齐 | 任务清单完成 | 开发 + 产品 + 测试 | 任务/依赖/DoR/DoD/检查点 | `confirm_backlog` |
| 提测交接 | 自测/门禁通过 | 开发 + 测试（+产品） | **自洽提测单**（默认唯一交付）；`QA` 包仅按需先问后发 | 完成门 `COMPLETE` |
| 缺陷/回归 | 测试提交缺陷/修复完成 | 开发 + 测试（+产品） | BUG/FIX 包、复现/证据、回归结果 | 平台门/完成门 |
| 发布交接 | 发布就绪 | 开发 + 产品 + 测试 + 运维 | 发布说明/检查单/回滚 + REL 包 | `confirm_deploy` |
| 复盘 | 发布/事故/迭代关闭 | 全体 | 复盘 + 行动项 + RETRO 包 | `confirm_actions` |

> 产品/测试角色不存在时，由用户本人代收；交接包照常生成，接收回执由用户确认。**不因缺角色阻塞**。

## 3. 交接矩阵（开发轨）

### 3.0 总策略（内容优先 · 包按需 · 与产品/测试同口径）

| 层 | 默认交付（必产、自洽） | HO 交接包（按需） |
| --- | --- | --- |
| 提测 | **自洽提测单**（一份 md） | `QA`：多文件证据/正式签收/仓外 ZIP/同发发版材料/点名 |
| 发布 | 发布说明/回滚/上线检查（正文） | `REL`：同上 |
| 缺陷 | **有平台→平台**；无平台→评估/修复详单 | `BUG`/`FIX`：无平台或点名/多文件/仓外 |
| 变更 | CR/技术变更单 | `CHG`：多角色冻结/签收/仓外/点名 |

**包触发**：① 多文件证据 ② 正式签收 ③ 仓外 ZIP ④ 同发多主文档 ⑤ 用户点名。未命中不机械每问；禁止静默发包。详见 `技能/qa-handoff-and-release`。

**内容通用（硬规则 · 提测单与 HO 包同等适用）**

1. **不偏科**：提测单/发布说明若同时给测试与产品，共享事实（改动/范围/风险/环境）写通用业务语言；角色动作分行，禁止只写「给 QA 的暗语」或只写实现细节堆砌。  
2. **假定对方无工作流**：禁「见开发计划 § / 见 `.gate/` / 见任务清单路径」充数。  
3. **假定对方无平台/无同仓**：结论与关键证据摘要写进正文。  
4. **一份可读**：普通同事只拿提测单这一份 md，也应能开测或知悉范围。

### 3.1 开发发出（适用交接包 · **先问后发**）

> **硬规则（发包总闸）**：凡拟生成任一类型 `开发/交接/{HO-ID}/`（含 CLAR/DES/PLAN/CHG/QA/BUG/FIX/REL/RETRO），**一律先 STOP 问用户**——出示类型、接收方、必带摘要、路径意图；**仅当用户明确确认「要/生成/确认发包」后才落盘**。禁止因「完成门/提测就绪/平台回写/规则写必须」而静默生成。用户拒绝或未答 → 零发包。口令「生成交接包/提测交接包/发布交接包/发变更通知」同样先过交接门（口令≠已确认内容）。

| 时机 | 类型 | 接收方 | 最小必带 | 前置（仍须用户确认后才生成） |
| --- | --- | --- | --- | --- |
| 收到需求后 | `CLAR` | 产品 | 问题清单、原文引用、影响、建议、需要拍板项 | 理解包已出 + **用户确认发包** |
| 技术方案/影响面 | `DES` | 产品、测试 | 方案/ADR、接口/数据、兼容/回滚、测试策略、风险 | `confirm_spec` + **用户确认发包** |
| 任务清单/排期 | `PLAN` | 产品、测试 | 任务清单、依赖、DoR/DoD、检查点、影响面 | `confirm_backlog` + **用户确认发包** |
| 变更实施前 | `CHG` | 产品、测试 | 技术变更单、影响矩阵、迁移/兼容、测试范围、截止 | `confirm_change` + **用户确认发包** |
| 提测 | `QA` | 测试（+产品） | **默认只交自洽提测单**。包触发：多文件证据/正式签收/仓外ZIP/同发发版材料/点名 → 先问后发；包内=单快照+`03`证据+回执 | 完成门 `COMPLETE`；单必产；包按需 |
| 产品缺陷评估（无平台/点名） | `BUG` | 产品 | **自包含评估详单**（依据/选项/影响 AC/建议）；不依赖平台号 | 见 §3.1.1 + **用户确认发包** |
| 修复/回归（无平台写回/点名） | `FIX` | 测试（+产品） | 修复说明、提交/构建、根因、影响面、红绿证据、回归建议 | 见 §3.1.1 + **用户确认发包** |
| 发布 | `REL` | 产品、测试、运维 | 发布说明、上线检查单、回滚预案、监控/公告、观察计划 | `confirm_deploy` + **用户确认发包** |
| 复盘 | `RETRO` | 产品、测试 | 复盘、行动项、负责人/截止/验收 | `confirm_actions` + **用户确认发包** |

### 3.1.1 缺陷双通道（互斥 · 禁「平台 + 重复 HO」）

| 协作方式 | 主通道 | HO 包（BUG/FIX） | 台账 |
| --- | --- | --- | --- |
| **有缺陷平台**且已交/已回写平台（含评估附件指派产品、修复备注回测） | **平台单** | **禁止**再强制生成与平台正文重复的 `BUG`/`FIX` 整包 | 可记「平台 #{id} / 动作」（非 HO 整包） |
| **无平台** / `export` / 用户点名「缺陷交接包/修复交接包」 | **BUG/FIX 交接包** | **适用**；先问后发；正文假定对方看不到禅道/Jira | 状态=`已发送`；本地键 |

**硬规则**：① 平台已交齐 ≠ 再打一份 HO；② 包不以平台号为生成前置；③ 自包含：复现/根因/证据/回归写清；④ 「提交到平台/平台回写」→ 默认不发包；点名交接包 → 先问再发；⑤ 提测/发布/回归完成节点最多**建议**发包，不得静默生成。与「三包独立」兼容：有平台时缺陷流转以平台为主；无平台才用 HO 承载。

### 3.2 开发接收（读包核对；回执默认可选）

| 时机 | 类型 | 来源 | 开发动作 |
| --- | --- | --- | --- |
| PRD/需求交接 | `REQ` | 产品 | 核对 PRD/AC/原型；出理解包；冲突/GAP 发 `CLAR`；回执 |
| 设计交接 | `DES` | 产品 | 核对原型/开发交接/状态矩阵；需补设计发 `CLAR`；回执 |
| 计划/排期 | `PLAN` | 产品 | 核对范围/里程碑/依赖；更新开发计划；回执 |
| 变更通知 | `CHG` | 产品 | 影响分析/方案调整/重排；回执；必要时反向发 `CHG` |
| 测试报告/准出 | `TEST` | 测试 | 读失败/缺口/遗留；安排修复或发布；回执 |
| 缺陷 | `BUG` | 测试 | 复现/分诊/修复；回执；产品缺陷发评估 `BUG` 给产品 |
| 澄清/补充 | `CLAR` | 测试/产品 | 补信息/复现/说明；回执 |
| UAT 结论 | `UAT` | 产品 | 读遗留/条件；修复/发布决策；回执 |
| 发布结果 | `REL` | 产品/运维 | 更新发布记录/观察/复盘；回执 |

## 4. 交接包规范

### 4.1 目录与命名

```text
开发/交接/
├─ 交接台账.md                         # 唯一登记（状态/回执/影响）
└─ {HO-ID}/
   ├─ 00-交接说明.md                   # 封面、目的、接收方动作、验收、回执要求
   ├─ 01-交接清单.md                   # 文件清单：版本/来源/包内路径/必读/用途
   ├─ 02-文档/                         # 必带文档快照（按原文件名）
   ├─ 03-证据/                         # 必要证据副本（日志/截图/报告；脱敏）
   └─ 04-回执/
      └─ 接收回执.md                   # 空白模板必带；默认不强制填写，正式签收时再填回传
```

- **确认后才生成**：用户经交接门确认后，生成完整包（`00/01/02/03/04`）。**例外**：§3.1.1 有平台已交/回写 → 不强制 `BUG`/`FIX` 整包。
- **自包含详实（读包即懂）**：接收方假定无聊天上下文、无平台。`00` 写清目的/范围/非目标/接收方动作/验收；QA 包须含可开测信息；FIX 含根因与回归建议；CLAR 含原文引用。禁只写平台号/提交 SHA 而无业务可读说明。参考 Agent Handoff：Must Satisfy、Scope guardrails、Evidence to return。
- **ID（通用）**：`HO-{yyyyMMdd}-{NN}-{类型}-{发起}2{接收标签}`。单收：`…-QA-DEV2QA`；**多收**：`…-QA-DEV2ALL` 或短拼 `…-DEV2PMQA`。ID 只作检索标签，**不等于**「正文只给后缀那一方」；接收人清单以 `00` 为准。
- **一包多收**：同一提测/发布可一包给多人；`00` 列全员 + **按角色分行**写动作；`02` 正文须全体可读（勿只贴合开发或只贴合测试）。无工作流同事直接发文件夹/ZIP 即可。
- **版本**：新版本 `...-v2`；清单写 `取代：{旧ID}`。
- **快照**：`02` 副本；主副本在 `开发/`。
- **大文件 / 多包联动**：文本复制；超大可同仓联动；禁拷对方 `资料/交接/`。
- **安全**：密钥/真实 PII 不入包。

### 4.2 生成步骤（`handoff.send`）

0. **先问（不可跳过）**：出示【拟发包】→ 等用户确认；未确认 **零写盘**。完成门/平台回写 ≠ 发包已授权。
1. **冻结来源**：确认门已过；记录版本/提交/构建。
2. **选类型与接收方**：按 §3；缺必带 → 不发送，列缺口。
3. **复制 / 联动**：必带进 `02`（或同仓联动路径）；证据进 `03`。
4. **写说明与清单**：`00`/`01`（自包含）+ `04` 空白回执。
5. **自检**：`validate_handoff.py`（可用时）。
6. **登记**：台账=`已发送`、开发计划 §0/§12、索引、`activeContext.md`。
7. **传递**：多包同仓 → 对方直读 `开发/交接/{HO-ID}/`（及联动路径），**禁止转发/拷到对方资料/交接**；仓外 → 文件夹或 ZIP。
8. **告诉用户**：【交接包已生成】；不得写「已接收」。

```text
【交接包已生成】
- 交接：{HO-ID}｜{类型}｜{发起方} → {接收方}
- 路径：开发/交接/{HO-ID}/
- 传递：多包同仓 → 对方直接读上述路径（禁止再转发/拷到对方资料/交接）；仓外/单包 → 发文件夹或可选 ZIP（{HO-ID}.zip）
- 必带：{…}
- 阻断/待决：{…}
- 回执：默认可选（模板在 04-回执/）；点名正式签收或发布/C2/C3 时再填回传
- 状态：已发送
```

### 4.3 接收与回执（`handoff.receive`）

1. **定位包**：
   - **多包同仓**：直接打开发送方路径（如 `产品/交接/{HO-ID}/` 或 `测试/交接/{HO-ID}/`），**不要求**拷入本侧 `开发/资料/交接/`。
   - **仓外/单包**：在用户放置处打开文件夹或解压 ZIP；台账可登记实际路径；仅在归档有用时可选复制到 `开发/资料/交接/{HO-ID}/`。
2. 先读 `00`，再按 `01` 核对五件事：清单文件是否齐、版本/提交是否对、是否有阻断缺口、是否有互相矛盾、是否有需开发拍板项。
3. 结论三选一：**接受** / **有条件接受**（列非阻断缺口/假设/责任人/截止） / **退回**（列阻断缺口与需要补什么）。
4. **回执**：默认可选。用户点名要回执，或发布/重大变更 C2/C3 正式节点 → 填写 `04-回执/接收回执.md` 并回传，台账改为 `已接收`/`有条件接收`/`退回`。无回执时只可声称「已发送」，**不得**声称「已接收」；日常工作不因缺回执阻塞，除非用户要求正式签收或当前是其点名的正式门。
5. 更新开发计划 §0/§1/§2/§10/§12、需求基线/方案/任务清单、文档索引、`activeContext.md`。
6. 若包内是变更通知 → 走 §6；若含实质变更 → 先 `confirm_change`/`confirm_plan`，不得边实施边改口径。
7. 发送方收到正式回执后更新台账：`已接收`/`有条件接收`/`退回`；退回补件后发新版本，旧包标 `已取代`。**正式签收时不得替对方签收**。

**时限（默认，仅正式签收场景）**：普通交接 1 个工作日；阻断/提测/发布 4 小时。超时由发送方在台账标 `待回执` 并升级给用户。

## 5. 交接完成判定

| 状态 | 含义 | 能否进入下游 |
| --- | --- | --- |
| `草稿` | 包未生成完/未自检 | 否 |
| `已发送` | 已生成并交给对方（回执未填或未收回） | 本侧可继续准备；不得称「已接收」 |
| `已接收` | 正式回执=接受，清单齐 | 是（正式签收完成） |
| `有条件接收` | 正式回执=有条件，非阻断缺口有主/截止 | 是，条件进计划风险 |
| `退回` | 正式回执=退回，阻断缺口未解 | 否；补件后发新版本 |
| `已取代` | 有新版本包 | 否；以新版本为准 |
| `已关闭` | 下游工作完成/验收关闭 | 是（作为历史） |

**硬规则**：日常外发以包生成/`已发送`为准，可继续本侧准备，**不得**用「须等回执」阻塞日常。**正式签收**（用户点名要回执，或发布/重大变更 C2/C3）才要求回执后标 `已接收/有条件接收`；不得用「已接收」冒充未签收。

## 6. 变更与计划自适应

### 6.1 变更分级

| 级别 | 判定 | 例子 | 审批 | 计划动作 | 交接 |
| --- | --- | --- | --- | --- | --- |
| `C0` 澄清/纠错 | 不改变范围/AC/资源/里程碑 | 文案、口径、笔误、注释 | 无（书面留痕） | 就地更新，不重基线 | `DEC`，受影响才发 |
| `C1` 同范围增量 | 在已批准范围内增/改 AC、任务、用例 | 补边界、补状态、补回归 | 开发负责人 | 更新任务/方案/计划 §0/§10 | `CHG` + 回执 |
| `C2` 范围/里程碑/资源变化 | 范围、优先级、版本、窗口、验收口径变化 | 加需求、砍范围、延期 | `confirm_change` + `confirm_plan` | 重新基线；更新方案/任务/排期/提测/发布 | `CHG` + 回执 + 重过受影响门 |
| `C3` 战略/架构/合规/破坏性 | 架构、公共 API、数据迁移、安全/合规 | 换方案、迁移、破坏性接口 | 方案评审 + 发布门 | 重跑方案/评审/发布；回滚演练 | `CHG` + `RISK` + 回执 |

> 不允许把 C2/C3 拆成多个 C0/C1 绕过门；拆批必须写清总变更单与子项。

### 6.2 重规划触发

| 触发 | 默认阈值 | 动作 | 负责人 |
| --- | --- | --- | --- |
| 需求/AC/范围变化 | 出现即触发 | 按 C1/C2/C3 重基线 | 开发 + 产品 |
| 方案缺陷/技术不可行 | 评审或 PoC 发现 | 重设计/换方案/升级 | 开发 |
| 依赖/API/数据变更 | 影响当前任务 | 重排/加适配层/升级 | 开发 + 依赖方 |
| 完成门失败或关键缺陷 | 出现即触发 | 停提测/修复/重验 | 开发 + 测试 |
| CI/环境不可用 | > 1 个工作日 | 降级/换环境/暂停 | 开发 |
| 产能变化 | > 20% | 砍范围/拆波次/延期 | 开发 + 产品 |
| 发布窗口变化 | 影响发布 | 重排发布/回滚/观察 | 开发 + 产品 + 运维 |

**重规划动作**（选一个并写理由）：保持计划+加缓冲｜重排顺序｜砍范围/降级 MVP｜拆波次｜重设计｜暂停升级｜重新基线。重规划必须在触发后 1 个工作日内完成，并同步计划/台账/索引。

### 6.3 文档同步矩阵（开发侧）

| 变更 | 必更新 | 通知 |
| --- | --- | --- |
| C0 | 需求基线/方案/代码注释、变更记录、文档索引 | 受影响产品/测试（`DEC`） |
| C1 | 需求基线/AC、任务清单、开发计划 §0/§1/§5/§6/§10、提测单 | `CHG` → 产品/测试 |
| C2 | 上述 + 方案/ADR、接口/DB/前端设计、排期、发布说明、UAT | `CHG` + 计划门 + 回执 |
| C3 | 上述 + 架构评审、安全/隐私、迁移/回滚、上线检查单、发布审批 | `CHG` + `RISK` + 回执 + 重过评审/发布门 |

## 7. 计划回写与状态

- **计划是状态唯一入口**：`开发/开发计划.md` §0 写当前阶段/门/下一动作/待回执/健康度；§12 写执行日志；交接摘要进计划，详细在台账。
- **每次发送/接收/回执/变更**：更新 `交接台账.md` → 开发计划 §0/§1/§12 → 文档索引 → `activeContext.md`。四者同轮，不得只改一处。
- **计划状态**：`草稿` → `已确认` → `执行中` → `变更中` → `待关闭` → `已关闭`。
- **健康度**：绿=无阻断、回执齐；黄=有非阻断缺口/待回执/依赖延期但可恢复；红=阻断缺口/关键门未过/发布风险。红色必须在 §0 写升级对象与下一步。
- **禁止**：用“已发送”冒充“已接收”；用“计划写了”冒充“已执行”；正式签收场景用聊天结论替代回执/变更单。

## 8. 禁止事项

1. 未过门就发提测/发布包；未 `COMPLETE` 就写“可提测”。
2. 交接包无清单、无版本；或包内缺 `04-回执/` 空白模板文件（模板必带，不要求默认已填写）。
3. 正式签收场景下发送方替对方签收；用「已接收」冒充未签收。日常外发不以「未写回执」当作阻断。
4. 口头变更、先做后补单、边做边改 AC。
5. 把密钥/凭据/真实 PII 放进交接包。
6. 用旧版本包继续实施；有新版本仍引用旧包。
7. 交接包内容与主副本不一致；包内文档被接收方修改后当主副本。
8. 变更后不更新计划/台账/索引，导致下一角色按旧口径执行。
9. 多包同仓仍要求用户把包拷/转到对方 `资料/交接/`（应同仓直读）。

## 9. 参考实践（方法参考，非逐字复制）

- Three Amigos / Example Mapping / ATDD：需求、开发、测试在编码前用示例对齐 AC 与 oracle（<https://www.agilealliance.org/glossary/three-amigos/>）。
- GitHub Spec Kit：specify → plan → tasks → implement，规格与任务分离（<https://github.com/github/spec-kit>）。
- ADR（Nygard）：架构决策记录，决策与影响可追溯（<https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions>）。
- Google Engineering Practices：代码评审标准与变更小步化（<https://google.github.io/eng-practices/>）。
- Team Topologies：团队交互模式与交接边界（<https://teamtopologies.com/>）。
- DORA / Google SRE：变更失败率、MTTR、发布就绪与回滚（<https://dora.dev/>、<https://sre.google/>）。
- ISO/IEC/IEEE 29148、ISTQB：需求规格质量与风险驱动测试、准入准出（<https://www.iso.org/standard/72089.html>、<https://www.istqb.org/>）。
- Scrum/Kanban：Definition of Ready / Definition of Done、WIP 限制与流动效率（<https://scrumguides.org/>）。
