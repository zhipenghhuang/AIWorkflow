# 提测单 — {项目/系统} {版本}

> **本单定位**：面向测试的**转测件**（开发→测试）；描述已部署测试环境上的项目现状、本次迭代、环境账号、演示数据、业务规则和关键场景，供测试理解系统、生成用例并开测。  
> **读者**：测试（或用户代测）。不是开发计划、任务清单、门禁回执、交接台账或运维待办单。  
> **测试对象**：已部署测试环境的 `{版本}`。测试只通过页面和 API 操作即可。  
> **提测就绪（硬）**：标「可提测」= 环境已按本单就绪、可开测；**≠** 测试已通过/可发布。未就绪不得标可提测。  
> **内容边界**：只写项目/迭代事实、环境、数据、业务规则、验收点和已知问题；不写开发/测试流程。  
> **正确性（硬规则）**：规则、状态、字段、接口和错误码必须与**已部署实现**一致；需求/方案/任务清单中的简表只作线索，提测前逐条核对。无法确认写「待确认」并问；禁止编造。  
> **禁止把工程口径当可测事实**：禁止「默认关闭、建议开测、部署方另配、配置后可见」代替本测试环境**当前实际态**；有功能开关/灰度则必须写 §3.1 当前值表，未确认实际态 = 不得可提测。  
> **编号命名空间（表前须可扫）**：产品功能号（如 F-xx）≠ 开发任务号 ≠ 验收点 AC ≠ 规则 R- ≠ 债项 DEBT-；混用必须标注来源，禁止无来源裸号。  
> **工程追溯分流**：commit / tag / 构建号 / 部署标识 / 门禁 JSON / HO-ID **不进提测单**；写在环境部署记录或发布说明（工程版）。  
> **禁止夹带**：本地/服务器路径、命令行、仓库相对路径、`见开发/…` 代正文、DEV-IQ/gate 等内部暗号、台账/包材料清单。  
> **测试设计**：只拿本单须能设计用例并开测；至少含影响面、字段基线（或「不适用+理由」）、状态字典、规则明细、演示数据预期、可执行入口（菜单/URL）、用例设计维度。  
> **裁剪**：按项目实际裁剪；不适用写「不适用 + 理由」。  
> **账号**：内部测试演示账号可写明文，须标「仅测试」；生产/真实凭据、密钥、真实 PII 禁止写入。
