# 缺陷修复协作

> **步骤顺序**以 `../workflows/defect-fix.yaml` 为准；角色契约见 `../agents/defect-fixer.yaml`。  
> 本文定必须输出、平台要点与备注骨架。真值：`项目档案.md`。  
> 确认门**只认**步上 `hitl` 列表：`select_menu` / `confirm_commit`（含提交时）/ `confirm_remark`（含回写时）；本文不另造门。

## 0. 输出门

```text
route=workflow:defect-fix | step=… | next_action=…
```

| 时机 | 输出 |
| --- | --- |
| 启动 | 启动回执（批量禁问「请提供编号」） |
| 拉取后 | 清单摘要（空清单也要） |
| 归组后 | 分组一句（可并入摘要） |
| 批末 | 【缺陷修复处理总结】（总结性）+【用户选择菜单】 |
| 回写前确认 | 拟回写项的 **§6 备注全文**（可与【拟提交】同轮；勿在总结里倾销长备注） |
| 提交后 | 【…缺陷修复汇报】（真实 hash） |

## 1. 口令

| 形态 | 范围 |
| --- | --- |
| 指派给我 / 我的待修… | 批量未解决且指派给我 |
| 修复…#123 / 仅 #123 | 点名 |
| 落地…#123 优化方案 | §5 |
| 一次性 / 直接跑完 / 中途不停 | 预授权：声明**默认只到做完任务**（修复＋门禁＋总结菜单），直接执行；仅当口令同时提到后续（提交/推送/部署/回写）且范围不明时一问；只免等待不免输出（`../AGENTS.md` §0.8） |
| 菜单编号或执行提交/推送/… | 精确执行 |

编号只来自平台 API；空清单摘要后收尾。无平台编号、只描述现象 → `workflow:change`。

## 2. 前置

档案缺陷配置已填（provider、提交方式、平台适配）；凭据可取不入库。缺失一问补齐。  
**provider=「无」或未配置**：立即降级 `workflow:change`（`defect-fix.yaml` preflight），禁索要编号、禁空转拉平台。  
**平台/工具暂不可用**（含 MCP/登录/网络）：先输出启动回执与阻塞说明，再排障；恢复后回 `pull` 补出清单摘要——禁静默排障取代输出门。

## 3. 平台要点（内置 zentao；其它 provider 按档案适配）

提交/回写方式按档案「提交方式」：`api`（默认，按档案「平台适配」端点/字段）/ `browser`（档案适配后经浏览器操作）/ `export`（AI 出提交/回写包，用户执行并回填）。未适配先补档案；禁猜接口。

zentao 内置：API 直连；Token：`POST /api.php/v1/tokens`。列表/详情/解决/指派：v1。附件：v2 `/files` 字段 **`file`**；**非 ASCII 文件名须按 UTF-8 原字节写入 multipart `filename`**（防 .NET 自动转 MIME 编码致乱码）；**回查用 `GET /api.php/v2/files/{fileId}` 核对 `objectType/objectID`**（实测：v1 缺陷详情 `files` 字段可为空数组，**不得**据此判未挂载）。禁删 Bug。

## 4. 主流程（顺序以 YAML 为准）

```text
preflight → pull（含历史预检）→ fix → gates → menu
→ close：按菜单（拟提交 → 部署就绪/confirm_deploy → 部署 → 备注确认 → 回写）
```

先读全单（原单提交信息＋历史备注/附件）再动手，复现与写回按原单口径对齐（§6）。修前红证；无根因不修；未自验通过不进可提交项、不回写。无效换路径 / 回根因见 `../AGENTS.md` §0.3-7。

**子代理**：批量可独立时派（默认串行）；提示含 bugId/路径/红证/验收；禁 commit/push/回写；**返回须为可直填 §6 备注各节的事实素材**（现象/根因/修复后行为/改动范围/影响面/回归指引/拟提交信息），禁「已修复」空壳；编排核验差异与红绿证据后再写入总结；同文件集合并组勿多代理并行覆盖。

**合并组**：同根因或同文件集可合并；产品缺陷初次/无法判定不入组。组内一次实施、逐条红绿、一次门禁与提交、逐条回写。

### 4.1 总结 + 菜单

排版：`- ` 列表、子项两格缩进，整块可复制；不用表格。

```text
【缺陷修复处理总结】{时间} | 处理{N}：待提交{A}/已提交{B}/拟回写{C}/无法判定{D}/跳过{E}

- #{id} [{类别}] {标题}：{一句}｜文件 {模块/类名或无}｜验证 {命令要点}｜{待提交|不提交|hash}｜回写 {动作}→{人}

现场：{本地/远程/平台一句}

【用户选择菜单】
1 提交｜2 提交+推送｜3 提交+推送+部署｜4 完整链路｜5 回写｜0 不执行
（单行选项；按档案部署方式与已完成步骤裁剪并顺延编号；组合用 + 表示并集、重复步骤只执行一次；标签写实际步骤与目标；回复编号即授权，精确执行）
```

选含提交的选项 → 须先过 YAML `confirm_commit`（【拟提交】；提交信息与粒度见 `规则/工作流.md` §2）。  
选含回写的选项 → 须先过 YAML `confirm_remark`（§6 全文）。可与菜单同轮一次确认后连续执行。  
【缺陷修复处理总结】置入【任务收尾】第 1 点（可复制内容）；第 2～6 点按 `../AGENTS.md` §2。

```text
【{项目名称} 缺陷修复汇报】{日期} | {N} 项
- #{id} [{类别}] {标题}
  - 修复内容：{业务语言}
  - 验证：{要点}；提交 {hash}
（无法判定/跳过项也各一行说明）
```

## 5. 方案落地

产品经理已确认（回派/备注/评审附件；三者皆无时向用户确认一次）才实施；**仍未确认即停**，不得按未确认方案实施。  
**输入三源**：本地优化方案 + 缺陷历史备注 + 缺陷附件——评审类文档必须下载并**读全文**（禁只列文件名；扫描件按可读范围提取要点）。  
口径：较新上传的评审附件 > 历史备注 > 本地原方案；多份评审附件取最新为主、冲突点写「调整项摘要」。  
方案文档落盘按 `模板/方案模板.md`，**文件名须含缺陷号**；落 文档事实源目录 `02-设计基线/`（或档案所记映射；`规则/工作流.md` §5）；纳入拟提交范围（独立提交，与代码分离）。  
自验后经菜单回写（备注点名评审附件）。

## 6. 回写备注（详细 · 与状态同轮）

禁：密钥、仓库绝对路径、用例/台账路径。确认前展示全文（渲染等效版，非 HTML 源码）。备注**一次性写入**（与状态同轮）；写错修正=编辑原备注，禁追加第二条补丁备注。

**写回先综合读单**：原单提交信息（标题/steps——前置·复现·实际·预期·数据标识·环境版本）＋历史备注/讨论（此前处理与争议点）＋附件——复现与写回按原单口径对齐、逐项对照（引用原单步骤/数据；标明一致/差异）。业务中文为主；必要的模块/接口/字段/错误码等证据锚点保留，勿通篇代码。

**书写版式（zentao=HTML · 防「每行一空行」）**：整条备注默认单块——行间用 `<br>` 相连（拼装=`lines.join('<br>')`），条目（一、二、…）间不插空段；确需分段最多一个 `<p></p>`。**禁**每行外包 `<p>`（`'<p>'+l+'</p>'` 式→渲染成每行一空段）、`<br><br>`、`\n\n` 与连续空段。非 HTML 平台同构（行间单换行、块间至多一空行）。写入前按 payload 自检，违者改正再写。

**无法判定**（业务中文为主，必要的模块/接口/字段等证据锚点可保留；只写事实与请求，禁状态/回派等处置）

```text
【无法判定】Bug#{id} · {标题}
一、业务场景：{业务中文：模块/页面做什么用；谁在什么业务流程里用；正常应达到什么业务效果}

三、无法判定原因：{分类（信息不足/关键前提无法对齐/概率性现象/数据已变化/版本不一致/预期未确认）＋具体事实：缺哪项、为什么现有材料不足以判定；禁以「测试环境缺数据/与本地不一致」笼统作理由}
四、已尝试：{逐条 1)…2)…：按原单条件对齐后试了什么（环境/版本/账号/数据，单变量变化）→ 结果；含本地自造场景验证；≥3 条或穷尽}
五、已排查：{核对业务链路/设计口径/历史备注的结论（结论与推测分开；必要的模块/接口/字段/错误码可保留）}
六、请补充：{一次性列最关键的信息/材料（复现频率、操作录屏、原始返回/日志要点、时间点与账号、数据标识），注明各自影响哪一步判断；只请测试在其环境可执行；禁替开发补数}
七、补齐后判定：{复测步骤 → 若…则缺陷（开发修）/ 若…则非缺陷（判定标准 ≥1）}
```

### 6.1 部署

档案 `更新服务器部署.方式`：`本地` / `无` / `手动`（等「已部署」）/ `自动|命令`。未声明先问并写入档案。失败则停、不回写。  
含部署的任务：同轮按 `规则/工作流.md` §4.7 产出/更新 发布说明+回滚预案+上线检查单（`模板/发布说明模板.md`、`模板/上线检查单模板.md`），落 `05-发布与交付/`；发布说明纳入拟提交清单。  
部署前按 `技能/acceptance-and-launch/SKILL.md` 过就绪检查；部署后先冒烟再回写；失败/回滚按发布说明执行，不把未验证状态写成“已修复”。

### 6.2 发布后验证与复盘

- 部署后跑主链路冒烟与关键回归；观察日志/指标/告警；触发回滚条件就回滚。  
- 更新发布记录与 `05-发布与交付/发布说明-{版本}.md`；`activeContext.md`/文档索引同轮更新。  
- L2+ 同步开发计划（阶段/证据/下一步）；事故/回滚/重复缺陷 → `retro` 工作流（`技能/retrospective-and-improvement/SKILL.md`；模板 `复盘模板.md`），落 `06-复盘与改进/`。

## 7. 分类

- 实现缺陷 → 修+自验+回写已修复  
- 产品缺陷 → 出方案 + **上传方案附件** + 指派产品经理（按 §3 回查挂载；平台不支持附件时备注说明）  
- 无法判定 → 不改代码或无法重现（平台侧＝「无法重现」类）+ 备注要信息（先自造/按设计判定；原因按 §6 分类写；**禁**以「环境缺数据/不一致」笼统为由）
