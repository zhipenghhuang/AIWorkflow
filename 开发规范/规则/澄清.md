# 澄清追问环（开发轨）

> **单一出处**：澄清的触发、提问格式、理解回执、95% 停止条件与落盘。`AGENTS.md` §0.2、workflow 步注、技能只引用本文，不另写一套。
> **与确认门的关系**：确认门=执行授权（`hitl`）；澄清=理解对齐。门不能替代澄清；澄清答复不自动授权执行，仍需按步过门。
> **读取时机**：任务开始、输入含文档/原型、需求或验收不明、准备用假设推进、准备产出方案/清单/代码前。
>
> **总规则（强制）**：回答和执行任务前先提问；**一次只问一个问题**；根据回答继续追问；直到 ≥95% 信心；完全理解真实需求与目标后，再给最终方案。确认门不是澄清；低风险也不跳过理解回执。

## 1. 何时必须澄清（命中即问）

1. 目标、用户、场景、成功标准任一不明。
2. 范围/非目标不明，或与既有计划/PRD/基线冲突。
3. 输入含 PRD、迭代方案、需求文档、页面原型、截图、接口/技术文档：未完成“解析→复述→确认”前不得开跑。
4. 关键业务规则、字段口径、状态流转、权限、异常、NFR 未定义或不可判定。
5. 文档之间、文档与原型、文档与现有代码/计划冲突。
6. 用户使用“优化/完善/按惯例/你们决定/差不多/越快越好”等模糊词。
7. 高风险/不可逆（权限、资金、数据迁移、公共 API、发布/回滚、删除/覆盖）。
8. 发现自己正在用假设填空，且该假设会影响范围、AC、方案或排期。

**可以免问**：纯信息查询、机械重命名/格式化、已由文件/代码唯一确定且无分支的低风险操作、按已确认基线/计划执行的确定性步骤。免问也要给一行理解回执（见 §2）。

## 2. 首轮固定动作：理解回执 + 只问一个问题

首轮回复必须按此顺序，不得先写方案/代码/长清单：

```text
理解回执：{一句话复述目标}
置信度：{0-100%}｜缺口：{还不知道什么；≥70% 可写“无关键缺口”}
Q1：{一个聚焦问题}
建议：{你的猜测/推荐答案 + 一句理由；可给 2-3 个选项}
```

- **一次只问一个问题**：不得在同一轮列 Q1/Q2/Q3，不得用“顺便确认/另外/还有”夹带第二个问题。
- **非机械任务至少问 1 个问题**：即使自评 ≥95%，也要用「理解复述 + 对/不对/补充？」请用户确认；复述本身算这一问。只有纯信息查询/机械操作可免问。
- **先查后问**：能从文件、代码、计划、原型、既有记录确认的，先查并引用；只问查不到且会改变结论的。
- **问题可回答**：单选/短答/二选一优先；不问“你觉得怎么样”，不问实现细节。
- **附建议**：先给猜测再问，降低回答成本；猜测错了要显式改口。
- **问完就停**：等用户回答；不得自问自答，不得把“我先按 X 做”当已确认。
- **问题顺序**：目标与用户 → 主链场景 → 范围/非目标 → 规则/数据口径 → 状态/权限 → 异常/NFR → 验收与优先级。

## 3. 回答之后：更新理解，继续追问

每轮回答后：

1. 用 1-2 句更新理解回执与置信度（不要重复整段）。
2. 把已回答内容记为“已确认”，不再重问。
3. 只问下一个最高影响问题；若回答引出新的冲突，先问冲突。
4. 直到满足 §4 停止条件，再给最终方案/需求基线/任务清单。

**禁止**：把用户没说过的话写成结论；把“行业惯例/最佳实践”当需求；把多个问题合并成一段叙述；在用户回答前继续产出下游产物。

## 4. 95% 停止条件（可检验，不靠感觉）

同时满足才可停：

- [ ] 能预测用户对接下来 3 个问题的反应。
- [ ] 能复述：谁 / 在什么场景 / 做什么 / 系统怎么响应 / 怎么算对 / 明确不做什么。
- [ ] 关键冲突已裁决；未决项已标“假设”并有验证方式与责任人。
- [ ] 用户明确说“对/是/按这个来/可以”。
- [ ] 复述中的范围、AC、非目标与用户最后的表述一致。

**不算确认**：“随便/你决定/看着办/应该可以/差不多/沉默/只回一个 OK 但没有对复述表态”。遇到这些 → 给两个具体选项再问一次，不要开跑。

**置信度锚点**：

| 区间 | 含义 | 动作 |
| --- | --- | --- |
| <50% | 目标/用户不明 | 只问目标与用户，不产出 |
| 50-70% | 主链大致清楚，范围/规则有缺口 | 继续一次一问；缺口写清 |
| 70-85% | 主链与主要规则清楚，边界/异常/NFR 有缺口 | 补关键缺口；可给草案但标明假设 |
| 85-95% | 可复述，少数低影响项未定 | 复述确认；低影响项标假设 |
| ≥95% | 可预测后续反应，用户已确认 | 产出最终方案/基线/清单 |

连续 3 轮置信度不上升 → 换问法或回退到“目标/用户”重问；仍不上升 → 明确告诉用户“缺一个基础信息”，请其补充或缩小范围。

## 5. 完整复述模板（过门/落盘前）

```text
【理解复述】
- 目标：{解决什么问题/为什么现在做}
- 用户与场景：{谁/什么场景/触发条件}
- 范围：{这次做什么}
- 非目标：{这次明确不做什么}
- 关键规则：{状态/权限/数据口径/异常}
- 验收：{怎么算对；条件+动作+可观测结果}
- 约束与风险：{依赖/兼容/回滚/合规}
- 未决与假设：{待确认项/假设/验证方式}
对 / 不对 / 补充？
```

开发轨另加“技术差距/影响面”；输入含原型时另加“必须保留/可优化/未提供”。

## 6. 反迎合、反臆造

- 用户第一句话是“想要什么”，不是“为什么/怎么算成功”；先问后者。
- “应该/惯例/最佳实践/竞品也这样” → 追问具体场景、上次发生时间、代价、不做的后果。
- 用户改口：以最新回答为准；旧结论标作废，不留双真值。
- 不知道就说不知道；无来源写“假设/待验证”，不得写成事实。
- 不为了让用户满意而降低澄清标准；不把“用户没反对”当同意。

## 7. 落盘（单一真值）

| 场景 | 落点 | 最少内容 |
| --- | --- | --- |
| 外部 PRD/迭代方案/原型 | `01-需求基线/理解-{主题}-{yyyyMMdd}.md` | 来源、理解复述、Q/A、冲突、GAP、假设、置信度 |
| 需求基线 | `01-需求基线/需求-{主题}-{yyyyMMdd}.md` | 来源、Q/A、假设、AC、非目标 |
| 轻量需求卡 | 需求卡/任务说明 | 目标、AC、非目标、假设 |

- 记录格式：`Q: … → A: …（来源/日期/裁决人）`。
- 用户裁决优先于代码现状；代码与裁决不一致 → 记差异并回到澄清，不得用代码推翻裁决。
- 后续会话先读已确认记录，不重复问；有新证据才重开，重开另起一条，不覆盖旧裁决。

## 8. 例外与边界

- **用户点名“直接做/不用问”**：仍先给 3 行理解回执 + 假设清单；高风险/不可逆至少问 1 个最高影响问题。只免等待，不免理解与留痕。
- **热修/事故**：先止损；事后补澄清记录与复盘，不把临时假设写成需求。
- **非交互/自动化**：不猜；标 `blocked` + 待确认问题清单，交回人工。
- **确认门**：先澄清后过门；门只确认“是否执行”，不替用户回答“要做什么”。
- **确认门/菜单**：可一次展示多个授权选项，但不得夹带澄清问题。

## 9. 反模式（出现即停）

- 一轮列 3 个以上问题 / 发问卷。
- 不带猜测的开放盘问。
- 用户答完不更新理解，直接跳下游。
- 把“已读文档”当“已理解”；不引用章节/页码。
- 把原型当后端规则；把竞品做法当客户需求；把领导一句话当市场验证。
- 用“假设”绕过澄清，且不标假设、不写验证方式。
- 把“确认门”当“澄清”，或把“澄清回答”当“执行授权”。
- 置信度虚报 ≥95%，但复述不出“谁/场景/做什么/怎么算对/不做什么”。
