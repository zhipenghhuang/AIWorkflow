# 版本策略（开发轨）

> **定位**：产品/测试版本、构建/制品、部署版本、文档版本的通用规则；解决“rc 何时转正式、测试部署算不算发布、补丁何时升”的口径。
> **适用**：开发计划、提测单、发布说明、上线检查单、测试报告、UAT、CHANGELOG、tag、部署记录。
> **项目裁剪**：项目可在 `开发/06-发布与交付/版本策略.md` 按模板落一页；不适用项写「不适用 + 理由」，不机械套用。
> **原则**：版本是承诺与追溯标识，不是工作计数器；候选期只加 `rc.N`，正式后才升 patch。

## 1. 四类标识分开

| 标识 | 示例 | 作用 | 事实源 |
| --- | --- | --- | --- |
| 产品/测试版本 | `0.3.0-rc.4`、`0.3.0`、`0.3.1` | 测试、验收、发布沟通 | `VERSION` / 包版本 |
| 构建/制品 | tag、commit、构建号、镜像 digest | 指认“这份代码/制品” | Git tag/commit、CI 构建号 |
| 部署版本 | `build-manifest`、`.deploy-rev` | 指认“这个环境实际跑的是哪份” | 部署清单/部署目录 |
| 文档版本 | 文档自身日期/内部修订号 | 只标识文档自身，不进入提测单版本字段 | 文档修订记录 |

- 测试只认**实际部署版本**；文档 commit/HEAD 不是构建版本。
- **提测单只写实际部署版本**；构建/commit/tag/`.deploy-rev` 属于开发/运维内部追溯，不写入提测单，也不要求测试读取本地文件。
- 代码不变，文档怎么提交都不改变产品版本；文档版本不进入提测单的版本字段。
- 项目/URL 必须提供版本查看方式（页脚、`/api/v1/version`、等价接口），测试能在页面/API 核对部署版本。
- 禁止把四个标识混成一个字段；禁止用文档 rev 代替部署版本。

## 2. 版本模式与格式

### 2.1 先选模式（项目二选一）

| 模式 | 适用 | 版本节奏 |
| --- | --- | --- |
| **A 发布候选模式** | 有明确生产/正式发布（GA） | `0.3.0-rc.N` → `0.3.0` → 正式后 `0.3.1` |
| **B 连续迭代模式** | 无生产发布，只交 QA/测试；测试通过就继续迭代 | 迭代基线 `0.3.0`；每次 QA 部署批次 `0.3.1`、`0.3.2`；下一迭代 `0.4.0`；不用 rc |

- 一个项目/产品线只选一种，不混用。
- **未声明时的默认**：项目档案/环境清单**无 prod** → 默认 B；**有 prod** → 默认 A；无法判断 → 问一次，不默认生产。
- 唯一环境必须确认是 test 还是 prod；不能仅因“只有一个”就默认 test。
- A：`rc` 是发布候选；测试通过才去 rc。
- B：没有“发布候选”概念；`0.3.0` 是迭代/交付基线，`0.3.1` 是下一次 QA 部署批次（含缺陷修复），不是生产补丁。
- B 模式仍然遵守“版本标识制品”：同一制品换环境不升版本；只有新构建/新批次才升 patch。

### 2.2 格式

默认采用 SemVer 风格：

```text
MAJOR.MINOR.PATCH[-prerelease][+build]
例如：0.3.0-rc.4、0.3.0、0.3.1、1.0.0
```

- `MAJOR`：不兼容/破坏性变化；
- `MINOR`：向后兼容的新功能；
- `PATCH`：向后兼容的缺陷修复；
- `-rc.N`：同一目标版本的第 N 个候选，不是 patch；
- `0.x`：未稳定期，允许不兼容变化；`1.0.0` 表示首个稳定/对外承诺兼容的版本。
- 项目也可用 CalVer（如 `2026.10.0`），但必须在一个项目内统一，不能混用；内部系统推荐 CalVer + 部署清单，对外产品/API 推荐 SemVer。
- 团队可保留历史 `rc1` 写法，但新版本统一用 `-rc.N`，避免 `rc10` 与 `rc1` 排序歧义。

## 3. 升级矩阵

| 变更 | 版本动作 | 示例 |
| --- | --- | --- |
| A 模式：同一目标版本的测试候选 | 只加 `rc.N` | `0.3.0-rc.4` → `0.3.0-rc.5` |
| A 模式：候选通过、冻结正式版 | 去掉 `-rc.N` | `0.3.0-rc.5` → `0.3.0` |
| B 模式：QA 部署批次（含缺陷修复） | `PATCH + 1` | `0.3.0` → `0.3.1` → `0.3.2` |
| 正式版后的兼容缺陷修复 | `PATCH + 1` | `0.3.0` → `0.3.1` |
| 新增兼容功能 | `MINOR + 1`，`PATCH=0` | `0.3.1` → `0.4.0` |
| 不兼容/破坏性变化 | `MAJOR + 1`，MINOR/PATCH=0 | `0.4.0` → `1.0.0` |
| 仅构建/部署变化 | 产品版本不变，构建号/部署标识变 | `0.3.0` + build 20261028.1 |
| 仅文档变化 | 产品/构建/部署版本不变 | 文档自身更新，不改变提测单的部署版本字段 |

- A 模式候选期修 bug **不升 patch**；B 模式每次 QA 部署批次按 patch。
- 多个小修复可合并为一个新候选/新批次；不必每个 commit 加一个版本。
- 新功能进入候选前先判断：是否仍属于当前目标版本；不属于 → 新 minor，不塞进当前 rc。

### 3.1 “测试”指什么

- **开发自测**：提测前，开发自己跑单测/冒烟；不改变版本节奏。
- **正式测试（QA/S7）**：独立测试人员按提测单执行；发现缺陷 → 修复后出新构建。A 模式出 `rc.N`，B 模式出 `patch`。
- **测试通过**：达到退出标准（AC/回归/无阻塞缺陷/遗留接受），不是“零缺陷”。
- 没有正式测试人员时，用户/产品代测也必须按同一版本口径记录，不能把开发自测写成正式测试通过。

## 4. 候选生命周期（A 模式；B 模式见 §4.1）

```text
范围冻结（不再加新功能）
  → 出 0.3.0-rc.1
  → 测试/回归
  → 缺陷修复 → 0.3.0-rc.2、rc.3 …
  → 回归 + 验收通过
  → 冻结代码 → 0.3.0（正式/交付基线）
  → 正式后缺陷 → 0.3.1
```

- **范围冻结**：候选期只修缺陷、回归、文案/一致性问题，不加新需求。
- **候选递增**：每出一个测试候选包/测试轮次加一次；不是每个 commit。
- **正式条件**：范围冻结 + 测试/验收通过 + 无阻塞缺陷 + 遗留问题已登记并接受 + 决定不再改。
- **正式动作**：`VERSION` 去掉 `-rc.N`；打 `v{版本}` tag；更新提测/验收/CHANGELOG/发布记录。
- **不允许无限 rc**：如果持续加新功能，应升 minor 开新候选线；如果一直不冻结，说明范围/计划失控，先收口。
- 最后一个 rc 与正式版之间通常只差版本号和发布文档；代码是否再变由验收结果决定。

### 4.1 B 模式：连续迭代 / 无生产发布

```text
V0.3 迭代基线 0.3.0
  → 正式 QA 第 1 批部署 0.3.1（可含多个缺陷修复）
  → 正式 QA 第 2 批部署 0.3.2
  → 测试通过，继续下一迭代 0.4.0
  → 下一迭代 QA 批次 0.4.1、0.4.2 …
```

- 不用 `rc`；`0.3.0` 是迭代/交付基线，不是生产发布。
- **一次 QA 部署批次 = 一个 patch**；多个缺陷合并，不按单 bug 升版。
- 同一制品重复部署到另一个测试环境 → 版本不变；有新构建才升 patch。
- 测试通过不等于“发布”，只表示本迭代可收口；下一迭代升 minor。
- 旧迭代测试未完、新迭代已来 → 按 §10 并行/关闭规则处理，不能把新功能塞进旧 patch。

## 5. 正式版、交付基线、生产发布

| 形态 | 版本 | 是否 S8 发布 | 说明 |
| --- | --- | --- | --- |
| 开发/联调 | `0.3.0-dev` 或无 | 否 | 可频繁变 |
| 测试候选（A） | `0.3.0-rc.N` | 否 | 有生产发布计划时的候选 |
| 测试批次（B） | `0.3.1`、`0.3.2` | 否 | 无生产发布，QA 部署批次 |
| 预发/UAT | A: `rc.N`；B: `0.3.x` | 否 | 验收用，仍非生产发布 |
| 交付/迭代基线（无生产部署） | `0.3.0` | 不适用 | 冻结、验收、可交付；不得称“已上线” |
| 生产发布 | `0.3.0` | 是 | 走 release 工作流、`confirm_deploy`、验证、记录 |

- **正式版**不等于“部署了”；它是范围冻结、验收通过、决定不再改的版本。
- 没有生产部署形态时，可以发 `0.3.0` **交付基线**，S8/G8 写「不适用 + 依据」。
- 测试/预发环境部署**不触发** S8；A 模式版本保持 `rc.N`，B 模式为 QA 批次 `0.3.x`；都只记录环境部署与冒烟。
- 只有生产/正式环境部署才去 rc/进入 S8；部署成功也不等于发布完成，还要验证/观察/记录。

## 6. 环境与发布边界

| 环境 | 版本 | 部署记录 | 发布门 |
| --- | --- | --- | --- |
| dev | dev/最新 | 可无 | 无 |
| test | A: `rc.N`；B: `0.3.x` | `APP_ENV=test`、`.deploy-rev` | 无 S8 |
| staging/UAT | A: `rc.N`；B: `0.3.x` | 部署清单/验收记录 | 无 S8 |
| prod | 正式版 | build-manifest/`.deploy-rev` | S8 + `confirm_deploy` |

- 环境角色决定是否发布，不是“有没有执行部署命令”。
- 复合请求「提交推送部署更新服务器」：拆成 commit→push→环境更新；项目只有一个环境且已声明 test/staging → 直接按 S7；多个环境 → 只问一次目标；prod → S8；不得默认 S8。
- 版本变化看**制品是否变化**：同一制品重部署到另一个环境不升版本；有新构建/新批次才升。
- 测试服务器部署需要：构建来源、`VERSION`、`DEPLOY_REV`/`.deploy-rev`、`APP_ENV`、迁移、冒烟、回滚、日志；这些是开发/运维记录，测试只核对页面/API 的部署版本，不读取本地文件。
- 同一制品晋级：build once，test/staging/prod 用同一制品；不要把开发工作树直接复制到生产。
- 生产发布必须是干净工作区、已提交/已打 tag 的构建；A 模式 `rc.N`、B 模式 QA 批次 `0.3.x` 都不得直接上生产，上生产必须是正式版/交付基线。

## 7. Tag、平台 Release、部署

- **Git tag**：指向 commit 的固定书签；用于版本指认、检出、构建、回滚；不部署。
- **平台 Release**（Gitee/GitHub Releases）：挂在 tag 上的说明/附件/预发布标记；不改变代码/环境；可选。
- **部署**：把构建产物放到目标环境并启动；改变运行环境，不自动等于发布。
- **tag 规则**：
  - 只在候选/正式边界打，不每个 commit 打；
  - 命名 `v{版本}`，如 `v0.3.0-rc.4`、`v0.3.0`；
  - 用 annotated tag；重要发布可 signed；
  - 已推送 tag 不移动、不删除；修复发新版本/新 tag；
  - `git push` 默认不推 tag，需显式 `git push origin <tag>` 或 `--tags`；
  - rc 在平台标预发布，不标 latest/stable；不为每个 rc 建正式 Release。
- 回滚目标必须是**上一版 tag/制品/部署清单**，不能靠“重新拉最新代码”。

## 8. 项目内版本查看合同

最低要求：

- `VERSION`（或包版本）是产品版本单一事实源；
- 页面页脚/关于页显示产品版本；
- `GET /api/v1/version`（或等价接口）返回 `version`；登录后可返回 `deploy_rev`、`environment`；
- 部署目录写 `.deploy-rev` 或 build-manifest，记录实际 commit/构建；
- 测试报告记录：产品/部署版本、环境、版本查看证据；构建/commit 由开发在部署记录中维护，不要求测试读取本地文件；
- 版本不一致（页面/接口/部署清单/提测单）→ 阻断测试/发布，先对齐。

补充：

- 测试环境允许 `commit-dirty`，但必须显式标记；生产发布禁止 dirty；
- 接口不返回密钥/内部路径；
- 版本接口设 `Cache-Control: no-store`，避免旧版本缓存；
- 提测单只写实际部署版本，不写文档版本/commit/tag/`.deploy-rev`；发布说明/部署记录引用 tag/commit，不引用文档 HEAD。

## 9. 连续迭代与收口

- 每个迭代先定目标版本（如 V0.3 → `0.3.0`）；A 模式候选用 `rc.N`，B 模式用 QA 批次 `0.3.x`。
- 迭代结束必须收口：正式/交付基线 `0.3.0`，或明确“并行不关”并记录原因；不能无限停在 rc/测试批次。
- 下一轮新功能开新 minor（A: `0.4.0-rc.1`；B: `0.4.0`），不要在当前版本上叠新范围。
- 正式版后的缺陷修复走 patch（`0.3.1`）；hotfix 从正式 tag 拉分支，修完打新 patch tag，不带新功能。
- **测试中又来新方案**：先判「继续当前测试 / 关闭当前 / 并行」；未关闭不得把新需求塞进当前测试版本。
  - 继续：当前版本优先，新方案只做澄清/排期，不改测试版。
  - 关闭：`confirm_iteration_close`，停止新范围/冻结版本线，再开新 minor；**测试和缺陷修复可继续**（旧版走 patch），归档等测试完成，不是“停止测试”。
  - 并行：当前测试版冻结 tag/分支；新需求在新分支/新版本开发；旧版只修缺陷走 patch，新功能不得回灌旧版；测试环境分开或排队，不能互相覆盖。
- `0.x` 阶段可接受不兼容调整；一旦对外承诺稳定，升 `1.0.0` 并遵守兼容规则。

## 10. 角色与审批

- 产品/负责人：确认范围、AC、是否冻结。
- 开发：维护 `VERSION`、构建、tag、部署标识；保证可追溯。
- 测试：按实际部署版本测试；报告写清版本/构建/环境。
- 发布负责人：`confirm_deploy` 前出示版本/窗口/影响面/回滚决策人。
- 正式版/tag/生产发布必须显式确认；不得自动打 tag、自动推远程、自动部署。

## 11. 检查清单

- [ ] 目标版本明确；A 模式 rc 只用于同一目标版本
- [ ] A 模式候选期缺陷修复只加 `rc.N`；B 模式 QA 批次按 patch
- [ ] 正式/基线条件满足；没有无限 rc/测试批次
- [ ] 测试/预发部署版本符合模式（A: rc；B: QA 批次）；生产发布才用正式版
- [ ] tag 只在候选/正式边界；annotated；未移动/删除
- [ ] 平台 Release（如有）标预发布，未冒充稳定版
- [ ] `VERSION`/页脚/接口可核对部署版本；`.deploy-rev` 仅开发/运维内部核对，测试不读取
- [ ] 提测单只写实际部署版本，不写文档版本/commit/tag/`.deploy-rev`；测试报告记录部署版本与环境
- [ ] 发布构建干净、已提交/已打 tag；dirty 未进生产
- [ ] 回滚目标（上一版 tag/制品）明确
