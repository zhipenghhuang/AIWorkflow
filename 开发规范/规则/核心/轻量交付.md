# 轻量交付（单人或小项目轨）

> **定位**：给「一个想法 / 一个小改」用的默认快车道；不是完整产品/测试包的替代。完整链仍是 `workflows/change.yaml` / `workflows/iterate.yaml`。
> **单一出处**：档位、升级触发、文档最小集、测试最小集、门策略、本包产品/测试职责边界、不降标口径。`AGENTS.md`、`workflows/solo.yaml`、模板只引用本文，不复制阈值。
> **读取时机**：命中 `solo` 入口、判断是否升级、准备方案卡/测试报告、无 QA 自验、收尾前；改「不阻塞/降级」语义时也读。

## 0. 本包产品/测试职责边界（硬）

开发包**以工程交付为主**；单包独立落地时附带**够用的产品判断与开发自验**，标准不因「个人项目 / 无多职责分工」降低。

| 本包负责（开发侧切片） | 本包不负责（归他包或完整档） |
| --- | --- |
| 值不值得做 / MVP / 非目标 / 可观察成功标准 | 需求池、路线图、立项 Go-Hold-Kill、客户访谈 |
| 理解 PRD/原型 → 冲突表 / GAP / AC 可验收 | 写完整 PRD、原型/IA/视觉体系、GTM |
| 方案卡/需求基线里的产品行为 + 验收表 | 产品变更单作业务 SSOT |
| 风险驱动最小充分集实测 + **开发自验**报告 | 测试计划、用例库、覆盖三闸、**版本准出** |
| 有 QA 时提测单；无 QA 时自验结论可交付 | 替测试判准出、替产品改业务口径 |

**口径分离（禁混用）**

- **开发自验** verdict：`PASS` / `CONDITIONAL` / `FAIL`（轻量测试报告 / 方案卡 §5.1）→ 回答「本轮改动能不能用」。
- **版本准出**：仅测试包 / 正式测试负责人结论 → 回答「版本能不能出」；本包不得写「已准出」。
- **可选输入不阻塞**：缺他包产物（PRD/测试报告/UAT）→ 一句缺口，用本包模板补或用户提供；**不**等于可省 AC、产品最小判断、完成门、自验证据。
- **轻量**：裁剪文档厚度与门数量；**不**裁剪证据、P0、完成门、红线。

**不确定时**：solo vs 完整档、是否升级、是否免产品盘问但仍须 AC——先出推荐 + **只问 1 问**确认，不静默降档或硬撑。

## 1. 三档

| 档 | 适用 | 典型 | 产物 | 门 |
| --- | --- | --- | --- | --- |
| **快档** | 想法清楚、单点改动、≤3 文件 / ≤1 模块 | 文案、样式、单接口、小脚本 | 方案卡（一页；含产品判断/技术/任务/验收/测试） | `confirm_spec` + `completion-gate` + `confirm_commit` |
| **标准档** | 小功能、2～3 模块、需要产品定义 | 新页面、新流程、一次小迭代 | 产品定义卡 + 方案卡 + 轻量测试报告 | `confirm_spec` + `completion-gate` + `confirm_commit` |
| **完整档** | L2+/L3、跨系统/高风险 | 权限/资金/迁移/公共 API/破坏性 | 现有需求基线/方案/任务清单/评审/提测/发布 | 现有门 |

- 默认快档；**不确定按高一档**，并在首条 `reason=` 写清；若用户意图与体量冲突 → §0 一问确认。
- 快档不强制产品定义卡；方案卡 §0/§1 须含**产品最小硬门槛**五字段（见 §3.1），不得空写「按用户说的做」。
- 标准档只在「新想法 / 新产品 / 方向不清」时加产品定义卡；需求已清楚可只用方案卡，但测试报告优先独立落盘。
- 完整档直接走 `change` / `iterate`，不把轻量档当绕过评审/测试的借口。
- 「做个 / 快速做」只影响入口口令；**体量/风险仍按 §2 判定**，命中即升级，勿死板塞 solo。

## 2. 升级触发（命中任一 → 停，说明理由，转完整档）

1. 新产品 / 新业务 / 新用户群，或价值、成功标准说不清。
2. 跨 3 个以上模块，或改动 >5 个文件 / >300 行（不含生成/锁文件）。
3. 接口 / 数据库 / 权限 / 资金 / 迁移 / 安全 / 合规 / 破坏性变更。
4. 需要正式评审、提测、发布审批、回滚演练、交接包/回执。
5. 测试出现 P0 失败，且根因涉及产品范围/架构，不是单点实现错误。
6. 用户明确说「走完整流程 / 写 PRD / 出测试计划 / 按团队流程」。

> 升级不是失败；把轻量档硬撑成完整档才是。升级时保留已产出的方案卡，作为完整档输入，不重写。拿不准是否命中 → 推荐升级并一问确认。

## 3. 文档最小集

| 档 | 必产 | 可并入 | 不产 |
| --- | --- | --- | --- |
| 快档 | 方案卡（含验收表/测试点/**自验结果**） | 产品判断、自验结果可写在方案卡内 | 独立 PRD、需求基线、测试计划、用例库、提测单 |
| 标准档 | 产品定义卡（按需）+ 方案卡 + **独立**轻量测试报告 | 极小功能才可把报告并入方案卡附录（须仍有完整 verdict/P0/证据） | 16 节 PRD、18 节测试计划、用例库 |
| 完整档 | 现有模板 | — | — |

- 方案卡落 `开发/02-方案设计/方案卡-{主题}-{yyyyMMdd}.md`；产品定义卡落 `开发/01-需求基线/产品定义-{主题}-{yyyyMMdd}.md`；测试报告落 `开发/05-测试与验收/测试报告-{主题}-{yyyyMMdd}.md`。
- 一页为目标，不为凑节写空话；超出用附录，不另起一套文档。
- 方案卡必须含可被 `completion-gate` 读取的验收表：`ID | 验收标准 | 检查 | 证据`；每条证据是路径或可复跑命令。

### 3.1 产品最小硬门槛（实施前必齐；免盘问不免字段）

无论是否写产品定义卡、用户是否说「不做产品判断」，进入 `confirm_spec` / 写代码前必须齐：

| 字段 | 最低要求 |
| --- | --- |
| 谁 | 具体角色（禁「所有人」空写） |
| 问题 | 场景 + 现状代价（可标假设） |
| 成功标准 | 条件 + 动作 + 可观测结果 |
| 非目标 | ≥1 条明确不做 |
| AC | ≥1 条可被完成门读取 |

用户豁免「产品盘问」→ 仍输出上述五字段（假设标 `[假设]`），在方案卡确认时一并签收；**不得**无 AC 开工。

## 4. 测试最小集（开发自验）

| 变更 | 必测 | 证据 |
| --- | --- | --- |
| 纯文案/样式 | 受影响页面 + console 无 error | 截图（桌面/移动按需） |
| 前端行为 | 主路径 + 1 边界 + 1 异常 + 受影响回归；状态/视口/console/network | 截图 + network 摘要 |
| 后端/接口 | 主路径 + 1 边界 + 1 错误码/权限 + 受影响回归 | 命令/响应/日志 |
| 数据/迁移 | 上述 + 迁移前后核对 + 回滚路径 | 查询结果/脚本输出 |
| 高风险 | 升级完整档，按检查矩阵 L2/L3 | 现有证据 |

- **AC 走查**：方案卡/基线每条 AC 至少对应一次检查结果（通过/失败/未测+理由）；未走查不得写 PASS。
- P0 未过 = 整体 FAIL；不得用「有条件通过」掩盖 P0。
- 有条件通过仅限 P0 全过、缺口非 P0、用户明确接受并记录。
- 未测项必须列缺口；不得写「应该没问题」。
- 能脚本的稳定回归优先脚本；一次性/探索式用 AI + 浏览器/API；同一失败修复后跑「原用例 + 冒烟 + 影响面」。
- 结论用语写「开发自验 / 可交付（有条件）」；禁写「版本准出 / 测试通过可发布」（后者归测试包）。

### 4.1 完整档无 QA 时（`change` / `iterate`）

- **跳过 `deliver`（无提测单）≠ 跳过自验**。
- L1+ 且改动触及用户路径 / 交互 / 业务规则 / 接口行为 → verify/gates **必须**产出轻量测试报告（或方案卡/验收附录含完整 verdict/P0/缺口/证据）；仅 build/lint/单测绿不算功能自验完成。
- L0 纯文案/配置仍按检查矩阵最小集；无用户路径可不强制独立报告，但收尾须写自验依据。
- 有测试包且本轮已有正式测试报告 → 引用，不重复造轻量报告；不以开发自验替代准出。

## 5. 门策略

- 快档只保留两个确认点：`confirm_spec`（方案卡批准）与 `confirm_commit`（拟提交）；产品定义不单独设门，方向不清在方案卡里列选项一次性确认。
- `completion-gate` 仍必须过；轻量不等于免验证。
- 不单独走 `select_review_mode`、`confirm_requirements`、`confirm_backlog`；这些在完整档使用。
- 需要独立代码评审 → 转 `change.review`，不在轻量档内自称已评审。
- 测试报告未落盘/无 verdict/证据不存在（且本档要求报告时）→ 不得收尾为完成。

## 6. 反模式

- 把「轻量 / 个人项目 / 无 QA」当「不测试/不验证/无 AC」。
- 把「可选输入不阻塞」读成「可以没有验收标准」。
- 一个想法直接写代码，跳过方案卡与确认。
- 小改也生成 16 节 PRD、18 节测试计划、用例库。
- 方案卡只有技术，没有产品判断/AC/测试点。
- 测试只跑 build，不跑用户路径。
- 发现 P0 还写「基本可用」；把开发自验 PASS 写成「已准出」。
- 用轻量档绕过权限/资金/迁移/安全评审；「做个/快速做」死板塞 solo 无视 §2。

## 7. DoD

- 产品最小硬门槛五字段齐；方案卡已确认；范围/非目标/AC/测试点/风险齐。
- 验收表每条有检查与证据；证据路径存在；AC 走查完成。
- 自验有 verdict、P0 结论、缺口；失败项已修/已接受/已升级；用语为开发自验非准出。
- `completion.json=COMPLETE`（本轮 task_id/diff_hash 匹配）。
- 收尾写清未验证/阻塞/升级项；无 QA 时含【开发自验】段；提交按 `confirm_commit`。
