# 澄清追问环（开发轨）

> **单一出处**：澄清的触发、提问格式、需求理解包、缺口清单、停止条件与落盘。`AGENTS.md` §0.2、workflow 步注、技能只引用本文，不另写一套。
> **与确认门的关系**：确认门=执行授权（`hitl`）；澄清=理解对齐。门不能替代澄清；澄清答复不自动授权执行，仍需按步过门。
> **读取时机**：任务开始、输入含文档/原型、需求或验收不明、准备用假设推进、准备产出方案/清单/代码前。
>
> **总规则（强制）**：先读规则/技能/代码/文档并做分析，再问用户；**只问影响意图、范围、验收、风险且 AI 无法自行确定的问题**；技术细节（接口/组件/字段/状态实现/性能/兼容）由 AI 查规则与技能后给建议，不逐条问用户。不确定项先按 **§1.1 决策归属（P/D/S）** 分流。首轮通常 0～1 个问题，最多 3 个高影响问题（阻塞/安全/合规/高风险不受限）；**意图有歧义时先确认再执行，意图已清可直跑**。95% 仅参考，不作为停止条件。确认门不是澄清。

## 0. 意图理解确认（择优 · 防自作主张 · 忌死板）

> 与 `confirm_understanding`（需求 Brief+差量）分工：本节是**本轮你要我干什么**的轻量对齐；需求建模仍走理解门。  
> **原则**：AI 先根据口令清晰度、上下文、是否跨角色外发，**择优**选档；禁止「凡落盘必弹长表」，也禁止「含糊口令直接写文件」。

### 0.1 何时必须停（`intent_needs_confirm`=真）

命中任一即停，出示完整【意图理解】，等用户「对/按这个来」后再落盘：

1. 口令含糊（如只说「交接/处理一下」），给谁/交什么/形态推不出唯一解。  
2. 接收方、交付形态（A/B/C/专模/HO）、产物类型有 ≥2 种合理解读。  
3. **跨角色外发**交接单/确认文（给产品/测试/运维看）且本任务尚未对齐过该意图。  
4. 新开对外交付主题（与上一段已确认意图明显不同）。

### 0.2 何时可直跑（`intent_needs_confirm`=假）

1. 纯查询 / 只读状态 / 机械低风险且无分支。  
2. 同任务意图已确认且未变（续写、按已确认方案改代码、补证据等）。  
3. **本句或上下文已把意图写死**（谁+做什么+产物形态唯一）→ 一行意图回执后即可执行，**不等**第二轮「对不对」。  
4. 任务内已对齐范围的实施续跑（改代码/配配置属已确认任务的自然步骤）→ **不**另开意图门（需求侧仍走 `confirm_understanding` 等原门）。

拿不准是否歧义 → 按真处理（停问）；能唯一确定 → 按假直跑。

### 0.3 三档输出（AI 择优）

| 档 | 何时 | 做什么 |
| --- | --- | --- |
| **A 完整确认** | §0.1 | 出【意图理解】五条 → **停等**确认 → 再落盘 |
| **B 一行回执即做** | §0.2.3 意图已清 | `【意图】给谁｜做什么｜形态` 一行后直接落盘；用户当场纠正则停改 |
| **C 免示** | §0.2.1～2、4 | 可不单独出示；需要时收尾带一句即可 |

```text
【意图理解】（仅 A 档）
- 你要我做：{动作}
- 接收方/受众：{…；无则写「无」}
- 交付形态：{A/B/C/专模/HO}（推荐：…｜备选：…）
- 关键要点：{3～5 条}
- 明确不做：{…}
请确认：对 / 不对（指出哪条）/ 补充…
```

- A 档：只回「OK/随便/你定」且未对复述表态 → 不算确认。  
- 步上 `hitl: confirm_intent` 仅当 `intent_needs_confirm` 为真才停；为假则跳过该门。  
- 未挂 hitl 的产出步：仍按 §0.1～0.3 择优，有歧义不得静默落盘。

## 1. 问什么 / 不问什么

**必须问用户（AI 无法从资料推断，且会影响结果）**：

1. 目标/要解决的问题、用户与场景、成功标准。
2. 范围/非目标、优先级与取舍。
3. 只有用户知道的业务规则、约束、验收差异。
4. 需求/文档/原型冲突需要用户裁决。
5. 高风险/不可逆动作的接受度（权限、资金、迁移、发布/回滚、删除/覆盖）。

**AI 自行分析，不问用户**：

- 技术实现、接口是否存在/怎么设计、组件复用、字段命名、状态机实现、异常处理方式、性能方案、兼容方案、测试方法。
- 先查 `规则/`、`技能/`、`项目档案.md`、代码、PRD/原型；能确定就直接给方案/建议。
- 只有技术选择会改变用户可见范围/AC/风险时，才升级为“需要你拍板”的取舍题，并附推荐。

**可以免问**：纯信息查询、机械操作、已由文件/代码唯一确定且无分支的低风险步骤；免问也给一行理解回执。

## 1.1 决策归属三分法（强制 · 防瞎做 / 防乱抛）

每条不确定项、冲突、GAP、文档「待确认」必须先标**归属**，再决定问谁、是否停实施。归属写进理解包 / 待决项 / 收尾第 4 点；禁止无归属散问。

| 归属 | 触发（命中即归此类） | AI 动作 | 默认接收方 |
| --- | --- | --- | --- |
| **P 产品** | 业务目标/范围/非目标/优先级；业务规则/验收差异；文档·原型冲突需业务裁决；**多份权威文档口径打架**（含表 vs 注）；文档未标明交开发的业务缺口 | 不静默选边；出理解复述 + 选项 + 推荐；阻塞则即时问；需产品拍板 → 【待确认单·产品】（用户可转发）或经用户确认后发 `CLAR`；**关闭前禁实现任一侧完整行为**（`规则/核心/实施质量门.md` DEV-IQ-04） | 用户 → 产品 |
| **D 开发** | 文档明示「由开发确认 / 开发决定 / TBD（开发）/ 技术选型交开发」；纯技术实现（接口/组件/字段命名/状态实现/性能/兼容/测试方法）且不改变用户可见范围/AC | **按项目档案 · 现行代码 · 技能 · 市面规范择优** → 出示「推荐 + 理由 + 备选」→ **向用户确认后执行**；**默认不回抛产品** | 用户（开发拍板） |
| **S 方案缺陷** | 方案/PRD 自相矛盾、逻辑断裂、不可测措辞无阈值、缺主路径/非法跃迁/终态且无法从原文推断；条款互相否定 | **统一出【待确认单】**（问题 / 原文位置 / 影响 / 建议裁决）；**停 design/implement**；不静默选边、不用惯例补洞；UI 不得开放与未决口径冲突的可操作入口 | 用户（必要时转产品） |

**硬规则**：

1. **先归类再问**：同一事项只标一个主归属；兼有业务与技术时，改 AC/范围 → **P**，仅实现路径 → **D**；方案自相矛盾 → **S** 优先于瞎做。
2. **D 不得静默落地**：即使文档写「由开发确认」，也须给用户看推荐与影响；用户明确同意或「按建议」后才写入基线/方案并实施。低影响 D 可进收尾第 4 点「默认按建议」，但须列出。
3. **D 改变可见行为/AC/风险** → 升级为 **P**（或向用户明示「开发建议已越出原文，需业务确认」）。
4. **S 未关闭** → 不得进入 `design` / `plan` / `implement`；可继续只做理解包与待确认单。
5. **禁止**：把 **P/S** 当成 **D** 用惯例补需求；把 **D** 整包甩给产品；无归属问卷；把「行业最佳实践」写成 `[原文]`。

**【待确认单】最小字段**（对话展示 + 可落 `开发/00-项目治理/待决项.md`；转发产品时只含 P/S）：

```text
【待确认单】主题={…}｜日期={yyyy-MM-dd}｜来源={文档路径/章节}
| 编号 | 归属(P/D/S) | 事项 | 原文/证据 | 选项 | 建议 | 影响 | 可转发产品 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Q1 | P | … | … | A/B | A（理由） | 阻塞实施/仅口径 | 是 |
```

- 用户回复：`编号=选项` 或「全部按建议」。
- 转发产品：复制表中 `可转发产品=是` 的行（可去掉 D 行）；收回答复后回写待决项与理解包。

## 2. 首轮固定动作：先分析，再问 0～1 个关键问题

> **只读/解释例外**：`入口判定` 意图类 **L** 或 `执行契约` §1.2 只读分析（解释/对比/诊断/复盘、不改文件不入交付链）→ **可不套**本节 5～8 行交付骨架；用理解要点 + 0～1 问（或分析说明）即可。澄清/方案/实施等**交付链**仍走下方骨架与 P/D/S。

首轮回复按此顺序，不得先写方案/代码/长清单，也不得先列一串问题：

```text
【我的理解】{目标/用户场景/范围/不做/AC/关键约束，5～8 行}
【我已按规范/技能分析】{技术方案/复用/风险/建议，3～6 行；不把技术细节抛给用户}
【需要你拍板】{0～1 个最关键问题；附推荐；没有则写“无阻塞问题”}
【其余假设】{不影响方向的技术/细节假设；用户不反对即按此执行}
确认后我执行：{下一步}
```

- **首轮最多 1 个问题，总提问不超过 3 个高影响问题**；不把接口/组件/字段/状态实现等技术细节列成问题。
- **非机械任务至少给一次理解复述，请用户确认**；复述本身算确认，不必额外编问题。
- **先查后问**：能从规则、技能、档案、代码、计划、原型、既有记录确认的，先查并引用；只问查不到且会改变结论的。
- **问题可回答**：单选/短答/二选一优先；不问“你觉得怎么样”，不问实现细节。
- **附建议**：先给推荐答案 + 一句理由；猜测错了要显式改口。
- **问完就停**：等用户回答；不得自问自答，不得把“我先按 X 做”当已确认。
- **问题顺序**：目标/问题 → 范围/非目标 → 成功标准/验收 → 业务约束/冲突 → 风险取舍；技术细节不进入提问列表。

## 2.1 不确定项分流（防散问）

- **先标归属（§1.1）**：每条 OPEN 写 P/D/S；收尾表与待决项同步带归属列。
- **阻塞项**（含全部 **S**、未决且挡门的 **P**、会改 AC/风险的 **D**）：不决定就无法继续当前步/门/验收 → 即时问（0～1 个），按 §2 格式；收尾第 4 点复述。
- **非阻塞项**（低影响 **D**、不挡门的 **P**）：不即时问；登记 `开发/00-项目治理/待决项.md`；收尾第 4 点一次输出；**D** 写清「默认按建议」。
- 首轮只列阻塞项；常规总提问 ≤3（阻塞/安全/合规/高风险问题不受 3 问限制，仍一次一问）；收尾表 ≤5；编号带中文名。禁止散问/重复问；阻塞项不得拖到收尾。
- 回复后更新待决项/决策记录/计划；已确认不重复。

## 3. 回答之后：更新理解，必要时才追问

每轮回答后：

1. 用 1-2 句更新理解与方案（不要重复整段）。
2. 把已回答内容记为“已确认”，不再重问。
3. 只有回答引出新的高影响缺口/冲突才追问；否则更新理解并给方案/建议。
4. 常规总提问不超过 3 个；阻塞/安全/合规/高风险问题不受此限，但仍一次一问。超过说明需求本身不清楚，先帮用户收敛范围，不继续盘问。

**禁止**：把用户没说过的话写成结论；把“行业惯例/最佳实践”当需求；把多个问题合并成一段叙述；在用户回答前继续产出下游产物。

## 4. 停止条件（无实质缺口 + 用户确认，不靠感觉）

同时满足才可停：

- [ ] 需求理解包核心项已填；技术细节已有 AI 建议/方案；未知项只保留高影响缺口。
- [ ] 能复述：谁 / 在什么场景 / 做什么 / 系统怎么响应 / 怎么算对 / 明确不做什么。
- [ ] 关键冲突已裁决；未决项已标归属（P/D/S）与“假设”，并有验证方式与责任人；**S 无未关闭项**。
- [ ] 用户明确说“对/是/按这个来/可以”；**D** 项已确认推荐或写入「默认按建议」。
- [ ] 复述中的范围、AC、非目标与用户最后的表述一致。
- [ ] 剩余缺口只是低影响假设 / 非阻塞 **D**，或已给建议待用户确认，不需要继续盘问。

**不算确认**：“随便/你决定/看着办/应该可以/差不多/沉默/只回一个 OK 但没有对复述表态”；**只回范围选项（如选 A/B）而未对整包理解复述表态**。遇到这些 → 给两个具体选项再问一次，或更新理解后等「对/按这个来」，不要开跑。

**置信度锚点（参考值，不作为停止条件；以缺口清单和用户确认为准）**：

| 区间 | 含义 | 动作 |
| --- | --- | --- |
| <50% | 目标/用户不明 | 只问目标与用户，不产出 |
| 50-70% | 主链大致清楚，范围/规则有缺口 | 只问最高影响问题；技术细节自行分析 |
| 70-85% | 主链与主要规则清楚，边界/异常/NFR 有缺口 | 补关键业务缺口；技术细节给方案/假设 |
| 85-95% | 可复述，少数低影响项未定 | 复述确认；低影响项标假设 |
| ≥95% | 可复述且用户已确认 | 产出最终方案/基线/清单 |

连续 3 轮置信度不上升 → 换问法或回退到“目标/用户”重问；仍不上升 → 明确告诉用户“缺一个基础信息”，请其补充或缩小范围。

## 5. 完整复述模板（过门/落盘前）

```text
【理解复述】
- 目标：{解决什么问题/为什么现在做}
- 用户与场景：{谁/什么场景/触发条件}
- 范围：{这次做什么}
- 非目标：{这次明确不做什么}
- 关键规则：{状态/权限/数据口径/异常}
- 验收：{怎么算对；条件+动作+可观测结果}
- 约束与风险：{依赖/兼容/回滚/合规}
- 未决与假设：{待确认项/假设/验证方式}
对 / 不对 / 补充？
```

开发轨另加“技术差距/影响面”；输入含原型时另加“必须保留/可优化/未提供”。

## 6. 反迎合、反臆造

- 用户第一句话是“想要什么”，不是“为什么/怎么算成功”；先问后者。
- “应该/惯例/最佳实践/竞品也这样” → 追问具体场景、上次发生时间、代价、不做的后果。
- 用户改口：以最新回答为准；旧结论标作废，不留双真值。
- 不知道就说不知道；无来源写“假设/待验证”，不得写成事实。
- 不为了让用户满意而降低澄清标准；不把“用户没反对”当同意。

## 7. 落盘（单一真值）

| 场景 | 落点 | 最少内容 |
| --- | --- | --- |
| 外部 PRD/迭代方案/原型 | `开发/01-需求基线/理解-{主题}-{yyyyMMdd}.md` | **§0 Brief+本期差量表（必填）**、来源、下钻理解包、缺口清单、Q/A、冲突、GAP、假设、置信度；模板见 `规则/模板/10-规划与需求/需求理解包模板.md` |
| 需求基线 | `开发/01-需求基线/需求-{主题}-{yyyyMMdd}.md` | 来源、Q/A、假设、AC、非目标 |
| 轻量需求卡 | 需求卡/任务说明 | 目标、AC、非目标、假设 |
| 待确认/决策项 | `开发/00-项目治理/待决项.md` | 编号+中文短名/**归属(P/D/S)**/事项/选项/建议/影响/默认/可转发产品/结论 |
| 待确认单（对话或转发） | 对话第 4 点或独立块；P/S 可复制转发产品 | 见 §1.1 最小字段 |

- 记录格式：`Q: … → A: …（归属/来源/日期/裁决人）`。
- 用户裁决优先于代码现状；代码与裁决不一致 → 记差异并回到澄清，不得用代码推翻裁决。
- 后续会话先读已确认记录，不重复问；有新证据才重开，重开另起一条，不覆盖旧裁决。
- **D** 结论记「开发择优 + 用户确认」；**P/S** 结论记裁决人（用户/产品）。


## 8. 例外与边界

- **用户点名“直接做/不用问”**：仍先给 3 行理解回执 + 假设清单；高风险/不可逆至少问 1 个最高影响问题。只免等待，不免理解与留痕。
- **热修/事故**：先止损；事后补澄清记录与复盘，不把临时假设写成需求。
- **非交互/自动化**：不猜；标 `blocked` + 待确认问题清单，交回人工。
- **确认门**：先澄清后过门；门只确认“是否执行”，不替用户回答“要做什么”。
- **确认门/菜单**：可一次展示多个授权选项，但不得夹带澄清问题。

## 9. 反模式（出现即停）

- 一轮列 3 个以上问题 / 发问卷；首轮把非关键问题也列出来。
- 把接口/组件/字段/状态实现/性能等 AI 能查的技术细节逐条问用户，而不是先查规则/技能/代码给建议。
- 不带猜测的开放盘问。
- 用户答完不更新理解，直接跳下游。
- 把“已读文档”当“已理解”；不引用章节/页码。
- 把原型当后端规则；把竞品做法当客户需求；把领导一句话当市场验证。
- 用“假设”绕过澄清，且不标假设、不写验证方式。
- 把“确认门”当“澄清”，或把“澄清回答”当“执行授权”。
- 置信度虚报 ≥95%，但复述不出“谁/场景/做什么/怎么算对/不做什么”。
- 不确定项无归属；把 **P/S** 当 **D** 用惯例补需求；把 **D** 整包甩产品；**S** 未关闭仍开写方案/代码。
