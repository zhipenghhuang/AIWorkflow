# 规则治理（开发轨）

> 目的：防止规则越写越多、互相冲突、没有执行载体。维护/改规则时读；业务任务不读。
> 原则：**规则不是越多越稳；一条规则一个 owner；能被脚本检查的，不写成长文。**

## 1. 预算

| 对象 | 上限（估算 tokens） | 说明 |
| --- | ---: | --- |
| `AGENTS.md` | ≤ 5,500（目标） | 常驻；§0 计入总量、宜指针化收敛；只留路由、最短不变量、读取协议、验证/汇报指针 |
| 常驻/必读规则 | ≤ 3,000 | 每次任务可能读的规则；超了拆节或移 playbook |
| 参考手册/playbook | ≤ 10,000 | **必须**在头部标 `读取级别：参考` + 节索引；只读当前节，禁止通读 |
| 单个 `技能/<name>/SKILL.md` | ≤ 4,500 | 技能按步加载；超了拆 `references/` 或脚本 |
| 模板 | 不设 token 上限 | 只复制/填写，不作为规则通读 |
| 单步读取总量 | ≤ 8,000 | 核心 ≤3～4 来源（命中才读）；复杂可至 5；AGENTS 当前步 + workflow step + 当前 agent + 命中技能/playbook 节 + 产物 |

估算：CJK 字符约 1 token/字；ASCII 约 4 字符/token。`Test-DocHygiene.ps1` 检查常驻规则、参考手册、AGENTS、技能；模板不报预算。

**读法分级**：
- **常驻**：`AGENTS.md`、`规则/门.md`、`规则/核心/验证规则.md`、`规则/核心/澄清.md`、`规则/读取索引.md`、`规则/文档治理.md` 的核心节。
- **参考**：`工作流.md`、`规则/缺陷/缺陷修复协作.md`、`规则/协作/协作与交接.md` 等长流程；只在对应 step 读当前节。
- **技能**：命中步才读，不命中不读。
- **模板**：只读当前要填的一份，不通读模板库。

## 2. 单一出处

- 每条规则只在一个文件定义；其他位置只放“指针 + 规则 ID”。
- 高频重复规则（一次一问、证据先于结论、文档现行有效、子代理边界）必须合并。
- 阻断路径统一 `必须/禁止/不得`；`可/建议/按需/必要时` 只用于非阻断能力。
- 新增规则前先问：能否合并到现有规则？能否用脚本检查？能否删掉旧规则？三者都否，才新增。

## 3. 规则 ID

- 格式：`DEV-<域>-<序号>`，如 `DEV-VER-03`。
- 每个 ID 对应：一句话不变量、执行载体（gate/script/human）、适用 step。
- 报告/gate 输出引用 ID；无法引用 ID 的规则视为“无执行载体”，应删除或改写。

## 4. 条件门

- **只认** workflow 步上 `hitl` / `hitl_when` / `gate_when`；语义见 `规则/门.md`；专规不另造门。`hitl_when` 用于按事实条件开门/跳过，**合法且应保留**。
- L2+、外部文档输入、前端行为变化：默认开门；**禁止用条件把 L2+ 高风险门跳过**（不得写使高风险门恒假的条件）。
- L0/L1 才允许用条件跳过低风险门；跳过必须记录理由。
- 条件由外部事实/脚本判定优先；模型自评只作建议，不确定按触发处理。

## 5. 规则卫生检查（维护时）

```powershell
powershell -ExecutionPolicy Bypass -File "开发规范/规则/tools/Test-DocHygiene.ps1"
powershell -ExecutionPolicy Bypass -File "开发规范/规则/tools/Test-Template.ps1"
python "开发规范/规则/tools/validate_workflow.py" "开发规范"
```

检查：引用/锚点、YAML、workflows→agents、版本单点、AGENTS/规则行数、读取索引挂载、孤立模板。
新增检查（后续）：token 预算、重复句、同范围“必须/可跳过”冲突、孤儿规则。未实现前由维护者人工核对。

## 6. 规则 eval（改规则时，5 个场景）

1. 没跑测试就写“完成” → 报告 lint 必须失败。
2. 前端只测 happy path → gate 必须 BLOCKED（缺状态/截图）。
3. console 有 error 仍报通过 → gate 必须 BLOCKED。
4. UI 改动被降级为 L0 → 风险分级必须升到 L1。
5. 验收清单缺证据 → gate 必须 BLOCKED。
6. 空 diff / dry-run → 必须 `NOT_VERIFIED` / `DRY_RUN`，不得 `COMPLETE`。
7. 包内 `.state`/包内 `project-profile.json` 存在 → 不得被读取；旧截图/旧验收 → BLOCKED。

eval 通过才算规则改好；不通过先修规则/脚本，不加新规则。

## 7. 变更流程

1. 说明要解决的问题与现有规则冲突/冗余；
2. 优先合并/删除，再新增；
3. 改 workflow/agent/规则/技能/模板中的一处 owner；
4. 跑规则卫生检查 + 5 个 eval；
5. 更新 `CHANGELOG.md` 与版本单点；
6. 旧规则删除或归档；现行文档遵守「当前有效状态」（见 `文档质量标准.md` §1 第9条）：不留“旧方案/已废弃/不要再用”等删后说明。
