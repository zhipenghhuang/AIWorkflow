# 入口判定（无显式口令时）

> **定位**：用户直接描述问题、需求、改动时，不要求前缀；按「输入 → 意图 → 项目状态」选最小可用 workflow。
> **读取时机**：`AGENTS.md` §3 未命中、口令不明确，或用户用自然语言描述问题时。
> **与口令表的关系**：明确口令仍按 `AGENTS.md` §3 表优先；本文件只补“没有口令/口令模糊”时的判定，不另造 workflow。
> **单一出处**：自然语言入口、默认路由、歧义处理、首条 `reason` 格式；其它文件只引用。

## 1. 判定顺序

### 1.1 先看输入

| 输入 | 走法 |
| --- | --- |
| 附 PRD/方案/需求文档/原型/截图/接口文档，要吸收/更新基线/影响分析 | `intake` |
| 附文档/方案，要生成或更新开发计划 | `control.init`（已有计划则 `control.sync`/`run`） |
| 附方案/文档，要按方案实施、拆任务、继续迭代 | `iterate.precheck` |
| 现有代码/仓库 + 具体描述 | 进入 §1.2 |
| 空项目/只有想法/从零 | `solo`（需要建档时再 `onboard`） |

### 1.2 再看意图

| 意图 | 默认 |
| --- | --- |
| 报错/失败/异常/回归/“没反应/不对/坏了” | 单包/单人 → `change`（先复现/红证/根因）；有缺陷 ID/平台/指派 → `defect-fix` |
| 新想法/新项目/从零/范围不清/“值不值得做” | `solo` |
| 具体功能/改动/优化/重构/“加个/改个/做个” | 单包小项目 → `solo`；多包/正式协作 → `change` |
| 测试/验收/“测一下/验一下/能不能用” | 无测试计划 → `solo.test`；已有本轮代码改动 → `change.verify`；发布前 → `release` |
| 计划/进度/下一步/当前状态/排期 | `control` |
| 发布/上线/回滚/复盘 | `release` / `retro` |
| 文档/资料整理/归档/清理 | `onboard` |

### 1.3 再看项目状态

1. `项目档案.md` §1 已填 `协作模式`/`流程偏好` → 以档案为准，不被启发式覆盖。
2. 未填时按以下推断：
   - **单人/轻量优先**：单包 + 无 `开发/开发计划.md` + 无 `测试/` + 无 `产品/` + 无 QA/交接。
   - **团队/完整优先**：多包，或已有开发计划/QA/交接/正式评审。
3. 推断结果在首次任务收尾写回 `项目档案.md` §1；不额外提问。

### 1.4 歧义处理

- 两条路线**只差文档厚度/门数，风险相同** → 选低风险/低文档路线，首条写 `reason=`；用户可一句纠正。
- 两条路线会改变**范围/验收/风险/是否实施** → 只问 1 个问题，附推荐；不列问题清单。
- 连续 3 轮无新信息 → 按推荐路线执行或缩小范围，不继续盘问。

## 2. 默认表（按真实说法）

| 你说 | 默认路线 |
| --- | --- |
| “登录后刷新就退出，帮我看看” | `change`（bug 意图；先复现/红证/根因；有缺陷 ID → `defect-fix`） |
| “我想加个导出功能” | 单包 → `solo`；多包/正式 → `change` |
| “根据这个 PRD 生成开发计划” | `control.init` |
| “按这个方案做一下” | `iterate.precheck` |
| “帮我测试一下登录” | 无测试计划 → `solo.test`；有本轮改动 → `change.verify` |
| “改一下登录逻辑” | 单包 → `solo`；多包/正式 → `change` |
| “这个项目我中途加入，想改…” | `change`/`solo` + 轻量摸底（§3） |
| “下一步/当前状态/进度” | `control` |
| “发布/回滚/复盘” | `release` / `retro` |

## 3. 项目摸底（中途加入）

没有 `项目档案.md` / `activeContext.md` 时，**不强制完整 onboard**；先做一次轻量摸底：

1. 读 README、包管理/构建文件、目录结构、入口文件、测试命令、已有文档。
2. 能推断栈/命令/入口/测试方式 → 直接继续，把结论写 `项目档案.md` §1/§2/§7 或收尾假设。
3. 缺关键事实（构建/测试命令、环境、数据）且影响验收 → 只问 1 个问题；不要求补 PRD/测试计划。
4. 项目已存在但无档案 → 首次改动后建议「接入开发规范」补档案；不阻塞当前任务。

## 4. 首条格式

```text
route=workflow:<id> | step=<id> | level=<L0-L3> | reason=<输入/意图/项目状态一句话> | next_action=…
```

- `reason` 必写，让用户能看出为什么这样走；判断错时用户可一句纠正。
- **明确短命令**（如「发布」「提测」「下一步」「接入」「提交」）仍按 `AGENTS.md` §3 表优先；描述句里出现「计划/变更/测试」等词，不单独作为命中依据。
- 不因“想走轻量”降低证据/门/红线；不因“想快”跳过产品判断/测试。
- 判定为 `solo` 时按 `规则/核心/轻量交付.md`；判定为 `change`/`iterate` 时仍按原链路，不另造门。

## 5. 反模式

- 用户没喊“轻量开发”就永远不走 `solo`，继续用完整链。
- 用户描述 bug，却因为没写“修复#”就当成普通需求，跳过复现/红证/根因。
- 用户给了 PRD 说“出计划”，却先问一堆产品问题或重写需求。
- 用户说“按这个方案做”，却回到需求分析重做一遍。
- 为了“自然语言”增加隐藏门/额外提问；或反过来跳过完成门/测试。
- 把“项目状态推断”写成事实，不记录假设。
