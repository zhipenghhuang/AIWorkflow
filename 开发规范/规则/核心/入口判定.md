# 入口判定（无显式口令时）

> **定位**：任意自然语言 → 选**最小可用** workflow/step。不依赖固定口令措辞；靠「信号抽取 + 意图类 + 项目状态」判定。
> **读取时机**：`AGENTS.md` §3 未命中、口令模糊、或用户用描述句提出任务时。
> **与口令表**：明确短命令仍优先；本文只补模糊入口，**不另造 workflow/门**。
> **技能**：路由后只读当前步技能；口语不能跳过必用技能。
> **单一出处**：自然语言路由；其它文件只引用。
> **与轻量交付**：档位/升级/不降标见 `规则/核心/轻量交付.md` §0～§2；本文只负责选路。

## 0. 原则

1. **看意图与对象，不抠关键词**。同义说法（看看/帮我弄/弄一下/处理下/麻烦看下）等价；禁止「必须含某词才路由」。
2. **最小可用**：能 `solo`/clarify 解决的，不升完整链；风险/跨模块才升级。「做个/快速做」类：分析体量与意图——轻量/想法落地 → `solo`；明显 L2+/权限资金迁移等多模块重活 → `change`/`iterate`，勿死板塞 solo。
3. **有计划先续跑**：已有开发计划且像「继续/下一步/做到哪了」→ `control`，不另起炉灶。
4. **先理解再改**：对象是外部文档/原型且目标是理解或落地 → 先解析/澄清，不直接改代码。
5. **首条可纠正**：`reason=` 写清依据；用户一句可改道。
6. **不确定先确认**：两路线会改变范围/是否实施/验收/档位时 → 推荐 + **只问 1 问**；不静默降标、不硬撑轻量。
7. **轻量优先 ≠ 降标**：单人/无他包时优先 `solo` 入口，仍须产品最小硬门槛 + 完成门 + 开发自验（`轻量交付.md` §0）。

## 1. 每条消息先抽五元组（必做）

从当前用户话 + 附件/路径/会话焦点抽出（缺项标「未知」）：

| 轴 | 问什么 | 取值示例（非穷尽） |
| --- | --- | --- |
| **动作** | 要理解、决策、产出文档、改系统、验证、运维发布、还是治理资料？ | understand / decide / produce / change / verify / operate / govern |
| **对象** | 在处理什么？ | 现象(bug) / 想法 / 功能点 / 产品文档·原型 / 技术方案 / 代码·配置 / 计划·进度 / 缺陷单 / 交接包 / 仓库资料 |
| **结果** | 结束时要什么？ | 解释·建议 / 方案·清单 / 代码变更 / 验证结论 / 计划更新 / 发布·回滚 / 交接·归档 |
| **连续** | 新开、续跑、还是纠正上轮？ | new / resume / correct |
| **体量** | 单点还是跨面？有无权限/资金/迁移/破坏性信号？ | L0～L3 初判；未知先按高一档再在 clarify 收敛 |

**快速启发（可叠加，冲突用 §3）**：

- 附件=PRD/方案/原型/接口文档 → 对象偏「产品文档·原型」或「技术方案」。
- `#数字` / 平台指派 / 「待修」 → 对象偏「缺陷单」。
- 「继续/接着/还没做完/下一步」+ 已有计划 → 连续=`resume`。
- 报错栈、失败截图、「不对/坏了/挂了」→ 动作偏 verify/change，对象偏现象(bug)。
- 「从零/新项目/值不值得」+ 空仓或无档案 → 对象偏想法，优先轻量入口（标准不降）。
- 「做个/快速做」+ 多模块/权限/资金/迁移信号 → **不要**仅因口令塞 solo，按 §2 升级或 §4 一问。

## 2. 意图类 → workflow（本包）

按五元组落入**一类**；一类对应一个默认入口。类内再选 step。

| 意图类 | 判定要点（通用） | 默认入口 |
| --- | --- | --- |
| A 故障处置 | 对象=现象/缺陷；要根因或修复 | 有缺陷 ID/平台 → `defect-fix`；否则 `change`（先复现/红证） |
| B 文档吸收 | 新外部资料要入库/影响分析/改基线 | `intake` |
| C 文档理解 | 已有产品文档/原型，要理解包/冲突表，暂不实施 | `change.analyze_input` |
| D 计划编排 | 要生成/同步/推进开发计划，或问进度/阶段 | `control`（init/sync/next/run） |
| E 按案实施 | 已有方案/清单，要落地或拆任务执行 | `iterate.precheck` |
| F 功能变更 | 要增删改行为/接口/配置；非纯 bug | 轻量单人 → `solo`；正式/多包/L2+ → `change.clarify`（有文档先 C） |
| G 方案设计 | 只要架构/接口/数据方案，或点名出方案 | `change.design`（「只出方案」到 review-docs 后收） |
| H 验证交付 | 要测/验/提测材料/评审代码或文档 | 轻量实测/无 QA 自验 → `solo.test`；本轮改动验收 → `change.verify`；提测 → `deliver`；代码审 → `review`；文档审 → `review-docs` |
| I 发布运维 | 上线/部署/回滚/发版观察 | `release`；复盘 → `retro` |
| J 协作交接 | 发包/收包/变更通知/重规划 | `handoff` |
| K 仓库治理 | 接入、档案、资料整理、清理、技能体检 | `onboard` / `skill-audit` |

**动作×对象速查（冲突时以上表+§3 为准）**：

| 动作 ↓ \ 对象 → | 现象/缺陷 | 文档·原型 | 想法/功能 | 计划 | 代码 |
| --- | --- | --- | --- | --- | --- |
| understand | A | C | F 的 clarify 或 solo.frame | D | F clarify / G |
| change / produce 实现 | A | 先 C 再 F/E | F | D 后按阶段 | F |
| verify | A 或 H | H（对照文档测） | H | D status | H |
| operate | I | — | — | D→I | I |
| govern | — | B/K | K | K | K |

## 3. 项目状态修正

1. 档案 §1 `协作模式`/`流程偏好` **覆盖**启发式。
2. 未填时：单包 + 无开发计划 + 无产品/测试包 + 无 QA → **轻量优先（solo 入口）**；否则 **完整优先（change/iterate）**。轻量优先仍适用 `轻量交付.md` §2 升级触发；无测试包 ≠ 免开发自验。
3. 已有 `开发/开发计划.md` 且连续=`resume` → 优先 `control`，不要新开 change 打断阶段。
4. 无档案/中途加入 → §5 轻量摸底，**不**强制完整 onboard。
5. 推断写 `reason=` / 收尾假设；首次任务可回写档案 §1。

## 4. 置信度与一问（不确定先确认）

| 情况 | 做法 |
| --- | --- |
| 唯一意图类，风险与文档厚度清楚 | 直接路由，`reason=` |
| 两路线只差文档厚度/门数 | 选更轻的；`reason=` 说明可改道 |
| 两路线改变范围/是否实施/验收/solo vs 完整档 | **只问 1 问**，附推荐与取舍；不列清单 |
| 「做个/快速做」与 L2+/高风险信号并存 | 推荐完整档并一问；勿死板塞 solo |
| 五元组多轴「未知」且影响路由 | 用附件与仓库现状补全；仍未知再 1 问 |
| 连续 3 轮无新信息 | 按推荐执行或缩范围 |

不问实现细节（那是澄清/技能的事）；只问**选哪条路**。问句模板示例：「按体量更适合走完整开发链（含评审/基线）；若你确认只做单点快改，我走轻量方案卡。选哪个？」

## 5. 中途摸底

无 `项目档案.md` / `activeContext` 时：

1. 读 README、依赖/构建、目录、入口、已有测试命令与文档。
2. 能推断栈与命令 → 继续任务，结论写入档案或假设。
3. 缺构建/环境且卡验收 → 一问。
4. 建议事后「接入开发规范」；不阻塞当前 A～F 类任务（自验/AC 仍按命中档执行）。

## 6. 首条格式

```text
route=workflow:<id> | step=<id> | level=<L0-L3> | reason=<意图类+关键信号一句话> | next_action=…
```

- 可附 `intent=<A-K>`、`input=<路径>`；若一问待答可写 `pending_confirm=档位|升级|范围`。
- 描述句里偶然出现「计划/测试/变更」**不等于**口令命中。
- 不因口语降低完成门/证据/红线；不把开发自验写成准出。

## 7. 反模式

- 把入口判定当成「口令同义词表」逐条字符串匹配。
- 永远走完整链，或永远走 solo，无视体量与档案。
- 「做个/快速做」死板塞 solo，忽略权限/资金/迁移/多模块。
- 把「轻量优先 / 无测试包」读成免 AC / 免自验。
- 对象是故障却当新功能做，跳过复现/红证。
- 对象是文档却直接写代码或重写需求。
- 已有计划且用户在续跑，却新开无关 workflow。
- 意图不清却静默选路，不问用户。
- 为自然语言加隐藏门，或跳过门/技能。
- `reason` 不写或写成无法纠正的断言。

## 附录：说法校验（非匹配词典）

任意改写只要五元组同类，路由应相同：

| 五元组摘要 | 应落入 |
| --- | --- |
| change + 现象 + 要修好 | A |
| understand + 产品文档 + 要理解包 | C |
| change + 功能点 + 要行为可用 | F |
| produce + 计划 + 要排期/阶段 | D |
| change + 已有方案 + 要落地 | E |
| verify + 功能/本轮改动 | H |
| operate + 发版/回滚 | I |
