# 工作流（常规变更 · 提交 · 交付 · 文档治理）

> **步骤顺序**以 `../workflows/change.yaml` / `release.yaml` 为准；本文保留护栏、阶段衔接与文档治理。  
> 缺陷 → `缺陷修复协作.md`；迭代 → `迭代交付.md`；发布/验收 → `技能/acceptance-and-launch/SKILL.md`。  
> 步内怎么改/怎么验 → AI 自定（`AGENTS.md` §0.6）。确认门**只认**步上 `hitl:`（标量用 `hitl_when`；列表各项带 `when`）。

## 0. 开发计划（开发控制面）

> 测试有《测试计划》总领；开发用《开发计划》总领**开发工作自身**。  
> 路径：`{文档事实源目录}/开发计划.md`（新项目建议 `开发/开发计划.md`；旧项目可保留 `docs/00-项目治理/开发计划.md`）；模板 `模板/开发计划模板.md`；技能 `技能/development-plan/SKILL.md`；流程 `workflows/control.yaml`（init/run/sync/check/next）。  
> 定位：只做阶段、门、状态、角色、产物索引、风险、下一步；**不复制** PRD/方案/任务/测试正文。L2+ 新项目/新产品默认启用；L0/L1 可写「不适用」。  
> 计划状态：草稿 / 已确认 / 执行中 / 变更中 / 待关闭 / 已关闭；首次创建或范围·版本·里程碑实质变更过 `confirm_plan`。  
> 归档：当前文件不移动；关闭时快照到 `{文档事实源目录}/_归档/{yyyyMMdd}-{版本}/开发计划.md`，当前计划重置/新建；稳定技术真值留 `项目档案.md`/ADR。

阶段：`S0 输入检查 → S1 需求分析 → S2 技术方案 → S3 任务与排期 → S4 编码自测 → S5 评审/CI → S6 提测 → S7 测试/缺陷 → S8 发布 → S9 收尾/复盘`。  
门：`G0 输入就绪 → G1 需求分析 → G2 方案批准 → G3 排期确认 → G4 开发完成 → G5 评审/CI → G6 提测就绪 → G7 测试通过 → G8 发布就绪 → G9 交付完成`。  
规则：

- 上一阶段未过门，不进入下一阶段；回退写明原因与影响。  
- 每阶段转换/过门/发布/复盘必须更新开发计划（阶段/状态/产出/证据/下一步）；**未更新开发计划，不得声称阶段完成**。  
- 开发计划与代码/文档不一致 → 以代码与本轮验证为准，先修开发计划。  
- 输入缺失（PRD/原型/AC/接口/环境）→ 一句话说明缺口，由用户提供/选择已有资料/本包模板补；不强制引用其它包。  
- 阶段门检查：`gate: dev-plan`（阶段表/门/证据/下一步完整；L2+ 缺则不过）。

## 0.1 新输入 / 变更吸收（intake）

> 用户随时可能发新文档/聊天变更/确认项；新文档不等于新真值，先登记分类，再影响分析，最后局部更新。  
> 流程：`workflows/intake.yaml`；方法：`技能/change-intake/SKILL.md`；模板：`模板/变更记录模板.md`、`模板/待决项模板.md`、`模板/决策记录模板.md`、`模板/变更吸收报告模板.md`。

- 文件 → `资料/原始素材/_收件箱/`；处理后移 `资料/原始素材/{yyyyMMdd}-{来源}/`，登记 `文档索引`。
- 聊天 → `00-项目治理/变更记录.md`（CR）或 `00-项目治理/待决项.md`（OPEN）；确认项写 `DEC` 并关 OPEN。
- 分类：PRD 更新/迭代方案/未决项确认/设计原型/测试发布/原始资料/新需求/变更。
- 关联：`R-xx`/`AC-xx`/`OPEN-xx`/`CR-xx`/`T-xx`；找不到标 `GAP`。
- 影响矩阵：需求/AC、原型、架构/ADR、DB、API、前端、测试、任务、发布、回滚；每项写“受影响/不受影响 + 依据”。
- 实质变更 → `confirm_change`；只影响设计 → `confirm_spec`；影响需求基线 → `confirm_requirements`；影响任务/排期 → `confirm_backlog`。
- 局部更新：只改受影响章节；保留 ID；追加修订；旧结论标“已替代”；更新需求台账/迭代计划/任务/测试/发布/开发计划/文档索引/activeContext。
- 输出【变更吸收报告】；需要实施 → `change`/`iterate`；只确认 → 关闭 CR/OPEN。

## 1. 常规变更护栏

```text
route=workflow:change | step=… | next_action=ASK|RESTATE|IMPLEMENT|DONE
```

- 探查前先读 `项目档案.md` §2（代码地图）；L2+ 先读 `{文档事实源目录}/开发计划.md`（旧项目可 `00-项目治理/开发计划.md`；阶段/下一步/缺口）；命中即免重复探查；新发现收尾回写（档案 §5）。  
- 变更分级见 `AGENTS.md` §0.1；L0 微改不强制方案/清单/评审文档，L2+ 走完整链路。  
- 目标/范围/验收按 `AGENTS.md` §0.1；架构级/新子系统先方案（`模板/方案模板.md`；design 步 `confirm_spec`）批准再改；大改/高风险走 review 步（§4.4）。  
- 多文件/新功能先拆任务清单（`模板/任务清单模板.md`；技能 `技能/task-breakdown/SKILL.md`），确认后实施。  
- 有 QA 交接或含部署 → deliver 步产提测单/发布说明（§4.5/§4.7）；含部署 → 转 `release` 工作流。  
- 动手前说明拟改文件；有产品方案/缺陷预期时用验收点自检勾完。  
- 无文件变更 → 跳过 `verify` 门禁与 `confirm_commit`。

## 2. 提交与推送

`hitl: confirm_commit`（条件满足或未写条件）时必须输出：

```text
【拟提交】
- 文件：{清单}
- .gitignore 现状：{一句}
请确认后执行。
```

未确认不得提交/推送。密钥与凭据不得纳入。  
提交信息与粒度：缺陷 `Bug #{id}：{简述}`（合并组一次提交并列出组内全部编号；独立缺陷单独提交）；迭代 `迭代 {版本/主题}：{简述}`；常规变更用简述。一次提交一类改动。  
**文档同提交**：任务清单、提测单/发布说明、需求/方案、文档索引、activeContext 等本轮产物应纳入同一提交或紧随的独立文档提交；不得留一批未提交文档在根目录。

## 3. 护栏（准确度）

### 3.1 证据

完成/通过类结论须附**本任务内**验证命令与结果；「应该通过 / 之前跑过 / 看起来正常」不构成证据；部分验证须显式写明未覆盖路径为「未验证」。  
证据落点：任务清单状态记录、提测单 §3、发布记录 §8、测试台账（测试包）；聊天里的口头结论不算唯一证据。

### 3.2 红绿与测试诚信（缺陷/修复）

修前留红证；**禁修复后回退补红证**；无根因不修。禁先实现后补测冒充验收；禁改断言/跳过测试/禁用告警凑绿（豁免须用户批准）。无效换路径与回根因见 `AGENTS.md` §0.3-7。

### 3.3 门禁

`gate: project-gates`：按档案「质量门禁命令」取**最小充分集**——定向：单项完成即跑；全量：批次收口一次；仅文档变更不跑代码门禁。  
负面验证（写接口/关键流程）：鉴权/越权、参数边界、终态重复、幂等并发、不存在对象、错误码语义。  
门禁输出只取摘要（通过/失败数、新增失败清单）进对话，原始日志落盘；存量失败建基线，只对账新增差异。  
核心模块且装配 mutation-gate（`能力/00-能力注册表.md`）时可作测试有效性加强信号；不替代门禁结论。  
门禁失败 → 最小修复，不夹带无关重构。  
**安全/供应链**：装配 `security-scan`/`sbom` 时，评审/发布前跑最小集（密钥、依赖漏洞、许可证、SAST）；未装配=人工清单，不阻塞但记录降级。

### 3.4 安全与文档

文档与实现同变更；写入前以 `项目档案.md` 核验真实路径；接口与行为以代码或本轮实测为准。  
安全底线：外部输入校验；防注入/越权；接口鉴权按接口自校；外部调用超时/错误处理；错误不回传敏感信息；密钥零入库；个人信息最小化/脱敏。  
文档只写现行有效（AGENTS §0.9）；旧版移 `_归档/`（旧项目可用 `历史/`），不堆“最终版/最终版2”。

### 3.5 子代理

需要隔上下文或改动面大时可派；单点小改不硬拆。默认串行；连续失败停止上报（不无变化重试）。

- 提示词：目标、允许路径、验收、禁 commit/push/改平台/超范围。  
- 返回须含：改了哪些文件、验证结果、未决项；（缺陷轨）可直填备注各节的事实素材（见 `缺陷修复协作.md` §4）。  
- 编排核验差异/命令后再结论；审查只报正确性/需求覆盖/安全/性能缺口，不追风格偏好。提交/回写仅菜单确认后由编排做。  
- 高风险/大改/破坏性变更：核验者≠实施者（按 `agents/reviewer-agent.yaml` 派独立核验；核验不替代门禁）。

## 4. 阶段衔接（按变更分级取用）

> 条件步以 `../workflows/*.yaml` 为准；技能对应 `技能/01～08`（步注已挂，先读再执行）；外部工具/能力见 `能力/00-能力注册表.md`（已安装即启用；未安装=降级，不阻塞）。

### 4.1 需求基线（requirements 步）

- 触发：新功能/范围变更/验收不明；L0/L1 可用轻量需求卡，L2+ 落 `01-需求基线/`（`模板/需求基线模板.md`）。  
- 内容：背景/目标/用户故事/AC/NFR/明确不做/假设与依赖/签收。  
- 门：`confirm_requirements`（需求基线或范围实质变更）；用户确认后冻结，变更走 §6。  
- 产出：需求基线路径写入方案/任务清单/项目档案；未签收不得进入设计/排期（用户豁免须记录）。

### 4.2 方案与设计（design 步）

- 触发：架构级/新子系统/破坏性变更/高风险，或点名「出方案/方案评审」；小改直进 implement。  
- 产出：方案（`模板/方案模板.md`）——范围/接口/兼容与回滚/验收/未决项/NFR/安全/观测/测试策略；架构决策另落 `ADR模板.md`。  
- 技能：`技能/solution-design/SKILL.md`，按变更面加载 `02A 技术选型`/`02B 数据库设计`/`02C API设计`/`02D 前端设计`/`02E 安全威胁建模`/`02F 性能与容量`；不涉及不加载。  
- 门：`confirm_spec`——出示方案要点，批准后才实施；「只出方案」→ 本步后收尾。  
- 装配 design-diagram 时可产架构图；不可用纯文本。

### 4.3 任务清单（plan 步）

- 触发：多文件/新功能/迭代，或点名「只出任务清单」；L0 单文件小改可跳过。  
- 方法：`技能/task-breakdown/SKILL.md`；模板 `模板/任务清单模板.md`；落 `03-计划与状态/任务清单-{版本或主题}.md`。  
- 门：`confirm_backlog`（清单/节奏变更）；展示任务数/RP 覆盖/依赖/风险/节奏三选。  
- 要求：每任务有 AC/验证/精确文件/DoD；每个 RP 有覆盖；垂直切片；检查点；变更记录；未完成任务清单禁止覆盖。

### 4.4 评审（review 步）

- 触发：L2+ 多文件/新功能、大改/高风险/破坏性变更或点名「代码评审」；L0 单文件可跳过；范围纪律同 §3.5。  
- 执行：本机可用 `code-review` 时按其评审全量 diff；不可用派 `reviewer-agent` 独立核验。  
- 补充：`security-scan` 可用时跑最小安全集；变更规模过大先拆。  
- 产出：通过/需修 + 缺口清单（文件:行/问题/证据/严重度/修法）；需修回 implement，同回合重验≤1。

### 4.5 提测（deliver 步）

- 触发：有 QA 交接或含部署/发版；无 QA 且无部署可跳过。  
- 产出：提测单（`模板/提测单模板.md`）——版本/构建、改动点/影响面、自测证据、已知问题、回归指引、QA 接收；发布说明+回滚预案（`模板/发布说明模板.md`）。  
- 落盘：`05-发布与交付/`；提测单单点滚动，发布说明一版一档。  
- 纪律：自测证据不足不交 QA；已知问题不瞒报；若同项目有测试包，提测单可作为其计划的可选输入（不强制）。

### 4.6 验收 / UAT（release.acceptance 步）

- 触发：有业务验收/产品签收要求。  
- 可选输入：已有 UAT/验收资料（任意路径/来源）→ 直接引用/对照，不重复验收；没有 → 本步产 UAT；不要求安装其它包。  
- 产出：UAT/验收记录（`模板/UAT验收模板.md`）落 `04-测试与验收/`。  
- 门：`confirm_acceptance`；结论=通过/有条件/不通过；未签收不得进入工程部署审批（用户豁免须记录）。  
- 依据：需求基线/PRD AC + 测试报告 + 提测单；失败/遗留不瞒报。

### 4.7 发布 / 上线（release 工作流）

- 触发：发布/上线/部署/发版；回滚单独入口。  
- 前置：提测单/测试报告/UAT/上线检查单/回滚预案齐；`gate: release-readiness`。  
- 门：`confirm_deploy`（工程部署 go/no-go）；例外须写明风险/补偿/批准人。若项目已有业务发布决策（其它流程/用户确认）且 UAT 已过，本门只确认工程就绪，不重复业务决策；没有则本门覆盖业务+工程范围。  
- 执行：按项目档案发布方式；失败即停；发布后先冒烟再回归；触发回滚条件就回滚（`confirm_rollback`）。  
- 产出：上线检查单、发布记录、发布后验证；落 `05-发布与交付/`；更新文档索引/activeContext；公告/客服/业务指标复盘若由其它角色负责，可引用本记录（不强制）。

### 4.8 发布后 / 复盘（postrelease / retro）

- 发布后按 `技能/acceptance-and-launch/SKILL.md` 观察日志/指标/告警；观察期结束出结论（成功/带风险成功/回滚）。  
- 事故/回滚/重大发布/重复缺陷 → `retro` 工作流（`技能/retrospective-and-improvement/SKILL.md`；模板 `复盘模板.md`），落 `06-复盘与改进/`。  
- 行动项必须有负责人/截止/验收；下次复盘先对账上次行动项。

## 5. 文档落位与归档（文档事实源目录）

> 一切入库文档（需求/方案/清单/提测/发布/UAT/复盘/评审附件等）落点=档案 §1「文档事实源目录」；**分类优先从既有**，无既有分类用下表标准。  
> 目标：项目根只留代码、构建、README、项目档案、activeContext、工作流包、文档根、测试根；**禁止**把方案/清单/报告/截图/临时文件堆根。

**标准结构（无既有分类时）**：

```text
{文档事实源目录}/                 # 新项目建议直接命名 开发/
├─ 开发计划.md        开发轨总控（当前版本/迭代；人类先看这个）
├─ 文档索引.md        当前版本导航 + 归档索引
├─ 00-项目治理/      变更记录/待决项/决策记录、项目章程、风险登记（按需）
├─ 01-需求基线/      需求台账、PRD/需求规格、用户故事、验收标准、需求变更
├─ 02-设计基线/      技术方案、接口/DB 设计、ADR、安全/隐私评审
├─ 03-计划与状态/    任务清单、迭代计划、状态报告、依赖/风险
├─ 04-测试与验收/    UAT/验收记录、发布后验证（测试包计划/报告在 测试/）
├─ 05-发布与交付/    提测单、发布说明、上线检查单、发布记录、回滚预案
├─ 06-复盘与改进/    复盘、事故报告、改进项
├─ 资料/
│  ├─ 项目文档/     外部 PRD/需求/方案/设计稿/合规资料
│  ├─ 原始素材/     外部原件（docx/pdf/图）；`_收件箱/` 待吸收，处理后按批次子目录
│  └─ 资料索引.md   来源/日期/版本/关联需求/状态
└─ _归档/            已关闭版本/迭代快照（{yyyyMMdd}-{版本}/）
```

> 兼容：旧项目保留 `docs/00-项目治理/开发计划.md` 与 `历史/` 也可；以 `项目档案.md` §9 的实际路径为准，不强行迁移。

**workflow 产出 → 落点**：

| 产出 | 落点 | 命名 |
| --- | --- | --- |
| 项目治理 | `开发计划.md`（根）；其余 `00-项目治理/` | 开发计划（L2+ 必建）、项目章程、风险登记、变更记录（按需） |

1. 项目已有分类 → 档案 §9 记「文档分类」映射（类别→实际目录），**按映射落位、不强行搬迁**（整理仅用户点名或接入时一次性建议）。  
2. 文件名含版本/日期；发布说明一版一档；任务清单确认后冻结，旧版移 `_归档/`。  
3. 旧版/过期文档移 `_归档/{yyyyMMdd}-{版本}/`（旧项目可用 `历史/`）；测试产物移 `测试/_归档/{版本或日期}/`；**禁**覆盖历史发布说明。  
3.1 **计划不移动**：`开发计划.md` 当前文件保持在根；关闭时复制快照到 `_归档/{yyyyMMdd}-{版本}/开发计划.md`，当前计划重置/新建；稳定技术真值留 `项目档案.md`/ADR。

6. 接入时一次性整理：根目录/文档根平铺 → 按标准分类归位；旧结构（如 `项目规范/`）并入档案 §7 后删除；无法判断归属 → 先问用户，不擅自删。

## 6. 变更控制（需求/方案/清单/发布）

- **基线**：需求基线、方案、任务清单、发布说明一经确认即冻结；后续变更写“变更记录”（日期/变更/原因/影响/批准）。  
- **需求变更**：影响 AC/范围/排期 → 回 `requirements`/`design` 重评；不得在实施中静默扩范围。  
- **任务清单变更**：新增/删除/拆分/调序 → 更新清单并记 §6 变更记录；**禁覆盖未完成任务清单**；不同工作先问用户。  
- **发布变更**：已批准发布的内容/窗口/回滚方案变更 → 重新 `confirm_deploy`；不得先斩后奏。  
- **文档变更**：正式文档只写现行有效；旧版归档；同名文件不堆“最终版”。  
- 变更控制记录落 `{文档事实源目录}/00-项目治理/变更记录.md`（按需）或任务清单/发布说明的变更记录节。
