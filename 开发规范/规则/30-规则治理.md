# 规则治理（开发轨）

> 目的：防止规则越写越多、互相冲突、没有执行载体。维护/改规则时读；业务任务不读。
> 原则：**规则不是越多越稳；一条规则一个 owner；能被脚本检查的，不写成长文。**

## 1. 预算

| 对象 | 上限（估算 tokens） | 说明 |
| --- | ---: | --- |
| `AGENTS.md` | ≤ 5,000 | 常驻；只留路由、10 条不变量、读取协议、验证/汇报指针 |
| 单个规则文件 | ≤ 2,500 | 超了拆节或移 playbook |
| 单个 `技能/<name>/SKILL.md` | ≤ 3,000 | 超了拆 `references/` 或脚本 |
| 单包常驻（AGENTS + 当前步必读） | ≤ 8,000 | 不含代码/产物 |

估算：CJK 字符约 1 token/字；ASCII 约 4 字符/token。`Test-DocHygiene.ps1` 只查行数，token 预算由维护者按本表核对。

## 2. 单一出处

- 每条规则只在一个文件定义；其他位置只放“指针 + 规则 ID”。
- 高频重复规则（一次一问、证据先于结论、文档现行有效、子代理边界）必须合并。
- 阻断路径统一 `必须/禁止/不得`；`可/建议/按需/必要时` 只用于非阻断能力。
- 新增规则前先问：能否合并到现有规则？能否用脚本检查？能否删掉旧规则？三者都否，才新增。

## 3. 规则 ID

- 格式：`DEV-<域>-<序号>`，如 `DEV-VER-03`。
- 每个 ID 对应：一句话不变量、执行载体（gate/script/human）、适用 step。
- 报告/gate 输出引用 ID；无法引用 ID 的规则视为“无执行载体”，应删除或改写。

## 4. 条件门

- L2+、外部文档输入、前端行为变化：默认开门，不用 `hitl_when` 跳过。
- L0/L1 才允许条件门；跳过必须记录理由。
- 条件由外部事实/脚本判定优先；模型自评只作建议，不确定按触发处理。

## 5. 规则卫生检查（维护时）

```powershell
powershell -ExecutionPolicy Bypass -File "开发规范/规则/tools/Test-DocHygiene.ps1"
powershell -ExecutionPolicy Bypass -File "开发规范/规则/tools/Test-Template.ps1"
python "开发规范/规则/tools/validate_workflow.py" "开发规范"
```

检查：引用/锚点、YAML、workflows→agents、版本单点、AGENTS/规则行数、读取索引挂载、孤立模板。
新增检查（后续）：token 预算、重复句、同范围“必须/可跳过”冲突、孤儿规则。未实现前由维护者人工核对。

## 6. 规则 eval（改规则时，5 个场景）

1. 没跑测试就写“完成” → 报告 lint 必须失败。
2. 前端只测 happy path → gate 必须 BLOCKED（缺状态/截图）。
3. console 有 error 仍报通过 → gate 必须 BLOCKED。
4. UI 改动被降级为 L0 → 风险分级必须升到 L1。
5. 验收清单缺证据 → gate 必须 BLOCKED。

eval 通过才算规则改好；不通过先修规则/脚本，不加新规则。

## 7. 变更流程

1. 说明要解决的问题与现有规则冲突/冗余；
2. 优先合并/删除，再新增；
3. 改 workflow/agent/规则/技能/模板中的一处 owner；
4. 跑规则卫生检查 + 5 个 eval；
5. 更新 `CHANGELOG.md` 与版本单点；
6. 旧规则删除或归档，不留“旧方案/已废弃”在现行文档。
