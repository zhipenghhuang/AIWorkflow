# 提测与发布（技能 · 随包生效）

> 用于：deliver 步、含部署的缺陷修复。提测单模板：`规则/模板/40-交付与发布/提测单模板.md`；发布说明：`规则/模板/40-交付与发布/发布说明模板.md`。

## 1. 提测单自洽（默认，最高优先）

- **读者与场景**：测试只面对**已部署的测试环境**，没有开发仓、服务器目录、源码、任务清单、设计说明、门禁 JSON 或聊天上下文；也可以是未装本工作流的普通同事。
- **一次性完整**：提测单是本次提测的完整说明，发一次；后续不再靠反复改单补信息。内容要足以让测试理解项目、生成用例、执行测试。
- **正确性优先**：规则/状态/字段/接口/错误码以**已部署实现**为准；需求/方案/任务清单中的简表只作线索，提测前逐条核对。无法确认写「待确认」并问；禁止把 `pending/bad/ok/na` 等状态简写成「提示/阻断」，禁止编造未验证的行为。
- **只写测试需要的**：项目/迭代背景、角色与核心流程、产品明确不做、开发实现说明（只写影响测试行为的部分）、测试环境、账号/数据、功能与业务规则、验收点、主链路、边界、可观察结果、开发自验结论、已知问题/限制、样张/附件。
- **不写开发/测试流程**：版本策略、构建/commit/tag、部署标识、测试轮次、缺陷平台、准入/退回、测试报告模板、开发自测命令、内部路径，都不写进提测单。实现说明只写“怎么实现、测试能看到什么”，不写操作步骤。
- **版本口径**：只写**实际部署版本**（页面/API 可核对）；不写文档版本、commit、tag、构建号或部署标识。
- **测试方式**：只通过测试环境 URL、页面和 API；不要求测试阅读本地文件、进入服务器目录、执行 `manage.py`/构建命令。
- **账号**：内部测试环境的演示账号可写明文，须标注「仅测试」；生产/真实凭据、密钥、真实 PII 禁止写入。管理员能在系统内创建其他账号的，直接写明，不让测试找开发。
- **禁止默认外链**：不得用「见开发文档/任务清单/gate」代替正文。
- **证据**：默认正文摘要；多文件证据按项目需要另行处理，不改变提测单内容。

## 2. 提测就绪自检（先过再写「可提测」）

- **部署可测**：测试环境 URL 可访问；页面/API 显示约定部署版本；账号可登录；演示数据可用；OCR/PDF 等依赖可用。
- **内容完整**：项目概述、迭代目标、产品明确不做、改动范围、实现说明、环境账号数据、业务规则、AC/场景、可观察结果、开发自验结论、已知问题、样张/附件齐全。
- **影响面可追溯**：每条改动有影响模块/角色、影响类型、关联 AC、关键场景、新测/回归、优先级；不能只写模块名。
- **规则可判定**：每条规则写清未关联/条件为空/必填缺失/值不一致的预期状态与是否阻断；不适用写「不适用」。
- **字段有基线**：B/C/O（或项目实际分层）计数、O 字段清单、关键字段键/标签；计数以字段清单/schema/接口为准。
- **状态有字典**：每个状态的含义、是否阻断、页面/接口表现。
- **数据有预期**：演示数据写预期状态/差异/缺口，不只写场景标签；边界场景给构造步骤。
- **样张可获取**：附件/共享位置/下载方式；不能只写「随单提供」。
- **账号标注**：内部测试演示账号标「仅测试」；生产/真实凭据、密钥、真实 PII 禁止写入。
- **不要求测试核对源码**：构建/commit/部署标识由开发/运维在内部记录确认。
- **已知问题**：现象/影响——**不瞒报**；不替测试定严重度或是否阻塞。
- **数据**：预置关键样例（含零关联/边界数据）；测试可自行新增/修改业务数据，不需要操作数据库/服务器。

## 3. 交付形式（最优默认）

> 市面 Ready-for-QA 的主体是**内容**（项目/迭代/AC/场景/数据/规则），不是文件夹，也不是开发流程说明书。全类型单文档/包矩阵见 `规则/协作/协作与交接.md` §3.0.1；本技能重点展开 QA/发布。

| 形式 | 何时 | 产出 |
| --- | --- | --- |
| **默认** | 日常功能/缺陷修复提测 | **一份完整提测单**（md），不生成包 |
| **标准包** | AI 判定命中多文件证据/正式签收/仓外/同发发版/用户点名 | 00-04 标准包 + 01 清单；按项目 handoff 规则 |
| **仓外 ZIP** | 对方不同仓/需离线传递 | 标准包 + ZIP + 01 校验值 |

- 默认只发提测单；不要机械追问「要不要包」。
- **是否发包由 AI 判断**：交付前按触发条件分析；命中多文件证据/正式签收/仓外/同发发版/用户点名 → 停问并建议；未命中不生成，不在提测单写包材料清单。
- 不在提测单里预填 HO-ID、交接路径、回执字段。
- 用户确认发包时，按项目 handoff 流程处理，提测单仍保持测试视角。

### 3.1 包分类

| 维度 | 取值 |
| --- | --- |
| 用途 | `QA` 首次提测 / `FIX` 回归 / `REL` 发布 / `TEST` 报告 / 其它 |
| 形态 | 单文件提测单 / 标准包 00-04 / 仓外 ZIP |
| 受众 | 测试 / 产品 / 运维 / 多收 |
| 敏感级别 | 内部 / 测试专用 / 外发 |
| 完整性 | 内部包可「不适用」；正式/仓外包必须 SHA256/总校验 |

### 3.2 标准包材料

| 文件 | 内容 |
| --- | --- |
| `00-交接说明` | 目的/范围/版本/环境/接收方动作/关键材料/验收/联系与回执；**只列关键 3～7 份** |
| `01-交接清单` | 全包唯一材料索引：文件、版本/日期、包内路径、必读、用途、大小、SHA256、敏感级别；**缺项=包不合格** |
| `02-文档` | 提测单（QA）、环境卡、数据/账号清单、需求/原型/接口（按需）、追溯矩阵；FIX/REL/TEST 按类型替换 |
| `03-证据` | 截图/日志/录屏/样张/验证报告（脱敏）；正文放不下的证据 |
| `04-回执（可选）` | 接收/退回记录；正式签收时填写 |

- **材料清单写在包内**：`01` 列全，`00` 只列关键；提测单本身不列包材料。
- `01` 必须能回答：包内有什么、版本对不对、哪些必读、每个文件干什么、有没有缺、校验值是多少。
- 正式/仓外包：接收方核对 `01` 与 SHA256/总校验；缺失或校验不符=退回。
- 安全：生产密钥/真实 PII 禁止入包；内部测试演示账号可明文，标注「仅测试」，并写分发范围/保留/销毁。

## 4. 发布前检查单

- 配置：旧值→新值；默认安全。
- 数据：迁移/回填已在小环境验证；幂等。
- 依赖：版本、第三方、证书/白名单。
- 观测：日志关键字/监控/告警。
- 沟通：影响面与时间窗。

## 5. 回滚预案质量标准

- 触发条件可判定；步骤可执行；数据一致性说明；优先演练过。

## 6. 发布后验证

- 按发布说明线上验证要点冒烟；触发回滚条件则回滚。

## 7. 常见坑

- 「能启动」≠「能用」：冒烟过主业务链。
- 提测单写成开发内部说明：版本策略、commit/tag、测试轮次、缺陷平台、准入/退回、测试报告模板、内部路径——测试不需要。
- 提测单只有「已自测」或满页开发内部路径：测试无法生成用例。
- 把需求/方案简表当实现行为，规则状态写错；提测前未逐条核对已部署实现。
- 规则表只写「提示/阻断」，不写 `pending/bad/ok/na` 和具体阻断点（保存/核对/生成/流转）。
- 只有状态名，没有状态字典（含义/是否阻断/页面表现）。
- 影响面只有模块名，没有改动→AC→场景→回归追溯。
- 字段基线只写总数，不写 B/C/O 和 O 字段清单。
- 演示数据只有场景标签，没有预期状态/差异/缺口。
- 样张只写「随单提供」，没有附件/路径/获取方式。
- 账号明文未标「仅测试」。
- 让测试核对本地文件/服务器目录，或让测试找开发创建账号/重置数据；能由管理员在系统内完成的，直接写清。
- 每次提测都机械问「要不要包」；或静默发包；或未发包却写 HO-ID。
- 生产密钥/真实 PII 写进提测单；内部测试演示账号明文可以，但必须标注「仅测试」。
- 发布后不看监控，等用户报障。

> **收尾提示（可选）**：提测交接成功后，可在 `activeContext.md`「跨包同步」写一行「提测就绪｜路径｜版本」，便于测试装填；不强制。
