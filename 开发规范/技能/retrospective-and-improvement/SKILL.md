# 复盘与改进（技能 · 随包生效）

> 用于：`retro` 工作流、`release` 的事故后复盘、迭代收尾。  
> 产出：`06-复盘与改进/复盘-{版本或事件}-{yyyyMMdd}.md`，模板见 `规则/模板/60-复盘与改进/复盘模板.md`。  
> 原则：**对事不对人；事实先于判断；改进项必须有着落。**

## 1. 何时做

- 每个迭代/版本收尾（轻量复盘，3～5 条）。
- 发布回滚、线上事故、重大缺陷、重复缺陷。
- 用户点名“复盘 / 事故复盘 / 迭代复盘”。

小迭代可只写“做得好/待改进/行动项”三节；事故/重大发布按模板全量。

## 2. 先收事实

- 时间线：发现 → 响应 → 止损 → 恢复 → 关闭。  
- 影响：用户/业务/数据/资损/合规；持续时长。  
- 证据：日志、监控、告警、发布记录、缺陷单、沟通记录。  
- 指标：lead time、cycle time、change failure rate、escaped defects、回滚次数、平均恢复时间。  
- 不采信“应该/大概”；无法确认的写“未知”。

## 3. 分析

- **直接原因**：什么触发了问题。  
- **根本原因**：用 5 Whys / 因果链追到可改变的系统性原因；不要停在“人为疏忽”。  
- **贡献因素**：流程、工具、测试、评审、监控、文档、排期、沟通。  
- **做得好**：哪些机制起了作用，值得保留。  
- **做不好**：哪些环节失效，为什么没拦住。

## 4. 行动项

- 每条行动项必须：具体动作 + 负责人 + 截止日期 + 验收标准 + 跟踪位置。  
- 优先级：先修复“会再次造成同类事故”的系统性缺口；不要只写“加强意识”。  
- 能落到规则/技能/模板/门禁的，直接改对应文件；不能落地的，建跟踪项。  
- 行动项进任务清单或 `{文档事实源目录}/06-复盘与改进/改进项.md`；下次复盘先对账上次行动项。

## 5. 输出骨架

```text
【复盘】{版本/事件} | {日期} | 结论：{一句话}

一、事实与时间线：{…}
二、影响：{用户/业务/数据/时长}
三、根因：{直接原因 + 根本原因 + 贡献因素}
四、做得好：{…}
五、待改进：{…}
六、行动项：
- [ ] {动作} | 负责人：{…} | 截止：{…} | 验收：{…} | 跟踪：{…}
七、指标：{lead time / cycle time / CFR / escaped defects / MTTR}
八、关联：{发布记录/缺陷单/文档}
```

## 6. 常见坑

- 变成追责会：没人说真话，根因查不出。  
- 只写“加强测试/加强评审”：没有具体动作和验收。  
- 行动项没有负责人/日期：下次复盘还在。  
- 复盘文档散落聊天/根目录：必须落 `06-复盘与改进/` 并进文档索引。  
- 事故后只修代码，不改流程/门禁/监控。
