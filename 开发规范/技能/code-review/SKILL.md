# 代码评审（技能 · 随包生效）

> 用于：review 步（大改/高风险/点名）。范围纪律以 `规则/工作流.md` §4.4 为准；本技能=怎么审到位。  
> **工程质量 rubric**：评审时同时使用 `技能/engineering-quality/SKILL.md` §5（12 项评分卡）；本技能只写评审方法与范围纪律。

## 1. 六轴顺序（先致命后打磨）

1. **正确性**：逻辑与需求一致？边界、空值、类型、精度、时区、并发、事务正确？
2. **需求覆盖**：验收点都有对应实现？有无范围外改动（防夹带）？
3. **安全**：输入校验、鉴权/越权、注入、敏感信息（日志/回显）、密钥硬编码。
4. **性能与资源**：N+1、循环内 IO、无界集合、连接/句柄泄漏、大事务。
5. **可读与一致性**：命名、与既有模式一致、注释只写「为什么」；风格类只报项目规则内的，不挑偏好。
6. **体验三维**：UX（任务/文案减法/状态）、DX（边界/可测/可调试/命令）、AX（入口/单一出处/可验证）是否至少不退化？无法同向是否有取舍与确认？开发阶段是否残留旧数据兼容分支？

## 2. 全量覆盖法（防挑着看）

- 先列**改动文件清单**（含测试、配置、迁移、文案资源），逐文件勾核一遍再写结论。
- 大 diff 先按文件分组过，再回头精读高风险文件（金额/权限/并发/数据迁移）。
- 本机可用 code-review 时按其全量 diff 模式跑（`能力/00-能力注册表.md`）；不可用=人工/子代理按同清单。

## 3. 高风险信号清单（重点盯）

边界与空值｜金额与精度｜时间与时区｜分页与排序｜权限与数据域｜并发与幂等｜事务边界与回滚｜异常吞噬（空 catch）｜日志泄露与噪音｜配置默认值｜迁移脚本幂等性｜开发阶段旧数据兼容分支/双写｜跨层判定不一致（summary/preflight/status 各一套）｜第二次写/空缓存+既有行｜测试预期与方案相反。

## 4. 输出格式

- 需修项：`位置（文件:行）｜问题｜证据｜严重度（阻断/重要/建议）｜修法建议`。
- 通过/需修结论 + 缺口清单；不重写代码（建议级，修复由实施完成）。
- 只报影响正确性/需求覆盖/安全/性能的问题；不为假想场景要求防御（防过度设计）。
- **评审记录**（同时写 `.gate/review.md`）：`reviewer` / `implementer` / `verdict=通过|需修` / 评审范围（diff/提交，必须覆盖本轮门禁 diff）/ `review_required` 与免审理由（如适用）/ AC 覆盖（已覆盖/未覆盖/不适用+依据）/ 缺口清单 / 证据路径。L2+ 缺记录、reviewer=implementer、或评审范围小于门禁 diff → 完成门 BLOCKED。

## 4.1 评审必要性与简单阶段

- 先判 `review_required`：L2+/L3、高风险/大改/破坏性、权限/资金/迁移/公共 API、点名 → 必审；L0 或确实低风险/单点的 L1 → 可免。
- 免审不是免验证：测试/冒烟/证据/完成门仍按级别执行（定向或全仓以 profile 为准）；计划/任务清单写“免审理由 + 风险接受人”。
- 不得把 L2+ 说成“阶段简单”绕过；若确实简单，先重定级并记录。
- 多波次二选一：每波独立评审+过门，或整迭代只过 S5 全量评审；不得混用。
- S5 已有波次评审时做集成/AC/证据/前序阻断复核+高风险抽样，不逐行重审；S5 是唯一评审时必须全量覆盖。

## 5. 变更规模与安全补充

- **规模**：单次评审理想 ≤~400 行有效 diff；超过先拆或说明理由。  
- **安全**：认证/授权/越权、注入、SSRF、文件上传、反序列化、敏感信息、密钥硬编码、依赖漏洞/许可证。  
- **供应链**：新增依赖看版本/许可证/维护状态；有 SBOM/锁文件则核对。  
- **可观测**：关键路径日志/指标/告警是否齐；错误是否被吞。  
- **迁移**：脚本幂等、回滚/前滚、锁与时长；生产阶段才做老数据兼容，开发阶段按 `技能/engineering-quality/SKILL.md` §1.2 直接重建。  
- **证据**：每条需修项给文件:行、问题、证据、严重度、修法；不采信“已修好”。

### 5.1 AI 生成代码 / 供应链 / 可访问性

- **AI 生成代码**：重点查“看似合理但不存在”的 API/配置/依赖、复制粘贴的过期用法、无依据的异常处理、未使用的抽象；要求作者能解释关键决策，不把“模型写的”当免责。
- **供应链**：新增依赖看来源/版本/许可证/维护状态/锁文件；构建产物可追溯（SBOM/来源证明按项目适用）；不引入同名混淆包。
- **可访问性/国际化**：键盘/焦点/语义/对比度；文案是否可翻译、日期/金额/时区/复数是否正确；不把中文硬编码进通用组件。
- **隐私**：新增日志/埋点/导出是否含 PII；缓存/队列/第三方是否扩大数据暴露面。
- 方法与测试分别见 `技能/ai-application-engineering/SKILL.md`、`技能/threat-modeling/SKILL.md`；本技能只列评审关注点。

### 5.2 跨层一致性审查（L2+/权限/状态/数据基数/多表面必做）

- 按 `技能/cross-layer-consistency/SKILL.md` 对四张矩阵：需求追溯、角色权限、状态表面、数据形状/写路径。
- **单一谓词**：同一业务判定是否只在一个服务端谓词实现？列表/详情/预览/打印/归档/导出是否都复用它？有没有交易级结论冒充单据级结论？
- **权限**：UI 可见动作是否有同权限 API？每个角色是否有允许+拒绝用例？是否只测管理员？
- **状态**：同一状态在列表/预览/打印/归档的标签/水印/可操作项是否一致？
- **数据**：唯一约束/多值对象是否测了第二次写、并发、既有行但缓存空？冲突是否 409/业务码而非 500？
- **测试预期**：是否有测试与方案相反、或测试只抄现网实现？
- **同类路径**：同一模型/谓词/权限/状态的其他入口是否也中招？列出文件:行与判定。

## 6. 与流程衔接

- 需修 → 回 implement；同回合重验 ≤1（`agents/reviewer-agent.yaml` 同规）。
- 评审结论与依据（diff、命令输出）一并交编排；不采信口头「已修好」。

## 7. 常见合理化与反驳

| 合理化 | 现实 |
| --- | --- |
| “测试过了，不用审” | 测试覆盖与断言质量未知；评审看需求覆盖、边界与风险。 |
| “改动很小” | 权限/数据/契约问题往往一行就够；按风险不看行数。 |
| “AI 生成的应该没问题” | 模型会编造 API/配置；必须核对来源与可运行证据。 |
| “主路径/管理员测过了” | 权限、状态、第二次写、空缓存往往才是缺陷；按矩阵补正反用例。 |
| “测试都绿了” | 测试可能只覆盖 happy path，甚至把错误实现固化成预期；先对方案再对代码。 |
| “风格问题不重要” | 只报项目规则内的风格；正确性/安全/可维护性优先。 |
| “先合并再补” | 合并后修复成本更高；阻断项必须修完再合。 |
