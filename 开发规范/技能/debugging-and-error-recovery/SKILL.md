# 调试与故障恢复（技能 · 随包生效）

> 用于：implement / verify 失败、缺陷修复、发布后异常、性能退化、间歇性故障。  
> 定位：**先恢复服务，再定位根因**；本技能=调试方法与证据纪律，不替代 `技能/implementation-and-selftest/SKILL.md` 的实现流程。  
> 红线：未复现不猜修；未验证不称修复；生产故障先止损（回滚/降级/开关），不拿生产环境做试验。

## 1. 何时用 / 不用

**用**：

- 构建、单测、集成、E2E、启动、部署失败，或现象与预期不符。
- 线上错误率、延迟、资源、业务指标异常，或用户报障。
- 间歇/偶发问题（flaky）、环境差异、数据相关异常。
- 修复后需要证明“真的修好且没伤到别处”。

**不用**：

- 纯需求变更/新功能实现（走 `implementation-and-selftest`）。
- 已知口径的产品争议（走澄清/缺陷协作，不靠调试定对错）。

## 2. 五步法（顺序不可跳）

### 2.1 复现（Reproduce）

- 固定四要素：**版本/构建 + 环境/配置 + 数据/账号 + 操作步骤**；缺一项就标“未稳定复现”。
- 记录首错，不只看末错：完整错误文本、堆栈、日志时间窗、trace/request id、截图、网络响应。
- 区分确定性/间歇性：间歇问题记录频率、时间分布、并发/数据规模/网络条件。
- 目标是**最小稳定复现**；做不到时先收集证据并缩小观察面，不进入“猜修”。

### 2.2 定位（Localize）

- 列 **2～3 个候选根因**，每个写“若成立，应观察到什么”；不要只猜一个。
- 二分：`git bisect`、按提交/配置/依赖/数据分批、日志分段、注释/替换半区、逐层（UI→Network→API→DB）。
- 对照：与最近一次正常版本/环境/账号/数据对比，优先看“最近变了什么”（代码、配置、依赖、数据、证书、权限、流量）。
- 先查最常见低成本项：空值/类型、权限、配置缺失、依赖版本、迁移未执行、缓存/时钟、磁盘/连接池。

### 2.3 缩小（Reduce）

- 把复现压到最小输入/最小路径/最少依赖；能脱离 UI 用接口/脚本复现就脱离。
- 一次只改一个变量；每次改动前写“预期变化”，避免多点同时动。
- 确认故障层：表现层（渲染/文案）、契约层（字段/状态码）、业务层（规则）、数据层（脏数据/迁移）、基础设施层（网络/资源）。

### 2.4 修因（Fix the cause）

- 写清根因三句：**触发条件 + 失效机制 + 为什么之前没挡住**。
- 修根因不修表象；禁止“加个 try/catch 先过”“加大超时/重试”“前端隐藏错误”当作修复。
- 最小改动；一次提交只修一个问题；需要连带重构时先记录边界。
- 有数据/迁移影响时先备份/可回滚；生产修复优先开关/灰度。

### 2.5 防回归（Guard）

- 在**最低可行层**补测试：单测 > 集成/契约 > E2E；断言行为，不复刻实现。
- 回归范围=原场景 + 相邻路径 + 同类输入；高风险/连环问题扩大影响面。
- 需要时补监控/告警/日志字段，防同类问题再次静默发生。
- 记录：修复前后证据、命令/退出码、回归结果、剩余风险。

## 3. 失败分类（先分类再动手）

| 类型 | 典型信号 | 首要动作 |
| --- | --- | --- |
| 代码/逻辑 | 稳定复现、断言失败、边界/空值 | 二分定位 + 补测试 |
| 配置/环境 | 仅某环境、启动即错、依赖缺失 | 对照基线/配置差异 |
| 数据 | 特定记录/租户/时间窗、迁移后 | 校验数据/迁移/回滚 |
| 依赖/契约 | 升级后、字段/状态码变化 | 查变更日志/契约 |
| 并发/时序 | 偶发、压测/多用户出现 | 复现频率 + 锁/幂等/超时 |
| 资源/容量 | 延迟/错误随负载上升 | 看池/CPU/IO/GC/慢查询 |
| 安全 | 越权/注入/异常流量 | 止损 + 安全流程，不自行掩盖 |

## 4. 升级与止损

- 同一方案无效 **2 次** → 换假设/换手段；同一问题 **3 轮** 无进展 → 升级（用户/负责人/子代理独立核验）。
- 生产故障：先判断影响面 → 回滚/降级/关开关/限流 → 保留现场证据 → 再根因；不要先改代码再回滚。
- 不可逆/资金/权限/数据问题：立即停下，按 `规则/工作流.md` 与缺陷协作规则走人工确认。
- 不在生产环境做未批准的试验；不复用真实 PII 做调试数据。

## 5. 常见合理化与反驳

| 合理化 | 现实 |
| --- | --- |
| “我本地是好的” | 环境/数据/版本差异正是根因候选；先对齐四要素。 |
| “先加个 try/catch/重试” | 吞异常会把可定位故障变成静默数据错误。 |
| “肯定是缓存” | 缓存只是假设；清缓存前先证明旧值来源与失效路径。 |
| “复现不了，先关掉” | 无复现也要留证据、加观测、标未解决；不得假称修复。 |
| “改完看起来对了” | 没有回归证据=未验证；至少原场景+相邻路径。 |
| “顺手把这块重构了” | 扩大变更面会混淆因果；重构另开提交。 |

## 6. 红旗

- 同时改多处、没有单一变量对照。
- 没有首错/完整堆栈，只截最后一行。
- 用“重启/清缓存/重装”当结论，不解释机制。
- 修复后不回跑原场景，或只跑 happy path。
- 为了让测试变绿而改断言/跳测试/降阈值。
- 生产故障先改代码、后想回滚。

## 7. 输出（故障卡）

```text
现象/影响：{谁在什么场景遇到什么，影响面}
复现：{版本/环境/数据/步骤；确定性或频率}
首错证据：{日志/堆栈/trace/截图路径}
根因：{触发条件 + 机制 + 为什么没挡住}
修复：{文件/提交/开关；最小改动说明}
验证：{命令/退出码/回归范围/结果}
剩余风险：{未覆盖路径/监控缺口/后续动作}
```

## 8. DoD

- 有稳定复现或明确的“未稳定复现+观测方案”。
- 根因能解释现象，不是“改了就好了”。
- 修复最小且可回滚；生产修复有止损路径。
- 原场景 + 相邻路径回归通过，证据可复核。
- 未验证项、剩余风险、后续监控写清。
