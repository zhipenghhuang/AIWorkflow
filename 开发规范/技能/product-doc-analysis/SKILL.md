# 产品文档解析与需求理解（技能 · 随包生效）

> 用于：`change.clarify` / `change.analyze_input` / `change.requirements` / `intake.parse`。  
> 目标：把 PRD、迭代方案、文档、页面原型、截图、接口/技术文档，还原成**可开发、可测试、可追溯**的需求理解包；先理解，后设计。  
> 边界：本技能不写方案、不写代码、不写任务清单；不替用户裁决冲突，不把原型反推成后端规则。

## 1. 输入盘点（先列清单，再读内容）

| 输入 | 必看 | 记录 |
| --- | --- | --- |
| PRD / 需求文档 | 版本、状态、负责人、更新日期、范围、F/R/AC、非目标、待确认、变更记录 | 文档路径 + 章节/页码 |
| 迭代方案 | 本期范围、相对上版增/改/删、依赖、排期、验收 | 与 PRD 的对应关系 |
| 页面原型 / 截图 | 页面清单、导航、区域、组件、字段、状态、交互、文案、权限可见性 | 页面名/画板号/截图名 |
| 接口 / 技术文档 | 接口清单、字段、错误码、鉴权、时序、限制 | 版本 + 接口路径 |
| 会议纪要 / 聊天 / 工单 | 决策、口径、例外、承诺 | 日期 + 说话人角色 |
| 现有代码 / 旧系统 | 实际行为、兼容约束、历史包袱 | 分支/commit/文件:行 |

- 输入缺失 → 列 GAP，不默认；不能读的文件 → 请用户给关键段/截图，禁假装已读。
- 多份文档 → 先定**主读**（通常 PRD/迭代方案），其余为对照；冲突时列双方原文，不静默选一个。
- 大输入（≥3 份或长文档）→ 按 `规则/协作/子代理编排.md` §2 只读扇出，每份返回“来源/目标/范围/F-R-AC/冲突/GAP ≤30 行”，主上下文统一建模。

## 2. 五遍阅读法

### 第一遍：结构与元信息

- 文档类型、版本、状态（草稿/评审/定稿）、作者/owner、更新日期、适用范围。
- 目录与章节：哪些章节定义需求，哪些是背景/方案/附录。
- 变更记录：本版相对上版改了什么；旧版是否仍被引用。
- 产出：来源清单 + 主读判定 + 阅读范围（哪些章节已读/未读）。

### 第二遍：需求模型（十要素）

```yaml
requirement_model:
  goal:            # 一句话目标 + 成功标准
  scope:           # 范围内 + 明确非目标
  roles: []        # 角色 → 能做什么/不能做什么/数据域
  inputs: []       # 输入来源/格式/约束
  outputs: []      # 输出去向/格式/消费方
  states: []       # 状态A --事件--> 状态B；非法跃迁
  rules: []        # 业务规则/校验/阈值/计算口径；每条带 evidence
  exceptions: []   # 失败/空值/重复/并发/超时/降级
  dependencies: [] # 上下游/共享数据/时序/外部系统
  open_questions: [] # 未定义/冲突/待裁决
```

- 每条 `rules/states/exceptions` 必须带 `evidence`（文档章节、页面/画板、接口字段、代码位置）。
- 空字段标“已核对，无此类要素”，不要留空让人误以为没查。
- 需求点编号：沿用原文 `F-xx/R-xx/AC-xx`；原文没有则建 `RP-xx` 并记来源，禁止重编号导致追溯断裂。

### 第三遍：原型与交互（页面原型专项）

- **页面地图**：页面/弹层/抽屉/向导步骤清单；入口、返回、跨页跳转。
- **区域与组件**：头部/筛选/列表/表单/详情/操作区/分页/批量操作；组件类型与复用。
- **字段清单**：字段名、类型、必填、默认值、枚举、单位、精度、来源、校验、只读/禁用条件。
- **状态矩阵**：空态/加载/成功/失败/部分失败/无权限/禁用/超限/离线；每态的文案与可操作项。
- **交互**：点击/悬停/展开/拖拽/批量/快捷键/二次确认/撤销；成功/失败反馈。
- **权限可见性**：角色 × 页面/按钮/字段/数据行；无权限时隐藏还是禁用。
- **文案与一致性**：按钮/提示/错误文案；与 PRD 术语是否一致。
- **响应式与可访问性**：断点/最小宽度/键盘/焦点/对比度/屏幕阅读器（有要求才展开）。
- **交接标记**：`必须保留` / `可优化` / `未提供`；原型≠生产代码，不能据此反推后端规则、接口或数据模型。

### 第四遍：一致性检查（冲突表）

逐项对照，禁止沉默：

| 检查 | 要发现 |
| --- | --- |
| 文档内部 | 同一功能在摘要/正文/附录/FAQ 描述不一致 |
| 跨文档 | PRD vs 迭代方案 vs 接口文档 vs 测试报告 |
| 文档 vs 原型 | 页面/字段/状态/权限/文案不一致 |
| 文档 vs 代码/现网 | 规则、状态机、字段、默认值、错误码不一致 |
| 文档 vs 计划 | 范围、版本、里程碑、依赖冲突 |
| 术语 | 同一概念多个名字；同一名字多个含义 |

冲突记录格式：`{冲突ID}｜{归属P/S}｜{主题}｜A: 原文+位置｜B: 原文+位置｜影响｜建议裁决｜待确认`。  
默认**不裁决**；按 `规则/核心/澄清.md` §1.1 归 **P**（业务冲突）或 **S**（方案自相矛盾）；用户裁决后才写入基线。代码是现状事实，不是需求真值；文档是需求真值，但不等于实现现状。

### 第五遍：可开发性与可测性检查

逐类扫描，命中即进 `open_questions`（每条先标归属 P/D/S，见澄清 §1.1）：

- 模糊形容词：快/稳定/友好/合理/尽量/支持多种/等等——无阈值即不可测 → 多归 **S**（或 **P** 若仅缺业务口径）。
- 数值边界：区间端点含否、取整方向、精度、单位、时区、自然日/滚动窗口。
- 状态与权限：缺转换路径、终态重入、非法跃迁、角色×数据域、越权表现。
- 异常与恢复：失败提示、重试、幂等、重复提交、并发、超时、部分失败、降级、补偿。
- 异步时限：多久不发生判失败；轮询/回调/定时任务时序。
- 数据口径：来源、默认值、历史数据、迁移、删除/归档、审计。
- NFR：性能/容量/可用性/安全/隐私/兼容/可观测，只有定性无指标 → 问数值或显式“不适用+原因”。
- AC：是否“条件+动作+可观测结果”；每条 F 是否至少一条 AC；异常/边界是否有 AC。
- 非目标：是否明确“本次不做”；缺失 → 问，不默认。
- 技术边界：产品文档是否越界写架构/技术栈/DB/API 实现；越界只记录，不在本技能裁决。
- **开发确认标记**：正文/表格出现「由开发确认 / 开发决定 / TBD（开发）/ 技术选型交开发」→ 归 **D**，列入择优清单（推荐+理由+备选），**不回抛产品**；改变可见 AC 则升级 **P**。
- **方案自身问题**：条款互斥、主路径缺失、非法跃迁未定义且无法从原文推断 → 归 **S**，进【待确认单】，**停实施**。

## 3. 证据标注（每条结论都要能回查）

| 标记 | 含义 | 用法 |
| --- | --- | --- |
| `[原文]` | 文档/原型/接口原文 | 附章节/页码/画板/接口字段 |
| `[推断]` | 由多处原文合理推出 | 写推理链，标“待确认” |
| `[假设]` | 无原文，暂按此推进 | 写验证方式、责任人、截止 |
| `[待确认]` | 冲突/缺口/需用户裁决 | 进 open_questions，标归属 P/D/S，一次一问 |
| `[GAP]` | 文档明确没有 | 不猜，列出缺什么、影响谁、归属 |
| `[开发择优]` | 文档交开发确认或纯技术未定 | 归 **D**：写推荐+理由+备选，待用户确认；默认不转发产品 |

- 禁止把 `[推断]` 写成 `[原文]`；禁止用“通常/一般/应该是”替代来源；禁止把 **P/S** 写成 `[开发择优]`。
- 引用抽验：收尾前抽 2～3 条关键结论，打开被引文件核对；不实即改。

## 4. 输出：需求理解包（§0 门面 + 下钻）

> **人类快查**：文件**开头必有**【业务与变更简报】+【本期差量表】（对齐 OpenSpec proposal/delta、Change Brief）。完整十要素等下钻节供实现；确认门主屏只出示 §0 + 待确认单。  
> 模板：`规则/模板/10-规划与需求/需求理解包模板.md`。

- **权威 Delta**：若输入含产品「迭代变更摘要」或产品计划 §3.0 / 变更单差量表 → **引用其 ID 与增改删**，只做校验/补技术影响，禁止另造一套编号；冲突进冲突表。无产品 Delta → 自建并标「待产品确认」。
- 轻量（L0/L1 或单文档）：至少落 **§0 Brief + 迷你 Delta（≤5 行）** + 目标/AC/非目标/GAP/假设/置信度（可写在需求卡）。
- 完整（L2+ 或多文档/原型）：落 `开发/01-需求基线/理解-{主题}-{yyyyMMdd}.md`：

```text
§0 【业务与变更简报】+【本期差量表】+【影响摘要】（必填；见下）
1. 来源清单（文档/原型/接口/代码；版本/日期/状态；产品 Delta 路径若有）
2. 一句话目标与成功标准（可与 §0 合并，不重复长写）
3. 范围与非目标
4. 角色与场景（谁/入口/操作/结果/权限）
5. 需求点清单（RP/F/R/AC；原文编号 + 来源；与 Delta 对账）
6. 流程与状态机（主路径/异常/非法跃迁）
7. 权限矩阵（角色×操作×数据域）
8. 字段与数据口径（来源/类型/必填/默认/校验/精度）
9. 异常、边界、NFR
10. 原型/页面清单（页面/组件/状态/交互/必须保留/可优化/未提供）
11. 冲突表（归属 P/S + A/B 原文+位置+影响+待裁决）
12. GAP / 假设 / 开发择优清单（归属 P/D/S；验证方式/责任人/截止；D 含推荐+理由）
13. 追溯种子（RP/F/R/AC → 方案/任务/测试）
14. 【待确认单】摘要（按澄清 §1.1；可转发产品行单独标出）
15. 确认状态（已确认/待确认 + 日期/人 + 确认范围）
```

### §0 必填结构（门面）

```markdown
## 0. 业务与变更简报（Brief + Delta）

### 业务简报
- 一句话目标 / 成功标准：
- 用户与场景：
- 范围 / 非目标：
- Why（可选一句）：
- 冲突·GAP·开发择优计数（P/D/S）与置信度：

### 本期差量表
| ID | 操作 | 简述 | 业务影响 | 证据 |
| --- | --- | --- | --- | --- |
| {F/R/AC/RP/CR-…} | 增/改/删 | {…} | {…} | {章/页/画板} |

> 首版无上版 → 一行「全部为增」+ 范围指针即可。操作枚举仅用：`增`｜`改`｜`删`。

### 影响摘要（开发裁剪）
- 模块/接口/数据/权限：
- 回归边界：
- 产品 Delta 引用：{路径或「自建·待产品确认」}
```

## 5. 理解回执与确认（强制）

- **确认门主屏**：出示 §0 Brief + 本期差量表 + 待确认单摘要（冲突·GAP·开发择优按 P/D/S 计数）；**禁止**只用 6～8 行复述代替差量表（L0 迷你 Delta 除外）。
- 先给分析/建议；只问 0～1 个高影响问题（总≤3），技术细节不逐条问，按 `规则/核心/澄清.md`（含 §1.1 决策归属）处理。
- **S 或阻塞 P 未关闭** → 出【待确认单】并停止进入 design/implement；**D** → 出示择优建议，向用户确认（低影响可收尾默认），不默认甩产品。
- 用户明确确认后，才把理解包作为需求基线输入；未确认不得进入 `requirements/design/implement`。
- **无 §0 / 无差量表**（且非 L0 迷你）→ 不得称理解已确认，不得进入 iterate 拆单。
- 确认门 `confirm_understanding` 只确认“理解与本期变化是否正确”，不替代后续 `confirm_requirements` 的正式签收；待确认单可与该门同屏展示，但 **S** 未关闭不得当作已理解通过。

## 6. 交接给下游

- `requirements`：以理解包为输入，补技术验收/差距/NFR/签收；不重写已确认的业务需求。
- `design`：方案逐条响应 `RP/F/R/AC` 与 NFR；新增需求先回澄清，不擅自扩展范围。
- `plan`：任务必须能指到 `RP/AC`；无追溯的任务不拆。
- `implement`：按“必须保留/可优化/未提供”实现；原型冲突或缺失先停下说明。
- `review`：核对理解包/基线 → diff/测试的覆盖；缺覆盖列缺口。
- `test`：AC/规则/状态/权限/异常直接作为测试设计输入；GAP 不得当“免测”。

## 7. 常见坑（反模式）

- 只读 PRD 标题/摘要就开写；不读变更记录和非目标。
- 把迭代方案当完整 PRD；不建/不更新需求台账。
- 把原型当后端规则；按截图猜接口、字段、状态机。
- 文档冲突时静默选一个；或直接按代码现状覆盖需求。
- 把“文档没写”当“可以不做/不用测”；不列 GAP。
- 用“行业惯例/竞品也这样”补需求；不标假设。
- 需求点没有编号/来源；下游无法追溯。
- 读完不给复述、不确认，直接进入方案/任务/代码。
- 有完整下钻无 §0 Brief/Delta，或确认门只用口头复述代替差量表。
- 无视产品已有 Delta 另造一套 ID；或产品无 Delta 却不标「自建·待产品确认」。
- 把「由开发确认」当成免确认；或把开发择优整包甩回产品。
- 方案自相矛盾仍开写代码；open_questions 无归属（P/D/S）。

## 8. 参考（方法内化，非逐字复制）

- GitHub Spec Kit `clarify` / `analyze`：歧义分类、跨产物一致性、覆盖缺口、严重度。
- OpenSpec proposal + spec-delta；Speckit Diff；Change Brief / Change Impact Analysis：人类扫读 Why/What + 增改删。
- addyosmani/agent-skills `interview-me`：假设 + 置信度、一次一问、复述确认、95% 停止条件。
- fishzjp/qa-skills `requirement-analysis`：需求模型十要素、证据标注、冲突不改写。
- JohnWayneeee/casely-qa-skill：规格洞（矛盾/不可测措辞/缺失错误路径）。
- IIBA BABOK（需求分析/追溯）、ISO/IEC/IEEE 29119-3（测试依据）、C4/ADR（设计边界）。
