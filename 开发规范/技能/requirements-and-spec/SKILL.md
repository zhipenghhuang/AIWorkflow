# 需求与规格（技能 · 随包生效）

> 用于：clarify 步（需求/验收不明时）、design 步前段。目标：把模糊需求变成**可验收点**，一次问清、不返工。

## 1. 澄清追问环（先读 `规则/核心/澄清.md`）

- **首轮**：一句话理解回执 + 置信度 + 缺口 → **一次只问一个问题**（附 2～3 个候选/推荐答案）→ 等回答 → 更新理解与置信度。
- 问题优先级：目标与用户 → 主链路径 → 边界与非目标 → 验收与数据口径。
- 先分析；只问 0～1 个高影响问题（总≤3），技术细节给建议；能复述出「谁 / 在什么场景 / 做什么 / 系统怎么响应 / 怎么算对 / 明确不做什么」即达标（纪律见 `规则/核心/澄清.md`）。
- 用户明确说「对/是/按这个来」才算确认；“随便/你决定/看着办/沉默”不算；含糊回答换成候选选项继续定。
- 禁答题式盘问；禁一次列多问；禁把设计细节（怎么实现）当需求问题；禁把假设写成结论。
- 输入含 PRD/迭代方案/原型/文档 → 先按 `技能/product-doc-analysis/SKILL.md` 产出带引用的理解包，再澄清；不确定项按 `规则/核心/澄清.md` §1.1 标 P/D/S（产品 / 开发择优 / 方案缺陷），S 未关闭不进设计实施。

## 2. 必问清单（缺一即追问）

| 维度 | 要问出 |
| --- | --- |
| 目标与用户 | 谁用、解决什么问题、成功标准 |
| 主路径 | 入口 → 操作 → 结果的完整故事 |
| 输入与规则 | 关键字段/枚举/阈值/来源；非法与空值怎么算 |
| 状态与权限 | 有哪些状态流转、哪些角色不能用 |
| 数据与口径 | 数字怎么算、时间口径、精度；跨端一致性 |
| 异常与限制 | 失败提示、重复提交、并发、数据量级 |
| 非目标 | 本次明确不做（写进范围排除） |
| 验收 | 每条可验收点=条件+动作+可观测量 |

## 2.1 输入先解析（有文档/原型必做）

- 输入含 PRD、迭代方案、需求文档、页面原型、截图、接口/技术文档 → 先按 `技能/product-doc-analysis/SKILL.md` 产出需求理解包（来源/目标/范围/角色/F-R-AC/状态/权限/字段/异常/NFR/冲突/GAP/置信度）。
- 需求基线每条 AC 必须能指到理解包或原文；无来源标 GAP，不臆造。
- 版本级迭代方案/验收矩阵先分 `DEV-AC / QA-AC / REL-AC`；基线只收 `DEV-AC`，`QA-AC/REL-AC` 转测试/UAT 交接，不写成开发 AC/任务。
- 原型只作 UI/交互依据；后端规则/接口/状态机以 PRD/接口文档/用户裁决为准；冲突列出待裁决。
- 理解包的冲突/GAP 未裁决项必须继承到基线 §7；不得静默消失。

## 3. 可验收点写法

- 好：`已登录管理员在X页点[提交]后，列表出现新记录，状态=待处理`
- 坏：`提交功能正常`（无对象、无观测值）
- 每条附来源（原文/现网/口头确认）；未确认项显式标「**假设**」。

## 4. 输出（并入复述/方案，不另立文档）

- 1～2 句目标复述；验收点清单；明确非目标；未决与假设（供 design 与后续回问）。
- 命中权限/状态/数据基数/唯一约束/多表面时，按 `技能/cross-layer-consistency/SKILL.md` 同步产出四张矩阵（可并入基线/任务清单，不重复造文档）。

### 4.1 覆盖矩阵（强制）

- **需求追溯**：每个 `Then`、每个异常分支、每个「可补充/重新上传/重复/空列表/非法跃迁」都要有 AC；每条 AC 能指回原文。
- **角色权限**：角色 × 能力 × 数据范围 × UI 入口 × API；至少一条允许 + 一条拒绝。
- **状态表面**：状态 × 列表/详情/预览/打印/归档 × 标签/水印/可操作项；同一状态不得互相矛盾。
- **数据形状**：0/1/N + 首次/第二次/重复/并发 + 既有行但缓存空；唯一约束的槽位/分配/冲突处理写清。
- **验收/自测预期**：必须来自方案/AC，不来自现网实现；发现自测与方案相反 → 停下报告，禁止改预期迁就代码。

## 5. 需求基线落盘（L2+）

- 需求稳定后，按 `规则/模板/10-规划与需求/需求基线模板.md` 落 `01-需求基线/`；小改用轻量需求卡（背景/目标/AC/非目标）。
- 用户故事：`作为{角色}，我希望{能力}，以便{价值}`；每个故事至少一条 AC。
- NFR 必过：性能/可用性/安全/隐私/兼容/可观测；不适用写「不适用」。
- 范围必须含「明确不做」；未确认项标「假设」并写验证方式。
- 签收：产品/业务/技术/测试至少相关方确认；未签收不得进入设计/排期（用户豁免须记录）。

## 6. 常见坑

- 「我问过」≠「问清了」：回答含糊（“大概/应该”）→ 换成候选选项继续定。
- 用户改口：以最新为准，旧验收点标作废（不留双真值）。
- 只写功能不写 NFR：上线后性能/权限/兼容问题返工。
- AC 不可观测：无法验收，也无法生成测试。
- 只读 PRD 标题/摘要就写基线；不读变更记录、非目标、冲突/GAP。
- 把原型/截图当后端规则；用“行业惯例”补需求。
- 把「由开发确认」当免确认，或把开发择优甩回产品；方案自相矛盾仍写基线。
