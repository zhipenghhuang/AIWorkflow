# 产品定义与收敛（技能 · 随包生效）

> 用于：`solo.frame`、`solo.plan` 前段；也可在 `change.clarify` 遇到「只有一个想法、没有 PRD」时按需加载。
> 目标：先判断**值不值得做、做多大**，再进入方案；不把一句「我想要 X」直接变成代码。
> 边界：本技能不写技术架构、不写完整 PRD、不做市场调研；技术方案归 `solution-design`，完整 PRD 归产品包或 `requirements-and-spec` 的完整档。

## 1. 适用 / 不适用

**适用**

- 只有一个想法、目标用户/场景/成功标准还没说清。
- 新项目/新产品/新模块，需要先定 MVP 与不做什么。
- 多个需求抢资源，需要快速判断先后。
- 方案卡需要补「产品判断」一节。

**不适用**

- 已确认的 PRD/需求基线，直接走 `product-doc-analysis` + `requirements-and-spec`。
- 纯技术重构、依赖升级、文案错字等无产品决策的小改。
- 用户明确说「不做产品判断，直接按我说的做」——仍给 3 行理解回执与假设，不展开产品盘问。

## 2. 先判断「要不要做」

按顺序回答，答不出就标「未知」，不要编：

| 问题 | 要得到什么 | 不合格信号 |
| --- | --- | --- |
| 谁在什么场景遇到什么问题？ | 具体角色 + 触发场景 + 现状 | 「所有人」「随时」「不方便」 |
| 现在怎么解决？代价多大？ | 现有替代（人工/表格/竞品/不做） | 说不出现有做法 |
| 做了之后什么会变好？ | 一个主成功标准 + 一个护栏 | 「体验更好」「更先进」 |
| 最小可用是什么？ | 1～3 个必须能力 | 一上来就是完整平台 |
| 明确不做什么？ | 非目标 + 理由 | 「以后再说」但没有边界 |

**判断口径**

- **值得做**：问题真实、发生频率/代价可说明、最小版本能独立交付、成功可观察。
- **先验证**：问题真实但方案不确定 → 先做人工/假门/小样本，不写全量功能。
- **不值得做**：问题是假设、没有目标用户、收益无法观察、维护成本明显高于价值。
- **必须现在做**：合规/安全/阻断主链路/明确承诺；按高风险处理。

> 结论不是「做/不做」二选一；可以是「先做哪一小块」「先验证什么」「用什么最小实现」。

## 3. 产品定义卡（一页）

按 `规则/模板/10-规划与需求/产品定义卡模板.md` 填；最少包含：

1. **一句话定义**：给谁、解决什么问题、带来什么结果。
2. **问题与证据**：来源/样本/日期；事实与假设分开。
3. **用户与场景**：主角色、触发条件、现有替代、代价。
4. **价值与成功标准**：一个主指标 + 一个护栏指标；无数据写「待验证 + 验证方式」。
5. **MVP 范围**：Must / Should / Won't；Won't 写理由。
6. **产品行为**：主流程、关键状态、权限、异常/空态（只写行为，不写实现）。
7. **风险与假设**：最大 3 个；每个有验证方式或接受人。
8. **待确认**：影响方向/范围/验收的问题；技术细节不列入。

**写法**

- 每条标 `[事实]` / `[假设]` / `[待验证]`；无来源不写成结论。
- 成功标准用「条件 + 动作 + 可观测结果」，不写「更好用」。
- 一页为目标；超出时保留结论，把细节放附录，不扩成完整 PRD。

## 4. MVP 与优先级

**先砍，再排**

1. 删掉不影响主成功标准的能力。
2. 删掉可以用人工/现成工具替代的能力。
3. 删掉没有明确用户/场景的能力。
4. 剩下的按「阻断主链路 > 高频 > 高代价 > 锦上添花」排序。

**轻量优先级**（多需求时选一个口径，写清理由）

| 方法 | 用法 | 适合 |
| --- | --- | --- |
| Must / Should / Won't | 先保 Must；Won't 即范围排除 | 单版本、小项目 |
| 价值 / 成本 / 风险 | 高价值低成本先做；高风险先验证 | 个人项目、时间有限 |
| RICE | `(触达×影响×信心)/成本`；信心不足先验证 | 多需求、需要排队 |

- 不做优先级的需求不排期；未确认的需求标「待确认」，不承诺版本。
- 不替用户做价值判断；给建议 + 取舍后果，由用户拍板。

## 5. 从定义到方案

产品定义确认后，进入 `solo.plan` 的方案卡，只传递以下内容：

- 范围 / 非目标；
- 主流程、状态、权限、异常；
- 每条 AC（条件 + 动作 + 可观测结果）；
- 成功标准与验证方式；
- 最大风险与假设。

**不要**把产品定义卡复制进方案卡；用链接/摘要，避免两份真值。

## 6. 反合理化

| 常见说法 | 现实 |
| --- | --- |
| 「先做出来，用户自然会用」 | 没有目标用户和成功标准，做完也不知道对不对。 |
| 「竞品有，所以我们也要有」 | 竞品做法不是你的用户需求；先问场景与代价。 |
| 「功能越多越完整」 | 小项目先做最小闭环；多出来的都是维护成本。 |
| 「用户说想要 X」 | 想要 ≠ 需要；追问上次遇到是什么时候、怎么解决的。 |
| 「这个很简单，不用定义」 | 简单实现也需要一句目标 + 一条 AC；否则无法验收。 |
| 「先写代码，边做边想」 | 方向错了返工更贵；至少先给一页方案卡。 |

## 7. 红旗

- 用户/场景/成功标准三者缺任意一个，就开始写方案。
- 把「行业惯例/最佳实践/竞品」当作用户证据。
- MVP 列了 10 条 Must，没有 Won't。
- 成功标准是「更好/更快/更稳」，没有观测方式。
- 产品定义卡写成完整 PRD 或技术方案。
- 用户没确认，就把假设写成结论并进入实施。

## 8. 验证 / 自检 / DoD

- [ ] 一句话定义能说清「谁 / 什么问题 / 什么结果」。
- [ ] 至少一条事实来源；假设有验证方式。
- [ ] MVP 有 Must / Won't；非目标有理由。
- [ ] 成功标准可观察；无数据写「待验证」。
- [ ] 主流程/状态/权限/异常足够支撑 AC。
- [ ] 用户已确认方向与范围（或明确记录「按假设推进」）。
- [ ] 产品定义卡不超过一页；未写成完整 PRD/技术方案。
