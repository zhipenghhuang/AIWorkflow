# 同仓开发分支与发布分支

把本文发给**任意项目**里的 AI，说「按开发/发布分支区分」「main/dev 分内容」「配置生产分支瘦树」「正式分支与开发分支」或同类口令即可。  
AI 读本文后：**先探查项目实况并分析择优** → 输出【发布分支核对】（含主推结论与依据）请用户确认 → **仅不确定或不可逆处才停问** → 确认后再落盘。  
**独立通用**：不依赖、不假定某一托管商、固定分支名、某一脚本名或固定元数据目录名；分支名、路径、元数据落点由**项目实况分析 + 用户确认**决定。  
**一次配好**：落盘后日常真源是**项目内**允许列表（若有）/ README 裁剪标记（若有）/ 分支角色落点 / §3.3 / §3.5 薄规则 /（瘦 tip 时）**可执行的提升入口**；配完后日常会话**只读这些项目文件**，不必再打开本文。改范围或发现夹带时，按项目薄规则做核对与提升（见 §4）。

**执行要求（给 AI）**

1. **先探查分析择优、后动手**：未出示【发布分支核对】、未获用户确认，不得改分支 tip、不得推送正式分支、不得强推、不得重置历史；不得改允许列表 / ignore / README 标记 / 拟进正式 tip 的正文。  
2. **少问、主推（硬）**：能从仓库结构、已有分支/remote、CI/部署脚本、目录与命名判断的，**自行择优写入核对表（一项主推 + 一句依据）**，勿把附录选项或路径灰区整表甩给用户勾选，勿以「一次回齐」长串代替分析。仅当信息不足、多解等价、或涉及**建正式分支 tip / 首次提升 / 推远程 / 改默认分支或保护 / 强推清史**等不可逆项时，**一次一问**。与「协作面与公开面」文档同一交互口径。  
3. **本文范围（硬）**：只做**同一仓库内**开发分支与正式分支的**角色区分**；若为瘦 tip，再做**路径划分**与拟进正式 tip 正文的**开发向夹带**扫描（附录 C）。夹带处理写入核对表主推（默认 A）；**整包确认前不改正文**。**B 仅为去掉夹带、使正式侧步骤不指向缺失文件的最小改写**，不得扩大为全文重写。  
4. **禁止顺带质量改动**：不得在本任务中擅自做 README/文档的文案优化、结构调整、徽章与排版类改动。  
5. **优化建议（可选、分离）**：可另附【正式树优化建议】，**仅输出供用户勾选**；未采纳不得动手。与核对表分开。  
6. **文档必查（瘦 tip 时）**：对拟进正式 tip 的文本做附录 C 扫描；路径在允许列表中 ≠ 可原样提升。  
7. **三分表（瘦 tip 时）**：拟进正式 / 仅开发分支 / 不确定。能按附录 B 启发式归类的**写入拟进或仅开发并标主推**，不得借口「灰区」整表甩问。不确定**不得静默改清单**；仅真阻塞写入「不确定」，阻塞项一次一问。  
8. **对用户只给结论 + 待确认项**；不把修改方案/对话过程写入项目正式文档。  
9. **正式正文只写现行**：删除即移除；不写「已废弃/不要再用」类留痕。  
10. **按实况裁剪**：库/工具/文档仓/无服务端/不部署等 → 「部署起来」或整类路径标「不适用」并一句理由**写入核对表**；禁止按某一技术栈臆造文件。能判则不问。  
11. **已有配置与分支先复述**：已有开发/正式分支、允许列表、提升入口、保护/合入约定时，先读出现行再问是否改；无则从零起草并主推落点。  
12. **分支命名（择优）**：不预设唯一固定名。常见正式侧 `main` / `master` / `prod` / `release`，开发侧 `dev` / `develop` / `main`——**作识别线索**。按附录 D 择优写入核对表；已有长期分支优先沿用实况名。用户明示命名以用户为准。两长期分支角色争持或名冲突 → 停问。  
13. **配完收尾（硬）**：填实 §3.3；写入 §3.5（落点一并主推：常见根 `AGENTS.md` 一小节，或元数据目录内 `MAINTAIN.md`）。瘦 tip 时 **§3.3「提升或合入正式入口」不得长期为空**（有则复用；无则主推最小脚本或维护说明中的手工步骤）。声明「日常只维护项目内配置与薄规则 + 走提升/合入入口」。

## 1. 概念（现行）

| 角色 | 是什么 |
| --- | --- |
| **开发分支** | 日常研发真源 tip：完整工作树（源码 + 过程文档 + 规范/档案 + AI/协作入口等）。可以很大。分支名由实况分析主推或用户指定。 |
| **正式分支**（本文亦称**发布分支**） | 同仓内的**部署/生产基线 tip**（或用户确认的其它正式基线）。用途优先：**跑起来**、**部署起来**（CI/CD、环境更新、运维拉取），外加构建/运行/部署所需说明与版本摘要。可以与开发分支**同内容**（只分合入与谁可部署），也可以是**按路径裁剪的瘦 tip**。分支名由实况分析主推或用户指定。 |
| **仅本地** | 永不进任何远程：密钥、本机写死路径、个人草稿（选择不入库时）。用开发侧 ignore 排除。 |

### 1.1 易混概念（能判则写入核对表，勿三项都问）

| 概念 | 是什么 | 不是什么 |
| --- | --- | --- |
| **模式** | 同内容（仅角色/合入差）还是瘦正式 tip（路径裁剪） | 不是分支叫什么、也不是本轮是否推送 |
| **分支角色** | 哪条 tip 是日常开发、哪条是正式/生产基线 | 不是托管商默认分支是否已改（不代改除非明示） |
| **本轮动作** | 只落盘配置 / 落盘+建正式分支 / +首次提升 / +推远程 | 不是路径表本身；未点名提升/推送时主推「只落盘」 |

**铁律**

1. **角色先于裁剪**：先判明开发/正式分支（主推写入核对），再决定同内容还是瘦 tip。  
2. **环境更新 / 生产部署**默认拉取**正式分支** tip；不得默认要求检出开发全量 tip 才部署（无部署则写「不适用」）。  
3. 瘦 tip 时：正式分支不该有的内容靠「不出现在正式 tip」实现；不要靠正式树上 `.gitignore` 点名隐藏开发目录。  
4. 瘦 tip 时：发布用 ignore 只写正式消费者需要的规则（依赖、构建产物、`.env` 模式等）；允许列表、清洁 ignore、裁剪元数据**默认不进正式 tip**。  
5. 根目录协作/AI 入口、过程文档树、会话档案等默认只留开发分支；正式侧以可构建/可运行/可部署所需说明与运维步骤为准。  
6. 「部署起来」按**择优并经用户确认的实况**准备；无部署需求则跳过并写明。  
7. **瘦 tip**：日常在开发分支提交并推送；需要更新正式基线时再按允许列表**提升**（附录 A）。**禁止**把开发分支整支 `merge` / `rebase` 到正式分支作为默认同步。  
8. **同内容**：以核对表中主推（或用户改过）的合入/保护/回流约定为准；合入可用 merge/PR 等既有方式，**不适用**「禁止整支 merge」与允许列表提升。

## 2. 执行步骤（照做）

### 第 0 步 · 目标对齐

先探查（可与第 1 步合并）：已有允许列表/分支角色/用户口令/README 与部署入口。能判断则直接主推模式；**仅无法判断时**一问（同内容 / 瘦正式 tip）。有现成答案只复述确认，勿重复盘问。

| 主推或用户意向 | 走法 |
| --- | --- |
| 两边同内容，只区分日常开发与正式/生产基线 | **同内容**：不做路径允许列表；择优填同内容项后出示核对即可收束到 §3.3 / §3.5 |
| 要瘦正式 tip（口令含瘦树/生产裁剪/路径差等） | 走第 1～7 步完整配置 |
| 仍不确定 | **停问一次**，勿默认创建分支或臆造目录名 |

正式用途默认按「跑起来 +（如需）部署起来 + 构建/运行/部署所需说明」写入核对表；实况无部署则标不适用。有额外必须进正式 tip 的路径从仓库与口令判断，拿不准再列入不确定。

**同内容项（择优写入核对；勿逐项盘问）**

- 开发分支名、正式分支名（附录 D）  
- 远程默认分支（记实况；不代改托管设置）  
- 正式保护 / 合入方式（有 PR/保护规则则记实况；无则主推「经指定入口或 PR 合入」）  
- 部署/CI 触发对象（从现有流水线/脚本判断；无则人工）  
- **hotfix 回流**（无约定则主推「正式侧修复后 cherry-pick 或 PR 回开发分支」）  
- 密钥/PII/本机路径：仍按开发侧 ignore 与正文卫生处理  

### 第 1 步 · 探查

- 工作区结构、README、构建/运行/部署相关文件（有什么写什么）。  
- 已有本地与远程分支名、默认分支、CI/部署拉取哪条分支（原样记录）。  
- 是否已有：正式允许列表、正式用 ignore、README 仅开发段标记、提升/合入入口。  
- 项目类型粗判（应用 / 库 / 文档 / 单体 / 多包等）→ 影响附录 B 默认集。  
- 与角色无关的远程分支/归档 tip → 配置时忽略，**勿写入不确定勾选**。

### 第 2 步 · 分支角色、元数据、提升入口（择优写入核对表）

对每一项：**分析 → 一项主推 + 一句依据 → 写入【发布分支核对】**；能判则不问。

- **分支角色（附录 D）**：已有则沿用并说明依据；正式分支尚不存在 → 主推新建名（常见 `release`，或项目已用近义名）并写入本轮动作选项，**勿把「建不建」拆成路径表勾选**。  
- **元数据目录（仅瘦 tip）**：无冲突 → 主推 `.release/`；已有其它裁剪元数据目录则主推复用或并列说明。同内容可无。  
- **提升或合入入口（瘦 tip 必有归宿）**：  
  1. 已有可用提升/同步脚本 → **主推复用**；  
  2. 无入口且需重复提升 → **主推**落本项目最小步骤脚本（路径一并主推，常见元数据目录下）；  
  3. 极少提升 → **主推**把附录 A 步骤写入项目维护说明（手工）；  
  禁止假定外部管理仓命令存在；禁止向用户摊菜单代替分析。  
- **无远程、分支名冲突、两长期分支角色争持** → **停问**；禁止臆造托管地址与强推。

### 第 3 步 · 路径与文档分界（硬；仅瘦 tip）

| 类 | 含义 |
| --- | --- |
| 拟进正式 | 跑起来 /（如需）部署起来 / 构建·运行·部署所需说明 |
| 仅开发分支 | 过程文档、档案、协作/AI 入口、原始资料堆、本机一键/凭据、裁剪元数据、纯研发探针等 |
| 不确定 | **仅**附录 B 启发式仍无法归类、或含泄密/不可逆歧义的灰区 |

按附录 B **主动归类**；常见灰区优先用启发式消化（见附录 B「启发式」），写入拟进或仅开发并在摘要中带一句依据。  
对每一拟进正式文本做附录 C 扫描 → 夹带表（文件 | 信号 | **主推** A/B/C/D | 依据）；默认主推 **A**。

### 第 4 步 · 出示【发布分支核对】→ 等待确认

用 §3.1 填实（字段填主推值，不是空白问卷）。确认前**不落盘、不推送、不改正文**。  
可选：另附【正式树优化建议】。  
用户确认面压缩为：①主推整包（要改点名行）②本轮动作③若有阻塞再单问。

### 第 5 步 · 落盘（仅按确认结果）

在开发分支工作区写入（路径以核对确认的主推为准；瘦 tip 常见 `.release/`）：

- 正式允许列表（同内容模式省略）  
- 正式用清洁 ignore 正文（提升时作为正式 tip `.gitignore`，若需要）  
- README：优先**一份 README + 仅开发段标记**（提升时去掉）。推荐标记：`<!-- release:omit -->` … `<!-- /release:omit -->`（可改，写入 §3.3）  
- 保护 / 合入 / hotfix 回流：写入 §3.3；不擅自改托管商设置除非用户明示  
- 提升入口：按第 2 步落盘脚本或维护说明步骤  

元数据目录与允许列表文件本身默认不进允许列表。

### 第 6 步 · 试提升 / 预览 → 再确认 → 才更新正式分支（仅瘦 tip）

仅当本轮动作含「首次提升」或用户另令提升时执行：

- 调用本项目提升入口的**预览**（若有）；否则按允许列表列出正式 tip 文件集。  
- 出示【提升预览】（§3.2）；史学已在核对表主推（默认内容快照叠 tip），预览中复述即可。  
- 用户再次确认后才：更新正式分支 / 仅本地导出对照 / 取消。  
- 遵守附录 A。

同内容模式：按确认的合入入口更新正式分支；不做允许列表提升预览。

### 第 7 步 · 完成

填实 §3.3；写入 §3.5；向用户声明日常用法见 §4。  
若存在「环境更新/生产部署」脚本：应基于**正式分支** tip；若仍要求检出开发全量 tip 才部署 → 列入待确认请用户改（无则写「不适用」）。

### 3.5 日常薄规则（配完必须写入项目；此后日常只读项目内此文）

## 附录 A · 提升机械卫生（瘦 tip）

1. 仅按允许列表进入正式 tip；元数据与清单本身不得出现在正式 tip。  
2. 正式 `.gitignore` 用清洁正文，不得含「仅开发路径」点名藏匿。  
3. README 标记提升后不得残留；不得残留仅开发入口（以附录 C 为准）。  
4. 根 AGENTS（若有）默认不进入正式 tip。  
5. 密钥、真实 PII、内网独占地址不得进入应进正式 tip 的提交。  
6. **默认同步方式**：按允许列表在**临时目录或独立 worktree** 生成正式树，再叠到既有正式分支 tip（内容无变化可不推）。**禁止**默认 `merge` / `rebase` 开发分支整支到正式分支。  
7. **开发 tip 隔离**：提升过程不得把正式 tip checkout/reset 到开发分支再推回。推开发分支前 HEAD 须与提升前一致（或仅含用户确认的开发侧改动）。  
8. 强推、清史、改默认分支须先用户确认。  
9. 无现成脚本时：可给出最小步骤草案并主推落盘为入口，**确认后**再执行；不假装某一管理仓命令已存在。  
10. **正式 tip 史学**：允许列表叠 tip 默认为内容快照史（与开发提交史不同形）。用户要跟应用提交史或其它约定时，在核对表改主推；用户未确认本轮含更新正式 tip 前，不强推改写正式史。

---

## 附录 B · 默认路径口径与启发式（供 AI 择优；瘦 tip）

**通常拟进正式**：可运行/可构建所需源码与依赖清单；与实况匹配的编排/部署/健康检查/迁移等（有则进，无则不臆造）；脱敏示例配置；构建/运行/部署步骤说明；VERSION / CHANGELOG 或项目版本数据源；随应用树可跑、无业务密钥的测试文件（如 `apps/tests*.py`）。

**通常仅开发分支**：过程文档树（常见名如 `开发/`，以实况为准）；原始资料堆；会话上下文与项目档案类；根协作/AI 入口全文；本机一键/凭据；裁剪元数据目录；纯研发探针（bench / diagnose / e2e 手工 / verify_* 等）；门禁运行态与本地日志（多已 ignore）；运维长文/内部手册（正式侧用 README 摘要即可）。

**启发式（优先消化灰区，勿默认甩「不确定」勾选）**

| 情形 | 主推 |
| --- | --- |
| `scripts/` 含 `prod_*` / 部署打包，且其余为探针/e2e | 仅 prod/部署相关进正式；探针仅开发 |
| `scripts/` 无从区分 | 与「跑起来/部署起来」直接相关的进正式，其余仅开发；一句依据 |
| 应用内单元/集成测试、无密钥样例 | 进正式 |
| 含真实主机/客户数据/未脱敏夹具 | 仅开发或不确定（泄密则阻塞单问） |
| 运维长文 vs README | 长文仅开发；正式靠 README |
| 与角色无关的远程分支/归档 tip | 配置忽略，不进不确定表 |
| 多包仓范围 | 按部署/CI 实际构建的包进正式；其余仅开发；多解等价才停问 |
| 示例配置含真实主机名 | 不确定或主推脱敏/仅开发（阻塞则单问） |

**原则**：正式 tip 优先保证机器与运维能构建/运行/部署；过程文书、协作入口、机器特化本机入口留在开发分支。无「部署」时不要硬凑编排文件。

## 附录 C · 正文夹带（允许路径仍须扫；瘦 tip）

| 信号 | 风险 |
| --- | --- |
| 指向过程文档树、档案、内部交接的链接或路径 | 正式 tip 死链；部署/克隆步骤不可用 |
| 本机一键 / 仅开发脚本入口 | 正式 tip 无此文件，误导构建与部署 |
| 部署/CI 说明仍要求检出开发全量或过程树 | 与正式基线角色矛盾 |
| 「仅开发分支」「勿提升」等流程套话堆砌 | 噪音；干扰正式侧步骤 |
| 真实主机名、内网 IP、客户名、未脱敏样例 | 泄密 |

处理（写入核对表**主推**；整包确认前不改正文）：

- **A**（默认）移入「仅开发」标记块（提升时去掉）  
- **B** **最小改写**：去掉夹带或改为正式 tip 可用的现行步骤（不提及缺失文件）；禁止借此做结构/文案/排版优化  
- **C** 从本次正式范围排除该文件  
- **D** 保持原样（须用户明示接受风险）

文案结构、徽章等提升 → 不进本表；写入【正式树优化建议】由用户另选。

## 附录 D · 分支角色择优（勿整表甩问）

| 信号 | 主推倾向 |
| --- | --- |
| 仅一条长期分支且为日常 tip | 该分支 = 开发；正式分支尚无 → 主推新建 `release`（或项目近义名） |
| 已有 `release` / `prod` / `publish` 且部署/CI 跟它 | 该分支 = 正式；另一日常 tip = 开发 |
| 远程默认 = 日常开发 tip，部署脚本跟另一分支 | 默认分支侧 = 开发；部署跟随侧 = 正式 |
| 口令明确「main 开发、正式另建」等 | 按口令主推 |
| 两长期分支皆像正式或皆像开发 | **停问一次** |
| 用户明示命名 | 以用户为准 |

记录远程默认分支实况；**不**在未明示时代改托管商默认分支或保护规则。
