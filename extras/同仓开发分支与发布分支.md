# 同仓开发分支与发布分支

把本文发给**任意项目**里的 AI，说「按开发/发布分支区分」「main/dev 分内容」「配置生产分支瘦树」「正式分支与开发分支」或同类口令即可。  
AI 读本文后：先分析并区分**开发分支**与**正式分支（发布 / 主部署 / 生产基线）** → 输出【发布分支核对】请用户确认 → **不确定就问用户** → 确认后再落盘。  
**独立通用**：不依赖、不假定某一托管商、固定分支名、某一脚本名或固定元数据目录名；分支名、路径、元数据落点一律由**项目实况 + 用户选择或确认**决定。  
**一次配好**：落盘后日常真源是**项目内**允许列表（若有）/ README 裁剪标记（若有）/ 分支角色落点 / §3.3 / §3.5 薄规则；配完后日常会话**只读这些项目文件**，不必再打开本文。改范围或发现夹带时，按项目薄规则做核对与提升（摘要见 §4，须已写入项目）。

**执行要求（给 AI）**

1. **先分析、后动手**：未出示【发布分支核对】、未获用户确认，不得改分支 tip、不得推送正式分支、不得强推、不得重置历史；不得改允许列表 / ignore / README 标记 / 拟进正式 tip 的正文。  
2. **本文范围（硬）**：只做**同一仓库内**开发分支与正式分支的**角色区分**；若用户要瘦 tip，再做**路径划分**与拟进正式 tip 正文的**开发向夹带**扫描（附录 C）。夹带处理（A/B/C/D）须用户确认后再实施；**B 仅为去掉夹带、使正式侧步骤不指向缺失文件的最小改写**，不得扩大为全文重写。  
3. **禁止顺带质量改动**：不得在本任务中擅自做 README/文档的文案优化、结构调整、徽章与排版类改动。  
4. **优化建议（可选、分离）**：分析完成后，可另附【正式树优化建议】，**仅输出供用户勾选**；用户明示采纳后再单独实施。与核对表分开；未采纳不得动手。  
5. **文档必查（瘦 tip 时）**：对拟进正式 tip 的文本做附录 C 扫描；路径在允许列表中 ≠ 可原样提升。  
6. **三分表（瘦 tip 时）**：拟进正式 / 仅开发分支 / 不确定。不确定**不得静默归类**，写入核对表；阻塞项一次一问，非阻塞可表内勾选。  
7. **对用户只给结论 + 待确认项**；不把修改方案/对话过程写入项目正式文档。  
8. **正式正文只写现行**：删除即移除；不写「已废弃/不要再用」类留痕。  
9. **按实况裁剪**：库/工具/文档仓/无服务端/不部署等 → 「部署起来」或整类路径可标「不适用」并一句理由，**先问再定**；禁止按某一技术栈臆造文件。  
10. **已有配置与分支先复述**：已有开发/正式分支、允许列表、提升入口、保护/合入约定或其它相关配置时，先读出现行再问是否改；无则从零起草。  
11. **分支命名（硬）**：不预设固定名。常见正式侧名如 `main` / `master` / `prod` / `release`，开发侧如 `dev` / `develop`——**只作识别线索**，须用户确认角色。若仓库**已有**长期分支，按实况识别并请用户确认「哪条是开发分支、哪条是正式分支」；用户另有命名习惯以用户为准。仅当用户明确要求新建且未给名时，再提出候选名请用户选。  
12. **配完收尾（硬）**：填实 §3.3；把 §3.5 薄规则**写入用户确认的项目落点**（常见：根 `AGENTS.md` 一小节，或元数据目录内 `MAINTAIN.md`）；落盘后向用户声明「日常只维护项目内配置与薄规则」。

## 1. 概念（现行）

| 角色 | 是什么 |
| --- | --- |
| **开发分支** | 日常研发真源 tip：完整工作树（源码 + 过程文档 + 规范/档案 + AI/协作入口等）。可以很大。分支**名由项目实况或用户指定**。 |
| **正式分支**（本文亦称**发布分支**） | 同仓内的**部署/生产基线 tip**（或用户确认的其它正式基线）。常见名 `main`。用途优先：**跑起来**、**部署起来**（CI/CD、环境更新、运维拉取），外加构建/运行/部署所需说明与版本摘要。可以与开发分支**同内容**（只分合入与谁可部署），也可以是**按路径裁剪的瘦 tip**。分支**名由项目实况或用户指定**。 |
| **仅本地** | 永不进任何远程：密钥、本机写死路径、个人草稿（选择不入库时）。用开发侧 ignore 排除。 |

**铁律**

1. **角色先于裁剪**：先确认哪条是开发、哪条是正式（常为生产/主部署）；再决定同内容还是瘦 tip。  
2. **环境更新 / 生产部署**默认拉取**正式分支** tip；不得默认要求检出开发全量 tip 才部署（无部署则写「不适用」）。  
3. 瘦 tip 时：正式分支不该有的内容靠「不出现在正式 tip」实现；不要靠正式树上 `.gitignore` 点名隐藏开发目录。  
4. 瘦 tip 时：发布用 ignore 只写正式消费者需要的规则（依赖、构建产物、`.env` 模式等）；允许列表、清洁 ignore、裁剪元数据**默认不进正式 tip**。  
5. 根目录协作/AI 入口、过程文档树、会话档案等默认只留开发分支；正式侧以可构建/可运行/可部署所需说明与运维步骤为准（产品介绍类文案按用户确认，可「不适用」）。  
6. 「部署起来」按用户确认的形态准备；**不默认唯一形态**，无部署需求则跳过并写明。  
7. **瘦 tip**：日常不必双分支同时推送；平时在开发分支提交并推送；需要更新部署/生产基线时再按允许列表**提升**到正式分支（附录 A）。**禁止**把开发分支整支 `merge` / `rebase` 到正式分支作为默认同步（会把过程文档与协作入口一并带上）。  
8. **同内容**：以用户确认的合入/保护/回流规则为准（见第 0 步同内容核对）；合入正式分支可用 merge/PR 等项目既有方式，**不适用**「禁止整支 merge」与允许列表提升。

## 2. 执行步骤（照做）

### 第 0 步 · 目标对齐（停问）

先用 1～2 问对齐（有现成答案可复述确认，勿重复盘问）：

1. 正式分支与开发分支是**同内容**（只分谁日常开发 / 谁可部署或受保护），还是正式侧要**按路径瘦 tip**？  
2. 正式用途是否仍为「跑起来 +（如需要）部署起来 + 构建/运行/部署所需说明」？有无额外必须进正式 tip 的路径？

| 用户意向 | 走法 |
| --- | --- |
| 两边同内容，只区分日常开发与正式/生产基线 | **同内容**：不做路径允许列表；走下方「同内容核对」后填 §3.3 / §3.5（同内容版）可结束 |
| 要瘦正式 tip | 走第 1～7 步完整配置 |
| 不确定 | **停问**，勿默认创建分支或臆造目录名 |

**同内容核对（须用户确认后写入 §3.3）**

- 开发分支名、正式分支名（常见正式侧为 `main`）  
- 远程**默认分支**是哪一条  
- 正式分支是否保护、是否仅经 PR/指定入口合入（记录约定；**不擅自改托管商设置**，除非用户明示代改）  
- 部署/CI 触发对象：正式 tip / tag / 人工（写明）  
- **hotfix**：在正式侧修复后如何回流开发分支（须有约定；无则问用户）  
- 密钥/PII/本机路径：仍按开发侧 ignore 与正文卫生处理  

### 第 1 步 · 探查

- 工作区结构、README、构建/运行/部署相关文件（有什么写什么）。  
- 已有本地与远程分支名、默认分支、保护规则、CI/部署拉取哪条分支（原样记录）。  
- 是否已有：正式允许列表、正式用 ignore、README 仅开发段标记、提升/合入入口。  
- 项目类型粗判（应用 / 库 / 文档 / 单体 / 多包等）→ 影响默认拟进正式集；拿不准列入不确定。

### 第 2 步 · 分支角色与元数据落点（停问）

- **分支角色**：根据探查列出候选 → 请用户确认「开发分支 = ?」「正式分支 = ?」。已有分支优先沿用实况名（正式侧常见 `main`）；用户要新建或改名时以用户为准。  
- **元数据目录（仅瘦 tip）**：推荐默认 `.release/`（内含允许列表等），**必须先向用户确认**；用户指定其它路径则改用用户路径，并写入 §3.3。同内容模式可无元数据目录。  
- 无远程、分支名冲突、或正式分支尚不存在 → **问用户**如何处理；禁止臆造托管地址与强推。

### 第 3 步 · 路径与文档分界（硬；仅瘦 tip）

产出三类表：

| 类 | 含义 |
| --- | --- |
| 拟进正式 | 跑起来 /（如需）部署起来 / 构建·运行·部署所需说明 |
| 仅开发分支 | 过程文档、档案、协作/AI 入口、原始资料堆、本机一键/凭据、裁剪元数据等 |
| 不确定 | 灰区（见下）— 必须问或表内勾选 |

**常见不确定（示例，非穷尽）**：内部运维说明是否进正式 tip；验收证据是否随部署走；部署脚本与纯研发探针是否拆分；README 是否保留指向过程文档的链接；多包仓哪些包进正式 tip；多环境（预发/生产）是否共用同一正式角色；示例配置是否仍含真实主机名。

对**每一拟进正式的文本文件**做附录 C 扫描 → 夹带问题表（文件 | 信号 | 建议 A/B/C/D）。  
默认口径见附录 B；仍须用户确认增减。

### 第 4 步 · 出示【发布分支核对】→ 等待确认

用 §3.1 填实。确认前**不落盘、不推送、不改正文**。  
可选：另附【正式树优化建议】（与核对表分离；默认不实施）。

### 第 5 步 · 落盘（仅按确认结果）

在开发分支工作区写入（**路径/目录名以用户确认为准**；瘦 tip 推荐经确认后用 `.release/`）：

- 正式允许列表（同内容模式省略）  
- 正式用清洁 ignore 正文（提升时作为正式 tip `.gitignore`，若需要）  
- README：优先**一份 README + 仅开发段标记**（提升时去掉）。推荐标记（可改，须在 §3.3 写明）：`<!-- release:omit -->` … `<!-- /release:omit -->`  
- 保护分支 / 合入 / hotfix 回流：写入 §3.3；不擅自改托管商设置除非用户明示

元数据目录与允许列表文件本身默认不进允许列表。

### 第 6 步 · 试提升 / 预览 → 再确认 → 才更新正式分支（仅瘦 tip）

- 有项目自带的提升/同步入口：确认后调用；**无则**按允许列表列出将进入正式 tip 的文件集，或给出最小提升步骤/草案脚本，仍须确认。禁止假定外部管理仓命令存在。  
- 出示【提升预览】（§3.2）；并请用户确认正式 tip **史学**（附录 A 第 10 条）。  
- 用户再次确认后才：更新正式分支 / 仅本地导出对照 / 取消。  
- 遵守附录 A（在开发工作树外做提升；禁止用正式 tip 覆盖开发分支再推回；禁止整支 merge 作为默认同步）。

同内容模式：按用户确认的合入入口更新正式分支；不做允许列表提升预览。

### 第 7 步 · 完成

填实 §3.3；按用户确认的落点写入 §3.5 薄规则（填入本项目真实分支名、路径与标记名；同内容用同内容版条文）；本文使命结束。若存在「环境更新/生产部署」脚本：应基于**正式分支** tip；若仍要求检出开发全量 tip 才部署 → 列入待确认请用户改（无此类脚本则写「不适用」）。

### 3.5 日常薄规则（配完必须写入项目；此后日常只读项目内此文）

将下列对应模式的正文写入 §3.3「日常薄规则落点」（把尖括号换成本项目实值）。写入后日常 AI **以项目内此段 +（若有）允许列表为准**，不再检索配置用长文。

**瘦 tip 版：**

```text
## 开发分支与正式分支（日常）

- 配置真源：开发分支 `<名>`；正式分支 `<名>`；正式允许列表 `<路径>`；README 仅开发段标记 `<标记名，如 release:omit>`；提升入口 `<入口或无>`；部署/CI 拉取 `<正式分支或约定>`。
- 触发检查（本轮改动命中任一则执行，否则不巡检）：
  1. 新增/移动/重命名「跑起来或部署起来」可能需要的路径，或不在允许列表中的构建/运行/部署入口；
  2. 修改已在允许列表内的说明文（尤其根 README），或正式段新增指向过程文档/档案/仅开发入口的链接或路径；
  3. 用户明确要求改正式范围或提升正式分支。
- 检查动作：对照允许列表做拟进正式 / 仅开发分支 / 不确定；对拟进正式正文按夹带信号扫（死链到过程树、本机入口、部署说明指向仅开发路径、真实主机/未脱敏等）。不确定写入待确认，**一次一问**；不得静默改清单或正文；不得整支 merge 开发分支到正式分支。
- 确认后：更新允许列表与（如需）omit/最小改写 → 走本项目提升入口（或用户确认的允许列表叠 tip 步骤）更新正式分支。只改过程文档、且不影响正式段 → 只提交开发分支，不提升。
- 改清单/更新正式分支/强推前：先给出简短核对结论，用户确认后再执行。
```

**同内容版：**


## 附录 A · 提升机械卫生（瘦 tip）

1. 仅按允许列表进入正式 tip；元数据与清单本身不得出现在正式 tip。  
2. 正式 `.gitignore` 用清洁正文，不得含「仅开发路径」点名藏匿。  
3. README 标记提升后不得残留；不得残留仅开发入口（以附录 C 为准）。  
4. 根 AGENTS（若有）默认不进入正式 tip。  
5. 密钥、真实 PII、内网独占地址不得进入应进正式 tip 的提交。  
6. **默认同步方式**：按允许列表在**临时目录或独立 worktree** 生成正式树，再叠到既有正式分支 tip（内容无变化可不推）。**禁止**默认 `merge` / `rebase` 开发分支整支到正式分支。  
7. **开发 tip 隔离**：提升过程不得把正式 tip checkout/reset 到开发分支再推回。推开发分支前 HEAD 须与提升前一致（或仅含用户确认的开发侧改动）。  
8. 强推、清史、改默认分支须先用户确认。  
9. 无现成脚本时：可给出最小步骤草案，**确认后**再执行；不假装某一管理仓命令已存在。  
10. **正式 tip 史学（须确认）**：允许列表叠 tip 可为内容快照史（与开发提交史不同形）。部署/回滚/tag 跟哪条 tip、是否接受快照叠 tip，写入核对表；用户未确认前不强推改写正式史。

## 附录 B · 默认路径口径（仍须确认；瘦 tip）

**通常拟进正式**：可运行/可构建所需源码与依赖清单；与形态匹配的编排/部署/健康检查/迁移等（用户确认需要的）；脱敏示例配置；构建/运行/部署步骤说明；VERSION / CHANGELOG 或项目确认的版本数据源。

**通常仅开发分支**：过程文档树（常见名如 `开发/`，以实况为准）；原始资料堆；会话上下文与项目档案类；根协作/AI 入口全文；本机一键/凭据；裁剪元数据目录；纯研发探针；门禁运行态与本地日志（多已 ignore）。

**原则**：正式 tip 优先保证机器与运维能构建/运行/部署；过程文书、协作入口、机器特化本机入口留在开发分支。无「部署」时不要硬凑编排文件。产品介绍类说明按用户确认，可标不适用。
