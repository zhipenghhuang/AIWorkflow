# 同仓开发分支与发布分支

把本文发给**任意项目**里的 AI，说「按开发/发布分支区分内容」「配置发布分支瘦树」「main/dev 分内容」或同类口令即可。  
AI 读本文后：先分析并区分开发分支与发布分支应有内容 → 输出【发布分支核对】请用户确认 → **不确定就问用户** → 确认后再落盘。  
**独立通用**：不依赖、不假定某一托管商、固定分支名、某一脚本名或固定元数据目录名；分支名、路径、元数据落点一律由**项目实况 + 用户选择或确认**决定。  
**一次配好**：落盘后日常真源是项目内允许列表 / README 裁剪标记 / 分支角色落点；不必再通读本文。仅改发布范围或提升方式时再按 §4 缩略核对。

**执行要求（给 AI）**

1. **先分析、后动手**：未出示【发布分支核对】、未获用户确认，不得改分支 tip、不得推送发布分支、不得强推、不得重置历史；不得改允许列表 / ignore / README 标记 / 拟进发布树的正文。  
2. **本文范围（硬）**：只做**同一仓库内**开发分支与发布分支的**路径划分**，以及对拟进发布树正文的**开发向夹带**扫描与处理建议（附录 C）。夹带处理（A/B/C/D）须用户确认后再实施；**B 仅为去掉夹带、使发布侧步骤不指向缺失文件的最小改写**，不得扩大为全文重写。  
3. **禁止顺带质量改动**：不得在本任务中擅自做 README/文档的文案优化、结构调整、徽章与排版类改动。  
4. **优化建议（可选、分离）**：分析完成后，可另附【发布树优化建议】，**仅输出供用户勾选**；用户明示采纳后再单独实施。与核对表分开；未采纳不得动手。  
5. **文档必查**：对拟进发布树的文本做附录 C 扫描；路径在允许列表中 ≠ 可原样提升。  
6. **三分表**：拟进发布 / 仅开发分支 / 不确定。不确定**不得静默归类**，写入核对表；阻塞项一次一问，非阻塞可表内勾选。  
7. **对用户只给结论 + 待确认项**；不把修改方案/对话过程写入项目正式文档。  
8. **正式正文只写现行**：删除即移除；不写「已废弃/不要再用」类留痕。  
9. **按实况裁剪**：库/工具/文档仓/无服务端/不部署等 → 「部署起来」或整类路径可标「不适用」并一句理由，**先问再定**；禁止按某一技术栈臆造文件。  
10. **已有配置与分支先复述**：已有开发/发布分支、允许列表、提升入口或其它相关配置时，先读出现行再问是否改；无则从零起草。  
11. **分支命名（硬）**：不预设固定名。若仓库**已有**长期分支，按实况识别并请用户确认「哪条是开发分支、哪条是发布分支」；若用户另有命名习惯，以用户为准。仅当用户明确要求新建且未给名时，再提出候选名请用户选。  
12. **配完收尾**：填实 §3.3；声明「日常维护看这些配置，不必再读本文」。

## 1. 概念（现行）

| 角色 | 是什么 |
| --- | --- |
| **开发分支** | 日常研发真源 tip：完整工作树（源码 + 过程文档 + 规范/档案 + AI/协作入口等）。可以很大。分支**名由项目实况或用户指定**。 |
| **发布分支** | 有意裁剪后的瘦 tip。默认只服务：**跑起来**、**部署起来**（若项目需要），外加必要说明（产品是什么、如何构建/运行/部署、版本与变更摘要等）。分支**名由项目实况或用户指定**。 |
| **仅本地** | 永不进任何远程：密钥、本机写死路径、个人草稿（选择不入库时）。用开发侧 ignore 排除。 |

**铁律**

1. 发布分支不该有的内容靠「不出现在发布 tip」实现；不要靠发布树上 `.gitignore` 点名隐藏开发目录。  
2. 发布用 ignore 只写发布消费者需要的规则（依赖、构建产物、`.env` 模式等）。  
3. 允许列表、清洁 ignore、裁剪元数据**默认不进发布 tip**。  
4. 根目录协作用 `AGENTS`、过程文档树、会话档案等默认只留开发分支；发布侧以 README / 版本与变更说明 / 必要运维说明为准。  
5. 「部署起来」按用户确认的形态准备；**不默认唯一形态**，无部署需求则跳过并写明。  
6. **日常不必双分支同时推送**：平时在开发分支提交并推送即可；需要发布/部署基线时再按允许列表**提升**到发布分支（见附录 A）。  
7. **禁止**把开发分支整支 `merge` / `rebase` 到发布分支作为默认同步手段（会把过程文档与协作入口一并带上）。默认用附录 A 的允许列表提升。

## 2. 执行步骤（照做）

### 第 0 步 · 目标对齐（停问）

先用 1～2 问对齐（有现成答案可复述确认，勿重复盘问）：

1. 是否需要发布分支为**瘦树**？（要按路径裁剪 / 两边同内容只分合入节奏 / 尚不确定）  
2. 发布用途是否仍为「跑起来 +（如需要）部署起来 + 必要说明」？有无额外必须进发布 tip 的路径？

| 用户意向 | 走法 |
| --- | --- |
| 两边同内容，只区分谁可部署/谁日常开发 | **同内容**：不做路径允许列表；仍可约定合入/保护规则；确认分支角色后可结束 |
| 要瘦发布 tip | 走第 1～7 步完整配置 |
| 不确定 | **停问**，勿默认创建分支或臆造目录名 |

### 第 1 步 · 探查

- 工作区结构、README、构建/运行/部署相关文件（有什么写什么）。  
- 已有本地与远程分支名、默认分支、保护规则（原样记录）。  
- 是否已有：发布允许列表、发布用 ignore、README 发布裁剪标记、提升/同步入口。  
- 项目类型粗判（应用 / 库 / 文档 / 单体 / 多包等）→ 影响默认拟发布集；拿不准列入不确定。

### 第 2 步 · 分支角色与元数据落点（停问）

- **分支角色**：根据探查列出候选 → 请用户确认「开发分支 = ?」「发布分支 = ?」。已有分支优先沿用实况名；用户要新建或改名时以用户为准。  
- **元数据目录**：推荐默认 `.release/`（内含允许列表等），**必须先向用户确认**；用户指定其它路径则改用用户路径，并写入 §3.3。  
- 无远程、分支名冲突、或发布分支尚不存在 → **问用户**如何处理；禁止臆造托管地址与强推。

### 第 3 步 · 路径与文档分界（硬）

产出三类表：

| 类 | 含义 |
| --- | --- |
| 拟进发布 | 跑起来 /（如需）部署起来 / 必要说明所需 |
| 仅开发分支 | 过程文档、档案、协作/AI 入口、原始资料堆、本机一键/凭据、裁剪元数据等 |
| 不确定 | 灰区（见下）— 必须问或表内勾选 |

**常见不确定（示例，非穷尽）**：半对外设计/ADR；验收证据目录是否随产品测试走；部署脚本与纯研发探针是否拆分；README 是否保留指向过程文档的链接；多包仓哪些包进发布 tip；示例配置是否仍含真实主机名。

对**每一拟进发布的文本文件**做附录 C 扫描 → 夹带问题表（文件 | 信号 | 建议 A/B/C/D）。  
默认口径见附录 B；仍须用户确认增减。

### 第 4 步 · 出示【发布分支核对】→ 等待确认

用 §3.1 填实。确认前**不落盘、不推送、不改正文**。  
可选：另附【发布树优化建议】（与核对表分离；默认不实施）。

### 第 5 步 · 落盘（仅按确认结果）

在开发分支工作区写入（**路径/目录名以用户确认为准**；推荐经确认后用 `.release/`）：

- 发布允许列表（同内容模式可省略）  
- 发布用清洁 ignore 正文（提升时作为发布 tip `.gitignore`，若需要）  
- README：优先**一份 README + 仅开发段标记**（提升时去掉）。推荐标记（可改，须在 §3.3 写明）：`<!-- release:omit -->` … `<!-- /release:omit -->`  
- 若用户要求：保护分支 / 合入说明仅记录在核对结论或项目自有规范中，不擅自改托管商设置除非用户明示

元数据目录与允许列表文件本身默认不进允许列表。

### 第 6 步 · 试提升 / 预览 → 再确认 → 才更新发布分支

- 有项目自带的提升/同步入口：确认后调用；**无则**按允许列表列出将进入发布 tip 的文件集，或给出最小提升步骤/草案脚本，仍须确认。禁止假定外部管理仓命令存在。  
- 出示【提升预览】（§3.2）。  
- 用户再次确认后才：更新发布分支 / 仅本地导出对照 / 取消。  
- 遵守附录 A（在开发工作树外做提升；禁止用发布 tip 覆盖开发分支再推回；禁止整支 merge 作为默认同步）。

### 第 7 步 · 完成

填实 §3.3；本文使命结束。若存在「环境更新/发布」脚本：应基于**发布分支** tip；若仍要求检出开发全量 tip 才部署 → 列入待确认请用户改（无此类脚本则写「不适用」）。

## 4. 改发布范围时（缩略）

复述现行 §3.3 → 重做第 3～6 步 → 确认后落盘/提升。  
日常：只改过程文档 → 只提交开发分支，不动允许列表。运行/部署步骤变更且需进发布 tip 时，改拟发布正文（有标记则只改发布段）并提升。质量类改动仍走【发布树优化建议】→ 用户采纳后再做。

## 附录 A · 提升机械卫生

1. 仅按允许列表进入发布 tip；元数据与清单本身不得出现在发布 tip（同内容模式除外）。  
2. 发布 `.gitignore` 用清洁正文，不得含「仅开发路径」点名藏匿。  
3. README 标记提升后不得残留；不得残留仅开发入口（以附录 C 为准）。  
4. 根 AGENTS（若有）默认不进入发布 tip。  
5. 密钥、真实 PII、内网独占地址不得进入应发布的提交。  
6. **默认同步方式**：按允许列表在**临时目录或独立 worktree** 生成发布树，再叠到既有发布分支 tip（内容无变化可不推）。**禁止**默认 `merge` / `rebase` 开发分支整支到发布分支。  
7. **开发 tip 隔离**：提升过程不得把发布 tip checkout/reset 到开发分支再推回。推开发分支前 HEAD 须与提升前一致（或仅含用户确认的开发侧改动）。  
8. 强推、清史、改默认分支须先用户确认。  
9. 无现成脚本时：可给出最小步骤草案，**确认后**再执行；不假装某一管理仓命令已存在。

## 附录 B · 默认路径口径（仍须确认）

**通常拟进发布**：可运行/可构建所需源码与依赖清单；与形态匹配的最小说明与示例配置（无真实密钥）；根 README（发布可用）；VERSION / CHANGELOG 或项目确认的版本数据源；用户确认后可进发布的运维/部署脚本。

**通常仅开发分支**：过程文档树（常见名如 `开发/`，以实况为准）；原始资料堆；会话上下文与项目档案类；根协作/AI 入口全文；本机一键/凭据；裁剪元数据目录；门禁运行态与本地日志（多已 ignore）。

**原则**：发布 tip 给可复制的构建/运行/部署步骤；机器特化路径、过程文书、协作入口留在开发分支。无「部署」时不要硬凑编排文件。

## 附录 C · 正文夹带（允许路径仍须扫）

| 信号 | 风险 |
| --- | --- |
| 指向过程文档树、档案、内部交接的链接或路径 | 发布 tip 死链 + 暴露内部结构 |
| 本机一键 / 仅开发脚本入口 | 发布 tip 无此文件，误导使用者 |
| 「仅开发分支」「勿提升」等流程套话堆砌 | 噪音；可能暗示未提升流程 |
| 真实主机名、内网 IP、客户名、未脱敏样例 | 泄密 |
| 将「克隆后必须具备过程文档树」写成对外默认步骤 | 与瘦发布目标矛盾 |

处理（输出给用户勾选，勿擅自定稿）：

- **A** 移入「仅开发」标记块（提升时去掉）  
- **B** **最小改写**：去掉夹带或改为发布 tip 可用的现行步骤（不提及缺失文件）；禁止借此做结构/文案/排版优化  
- **C** 从本次发布范围排除该文件  
- **D** 保持原样（须用户明示接受风险）

文案结构、徽章等提升 → 不进本表；写入【发布树优化建议】由用户另选。

## 附录 D · 自检（执行前后）

- [ ] 开发分支名、发布分支名已按实况或用户指定确认（未擅自固定名）  
- [ ] 元数据目录已向用户确认（推荐 `.release/`，可改）  
- [ ] 发布用途未膨胀除非用户确认  
- [ ] 三类路径表已出示；不确定已问清或表内待勾选  
- [ ] 拟发布正文夹带已有用户决定；未做未确认的正文改动  
- [ ] 未顺带做 README/文档质量优化；若有优化建议表仅勾选后实施  
- [ ] 允许列表（若需要）已确认；元数据不在发布 tip；发布 ignore 清洁  
- [ ] 根 AGENTS 默认未进发布  
- [ ] 提升预览已确认再更新发布分支；未整支 merge；未改写开发分支 HEAD  
- [ ] 无密钥/PII/内网独占地址  
- [ ] §3.3 已填；已告知日常真源为项目内配置
