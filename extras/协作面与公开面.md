# 协作面与公开面

把本文发给**任意项目**里的 AI，说「按协作面与公开面配置」或「配置公开面 / 双面 / 开源面」即可。  
AI 读本文后：先分析并区分协作面与公开面内容 → 输出【公开面核对】请用户确认 → **不确定就问用户** → 确认后再落盘。  
**独立通用**：不依赖、不假定某一托管商、某一多仓管理仓库、某一脚本名或固定目录名；拓扑、路径、元数据落点一律由用户选择或确认。  
**一次配好**：落盘后日常真源是项目内允许列表 / 清洁 ignore / README 裁剪 / remote·分支；不必再通读本文。仅改公开范围或拓扑时再按 §4 缩略核对。

**执行要求（给 AI）**

1. **先分析、后动手**：未出示【公开面核对】、未获用户确认，不得改 remote/默认分支、不得推公开目标、不得强推、不得重置公开史；不得改允许列表 / ignore / README 标记 / 拟公开正文。  
2. **本文范围（硬）**：只做协作面与公开面的**路径划分**，以及对拟公开正文的**协作向夹带**扫描与处理建议（附录 C）。夹带处理（A/B/C/D）须用户确认后再实施；**B 仅为去掉夹带、使公开步骤不指向缺失文件的最小改写**，不得扩大为全文重写。  
3. **公开正文不讲分面机制（硬）**：公开可见正文按**普通对外说明**来写（是什么、怎么用、许可证等）。**双面 / 协作面 / 公开面**等机制说明、仅协作入口、默认指向协作全量仓的第二托管徽章或克隆说明 → 默认进 omit 块或拟剥离，列入夹带表请用户确认；**禁止**在公开段向访客解释「我们有协作面/公开面」或把「公开面」写成给读者看的注释。  
4. **禁止顺带质量改动**：不得在分面任务中擅自做 README/文档的文案优化、结构调整、徽章与排版、「更高质量开源仓」类改动。  
5. **公开面优化建议（可选、分离）**：分析完成后，可另附【公开面优化建议】（如 README 结构、徽章、对外说明完整度、开源习惯项等），**仅输出供用户勾选**；用户明示采纳哪些项后，再按所选项单独实施。建议与分面核对表分开；未采纳不得动手。  
6. **文档必查**：对拟进公开面的文本做附录 C 扫描；路径在允许列表中 ≠ 可原样公开。  
7. **三分表**：拟公开 / 拟剥离 / 不确定。不确定**不得静默归类**，写入核对表；阻塞项一次一问，非阻塞可表内勾选。  
8. **对用户只给结论 + 待确认项**；不把修改方案/对话过程写入项目正式文档。  
9. **正式正文只写现行**：删除即移除；不写「已废弃/不要再用」类留痕。  
10. **按实况裁剪**：库/工具/文档仓/无服务端/不上线等 → 「部署起来」或整类路径可标「不适用」并一句理由，**先问再定**；禁止按「典型 Web+Docker」臆造文件。  
11. **已有配置先复述**：已有允许列表、双 remote、公开分支、或其它面配置时，先读出现行再问是否改；无则从零起草。勿假定存在旁路管理仓或固定元数据目录名（如是否叫 `.public/` 由用户定或采用推荐默认并确认）。  
12. **配完收尾**：填实 §3.3；声明「日常维护看这些配置，不必再读本文」。

## 1. 概念（现行）

| 面 | 是什么 |
| --- | --- |
| **协作面** | 团队日常真源：完整工作树（源码 + 过程文档 + 规范/档案 + 本机入口等）。可以很大。 |
| **公开面** | 有意裁剪后的派生视图。默认只服务：**跑起来**、**部署起来**（若项目需要），外加必要对外说明（产品是什么、许可证、致谢、对外 API/架构摘要等）。 |
| **仅本地** | 永不进任何远程：密钥、本机写死路径工具、个人草稿（选择不入库时）。用协作侧 ignore 排除。 |

**铁律**

1. 未公开内容靠「不出现在公开树」实现；不要靠公开树 `.gitignore` 点名隐藏内部目录。  
2. 公开 ignore 只写公开消费者需要的规则（依赖、构建产物、`.env` 模式等）。  
3. 允许列表、清洁 ignore、裁剪元数据**默认不进公开树**。  
4. 根目录协作用 `AGENTS`（若有）默认只留协作面；公开侧以 README / LICENSE / 必要对外文档为准。  
5. 「部署起来」按用户确认的形态准备（容器 / 可执行包 / 直接进程 / 静态分离 / 交付包 / **不适用**）；**不默认只能 Docker**，无部署需求则跳过并写明。

## 2. 执行步骤（照做）

### 第 0 步 · 目标与简化分支（停问）

先用 1～2 问对齐（有现成答案可复述确认，勿重复盘问）：

1. 是否需要**裁剪**公开面？（要瘦子集 / 只要全量开源同内容 / 只要交付包 / 尚不确定）  
2. 公开用途是否仍为「跑起来 +（如需要）部署起来 + 必要对外说明」？有无额外要公开的（如规范包、评测集）？

| 用户意向 | 走法 |
| --- | --- |
| 全量开源、两端同内容 | **镜像**：跳过允许列表；仍做密钥/PII 与正文卫生；确认 remote/推送策略后结束 |
| 只要一次性源码/目录包 | **交付包**：做路径三分表 + 正文扫描 + 核对 → 打清单/ZIP；可不建第二 git 史 |
| 要瘦公开面（分远程或同仓分支等） | 走第 1～7 步完整配置 |
| 不确定 | **停问**，勿默认选分远程或 Docker |

### 第 1 步 · 探查

- 工作区结构、README、构建/运行/部署相关文件（有什么写什么）。  
- 本机提交/推送/更新入口（若有）；已有 remote/分支名（原样记录，不改名除非用户要求）。  
- 是否已有：允许列表、公开用 ignore、README 协作段标记、双 remote / 公开分支、其它面相关配置。  
- 项目类型粗判（应用 / 库 / 文档 / 单体 / 多包等）→ 影响默认拟公开集；拿不准列入不确定。

### 第 2 步 · 拓扑与部署形态（停问）

- 非镜像/非纯交付包：按附录 A 列选项与一句利弊 → **停问用户选择**（可组合）。  
- 确认部署形态（可多选并标默认，或「不适用」）。  
- 无第二托管地址、无公开远程、或远程名冲突 → **问用户**要新建/复用/改名哪一侧，禁止臆造托管商与 URL。

### 第 3 步 · 路径与文档分面（硬）

产出三类表：

| 类 | 含义 |
| --- | --- |
| 拟公开 | 跑起来 /（如需）部署起来 / 必要对外说明所需 |
| 拟剥离 | 过程文档、档案、本机一键/凭据脚本、内部钩子、协作 AGENTS、裁剪元数据等 |
| 不确定 | 灰区（见下）— 必须问或表内勾选 |

**常见不确定（示例，非穷尽）**：半对外设计/ADR；评测基线；演示账号说明；测试夹具是否含业务数据；README 是否保留第二托管或内网链；是否公开脱敏后的更新脚本；多包仓哪些包进公开；示例配置是否仍含真实主机名。

对**每一拟公开文本文件**做附录 C 扫描 → 夹带问题表（文件 | 信号 | 建议 A/B/C/D）。  
默认口径见附录 B；仍须用户确认增减。

### 第 4 步 · 出示【公开面核对】→ 等待确认

用 §3.1 填实。确认前**不落盘、不推送、不改正文**。  
可选：另附【公开面优化建议】（与核对表分离；默认不实施）。

### 第 5 步 · 落盘（仅按确认结果）

在协作面写入（**路径/目录名自定**，推荐可集中在单一元数据目录；写入 §3.3）：

- 允许列表（镜像模式可省略）  
- 公开用清洁 ignore 正文（导出时作为公开树 `.gitignore`）  
- README：优先**一份 README + 协作段标记**（导出去掉）。推荐标记（可改，须在 §3.3 写明）：`<!-- public:omit -->` … `<!-- /public:omit -->`  
- 拓扑相关 git 配置（按用户所选；无用户给定的 URL/remote 名则停问）

元数据目录与允许列表文件本身默认不进允许列表。

### 第 6 步 · 试导出 / 预览 → 再确认 → 才推送

- 有项目自带的导出/同步入口：确认后调用；**无则**按允许列表列出将生成的公开文件集，或给出最小导出步骤/草案脚本，仍须确认。禁止假定外部管理仓命令存在。  
- 出示【导出预览】（§3.2）。  
- 用户再次确认后才：推公开 / 仅本地导出 / 打交付包 / 取消。  
- 遵守附录 D（协作工作树外导出；禁止用公开 tip 覆盖协作默认分支再推协作侧）。

### 第 7 步 · 完成

填实 §3.3；本文使命结束。若存在「环境更新/发布」脚本：应拉取**公开目标**；若仍拉全量协作默认分支 → 列入待确认请用户改（无此类脚本则写「不适用」）。

## 4. 改公开范围时（缩略）

复述现行 §3.3 → 重做第 3～6 步 → 确认后落盘/推送。  
日常：运行/部署步骤本身变更，或用户已确认的夹带处理需要动公开段时，只改公开可见 README（有标记则只改公开段）。只改协作过程文档：不动允许列表。质量类改动仍走【公开面优化建议】→ 用户采纳后再做。

## 附录 A · 拓扑选项（并列；须用户选）

| 模式 | 要点 | 复杂度 |
| --- | --- | --- |
| 分远程 | 协作远程全量；公开远程仅子集。托管商与 remote 名由用户指定 | 中 |
| 同仓分支 | 同一 remote：协作全量分支 + 公开子集分支 | 中 |
| 外置协作 | 应用仓偏公开；协作文档在 Wiki/其它私有仓 | 低（仓内） |
| 交付包 | 不维护第二 git 史；按清单打 ZIP/目录 | 低～中 |
| 镜像同内容 | 两端同一文件集；仍须密钥/PII 卫生 | 低 |

若项目旁路另有自动化且只支持部分拓扑：复述「当前能力 = …」，未支持的选项说明限制并停问；**不要假装已支持**。无旁路自动化则纯按本文 + 本项目脚本/手工步骤执行。

## 附录 B · 默认路径口径（仍须确认）

**通常拟公开**：可运行/可构建所需源码与依赖清单；与形态匹配的最小说明与示例配置（无真实密钥）；对外 README；LICENSE / THIRD_PARTY / 必要对外变更说明；用户确认后可公开的规范/模板包目录。

**通常拟剥离**：过程文档树、档案、会话上下文、内部交接与客户原件；本机一键/凭据脚本；绑定私有环境的更新/发版脚本（公开侧用通用步骤，或用户确认后公开脱敏版）；裁剪元数据；协作专用 AI 入口全文。

**原则**：公开树给可复制的通用步骤与示例；机器特化路径/账号/钩子留协作面。库/文档等无「部署」时不要硬凑编排文件。

## 附录 C · 正文夹带（允许路径仍须扫）

| 信号 | 风险 |
| --- | --- |
| 指向过程文档树、档案、内部交接的链接或路径 | 公开死链 + 暴露内部结构 |
| 本机一键 / 特化运维脚本入口 | 公开树无此文件，误导使用者 |
| 「仅协作」「勿提交」「内部」等流程套话堆砌 | 噪音；可能暗示未公开流程 |
| 向公开读者解释「双面 / 协作面 / 公开面」机制，或 clone/安装注释写「公开面」等面术语 | 对访客无用；暴露内部工作方式 |
| 公开段保留第二托管徽章/链接，或默认引导克隆协作全量仓 | 与裁剪目标矛盾；把协作入口当成对外默认入口 |
| 真实主机名、内网 IP、客户名、未脱敏样例 | 泄密 |
| 将「全量克隆协作侧」写成对外默认入口 | 与裁剪目标矛盾 |

处理（输出给用户勾选，勿擅自定稿）：

- **A** 移入「仅协作」标记块（导出去掉）  
- **B** **最小改写**：去掉夹带或改为公开可用的现行步骤（不提及缺失文件、不讲解分面机制）；禁止借此做结构/文案/排版优化  
- **C** 从本次公开范围排除该文件  
- **D** 保持原样（须用户明示接受风险）

文案结构、徽章数量、开源习惯等提升 → 不进本表；写入【公开面优化建议】由用户另选。第二托管是否进 omit 属夹带/灰区，先表内确认，勿当成「质量优化」擅自改。

## 附录 D · 导出机械卫生

1. 仅按允许列表进入公开树；元数据与清单本身不得出现在公开树（镜像模式除外）。  
2. 公开 `.gitignore` 用清洁正文，不得含仅协作路径字样。  
3. README 标记导出后不得残留；不得残留仅协作入口；公开正文不得残留向访客解释分面机制的句子（以附录 C 为准）。  
4. 协作面根 AGENTS（若有）默认不拷入公开树。  
5. 密钥、真实 PII、内网独占地址不得进入应公开的提交。  
6. 公开目标曾有全量历史时：过滤推送不够；是否清史/轮换密钥须用户确认，并知会依赖该历史的环境。  
7. **协作 tip 隔离**：导出/同步在协作工作树外进行（临时目录或独立 clone）。禁止把公开 tip checkout/reset 到协作默认分支再推协作侧。推协作侧前 HEAD 须与协作远程对应分支同史；结束后协作仓 HEAD 与同步前一致。  
8. 启用裁剪后：协作推全量；公开推**导出树**。强推、清史、改默认分支须先用户确认。
