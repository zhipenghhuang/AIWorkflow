# 协作面与公开面

把本文发给**任意项目**里的 AI，说「按协作面与公开面配置」或「配置公开面 / 双面 / 开源面」即可。  
AI 读本文后：**先探查项目实况并分析择优** → 输出【公开面核对】（含主推结论）请用户确认 → **仅不确定或不可逆处才停问** → 确认后再落盘。  
**独立通用**：不依赖、不假定某一托管商、某一多仓管理仓库、某一脚本名或固定目录名。拓扑、路径、元数据、同步入口由**项目实况分析 + 用户确认**决定。旁路管理仓（若本机另有）**仅作实现参考**；未接入则按附录 F 在本项目落地同步能力。  
**一次配好**：落盘后日常真源是**项目内**允许列表 / 清洁 ignore / README 裁剪 / remote·分支 / §3.3 / §3.5 薄规则 / **可执行的公开同步入口**；配完后日常会话**只读这些项目文件**，不必再打开本文。

**执行要求（给 AI）**

1. **先探查分析择优、后动手**：未出示【公开面核对】、未获用户确认，不得改 remote/默认分支、不得推公开目标、不得强推、不得重置公开史；不得改允许列表 / ignore / README 标记 / 拟公开正文。  
2. **少问、主推（硬）**：能从仓库结构、已有 remote/清单/脚本、构建与部署文件判断的，**自行择优写入核对表（一项主推 + 一句依据）**，勿把附录选项整表甩给用户勾选。仅当信息不足、多解等价、或涉及新建托管地址/改默认分支/强推/清史等不可逆项时，**一次一问**。与同仓「开发/正式分支」文档同一交互口径。  
3. **本文范围（硬）**：只做协作面与公开面的**路径划分**、拓扑与同步入口落地，以及对拟公开正文的**协作向夹带**扫描（附录 C）。夹带处理（A/B/C/D）须用户确认后再实施；**B 仅为去掉夹带、使公开步骤不指向缺失文件的最小改写**，不得扩大为全文重写。  
4. **公开正文不讲分面机制（硬）**：公开可见正文按**普通对外说明**来写（是什么、怎么用、许可证等）。**双面 / 协作面 / 公开面**等机制说明、仅协作入口、默认指向协作全量仓的第二托管徽章或克隆说明 → 默认进 omit 块或拟剥离，列入夹带表请用户确认；**禁止**在公开段向访客解释分面机制。  
5. **禁止顺带质量改动**：不得在分面任务中擅自做 README/文档的文案优化、结构调整、徽章与排版、「更高质量开源仓」类改动。  
6. **公开面优化建议（可选、分离）**：可另附【公开面优化建议】，**仅输出供用户勾选**；未采纳不得动手。与核对表分开。  
7. **文档必查**：对拟进公开面的文本做附录 C 扫描；路径在允许列表中 ≠ 可原样公开。  
8. **三分表**：拟公开 / 拟剥离 / 不确定。不确定**不得静默归类**；阻塞项一次一问，非阻塞可表内勾选。  
9. **对用户只给结论 + 待确认项**；不把修改方案/对话过程写入项目正式文档。  
10. **正式正文只写现行**：删除即移除；不写「已废弃/不要再用」类留痕。  
11. **按实况裁剪**：库/工具/文档仓/无服务端等 → 「部署起来」或整类路径标「不适用」并一句理由写入核对表；禁止按某一技术栈臆造文件。  
12. **已有配置先复述**：已有允许列表、双 remote、公开分支、同步入口时，先读出现行再问是否改；无则从零起草并主推落点（如元数据目录名）。勿假定固定目录名未确认就落盘。  
13. **配完必须可日常使用（硬）**：填实 §3.3；写入 §3.5；**§3.3「公开同步入口」不得长期为空**。入口由 AI **按实况择优**写入核对表请确认（见第 2 步），不向用户摊「三选一菜单」。声明「日常只维护项目内配置与薄规则 + 走同步入口」。

## 1. 概念（现行）

| 面 | 是什么 |
| --- | --- |
| **协作面** | 团队日常真源：完整工作树（源码 + 过程文档 + 规范/档案 + 本机入口等）。可以很大。 |
| **公开面** | 有意裁剪后的派生视图（或镜像同内容）。默认只服务：**跑起来**、**部署起来**（若需要），外加必要对外说明（产品是什么、许可证、致谢、对外 API/架构摘要等）。 |
| **仅本地** | 永不进任何远程：密钥、本机写死路径工具、个人草稿（选择不入库时）。用协作侧 ignore 排除。 |

### 1.1 三个易混概念（分开记；能判则写入核对表，勿三项都问）

| 概念 | 是什么 | 不是什么 |
| --- | --- | --- |
| **部署形态** | 应用**怎样跑起来/部署起来**（进程怎么起、要不要容器/静态资源等）。用来决定公开树里**要不要、要哪些**运行/编排文件。库/文档仓常为**不适用**。 | 不是 git 怎么分面，也不是同步脚本叫什么。 |
| **公开拓扑** | 协作真源与公开目标在 git 上**怎么摆**（分远程 / 同仓分支 / 镜像 / 交付包等）。见附录 A。 | 不是服务器上的进程形态。 |
| **公开同步** | 把允许列表导出树**更新到公开目标**的动作（项目内脚本或附录 F 步骤）。 | 不是「环境更新/上线」本身；上线是否跟公开 tip 另见「运行环境拉取对象」。 |

**部署形态（供 AI 按实况择优；写入核对表待确认）**

| 取值 | 含义（现行） | 对公开路径的影响 |
| --- | --- | --- |
| 单进程 / 直接跑 | 安装依赖后启一个进程或一组进程 | 依赖清单、启动说明、必要配置模板 |
| 容器 | 镜像构建 + 编排（如 Compose） | Dockerfile / compose 等（有则拟公开，无则不臆造） |
| 静态站点 | 构建产物由静态服务器或对象存储托管 | 构建命令与产物说明；不一定公开服务端 |
| 可执行包 / 安装包 | 发布二进制或安装包 | 打包说明与校验方式；源码是否进公开另析 |
| 不适用 | 库、文档、纯规范等无「部署」 | 不要硬凑编排文件；公开侧重跑通示例/说明 |

### 1.2 铁律

1. 未公开内容靠「不出现在公开树」实现；不要靠公开树 `.gitignore` 点名隐藏内部目录。  
2. 公开 ignore 只写公开消费者需要的规则（依赖、构建产物、`.env` 模式等）。  
3. 允许列表、清洁 ignore、裁剪元数据**默认不进公开树**。  
4. 根目录协作用 `AGENTS`（若有）默认只留协作面；公开侧以 README / LICENSE / 必要对外文档为准。  
5. 「部署起来」按**择优并经用户确认的部署形态**准备；不适用则跳过并写明。  
6. 协作推全量；公开推**导出树**（镜像模式除外）。同步遵守附录 D + F。  
7. **运行环境拉取对象**：能从现有环境更新脚本判断则写入实况；仅当用户确认「上线跟公开 tip」时才写公开目标；生产跟协作正式分支或其它基线 → 记实况或「不适用」，**勿默认改成拉公开**。

## 2. 执行步骤（照做）

### 第 0 步 · 目标对齐

先探查（可与第 1 步合并）：已有允许列表/双 remote/用户口令/README 意图。能判断则直接主推简化分支；**仅无法判断时**一问（裁剪瘦子集 / 镜像同内容 / 交付包）。有现成答案只复述确认，勿重复盘问。

| 主推或用户意向 | 走法 |
| --- | --- |
| 全量开源、两端同内容 | **镜像**：跳过允许列表；密钥/PII 卫生；择优同步/推送方式写入核对表后确认即可结束 |
| 只要一次性源码/目录包 | **交付包**：三分表 + 夹带 + 核对 → 清单/ZIP；同步入口主推「打交付包步骤」 |
| 要瘦公开面（已有或拟建公开子集） | 走第 1～7 步完整配置 |
| 仍不确定 | **停问一次**，勿默认选分远程或某一部署形态 |

公开用途默认按「跑起来 +（如需）部署起来 + 必要对外说明」写入核对表；实况无部署则标不适用。有额外要公开的（规范包、评测集等）从仓库与口令判断，拿不准列入不确定。

### 第 1 步 · 探查

- 工作区结构、README、构建/运行/部署相关文件（有什么写什么）。  
- 本机提交/推送入口；已有 remote/分支名；是否已有允许列表、公开 ignore、README 协作段标记、公开同步入口、旁路管理仓能力。  
- 项目类型粗判 → 拟公开默认集与部署形态是否「不适用」。

### 第 2 步 · 拓扑、部署形态、同步入口（择优写入核对表）

对每一项：**分析 → 一项主推 + 一句依据 → 写入【公开面核对】**；能判则不问。旁路工具只支持部分拓扑时：在主推中避开未支持项并写明限制，**不要假装已支持**。

- **拓扑（附录 A 供参照，勿整表甩问）**：已有双 remote 且内容差 → 主推分远程；仅单 remote 且已有公开子集分支 → 主推同仓分支；口令只要包 → 交付包；两端同内容 → 镜像。  
- **部署形态（§1.1 表供参照）**：按仓库实有编排/启动方式择优；库/文档等主推「不适用」。  
- **公开同步入口（必有归宿；择优规则）**：  
  1. 已有可用同步脚本/口令 → **主推复用**；  
  2. 无入口且为瘦公开、需重复同步 → **主推**按附录 F 落本项目最小脚本（路径一并主推，常见元数据目录下）；  
  3. 无入口且交付包/极少同步 → **主推**把附录 F 步骤写入项目维护说明（手工）；  
  4. 旁路管理仓已有等价同步且项目在用 → **主推**填该入口。  
  禁止假定外部命令存在；禁止向用户摊开①②③菜单代替分析。  
- **缺公开托管 URL、remote 名冲突、须新建仓库** → **停问**；禁止臆造 URL。

### 第 3 步 · 路径与文档分面（硬；瘦公开 / 交付包）

| 类 | 含义 |
| --- | --- |
| 拟公开 | 跑起来 /（如需）部署起来 / 必要对外说明所需 |
| 拟剥离 | 过程文档、档案、本机一键/凭据、内部钩子、协作 AGENTS、裁剪元数据等 |
| 不确定 | 灰区—必须问或表内勾选 |

**常见不确定**：半对外 ADR；评测基线；演示账号；测试夹具是否含业务数据；README 第二托管或内网链；脱敏后的更新脚本是否公开；多包仓范围；示例是否含真实主机名。

对每一拟公开文本做附录 C 扫描 → 夹带表（A/B/C/D）。默认口径见附录 B。

### 第 4 步 · 出示【公开面核对】→ 等待确认

用 §3.1 填实。确认前**不落盘、不推送、不改正文**。  
可选：另附【公开面优化建议】。

### 第 5 步 · 落盘（仅按确认结果）

在协作面写入（路径用户确认；瘦公开推荐集中元数据目录，常见名 `.public/` 须确认）：

- 允许列表（镜像可省略）  
- 公开用清洁 ignore 正文（导出时作为公开树 `.gitignore`）  
- README：一份 + 协作段标记（导出去掉）。推荐：`<!-- public:omit -->` … `<!-- /public:omit -->`（可改，写入 §3.3）  
- 拓扑相关 git remote（按用户所给 URL/名）  
- **公开同步入口**：按第 2 步选择落盘脚本或把附录 F 步骤写入项目内维护说明  

元数据目录与允许列表默认不进允许列表。

### 第 6 步 · 试导出 / 预览 → 再确认 → 才推送

- 调用本项目同步入口的**预览/dry-run**（若有）；否则按允许列表列出公开文件集并走附录 F 至「预览」为止。  
- 出示【导出预览】（§3.2）。  
- 用户再次确认后才：推公开 / 仅本地导出 / 打交付包 / 取消。  
- 遵守附录 D（协作工作树外导出；禁止用公开 tip 覆盖协作默认分支再推协作侧）。

### 第 7 步 · 完成

填实 §3.3（含同步入口路径或「见某段手工步骤」）；写入 §3.5；向用户声明日常用法见 §4。  
若有环境更新脚本：仅当 §3.3「运行环境拉取对象」为公开目标时，核对是否已指向公开 tip；否则保持实况并写「不适用/跟其它基线」。

### 3.5 日常薄规则（配完必须写入项目）

将下列正文写入 §3.3「日常薄规则落点」（尖括号换成本项目实值）。日常 AI **只读此段 + 允许列表 + 同步入口**，不再检索配置用长文。

```text
## 公开面（日常）

- 配置真源：允许列表 `<路径或镜像>`；README 协作段标记 `<如 public:omit>`；公开 ignore 源 `<路径或无>`；公开发布目标 `<remote/分支或交付说明>`；同步入口 `<脚本或手工步骤位置>`。
- 日常开发：在协作真源提交并推送全量即可；**不必**每次推公开。
- 触发检查（命中任一才巡检，否则不巡检）：
  1. 新增/移动/重命名「跑起来或部署起来」可能需要的路径，或不在允许列表中的构建/运行入口；
  2. 修改已在允许列表内的说明文（尤其根 README），或公开段新增指向过程文档/档案/本机入口/仅协作脚本的链接或路径；
  3. 用户明确要求改公开范围或同步公开目标（口令如「同步公开面」）。
- 检查动作：对照允许列表做拟公开 / 拟剥离 / 不确定；扫夹带（死链、本机入口、真实主机、引导克隆协作全量、向访客讲分面等）。不确定一次一问；不得静默改清单或正文。
- 确认后：更新允许列表与（如需）omit/最小改写 → **走同步入口**更新公开目标（先预览，用户确认再推）。只改协作过程文档且不影响公开段 → 不动清单、不同步。
- 改清单/推公开/强推前：先给简短核对结论，用户确认后再执行。
```

镜像模式可将「允许列表」写为「镜像同内容」，触发检查侧重密钥/PII 与推送策略；同步入口为「推公开 remote」或项目实况。

## 附录 B · 默认路径口径（仍须确认）

**通常拟公开**：可运行/可构建所需源码与依赖清单；与**部署形态**匹配的最小编排/启动说明与示例配置（无真实密钥）；对外 README；LICENSE / THIRD_PARTY / 必要对外变更说明；用户确认后可公开的规范/模板包。

**通常拟剥离**：过程文档树、档案、会话上下文、内部交接与客户原件；本机一键/凭据；绑定私有环境的特化发版钩子（公开侧用通用步骤，或用户确认后脱敏公开）；裁剪元数据；协作专用 AI 入口全文。

**原则**：公开树给可复制的通用步骤与示例；机器特化路径留协作面。部署形态为「不适用」时不要硬凑编排文件。

## 附录 D · 导出机械卫生

1. 仅按允许列表进入公开树；元数据与清单本身不得出现在公开树（镜像除外）。  
2. 公开 `.gitignore` 用清洁正文，不得含仅协作路径字样。  
3. README 标记导出后不得残留；不得残留仅协作入口；公开正文不得残留分面机制说明（附录 C）。  
4. 协作面根 AGENTS（若有）默认不拷入公开树。  
5. 密钥、真实 PII、内网独占地址不得进入应公开的提交。  
6. 公开目标曾有全量历史时：过滤推送不够；是否清史/轮换密钥须用户确认。  
7. **协作 tip 隔离**：导出/同步在协作工作树外进行（临时目录或独立 worktree/clone）。禁止把公开 tip checkout/reset 到协作默认分支再推协作侧。结束后协作仓 HEAD 与同步前一致（或仅含用户确认的协作侧改动）。  
8. 强推、清史、改默认分支须先用户确认。

## 附录 F · 通用最小同步（不依赖旁路管理仓）

配瘦公开且项目尚无同步入口时：由 AI **择优**落地——默认主推项目内脚本（可重复）；交付包或极少同步可主推维护说明中的手工步骤。路径/语言按项目实况主推，写入核对表确认。**任何推送/强推前须用户确认。**

### F.1 目标

从当前协作工作树，按允许列表生成导出目录 → 叠到公开目标 tip →（确认后）推送。镜像模式：无需导出裁剪，按约定直接推公开 remote。交付包：导出目录打 ZIP/交目录即可。

### F.2 步骤（瘦公开 · 分远程或同仓公开分支）

1. **读取配置**：允许列表路径、公开 ignore 源、README 标记名、公开 remote/分支（均来自 §3.3）。  
2. **建导出目录**：在系统临时目录（或用户指定目录）建空文件夹；**不要**在协作工作树内直接改成公开 tip。  
3. **拷贝**：按允许列表把文件/目录拷入导出目录（目录项拷整树）；跳过元数据目录与清单自身。  
4. **README**：若使用标记块，导出副本中删除标记及其间仅协作段，并去掉标记行。  
5. **`.gitignore`**：若有公开 ignore 源，写入导出目录根为 `.gitignore`（清洁正文）。  
6. **预览**：向用户列出导出顶层条目与文件数（或 diff 摘要）→【导出预览】→ 等待确认。  
7. **叠到公开 tip**（确认后）：  
   - 用独立 worktree 或临时 clone 检出公开分支（分远程则 fetch 公开 remote；同仓则检出公开分支到独立 worktree）；  
   - 用导出目录内容替换该 tip 的工作树文件（保留该 tip 的 `.git`）；  
   - 若无变更可跳过提交；有变更则提交（说明写「sync public tree」类现行摘要，由用户或约定生成）；  
   - **确认后**再 `push` 到公开发布目标。  
8. **收尾**：删除临时导出目录；确认协作工作树 HEAD 未被换成公开 tip。

### F.3 禁止

- 在协作默认分支上 `checkout`/`reset` 成公开 tip 再推回协作远程。  
- 未确认的强推、清史、改默认分支。  
- 假定某管理仓、某固定脚本名已存在。

### F.4 项目内脚本（主推落盘方式）

核对确认后，将 F.2 做成本项目脚本（路径按主推，例如元数据目录下 `sync-public`），§3.3「公开同步入口」填该路径。脚本须支持：**仅预览**与**确认后推送**（AI 代跑须走参数，禁止无人确认推送）。

旁路管理仓已有等价同步：§3.3 填该入口即可，仍须满足附录 D；本文不绑定其文件名或安装方式。
