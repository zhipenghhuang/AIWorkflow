# 协作面与公开面（通用可执行说明）

> **读取级别：可选专题（默认不读）**  
> 复制到任意项目后，用户点名「协作面 / 公开面 / 双面 / 开源面 / 导出公开 / 同步公开」时按本文执行。  
> **通用规则**：不绑定某一托管商、某一脚本实现或某一仓库命名；拓扑与路径由用户确认后落盘。  
> **正式正文只写现行有效状态**（删除即移除；不写「已废弃/不要再用」类留痕套话）。

---

## 0. 目标与边界（先对齐再动手）

### 0.1 公开面只服务两件事

1. **跑起来**：他人按公开树内说明与示例配置，能在本机把服务启动并做基本验证（开发态或与生产同构的最小运行态均可，以 README 现行步骤为准）。  
2. **部署起来**：他人/机器按公开树内**该项目选用的部署形态**说明，能完成一次可重复部署。形态由用户确认，**不默认只能 Docker**（见 §2.4）。

另可含**必要的对外说明**（产品是什么、许可证、第三方致谢、对外 API/架构摘要等）。除此之外默认不进公开面。

**不含**（默认留协作面或统一管理侧）：本机一键 bat/专用凭据脚本、仅某一台机器写死的路径、内部发版钩子专属逻辑、过程文档与规范包实例（除非产品本身就是规范包且用户确认公开）。

### 0.2 协作面

团队日常真源：完整工作树（源码 + 过程文档 + 规范包实例 + 本机入口脚本 + 可提交上下文等）。协作面可以很大；**公开面必须是有意裁剪后的派生视图**。

### 0.3 仅本地

永不进入任何远程：密钥文件、本机写死路径的工具、个人草稿（若选择不入库）。在协作仓 ignore 中排除即可。

### 0.4 铁律

1. **未公开内容靠「不出现在公开树」实现**，不要靠公开树里的 `.gitignore` 点名「隐藏」内部目录（否则公开 ignore 会变成内部结构说明书）。  
2. 公开用 ignore **只写公开消费者需要的规则**（依赖目录、构建产物、`.env` 模式等）。  
3. **公开清单、清洁 ignore、裁剪元数据本身默认不进公开树**（避免把「裁了什么」开源出去）。  
4. 根目录协作用 `AGENTS`（若有）默认**只留协作面**；市面开源仓通常也不放 AI 协作入口文件。公开侧以 README / LICENSE / 必要对外文档为准。  
5. 凡将进入公开树的文件，除路径允许外，还须做**正文卫生**（见 §5）：允许路径里夹带的协作专用描述、本机脚本入口、内部文档链接等，一律视为风险，须分析并请用户确认处理方式。

## 1. 拓扑模式（并列；须用户选择确认）

无唯一真理。AI **先列出选项与利弊 → 用户确认选用哪一种（或组合）→ 再改配置/远程/分支**。统一管理工具可能只实现其中一部分——若项目已接入某工具，以实现与登记配置为准，但仍须向用户明示当前实现的拓扑。

### 1.1 分远程（多托管）

- 协作远程：全量主分支。  
- 公开远程：仅公开子集（常映射为公开侧默认分支）。  
- 适合：已有两个托管地址；运行环境只 clone 公开远程。  
- **托管商与本地 remote 名均不限**（Gitee / GitHub / GitLab / 自建等均可）；谁当协作、谁当公开、本地叫 `origin` 还是别的名字，均由用户指定。某统一管理工具若写死 remote 名或默认托管商，须在登记/说明里明示，不得当成通用机制。

### 1.2 同仓不同分支

- 同一 remote：例如协作全量分支 + 公开子集分支。  
- 推送时分支分流；对外默认分支可指向公开分支。  
- 适合：只维护一个托管仓，仍要隔离可见内容。

### 1.3 单公开仓 + 协作外置

- 应用 git 只保留公开面；协作文档在 Wiki / 文档仓 / 其它私有仓。  
- 适合：开源为主、过程文档本就不想进应用仓。

### 1.4 交付包 / 过滤导出

- 不维护第二 git 史；按清单打 ZIP/目录交付或发版。  
- 适合：给客户源码包、一次性导出。

### 1.5 镜像同内容（可选）

- 协作与公开推送**同一文件集**（不做裁剪）。  
- 适合：本来就要全量开源；此时无「瘦公开面」，本文 §3～§5 的裁剪清单可省略，但仍须做密钥/PII 卫生。

### 1.6 对照

| 模式 | 第二历史 | 运行环境常见拉法 | 复杂度 |
| --- | --- | --- | --- |
| 分远程 | 有（另一 remote） | 拉公开 remote | 中 |
| 同仓分支 | 有（另一 branch） | 拉公开分支 | 中 |
| 外置协作 | 无（在仓外） | 拉唯一仓 | 低（仓内） |
| 交付包 | 无 | 不依赖 git | 低～中 |
| 镜像同内容 | 可选双远程同内容 | 拉任一端 | 低 |

## 2. 公开面应有 / 不应有（默认口径）

下列为**默认建议**，落地前仍输出清单请用户确认增减。

### 2.1 通常应进公开面

- 可运行业务源码与构建所需清单（如依赖清单、锁文件、必要的构建描述）。  
- **与选用部署形态匹配**的最小部署说明与示例配置（见 §2.4）；示例环境文件无真实密钥。  
- 对外 README（安装 / 运行 / 部署的现行步骤，对应该形态）。  
- LICENSE / THIRD_PARTY / 必要的对外变更说明（若项目有）。  
- 产品本身就是「规范/模板包」时：用户确认后可公开相应包目录。

### 2.2 通常不进公开面

- 过程文档树、档案、会话上下文、内部交接与客户原件。  
- 本机一键脚本、共用电脑凭据相关脚本、仅协作用钩子。  
- **服务器上的项目更新脚本**若绑定私有拓扑、内部钩子或本机假设：默认留协作面；公开侧用「通用部署步骤」替代（用户可确认改为公开一份**脱敏后的通用更新脚本**）。  
- 发版/备份/同步数据库等**环境特化**运维脚本（统一管理工具侧的钩子更不应塞进公开应用仓）。  
- 公开裁剪元数据目录/清单/清洁 ignore 源文件（只留协作侧）。  
- 协作专用 AI 入口全文。

### 2.3 灰区（必须单项确认）

- 「半对外」技术设计、评测基线、演示账号说明、可观测性示例配置。  
- 测试夹具是否含可识别业务数据。  
- README 中是否保留第二托管地址、内网域名、组织内部流程链接。  
- 是否公开一份「通用 `update`/发布脚本」还是只写文档步骤。

### 2.4 部署形态（并列；与 Docker 同等可选）

公开面「部署起来」按**用户确认的形态**准备材料，可多选，但 README 须写清默认推荐哪一种。AI 不得默认「只有 Docker 才算部署」。

| 形态 | 公开面通常需要 | 通常仍留协作面 |
| --- | --- | --- |
| 容器编排 | 编排文件、Dockerfile、`.env.example`、端口/卷说明 | 机器专属 compose override、私有 registry 账密 |
| 可执行包（如 jar/war） | 构建命令、产物相对路径约定、JVM/运行参数示例、反向代理示例片段 | 某一主机上的绝对路径启停脚本、内网制品库账号 |
| 解释型进程（如 node/python 直接跑） | 运行时版本、安装依赖命令、进程管理示例（systemd unit **示例**或等价） | 已填好真实 User/路径的生产 unit、机器证书 |
| 静态前端 + 后端分离 | 前端构建产物约定或构建步骤、后端同上之一 | CDN/证书自动化私货 |
| 仅交付包 | 按清单打出的目录/ZIP + 内附 README | git 历史本身 |

原则：公开树给出**可复制的通用步骤与示例配置**；把「这台服务器上已经改过的真实路径/账号/钩子」留在协作面或统一管理侧。

## 3. 清单与元数据（协作侧）

启用裁剪时，在协作面维护机器可读配置（路径/文件名自定，推荐集中在单一元数据目录，且**该目录默认不进公开树**）：

| 角色 | 内容 |
| --- | --- |
| 允许列表 | 一行一路径；目录以 `/` 结尾表示整树；`#` 注释；未列出 = 不进公开 |
| 公开用 ignore 正文 | 导出时作为公开树 `.gitignore`；禁止点名仅协作/仅本地路径 |
| （可选）正文裁剪标记 | 如在唯一 README 中用成对标记包住「仅协作」段落，导出时去掉标记块 |

**不要**再维护多份易漂移的「公开专用 README / 公开专用 AGENTS」除非用户明确要求；优先：**一份 README + 协作段标记裁剪**，AGENTS 留协作面。

## 4. 导出 / 同步时的机械卫生（实现侧须保证）

无论手工还是脚本：

1. 仅按允许列表进入公开树；元数据目录与清单文件本身不得出现在公开树。  
2. 公开 `.gitignore` 使用清洁正文，不得含仅协作路径字样。  
3. 若使用 README 协作段标记：导出后公开 README 不得残留标记，且不得残留仅协作入口（本机脚本名、过程文档树链接等——以 §5 扫描为准）。  
4. 协作面根 AGENTS（若有）默认不拷入公开树。  
5. 密钥、真实 PII、内网独占地址不得进入应公开的提交；协作面也应脱敏。  
6. 若公开目标上曾有全量历史：仅靠之后过滤推送不够；须按用户确认做历史清理/轮换密钥，并知会依赖该公开史的运行环境（可能无法快进，需对齐到公开尖端）。  
7. **协作 tip 隔离**：公开导出/同步必须在**协作工作树之外**进行（独立临时目录或独立 clone）。禁止把公开分支 tip `checkout`/`reset` 到协作默认分支上再推协作远程。推协作远程前，本地 HEAD 须与协作远程对应分支有共同历史；同步结束后协作仓 HEAD 须与同步前一致。

## 5. 正文级风险（允许路径仍可能「夹带」）

**路径在允许列表中 ≠ 可以原样公开。** AI 必须对拟公开的文本类文件做扫描，至少关注：

| 信号 | 风险 |
| --- | --- |
| 指向过程文档树、档案、内部交接的链接或路径 | 公开死链 + 暴露内部结构 |
| 本机一键脚本 / 运维脚本入口 | 公开树无此文件，误导使用者 |
| 「仅协作」「勿提交」「内部」等流程套话堆砌 | 噪音；且可能暗示未公开流程 |
| 真实主机名、内网 IP、客户名、未脱敏样例 | 泄密 |
| 与允许列表矛盾的「全量克隆协作远程」为主说明 | 把协入口当成对外默认入口 |

处理建议（输出给用户勾选，勿擅自定稿）：

- A. 将段落移入「仅协作」标记块（导出自动去掉）  
- B. 改写为公开可用的现行步骤（不提及缺失文件）  
- C. 从本次公开范围排除该文件  
- D. 保持原样（须用户明示接受风险）

## 6. 点名执行协议（给 AI · 可直接照做）

**触发词示例**：协作面、公开面、双面、开源面、导出公开包、同步公开、设置公开范围、检查公开卫生。

### 6.1 禁止

- 未出示分析、未获用户确认，不得推公开目标、不得改默认分支、不得强推、不得重置公开史。  
- 不得把「修改方案 / 本次对话过程」写入正式项目文档；对用户的回复用**结论 + 待确认项**。  
- 不得只实现「分远程」一种口径却不提其它拓扑；须列出选项请用户选。

### 6.2 步骤

1. **澄清目标**：公开面用途确认是否仍为「跑起来 / 部署起来 + 必要对外说明」。若用户要扩大（如公开过程规范包），记入待确认。  
2. **拓扑**：按 §1 列出适用选项与简要利弊 → **停问用户选择**（可多选组合）。若项目已有统一管理工具登记，先读登记再复述「当前实现 = …」，问是否更改。  
3. **草案允许列表**：扫描工作区，产出三类表：拟公开 / 拟剥离 / 不确定（灰区）。  
4. **正文扫描**：对拟公开文本做 §5 扫描，产出「夹带问题」表（文件、信号、建议 A/B/C/D）。  
5. **出示【公开面核对】**（模板见 §7）→ **等待用户确认或勾选修改**。  
6. **落盘**：仅按确认结果写允许列表、清洁 ignore、README 标记/改写、拓扑相关 git 配置。  
7. **试导出 / dry-run**（若有工具则用工具；否则按清单说明将生成的公开文件集）→ 再出示一次简短【导出预览】（路径列表 + 是否含元数据/AGENTS/夹带项归零）。  
8. **用户再次确认**后才推送/发布/打交付包。  
9. 若公开史被重写：提醒检查依赖公开尖端的运行环境是否需对齐（非快进时的处理须用户确认）。

### 6.3 日常变更

- 改「如何运行/部署」：改公开可见的 README 现行段落；有标记裁剪时只改公开段。  
- 改协作专用入口/过程文档：只动协作段或协作路径，不进公开。  
- 改公开范围：只改允许列表（元数据留协作侧）→ 走 §6.2 第 3～8 步缩略版（至少核对 + 确认）。  
- 改根 AGENTS：默认只影响协作面；**除非用户明确要求公开 AI 入口**，否则不映射到公开树。

## 8. 落地场景：有统一管理工具 vs 独立项目自带脚本

本文复制到项目后，**不依赖**某一「多仓 deploy」仓库是否存在。按下面分支执行。

### 8.1 项目在统一管理工具下（多仓登记、统一 commit、服务器统一拉公开源）

- **是否双面、推哪一侧、运行环境拉哪一侧**以该工具登记为准；AI 更改前复述登记项并确认。  
- 公开同步若工具已提供导出/推公开命令：确认后走工具；未实现的拓扑可文档约定 + 手工导出，仍须 §6 确认门。  
- 服务器发版特化步骤优先放在**管理工具侧钩子**，避免塞进公开应用仓。  
- 若工具为 **deploy**（现行）：登记在 `surfaces.txt`（`mirror` / `split`；脚本实现拓扑为分远程 `remotes`）；公开元数据推荐 `.public/allowlist.txt` + `.public/gitignore`；README 协作段用 `<!-- public:omit -->…<!-- /public:omit -->`；公开同步走其 `Invoke-SyncPublicSurface`（临时目录、禁止改写协作 HEAD）；本机 bat/`scripts/` 与可选项目内 `update.sh` 默认不进公开清单；服务器发版特化在 deploy `hooks/`，不依赖公开仓运维脚本。整理/清查类口令由该仓 AI 按现行 `AGENTS`/`DEPLOY` 执行（无强制专用 bat）。

### 8.2 独立项目（无统一管理工具；自有提交推送脚本 + 自有服务器更新脚本）

复制本文与允许列表元数据到该项目协作面后，典型分工如下（路径名自定，须写入 §7.4）：

| 能力 | 放哪 | 公开面？ |
| --- | --- | --- |
| 本机/团队提交推送脚本 | 协作面 | 默认否（常含双面分流、凭据假设） |
| 公开子集导出并推到公开目标 | 由提交脚本在用户选「公开/两者」时调用，或单独脚本；逻辑遵循本文 §4～§6 | 脚本本身默认否；**导出结果**才是公开树 |
| 服务器更新脚本 | 协作面可保留「拉公开源 → 按形态发布」的完整版 | 默认否；公开 README 写清同构步骤。若用户要求公开脚本：须脱敏（无内网地址/账号），且与选用形态一致 |
| 允许列表 / 清洁 ignore | 协作面元数据目录 | 否 |

**独立项目上 AI「会怎么做」（结论流程）：**

1. 读本项目是否已有双面登记/允许列表；无则按 §6 起草并确认。  
2. 确认拓扑与**部署形态**（§1 + §2.4）。  
3. 扫路径与正文夹带 →【公开面核对】→ 用户确认。  
4. 落盘允许列表与 README 裁剪；**改的是协作面**。  
5. 调用（或提示用户运行）**本项目自己的**提交/公开同步入口推协作与/或公开；不假定存在外部 deploy 仓库。  
6. 服务器：更新脚本应 `fetch/pull` **公开目标**（公开 remote 或公开分支），再按形态执行（compose up / 换 jar 并重启进程 / 同步静态资源等）。脚本若仍在拉「全量协作默认分支」→ 视为配置错误，列入核对项请用户改。  
7. 无现成导出命令时：按允许列表说明手工步骤或最小脚本草案 → 仍须确认后才推公开。

### 8.3 提交脚本与公开同步的最小约定（独立项目可照此改自己的脚本）

- `mirror` 或未启用裁剪：推送内容两端（或单端）一致。  
- 启用裁剪后：协作推全量；公开推**导出树**（不是工作区全量）。  
- 交互上可提供：仅协作 / 仅公开 / 两者；默认两者须在说明里写清。  
- 任何强推、历史重写、改默认分支：必须先用户确认。
