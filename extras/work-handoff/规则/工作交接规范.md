# 工作交接规范（通用）

> **单一出处**：工作交接包的目的、结构、优先级、完成定义以本文为准；文件骨架见同级 `../模板/`。  
> **定位**：便于**工作顺利接续**的资料包。不绑定交接原因；接收方可待定。  
> **排除**：AIWorkflow 三包内跨角色交付物交接（REQ/QA/REL…）见各包 `规则/协作/协作与交接.md`，本文不管。

---

## 1. 目标与非目标

### 1.1 目标

让任意具备基本项目权限的接任者（或未来的自己）在合理时间内能够：

1. 知道**负责什么、什么时候会找上门**；  
2. 找到**系统、仓库、文档、环境**的入口；  
3. 接住**进行中的事**与未兑现承诺；  
4. 理解**为何如此设计**与常见坑；  
5. 知道**权限怎么开、密钥在哪类保管处**（不是密钥本身）；  
6. 可选地按清单做几项**演练**，证明「交得清」。

### 1.2 非目标

- 不替代人事/行政流程、资产归还、劳动合同文本。  
- 不替代日常提测/发布交接包。  
- 不要求写成小说或「交一切」；按影响面排序，允许书面标明**已知缺口 / 暂缓细化**。  
- 不把个人评价、八卦、未核实猜测写入包。

### 1.3 成功标准（包本身）

| 级别 | 标准 |
| --- | --- |
| 可发送 | `00`+`01`+`03`+索引存在；无明文密钥；待确认项已单列 |
| 标准完备 | 00～09 按项目裁剪后无空洞占位；高影响领域有地图或缺口说明 |
| 可验证（可选） | `09` 中至少 1 项高影响演练可由第三人执行并留下结果栏 |

「交接合不合格」以资料与演练为准，**不以**是否填写接收人姓名为准。

## 2. 包结构

见 `AGENTS.md` §2 目录树。文件职责：

| 文件 | 职责 |
| --- | --- |
| `00-交接包说明.md` | 封面：范围、如何阅读、默认接收说明、自检 |
| `01-职责与领域台账.md` | **主台账**：一行一项职责/领域（不是文件夹列表） |
| `02-领域知识地图.md` | 每领域一页：做什么、入口、数据、依赖、失败模式 |
| `03-进行中与待办.md` | 进行中变更、开放 PR、承诺、近期排期 |
| `04-系统资产与仓库.md` | 仓、包、环境、制品、第三方服务 |
| `05-运维发布与值班.md` | 发布/回滚/监控/值班/应急 |
| `06-联系人与协作约定.md` | 内外部协作方式与升级路径 |
| `07-隐性知识与决策背景.md` | 代码与文档写不清的 why / 坑 / 偏好 |
| `08-权限与访问位置清单.md` | 账号角色与开通/保管位置 |
| `09-验收演练清单.md` | 建议的动手验证项 |
| `交接索引.md` | 总目录与阅读顺序 |
| `附件/` | 仅外部无主副本的材料 |

**铁律**：交接包是**导航 + 摘要 + 台账**；仓库真源仍在原路径。更新真源后应回写包内链接或注明「以仓内为准，本包日期：…」。

## 3. 台账优先（对标企业实践）

### 3.1 不要只交文件夹

「几百个文件的目录」≠ 交接完成。必须以**职责/领域**为行：

| 字段 | 写什么 |
| --- | --- |
| 职责/领域 | 可触发的工作单元，如「账单服务」「每周数据核对」「发布值班」 |
| 为何重要 | 没人接住时会怎样（停摆/资损/合规/客户） |
| 影响面 | P0～P3 或 高/中/低（见 §4） |
| 触发方式 | 谁、通过什么渠道、多久一次、下次大致何时 |
| 现行资料 | 文档/runbook/看板链接 |
| 建议接手 | 姓名 **或** `待定` |
| 备份 | 可咨询的人；可无 |
| 状态 | 已整理 / 待补 / 已知缺口 |

### 3.2 领域列表怎么来

按可用性依次：

1. 用户口述的职责范围；  
2. 项目档案 / 团队文档中的模块划分；  
3. 仓库目录与 README；  
4. （可选）近期 git 作者/路径热度，用于发现「实际常动但文档没写」的面；  
5. 运维面：值班、发布、厂商接口——git 往往看不见，必须手补。

### 3.3 允许「已知缺口」

时间或信息不够时，在台账该行写 `已知缺口` + 原因 + 风险；**禁止**留空假装没有。缺口清单汇总进 `00`。

## 4. 影响面与投入顺序

对每个领域估两点：**业务/安全后果** × **近期是否仍在变**。

|  | 近期常变 | 较少动 |
| --- | --- | --- |
| **后果高** | 先写地图 + 进行中移交 + 演练项 | 先写地图 + runbook 要点 |
| **后果低** | 台账一行 + 入口链接即可 | 可标「暂缓细化」 |

生成时按此排序填 `01`/`02`/`09`，避免平均用力。

## 5. 各章内容要求（摘要）

### 5.1 进行中与待办（`03`）

必须尽量列出：开放 PR/MR、半截迁移、对别的团队的承诺、日历上已定窗口、已知故障跟进。  
每项：现状、阻塞、建议下一步、建议归属（可待定）、截止或窗口。

### 5.2 系统与资产（`04`）

仓库地址与用途、主要技术栈、环境 URL（无权限则写申请方式）、制品/镜像、云账号**项目名**（非密钥）、域名与证书**保管位置**、第三方 SaaS。

### 5.3 运维发布（`05`）

如何发版、如何回滚、谁审批（角色即可）、监控与告警入口、常见告警含义、值班与升级顺序、应急沟通渠道。

### 5.4 联系人（`06`）

内部角色与外部厂商/客户对接方式；写**业务目的与未了事项**，不写私人评价。对外名单是否入包：不确定则列入「待你确认」。

### 5.5 隐性知识（`07`）

- 看似奇怪但必须保留的行为  
- 曾尝试后放弃的方案  
- 「告警很吵但可忽略」类项  
- 客户/业务方沟通偏好（仅职业相关）  
- 「接任者最好先知道的三件事」

### 5.6 权限（`08`）

表格：系统 | 需要的角色/权限 | 开通方式或工单 | 密钥/配置保管位置 | 备注。  
**禁止**填写密码、Token、私钥正文。

### 5.7 验收演练（`09`）

每条：目标、前置权限、步骤要点、期望结果、结果栏（留空给执行人）。  
高影响领域至少建议 1 条「读文档无法替代」的动手项（如：按 runbook 走一遍预发部署演练、复现一条告警处置、独立完成一个小修复的说明级步骤）。  
无接收人时仍输出清单，标题注明「建议演练（接收人确定后执行）」。

## 6. 生成与更新纪律

1. **一次生成、可增量更新**：再跑时保留人工补丁段落（可用 `<!-- manual -->` 包裹），只刷新自动可探查部分并更新日期。  
2. **中文**正文；专有名词可保留英文。  
3. **脱敏**：客户名/个人手机等按项目惯例；不确定则「待确认是否写入」。  
4. **日期**：包目录名与 `00` 内「生成/更新日期」一致。  
5. **不要**把本规范目录自己拷进交接包；交接包是实例产出。

---

## 7. 阅读顺序（写给接任者）

推荐写在 `交接索引.md`：

1. `00` 说明 → 2. `01` 台账（先看 P0/高）→ 3. `03` 进行中 → 4. 对应 `02` 地图 → 5. `04`/`05` 按需 → 6. `07` 隐性知识 → 7. `08` 开通权限 → 8. `09` 演练。

---

## 8. 质量自检清单（生成方）

- [ ] 台账行是「职责」不是「文件名堆砌」  
- [ ] 高影响且常变的领域有地图或显式缺口  
- [ ] 进行中事项无遗漏「只有聊天里才有」的承诺（能问则问，否则标待确认）  
- [ ] 权限章无密钥正文  
- [ ] 与三包 HO 目录未混淆  
- [ ] `00` 含范围/非范围与阅读方法  
- [ ] 接收人可为空/待定，不影响包结构完整
