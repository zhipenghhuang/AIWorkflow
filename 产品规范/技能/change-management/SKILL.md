# 需求/问题受理与变更（技能 · 随包生效）

> 用于：`change` 工作流的 intake / triage / assess / apply；交付跟进中发现的变更、缺陷、新需求也转本流程。  
> 目标：用户只发需求或问题（对话/文档），流程完成定性、影响评估、决策、联动更新与回执，并给出最新产物。

## 1. 受理（intake）

- 输入形态：对话、Markdown/文本、docx/pdf（能解析则解析，不能则请用户给关键段/截图）、链接、缺陷单/平台单/备注/附件、测试报告、提测单。
- 必收：提出人/来源/日期、原始描述、期望、关联需求/PRD/AC、版本/环境/构建、证据、时间要求。
- 信息不足：一次一问至可判定；未知写「待确认」，禁臆造。
- 去重：同一问题合并，重复项指向主条目；一条一档，生成 `RQ/CR/BUG-…` 编号。
- 落 `产品/{版本或主题}/受理-{主题}-{yyyyMMdd}.md`（模板 `规则/模板/受理与处置模板.md`）。

## 2. 分诊判定树

| 分类 | 判定 | 去向 |
| --- | --- | --- |
| 0→1 新产品/新业务 | 无产品定义/立项，需验证问题、市场、用户 | 转 `workflows/new-product.yaml`（discover→go→define） |
| 新需求 | 已有产品/版本，不在已定稿范围/需求池 | 需求池 `R-xx` → 优先级 → 本期/下期/不做 |
| 需求变更 | 改动已定稿 PRD 的范围/AC/规则/计划 | 变更单 `CR-xx` → `confirm_change` |
| 答疑 | 口径已有，只是理解问题 | 书面答复；若影响基线则升级为变更 |
| 产品缺陷 | 实现符合 PRD/设计，但口径本身不合理/有风险 | 产品决策：立即修 / 下版 / 不修 |
| 实现缺陷 | 与 PRD/设计不一致（未做/做错/缺段） | 退回开发/测试，不改 PRD |
| 技术不确定 | 技术方案/可行性/选型不明 | 开发 ADR/Spike；涉及产品取舍回产品 |
| 重复/无效/信息不足 | 重复、误报、缺关键证据 | 合并 / 关闭 / 补充信息 |

**判定纪律**：有设计文档可引时，现网 ≠ 资料 → 实现缺陷；现网 = 资料但挡主路径或有风险 → 产品缺陷。无设计文档可引 → 默认实现缺陷（写「无设计文档·现网依据」）。拿不准 → 补充信息，禁猜。

### 2.1 产品缺陷（交产品确认）

必须同时具备：

1. 关联的 PRD/设计原文（文件 + 章节/节点，真实可回查）；
2. 现网/测试的实际表现与证据（截图/日志/接口/测试报告/缺陷单）；
3. **相符证明**：写明实现与 PRD/设计一致的具体事实，以及为什么该口径导致主路径受阻或有风险；
4. 开发/测试的建议方案或待确认点（如有）。

没有相符证明 → 不得判产品缺陷；按实现缺陷或补充信息处理。

### 2.2 处置选项（产品缺陷）

| 选项 | 动作 | 输出 |
| --- | --- | --- |
| 立即修（本期） | 变更单（类型=缺陷修复）+ PRD/AC 更新 + 重审（如实质）+ UAT 重验 | 变更单 + 受理单 + 最新 PRD/UAT + 开发回执 |
| 下版 | 需求池 + 路线图 + 通知 | 需求池条目 + 产品计划 §2 + 回执 |
| 不修 | 记录理由、风险、接受人；必要时更新 PRD 说明 | 受理单 §5/§7 + 回执 |
| 退回开发（实现缺陷） | 给依据与复现/验收要求，不改 PRD | 受理单 + 开发/测试回执 |
| 补充信息 | 一次列清缺什么、谁补、截止 | 受理单 §2/§5 |

## 3. 影响评估（assess）

- 需求/范围：改了什么？影响哪些功能/模块/接口/页面？
- 验收标准：哪些 AC 变化？是否需要 UAT 重验？
- 成本/排期：工作量增减？里程碑是否移动？
- 技术/测试风险：契约/数据/权限/安全/合规是否变化？回归范围多大？
- 回滚：出问题怎么退？
- 依赖/通知：开发/测试/运营/客服谁需要知道？谁给出回执？

同时列出**受影响产物**：PRD 正文/AC、原型、评审记录、交付计划、产品计划、需求池、UAT、发布检查/GTM、产品计划 §7/资料索引/activeContext。

## 4. 处置决策（decide）

- 结论只有：接受 / 拒绝 / 延后 / 下版 / 不修 / 退回开发 / 补充信息。
- 改动已定稿基线 → 变更单 + `confirm_change`；新需求/范围变化 → `confirm_scope`；影响版本范围/里程碑/KPI → 叠加 `confirm_plan`。
- 产品缺陷出示：分类依据 + 相符证明 + 影响 + 处置选项 + 建议；批准后才实施。
- 无变更单不实施；口头变更一律先落单。

## 5. 联动落地（apply）

按受理单 §6 逐项更新，只写现行有效；每项标「已更新 / 不适用 / 待补」：

| 产物 | 必须检查 |
| --- | --- |
| PRD | 正文、§13 AC、§16.4 变更记录；状态改「修订中」或「已定稿」 |
| 原型/交互 | 涉及页面/状态/文案/校验时同步 |
| 评审记录 | 实质变更 → 独立重审；记录缺口与结论 |
| 交付计划 | 范围、任务、里程碑、发布窗口 |
| 产品计划 | §0 状态、§2 路线图（下版）、§8 决策/变更记录 |
| 需求池 | R-xx 状态、版本、优先级、搁置原因 |
| UAT | 受影响 AC、问题清单、验收结论、发布前置 |
| 发布检查/GTM | 回滚、公告、客服、监控、对外承诺 |
| 通知/回执 | 开发/测试/运营/客服 + 需要做什么 + 截止；缺陷在平台则回写处置结论/附件，不可用则由用户转贴 |
| 产品计划 §7 / activeContext | 最新版本/产物路径、当前焦点、下一步 |

变更单与受理单互相链接；旧版归档，不堆「最终版/最终版2」。

## 6. 重审与验证

- **实质变更**：范围、AC、状态机、权限、数据规则、NFR、版本目标变化 → `reviewer-agent` 重审 + `confirm_prd`；未通过不得标「已定稿」。
- **非实质**：错别字、无行为变化的表述、纯答疑 → 不重审，但要在受理单记录。
- **验证**：影响 AC/UAT/发布 → 受影响项重验并更新 UAT；未 UAT/未发布 → 测试报告/回归/冒烟证据；不适用写原因。
- 未验证不得关闭；关闭后更新产品计划 §0/§7、资料索引、activeContext。

## 7. 输出

```text
【任务收尾】
1. 完成了什么：受理编号 / 类型；分诊依据 / 结论；处置（接受/拒绝/延后/下版/不修/退回/补充）；联动变更（PRD/AC、原型、评审、交付计划、产品计划、需求池、UAT、发布检查）；最新产物路径
   可直接复制汇报：
   {受理编号/主题}已{处置结论}。覆盖{受影响产物 N 项}，已更新 {n} 项（{P%}）；{核心业务影响}；{未决/风险一句}。结论：{已关闭/待验证/待回写}。
```

第 2～6 点严格按 `../AGENTS.md` §2 输出（改了哪些文件 / 如何验证 / 假设与未决项 / 风险 / 下一步），不得省略字段。

## 8. 常见坑

- 把实现缺陷甩成产品缺陷（没有相符证明就改 PRD）；
- 只出变更单，不更新 PRD/AC/计划/UAT，旧文档继续被使用；
- 变更后不重审、不重验，却仍标「已定稿/可发布」；
- 新需求绕过需求池和优先级，直接塞进本期；
- 产品缺陷只写「已确认」，没有处置结论、目标版本和回执；
- 拒绝/延后不留原因、不接受人、不回需求池。
