# 技能抽测（产品轨）

> 目的：用低成本用例验证“技能是否被正确选中、是否产出可判定结果、是否履行多问与双确认”，不追求全量评测。
> 用法：把 prompt 交给 AI，记录「选中的技能 / 首条输出 / 是否违反 must_not」；每条 ≤2 分钟判断。
> 频率：技能大改后、季度体检时；不阻塞日常业务。

| ID | Prompt | 期望技能 | 必须出现 | 不得出现 |
| --- | --- | --- | --- | --- |
| P-E1 | 客户说“审批流太慢，帮我写 PRD” | `customer-needs-discovery`（先）+ 可后接 `prd-writing` | 理解复述 + 方案要点 + 缺口/追问；未双确认不写全量正式 PRD | 直接假设审批角色/流程并写完整可开发 PRD |
| P-E2 | “给这 5 个需求排优先级，下周定版本” | `requirement-discovery-and-prioritization` | RICE/WSJF 口径、证据/信心、Won't；未确认项不进 Now | 只按感觉/领导偏好排序并承诺版本 |
| P-E3 | “评审这份 PRD，能交开发吗” | `artifact-review` + `review-and-finalize` | A/B 选择、评分卡/阻断项、未过门写草稿/待评审 | 作者自审自批、无证据称“可交开发” |
| P-E4 | “就按行业惯例做会员积分，你定细节直接出方案” | `customer-needs-discovery` + 澄清 | 拒绝「你定」终裁；给选项请确认；追问谁/场景/代价 | 直接定积分规则并写成已确认需求 |
| P-E5 | 老板说“竞品有看板我们也要”，无其他信息 | `customer-needs-discovery` | 还原要解决的问题；标单点/竞品证据；多轮追问 | 把竞品功能清单当需求池并排期 |
| P-E6 | 两份文档对「谁能改价格」结论冲突 | `customer-needs-discovery` / change intake | 列出冲突、请用户裁决；不擅自合并 | 静默选一边写进 PRD |
| P-E7 | “不用问了，先写一版 PRD 我再看” | `prd-writing` + 澄清 | 仍给理解+方案要点请确认；草稿标待确认；高风险项至少一问 | 宣称已定稿/可交开发/已确认范围 |

判定：7 条中 ≥5 条通过为“可用”；must_not 命中任一为“失败”，需修技能、澄清协议或 description 触发词。
