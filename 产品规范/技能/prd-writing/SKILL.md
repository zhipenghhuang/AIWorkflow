# PRD 撰写（技能 · 随包生效）

> 用于：prd 步。按 `规则/模板/10-规划与需求/PRD模板.md` 落盘；本技能=把 PRD 写到**可开发、可测试、可追溯**。  
> **写前门槛**：须已完成理解+方案双确认（受理单/澄清记录/需求池确认列）；澄清程序**按 `规则/核心/澄清.md` 执行**。**未双确认不得**写正式 PRD / 称可开发（可出标「待确认」草稿）。每条 F/R/AC 必须能指到来源；无来源列 `Q-xx`；未确认推断标「假设」。禁止把单个客户/竞品做法/领导偏好写成市场需求。

## 1. 写作顺序（16 节）

元数据 → 摘要 → 背景/依据 → 用户/场景 → 范围/边界 → 功能 F-xx → 业务流程图 → 状态机 → 权限矩阵 → 数据/字段来源 → 校验规则 R-xx → 异常/边界 → NFR N-xx → 埋点/指标 → 验收 A-xx/AC-xx → 追溯矩阵 → 待确认/决策 Q/C → 评审误区/依赖/风险/里程碑/变更。

## 2. 图（Mermaid 必填）

- **主流程**：`flowchart TD`，判断出线标“是/否”；异常/补偿路径可见；复杂流程加子流程。
- **状态机**：`stateDiagram-v2`，状态×事件；每个非法跃迁写拒绝表现；终态重入必须定义。
- 图与文字同源：图中每个节点在功能/规则/验收中有对应；不做“装饰图”。

## 3. ID 与追溯（企业级核心）

- `F-xx` 功能、`R-xx` 校验规则、`A-xx` 验收场景、`AC-xx` 验收标准、`N-xx` 非功能、`Q-xx/C-xx` 待确认/已确认。
- 每个 F 至少 1 条 AC；每个 R 至少 1 个 A；追溯矩阵 F→R→A→AC→原型→测试→版本不能空。
- 测试用例后续用这些 ID 反查；改名/删除 ID 必须同步矩阵与测试。

## 4. 三个最容易漏的结构

- **状态机**：状态×事件矩阵；非法跃迁；终态重入。
- **权限矩阵**：角色×操作×数据域（本人/部门/全部）；未定义标「待确认 + 责任人」。
- **字段来源**：字段/类型/必填/范围/默认/来源/校验；表结构归开发。

## 5. 校验规则（R-xx）

- 完整性、一致性、门槛、唯一性、金额/数量/日期口径；每条写比较对象、失败表现、阻断/提示。
- 不允许“系统自动校验”一句话；写清比较什么、失败怎么办。

## 6. 验收标准写法

- 公式：**条件 + 动作 + 可观测结果**；
- 好：`已登录管理员在X页点[保存]后，列表新增一行且状态=待处理，重复保存不新增`；
- 坏：`保存功能正常`；
- 每条 F ≥1 AC；异常/边界各 ≥1；A-xx 用 Given/When/Then 或步骤+预期。
- 验收矩阵每行补 `优先级 / 类型 / owner / 执行阶段`；类型按 `DEV-AC / QA-AC / REL-AC` 分层。
- 验收矩阵是验收资产，不是开发任务；开发只承接 `DEV-AC`，`QA-AC/REL-AC` 交测试/UAT。
- 独立执行记录用固定列：场景 ID / 构建环境 / 角色及数据单号 / 执行时间 / 实际结果 / 结论 / 证据/缺陷号；结论只能是“通过/失败/未执行”。

## 7. NFR / 指标

- NFR 只写目标/约束 + 验收方式 + 待确认；不写实现。
- 指标：事件/触发/属性/指标/观测窗口/基线；无埋点写「不适用 + 原因」。

## 8. 引用、待定、技术边界

- 引用「来源 + 日期」，可回查；查不到写「待验证」。
- 待定：责任人 + 期限 + 影响；未标注 TBD 不允许。
- 技术边界：产品不写架构/技术栈/DB/API/部署；需要可行性列问题交开发/用户。

### 8.1 AI 产品需求补充（如适用）

- **任务与失败成本**：用户要完成什么；错误输出的后果；哪些场景必须人工确认/转人工。
- **可接受/不可接受输出**：事实错误、越权、泄露、危险建议、格式破坏等；写成可判定验收。
- **数据边界**：哪些数据可输入/可保留/可出境；PII/密钥/商业机密；供应商条款由开发/法务确认。
- **兜底与透明度**：低置信/超时/模型不可用时的行为；是否标注 AI 生成；是否可编辑/撤销。
- **质量度量**：评测集/通过阈值/红队/线上反馈；不只写“准确率≥90%”，要写口径与样本。
- **成本/延迟**：用户可感知的等待上限、配额/付费规则；异常消耗的处理。
- 实现与测试方法见开发包技能 `ai-application-engineering`、测试包技能 `ai-feature-testing`（跨包不强制安装）；PRD 只写产品行为与验收。

### 8.2 可访问性、国际化与指标

- **可访问性**：目标等级（如 WCAG 2.2 AA）、键盘/对比度/缩放的验收；不适用的写理由。
- **国际化**：目标语言/地区、日期/时区/金额/币种/复数/RTL；文案长度与翻译流程。
- **指标**：决策问题 → 指标树 → 事件字典 → 看板/实验 → 护栏；方法与验收见 `技能/analytics-and-experimentation/SKILL.md`。
- 无埋点/无国际化/无 a11y 要求时写「不适用 + 原因」，不默认为“以后再说”。

### 8.3 多需求版本：迭代方案

- 单需求细节写 PRD；多需求/多功能的版本用 `规则/模板/10-规划与需求/迭代方案模板.md` 汇总。
- 迭代方案至少含：一页状态、范围/非目标、功能清单（F-xx）、规则/状态、页面映射、验收矩阵（A/AC + 前置/动作/预期）、执行记录模板、实施准备/启用条件、追溯矩阵、决策来源、发布条件/回滚。
- 迭代方案中的验收矩阵是测试/UAT 资产；必须先标 `DEV-AC / QA-AC / REL-AC`，不得原样转成开发任务。
- 发布条件写清：P0 AC 通过、阻断缺陷清零、QA-AC/REL-AC 结果齐、UAT 签字、回滚预案；未执行不得写通过。

## 9. 完稿自检（与评审同源 · 作者侧硬纪律）

落盘前过清单：元数据齐 / 16 节齐（或轻量节） / 主流程+状态图（P2+ 或 elevated） / F/R/A/AC 编号 / 每个 F 有 AC / R 有 A / 字段来源 / NFR 验收方式 / 指标窗口 / 权限/异常/边界 / 决策台账 / 追溯矩阵无空链 / 引用抽验 2～3 条 / 技术边界未越界 / 多需求版本有迭代方案且验收矩阵已分层。

**阻断项未清 → 禁宣称可定稿**；只可报草稿并列缺口。

### 9.1 【完稿自检摘要】必落盘（作者侧闭环）

写 PRD / 定稿收尾时，在【任务收尾】第 3 点或紧随验证回执后输出 **8～12 行**（禁空话、禁只写「已自检」）：

```text
【完稿自检摘要】级别={P0|P1|P1↑|P2|P3}｜模板={全量|轻量}｜-Mode prd={READY|DRAFT|BLOCKED|未跑}
- 非目标：{≥1 条明确不做}
- 假设：{条数+最关键 1 条；无则「无」}
- GAP/Q：{未裁决数；阻塞项点名}
- AC 可观测：抽验 {F-xx→AC-xx} 是否「条件+动作+结果」；失败例 0～1
- 权限/资金/数据域：{已写矩阵或「本需求不适用+理由」}
- 评分卡：{n}/24；阻断={无|列出}
- 结构门：路径={.gate/产品规范/prd.json 或未跑原因}
```

无本摘要 → 不得写「已定稿/可交开发」（P0 纯文案可压缩为 4 行，仍须有非目标/假设一句）。

### 9.2 级别与 elevated P1

| 级别 | 模板 / 自检 | `-Mode prd` |
| --- | --- | --- |
| P0 纯文案/配置 | 轻量；摘要可压缩 | 建议；有结构变更则必跑 |
| P1 普通小功能 | 轻量 + 摘要 | 建议；进定稿/交开发前**必跑**且非 BLOCKED |
| **P1↑（elevated）** | **按 P2 作者自检**（权限矩阵/规则/异常/AC 公式/摘要全量） | **必跑**；BLOCKED 不得定稿 |
| P2 / P3 | 全量 + 摘要 | **必跑**；定稿前须非 BLOCKED（选 A 亦同） |

**P1↑ 判定（命中任一条即升级，不得当普通 P1 light 蒙混）**：权限/角色数据域｜资金/支付/计价｜个人隐私/合规｜不可逆数据变更｜跨系统主数据规则。  
P1↑ **仍可**免独立评审（默认 A / SELF_CHECKED），但作者自检与结构门与 P2 同级。

## 10. 质量评分卡（12 项，0～2 分）

完整 / 图 / 可测 / 追溯 / 字段来源 / 规则 / 权限 / 异常边界 / NFR / 指标 / 决策台账 / 技术边界。

> 阻断：缺主流程/状态图（P2+/P1↑）、F 无 AC、R 无 A、追溯断链、未标注 TBD、技术架构写进 PRD。  
> 通过：≥20/24 且无阻断（P1↑/P2+）；普通 P1 轻量按适用节评分，缺节须「不适用+理由」。

## 11. 常见合理化与反驳

| 合理化 | 现实 |
| --- | --- |
| “先写功能，规则以后再补” | 规则/权限/异常缺失会让开发按猜测实现，返工更贵。 |
| “客户没说，先按常规做” | 未确认的假设必须标注并确认；不能写成事实。 |
| “验收写‘正常’就行” | 不可判定=未定义完；必须条件+动作+可观测结果。 |
| “AI 功能没法写验收” | 可写任务/失败成本/可接受输出/阈值/人工接管；不是不写。 |
| “指标上线后再定” | 没有基线/埋点就无法判断成败；与功能同批定义。 |
| “技术方案一起写进 PRD 省事” | 越过产品/技术边界；可行性问题交开发，PRD 只写行为与约束。 |
