# 门（产品轨）

> 单一出处：门语义、`when` 词表、门档位。步骤顺序与是否触发以 `../workflows/*.yaml` 为准；**只认步上 `hitl`/`hitl_when`/`gate_when`**，专规不另造门。
> 读取时机：当前步有门时只读本表对应一行；写/改 YAML 时才读全表。不要每次开工通读。
> 质量审计/评分卡参考见 `专项/质量门.md`；它不是额外确认门，执行仍只认步上 `hitl`/`hitl_when`/`gate_when`。

## 1. 门语义

| 门 | 含义 | 必须行为 |
| --- | --- | --- |
| `confirm_go` | 新产品立项 | 出示问题/市场/方案/MVP 假设/成本收益/风险/结论（Go/Hold/Kill）；未过不写全量 PRD |
| `confirm_intent` | 意图理解（择优·防自作主张） | 仅当 `intent_needs_confirm`：出示【意图理解】，确认后才落盘。意图已清 → 跳过（可一行回执即做）。细则 `澄清.md` §0。≠ `confirm_understanding`；≠ `confirm_handoff` |
| `confirm_understanding` | 需求理解 + 方案要点 | 出示【理解复述】（谁/场景/问题/现有替代/代价/目标/范围/非目标/证据/假设）+【推荐方案要点】（主路径/关键规则/异常期望/验收口径/不做）+ 缺口清单；涉及换迭代/相对上版时附**本期差量要点**（增/改/删或「首版全部为增」）。用户须对理解与方案均表态；仅回 OK 未对复述/方案表态不算过；确认后才分诊/入池承诺/写正式 PRD/计划/排期 |
| `confirm_plan` | 产品计划 | 首次计划或范围·指标·版本实质变更：目标/路线图/本期范围/**§3.0 Brief+差量表** /里程碑/风险摘要；无差量表（且非明示首版一行）不过门；未确认不进 PRD/排期 |
| `confirm_change` | 需求变更/产品缺陷处置/实现缺陷退回 | 出示分诊依据、影响与变更单要点（**含 §2.1 差量表** Now→Proposed）；产品缺陷须有相符证明；无单不实施 |
| `confirm_design` | 设计方向 | IA/线框/2～3 个视觉方向/tokens；确认后才做高保真 |
| `confirm_prototype` | 原型交接 | 原型路径/设计评审结论/交接要点；确认后才交开发 |
| `confirm_narrative` | 展示叙事 | 受众/目标/故事线/演示范围已成形后确认；仅叙事不明或首次对外演示时停 |
| `confirm_materials` | 对外材料 | 一页纸/Deck/用户文档/发布说明；数字/截图/流程与当前项目一致；仅对外发送、承诺或发布前触发 |
| `confirm_scope` | 单需求立项范围 | 范围（MVP）/排除项/粗排期/风险 一行摘要；条件门：仅跨版本/高价值/未确认范围时停 |
| `select_review_mode` | 落地文档评审方式 | **STOP 二选一**：A 自行评审通过（HUMAN_APPROVED）｜B AI 独立评审（异人量规+评审记录）。适用 PRD/产品计划/设计交接等（`技能/artifact-review`）；同产物只问一次；点名「AI 评审」=B、「我审/自行通过」=A；未选不得宣称通过/定稿/交开发 |
| `confirm_prd` | PRD 定稿/实质变更重审 | 评审结论为「通过（可定稿）」且用户点名定稿/进入排期时出示；**出示前**须有【完稿自检摘要】且 `-Mode prd` 非 BLOCKED；定稿前不排期；仅评审不弹门 |
| `confirm_remark` | 缺陷平台回写 | 出示 id+结论+备注全文+附件名+状态/指派变更；备注与状态同轮；平台不支持出 export |
| `confirm_release` | 发布 | 出示 UAT 结论、回滚预案、公告/客服/监控就绪；未过不发布；已发布仅复盘不重复确认 |
| `confirm_commit` | 拟提交 | 【拟提交】块（文件+`.gitignore`+分支/跟踪+本次动作）；确认后提交；禁擅自切主干/force push/开合并 PR；≠收尾第 2 点「待提交摘要」 |
| `confirm_handoff` | 交接包发送 | **凡拟生成任一 HO 包必停**：出示类型/接收方/必带摘要/阻断/传递方式；用户确认后才落盘；未确认零发包。禁止用「定稿门/评审门/发布门已过」代替本门。未收回执不得称「已接收」；可称「已发送」 |
| `confirm_gitignore` | 入库策略 | 四选一确认并写 `.gitignore` |
| `confirm_docs_migration` | 资料/工作文档搬迁、归档或临时清理 | 出示分类/覆盖对照/拟归档或清理清单与目标；确认后执行；不擅自删、不覆盖 |
| `confirm_iteration_close` | 结束当前迭代/版本并进入下一 | 出示当前迭代标识、未完成项、拟归档摘要、下一迭代标识；确认后按 `规则/文档治理.md` §7.1 关账；选「并行不关」则只落新资料 |
| `confirm_skill_changes` | 能力/技能体检拟变更 | 出示【拟变更清单】（改 `技能/`·`能力/`·装配项）；确认后才改本包或给安装步骤；未确认零改动 |
| `gate: product-prd` | PRD 结构门（when: `prd_structure_required`） | 运行 `验证/Invoke-Gate.ps1 -Mode prd -Artifact <当前PRD>`（推荐显式路径）；BLOCKED → 不得进评审/定稿/交开发；DRAFT → 可审不可定稿；回执 `.gate/产品规范/prd.json`。light 缺追溯仅警告。P2+/P1↑/拟定稿或交开发时为真 |
| `gate: product-review` | PRD 评审门禁（when: `ai_review_chosen`） | 仅选 B（AI）时运行 `-Mode review`；评审人≠作者；READY 后取 `gate_id`；选 A 不跑本门，须 HUMAN_APPROVED + `approved_by` + 自检摘要 + 复跑 `-Mode prd` 至 READY |

> **`gate_type`**：`machine`=有脚本回执（读 `.gate/` JSON）；`checklist`=按清单/工具核验并留证据。未标默认 `checklist`；新增 gate 必须写 `gate_type` + 证据来源，禁止空门。
| `gate: uat-evidence` | UAT 门禁 | 运行 `验证/Invoke-Gate.ps1 -Mode uat`；AC 覆盖、证据、有条件通过的责任人/接受人；未 READY 不得写 UAT 通过。无 UAT 要求可写 `verdict: 不适用` + 依据/批准人，门放行但记警告 |
| `gate: change-closure` | 变更/缺陷联动闭合 | 运行 `验证/Invoke-Gate.ps1 -Mode change`；§6 每项“已更新/不适用/待补”，待补有责任人/截止；未闭合不得关闭 |
| `gate: writeback-receipt` | 平台回写门禁 | `Invoke-Gate.ps1 -Mode writeback -Artifact …`；单号+备注实质+状态取值+fileId/无附件；禁标题刷绿；无回执不得声称已回写 |

## 2. `when` 词表

`has_pending_commit` 有文件变更待提交｜`has_uat` 本轮有 UAT/验收要求（发布门必须核）｜`change_requested` 改动已定稿基线或产品缺陷/问题处置需确认（不含纯新需求入池）｜`intent_needs_confirm` 口令/上下文对「给谁·做什么·交付形态」**无法唯一确定**，或跨角色外发交接/确认文且本任务未对齐，或新开对外交付主题 → 真；纯查询/机械、同任务已确认未变、本句已写死意图、已对齐任务内续跑 → 假；拿不准按真。细则 `澄清.md` §0｜`understanding_needs_confirm` 输入为模糊/单点需求、含外部文档或原型、存在实质冲突、方案有取舍、或 P1↑/P2/P3/点名写 PRD/计划/收集需求时需确认**理解+方案要点**；已有**当前任务**理解与方案双确认记录/已确认受理单（含方案要点）、或信息完整的缺陷单/答疑且已能复述且无新方案取舍时假｜`plan_needs_confirm` 首次计划或范围·指标·版本实质变更｜`new_requirement_or_scope_change` 新需求/范围变化｜`new_requirement` 分诊为新需求（不含已定稿基线的需求变更）｜`scope_decision_required` 跨版本/高价值/点名立项，需单需求范围确认｜`scope_unconfirmed` 无已确认产品计划且无已批准的单需求范围｜`landing_doc_review_needed` 落地文档（PRD P2+、产品计划实质变更、设计交接、实质变更重审、或用户点名评审）待选评审方式且本会话尚未选定；P0/普通 P1 light 且用户未点名时可假；**P1↑ 默认提示 A / SELF_CHECKED，不强制独立审；P2+ 必问 A/B**｜`ai_review_chosen` 用户已选 B（AI 独立评审）｜`prd_structure_required` 本步为写/改 PRD 且级别为 P2+/P1↑，或用户点名定稿/交开发/拟置 APPROVED，或普通 P1 将交开发；P0 纯文案无结构变更为假｜`finalize_requested` 评审通过且用户点名定稿/进入排期（仅评审不触发）｜`has_ui_requirement` 有页面/界面需求或点名画原型｜`narrative_needs_confirm` 受众/目标/演示范围不明或首次对外演示｜`materials_for_external` 材料/文档将对外发送、承诺或发布｜`demo_needs_dryrun` 准备演示/客户介绍/彩排｜`docs_requested` 点名用户手册/快速开始/FAQ/发布说明/培训材料｜`needs_impact_assessment` 变更/缺陷/新需求需影响评估｜`needs_linked_update` 需联动回写与回执（除纯答疑外均为真）｜`substantive_change` 实质变更需重审｜`plan_level_change` 影响版本范围/里程碑/KPI｜`release_decision_needed` 未发布或发布内容/窗口变更｜`remark_writeback` 有拟回写缺陷平台的备注/附件/状态/指派｜`handoff_send_required`（**拟生成或用户点名生成任一 HO 交接包（常用类型为示例，含 OTHER/项目扩展）且本包本会话尚未得到用户对该次发包的明确确认 → 真**；用户已明确确认「要/生成/确认发包」且拟发摘要未变 → 假。**不得**因其它门已过而置假）｜`handoff_change_substantive` 交接包内变更达到 C2/C3 或改动已定稿基线｜`prd_ready_for_handoff` PRD 已 `APPROVED` 且 PRD 门 READY，本轮 `confirm_prd` 定稿/进入排期，且台账无同版本 `REQ` 已发送/已接收记录；仅评审不触发｜`docs_migration_needed` 有未登记资料、拟改名/搬迁/归档、工作文档归档或临时文件清理、或旧结构迁移｜`skill_changes_pending`（`skill-audit` 出具拟改技能/能力表/装配项且用户尚未确认；无拟变更或已确认/拒绝后为假）｜`iteration_close_needed`（探测到下一期方案/换主题/版本升级且当前迭代是否结束不明确；已确认结束或明确并行不关后为假）。

条件不满足则跳过该门；未写 `when` 视为无条件。`gate_when: ai_review_chosen` 不满足 → 跳过该 gate（步骤可走 A 路径）。同一确认点只问一次；固定骨架不得省略。

## 3. 门档位（防过度审批）

| 档 | 适用 | 行为 |
| --- | --- | --- |
| autonomous | 只读、低风险、可逆 | 直接做，收尾记录假设 |
| notify | 中风险、可回退 | 展示计划/清单后继续，用户可打断 |
| approve | 高风险/不可逆 | 停：立项、计划、**评审方式选择**、定稿、变更、平台回写、发布、提交、搬迁/归档/清理、交接包发送、技能/能力拟变更 |

低风险动作不要升级为 approve；高风险动作不得降为 notify。红线不被“少问/直跑”覆盖。
