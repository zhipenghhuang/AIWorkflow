# Playbook · 需求/问题受理与变更（含 P0～P3 分级）

> 只读本卡 + 当前步 YAML；细节按指针读，**不要通读 `工作流.md` 全本**。
> 当前步：`change.intake / triage / new_requirement / assess / decide / apply / review / verify`。

## 1. 分级（先判，决定走多深）

| 级别 | 典型 | 必走 | 可跳过 | 产物 |
| --- | --- | --- | --- | --- |
| P0 文案/配置 | 无行为/AC 变化 | intake → triage → apply → verify | 全量 PRD/独立评审/计划门 | 受理单/变更记录 |
| P1 小功能 | 单页面/≤3 AC，已在计划范围内 | intake → triage → apply → verify | 全量 PRD/独立评审 | 1 页 PRD 增补或需求卡 |
| P2 功能/版本 | 跨模块/AC/状态/权限/数据变化 | 全链 | 无 | PRD/变更单/评审/UAT |
| P3 0→1/战略 | 新产品/新业务 | `new-product` + `plan` + PRD | 无 | 全量 |

分级由 AI 在 intake 判断并写入首条路由；不确定按高一档。P0/P1 不因“流程完整”强行写全量 PRD。

## 3. 流程卡

1. **intake**：对话/文档/缺陷单/测试报告均可；按 `规则/澄清.md` + `技能/customer-needs-discovery/SKILL.md` 先还原谁/场景/问题/现有替代/代价/目标结果/成功标准/非目标，给理解回执并一次一问至 ≥95%，用户确认后才分诊；抽取提出人/来源/日期、原文、期望、关联 PRD/AC、版本/环境/证据、时间要求。未知标「待确认/假设」。去重合并，生成 RQ/CR/BUG 编号。新资料按文档治理 §3 输出候选，确认后才落位。
2. **triage**：判定树分类（新需求/变更/答疑/产品缺陷/实现缺陷/技术不确定/重复/无效）。产品缺陷必须有 PRD/设计原文 + 现网/测试证据 + 相符证明；无依据按实现缺陷/待确认。结论写受理单，不在此实施。
3. **new_requirement**（条件）：入需求池 R-xx，价值/成本/风险/优先级/版本/状态；仅跨版本/高价值/点名立项才 `confirm_scope`，小需求直接进 PRD/变更。
4. **assess**（条件）：评需求/AC、成本/排期、技术/测试风险、数据/合规/权限、回滚、依赖；列受影响产物。改动已定稿基线 → 必须产生变更单。
5. **decide**：出示分诊依据/影响/处置选项/变更单要点；`confirm_change` 后才实施；影响版本范围/里程碑/KPI 叠加 `confirm_plan`。纯答疑可跳过。
6. **apply**：按受理单 §6 逐项更新，只写现行有效；每项标「已更新/不适用/待补」；待补写责任人与截止。变更单与受理单互链。
7. **review**（条件）：实质变更（范围/AC/状态机/权限/数据规则/NFR/版本目标）才重审；只报缺口；通过才恢复 `APPROVED`。
8. **verify**：影响 AC/UAT/发布 → 受影响项重验；未 UAT/未发布 → 测试/回归/冒烟证据；未验证不关闭。退回开发 → 回执后关闭受理单，不写「已修复」。

## 4. 红线

- 无变更单不实施变更；口头变更先落单。
- 未完成客户需求理解确认不得写 PRD/排期；客户说法不等于需求，单个客户/竞品/领导偏好不得直接当市场结论。
- 产品缺陷无相符证明不得判；实现缺陷不改 PRD。
- 联动清单未闭合不得关闭；未验证不得关闭。
- P0/P1 可轻量，但证据、回执、联动清单不可省。

## 5. 输出

受理单 + 变更单（如适用）+ 最新 PRD/AC/计划/UAT + 开发/测试回执 + 联动清单。收尾按 `规则/模板/收尾骨架.md`。
