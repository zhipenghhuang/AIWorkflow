## 2. 流程卡

1. **preflight**：读 provider；无配置 → 问一次是否配置；不配置 → 粘贴/export 降级，禁反复要编号、禁猜接口。
2. **pull**：默认拉当前产品账号被指派、未关闭；点名单号只拉这些。每条读全：标题、steps、severity/pri、status/resolution、提交人/指派、版本/环境、附件、近期备注、开发评估单/方案。`solutionChannel=manual` 或备注不全 → 请用户补，禁只看标题分析。批量 ≥5 单且读单成本高 → 逐单只读扇出，返回 ≤30 行；五选一/处置集中。
3. **source**：逐条标来源（测试直提/开发评估单/产品复核）。混批按条处理，不整批套模板。
4. **analyze**：对照 PRD/设计判产品缺陷 vs 实现缺陷；产品缺陷必须有 PRD/设计原文 + 现网/测试证据 + 相符证明。开发评估单读全文，五选一：认可/修改后认可/不认可/判定实现/判定非问题；不重做技术设计。
5. **decide**：出示每条来源/依据/相符证明/影响/处置选项/指派；`confirm_change` 后才实施。纯拉取/只读分析止于 analyze，不落处置单。
6. **apply**：更新 PRD/AC/原型/交付计划/产品计划/需求池/UAT/发布检查，逐项标「已更新/不适用/待补」；产品缺陷产出 `缺陷处置-{BUG-ID}-...md`；实质变更走 review。已回写平台 → 不强制 BUG 整包；无平台/点名 → **先问后发**自包含处置包。
7. **review**：只评产品视角（是否解决原问题/AC/范围/风险/合规），不评技术实现；通过才恢复 `APPROVED`。
8. **writeback**：出示 id+结论+备注全文+附件名+状态/指派；包末必有【拟回写·底部摘要】（无类省略）；`confirm_remark` 后执行；备注与状态同轮；附件回查挂载；失败重试 ≤1；无权限走 export；收尾「完成了什么」复述单号清单；对照 `收尾骨架` §2。
9. **verify**：受影响 AC/UAT 重验；实现缺陷由开发/测试跟踪，产品不写「已修复」；未验证不关单。检查 BUG 包回执；未回执不得写“开发/测试已接收”。

## 3. 红线

- 产品缺陷无相符证明 → 不得判产品缺陷；按实现缺陷/补充信息处理。
- 开发评估单不等于完整技术方案；产品不替开发评审架构。
- 平台回写必须 `confirm_remark`；禁删缺陷；无权限不声称已回写。
- 三包独立：只认平台单号/备注/附件，不引用其它包内部路径。

## 4. 输出

受理单/处置单/变更单/评审记录 + 平台回写结果或 export 包 + 最新产物路径 + 回执。收尾按 `规则/模板/90-交接与收尾/收尾骨架.md`。
