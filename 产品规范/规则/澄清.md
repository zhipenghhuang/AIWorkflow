# 澄清追问环（产品轨）

> **单一出处**：澄清的触发、提问格式、理解回执、95% 停止条件与落盘。`AGENTS.md` §0.1、workflow 步注、技能只引用本文，不另写一套。
> **与确认门的关系**：确认门=执行授权（`hitl`）；澄清=理解对齐。门不能替代澄清；澄清答复不自动授权执行，仍需按步过门。
> **读取时机**：任务开始、输入含客户需求/文档/原型、准备写 PRD/计划/优先级/范围前。
>
> **总规则（强制）**：回答和执行任务前先提问；**一次只问一个问题**；根据回答继续追问；直到 ≥95% 信心；完全理解真实需求与目标后，再给最终方案。确认门不是澄清；低风险也不跳过理解回执。

## 1. 何时必须澄清（命中即问）

1. 目标、用户、场景、成功标准任一不明。
2. 范围/非目标不明，或与既有产品计划/PRD/需求池冲突。
3. 输入含客户访谈、反馈、工单、PRD、迭代方案、页面原型、截图、竞品/市场资料：未完成“还原需求→证据→复述→确认”前不得写 PRD/计划/排期。
4. 关键业务规则、字段口径、状态流转、权限、异常、NFR 未定义或不可判定。
5. 文档之间、文档与原型、客户说法与数据/行为证据冲突。
6. 用户使用“优化/完善/按惯例/你们决定/差不多/越快越好/行业最佳实践”等模糊词。
7. 高风险/不可逆（定价、合同、合规、隐私、对外承诺、发布）。
8. 发现自己正在用假设填空，且该假设会影响范围、优先级、验收或客户承诺。

**可以免问**：纯信息查询、机械整理/格式化、已由档案/正式产物唯一确定且无分支的低风险操作、按已确认产品计划/受理单执行的确定性整理。免问也要给一行理解回执（见 §2）。

## 2. 首轮固定动作：理解回执 + 只问一个问题

首轮回复必须按此顺序，不得先写 PRD/方案/长清单：

```text
理解回执：{一句话复述客户要解决的问题}
置信度：{0-100%}｜缺口：{还不知道什么；≥70% 可写“无关键缺口”}
Q1：{一个聚焦问题}
建议：{你的猜测/推荐答案 + 一句理由；可给 2-3 个选项}
```

- **一次只问一个问题**：不得在同一轮列 Q1/Q2/Q3，不得用“顺便确认/另外/还有”夹带第二个问题。
- **非机械任务至少问 1 个问题**：即使自评 ≥95%，也要用「理解复述 + 对/不对/补充？」请用户确认；复述本身算这一问。只有纯信息查询/机械操作可免问。
- **先查后问**：能从档案、PRD、计划、需求池、数据、工单、原话确认的，先查并引用；只问查不到且会改变结论的。
- **问题可回答**：单选/短答/二选一优先；不问“你觉得怎么样”，不问实现细节。
- **附建议**：先给猜测再问，降低回答成本；猜测错了要显式改口。
- **问完就停**：等用户回答；不得自问自答，不得把“我先按 X 写”当已确认。
- **问题顺序**：谁/什么场景 → 现在怎么解决/代价 → 要达成什么结果 → 范围/非目标 → 规则/优先级 → 验收/指标 → 风险/依赖。

## 3. 回答之后：更新理解，继续追问

每轮回答后：

1. 用 1-2 句更新理解回执与置信度（不要重复整段）。
2. 把已回答内容记为“已确认”，不再重问。
3. 只问下一个最高影响问题；若回答引出新的冲突，先问冲突。
4. 直到满足 §4 停止条件，再写需求池/PRD/计划/优先级。

**禁止**：把用户没说过的话写成客户需求；把“行业惯例/最佳实践/竞品也这样”当需求；把多个问题合并成一段叙述；在用户回答前继续产出下游产物。

## 4. 95% 停止条件（可检验，不靠感觉）

同时满足才可停：

- [ ] 能预测用户对接下来 3 个问题的反应。
- [ ] 能复述：谁 / 在什么场景 / 遇到什么问题 / 现在怎么绕过 / 要达成什么结果 / 怎么算成功 / 明确不做什么。
- [ ] 关键冲突已裁决；未决项已标“假设”并有验证方式与责任人。
- [ ] 用户明确说“对/是/按这个来/可以”。
- [ ] 复述中的范围、目标、非目标与用户最后的表述一致。

**不算确认**：“随便/你决定/看着办/应该可以/差不多/沉默/只回一个 OK 但没有对复述表态”。遇到这些 → 给两个具体选项再问一次，不要开跑。

**置信度锚点**：

| 区间 | 含义 | 动作 |
| --- | --- | --- |
| <50% | 客户/问题不明 | 只问谁与什么问题，不产出 |
| 50-70% | 问题大致清楚，证据/范围有缺口 | 继续一次一问；缺口写清 |
| 70-85% | 问题与主场景清楚，优先级/验收/约束有缺口 | 补关键缺口；可给草案但标明假设 |
| 85-95% | 可复述，少数低影响项未定 | 复述确认；低影响项标假设 |
| ≥95% | 可预测后续反应，用户已确认 | 产出需求池/PRD/计划 |

连续 3 轮置信度不上升 → 换问法或回退到“谁/什么问题”重问；仍不上升 → 明确告诉用户“缺一个基础信息”，请其补充或缩小范围。

## 5. 完整复述模板（过门/落盘前）

```text
【理解复述】
- 客户/用户：{谁；角色；决策人/付费人/使用者}
- 场景：{什么情况下发生；频率}
- 问题：{现在遇到什么；现有替代/绕过方式}
- 代价：{时间/成本/风险/机会损失}
- 目标结果：{要达成什么；怎么算成功}
- 范围：{这次做什么}
- 非目标：{这次明确不做什么}
- 证据：{访谈/工单/数据/行为/竞品；来源+日期}
- 约束与风险：{预算/时间/合规/依赖}
- 未决与假设：{待确认项/假设/验证方式}
对 / 不对 / 补充？
```

产品轨另加“优先级初判与版本建议”；0→1 另加“市场/竞品/商业模式假设”。

## 6. 反迎合、反臆造、不自作主张

- 用户第一句话是“想要什么”，先还原“要解决什么问题”；不要从功能直接开始写 PRD。
- “应该/惯例/最佳实践/竞品也这样” → 追问具体场景、上次发生时间、代价、不做的后果。
- 单个客户/领导/销售的说法不等于市场需求；标样本量与来源，必要时写“待验证”。
- 用户改口：以最新回答为准；旧结论标作废，不留双真值。
- 不知道就说不知道；无来源写“假设/待验证”，不得写成事实。
- 不为了让用户满意而降低澄清标准；不把“用户没反对”当同意。
- 不替客户做优先级/范围/取舍；给建议可以，决定必须由用户确认。

## 7. 落盘（单一真值）

| 场景 | 落点 | 最少内容 |
| --- | --- | --- |
| 需求/问题受理 | 受理单 §2/§3 | 来源、原话、理解复述、Q/A、证据、假设 |
| 需求洞察 | `产品/需求池.md` / 洞察卡 | 来源、样本量、问题、现有替代、证据等级 |
| PRD | `产品/{版本}/PRD-*.md` §1/§2/§16 | 来源、理解复述、Q/A、假设、非目标 |
| 产品计划 | `产品/产品计划.md` §0/§8 | 目标依据、口径、待验证项 |

- 记录格式：`Q: … → A: …（来源/日期/裁决人）`。
- 用户裁决优先于竞品/数据/代码；有新证据才重开，重开另起一条，不覆盖旧裁决。
- 后续会话先读已确认记录，不重复问。

## 8. 例外与边界

- **用户点名“直接做/不用问”**：仍先给 3 行理解回执 + 假设清单；高风险/不可逆（定价/合同/合规/对外承诺/发布）至少问 1 个最高影响问题。只免等待，不免理解与留痕。
- **紧急客户问题/客诉**：先响应与止损；事后补需求理解与复盘，不把临时承诺写成 PRD。
- **非交互/自动化**：不猜；标 `blocked` + 待确认问题清单，交回人工。
- **确认门**：先澄清后过门；门只确认“是否执行/是否批准”，不替用户回答“客户要什么”。
- **确认门/菜单**：可一次展示多个授权选项，但不得夹带澄清问题。

## 9. 反模式（出现即停）

- 一轮列 3 个以上问题 / 发问卷。
- 不带猜测的开放盘问。
- 用户答完不更新理解，直接写 PRD。
- 把“已读文档”当“已理解”；不引用章节/页码/原话。
- 把单个客户当市场；把竞品做法当需求；把领导偏好当优先级。
- 用“假设”绕过澄清，且不标假设、不写验证方式。
- 把“确认门”当“澄清”，或把“澄清回答”当“执行授权”。
- 置信度虚报 ≥95%，但复述不出“谁/场景/什么问题/怎么算成功/不做什么”。
