# 协作与交接（产品轨）

> **读取级别：参考**（按节读取；按 `读取索引` 只读当前 step 节，禁止通读全本）。

> **目的**：把“产品 → 开发/测试、开发/测试 → 产品、变更 → 所有角色”的交接，从口头约定变成**可复制、可追踪**的交付（默认自洽主文档；按需标准包；回执可选）。
> **独立性**：本包可单独使用；接收方可以是本仓角色、用户本人或外部团队。交付物须自洽详实，文件夹/ZIP 即可传递。回执默认可选，仅正式签收时再填。本侧收到外部材料走资料入站（T1～T9）与理解/吸收；结构化 HO 可另走 `handoff.receive` 签收，与通用入站不互斥。
> **单一出处**：交接意图、单文档默认、包触发、回执策略、变更分级以本文为准。  
> **模板**：默认按 `通用交接单文档模板.md` 做**择优写法**（先分析再选形态，禁止整表填空）；升包用说明/清单/回执/台账。交付目的对等既有专模质量义务时用专模；无对等专模则五问合格线。
> **读取时机**：`handoff.*`、`prd.handoff`、`prototype.handoff`、`deliver.*`、`change.apply`、`defect.apply`、计划交接节；不需要每次开工通读。

## 1. 角色与决策权

| 角色 | 决策权 | 主要交接责任 |
| --- | --- | --- |
| 产品负责人（A） | 范围、优先级、AC、UAT、发布决策 | 需求/设计/计划/变更/UAT/发布交接包；对开发/测试的澄清给书面结论 |
| 开发负责人（R/C） | 可行性、技术方案、工作量、提测 | 需求澄清、方案风险、提测、修复/回归、发布结果 |
| 测试负责人（R/C） | 测试策略、oracle、准出建议 | 测试计划/用例、缺陷、测试报告、发布后验证 |
| 用户/业务（A/C） | 业务目标、预算、风险接受 | 确认范围/优先级/发布；接收对外材料 |
| 运维/客服（C/I） | 部署、监控、客服口径 | 发布/回滚/公告/培训交接 |

**原则**：一个交付物只有一个 A；R 做、C 咨询、I 知会。决策写进受理单/变更单/决策记录，不留在聊天里。产品不替开发做技术决策，开发/测试不替产品改业务口径。

## 2. 协作节奏（什么时候必须拉齐）

| 节点 | 触发 | 参与 | 必须产出 | 门 |
| --- | --- | --- | --- | --- |
| 需求澄清（Three Amigos） | PRD 定稿前 / 开发方案前 / 测试计划前 | 产品 + 开发 + 测试（可缺省） | 需求澄清记录 + **本期差量要点**（或计划 §3.0 / 迭代变更摘要）：问题/示例/AC/可测性/oracle/待决 | 不另设门；结论回写 PRD/AC 与 §3.0 |
| 设计交接 | 原型评审通过后 | 产品 + 开发（+测试） | 自洽开发交接/设计结论；`DES` 包按需 | `confirm_prototype` |
| 计划对齐 | 产品计划/排期确认后 | 产品 + 开发 + 测试 | 范围（含 §3.0 Brief+差量表）/里程碑/测试窗口/依赖（计划正文） | `confirm_plan` |
| 提测交接 | 开发自测/门禁通过后 | 开发 + 测试（+产品） | 自洽提测单；`QA` 包按需 | 对方提测单（若有）；本包不认他包门 id |
| 测试准出 | 测试执行完成/报告前 | 测试 + 产品 + 开发 | 自洽测试报告；`TEST` 包按需 | 对方测试报告（若有）；本包不认他包门 id |
| 发布就绪 | UAT 通过后 | 产品 + 开发 + 测试 + 运维 | UAT/发布决策正文；`REL` 包按需 | `confirm_release` |
| 复盘 | 发布后/事故/迭代关闭 | 全体 | 复盘+行动项；`RETRO` 包按需 | 无 |

> 开发/测试角色不存在时，由用户本人代收；交接包照常生成，接收回执由用户确认。**不因缺角色阻塞**。

## 3. 交接矩阵（产品轨）

### 3.0 总策略（内容优先 · 包按需 · 与开发/测试同口径）

> **三层并存，按目的选用**（不按文档名白名单拒做）：  
> ① **专模质量底线**——对方结果对等既有专模的质量义务（范围契约/实施可读需求、设计交接、计划确认、变更冻结、UAT/发布决策等）→ 用该专模，字段标准照旧；示例非穷尽。  
> ② **HO 标准包**——包触发、先问后发、齐套照旧。  
> ③ **通用择优单文档**——无对等专模时走五问 + A/B/C 合格线；**禁止**用通用菜单稀释①的质量义务；也**禁止**因「表上没有场景名」拒交接。

**选用判定（必做）**：① 对方要什么结果（范围契约 / 验收或实施依据 / 准出或发布决策 / 知会 / 拍板）② 协调面与风险 ③ 是否正式签收。结果对等专模 → 专模；否则 → 择优单文档；仅包触发才升 HO。

| 层 | 默认交付（必产、自洽） | HO 交接包（按需） |
| --- | --- | --- |
| **任意跨角色（无对等专模）** | **择优单文档** A/B/C（五问选形态） | 仅命中包触发 |
| 需求（范围契约） | **实施可读 PRD**（APPROVED；AC/范围/非目标/边界/NFR 写进 PRD，不靠口头） | `REQ`：多文件/点名要包/仓外 |
| 设计（实施依据） | 开发交接说明 + 原型关键结论（正文自洽） | `DES`：同上 |
| 计划/排期 | 产品计划 / 交付计划 | `PLAN`：按需 |
| 变更（冻结） | 变更单正文 | `CHG`：多角色点名要包/仓外 |
| 缺陷 | **有平台→平台回写**；无平台→处置详单 | `BUG`：无平台或点名要包/多文件/仓外 |
| UAT/发布 | UAT 记录 / 发布决策正文 | `UAT`/`REL`：按需 |

**包触发**：① 多文件证据/设计源 ② 用户点名正式签收且要标准包 ③ 仓外 ZIP ④ 同发多主文档 ⑤ 明确「要 HO」。口语「交接/确认」≠要包。未命中 → 目的对等专模用专模，否则择优单文档；**禁止用通用模板整表顶替对等专模的质量义务**。PRD 须 Developer-Ready。

**回执（三包统一）**：默认不需要；正式签收或 C2/C3/发布才要；**不得**把回执策略印进对方正文。

### 3.0.0 意图与择优（与开发/测试同口径）

落笔前五问 → 按目的判专模或形态 A/B/C/D（见通用模板）→ 仅触发升 HO。意图编码**不印成对方章节**。知会/确认类优先 **A/B**；拍板用 **C**；风险接受并入少数确认条，禁止单独工程风险卷。未列意图靠五问选形态，勿因「没有编码」升 HO 或硬套大表。

### 3.0.1 交付形态与合格线

**单文档合格线（结果导向）**：对方能懂情况介绍、清楚自己要做什么（或仅知悉）、掌握判断所需事实；无密钥；无内部路径代结论；未强迫回执。不要求意图码/固定 § 编号。

**交付质量**：目的对等专模用专模｜否则择优｜不偏科｜正文自洽｜外发禁内部路径与流程元数据｜一份可交付。

### 3.1 产品发出（**先择优单文档 · 升包另闸**）

> **默认**：先判意图（澄清 §0）→ 有歧义则完整【意图理解】确认；意图已清则一行回执 → 五问→形态或专模 → 落盘；不建 `产品/交接/{HO-ID}/`。含糊口令禁止直接成文。  
> **升包**：命中触发 + 确认「要包」（`confirm_handoff`）后才落盘。

| 时机 | 类型 | 接收方 | 最小必带（包内） | 前置 |
| --- | --- | --- | --- | --- |
| 计划通报 | `PLAN` | 开发、测试 | 计划关键节快照 | 按需 + 确认 |
| 需求交接 | `REQ` | 开发、测试 | PRD 快照（须已自洽可实施）+ 必要原型摘录 | 定稿后**默认交 PRD**；包按需+确认 |
| 设计交接 | `DES` | 开发 | 开发交接+原型/评审/状态矩阵快照 | 评审后默认交设计正文；包按需+确认 |
| 变更 | `CHG` | 开发/测试 | 变更单+影响矩阵+更新文档快照 | C1+ 按需+确认 |
| 其它 | `OTHER` / 项目扩展码 | 按 `00` 列明 | `00` 写清类型意图 + 最小必带 | 按需+确认；示例非穷尽 |
| 缺陷（无平台/点名） | `BUG` | 开发/测试 | 自包含处置详单 | §3.1.1 + 确认 |
| UAT | `UAT` | 开发、测试 | UAT 记录快照 | 按需+确认 |
| 发布 | `REL` | 开发/测试/运维 | 发布决策+窗口+回滚责任 | 按需+确认 |
| 复盘 | `RETRO` | 开发、测试 | 复盘+行动项 | 按需+确认 |
| 裁决 | `DEC` | 提问方 | 问题+结论+依据 | 按需+确认（可极简） |

### 3.1.1 缺陷双通道（互斥 · 禁绑死「平台后又打包」）

| 协作方式 | 主通道 | BUG 交接包 | 台账 |
| --- | --- | --- | --- |
| **有缺陷平台**且本轮已回写平台（备注/附件/状态/指派） | **平台单** | **禁止**再强制生成内容重复的 `BUG` 整包 | 可记一行「平台已回写 #{id}」（可选，非 HO 整包） |
| **无平台** / `export` / 用户点名「缺陷交接包」 | **BUG 交接包** | **适用**；先问后发；确认后生成，正文假定对方看不到平台 | 状态=`已发送`；本地键 `BUG-…` |

**硬规则**：① 平台已回写 ≠ 再打重复 BUG 整包；② 包不以平台号为前置；③ 自包含详单；④ 「平台回写」默认不发包；⑤ 定稿后默认交自洽 PRD，**不**默认打 REQ 包；命中 §3.0 触发才停问建议发包。

### 3.2 产品接收（读包核对；回执默认可选）

| 时机 | 类型 | 来源 | 产品动作 |
| --- | --- | --- | --- |
| 开发需求澄清 | `CLAR` | 开发 | 读问题/影响 → 答复 `DEC` 或变更 `CHG`；更新受理/PRD；回执 |
| 提测通知 | `QA` | 开发 | 记录提测/构建/已知问题；准备 UAT；回执（不需要 UAT 时说明） |
| 开发任务/排期 | `PLAN` | 开发 | 读取任务/里程碑/依赖；同步产品计划 §4/§7；回执 |
| 测试报告/准出 | `TEST` | 测试 | 读覆盖/缺口/P0/遗留；决定 UAT/发布；回执 |
| 产品缺陷证据 | `BUG` | 测试 | 分诊/处置；回执；必要时出 `CHG` 给开发 |
| 开发评估单 | `BUG` | 开发 | 五选一评审；回执；必要时出 `DEC`/`CHG` |
| 变更通知 | `CHG` | 开发/测试 | 影响评估；更新 PRD/计划；回执；必要时反向通知 |
| 发布结果 | `REL` | 开发 | 更新 UAT/发布记录/复盘；回执 |
| 缺陷修复/回归 | `FIX` | 开发/测试 | 按 AC 验证；关闭/重开；回执 |

## 4. 交接包规范

### 4.1 目录与命名

```text
产品/交接/
├─ 交接台账.md                         # 唯一登记（状态/回执/影响）
└─ {HO-ID}/
   ├─ 00-交接说明.md                   # 封面、目的、接收方动作、验收、回执要求
   ├─ 01-交接清单.md                   # 文件清单：版本/来源/包内路径/必读/用途
   ├─ 02-文档/                         # 必带文档快照（按原文件名）
   ├─ 03-证据/                         # 必要证据副本（截图/日志/报告；脱敏）
   └─ 04-回执/
      └─ 接收回执.md                   # 空白模板必带；默认不强制填写，正式签收时再填回传
```

- **确认后才生成**：用户确认后写完整包（`00/01/02/03/04`）。未命中 §3.0 触发 → 默认不发包；§3.1.1 有平台已回写 → 不强制 `BUG` 整包。正式签收/多包同仓 → 完整包；仓外一次性极简可 `00+02`（`00` 声明降级理由），正式签收仍须完整包。
- **自包含详实**：读包即懂；`02` 带主文档快照（PRD/处置单等须已自洽）；禁「见主副本/见禅道」充数。参考 Agent Handoff：Must Satisfy、Scope in/out、Evidence to return。
- **ID（通用）**：`HO-{yyyyMMdd}-{NN}-{类型}-{发起}2{接收标签}`。类型含 `OTHER`/扩展；接收标签常用示例，允许自由标签；ID 只检索。  
  - 单收：`…-REQ-PM2DEV`。  
  - **多收同包（推荐）**：`…-REQ-PM2ALL` 或短拼 `…-REQ-PM2DEVQA`（同一 PRD 同时给开发+测试）。  
  - 角色码常用示例：`PM/DEV/QA/OPS/BIZ/ALL`（允许自由标签）。  
  - **命名 ≠ 内容裁剪**：后缀只检索；多收时 `00` 列齐接收方，§3 **按角色分行**写动作；`02` 须全体可读，禁止只贴合某一方。仓外以文件夹/ZIP 传递。
- **版本**：包内文档带版本/日期；新版本新建 `...-v2` 目录，不覆盖旧包。`01-交接清单.md` 写 `取代：{旧ID}`。
- **快照**：`02-文档/` 是**生成时快照**；主副本仍在 `产品/{版本或主题}/`。接收方只读。
- **大文件 / 多包联动**：文本默认复制进 `02`；超大源文件可在清单写**同仓源路径**作联动引用（对方直读），须在 `00` 标明「同仓联动：{路径}」；**禁止**再拷到对方 `资料/交接/`。仓外仍须可获取或 ZIP。
- **安全**：密钥/凭据/真实 PII 不入包；截图脱敏；客户数据只留摘要。
- **00-04 是通用骨架，不新增 05**：校验值写 `01-交接清单`；大包在 `02-文档/`、`03-证据/` 下按类型子目录（需求/设计/接口/数据；截图/日志/样张/报告），小包可平铺；`01` 写清路径即可。

### 4.2 生成步骤（`handoff.send`）

0. **先问（不可跳过）**：按 §3.1 总闸出示【拟发包】类型/接收方/必带/阻断/传递方式 → 等用户确认；未确认 **零写盘**。业务门已过 ≠ 发包已授权。
1. **冻结来源**：确认门已过、文档状态正确（PRD `APPROVED`、原型已评审、UAT READY）；记录版本/日期/构建。
2. **选类型与接收方**：按 §3 选最小必带；缺必带 → 不发送，列缺口与责任人。
3. **复制 / 联动**：必带文档进 `02-文档/`（或同仓大文件写联动路径）；证据进 `03-证据/`；保留原文件名。
4. **写说明与清单**：按模板写 `00`/`01`（含自包含摘要与接收方动作）；`04-回执/` 空白模板必带。
5. **自检**：对照 §3.0 发出前合格线；运行 `python 产品规范/规则/tools/validate_handoff.py <包路径>`（可用时）；缺件/占位符/版本不符/悬空引用先修。
6. **登记**：更新 `交接台账.md`（状态=`已发送`）、产品计划 §0/§12、文档索引、`activeContext.md`。
7. **传递模式**（写进【交接包已生成】）：
   - **多包同仓**：对方**直接读** `产品/交接/{HO-ID}/`（及 `00` 所列联动路径）。**禁止**复制/转发到对方 `资料/交接/`。
   - **单包 / 仓外**：发 `{HO-ID}` 文件夹或可选 ZIP。
8. **告诉用户**：输出【交接包已生成】；**不得写“已接收”**。

```text
【交接包已生成】
- 交接：{HO-ID}｜{类型}｜{发起方} → {接收方}
- 路径：产品/交接/{HO-ID}/
- 传递：多包同仓 → 对方直接读上述路径（禁止再转发/拷到对方资料/交接）；仓外/单包 → 发文件夹或可选 ZIP（{HO-ID}.zip）
- 必带：{…}
- 阻断/待决：{…}
- 回执：默认可选（模板在 04-回执/）；点名正式签收或发布/C2/C3 时再填回传
- 状态：已发送
```

### 4.3 接收与回执（`handoff.receive`）

> **与通用入站**：普通文档/资料 → `规则/文档治理.md` 入站（T1～T9）+ 理解/吸收（如 `change` / materials）。HO 包 → 本步签收核对后，实质内容仍按入站 T9 与计划/基线回写；不另造平行通道。口头/邮件等价回执可记台账，正式节点优先填 `04-回执/`。

1. **定位包**：
   - **多包同仓**：直接打开发送方路径（如 `开发/交接/{HO-ID}/` 或 `测试/交接/{HO-ID}/`），**不要求**拷入本侧 `产品/资料/交接/`。
   - **仓外/单包**：在用户放置处打开文件夹或解压 ZIP；台账可登记实际路径；仅在归档有用时可选复制到 `产品/资料/交接/{HO-ID}/`。
2. 先读 `00`，再按 `01` 核对五件事：清单文件是否齐、版本/日期是否对、是否有阻断缺口、是否有互相矛盾、是否有需产品拍板项。对照 §3.0 发出前合格线，缺关键项按缺口处理。
3. 结论三选一：**接受** / **有条件接受**（列非阻断缺口/假设/责任人/截止） / **退回**（列阻断缺口与需要补什么）。
4. **回执（可选 vs 正式签收）**：默认可选。**正式签收**（用户点名要回执，或发布/C2·C3）→ 填写 `04-回执/接收回执.md` 并回传，结论三选一，台账改为 `已接收`/`有条件接收`/`退回`。仅通知/同仓直读/用户代收 → 台账「已发送」+用户确认即可关闭，不强制回执。无回执时只可声称「已发送」，**不得**声称「已接收/已交接完成」。回执正文用姓名/结论/缺口/下一步；本侧路由备注不外发。
5. 更新自己的计划/文档/索引：计划 §0/§7/§8/§10/§12、UAT/发布记录、需求池/受理单、`activeContext.md`。
6. 若包内是变更通知 → 走 §6；若含实质变更 → 先 `confirm_change`/`confirm_plan`，不得边执行边改口径。
7. 发送方收到正式回执后更新台账：`已接收`/`有条件接收`/`退回`；退回需补件后发新版本，旧包标 `已取代`。**正式签收时不得替对方签收**。

**时限（默认，仅正式签收场景）**：普通交接 1 个工作日；阻断/提测/发布 4 小时。超时由发送方在台账标 `待回执` 并升级给用户。

## 5. 交接完成判定

| 状态 | 含义 | 能否进入下游 |
| --- | --- | --- |
| `草稿` | 包未生成完/未自检 | 否 |
| `已发送` | 已生成并交给对方（回执未填或未收回） | 本侧可继续准备；仅通知/同仓直读/用户代收经用户确认可关；不得称「已接收」 |
| `已接收` | 正式回执=接受，清单齐 | 是（正式签收完成） |
| `有条件接收` | 正式回执=有条件，非阻断缺口有主/截止 | 是，条件进计划风险 |
| `退回` | 正式回执=退回，阻断缺口未解 | 否；补件后发新版本 |
| `已取代` | 有新版本包 | 否；以新版本为准 |
| `已关闭` | 下游工作完成/验收关闭；或仅通知类已发送+用户确认 | 是（作为历史） |

**硬规则**：日常外发以包生成/`已发送`为准，可继续本侧准备，**不得**用「须等回执」阻塞日常。**正式签收/C2·C3/发布相关须回执**后才可标 `已接收/有条件接收` 并关单；仅通知/同仓直读/用户代收 →「已发送」+用户确认可关。未回执不得称「已接收/已交接完成」。

## 6. 变更与计划自适应

### 6.1 变更分级

| 级别 | 判定 | 例子 | 审批 | 计划动作 | 交接 |
| --- | --- | --- | --- | --- | --- |
| `C0` 澄清/纠错 | 不改变范围/AC/资源/里程碑 | 文案、口径、笔误 | 无（书面留痕） | 就地更新，不重基线 | `DEC`，受影响才发 |
| `C1` 同范围增量 | 在已批准范围内增/改 AC、任务、用例 | 补边界、补状态、补回归 | 产品负责人 | 更新任务/用例/计划 §0/§10 | `CHG`；正式签收时回执 |
| `C2` 范围/里程碑/资源变化 | 范围、优先级、版本、窗口、验收口径变化 | 加需求、砍范围、延期 | `confirm_change` + `confirm_plan` | 重新基线；更新路线图/排期/UAT/测试计划 | `CHG` + **须回执** + 重过受影响门 |
| `C3` 战略/架构/合规/破坏性 | 商业模式、架构、合规、破坏性接口/数据 | 换方案、迁移、合规要求 | 立项/重审 + 发布门 | 重跑发现/方案/评审/发布；回滚演练 | `CHG` + `RISK` + **须回执** |

> 不允许把 C2/C3 拆成多个 C0/C1 绕过门；拆批必须写清总变更单与子项。

### 6.2 重规划触发

| 触发 | 默认阈值 | 动作 | 负责人 |
| --- | --- | --- | --- |
| 基线变化 | 范围/AC/里程碑/验收/发布窗口 | 按 C2/C3 重基线 | 产品 |
| 关键依赖延期 | > 2 个工作日或 > 阶段工期 10% | 重排/加缓冲/升级 | 产品 + 开发 |
| S1/S2 缺陷或准出失败 | 出现即触发 | 停轮/修复/重测；评估发布 | 产品 + 测试 |
| 环境/数据不可用 | 测试 > 4 小时；开发 > 1 个工作日 | 降级/换环境/暂停 | 开发/测试 |
| 产能变化 | > 20% | 砍范围/拆波次/延期 | 产品 |
| 合规/安全事件 | 出现即触发 | 停发/整改/重审 | 产品 + 开发 |

**重规划动作**（选一个并写理由）：保持计划+加缓冲｜重排顺序｜砍范围/降级 MVP｜拆波次｜暂停升级｜重新基线。重规划必须在触发后 1 个工作日内完成，并同步计划/台账/索引。

### 6.3 文档同步矩阵（产品侧）

| 变更 | 必更新 | 通知 |
| --- | --- | --- |
| C0 | PRD/AC、受理单、文档索引 | 受影响开发/测试（`DEC`） |
| C1 | PRD/AC、原型、交付计划、UAT、需求池、产品计划 §0/§8/§10 | `CHG` → 开发/测试 |
| C2 | 上述 + 产品计划 §2/§3/§4、路线图、评审记录、发布计划 | `CHG` + 计划门 + 回执 |
| C3 | 上述 + 立项/商业论证、重审记录、合规/安全评估、回滚预案 | `CHG` + `RISK` + 重审/发布门 |

## 7. 计划回写与状态

- **计划是状态唯一入口**：`产品/产品计划.md` §0 写当前阶段/门/下一动作/待回执/健康度；§10 写执行日志；§12 写交接摘要；详细交接在台账。
- **每次发送/接收/回执/变更**：更新 `交接台账.md` → 产品计划 §0/§10/§12 → 文档索引 → `activeContext.md`。四者同轮，不得只改一处。
- **计划状态**：`草稿`（未确认）→ `已确认`（计划门过）→ `执行中`（已开工）→ `变更中`（C2/C3 或重规划）→ `待关闭`（交付/验收完成）→ `已关闭`（复盘/归档）。
- **健康度**：绿=无阻断，且**须回执项**已齐（无回执要求不计入）；黄=有非阻断缺口/正式签收待回执/依赖延期但可恢复；红=阻断缺口/关键门未过/发布风险。红色必须在 §0 写升级对象与下一步。
- **禁止**：用“已发送”冒充“已接收”；用“计划写了”冒充“已执行”；正式签收场景用聊天结论替代回执/变更单。

## 8. 禁止事项

1. 未过门就发 PRD/原型/提测/发布包。
2. 交接包无清单、无版本；或包内缺 `04-回执/` 空白模板文件（模板必带，不要求默认已填写）。
3. 正式签收场景下发送方替对方签收；用「已接收」冒充未签收。日常外发不以「未写回执」当作阻断。
4. 口头变更、先做后补单、边做边改 AC。
5. 把密钥/凭据/真实 PII 放进交接包。
6. 用旧版本包继续实施；有新版本仍引用旧包。
7. 交接包内容与主副本不一致；包内文档被接收方修改后当主副本。
8. 变更后不更新计划/台账/索引，导致下一角色按旧口径执行。
9. 多包同仓仍要求用户把包拷/转到对方 `资料/交接/`（应同仓直读）。

## 9. 参考实践（方法参考，非逐字复制）

- Three Amigos / Example Mapping / ATDD：需求、开发、测试在编码前用示例对齐 AC 与 oracle（<https://www.agilealliance.org/glossary/three-amigos/>）。
- GitHub Spec Kit：specify → plan → tasks → implement，规格与任务分离（<https://github.com/github/spec-kit>）。
- ADR（Nygard）：架构决策记录，决策与影响可追溯（<https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions>）。
- Google Engineering Practices：代码评审标准与变更小步化（<https://google.github.io/eng-practices/>）。
- Team Topologies：团队交互模式与交接边界（<https://teamtopologies.com/>）。
- DORA / Google SRE：变更失败率、MTTR、发布就绪与回滚（<https://dora.dev/>、<https://sre.google/>）。
- ISO/IEC/IEEE 29148、ISTQB：需求规格质量与风险驱动测试、准入准出（<https://www.iso.org/standard/72089.html>、<https://www.istqb.org/>）。
- Scrum/Kanban：Definition of Ready / Definition of Done、WIP 限制与流动效率（<https://scrumguides.org/>）。
