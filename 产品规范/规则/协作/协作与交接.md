# 协作与交接（产品轨）

> **读取级别：参考**（按节读取；按 `读取索引` 只读当前 step 节，禁止通读全本）。

> **目的**：把“产品 → 开发/测试、开发/测试 → 产品、变更 → 所有角色”的交接，从口头约定变成**可复制、可回执、可追踪**的交接包。
> **独立性**：本包可单独使用；接收方可以是开发/测试角色、用户本人或外部团队，**不要求对方安装同套包**。对方未装包时，把交接包当作普通文档阅读并按回执模板回复即可。
> **单一出处**：交接包结构、回执、变更分级、重规划触发以本文为准；模板见 `规则/模板/90-交接与收尾/交接包说明模板.md`、`规则/模板/90-交接与收尾/交接清单模板.md`、`规则/模板/90-交接与收尾/接收回执模板.md`、`规则/模板/90-交接与收尾/交接台账模板.md`。
> **读取时机**：`handoff.*`、`prd.handoff`、`prototype.handoff`、`deliver.*`、`change.apply`、`defect.apply`、计划交接节；不需要每次开工通读。

## 1. 角色与决策权

| 角色 | 决策权 | 主要交接责任 |
| --- | --- | --- |
| 产品负责人（A） | 范围、优先级、AC、UAT、发布决策 | 需求/设计/计划/变更/UAT/发布交接包；对开发/测试的澄清给书面结论 |
| 开发负责人（R/C） | 可行性、技术方案、工作量、提测 | 需求澄清、方案风险、提测、修复/回归、发布结果 |
| 测试负责人（R/C） | 测试策略、oracle、准出建议 | 测试计划/用例、缺陷、测试报告、发布后验证 |
| 用户/业务（A/C） | 业务目标、预算、风险接受 | 确认范围/优先级/发布；接收对外材料 |
| 运维/客服（C/I） | 部署、监控、客服口径 | 发布/回滚/公告/培训交接 |

**原则**：一个交付物只有一个 A；R 做、C 咨询、I 知会。决策写进受理单/变更单/决策记录，不留在聊天里。产品不替开发做技术决策，开发/测试不替产品改业务口径。

## 2. 协作节奏（什么时候必须拉齐）

| 节点 | 触发 | 参与 | 必须产出 | 门 |
| --- | --- | --- | --- | --- |
| 需求澄清（Three Amigos） | PRD 定稿前 / 开发方案前 / 测试计划前 | 产品 + 开发 + 测试（可缺省） | 需求澄清记录：问题/示例/AC/可测性/oracle/待决 | 不另设门；结论回写 PRD/AC |
| 设计交接 | 原型评审通过后 | 产品 + 开发（+测试） | 开发交接 + DES 交接包 | `confirm_prototype` |
| 计划对齐 | 产品计划/排期确认后 | 产品 + 开发 + 测试 | 范围/里程碑/测试窗口/依赖 | `confirm_plan` |
| 提测交接 | 开发自测/门禁通过后 | 开发 + 测试（+产品） | 提测单 + QA 交接包 | 完成门 `COMPLETE` |
| 测试准出 | 测试执行完成/报告前 | 测试 + 产品 + 开发 | 测试报告 + TEST 交接包 | 报告门 PASS/CONDITIONAL |
| 发布就绪 | UAT 通过后 | 产品 + 开发 + 测试 + 运维 | UAT/发布决策/回滚/监控 + REL 交接包 | `confirm_release` |
| 复盘 | 发布后/事故/迭代关闭 | 全体 | 复盘 + 行动项 + RETRO 交接包 | 无 |

> 开发/测试角色不存在时，由用户本人代收；交接包照常生成，接收回执由用户确认。**不因缺角色阻塞**。

## 3. 交接矩阵（产品轨）

### 3.1 产品发出（必须用交接包）

| 时机 | 类型 | 接收方 | 最小必带 | 前置 |
| --- | --- | --- | --- | --- |
| 产品计划确认后 | `PLAN` | 开发、测试 | 产品计划 §1～§4、范围、里程碑、依赖、风险 | `confirm_plan` |
| PRD 定稿后 | `REQ` | 开发、测试 | PRD（`status: APPROVED`）、AC、原型/开发交接、范围/非目标、优先级、风险、UAT 标准 | `confirm_prd` + PRD 门 READY |
| 原型评审后 | `DES` | 开发 | 开发交接、原型、设计评审、可用性、tokens、状态矩阵 | `confirm_prototype` |
| 排期后 | `PLAN` | 开发、测试 | 交付计划、里程碑、测试窗口、依赖 | 排期已确认 |
| 变更批准后 | `CHG` | 受影响开发/测试 | 变更单、更新后的 PRD/AC/原型、影响矩阵、要求、截止 | `confirm_change`（计划级叠加 `confirm_plan`） |
| 产品缺陷处置后 | `BUG` | 开发或测试 | 缺陷处置单、PRD/设计依据、相符证明、新口径、验收、指派 | `confirm_change` + 回写门 |
| UAT 完成后 | `UAT` | 开发、测试 | UAT 记录、逐条 AC 结果、遗留/条件、发布建议 | UAT 门 READY |
| 发布决策后 | `REL` | 开发、测试、运维 | 发布决策、窗口、公告/客服/监控、回滚责任 | `confirm_release` |
| 复盘后 | `RETRO` | 开发、测试 | 复盘、行动项、负责人/截止/验收 | 无 |
| 答疑/裁决 | `DEC` | 提问方 | 问题、结论、依据、影响、生效版本 | 无（书面留痕） |

### 3.2 产品接收（必须签收）

| 时机 | 类型 | 来源 | 产品动作 |
| --- | --- | --- | --- |
| 开发需求澄清 | `CLAR` | 开发 | 读问题/影响 → 答复 `DEC` 或变更 `CHG`；更新受理/PRD；回执 |
| 提测通知 | `QA` | 开发 | 记录提测/构建/已知问题；准备 UAT；回执（不需要 UAT 时说明） |
| 开发任务/排期 | `PLAN` | 开发 | 读取任务/里程碑/依赖；同步产品计划 §4/§7；回执 |
| 测试报告/准出 | `TEST` | 测试 | 读覆盖/缺口/P0/遗留；决定 UAT/发布；回执 |
| 产品缺陷证据 | `BUG` | 测试 | 分诊/处置；回执；必要时出 `CHG` 给开发 |
| 开发评估单 | `BUG` | 开发 | 五选一评审；回执；必要时出 `DEC`/`CHG` |
| 变更通知 | `CHG` | 开发/测试 | 影响评估；更新 PRD/计划；回执；必要时反向通知 |
| 发布结果 | `REL` | 开发 | 更新 UAT/发布记录/复盘；回执 |
| 缺陷修复/回归 | `FIX` | 开发/测试 | 按 AC 验证；关闭/重开；回执 |

## 4. 交接包规范

### 4.1 目录与命名

```text
产品/交接/
├─ 交接台账.md                         # 唯一登记（状态/回执/影响）
└─ {HO-ID}/
   ├─ 00-交接说明.md                   # 封面、目的、接收方动作、验收、回执要求
   ├─ 01-交接清单.md                   # 文件清单：版本/来源/包内路径/必读/用途
   ├─ 02-文档/                         # 必带文档快照（按原文件名）
   ├─ 03-证据/                         # 必要证据副本（截图/日志/报告；脱敏）
   └─ 04-回执/
      └─ 接收回执.md                   # 空白模板；接收方填写后回传
```

- **ID**：`HO-{yyyyMMdd}-{NN}-{类型}-{发起方}2{接收方}`，例 `HO-20261024-01-REQ-PM2DEV`。类型见 §3；发起/接收用 `PM/DEV/QA/OPS/BIZ`。
- **版本**：包内文档带版本/日期；新版本新建 `...-v2` 目录，不覆盖旧包。`01-交接清单.md` 写 `取代：{旧ID}`。
- **快照**：`02-文档/` 是**生成时快照**，不是主副本；主副本仍在 `产品/{版本或主题}/`。接收方只读，不改包内文件。
- **大文件**：PRD/原型/报告等文本默认复制；超大二进制/设计源文件可只在清单写源路径 + 可选 `附件/`，但必须在 `00-交接说明.md` 写明“需另行获取”，不能假称包内完整。
- **安全**：密钥/凭据/真实 PII 不入包；截图脱敏；客户数据只留摘要。

### 4.2 生成步骤（`handoff.send`）

1. **冻结来源**：确认门已过、文档状态正确（PRD `APPROVED`、原型已评审、UAT READY）；记录版本/日期/构建。
2. **选类型与接收方**：按 §3 选最小必带；缺必带 → 不发送，列缺口与责任人。
3. **复制**：必带文档进 `02-文档/`；证据进 `03-证据/`；保留原文件名，不编辑内容。
4. **写说明与清单**：按模板写 `00-交接说明.md`、`01-交接清单.md`；清单逐项写源路径、版本、包内路径、必读、用途。
5. **自检**：运行 `python 产品规范/规则/tools/validate_handoff.py <包路径>`（可用时）；缺件/占位符/版本不符先修。
6. **登记**：更新 `交接台账.md`（状态=`已发送`）、产品计划 §0/§12、文档索引、`activeContext.md`。
7. **告诉用户**：输出【交接包已生成】，给路径、接收方、必带清单、阻断项、回执截止、复制方法；**不得写“已交接/已接收”**，只写“已生成/已发送”。

```text
【交接包已生成】
- 交接：{HO-ID}｜{类型}｜{发起方} → {接收方}
- 路径：产品/交接/{HO-ID}/
- 复制：把整个 {HO-ID} 文件夹复制给{角色}；对方从 00-交接说明.md 开始，按 01-交接清单.md 核对
- 必带：{3～7 份关键文档}
- 阻断/待决：{…；无则「无」}
- 回执：{yyyy-MM-dd HH:mm} 前填写 04-回执/接收回执.md 并回传
- 状态：已发送（未收回执，不算已交接）
```

### 4.3 接收与回执（`handoff.receive`）

1. 把整包复制到 `产品/资料/交接/{HO-ID}/`（外部输入，只读）；先读 `00`，再按 `01` 核对。
2. 核对五件事：清单文件是否齐、版本/日期是否对、是否有阻断缺口、是否有互相矛盾、是否有需产品拍板项。
3. 结论三选一：**接受** / **有条件接受**（列非阻断缺口/假设/责任人/截止） / **退回**（列阻断缺口与需要补什么）。
4. 填写 `04-回执/接收回执.md`，回传发送方；**未写回执 = 未接收**。
5. 更新自己的计划/文档/索引：计划 §0/§7/§8/§10/§12、UAT/发布记录、需求池/受理单、`activeContext.md`。
6. 若包内是变更通知 → 走 §6；若含实质变更 → 先 `confirm_change`/`confirm_plan`，不得边执行边改口径。
7. 发送方收到回执后更新台账：`已接收`/`有条件接收`/`退回`；退回需补件后发新版本，旧包标 `已取代`。

**时限（默认，可项目覆盖）**：普通交接 1 个工作日；阻断/提测/发布 4 小时。超时由发送方在台账标 `待回执` 并升级给用户；**不得替对方签收**。

## 5. 交接完成判定

| 状态 | 含义 | 能否进入下游 |
| --- | --- | --- |
| `草稿` | 包未生成完/未自检 | 否 |
| `已发送` | 已生成并交给对方，未收回执 | 否（只能准备，不得声称已交接） |
| `已接收` | 回执=接受，清单齐 | 是 |
| `有条件接收` | 回执=有条件，非阻断缺口有主/截止 | 是，条件进计划风险 |
| `退回` | 回执=退回，阻断缺口未解 | 否；补件后发新版本 |
| `已取代` | 有新版本包 | 否；以新版本为准 |
| `已关闭` | 下游工作完成/验收关闭 | 是（作为历史） |

**硬规则**：提测、UAT、发布、变更实施前，必须有对应包的 `已接收/有条件接收` 回执；否则只能报“待交接/待回执”。

## 6. 变更与计划自适应

### 6.1 变更分级

| 级别 | 判定 | 例子 | 审批 | 计划动作 | 交接 |
| --- | --- | --- | --- | --- | --- |
| `C0` 澄清/纠错 | 不改变范围/AC/资源/里程碑 | 文案、口径、笔误 | 无（书面留痕） | 就地更新，不重基线 | `DEC`，受影响才发 |
| `C1` 同范围增量 | 在已批准范围内增/改 AC、任务、用例 | 补边界、补状态、补回归 | 产品负责人 | 更新任务/用例/计划 §0/§10 | `CHG` + 回执 |
| `C2` 范围/里程碑/资源变化 | 范围、优先级、版本、窗口、验收口径变化 | 加需求、砍范围、延期 | `confirm_change` + `confirm_plan` | 重新基线；更新路线图/排期/UAT/测试计划 | `CHG` + 回执 + 重过受影响门 |
| `C3` 战略/架构/合规/破坏性 | 商业模式、架构、合规、破坏性接口/数据 | 换方案、迁移、合规要求 | 立项/重审 + 发布门 | 重跑发现/方案/评审/发布；回滚演练 | `CHG` + `RISK` + 回执 |

> 不允许把 C2/C3 拆成多个 C0/C1 绕过门；拆批必须写清总变更单与子项。

### 6.2 重规划触发

| 触发 | 默认阈值 | 动作 | 负责人 |
| --- | --- | --- | --- |
| 基线变化 | 范围/AC/里程碑/验收/发布窗口 | 按 C2/C3 重基线 | 产品 |
| 关键依赖延期 | > 2 个工作日或 > 阶段工期 10% | 重排/加缓冲/升级 | 产品 + 开发 |
| S1/S2 缺陷或准出失败 | 出现即触发 | 停轮/修复/重测；评估发布 | 产品 + 测试 |
| 环境/数据不可用 | 测试 > 4 小时；开发 > 1 个工作日 | 降级/换环境/暂停 | 开发/测试 |
| 产能变化 | > 20% | 砍范围/拆波次/延期 | 产品 |
| 合规/安全事件 | 出现即触发 | 停发/整改/重审 | 产品 + 开发 |

**重规划动作**（选一个并写理由）：保持计划+加缓冲｜重排顺序｜砍范围/降级 MVP｜拆波次｜暂停升级｜重新基线。重规划必须在触发后 1 个工作日内完成，并同步计划/台账/索引。

### 6.3 文档同步矩阵（产品侧）

| 变更 | 必更新 | 通知 |
| --- | --- | --- |
| C0 | PRD/AC、受理单、文档索引 | 受影响开发/测试（`DEC`） |
| C1 | PRD/AC、原型、交付计划、UAT、需求池、产品计划 §0/§8/§10 | `CHG` → 开发/测试 |
| C2 | 上述 + 产品计划 §2/§3/§4、路线图、评审记录、发布计划 | `CHG` + 计划门 + 回执 |
| C3 | 上述 + 立项/商业论证、重审记录、合规/安全评估、回滚预案 | `CHG` + `RISK` + 重审/发布门 |

## 7. 计划回写与状态

- **计划是状态唯一入口**：`产品/产品计划.md` §0 写当前阶段/门/下一动作/待回执/健康度；§10 写执行日志；§12 写交接摘要；详细交接在台账。
- **每次发送/接收/回执/变更**：更新 `交接台账.md` → 产品计划 §0/§10/§12 → 文档索引 → `activeContext.md`。四者同轮，不得只改一处。
- **计划状态**：`草稿`（未确认）→ `已确认`（计划门过）→ `执行中`（已开工）→ `变更中`（C2/C3 或重规划）→ `待关闭`（交付/验收完成）→ `已关闭`（复盘/归档）。
- **健康度**：绿=无阻断、回执齐；黄=有非阻断缺口/待回执/依赖延期但可恢复；红=阻断缺口/关键门未过/发布风险。红色必须在 §0 写升级对象与下一步。
- **禁止**：用“已发送”冒充“已交接”；用“计划写了”冒充“已执行”；用聊天结论替代回执/变更单。

## 8. 禁止事项

1. 未过门就发 PRD/原型/提测/发布包。
2. 交接包无清单、无版本、无回执模板。
3. 接收方静默不签收；发送方替对方签收。
4. 口头变更、先做后补单、边做边改 AC。
5. 把密钥/凭据/真实 PII 放进交接包。
6. 用旧版本包继续实施；有新版本仍引用旧包。
7. 交接包内容与主副本不一致；包内文档被接收方修改后当主副本。
8. 变更后不更新计划/台账/索引，导致下一角色按旧口径执行。

## 9. 参考实践（方法参考，非逐字复制）

- Three Amigos / Example Mapping / ATDD：需求、开发、测试在编码前用示例对齐 AC 与 oracle（<https://www.agilealliance.org/glossary/three-amigos/>）。
- GitHub Spec Kit：specify → plan → tasks → implement，规格与任务分离（<https://github.com/github/spec-kit>）。
- ADR（Nygard）：架构决策记录，决策与影响可追溯（<https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions>）。
- Google Engineering Practices：代码评审标准与变更小步化（<https://google.github.io/eng-practices/>）。
- Team Topologies：团队交互模式与交接边界（<https://teamtopologies.com/>）。
- DORA / Google SRE：变更失败率、MTTR、发布就绪与回滚（<https://dora.dev/>、<https://sre.google/>）。
- ISO/IEC/IEEE 29148、ISTQB：需求规格质量与风险驱动测试、准入准出（<https://www.iso.org/standard/72089.html>、<https://www.istqb.org/>）。
- Scrum/Kanban：Definition of Ready / Definition of Done、WIP 限制与流动效率（<https://scrumguides.org/>）。
