# 文档质量标准（产品轨）

> **定位**：产品轨所有文档的**通用合格线**。模板只提供结构；本文件判断“这份文档能不能用、能不能作为决策依据”。
> **适用**：PRD、需求池、原型说明、产品计划、UAT、GTM、演示/一页纸/用户手册、复盘、交接包、工作日志。
> **原则**：按文档位置定内容；PRD 不写技术方案，UAT 不用开发自测替代，GTM 不写未证实宣称。

## 0. 冲突优先级

默认按规则/红线；用户指令冲突时先说明再等选择，用户选择后以用户为准。无冲突：用户明确指令 > 项目根 AGENTS > 包 AGENTS > 本文件 > 模板结构 > 历史文档。

模板与本文件冲突：按项目适配——先出拟改/原因/影响，用户确认后改本包模板/规则/技能并登记；不按旧口径硬产出。

## 0.1 模板 / 规则 / 技能的适配

- **可按项目适配**：发现模板/规则/技能不匹配或更好做法 → 先出拟改/原因/影响，用户确认后改本包并登记。
- **本地适配要留痕**：确认后在项目档案或本地适配记录登记（文件/原因/日期/确认人）。
- **模板是骨架、标准是底线**：按项目裁剪；不适用写不适用+理由；能靠产出文档解决的优先改产出（PRD/UAT/演示等），使其贴合实际并可验收。
- 不为凑模板写空话；不要求逐条机械填写。

## 1. 通用硬门槛（任一不满足 = 不合格）

1. **目的与读者明确**：开头能看出“给谁、解决什么、用来做什么决定”。
2. **事实有来源**：客户/用户原话、角色、数据、日期、指标、范围、优先级必须来自来源/研究/用户确认；无来源写「假设/待验证」，不得写成事实；未确认先问，禁止用默认/示例/历史值。
3. **范围有边界**：in/out、目标/非目标、本期/后续分开；out 有来源/理由/确认人。
4. **可验收**：每条需求/场景有可观察结果或 AC；禁“体验更好/更完善”等空话。
5. **证据可核对**：引用原文/数据/原型/访谈/评审记录；结论能回到来源。
6. **一致与追溯**：需求 ID/AC/原型/版本互相一致；不出现两套口径。
7. **状态与变更**：版本/日期/负责人/状态/变更记录齐；旧版归档。
8. **安全与合规**：无真实 PII/密钥；客户数据脱敏；合规/隐私边界写清。
9. **当前有效状态（硬）**：正式文档以当前最终状态为唯一事实来源。
   1. 只描述当前存在的功能、流程、规则和约束。
   2. 删除后直接移除相关表述；不追加「已删除 / 已废弃 / 不要再用xxx / 禁止xxx（因旧物）」等说明。现行仍生效的约束可写，那是现行规则，不是删后留痕。
   3. 不记录历史修改过程、原因、旧方案和已取消内容。
   4. 不为防误解而引入当前不存在的概念或对照物。
   5. 改完以最终状态落笔，保持简洁准确。
   6. 对用户的文档/结论输出写现行结论，不复述用户需求原文，不写「本次改了什么」。
   7. 禁止在正式正文记录变更原因与废弃史；留痕仅限受理/变更单 / **产品计划 §3.0 或迭代变更摘要（Brief+Delta）** / 工作日志 / 复盘 等允许载体，且不回流 PRD 常青正文。
   8. 不把未采纳的修改方案、对比草案写入正式文档。
   9. **常青格同属正式正文**：产品档案、计划/需求池控制面、资料索引现行行等只写当前落点与角色；接入/迁移/归档等事件进工作日志或归档清单；回写覆盖终态，不追加过程句。

> **说明性输出的例外**：用户明确要求“变更说明/版本对比/复盘/交接/培训”时，可按时间线写“此前→当前”的差异；该文本是说明材料，不是正式资产。必须标注来源/时点，不回流 PRD/方案/基线等正式正文；正式资产仍只写现行状态。

10. **语言克制**：禁辩解式/对比式/冗余括注、未经确认的“应该/可能”。
11. **不替开发/测试下结论**：业务规则/验收写清，技术方案/测试准出归开发/测试。

## 2. 产品文档类型矩阵

| 文档 | 位置/作用 | 必须具备 | 不应包含 | 合格判据 |
| --- | --- | --- | --- | --- |
| PRD | 业务需求合同 | 问题/用户/场景/范围/AC/NFR/非目标/来源/追溯；写前须理解+方案双确认 | 技术架构/DB/API 实现；未确认臆造；堆砌历史改了什么 | 开发可拆任务、测试可设计用例 |
| 计划 §3.0（默认）/ 迭代变更摘要（按需） | 本期业务+差量门面 | Brief + 增/改/删；默认写计划 §3.0；独立摘要仅仓外/归档/点名且唯一权威 | 完整 PRD 复述、双份差量表、技术实现 | 人类可扫清本期变化；下游可引用 ID |
| 需求池 | 需求候选管理 | 来源/证据等级/替代与代价/方案要点/确认状态/价值/优先级/状态 | 未双确认却承诺排期；竞品有→自动 Must | 可排序、可追溯、可看确认 |
| 竞品分析（S） | 选择性学习依据 | 竞品集合/证据链接日期/借·改编·不借/回绑问题/差异化 | 无证据空写领先；功能清单当需求 | 可支撑立项/定位确认 |
| 竞品对标（P） | 迭代差距管理 | 矩阵含本产品与≥2 竞品；差距→候选项；进版本有确认 | 自动已排期；无链接日期 | 可入池、可取舍 |
| 原型说明 | UI/交互依据 | 流程/状态/文案/异常/权限/断点 | 后端规则臆测 | 设计与开发可落地 |
| 产品计划 | 版本/里程碑控制 | 目标/范围/里程碑/依赖/风险/决策 | 开发详细排期 | 可检查、可调整 |
| UAT 验收（业务 SSOT） | 业务/产品签收 | AC/角色/数据/步骤/结果/证据/签收 | 开发自测替代；与开发工程侧 UAT 混用外发 | 逐条 AC 有结论；多包时外发签收认本模板 |
| 发布说明（客户版） | 客户/用户可见 | 已发布能力/入口/影响/升级方式 | commit/工单/技术实现；与开发「工程发布说明」混发 | 读者能判断「这版能多做什么」 |
| GTM | 上市/运营计划 | 人群/价值/证据/渠道/节奏/风险 | 未证实宣称/虚假数据 | 可执行、可合规审查 |
| 演示/一页纸/用户手册 | 对外表达 | 受众/场景/步骤/边界/术语 | 内部黑话、未公开信息 | 目标读者能懂 |
| 复盘 | 改进闭环 | 事实/根因/行动项/负责人/截止/验证 | 追责、空泛口号 | 行动项可验收 |
| 交接单文档（默认） | 跨角色外发 | 先择优形态；介绍+对方动作清晰；按需事实；结果合格线；禁外印流程元数据 | 整表套模、考卷体风险清单、密钥、见 `产品/…` 代正文 | 只拿本文即可懂情况并知道自己做什么 |
| 交接包 | 升包快照 | 00/01/必带快照；回执文件可空白；正式签收才填 | 密钥、未过门草稿、未命中触发却发包 | 接收方可独立核对 |
| 根 CHANGELOG | 项目发版史（仅开发维护） | — | 本包写入/补链/创建 | 本包不写；无开发包则不建 |
| 工作日志 | 本岗里程碑 | 日期/事件/结论/产出/遗留（发布决策可含对外变化摘要） | 根 CHANGELOG、台账全文 | 可扫；含接入/治理；≠发版史 |

## 3. 评审清单（交付前逐项过）

- [ ] 目的/读者/范围一句话能说清
- [ ] 客户/用户事实有来源；假设已标「假设/待验证」
- [ ] out/非目标有来源/理由/确认人
- [ ] 每条需求/AC 可观察、可验收
- [ ] 原型/文案/异常/权限状态齐
- [ ] 指标/数据有口径与来源
- [ ] 状态/版本/负责人/变更记录齐
- [ ] 无密钥/PII；引用可打开
- [ ] 当前有效状态：无「已删除/已废弃/不要再用」留痕；无历史过程/旧方案/未采纳草案；结论只写现行
- [ ] 不替开发/测试下结论

## 4. 参考基线（对齐，不照抄）

- ISO/IEC/IEEE 29148（需求工程）
- Diátaxis（按文档位置定位）
- Atlassian/Product School PRD 实践（问题/用户/AC/非目标）
- MADR（涉及产品技术决策时可引用）
- Keep a Changelog、Semantic Versioning（版本/变更）
- GitHub Docs：Issue Forms、PR 模板、Security Policy、Contributing
- WCAG 2.2（涉及 UI 可访问性）
- Google SRE Workbook（复盘/行动项）

## 5. 版本与构建标识（所有文档）

- **四个标识分开**：产品/测试版本（如 `{版本}`）、构建/制品（tag/commit/构建号/镜像 digest）、部署版本（build-manifest/`.deploy-rev`）、文档版本（文档自身）。**提测单只写实际部署版本**，不写文档版本/commit/tag/`.deploy-rev`；测试与验收只认实际部署版本；代码 commit 是追溯。
- **版本节奏**：按项目版本策略（A 发布候选/B 连续迭代）；产品/测试只记录版本与构建，不自行升版。
- **项目内可查**：项目/URL 必须提供版本查看方式（页脚、`/version`、`/health`、构建清单）；没有就补，不能靠文档 HEAD。
- **文档提交不改变构建**：禁止把 HEAD、文档 commit、文档 rev 当构建版本；代码不变，文档怎么提交都不影响被测版本。
- **提测单**：由**开发包**产出与冻结（提测单模板 + qa-handoff 技能）；产品轨不生成提测单。验收/UAT 冻结规则仍适用本包 UAT。
- **构建/发布不可变**：一次构建、同一制品晋级；变更出新版本；参考 12-Factor build/release/run、GitHub immutable releases。
- **证据**：UAT/验收记录部署版本、环境、版本查看证据；构建/commit 由开发在部署记录中维护，测试无需读取本地文件。

## 6. 维护

- 新增/修改模板时，同步更新本文件 §2 类型矩阵与模板索引。
- 发现“模板有结构但产出不可用” → 先修模板/标准，再修单份文档。
- 版本随包 `template_version` 更新；本文件不单独设版本号。
