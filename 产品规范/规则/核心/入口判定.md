# 入口判定（无显式口令时）

> **定位**：任意自然语言 → 选**最小可用** workflow/step。不依赖固定口令措辞；靠「信号抽取 + 意图类 + 项目状态」判定。
> **读取时机**：`AGENTS.md` §3 未命中、口令模糊、或用户用描述句提出任务时。
> **与口令表**：明确短命令仍优先；本文只补模糊入口，**不另造 workflow/门**。
> **技能**：路由后只读当前步技能；口语不能跳过必用技能。
> **边界**：产品定业务规则/NFR/AC；技术栈/DB/API/部署不归本包，可行性列问题交开发/用户。
> **单一出处**：自然语言路由；其它文件只引用。

## 0. 原则

1. **看意图与对象，不抠关键词**。同义说法等价；禁止「必须含某词才路由」。
2. **先定性再写长文**：单条未分类输入默认受理（`change`），不直接写全量 PRD。
3. **先理解客户问题，再写功能**：客户「想要 X」≠ 需求；还原谁/场景/问题后再分诊。
4. **有产品计划先续跑**：像进度/下一步且计划 §0 可路由 → 按计划，不另起。
5. **首条可纠正**：`reason=` 写清依据。

## 1. 每条消息先抽五元组（必做）

| 轴 | 问什么 | 取值示例（非穷尽） |
| --- | --- | --- |
| **动作** | 发现洞察、受理分诊、定义文档、设计体验、验收发布、展示对外、还是治理？ | discover / intake / define / design / accept / show / govern |
| **对象** | 在处理什么？ | 客户原声·反馈·访谈 / 单条诉求·抱怨·缺陷描述 / 需求池·竞品 / PRD·范围 / 原型·UI / 计划·路线图 / 平台缺陷 / 交接包 / 演示·对外材料 / 新产品空白 |
| **结果** | 结束时要什么？ | 洞察入池 / 受理与分诊结论 / PRD·评审 / 原型·设计评审 / 计划确认 / UAT·发布决策 / 演示材料 / 交接·回写 |
| **连续** | 新开、续跑、纠正？ | new / resume / correct |
| **体量** | 单点/跨模块/0→1/战略？ | P0～P3 初判；未知偏高一档 |

**快速启发（可叠加）**：

- 多条反馈/访谈/竞品/「这批需求」→ 对象偏客户原声或需求池（discover）。
- 一条对话/截图/链接/工单 → 对象偏单条诉求（intake）。
- 已有产品线 + 增量能力 → 非 new-product；全新品/无用户无竞品边界 → 才考虑 0→1。
- 附件=PRD 且要定稿/挑错 → define 的 review；只要写/补 → define 的 prd（范围未确认则先 intake/discover）。
- 平台产品缺陷/评估回流 → 平台缺陷对象。
- 「继续/下一步」+ 有 `产品/产品计划.md` → resume。

## 2. 意图类 → workflow（本包）

| 意图类 | 判定要点（通用） | 默认入口 |
| --- | --- | --- |
| A 单条受理 | 一条未分类诉求/问题/缺陷描述；要定性或处置 | `change.intake` |
| B 批量洞察 | 多来源发现、竞品、需求池盘点、客户研究 | `prd.discover` |
| C 范围定义 | 写/补/改 PRD；或 PRD 评审定稿 | 范围已确认 → `prd.prd` / `prd.review`；否则先 A 或 B |
| D 0→1 立项 | 新产品/新业务空白，要 Go/Hold/Kill 或最小定义 | `new-product` |
| E 版本规划 | 目标/KR/路线图/版本范围（非单条受理） | `plan` |
| F 体验设计 | 信息架构/线框/视觉/高保真/设计评审 | `prototype` |
| G 交付验收 | 排期、跟进答疑升级、UAT、发布检查、复盘 | `deliver`（答疑类可 `change` 到答复止） |
| H 平台缺陷 | 拉取/分析/回写产品侧平台单 | `defect` |
| I 对外展示 | 演示、手册、Deck、一页纸、彩排 | `showcase` |
| J 协作交接 | 发包/收包/变更通知/重规划 | `handoff` |
| K 仓库治理 | 接入、资料、清理、技能体检 | `onboard` / `skill-audit` |

**动作×对象速查**：

| 动作 ↓ \ 对象 → | 单条诉求 | 客户原声/池 | PRD | 空白新品 | 计划 | 原型 |
| --- | --- | --- | --- | --- | --- | --- |
| discover / understand | A | B | C（理解或评审） | D | E | F |
| define / produce | A→C | B→C | C | D→C | E | F |
| accept / decide 发布 | G | — | G | — | G | — |
| show | I | I | I | I | — | I |
| govern | K | K | K | K | K | K |

技术可行性争议 → 仍走 A/C 记录问题，**不**在产品包内定技术栈。

## 3. 项目状态修正

1. 档案中的协作/流程偏好覆盖启发式。
2. 无计划、无定稿 PRD、单点输入 → **轻量**：A 受理 + P0/P1 轻量 PRD 节。
3. 已有计划/多版 PRD/原型/交接 → **完整**；P2+ 不降级。
4. resume + 计划 §0 可路由 → 按计划阶段，不无故切到 A。
5. 无档案 → §5 摸底；不阻塞单条 A。

## 4. 置信度与一问

| 情况 | 做法 |
| --- | --- |
| 唯一意图类 | 直接路由 + `reason=` |
| 只差文档厚度 | 选更轻；可改道 |
| A vs D、A vs C、B vs C 影响是否立项/写全量 PRD | 一问 + 推荐 |
| 「理解」还是「评审定稿」不清 | 一问；默认先理解不擅自定稿 |
| 连续 3 轮无新信息 | 按推荐或缩到单条受理 |

## 5. 中途摸底

1. 读 README、`产品/`、需求池/计划/PRD（若有）。
2. 能推断产品与用户 → 继续；假设入收尾。
3. 缺「谁是用户/当前版本」且影响分诊 → 一问。
4. 建议事后接入；不阻塞 A/B。

## 6. 首条格式

```text
route=workflow:<id> | step=<id> | role=<agent> | mode=… | reason=<意图类+信号> | next_action=…
```

- `change` 加 `type=<初判>`；可附 `intent=<A-K>`、`input=`。
- 偶然出现「PRD/计划/变更」≠ 口令命中。
- 不跳过理解确认、变更留痕、AC、发布门。

## 7. 反模式

- 当口令同义词表做字符串匹配。
- 单条诉求直接写全量 PRD 或排期。
- 把「想要 X」写成需求事实，不还原问题、不标假设。
- 已有产品线却走 0→1；或空白新品却当小变更。
- 在产品链拍板技术实现。
- 加隐藏门或跳过门/技能；`reason` 缺失。
