# 澄清追问环（产品轨）

> **单一出处**：澄清的触发、提问格式、需求理解包、缺口清单、停止条件与落盘。`AGENTS.md` §0.1、workflow 步注、技能只引用本文，不另写一套。
> **与确认门的关系**：确认门=执行授权（`hitl`）；澄清=理解对齐。门不能替代澄清；澄清答复不自动授权执行，仍需按步过门。
> **读取时机**：任务开始、输入含客户需求/文档/原型、准备写 PRD/计划/优先级/范围前。
>
> **总规则（强制）**：先读规则/技能/档案/PRD/数据并做分析，再问用户；**只问影响意图、范围、验收、风险且 AI 无法自行确定的问题**；技术实现/字段/接口/原型细节由 AI 查规则与技能后给建议，不逐条问用户。首轮通常 0～1 个问题，最多 3 个高影响问题；用户确认理解/方案后执行。95% 仅参考，不作为停止条件。确认门不是澄清。

## 1. 问什么 / 不问什么

**必须问用户（AI 无法从资料推断，且会影响结果）**：

1. 目标/要解决的问题、用户与场景、成功标准。
2. 范围/非目标、优先级与取舍。
3. 只有用户知道的业务规则、约束、验收差异。
4. 客户说法/文档/原型/数据冲突需要用户裁决。
5. 高风险/不可逆动作的接受度（定价、合同、合规、隐私、对外承诺、发布）。

**AI 自行分析，不问用户**：

- 技术实现、字段口径、接口设计、原型细节、状态机实现、异常处理方式、性能方案、兼容方案。
- 先查 `规则/`、`技能/`、`产品档案.md`、PRD/计划/需求池/数据/工单/原话；能确定就直接给方案/建议。
- 只有技术/方案选择会改变用户可见范围/AC/客户承诺时，才升级为“需要你拍板”的取舍题，并附推荐。

**可以免问**：纯信息查询、机械整理、已由档案/正式产物唯一确定且无分支的低风险操作；免问也给一行理解回执。

## 2. 首轮固定动作：先分析，再问 0～1 个关键问题

首轮回复按此顺序，不得先写 PRD/方案/长清单，也不得先列一串问题：

```text
【我的理解】{谁/场景/问题/现有替代/代价/要什么结果/怎么算成功/不做什么，5～8 行}
【我已按规范/技能分析】{业务/范围/优先级/风险建议；技术细节不抛给用户}
【需要你拍板】{0～1 个最关键问题；附推荐；没有则写“无阻塞问题”}
【其余假设】{不影响方向的假设；用户不反对即按此执行}
确认后我执行：{下一步}
```

- **首轮最多 1 个问题，总提问不超过 3 个高影响问题**；不把字段/接口/原型/技术实现等细节列成问题。
- **非机械任务至少给一次理解复述，请用户确认**；复述本身算确认，不必额外编问题。
- **先查后问**：能从档案、PRD、计划、需求池、数据、工单、原话确认的，先查并引用；只问查不到且会改变结论的。
- **问题可回答**：单选/短答/二选一优先；不问“你觉得怎么样”，不问实现细节。
- **附建议**：先给推荐答案 + 一句理由；猜测错了要显式改口。
- **问完就停**：等用户回答；不得自问自答，不得把“我先按 X 写”当已确认。
- **问题顺序**：谁/什么场景 → 现在怎么解决/代价 → 要达成什么结果 → 范围/非目标 → 业务约束/优先级 → 验收/指标 → 风险取舍；技术细节不进入提问列表。

## 3. 回答之后：更新理解，必要时才追问

每轮回答后：

1. 用 1-2 句更新理解与方案（不要重复整段）。
2. 把已回答内容记为“已确认”，不再重问。
3. 只有回答引出新的高影响缺口/冲突才追问；否则更新理解并给方案/建议。
4. 总提问不超过 3 个；超过说明需求本身不清楚，先帮用户收敛范围，不继续盘问。

**禁止**：把用户没说过的话写成客户需求；把“行业惯例/最佳实践/竞品也这样”当需求；把多个问题合并成一段叙述；在用户回答前继续产出下游产物。

## 4. 停止条件（无实质缺口 + 用户确认，不靠感觉）

同时满足才可停：

- [ ] 需求理解包核心项已填；方案/优先级已有 AI 建议；未知项只保留高影响缺口。
- [ ] 能复述：谁 / 在什么场景 / 遇到什么问题 / 现在怎么绕过 / 要达成什么结果 / 怎么算成功 / 明确不做什么。
- [ ] 关键冲突已裁决；未决项已标“假设”并有验证方式与责任人。
- [ ] 用户明确说“对/是/按这个来/可以”。
- [ ] 复述中的范围、目标、非目标与用户最后的表述一致。
- [ ] 剩余缺口只是低影响假设，或已给建议待用户确认，不需要继续盘问。

**不算确认**：“随便/你决定/看着办/应该可以/差不多/沉默/只回一个 OK 但没有对复述表态”。遇到这些 → 给两个具体选项再问一次，不要开跑。

**置信度锚点（参考值，不作为停止条件；以缺口清单和用户确认为准）**：

| 区间 | 含义 | 动作 |
| --- | --- | --- |
| <50% | 客户/问题不明 | 只问谁与什么问题，不产出 |
| 50-70% | 问题大致清楚，证据/范围有缺口 | 只问最高影响问题；技术/方案自行分析 |
| 70-85% | 问题与主场景清楚，优先级/验收有缺口 | 补关键业务缺口；方案给建议/假设 |
| 85-95% | 可复述，少数低影响项未定 | 复述确认；低影响项标假设 |
| ≥95% | 可复述且用户已确认 | 产出需求池/PRD/计划 |

连续 3 轮置信度不上升 → 换问法或回退到“谁/什么问题”重问；仍不上升 → 明确告诉用户“缺一个基础信息”，请其补充或缩小范围。

## 5. 完整复述模板（过门/落盘前）

```text
【理解复述】
- 客户/用户：{谁；角色；决策人/付费人/使用者}
- 场景：{什么情况下发生；频率}
- 问题：{现在遇到什么；现有替代/绕过方式}
- 代价：{时间/成本/风险/机会损失}
- 目标结果：{要达成什么；怎么算成功}
- 范围：{这次做什么}
- 非目标：{这次明确不做什么}
- 证据：{访谈/工单/数据/行为/竞品；来源+日期}
- 约束与风险：{预算/时间/合规/依赖}
- 未决与假设：{待确认项/假设/验证方式}
对 / 不对 / 补充？
```

产品轨另加“优先级初判与版本建议”；0→1 另加“市场/竞品/商业模式假设”。

## 6. 反迎合、反臆造、不自作主张

- 用户第一句话是“想要什么”，先还原“要解决什么问题”；不要从功能直接开始写 PRD。
- “应该/惯例/最佳实践/竞品也这样” → 追问具体场景、上次发生时间、代价、不做的后果。
- 单个客户/领导/销售的说法不等于市场需求；标样本量与来源，必要时写“待验证”。
- 用户改口：以最新回答为准；旧结论标作废，不留双真值。
- 不知道就说不知道；无来源写“假设/待验证”，不得写成事实。
- 不为了让用户满意而降低澄清标准；不把“用户没反对”当同意。
- 不替客户做优先级/范围/取舍；给建议可以，决定必须由用户确认。

## 7. 落盘（单一真值）

| 场景 | 落点 | 最少内容 |
| --- | --- | --- |
| 需求/问题受理 | 受理单 §2/§3 | 来源、原话、理解复述、Q/A、证据、假设 |
| 需求洞察 | `产品/需求池.md` / 洞察卡 | 来源、样本量、问题、现有替代、证据等级 |
| PRD | `产品/{版本}/01-需求与定义/PRD-*.md` §1/§2/§16 | 来源、理解复述、Q/A、假设、非目标 |
| 产品计划 | `产品/产品计划.md` §0/§8 | 目标依据、口径、待验证项 |

- 记录格式：`Q: … → A: …（来源/日期/裁决人）`。
- 用户裁决优先于竞品/数据/代码；有新证据才重开，重开另起一条，不覆盖旧裁决。
- 后续会话先读已确认记录，不重复问。

## 8. 例外与边界

- **用户点名“直接做/不用问”**：仍先给 3 行理解回执 + 假设清单；高风险/不可逆（定价/合同/合规/对外承诺/发布）至少问 1 个最高影响问题。只免等待，不免理解与留痕。
- **紧急客户问题/客诉**：先响应与止损；事后补需求理解与复盘，不把临时承诺写成 PRD。
- **非交互/自动化**：不猜；标 `blocked` + 待确认问题清单，交回人工。
- **确认门**：先澄清后过门；门只确认“是否执行/是否批准”，不替用户回答“客户要什么”。
- **确认门/菜单**：可一次展示多个授权选项，但不得夹带澄清问题。

## 9. 反模式（出现即停）

- 一轮列 3 个以上问题 / 发问卷；首轮把非关键问题也列出来。
- 把字段/接口/原型/技术实现等 AI 能查的细节逐条问用户，而不是先查规则/技能/档案给建议。
- 不带猜测的开放盘问。
- 用户答完不更新理解，直接写 PRD。
- 把“已读文档”当“已理解”；不引用章节/页码/原话。
- 把单个客户当市场；把竞品做法当需求；把领导偏好当优先级。
- 用“假设”绕过澄清，且不标假设、不写验证方式。
- 把“确认门”当“澄清”，或把“澄清回答”当“执行授权”。
- 置信度虚报 ≥95%，但复述不出“谁/场景/什么问题/怎么算成功/不做什么”。
