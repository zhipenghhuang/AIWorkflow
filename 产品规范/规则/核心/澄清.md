# 澄清追问环（产品轨）

> **单一出处**：澄清的触发、提问格式、需求理解包、方案确认、缺口清单、停止条件与落盘。`AGENTS.md` §0.1、workflow 步注、技能只引用本文，不另写一套。
> **与确认门的关系**：确认门=执行授权（`hitl`）；澄清=理解与方案对齐。门不能替代澄清；澄清答复不自动授权执行，仍需按步过门。
> **读取时机**：任务开始、输入含客户需求/文档/原型、准备写 PRD/计划/优先级/范围/设计方案前。
>
> **产品职责（强制）**：产品轨的核心不是少问、也不是替用户拍板，而是**把需求问清楚、把方案设计完善、并拿到用户明确确认**。未确认理解与方案 → 不得入池 / 不得写正式 PRD / 不得承诺版本范围。
>
> **总规则**：先读规则/技能/档案/PRD/数据并做分析，再问用户；问的是**意图、场景、业务规则、范围、验收、优先级、风险与方案取舍**；技术实现/字段口径/接口/组件细节由 AI 查规则与技能后给**建议方案**请用户确认，不把「怎么实现」甩回给用户逐条填空。置信度百分比仅参考，以缺口清单与用户确认为准。**意图有歧义时先确认再执行，意图已清可直跑**（§0）；需求/方案双确认仍走 `confirm_understanding`。

## 0. 意图理解确认（择优 · 防自作主张 · 忌死板）

> 与 `confirm_understanding`（需求+方案双确认）分工：本节是**本轮你要我干什么**的轻量对齐。  
> **原则**：AI 按口令清晰度与是否跨角色外发**择优**选档；禁止「凡落盘必弹长表」，也禁止「含糊口令直接写文件」。

### 0.1 何时必须停（`intent_needs_confirm`=真）

命中任一：口令含糊推不出唯一解；接收方/形态/产物 ≥2 种解读；跨角色外发交接/确认文且本任务未对齐；新开对外交付主题。→ 完整【意图理解】停等确认后再落盘。

### 0.2 何时可直跑（=假）

纯查询/机械整理；同任务意图已确认未变；本句或上下文已写死意图（一行回执即做）；已对齐任务内的自然续跑。拿不准按真。

### 0.3 三档

| 档 | 何时 | 做什么 |
| --- | --- | --- |
| **A 完整确认** | §0.1 | 【意图理解】五条 → 停等 → 再落盘 |
| **B 一行即做** | 意图已清 | `【意图】…` 一行后直写；当场纠正则停 |
| **C 免示** | 查询/续跑已确认 | 可不单独出示 |

```text
【意图理解】（仅 A 档）
- 你要我做：{动作}
- 接收方/受众：{…；无则「无」}
- 交付形态：{A/B/C/专模/HO}（推荐：…）
- 关键要点：{3～5 条}
- 明确不做：{…}
请确认：对 / 不对 / 补充…
```

步上 `confirm_intent` 仅 `intent_needs_confirm` 为真才停；未挂 hitl 的产出步不新增正式门，但若有歧义仍先按 §0.1～0.3 出示【意图理解】/一行回执并停等，不得静默落盘。

## 1. 问什么 / 不问什么

**必须问到清楚（AI 无法从资料唯一确定，且影响需求或方案）**：

1. 目标/要解决的问题、用户与角色（使用者/付费人/决策人）、场景与频率。
2. 现有替代/绕过方式、代价、不做的后果；怎么算成功。
3. 范围/非目标、优先级与取舍（做/不做/暂缓）。
4. 业务规则、约束、权限/数据边界、验收差异（只有业务方知道的）。
5. 方案关键取舍：主流程怎么走、关键分支/异常期望、规则门槛、体验原则；有选项时给推荐请选。
6. 客户说法/文档/原型/数据冲突 → 请用户裁决。
7. 高风险/不可逆：定价、合同、合规、隐私、对外承诺、发布窗口的接受度。
8. 0→1 另问：市场/竞品假设、最危险假设、验证方式与承诺信号（愿试点/预付/介绍等）。
9. 竞品学习影响定位/差异化/本期范围时：确认「借/改编/不借」或对标进版本的 Top N；细节见 `技能/competitive-intelligence-and-learning/SKILL.md`（不在澄清环另造竞品问卷）。

**AI 自行分析后给建议，再请确认（不问实现填空）**：

- 技术实现路径、表结构、接口形状、组件选型、性能方案、兼容方案 → 先查规则/技能给 1 个推荐方案（可附 1 个备选），用业务语言说明利弊，请用户确认「业务结果是否接受」。
- 字段/状态/文案草案 → 产品先起草，标「建议」，请用户改或确认；不要空表让用户从零填。
- 只有技术选择会改变用户可见范围/AC/客户承诺时，才升级为「需要你拍板」的取舍题。

**可以少问或免问**：纯信息查询、机械整理、已由档案/正式产物唯一确定且无分支的低风险操作；免问也给一行理解回执。免问**不等于**免确认：写 PRD/计划/定范围前仍须理解与方案已确认（可复用本会话已确认记录）。

## 2. 首轮固定动作：先分析，再开澄清环

> **只读/解释例外**：`入口判定` 意图类 **L** 或 `执行契约` §1.2 只读分析（解释/对比/诊断/复盘、不改文件不入交付链）→ **可不套**本节 5～8 行交付骨架；用理解要点 + 0～1 问（或分析说明）即可。写 PRD/计划/定范围等**交付链**仍走下方骨架与双确认。

首轮回复按此顺序，不得先写正式 PRD/定稿计划/长功能清单，也不得一次甩出问卷：

```text
【我的理解】{谁/场景/问题/现有替代/代价/要什么结果/怎么算成功/不做什么，5～8 行}
【推荐方案要点】{主流程/关键规则/范围取舍/成功标准；用业务语言；附 1 句理由}
【缺口清单】{按影响排序的未决项；标阻塞/非阻塞}
【本轮请确认/选择】{1 个问题，或 2～3 个互斥方案选项 + 推荐；没有阻塞可写「请确认理解与方案是否正确」}
确认后我继续澄清/落盘：{下一步}
```

- **先复述再追问**：非机械任务至少给一次理解复述；复述可请「对/不对/补充」，本身算确认动作。
- **多问是职责**：需求或方案未齐，必须继续问，直到核心包齐且用户确认；禁止为「省问」用假设填平关键缺口。
- **每轮节奏**：常规每轮 **1** 个实质问题；方案阶段可一次给出 **2～3 个互斥选项**请选（仍算一轮）。禁止一轮抛 ≥4 个无关问题或空白问卷。
- **先查后问**：能从档案、PRD、计划、需求池、数据、工单、原话确认的，先查并引用；只问查不到且会改变结论或方案的。
- **问题可回答**：单选/短答/二选一/选项卡优先；不问「你觉得怎么样」；不问纯实现细节填空。
- **附建议**：每个问题先给推荐答案 + 一句理由；猜错了要显式改口。
- **问完就停**：等用户回答；不得自问自答，不得把「我先按 X 写」当已确认。
- **问题顺序**：谁/场景 → 问题与代价 → 目标结果/成功标准 → 范围/非目标 → 业务规则与方案取舍 → 验收/指标 → 优先级 → 风险/合规 →（0→1）验证与承诺信号。

## 2.1 不确定项分流

- **阻塞项**：不决定就无法正确理解需求、定方案、过门或写 AC → **即时问**（本轮 1 题或选项）；不得用假设顶替。
- **非阻塞项**：不决定也能按推荐方案推进 → 可登记待决，但须在收尾与落盘写明；若用户愿意可继续多轮补齐。
- 禁止散问/重复问已确认项；阻塞项不得拖到收尾才首次出现。
- 回复后更新待决项/决策记录；已确认不重复。

## 2.2 两段确认（理解 → 方案）

产品澄清分两段，可同会话连续完成，但**两段都须用户明确表态**：

| 段 | 产出 | 用户要确认什么 | 未确认不得 |
| --- | --- | --- | --- |
| A 需求理解 | 理解复述 + 证据/假设 | 谁/场景/问题/代价/目标/非目标是否正确 | 分诊定性、入池承诺、排优先级 |
| B 方案设计 | 推荐方案要点（流程/规则/范围/验收口径） | 方案是否按此做；选项取舍 | 写正式 PRD、定版本范围、交设计/开发 |

- A 未过可继续只澄清，不出正式方案定稿。
- B 可基于 A 出 1 个主方案 + 至多 1 个备选；用户确认后才落 PRD/计划范围。
- `confirm_understanding` 门：出示时须同时带齐 A 复述与 B 方案要点（或显式写「方案段本轮不适用 + 理由」）；用户只回「OK」但未对复述/方案表态 → 不算过。

## 3. 回答之后：更新理解与方案，继续问到齐

每轮回答后：

1. 用 1～3 句更新理解与方案（不要重复整段）。
2. 把已回答记为「已确认」，不再重问。
3. 还有阻塞缺口 → 继续下一问；引出新冲突 → 当场裁决问。
4. 核心包已齐 → 输出完整复述 + 方案要点，请用户明确确认。
5. 连续 3 轮无新信息且仍缺关键项 → 换问法或收敛范围（给两个缩小范围的选项），说明「缺哪一条就无法负责地定方案」；不编造填平，不假装已懂。

**禁止**：把用户没说过的话写成客户需求；把「行业惯例/最佳实践/竞品也这样」当需求；在用户确认前产出下游正式产物；用假设冒充已确认方案。

## 4. 停止条件（核心包齐 + 双确认）

同时满足才可停澄清、进入入池/PRD/计划正式产出：

- [ ] 需求理解包核心项已填（见 §5）。
- [ ] 方案要点已写出且用户确认（或本步明确不适用方案段）。
- [ ] 能复述：谁 / 场景 / 问题 / 现有替代 / 代价 / 目标结果 / 成功标准 / 明确不做什么。
- [ ] 关键冲突已裁决；未决项已标「假设」并有验证方式与责任人（不得冒充已确认）。
- [ ] 用户对复述与方案明确说「对/是/按这个来/可以」或等价确认。
- [ ] 复述中的范围、目标、非目标、方案要点与用户最后表述一致。

**不算确认**：「随便/你决定/看着办/应该可以/差不多/沉默/只回一个 OK 但没有对复述或方案表态」；**只回范围选项（如选 A/B）而未对整包理解/方案表态**。遇到这些 → 给两个具体选项再问一次，或更新理解后等「对/按这个来」，不要开跑。

**置信度锚点（参考，不作为停止条件）**：

| 区间 | 含义 | 动作 |
| --- | --- | --- |
| <50% | 客户/问题不明 | 只问谁与什么问题；可多轮；不产出正式文档 |
| 50-70% | 问题大致清楚，证据/范围/方案有缺口 | 按缺口清单继续问；给方案草案标「建议」 |
| 70-85% | 问题与主场景清楚，规则/验收/取舍有缺口 | 继续问业务与方案取舍；补证据 |
| 85%+ 且未确认 | 可复述但用户未拍板 | **必须**出示完整复述+方案请确认 |
| 已双确认 | 理解+方案均确认 | 入池/PRD/计划；其后改口走变更 |

## 5. 完整复述与方案模板（过门/落盘前）

```text
【理解复述】
- 客户/用户：{谁；角色；决策人/付费人/使用者}
- 场景：{什么情况下发生；频率}
- 问题：{现在遇到什么；现有替代/绕过方式}
- 代价：{时间/成本/风险/机会损失}
- 目标结果：{要达成什么；怎么算成功}
- 范围：{这次做什么}
- 非目标：{这次明确不做什么}
- 证据：{访谈/工单/数据/行为/竞品；来源+日期+样本量/等级}
- 约束与风险：{预算/时间/合规/依赖}
- 承诺/推进信号（若有）：{愿试点/预付/介绍/排期承诺；无则「未收集」}
- 未决与假设：{待确认项/假设/验证方式}

【推荐方案要点】
- 主路径：{用户怎么完成关键任务}
- 关键规则：{门槛/状态/权限/数据边界}
- 异常与边界：{失败/拒绝时期望表现}
- 验收口径：{可观察的成功/失败}
- 不做与暂缓：{…}
- 备选（可选）：{备选 + 为何不推荐}

请确认：理解是否正确？是否按此方案推进？对 / 不对 / 补充？
```

产品轨另加「优先级初判与版本建议」；0→1 另加「市场/竞品/商业模式假设 + Go/Hold/Kill 建议依据」。

## 6. 反迎合、反臆造、不自作主张

- 用户第一句话是「想要什么」，先还原「要解决什么问题」，再一起设计方案；不要从功能清单直接开写 PRD。
- 「应该/惯例/最佳实践/竞品也这样」→ 追问具体场景、上次发生时间、代价、不做的后果。
- 单个客户/领导/销售的说法不等于市场需求；标样本量与来源，必要时写「待验证」。
- 用户改口：以最新回答为准；旧结论标作废，不留双真值。
- 不知道就说不知道；无来源写「假设/待验证」，不得写成事实。
- 不为了让用户满意而降低澄清标准；不把「用户没反对」当同意。
- **不替客户做优先级/范围/方案终裁**；必须给建议，决定必须由用户确认。
- **禁止少问偷跑**：关键需求或方案未齐时，不得以「先写一版你再看」代替澄清（可出标「草稿/待确认」的工作稿，但不得称已定稿/可开发）。
- 用户方案不适配档案/约束/证据或明显更差：指出依据与风险，给出更优主推（可附 1 备选）请确认；禁止为迎合静默照做。用户二次明确坚持 → 按覆盖执行并留痕。

## 7. 落盘（单一真值）

| 场景 | 落点 | 最少内容 |
| --- | --- | --- |
| 需求/问题受理 | 受理单 §2/§2.1/§3 | 来源、原话、理解复述、方案要点、Q/A、证据、假设、双确认状态 |
| 需求洞察 | `产品/需求池.md` / 洞察卡 / 访谈综合 | 来源、样本量、问题、现有替代、代价、证据等级、假设、确认状态 |
| 访谈 | `产品/{版本或主题}/01-需求与定义/访谈指南-*.md` + `洞察综合-*.md` | 指南问题、原话、主题、机会排序 |
| PRD | `产品/{版本}/01-需求与定义/PRD-*.md` §1/§2/§16 | 来源、理解复述、方案依据、Q/A、假设、非目标 |
| 产品计划 | `产品/产品计划.md` §0/§8 | 目标依据、口径、待验证项、决策记录 |
| 待确认/决策项 | `产品计划` §6/§8 或受理单 | 编号+事项/选项/建议/影响/默认/确认人 |

- 记录格式：`Q: … → A: …（来源/日期/裁决人）`。
- 用户裁决优先于竞品/数据/代码；有新证据才重开，重开另起一条，不覆盖旧裁决。
- 后续会话先读已确认记录，不重复问；改口走变更/受理。

## 8. 例外与边界

- **用户点名「直接做/不用问」**：仍先给理解回执 + 方案要点 + 假设清单请确认；高风险/不可逆（定价/合同/合规/对外承诺/发布）至少问清最高影响项。只免「闲聊式追问」，不免理解、方案要点与确认留痕。
- **紧急客诉**：先响应与止损；事后补需求理解与复盘，不把临时承诺写成 PRD。
- **非交互/自动化**：不猜；标 `blocked` + 待确认问题清单，交回人工。
- **确认门**：先澄清（理解+方案）后过门；门确认「是否执行/是否批准」，不替用户填「客户要什么/方案选哪个」。
- **确认门/菜单**：可一次展示多个授权选项，但不得夹带未决澄清题冒充已确认。

## 9. 反模式（出现即停）

- 一轮甩 ≥4 个无关问题或空白问卷；或相反——关键缺口不问就写正式 PRD/定范围。
- 把字段/接口/组件实现等技术填空甩给用户，而不是先给业务向方案请确认。
- 不带推荐的开放盘问；或只给方案不复述需求。
- 用户答完不更新理解/方案，直接写 PRD。
- 把「已读文档」当「已理解」；不引用章节/页码/原话。
- 把单个客户当市场；把竞品做法当需求；把领导偏好当优先级。
- 用「假设」绕过澄清，且不标假设、不写验证方式、不请确认。
- 把「确认门」当「澄清」，或把「澄清回答」当「执行授权」。
- 虚报「已齐/已确认」，但复述不出「谁/场景/问题/怎么算成功/不做什么/方案要点」。
- 用户说「你定」就直接定范围/优先级/对外承诺。
