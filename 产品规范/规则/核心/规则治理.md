# 规则治理（产品轨）

> 目的：防止规则膨胀、重复、冲突、无执行载体。维护/改规则时读；业务任务不读。
> 原则：一条规则一个 owner；能脚本检查的不写长文；新增前先合并/删除。

## 1. 预算

| 对象 | 上限（估算 tokens） |
| --- | ---: |
| `AGENTS.md` §0 硬节（每任务常驻） | ≤ 5,500 |
| `AGENTS.md` 全文（含口令表） | 不计入每任务预算；口令表仅路由未定/首次命中时读 |
| 常驻/必读规则 | ≤ 3,000 |
| 参考手册/playbook | ≤ 10,000（头部标 `读取级别：参考`，只读当前节） |
| 单个 `技能/<name>/SKILL.md` | ≤ 4,500 |
| 模板 | 不设 token 上限 |
| 单步读取总量 | ≤ 8,000 |

**读法**：每任务精读 `AGENTS` **§0 硬节**（非通读全文）；参考手册只读当前 step 节；技能命中才读；模板只读当前一份。§0 超预算优先并入 SSOT 指针，勿在口令表重复硬规则。

## 2. 单一出处

- 每条规则只在一个文件定义；其他位置只放指针 + 规则 ID。
- 高频重复（需求先确认、AC 可判定、评审独立、平台回写确认）必须合并。
- 阻断路径统一 `必须/禁止/不得`；`可/建议/按需` 只用于非阻断能力。
- 新增前先问：能否合并？能否脚本检查？能否删旧规则？三者都否才新增。

## 2.1 自适应规则写法（防过拟合）

规则写“判断维度、不变量、升级条件、失败回退”，不写“具体场景清单/固定口令/固定文件数/固定角色名”。示例只作校准，最多 2～3 个，并标“示例，非穷尽”。三层写法：**不变量（硬，必须/禁止）→ 判断维度（柔，按影响/风险/协调面）→ 示例（参考，非穷尽）**；禁止把示例写成不变量。

- 一条规则只回答：什么目标、看哪些信号、何时取轻/取重、何时停、失败怎么办。
- 能用门/脚本/检查表判定的，不写成长篇叙述；不能机器判定的，给“判断问题”而非“标准答案”。
- 新规则必须写“不适用/降级”路径；否则不得新增。
- 同一规则不在 AGENTS/技能/模板重复正文；只留指针。
- 维护时删除“只为某个项目/某次事故写死”的条款；必须保留的，标为项目适配并登记。
- 评审规则时问：换一个团队/产品/规模，这条还成立吗？不成立就改成维度或降为示例。

## 3. 规则 ID 与条件

- 格式：`PRODUCT-<域>-<序号>`，如 `PRODUCT-VER-02`。
- 每个 ID 对应：一句话不变量、执行载体（gate/script/human）、适用 step。
- 确认门只认 YAML `hitl`/`hitl_when`/`gate_when`；条件不满足跳过；不新增确认门；能用门禁检查的不靠追问。
- 条件门由外部事实优先；模型自评不确定按触发处理。

## 4. 规则卫生（维护时）

```powershell
powershell -ExecutionPolicy Bypass -File "产品规范/规则/tools/Test-Template.ps1"
powershell -ExecutionPolicy Bypass -File "产品规范/规则/tools/Test-DocHygiene.ps1"
python "产品规范/规则/tools/validate_workflow.py" "产品规范"
```

检查：引用/锚点、YAML、workflows→agents、版本单点、AGENTS/规则行数、读取索引挂载、孤立模板。
后续可加：token 预算、重复句、同范围“必须/可跳过”冲突、孤儿规则；未实现前人工核对。

## 5. 规则 eval（改规则时）

1. PRD 有 TBD 无责任人/期限 → 门必须 BLOCKED。
2. 评审人=作者 → 门必须 BLOCKED。
3. P2+ PRD status=APPROVED 但无评审记录/gate_id → 门必须 BLOCKED；轻量 PRD（prd_level=light）不要求独立评审。
4. 变更联动清单有“待补”无责任人/截止 → 门必须 BLOCKED。
5. 平台无回执仍写“已回写” → 门必须 BLOCKED。
6. 用户只要解释/对比、未要求改文件 → 必须走只读分析，不得强制评审/计划更新；未评审不得写“已定稿”。
7. 低风险只读/单点任务被强制升级完整 PRD/评审 → 视为过度流程，规则判定失败。
8. 新增规则只列具体场景/固定口令，无判断维度/降级路径 → 规则卫生检查失败。
9. 口令表/专模列表/类型码写成穷尽白名单（未标「示例非穷尽」）→ 规则卫生检查失败。
10. 与「内容优先·包按需」冲突的「必须整包 HO」死句 → 规则卫生检查失败。

## 6. 变更流程

1. 说明问题与现有规则冲突/冗余；
2. 优先合并/删除，再新增；
3. 改一处 owner；
4. 跑规则卫生 + 本节 eval；
5. 更新包 `AGENTS.md` `template_version`。**业务项目会话禁止**改项目根 `CHANGELOG.md`。仅在 **AIWorkflow 母版仓**维护、且有对使用者可见的包能力变化时，由母版维护会话用产品语言记入母版根 CHANGELOG（通常开发轨落笔）；纯内部措辞收紧可不记；
6. 旧规则删除或归档；现行文档遵守「当前有效状态」（见 `文档质量标准.md` §1 第9条）：不留“旧方案/已废弃/不要再用”等删后说明。
