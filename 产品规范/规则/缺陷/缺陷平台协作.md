# 缺陷平台协作（拉取 · 分析 · 处置）

> 读取：只读当前步节 + `规则/模板/30-评审与变更/缺陷文案模板.md`/`规则/缺陷/缺陷平台适配.md` 对应节；不要通读。

> **适用**：产品侧处理禅道/Jira/ONES 等平台的缺陷，尤其是测试直接提交并指派给产品、开发提交产品缺陷评估单待产品评审、产品缺陷待处置。  
> **来源两类**：`测试直提`（测试判定产品缺陷，直接指派产品，不经开发）与 `开发评估单`（开发判定产品缺陷，提交评估单并指派产品）。  
> **步骤顺序**以 `../workflows/defect.yaml` 为准；分析/处置方法见 `../技能/change-management/SKILL.md`；平台配置见 `产品档案.md` §7。  
> **确认门只认步上 hitl**：`confirm_remark`（平台回写）、`confirm_change`（处置）、`confirm_plan`（计划级）；本文不另造门。  
> **三包独立**：不假设开发/测试包同目录；产品处置单落本包目录，附件上传平台；开发/测试从平台读取，不引用本包内部路径。

## 0. 启动与输出门

```text
route=workflow:defect | step=… | role=pm-lead | next_action=LOGIN|LIST|PULL|ANALYZE|AWAIT_CONFIRM|WRITEBACK|…
```

| 时机 | 输出 |
| --- | --- |
| 启动 | 启动回执；缺平台配置时说明降级方式，禁只回「请提供编号」 |
| 拉取后 | 缺陷清单摘要（空清单也要输出）；标明来源=测试直提/开发评估单 |
| 开发评估单 | 已读评估单 + 复核结论（认可/修改后认可/不认可/判定实现/判定非问题） |
| 测试直提 | 分诊结论（产品缺陷/实现缺陷/非问题/重复/信息不足）+ 依据 |
| 每条分析后 | 分诊/依据/处置建议（写入受理单）、指派对象、目标版本 |
| 回写前 | 缺陷 id + 结论 + **备注全文** + 附件名 + 状态/指派变更 + 来源 |
| 回写后 | 回写结果 + 批末总结（成功/待回写/失败） |

## 1. 配置与前置

读 `产品档案.md` §7（provider/baseUrl/凭据来源/默认产品/提交方式/备注格式/适配定义/solutionChannel/附件能力）。  
若同项目已有开发/测试包配置（`项目档案.md` §3/§4、测试包环境基线 §13），优先复用其 provider、端点和凭据来源；本表只记产品侧差异，不重复存凭据。

| 情况 | 处置 |
| --- | --- |
| provider=无 / §7 未填 | 问一次是否现在配置 §7；不配置则降级为「用户粘贴缺陷内容/导出文件/评估单文档」或转 `change` 受理；禁反复索要编号、禁猜接口、禁套用未声明平台路径 |
| 平台可用 | 按 §2 拉取；按 §5 回写（禅道/Jira/ONES 等均经 §7 映射；内置路径仅 provider 声明时可用） |
| 平台暂不可用（登录/网络/权限） | 输出阻塞说明与已尝试；恢复后回 pull；禁静默排障取代输出；可临时改粘贴/`export` |
| 无回写权限/平台不支持附件或状态变更 | 走 `export`：出可复制回写包（备注 + 附件清单 + 动作），用户执行后回填；标记「待回写」 |
| solutionChannel=manual | 备注/方案附件读不全 → 请用户补关键备注或附件；禁只凭标题分析 |
| 仅对话/文档输入（无单号） | 转 `change` 受理；同一判定树；可后补平台单号 |

## 2. 拉取与读取

### 2.1 拉取范围

| 口令 | 默认范围 |
| --- | --- |
| 拉取/查看/我的产品缺陷 / 指派给我 | 当前产品账号被指派、未关闭的缺陷（含 active / resolved）；按默认产品/项目过滤 |
| 开发评估单 / 待产品评审 | 指派给产品、含开发评估单附件或备注「【产品缺陷·开发评估】」的单；先读评估单全文 |
| 测试直提产品缺陷 / 产品缺陷待确认 | 测试提交、类型=产品缺陷、指派给产品的单；读相符证明 + 证据 |
| 点名「产品缺陷 / 待产品确认」 | 先拉指派给当前账号的未关闭单，再按标题/类型/标签/备注分拣；平台有类型字段则叠加过滤 |
| 点名单号（#123 / Bug-123） | 仅拉这些单 |
| 点名「已关闭 / 全部」 | 按点名范围；默认不拉已关闭 |
| 粘贴/文档/导出文件 / 无平台 | 不拉平台；用户粘贴或读入评估单/缺陷正文 → 建档分析；可转 `change` |

空清单：输出「拉取 0 条」+ 范围/过滤条件，禁编造。

### 2.2 每条必须读全

标题、steps/复现、severity/pri、status/resolution、提交人/指派、版本/构建/环境、附件、近期备注/讨论、开发评估单/方案附件（如有）、关联需求/PRD（平台有则读）。  
`solutionChannel=manual` 或备注读不全 → 请用户补关键备注/附件；禁只看标题。  
来源判断：备注含「【产品缺陷·开发评估】」或附件名 `缺陷评估-BUG-…` → 开发评估单；测试提交且类型=产品缺陷，或标题/【提交摘要】含“产品缺陷” → 测试直提。两者都要读全文，不只读一句备注；混批逐条标来源，不整批套用同一处置模板。

### 2.3 建档

每条缺陷落一份 `产品/{版本或主题}/03-变更与缺陷/受理-{主题}-{yyyyMMdd}.md`（模板 `规则/模板/30-评审与变更/受理与处置模板.md`），编号用平台单号（如 `BUG-123`），并记录平台、来源类型、提交人、指派、状态、附件清单、开发评估单。批末输出清单摘要。  
判定/处置完成后，落 `产品/{版本或主题}/03-变更与缺陷/缺陷处置-{BUG-ID}-{主题}-{yyyyMMdd}.md`（模板 `规则/模板/30-评审与变更/产品缺陷处置模板.md`），作为平台附件指派开发/测试；产品缺陷必落，实现缺陷/非问题/重复/信息不足也至少给说明+指派。

## 3. 分析

按 `../技能/change-management/SKILL.md` §2/§3：

- 先分来源：**测试直提** → 产品独立定性；**开发评估单** → 产品复核开发判定与方案选项，不重做技术设计。
- 现网 ≠ PRD/设计 → **实现缺陷**：退回开发/测试，不改 PRD；给依据、复现/验收要求。
- 现网 = PRD/设计，但口径不合理/有风险 → **产品缺陷**：必须有 PRD/设计原文 + 现网/测试证据 + **相符证明**。
- 无设计依据 → 默认实现缺陷或补充信息；禁把实现缺陷甩成产品缺陷。  
  例外：来源=开发评估单且开发给出「需求缺口/设计口径不明」依据与业务影响 + **实现核对** → 按需求缺口受理，产品确认是否补 PRD/设计；不以「没有 PRD」直接否定；**不责备测试无资料时的默认实现缺陷分类**。
- 开发评估单 → 读全文，先核「实现核对」是否已排除未做/做错/缺段/接口错误/环境；缺核对 → 退回开发补齐，不直接改 PRD。再评：是否解决原问题、影响哪些 AC/范围/数据/合规/回归/回滚；**技术架构/实现细节不替开发评审**；结论五选一：认可方案/修改后认可/不认可方案/判定实现缺陷/判定非问题。
- 测试直提产品缺陷 → 结论五选一：产品缺陷/实现缺陷/非问题/重复/信息不足；产品缺陷必须给新口径/新文档/AC。
- **体验类**：不挡主路径且无重大风险 → 不在本轨硬开产品缺陷；转 `change` 按新需求/变更受理（对话或文档）。
- 技术不确定 → 开发 ADR/Spike；涉及产品取舍才回产品。

处置选项：立即修 / 下版 / 不修 / 退回开发 / 补充信息；开发评估单另加：认可方案 / 修改后认可 / 不认可方案 / 判定实现缺陷 / 判定非问题。影响评估与联动更新按 `../workflows/change.yaml` 的 assess/apply 执行。无平台时粘贴/`export`/文档输入走同一分析与处置，禁只认单一厂商平台。

## 4. 处置与联动

### 4.1 测试直提产品缺陷

- 判定产品缺陷 → 更新 PRD/AC/设计/原型；产出 `缺陷处置-{BUG-ID}-{主题}-{yyyyMMdd}.md`（改基线时另加变更单）；附件上传平台；**指派开发**；给验收标准/回归范围/目标版本。
- 判定实现缺陷 → 不改 PRD；说明与设计/需求的差异、复现与验收要求；**指派开发**。
- 判定非问题/设计如此/重复/信息不足 → 说明依据；**指派回测试**（重复需关联主单；信息不足一次列清缺什么）。
- 补充信息 → 保持打开；一次列清谁补/截止。

### 4.2 开发评估单

- 认可方案 / 修改后认可 → 产品确认新口径；更新 PRD/AC/设计；产出 `缺陷处置` 单（改基线时另加变更单）；**指派开发**；给验收标准/回归范围/目标版本。
- 不认可方案 / 判定实现缺陷 → 产品说明理由与依据；给实施要求/验收标准；产出 `缺陷处置` 单（说明+实施要求）；**指派开发**。
- 判定非问题 → 产品说明依据；产出 `缺陷处置` 单（说明+下一步）；默认**指派开发**（便于开发关闭/回执），备注明确指派测试时按备注执行。
- 补充信息 → 一次列清缺什么、谁补、截止；保持待产品评审。

### 4.3 通用联动

- 立即修（本期）→ 变更单（类型=缺陷修复）+ PRD/AC 更新 + 实质变更重审 + UAT 重验 + 通知开发/测试。
- 下版 → 需求池 + 产品计划 §2 路线图 + 通知；本期不改。
- 不修 → 记录理由、风险、接受人；必要时更新 PRD 说明。
- 退回开发（实现缺陷）→ 产品不改 PRD；给依据与复现/验收要求，回执开发/测试。
- 补充信息 → 一次列清缺什么、谁补、截止；保持打开。

**指派矩阵（按来源）**：

| 产品结论 | 来源=测试直提 | 来源=开发评估单 |
| --- | --- | --- |
| 产品缺陷 | 开发 | 开发 |
| 实现缺陷 | 开发 | 开发 |
| 非问题/设计如此 | 测试 | 开发（默认）或按备注指派测试 |
| 重复 | 测试（关联主单） | 开发（关联主单） |
| 信息不足 | 测试/提交人 | 开发/提交人 |

联动清单、重审、验证按 `../workflows/change.yaml`；产品侧只出产品结论/变更单/评审意见，不修改代码或技术方案。
