# 工作流（铁律 · 产物 · 提交 · 收尾）

> **步骤顺序**以 `../workflows/*.yaml` 为准；本文保留铁律、产物路径、拟提交与收尾骨架。  
> 计划与 0→1 见 `../技能/zero-to-one-product-definition/SKILL.md`；原型见 `../技能/prototype-and-interaction/SKILL.md`、`../技能/ui-visual-design-system/SKILL.md`；展示/文档见 `../技能/demo-storytelling/SKILL.md`、`../技能/product-docs/SKILL.md`、`../技能/presentation-design/SKILL.md`；交付细则见 `../技能/change-management/SKILL.md`、`../技能/uat-and-retrospective/SKILL.md`。确认门**只认**步上 `hitl`（标量用 `hitl_when`；列表各项带 `when`）。

## 1. 铁律（不可让）

1. **PRD 定稿前不排期**（`confirm_prd`）；未定稿只做洞察/评审。
2. **无变更单不实施变更**（`confirm_change`）；口头变更一律先落单。
3. **UAT 未过不发布**（`confirm_release`）；带条件通过须列遗留/责任/接受人。
4. 每条需求有**可判定验收标准**；无优先级不排期。
5. 引用可回查（来源+日期）；**禁臆造**数据/反馈/竞品结论。
6. 上线必须定义**成功指标与埋点**（不适用须写原因）。
7. **新产品先立项**（`confirm_go`）：未过立项不写全量 PRD；结论只能 Go / Hold / Kill。
8. **计划总领**：`产品/产品计划.md` 为版本/范围/里程碑的单点；计划未确认（`confirm_plan`）不进入 PRD/排期；计划不替代 PRD。单需求可用已批准的 `confirm_scope` 范围结论作为 PRD 依据，不强制完整产品计划。  
9. **原型未过设计评审不交开发**（`confirm_prototype`）；原型为静态 HTML/CSS，不等于生产代码。  
10. **受理先定性**：新需求/变更/缺陷/开发不确定先入受理单（`change` 工作流）并分诊；已在需求池/立项书/产品计划范围内，或点名补 PRD 的，可直接写/改 PRD，不重复受理。  
11. **产品缺陷有依据**：产品缺陷必须有 PRD/设计原文 + 现网/测试证据 + 相符证明；实现缺陷退回开发/测试，不改 PRD；无依据不得判产品缺陷。  
12. **联动不留旧版**：变更/缺陷处置后，按受理单 §6 更新所有受影响产物并标「已更新/不适用/待补」；未回写、未验证不得关闭。  
13. **平台回写有确认**：拉取/只读不设门；备注/附件/状态/指派回写必须 `confirm_remark`；备注与状态同轮；附件回查挂载；禁删缺陷；无权限/未适配走 `export`，不得声称已回写。  

## 2. 产物与过程（相对项目根）

```text
产品/                         # 全部产品产物唯一根（根目录仅 产品档案.md + activeContext.md）
├─ 产品计划.md                # 总领单点：总控表 + 路线图 + 本期执行
├─ 需求池.md                  # 滚动单点（去重/分级/状态）
├─ 用户文档/                  # 对外交付：快速开始/用户手册/FAQ/发布说明/培训材料
├─ 资料/                      # 唯一外部资料区（只放输入）
│  ├─ 项目文档/              # 外部 PRD/方案/设计稿/合规资料
│  ├─ 反馈/                  # 用户/客服/销售反馈
│  ├─ 调研/                  # 访谈/问卷/市场调研
│  ├─ 竞品/                  # 竞品资料/截图
│  ├─ 数据/                  # 数据导出/指标摘要
│  └─ 资料索引.md            # 来源/日期/版本/关联需求/状态
├─ {版本或主题}/
│   ├─ 立项书-{yyyyMMdd}.md    # 0→1（按需）
│   ├─ PRD-{主题}.md
│   ├─ 评审-{主题}-{yyyyMMdd}.md
│   ├─ 受理-{主题}-{yyyyMMdd}.md   # 需求/问题/缺陷受理与处置（change）
│   ├─ 交付计划-{版本}.md
│   ├─ 变更-{主题}-{yyyyMMdd}.md
│   ├─ UAT-{版本}-{yyyyMMdd}.md
│   ├─ GTM-{版本}.md           # 上市计划（按需）
│   ├─ 展示/
│   │   ├─ 展示需求-{受众}-{yyyyMMdd}.md
│   │   ├─ 故事线-{受众}.md
│   │   ├─ 演示脚本-{受众}-{yyyyMMdd}.md
│   │   ├─ 一页纸-{产品}.md
│   │   ├─ Deck大纲-{受众}.md
│   │   ├─ 演示检查单-{yyyyMMdd}.md
│   │   └─ 反馈记录-{yyyyMMdd}.md
│   ├─ 原型/
│   │   ├─ 设计情境-{主题}.md
│   │   ├─ IA-{主题}.md
│   │   ├─ wireframe-*.html
│   │   ├─ prototype/index.html
│   │   ├─ design-tokens.css
│   │   ├─ 工程化检查-{主题}.md
│   │   ├─ 设计评审-{主题}.md
│   │   ├─ 可用性走查-{主题}.md
│   │   ├─ 原型说明-{主题}.md      # 小项目可合并单文件
│   │   └─ 开发交接-{主题}.md
│   └─ 复盘-{版本}.md
└─ _归档/
   ├─ {yyyy-Qn}/产品计划-{yyyy-Qn}.md   # 季度快照（主档不移动）
   └─ {yyyyMMdd}-{版本}/               # 版本/结项整套移入（点名执行）
```

- 单点滚动：`产品/需求池.md` 只留现行状态；同一需求的多份文档就地更新，不写历史过程。  
- 受理/变更：一条需求/问题一份受理单；变更单只在改动已定稿基线时产生；受理单链接变更单、PRD、交付计划、UAT，联动清单未闭合不得关闭。  
- **计划总控**：每阶段完成 → 更新 `产品/产品计划.md` §0 状态/当前门/下一动作、§10 执行日志；「继续 / 按产品计划执行」从当前状态续跑；计划偏离走 §8 决策记录（变更/缺陷另走 `change` 受理与变更单）。  
- **计划状态**：草稿 / 已确认 / 执行中 / 变更中 / 待关闭 / 已关闭；计划未确认不进入 PRD/排期。  
- **主档不移动**：`产品/产品计划.md` 常青；季度结束复制当期执行到 `产品/_归档/{yyyy-Qn}/产品计划-{yyyy-Qn}.md`，主档保留 §11 历史索引并重置当前季度。  
- 归档：版本/换代/结项 → 当期目录整体移入 `产品/_归档/{yyyyMMdd}-{版本}/`（用户点名）；旧季度只归档快照，不移动主档。  
- 素材进 `产品/资料/`（按分类/日期/来源命名，登记 `产品/资料/资料索引.md`）；正式产物不进 `资料/`。  
- **资料 vs 工作文档**：`产品/资料/` 只放外部输入；`产品/用户文档/` 放对外交付文档；`产品/产品计划.md`、`产品/需求池.md`、`产品/{版本或主题}/` 是工作文档。

## 3. 拟提交（`hitl: confirm_commit` 时）

```text
【拟提交】
- 文件：{清单}
- .gitignore 现状：{一句}
请确认后执行。
```

未确认不得提交/推送；真实用户数据/PII 不入库。提交信息：`产品 {版本/主题}：{简述}`；一次提交一类文档。

## 4. 阶段护栏

- **洞察**：来源分层（用户/客服/数据/销售/竞品/合规）；每条留来源与日期；同问题去重合并。
- **0→1 / 立项**：先验证问题/市场/用户（立项书），Go 才进入定义；未过不写全量 PRD；Hold 列待验证项与责任人。
- **计划**：目标/KR/路线图/本期范围/里程碑进计划；计划确认后才排期；计划只做总领，不写需求细节。
- **原型/设计**：无设计师时 PM 出原型；IA → 线框 → 视觉 → 高保真 → 设计评审 → 交接；状态/响应式/无障碍必做；未过评审不交开发。
- **PRD**：要素齐（模板为准）；验收标准可判定；状态机/权限矩阵/异常边界不得省；埋点与指标写清。
- **评审**：独立复核（不替写）；只报缺口；需修回 PRD，同回合重审≤1。  
- **受理/分诊**：对话/文档/缺陷单统一入受理单；先判新需求/变更/答疑/产品缺陷/实现缺陷/技术不确定；产品缺陷须有相符证明；实现缺陷退回开发。  
- **缺陷平台**：按 `缺陷平台协作.md` 拉取指派给产品的缺陷，读全 steps/备注/附件/方案；分析后走 change 处置；回写备注/附件/状态/指派前 `confirm_remark`；未配置走粘贴/export。  
- **交付/变更**：PRD 定稿才排期；变更走单（影响/成本/风险/回滚）；答疑书面留痕；实质变更重审后才恢复定稿。  
- **联动**：处置后更新 PRD/AC、原型、评审、交付计划、产品计划、需求池、UAT、发布检查与通知回执；每项标状态，未闭环不关闭。  
- **UAT/发布**：逐条对照验收标准（结果+证据）；产品缺陷≠实现缺陷；发布就绪（回滚/公告/客服/监控）才发。
- **上市（GTM）**：定价/渠道/物料/销售客服赋能；与 UAT 发布门咬合；对外承诺须已确认。
- **展示/介绍**：受众/目标 → 故事线/Mermaid 流程图 → 演示脚本（点击级）→ Demo 检查单 → 材料/用户文档 → 彩排；对外前 `confirm_materials`；与当前 PRD/原型/构建一致，未实现不演示。
- **复盘**：目标 vs 实际、指标达成、根因、改进项→回需求池（含责任人/期限）。

## 5. 收尾骨架

所有完整任务（工作流末步 / 产品计划全部阶段结束）统一用 `../AGENTS.md` §2 的 6 点骨架；下表只规定第 1 点的领域要点，不另起编号。第 1 点的「可直接复制汇报」按业务语言、量化、结论先行，禁过程词与内部路径。

| 任务类型 | 第 1 点领域要点（可复制汇报之后） |
| --- | --- |
| PRD | 主题/版本、落盘路径、要素自检与引用抽验、待决项 |
| 计划 | 周期、目标/KR、路线图、本期范围、里程碑/风险、计划确认 |
| 立项 | Go/Hold/Kill、依据、待验证项、立项书路径 |
| 原型 | IA/线框/视觉方向/高保真路径、设计评审结论、交接要点 |
| 评审 | 通过/需修、缺口（条目/问题/建议）、记录路径 |
| 受理/处置 | 受理编号/类型、分诊依据/结论、处置、联动变更、最新产物路径、回执/待办、验证/关闭 |
| 缺陷平台 | 拉取/产品缺陷/实现缺陷/立即修/下版/不修/退回/补充信息；回写成功/待回写/失败；每条处置与最新文档 |
| 交付/验收 | 范围/进度、变更单清单、UAT 结论、发布就绪项 |
| 展示/文档 | 受众/目标、故事线/流程图、演示脚本/材料/用户文档路径、项目对齐检查、彩排/反馈、拟提交 |
| 复盘 | 目标 vs 实际、指标、根因、改进项（回池）、责任人/期限 |

## 6. 受理与变更（摘要 · 方法见 `../技能/change-management/SKILL.md`）

```text
对话/文档/缺陷单/测试报告
→ intake 受理单（编号/来源/证据/关联 PRD/AC）
→ triage 分诊（新需求/变更/答疑/产品缺陷/实现缺陷/技术不确定/重复/无效）
→ assess 影响（范围/AC/成本/排期/风险/数据合规/回滚/受影响产物）
→ decide 处置确认（confirm_scope / confirm_change / confirm_plan；产品缺陷须相符证明）
→ apply 联动（PRD/AC、原型、评审、交付计划、产品计划、需求池、UAT、发布检查、通知）
→ review 重审（实质变更才走，confirm_prd）
→ verify 验证（受影响 UAT/回归/冒烟；未验证不关闭）
```

- **产品缺陷**：实现符合 PRD/设计但口径不合理/有风险 → 产品决策「立即修 / 下版 / 不修」；立即修走变更单，下版回需求池，不修留理由与接受人。
- **平台缺陷**：`defect` 工作流按 `缺陷平台协作.md` 拉取/读全/分析/处置；回写备注、附件、状态、指派走 `confirm_remark`；未配置/无权限走粘贴或 export。
- **实现缺陷**：与 PRD/设计不一致 → 退回开发/测试；产品不改 PRD，只给依据与验收要求。
- **新需求**：先入需求池并定优先级/版本；本期做再转变更单，下期走产品计划 §2。
- **纯答疑**：受理单即答复记录；若影响基线，升级为变更。
- **输出**：受理单 + 变更单（如适用）+ 最新 PRD/AC/计划/UAT + 开发/测试回执；未回写、未验证不得关闭。
