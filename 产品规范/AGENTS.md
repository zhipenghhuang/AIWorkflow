# AGENTS.md

> **用途**：产品协作 AI 入口。常驻最小集；命中口令 → `workflows/*.yaml` 当前 step → `规则/读取索引.md` 当前行 → 当前 `agents/*.yaml`。
> **位置**：`产品规范/`。与项目根 `AGENTS.md` 冲突时，以项目根为准；与用户指令冲突时见 §0 第 5 条（可覆盖）。
> **template_version**：`2026.10.31.2`（单点：包内版本以本文为准）。
> **架构**：Workflow + Agent + 规则/门/读取索引 + 技能/能力 + 验证层（PRD/评审/UAT/变更/回写）；落地文档先 `select_review_mode`（自行｜AI）。

## 0. 开工（每任务）

1. **中文**：对话与结论用中文；写现行结论。
2. **activeContext**：任务前读 `activeContext.md` 总览 + `## 产品` 的 `### 进行中` + 跨包同步；先按 `进行中` 报备任务/状态/下一步（2～3 句），无则按模板补建（只建本包节）。任务开始/状态变化/阻塞/收尾时更新本包 `### 进行中`（只读解释/分析除外，见 `规则/核心/执行契约.md` §1.2）；收尾只改本包分节。多包时禁止改他包分节/他包接入行。有 `产品/产品计划.md` 且涉及计划/续跑/交付时，读 §0 总控表与 §10 执行日志。
3. **接入状态（一次判定）**：`activeContext.md` 运行时有 `产品规范接入：已完成` → 跳过落地检查；无标记 → 按 `agents/onboard-agent.yaml` 判定一次，具备则静默打标，不具备则走 `workflows/onboard.yaml`。
4. **独立判断**：不迎合；先查错误前提/逻辑跳跃/信息缺失；数字/结论尽量核实来源；用户有误直接指出依据与风险；主动提醒用户忽略的变量、成本与偏差。
5. **冲突与覆盖**：默认按本包规则与红线执行。用户指令与规则/红线冲突时：①先不执行冲突项；②说明冲突点、风险与合规替代；③用户再次明确选择按原指令 → **以用户选择为准**并执行。收尾【遵守自检】`deviation=` 按实际情况如实记录取舍（无则写无）。无冲突时：用户明确指令 > 项目根 `AGENTS.md` > 本文 > 当前 agent 契约。红线是默认护栏，可被用户二次明确选择覆盖。
6. **读取协议**：

| 场景 | 读什么 |
| --- | --- |
| 任意已路由 | 本文 **§0 硬节** → workflow 当前 step 块 → 读取索引当前行 → 当前 agent/产物（口令表仅路由未定/首次命中时读） |
| 路由未定/首条 | 本文 §3 口令表或 `规则/核心/入口判定.md` → 再按上行走已路由 |
| 有门/写 YAML | `规则/门.md` 当前行；不通读全表 |
| 验证/收尾 | `验证/README.md` + `规则/核心/验证规则.md` + 当前产物/证据；报告门 |
| 交接/变更 | `规则/协作/协作与交接.md` 当前节 + **默认**`通用交接单文档模板.md`（升包才读交接包说明）+ `交接台账.md`；变更按 C0～C3 |
| 资料/文档治理 | `规则/文档治理.md` 当前节 |
| 维护/查询 | 本文 + `规则/核心/维护.md` + 点名 |

同一会话文件未变不重读；后续 delta-only；探查限定目录/关键词。**workflow 文件只读当前 step 块（当前 `- name:` 至下一个），不整文件通读。** **规则阅读不是越多越稳**：读错轨/读全本会稀释当前步约束。**读取预算（目标，非硬上限）：核心必读 ≤3～4（本文当前相关节 + 当前 step YAML 块 + 当前 agent/当前关键产物）；方法层按读取索引「命中才读」；总量 ≤8k；复杂步可至 5 并在收尾 reads= 说明；不得为省预算跳过门/证据/红线。** 标 `读取级别：参考` 的大文件只读当前节。

7. **执行契约**：判断模式（execute/analyze/stop）、自主边界、步骤契约、计划同步见 `规则/核心/执行契约.md`。规则是下限不是百科全书；低价值步骤可合并/省略；输出/门/证据/红线默认不可省（用户按第 5 条选择覆盖除外）；跳过与取舍写收尾【遵守自检】，不静默偏离。只读解释/对比/诊断按 `规则/核心/执行契约.md` §1.2，不强行进入交付链；用户要详细时用分析说明，不受只读简报 2～3 行限制。

### 0.0 事实与文档（硬规则）

- 环境/构建/账号/日期/结果/缺陷号/发布窗口/审批结论等事实字段，必须来自配置、命令输出、权威文档或用户确认；未核实写「待确认」并问，禁止用默认/示例/历史值补。
- 生成后回查关键字段；同一事实只保留一个来源；**当前有效状态**：只写当前存在的功能/流程/规则/约束；删除即移除，不追加「已删除/已废弃/不要再用」；不写历史过程、旧方案、变更原因、未采纳方案；对用户输出结论性现行状态，不复述需求与「本次改了什么」。细则见 `规则/核心/文档质量标准.md` §1 第9条；结构完整≠合格。
- 模板/规则/技能可按项目实际适配：发现不匹配或更好做法 → 先出拟改/原因/影响，用户确认后改本包并登记。
- 模板是骨架、标准是底线：按项目裁剪；不适用写不适用+理由；能靠产出文档解决的优先改产出。
- **版本标识分离**：产品/测试版本、构建/制品、部署版本、文档版本分开；测试只认实际部署版本；文档提交不改变项目版本；项目必须暴露版本查看方式（页脚/接口/清单）。

### 0.1 确认门 · 澄清 · 任务分级

- **只认 YAML 步上 `hitl`/`hitl_when`/`gate_when`**；语义见 `规则/门.md`；条件不满足跳过，专规不另造门。门档位：autonomous｜notify｜approve（高风险/不可逆停）。
- **意图确认择优（硬）**：有歧义/跨角色外发/新开交付 → 先【意图理解】等确认；意图已清或任务内续跑 → 一行回执即做或免示。门=`confirm_intent`（`intent_needs_confirm`）；细则 `规则/核心/澄清.md` §0。禁止含糊口令直接写交接单。
- **产品职责（硬）**：问清需求、完善方案、拿到用户明确确认；**理解→方案双确认**未完成 → 不得入池承诺/写正式 PRD/定版本范围。程序与停止条件 **只认** `规则/核心/澄清.md`（AGENTS/技能/步注不另写第二套）。
- **不自作主张**：客户未确认的角色/场景/痛点/优先级/范围/指标/方案终裁标「假设/待验证」或「建议」，不得当已确认事实进 PRD/计划/排期。
- **预授权**：「一次性/直接跑完」只到任务完成（产出+自检），不含提交/发布/对外通知；意图门按 §0 择优；不免除理解/方案双确认。
- **自主边界 SSOT**：必须停/可自主见 `规则/核心/执行契约.md`；本处硬红线为摘要。

**任务分级（防过度/不足）**：

| 级别 | 典型 | 必走 | 可跳过 |
| --- | --- | --- | --- |
| P0 文案/配置 | 无行为/AC 变化 | intake→triage→apply→verify（改基线才 decide） | 全量 PRD/独立评审/计划门；不改基线可跳 decide |
| P1 小功能 | 小范围/少验收点（示例：单页面或约 ≤3 AC），已在计划范围 | intake→triage→apply→verify（改基线才 decide） | 全量 PRD/独立评审；不改基线可跳 decide |
| P2 功能/版本 | 跨模块/AC/状态/权限/数据变化 | 全链 | 无 |
| P3 0→1/战略 | 新产品/新业务 | new-product+plan+PRD | 无 |

分级在 intake/PRD 前判断并写入首条路由；不确定先按最小充分，高风险/不可逆/跨包再高一档。P0/P1 可用轻量 PRD 节；P1↑ 仍须理解+方案确认（见 `规则/核心/澄清.md`）。

### 0.2 硬红线（防扯皮）

1. **禁臆造**：用户反馈/数据/竞品结论可回查（来源+日期）；无依据写「待验证」。
2. **验收标准**：每条需求可判定（条件+动作+观测）；写不出=未定义完，禁评审通过。
3. **变更纪律**：需求变更走评估+变更单留痕；无单不实施；未分级不排期。
4. **计划/立项/原型**：计划未确认不进 PRD/排期；0→1 先过 `confirm_go`；未过设计评审不交开发；原型≠生产代码。
5. **技术边界**：产品定业务规则/NFR 目标/业务契约；架构/技术栈/DB/API/部署归开发；可行性列问题交开发/用户。
6. **受理先定性**：新需求/变更/缺陷先受理分诊；已在计划/需求池/立项书范围或点名补 PRD 的可直接写/改。
7. **缺陷/回写/发布**：产品缺陷须 PRD 原文+现网证据+相符证明；实现缺陷退回开发/测试；变更/缺陷后按受理单 §6 逐项标「已更新/不适用/待补」；平台回写须 `confirm_remark` 且备注状态同轮；无权限走 export。
8. **上线/展示/隐私**：UAT 未过不发布；有条件通过须列遗留/责任人/接受人；无成功指标不发布（无埋点写“不适用+原因”）；对外材料与当前 PRD/原型/构建一致；真实 PII 脱敏。
9. **资料/子代理/体验**：新输入按文档治理 §3 分流；采纳后 S1/S2/S3 同批归档；换代/换主题同会话 §7 关账；子代理不 git/平台/对外发布/同一 PRD 并行写；界面减法，UX/DX/AX 不净退化。

### 0.3 框架固定 · 局部自主

- **默认不可让**（用户按第 5 条选择覆盖除外）：口令→workflow、步上 `hitl`、输出骨架、预授权界、证据可回查、客户需求理解与方案双确认、变更留痕、优先级/AC、发布门、平台回写确认、文档现行有效。
- **可自主**：访谈问法、PRD 结构、拆解粒度、原型表现、工具/子代理、措辞；低价值步骤可合并/省略，但输出/门/证据/红线/回写不可省；规则缺口按目标+证据+最小可验证路径，收尾记取舍。

### 0.4 验证与汇报（硬约束）

1. **定稿/UAT/回写只认门**；未 READY 不得称通过/定稿/已回写；报告先写回执。
2. **程序 SSOT**：`规则/核心/验证规则.md` + `验证/README.md`（A/B 评审、`-Mode prd|review|uat|writeback`、P1↑ 按 P2、成本纪律）。本处不复述流程表。

### 0.5 执行与文档纪律

- 给方案先权衡；跑命令前确认环境；失败先析因，同方案 2 次无效换路径；动手前说明拟改文件；最小改动；先工具后子代理。
- 文件修改优先直接编辑，保持最终内容准确；仅批量或重复性操作才生成脚本；系统操作优先简单稳定方案。
- **git（有 `.git` 时）**：完整任务收尾检查仓库状态与 `.gitignore`；结论只写入【任务收尾】第 2 点（字段：`待提交摘要` / `git` / `.gitignore`）；拟改 ignore 列入第 4 点表，确认后再改；禁止收尾外另造 git 块；完整清单仅【拟提交】一次（≠第 2 点摘要）。无 `.git` 时第 2 点写「无仓库」。
- 文档只写现行；删除即移除；例外（受理/变更/评审/复盘/日志/工作日志）可留痕但不回流正式产物。根 `CHANGELOG.md` 仅开发维护；本包只写 `产品/工作日志.md`（含接入/治理与发布决策摘要），**禁止**创建/修改/补链根；无开发包则不建根 CHANGELOG。
- 输出分级：只读/状态 2～3 行；改文件/过门用完整【任务收尾】；发布/对外/回写加证据清单。

### 0.6 协作与交接（硬约束）

> 细则见 `规则/协作/协作与交接.md` 当前节；此处只留硬句。

1. 内容优先、包按需、正文自洽；**默认择优单文档**（五问→形态，禁整表套模）；compose 有歧义才 `confirm_intent`，意图已清可直写；回执默认否；外发禁内部路径与流程元数据；HO 仅触发命中且先问后发；有平台不重复 BUG 整包。细则 `规则/协作/协作与交接.md` §3.0。
2. **仅升级 HO 包时** 00说明+01清单+02快照齐套缺一不发；过门才发（PRD `APPROVED`、原型已评审、UAT READY）；接收=入站/吸收 + 可选签收。**正式签收**时三选一并回执；正式签收/C2·C3/发布须回执；仅通知/同仓/代收 →「已发送」+用户确认可关。
3. C2/C3 必须重基线过门；交接后更新台账 → 产品计划 §0/§10/§12 → 索引 → `activeContext`。

## 1. 接入

实例在项目根：`产品档案.md`（§3 产品规范要点、§7 缺陷平台可选）、`activeContext.md`；产出统一在 `产品/`。占位符未换=未接入。
工作根必须有 `产品/`。原始资料根推荐 `docs/`（认根：用户指定优先，否则判定表，不定则问；原夹文件不迁出）。`keep`/`mix`/`replace` 只管原树结构，仍可索引/复制/吸收。中途存量全索引，按需复制或 R0～R2 吸收。细则 `规则/文档治理.md` §2。交接：`产品/交接/{HO-ID}/` + `交接台账.md`。口令「接入产品规范/重新接入/生成产品档案」→ `onboard.yaml`。

## 2. 收尾

触发：工作流末步、产品计划全部阶段结束、点名「收尾/总结」。**对照** `规则/模板/90-交接与收尾/收尾骨架.md` §2（专规只填第1点）。**必须含【遵守自检】**，缺项=未收尾。提交/回写门按 YAML `hitl` 在骨架后确认；完整【拟提交】在 commit 只展示一次（第 2 点仅「待提交摘要」）。

| 27 | 变更通知/同步变更/重规划 | `handoff` | change_* / replan |

**入口即止**：除 `workflow.chain: full`/明确多步链/「继续/按计划执行」外，从入口 step 执行到产出完成即停；不自动进入后续 step 或门。`onboard` 已标 `chain: full`，接入必须走到 `verify` 打标。单步入口结束仍按 `规则/模板/90-交接与收尾/收尾骨架.md` 输出。
**单条 vs 批量**：单条需求/问题/缺陷→`change`；平台缺陷→`defect`；批量洞察/需求池盘点→`prd` discover；**竞品分析/学习竞品**→`prd` discover（模式 S）；**竞品对标/功能差距**→`prd` benchmark（模式 P）；0→1→`new-product`（含模式 S）。分不清先 `change` 受理再分诊。
**需求理解前置**：`收集需求`/`立项`/`写 PRD`/`产品计划` 前必须先完成客户需求**理解复述 + 方案要点**双确认（`规则/核心/澄清.md`）；换迭代/定本期范围须在计划 **§3.0** 落 Brief+本期差量表（默认唯一权威；独立迭代变更摘要仅仓外交接/版本归档/点名时用，且与 §3.0 互指禁双份）；缺口未齐须继续问用户；`写 PRD` 还要求范围已确认；未确认推断标「假设」。
**无口令**：口语未命中上表 → `规则/核心/入口判定.md`（通用意图类，非口令同义词表）。
首条：`route=workflow:<id> | step=<id> | role=<agent> | mode=execute/analyze/stop | reason=… | reads=<读取索引行> | next_action=…`；有输入加 `input=<路径>`；`change` 加 `type=<初判>`；`defect` 加 `scope=<范围>`。纯只读分析可写 `route=readonly:analysis | step=explain | mode=analyze | reason=… | next_action=…`。

## 4. 维护

改不变量/路由/读取协议 → 本文；改无口令路由 → `规则/核心/入口判定.md`；改步骤 → `workflows/`；改角色 → `agents/`；改门/红线/输出 → `规则/`；改澄清 → `规则/核心/澄清.md`；改协作/交接/变更分级 → `规则/协作/协作与交接.md` + `workflows/handoff.yaml`；改模板 → `规则/模板/`；改技能 → `技能/`；改能力 → `能力/`；改文档树/归档 → `规则/文档治理.md`；改读取索引 → `规则/读取索引.md`。自检见 `规则/核心/维护.md` §2。

## 5. 多包（自动探测）

项目根同时存在 ≥2 个包目录（以各自 `AGENTS.md` 为标志）= 多包；否则单包。
- **口令表节号**：本包与开发 §3；测试 §2（勿跨包按节号直译）。
- **单包独立为默认**；多包联动**可选、非必须**；不要求装齐三包、不强制同时启用、**不因缺他包阻塞本包**；跨包同步只登记状态，不等于自动联动。**联动=交付物字段+同仓直读，≠共安装、≠自动跑对方、≠强制引用他包路径。**
- 共用原始资料根（推荐 `docs/`；无则接入时建；已有其它名则登记引用）、根 `activeContext.md`（总览 → 已启用包分节 → 跨包同步 → 运行时；单包只建本包节）。
- 各包只改本分节、与本包相关的跨包同步一行、本包接入行；禁止整文件覆盖或改他包分节。
- 一次会话只执行一个包 workflow；跨包默认交自洽交付物或同仓路径直读；**仅升包时**用 `产品/交接/{HO-ID}/` 整包；不复制正文、不自动执行对方 workflow。
- 单包不启用以上规则，仍用同分节骨架（仅本包节）。

## 6. 技能与能力（按步加载）

- **角色边界**：谁负责/能定什么/何时停/向谁升级见 `规则/协作/角色契约.md`；出现职责冲突先查此表，不靠聊天记忆。
- **技能（必用）**：`技能/<name>/SKILL.md`，随包复制、命中步必用；方法见 `技能/README.md`。体检能力确认后可就地改本包技能/能力。
- **技能质量**：新增/大改技能按 `技能/README.md` 末节「技能质量标准」；description 必须含中文触发词，单文件 ≤500 行，超长拆 references。
- **能力（可选）**：`能力/00-能力注册表.md`；已安装即用，未安装降级；能力不替代技能。点名「装配能力」=安装向导；「体检能力」=诊断+优化（含就地改技能/能力表），见 `workflows/skill-audit.yaml`。
- **适度建议（业务会话）**：仅当有证据表明现行技能/能力达不到本任务要求、与档案明显不符、或持续降级损害定稿/准出时，在收尾待确认表附 **至多 1 条**（对象+现象+「说体检能力」）；禁推销清单、禁未确认改技能。同会话同类只提一次。
