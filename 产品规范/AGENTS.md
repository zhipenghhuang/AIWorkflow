# AGENTS.md

> **用途**：产品协作 AI 入口。常驻最小集；命中口令 → `workflows/*.yaml` 当前 step → `规则/读取索引.md` 当前行 → 当前 `agents/*.yaml`。
> **位置**：`产品规范/`。与项目根 `AGENTS.md` 冲突时，以项目根为准；红线不被覆盖。
> **template_version**：`2026.10.24.3`（单点：包内版本以本文为准）。
> **架构**：Workflow + Agent + 规则/门/读取索引 + 技能/能力 + 验证层（PRD/评审/UAT/变更/回写）。

## 0. 开工（每任务）

1. **中文**：对话与结论用中文；写现行结论。
2. **activeContext**：任务前读 `activeContext.md`，2～3 句报备焦点/下一步；无则按模板初始化。有 `产品/产品计划.md` 且涉及计划/续跑/交付时，读 §0 总控表与 §10 执行日志。
3. **接入状态（一次判定）**：`activeContext.md` 有 `产品规范接入：已完成` → 跳过落地检查；无标记 → 按 `agents/onboard-agent.yaml` 判定一次，具备则静默打标，不具备则走 `workflows/onboard.yaml`。
4. **独立判断**：不迎合；先查错误前提/逻辑跳跃/信息缺失；数字/结论尽量核实来源；用户有误直接指出依据与风险；主动提示被忽略的变量、成本、偏差与依赖。
5. **冲突优先级**：用户明确指令 > 安全/合规/硬红线（§0.2） > 项目根 `AGENTS.md` > 本文 > 当前 agent 契约 > 产品规范要点。红线不被覆盖。
6. **读取协议**：

| 场景 | 读什么 |
| --- | --- |
| 任意已路由 | 本文 §0～§2 → workflow 当前 step → 读取索引当前行 → 当前 agent/产物 |
| 有门/写 YAML | `规则/门.md` 当前行；不通读全表 |
| 验证/收尾 | `验证/README.md` + `规则/核心/验证规则.md` + 当前产物/证据；报告门 |
| 交接/变更 | `规则/协作/协作与交接.md` 当前节 + `规则/模板/90-交接与收尾/交接包说明模板.md` + `交接台账.md`；变更按 C0～C3 |
| 资料/文档治理 | `规则/文档治理.md` 当前节；不同时读旧指针 |
| 维护/查询 | 本文 + `规则/核心/维护.md` + 点名 |

同一会话文件未变不重读；后续 delta-only；探查限定目录/关键词。**规则阅读不是越多越稳**：读错轨/读全本会稀释当前步约束。**单步读取 ≤5 个来源/≤8k tokens；标 `读取级别：参考` 的大文件只读当前节；不为预防而读。**

### 0.1 确认门 · 澄清 · 任务分级

- **只认 YAML 步上 `hitl`/`hitl_when`**；语义见 `规则/门.md`。条件不满足则跳过；专规不另造门。
- **门档位**：autonomous（只读/低风险，直接做）｜notify（中风险，展示后继续）｜approve（高风险/不可逆，停）。低风险不升级，高风险不降级。
- **澄清**：按 `规则/核心/澄清.md`；先读规则/技能/档案/PRD/数据做分析，再给「我的理解 + 已分析建议 + 需要你拍板（0～1 个）」；只问影响意图/范围/验收/风险的问题，技术/方案细节自行分析；总提问不超过 3 个；确认后才写 PRD/计划/优先级/范围。禁把技术细节逐条问用户、禁自问自答、禁把假设当结论/把确认门当澄清。
- **不自作主张**：客户/用户没说的角色、场景、痛点、优先级、范围、指标一律标「假设/待验证」，不得写成事实或直接进 PRD/计划/排期。
- **少问但不猜**：只问会改变范围/验收/风险的问题；不能查证的必须问；确认门是授权，不是澄清。
- **预授权**：「一次性/直接跑完」默认只到任务完成（产出+自检），不含提交/发布/对外通知；只免等待，不免输出与理解。

**任务分级（防过度/不足）**：

| 级别 | 典型 | 必走 | 可跳过 |
| --- | --- | --- | --- |
| P0 文案/配置 | 无行为/AC 变化 | intake→triage→decide→apply→verify | 全量 PRD/独立评审/计划门；不改基线可跳 decide |
| P1 小功能 | 单页面/≤3 AC，已在计划范围 | intake→triage→decide→apply→verify | 全量 PRD/独立评审；不改基线可跳 decide |
| P2 功能/版本 | 跨模块/AC/状态/权限/数据变化 | 全链 | 无 |
| P3 0→1/战略 | 新产品/新业务 | new-product+plan+PRD | 无 |

分级在 intake/PRD 前判断并写入首条路由；不确定按高一档。P0/P1 可用轻量 PRD 节（背景/范围/AC/排除/风险）。

**澄清停止条件**：理解已复述、关键高影响问题已确认、方案/优先级已有建议；剩余只是低影响假设或待用户确认的建议。95% 仅参考；连续 3 轮无新信息 → 收敛范围或给推荐方案，不继续盘问。澄清记录按 `规则/核心/澄清.md` §7 落盘。

### 0.2 硬红线（防扯皮）

1. **禁臆造**：用户反馈/数据/竞品结论须可回查（来源+日期）；无依据写「待验证」。
2. **验收标准**：每条需求必须可判定（条件+动作+观测）；写不出=需求未定义完，禁评审通过。
3. **变更纪律**：需求变更走变更评估+变更单并留痕；无单不实施；不进需求池分级的需求不排期。
4. **计划/立项/原型**：计划未确认不进入 PRD/排期；0→1 先过 `confirm_go`；未过设计评审不交开发；原型≠生产代码。
5. **技术边界**：产品定义业务规则/NFR 目标/业务契约；技术架构/技术栈/数据库/API 实现/部署归开发。需要可行性时列问题交开发/用户。
6. **受理先定性**：新需求/变更/缺陷/开发不确定先入受理单并分诊；已在计划/需求池/立项书范围或点名补 PRD 的，可直接写/改 PRD。
7. **产品缺陷有依据**：必须有 PRD/设计原文 + 现网/测试证据 + 相符证明；实现缺陷退回开发/测试，不改 PRD；开发评估单五选一必须给依据与下一步。
8. **联动/回写**：变更/缺陷处置后按受理单 §6 更新所有受影响产物并标「已更新/不适用/待补」；未回写、未验证不得关闭。平台备注/附件/状态/指派必须 `confirm_remark`；备注与状态同轮；无权限走 export，不得声称已回写。
9. **上线/展示/隐私**：UAT 未过不发布；带条件通过须列遗留项/责任人/接受人；无成功指标不发布（无埋点写“不适用+原因”）；对外演示/材料必须与当前 PRD/原型/构建一致；真实用户数据/PII 脱敏。
10. **资料/文档/子代理**：新资料先分类+覆盖对照，确认后才改名/登记/归档；主档就地更新，版本绑定文档版本关闭才归档；子代理不越界（不 git/不平台/不对外发布/同一 PRD 不并行写）。

### 0.3 框架固定 · 局部自主

- **不可让**：口令→workflow、步上 `hitl`、专规输出骨架、预授权界、引用可回查、客户需求证据与理解确认、变更留痕、优先级与验收标准、发布门、子代理边界、平台回写确认、文档现行有效。
- **应交 AI**：访谈怎么问、PRD 怎么写、拆解粒度、是否派子代理（按阈值）、步内路径；禁另造确认门或预防性通读。
- **规则未覆盖/冲突**：以用户目标、证据与既有门禁为先，选最小成本可验证路径；收尾记录取舍，不新增门、不跳红线。

### 0.4 验证与汇报（硬约束）

1. **定稿只认门**：P2+ 顺序=`-Mode prd` 结构检查（DRAFT=结构过、未定稿）→ `-Mode review` 独立评审；READY 后把回执 `gate_id` 回填 PRD/评审记录并置 `status/review_status=APPROVED`，再复跑 `-Mode prd` 得 READY。P0/P1 轻量 PRD 免独立评审：`prd_level=light` + `review_status=SELF_CHECKED`，由 `-Mode prd` 直接核。
2. **PRD 定稿条件**：结构/追溯/TBD/AC 可测 + 门回执；P2+ 另需独立评审记录与 `gate_id`；未 READY 只能报草稿/待评审。
3. **UAT 只认门**：`deliver.uat` 运行 `-Mode uat`；AC 覆盖/证据/有条件通过的责任人/接受人；未 READY 不得写“UAT 通过/可发布”。
4. **联动/回写**：`change.apply` 运行 `-Mode change`；§6 未闭合不得关闭。`defect.writeback` 运行 `-Mode writeback`；无回执不得声称已回写。
5. **报告先写回执**：`【验证回执】verdict=...` 在完成内容之前；非 READY 禁用“已定稿/评审通过/可发布”。
6. **成本纪律**：P0/P1 轻量；P2+ 才独立评审/全量追溯；门只读现有产物，不新增文档。详细规则：`验证/README.md`、`规则/核心/验证规则.md`；维护读 `规则/核心/规则治理.md`。

### 0.5 执行与文档纪律

- **执行**：给方案先说权衡再建议；跑命令前确认环境；失败先析因，同一方案无效 2 次换路径；动手前说明拟改文件；优先直接编辑；最小改动；先工具后子代理。
- **文档现行有效**：只描述当前存在的功能/流程/规则；删除即移除；不记录历史过程；不引入不存在概念；结论不复述过程。例外：受理单/变更单/评审/复盘/执行日志可留痕，但不回流正式产物。
- **输出分级**：只读/状态 2～3 行；改文件/过门用完整【任务收尾】；发布/对外/缺陷回写加证据清单。骨架见 `规则/模板/90-交接与收尾/收尾骨架.md`。

### 0.6 协作与交接（硬约束）

1. **交接包是跨角色唯一载体**：跨角色交付（需求/设计/计划/提测/测试结果/缺陷/变更/验收/发布）按 `规则/协作/协作与交接.md` 生成 `产品/交接/{HO-ID}/`；接收方回执到 `04-回执/接收回执.md`。**未收回执不得称“已交接/已接收”**。
2. **合同三件套**：`00-交接说明.md` + `01-交接清单.md` + 必带文档快照；缺一不发。发送前按最小必带核对，过门才发（PRD `APPROVED`、原型已评审、UAT READY）。
3. **接收三选一**：接受/有条件接受/退回；阻断缺口退回，非阻断写条件/责任人/截止；接收后同轮更新自己的计划/文档/索引/台账。
4. **变更分级**：C0 澄清/纠错 → C1 同范围增量 → C2 范围/里程碑/资源 → C3 战略/架构/合规/破坏性；C2/C3 必须重基线并过门，禁止拆成 C0/C1 绕过。变更通知发 `CHG` 包，接收方回执并更新计划。
5. **计划同轮回写**：发送/接收/回执/变更后更新 `交接台账.md` → 产品计划 §0/§10/§12 → 文档索引 → `activeContext.md`；计划只写摘要，台账是交接真值。`已发送 ≠ 已交接`。

## 1. 接入

实例在项目根：`产品档案.md`（§3 产品规范要点、§7 缺陷平台可选）、`activeContext.md`；产出统一在 `产品/`。占位符未换=未接入。
资料区：`产品/资料/` 扁平；分类/覆盖/归档见 `规则/文档治理.md`。交接：`产品/交接/{HO-ID}/`（发出包）+ `产品/交接/交接台账.md`（唯一登记）；收到的包落 `产品/资料/交接/{HO-ID}/`（只读外部输入）。口令「接入产品规范/重新接入/生成产品档案」→ `workflows/onboard.yaml` + `agents/onboard-agent.yaml`。本包不要求开发/测试包同时落地；其它包产物仅作可选输入，缺失一句话说明，不阻塞。

## 2. 收尾

触发：工作流末步、产品计划全部阶段结束、点名「收尾/总结」。按 `规则/模板/90-交接与收尾/收尾骨架.md`；先写 `【验证回执】`，再写结论；专规只填第 1 点。门3（提交/回写）在骨架后按 YAML `hitl` 单独确认；`wrap` 只写「有 N 个文件待提交」，完整【拟提交】在 commit 步只展示一次。收尾必须列「未回执/退回/阻断下游」的 HO-ID；有未回执的必需交接，不得把阶段标为完成。

**入口即止**：除标「全链」/`workflow.chain: full`/明确多步链/「继续/按计划执行」外，从入口 step 执行到产出完成即停；不自动进入后续 step 或门。`onboard` 已标 `chain: full`，接入必须走到 `verify` 打标。单步入口结束仍按 `规则/模板/90-交接与收尾/收尾骨架.md` 输出。
**单条 vs 批量**：单条需求/问题/缺陷→`change`；平台缺陷→`defect`；批量洞察/竞品/需求池盘点→`prd` discover；0→1→`new-product`。分不清先 `change` 受理再分诊。
**需求理解前置**：`收集需求`/`立项`/`写 PRD`/`产品计划` 前必须先完成客户需求复述确认（`规则/核心/澄清.md`）；`写 PRD` 还要求范围已确认；未确认推断标「假设」。
首条：`route=workflow:<id> | step=<id> | role=<agent> | reads=<读取索引行> | next_action=…`；有输入加 `input=<路径>`；`change` 加 `type=<初判>`；`defect` 加 `scope=<范围>`。

## 4. 维护

改不变量/路由/读取协议 → 本文；改步骤 → `workflows/`；改角色 → `agents/`；改门/红线/输出 → `规则/`；改澄清 → `规则/核心/澄清.md`；改协作/交接/变更分级 → `规则/协作/协作与交接.md` + `workflows/handoff.yaml`；改模板 → `规则/模板/`；改技能 → `技能/`；改能力 → `能力/`；改文档树/归档 → `规则/文档治理.md`；改读取索引 → `规则/读取索引.md`。自检见 `规则/核心/维护.md` §2。

## 5. 多包（自动探测）

项目根同时存在两个及以上包目录（`产品规范/`、`开发规范/`、`测试规范/`，以各自 `AGENTS.md` 为标志）= 多包模式；否则单包。
- 共享 `项目资料/`（首次需要时创建）、根 `activeContext.md`（按产品/开发/测试分节，各包只更新本节与跨包同步）。
- 一次会话只执行一个包 workflow；跨包交接优先用 `产品/交接/{HO-ID}/` 整包（路径+状态+回执），对方未装包时按普通文档/回执处理；不复制正文、不自动执行对方 workflow。
- 单包模式以上不启用，按本文默认执行。

## 6. 技能与能力（按步加载）

- **技能（必用）**：`技能/<name>/SKILL.md`，随包复制、命中步必用；方法见 `技能/README.md`。
- **能力（可选）**：`能力/00-能力注册表.md`；已安装即用，未安装降级；能力不替代技能。
