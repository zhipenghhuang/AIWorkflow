# AGENTS.md

> **用途**：产品协作 AI 入口。常驻最小集；命中口令 → `workflows/*.yaml` 当前 step → `规则/读取索引.md` 当前行 → 当前 `agents/*.yaml`。
> **位置**：`产品规范/`。与项目根 `AGENTS.md` 冲突时，以项目根为准；红线不被覆盖。
> **template_version**：`2026.10.28.10`（单点：包内版本以本文为准）。
> **架构**：Workflow + Agent + 规则/门/读取索引 + 技能/能力 + 验证层（PRD/评审/UAT/变更/回写）；落地文档先 `select_review_mode`（自行｜AI）。

## 0. 开工（每任务）

1. **中文**：对话与结论用中文；写现行结论。
2. **activeContext**：任务前读 `activeContext.md` 总览 + `## 产品` + 跨包同步，2～3 句报备焦点/下一步；无则按模板初始化（只建本包节）。有实质进展收尾只更新本包分节。多包时禁止改他包分节/他包接入行。有 `产品/产品计划.md` 且涉及计划/续跑/交付时，读 §0 总控表与 §10 执行日志。
3. **接入状态（一次判定）**：`activeContext.md` 运行时有 `产品规范接入：已完成` → 跳过落地检查；无标记 → 按 `agents/onboard-agent.yaml` 判定一次，具备则静默打标，不具备则走 `workflows/onboard.yaml`。
4. **独立判断**：不迎合；先查错误前提/逻辑跳跃/信息缺失；数字/结论尽量核实来源；用户有误直接指出依据与风险。
5. **冲突优先级**：安全/合规/硬红线（§0.2） > 用户明确指令 > 项目根 `AGENTS.md` > 本文 > 当前 agent 契约。红线不被覆盖。
6. **读取协议**：

| 场景 | 读什么 |
| --- | --- |
| 任意已路由 | 本文 §0～§3 → workflow 当前 step 块 → 读取索引当前行 → 当前 agent/产物 |
| 有门/写 YAML | `规则/门.md` 当前行；不通读全表 |
| 验证/收尾 | `验证/README.md` + `规则/核心/验证规则.md` + 当前产物/证据；报告门 |
| 交接/变更 | `规则/协作/协作与交接.md` 当前节 + `规则/模板/90-交接与收尾/交接包说明模板.md` + `交接台账.md`；变更按 C0～C3 |
| 资料/文档治理 | `规则/文档治理.md` 当前节 |
| 维护/查询 | 本文 + `规则/核心/维护.md` + 点名 |

同一会话文件未变不重读；后续 delta-only；探查限定目录/关键词。**workflow 文件只读当前 step 块（当前 `- name:` 至下一个），不整文件通读。** **规则阅读不是越多越稳**：读错轨/读全本会稀释当前步约束。**读取预算（目标，非硬上限）：常规单步 ≤5 个来源/≤8k tokens；确需更多时只读当前节并在收尾说明，不得为省预算跳过门/证据/红线。** 标 `读取级别：参考` 的大文件只读当前节。

### 0.0 事实字段不臆填（硬规则）

- 环境 URL/端口/IP、构建/提交、账号、日期、接收人、数据量、测试结果、缺陷号、发布窗口、审批/准出结论等事实字段，必须来自当前配置、命令输出、权威文档或用户确认；未核实前在文档写「待确认」并停下问，不得用开发默认、示例、历史值或“看起来合理”的值填充。
- 不确定先问 0～1 个关键问题；禁止自行补全，禁止把假设写成事实。影响范围/验收/风险的不确定项必须先问。
- 同一事实多处引用只保留同一来源；生成后回查关键字段，发现不一致先修再交付。
- 文档只写现行事实与必要说明；禁止辩解式/对比式/冗余括注（如解释“不是某个环境/端口”）、未经确认的猜测和“应该/可能”式结论。
- 适用于所有产出：需求/方案/计划/任务/提测单/测试计划与报告/发布说明/交接包/UAT/复盘/验收等。
- 各类文档按 `规则/核心/文档质量标准.md` 的定位/类型矩阵/评审清单判定合格；结构完整≠合格，事实/证据/可执行性缺一不可。
- **母版只维护通用高标准**；项目实例里的规范目录是只读副本，禁止直接编辑；更新只走整包分发。
- **模板是骨架、标准是底线**：按当前项目实际/文档位置裁剪，不逐条机械填写；不适用写「不适用 + 理由」。
- **不匹配先改产出**：优先修改当前项目生成的文档；可向用户提模板/标准适配建议，用户确认且属通用改进才回母版升版本。

### 0.1 确认门 · 澄清 · 任务分级

- **只认 YAML 步上 `hitl`/`hitl_when`/`gate_when`**；语义见 `规则/门.md`。条件不满足则跳过；专规不另造门。
- **门档位**：autonomous（只读/低风险，直接做）｜notify（中风险，展示后继续）｜approve（高风险/不可逆，停）。低风险不升级，高风险不降级。
- **澄清**：按 `规则/核心/澄清.md`；先读规则/技能/档案/PRD/数据做分析，再给「我的理解 + 已分析建议 + 需要你拍板（0～1 个）」；只问影响意图/范围/验收/风险的问题；总提问 ≤3（阻塞/安全/合规/高风险问题不受 3 问限制，但仍一次一问）；确认后执行；不确定项按澄清 §2.1 分流。
- **不自作主张**：客户/用户没说的角色、场景、痛点、优先级、范围、指标一律标「假设/待验证」，不得写成事实或直接进 PRD/计划/排期。
- **少问但不猜**：只问影响范围/验收/风险的问题；不能查证的必须问。
- **预授权**：「一次性/直接跑完」默认只到任务完成（产出+自检），不含提交/发布/对外通知；只免等待，不免输出与理解。

**任务分级（防过度/不足）**：

| 级别 | 典型 | 必走 | 可跳过 |
| --- | --- | --- | --- |
| P0 文案/配置 | 无行为/AC 变化 | intake→triage→apply→verify（改基线才 decide） | 全量 PRD/独立评审/计划门；不改基线可跳 decide |
| P1 小功能 | 单页面/≤3 AC，已在计划范围 | intake→triage→apply→verify（改基线才 decide） | 全量 PRD/独立评审；不改基线可跳 decide |
| P2 功能/版本 | 跨模块/AC/状态/权限/数据变化 | 全链 | 无 |
| P3 0→1/战略 | 新产品/新业务 | new-product+plan+PRD | 无 |

分级在 intake/PRD 前判断并写入首条路由；不确定按高一档。P0/P1 可用轻量 PRD 节（背景/范围/AC/排除/风险）。

**澄清停止条件**：理解已复述、关键高影响问题已确认、方案/优先级已有建议；剩余只是低影响假设或待用户确认的建议。95% 仅参考；连续 3 轮无新信息 → 收敛范围或给推荐方案，不继续盘问。澄清记录按 `规则/核心/澄清.md` §7 落盘。

### 0.2 硬红线（防扯皮）

1. **禁臆造**：用户反馈/数据/竞品结论须可回查（来源+日期）；无依据写「待验证」。
2. **验收标准**：每条需求必须可判定（条件+动作+观测）；写不出=需求未定义完，禁评审通过。
3. **变更纪律**：需求变更走变更评估+变更单并留痕；无单不实施；不进需求池分级的需求不排期。
4. **计划/立项/原型**：计划未确认不进入 PRD/排期；0→1 先过 `confirm_go`；未过设计评审不交开发；原型≠生产代码。
5. **技术边界**：产品定义业务规则/NFR 目标/业务契约；技术架构/技术栈/数据库/API 实现/部署归开发。需要可行性时列问题交开发/用户。
6. **受理先定性**：新需求/变更/缺陷/开发不确定先入受理单并分诊；已在计划/需求池/立项书范围或点名补 PRD 的，可直接写/改 PRD。
7. **产品缺陷有依据**：必须有 PRD/设计原文 + 现网/测试证据 + 相符证明；实现缺陷退回开发/测试，不改 PRD；开发评估单五选一必须给依据与下一步。
8. **联动/回写**：变更/缺陷处置后按受理单 §6 更新所有受影响产物并标「已更新/不适用/待补」；未回写、未验证不得关闭。平台备注/附件/状态/指派必须 `confirm_remark`；备注与状态同轮；无权限走 export，不得声称已回写。
9. **上线/展示/隐私**：UAT 未过不发布；带条件通过须列遗留项/责任人/接受人；无成功指标不发布（无埋点写“不适用+原因”）；对外演示/材料必须与当前 PRD/原型/构建一致；真实用户数据/PII 脱敏。
10. **资料/文档/子代理**：新输入先按 `规则/文档治理.md` §3 做意图分析（T1～T9）再分流（资料或工作区）；确认采纳后 S1/S2/S3（全量替代/全量覆盖/重复）**同批**失效进 `资料/_归档/`（或工作文档 `_归档/`），禁只落位不清理；主档就地覆盖；**新迭代文档采纳或换代/换主题（可不发版）→ 同会话 §7 关账**（不确定则 `confirm_iteration_close`）；单包闭环、他包不自动跑；子代理不越界（不 git/不平台/不对外发布/同一 PRD 不并行写）。
11. **全局体验**：界面减法（删冗余文案/标签；删后不清楚改布局，不加回说明）；UX/DX/AX 任一不得净退化且不破坏现有功能。细则 `技能/ui-visual-design-system` §1.3～1.4、`技能/review-and-finalize` §1。

### 0.3 框架固定 · 局部自主

- **不可让**：口令→workflow、步上 `hitl`、专规输出骨架、预授权界、引用可回查、客户需求证据与理解确认、变更留痕、优先级与验收标准、发布门、子代理边界、平台回写确认、文档现行有效。
- **应交 AI**：访谈怎么问、PRD 怎么写、拆解粒度、是否派子代理（按阈值）、步内路径；禁另造确认门或预防性通读。
- **模板是下限不是上限**：步内方法、顺序、工具、拆分、措辞可自行择优；低价值步骤/文档可合并或省略，但输出骨架、门、证据、红线、回写不可省。
- **规则未覆盖/冲突**：以用户目标、证据与既有门禁为先，选最小成本可验证路径；收尾记录取舍，不新增门、不跳红线；不确定且影响范围/验收/风险 → 停下问 1 个关键问题。

### 0.4 验证与汇报（硬约束）

1. **落地文档评审方式**：写完后按 `landing_doc_review_needed` 判断——P2+/实质变更/用户点名评审 → STOP `select_review_mode`（A 自行｜B AI）；P0/普通 P1 可默认 A + SELF_CHECKED。未选不得宣称通过/定稿。
2. **作者侧闭环（不依赖选 B）**：写 PRD 必须落【完稿自检摘要】（`技能/prd-writing` §9.1）；P2+/P1↑/拟定稿或交开发 → 必跑 `-Mode prd`（`gate: product-prd`），BLOCKED 不得定稿/交开发。
3. **定稿只认门**：选 B → `-Mode review` READY + `gate_id` + 复跑 `-Mode prd`；选 A → HUMAN_APPROVED + 自检摘要 + 结构非 BLOCKED（不跑 review 门）。P0/普通 P1 可 SELF_CHECKED；**P1↑**（权限/资金/隐私/不可逆数据/主数据）自检按 P2。
4. **PRD 定稿条件**：结构非 BLOCKED + 摘要 + 追溯/TBD/AC 可测；选 B 另需评审记录与 `gate_id`；未满足只能报草稿/待评审。
5. **UAT 只认门**：`deliver.uat` 运行 `-Mode uat`；未 READY 不得写“UAT 通过/可发布”。无 UAT 要求写 `verdict: 不适用` + 依据 + 批准人/接受人，不得绕过真实用户验收。
6. **联动/回写**：`change.apply` → `-Mode change -Artifact …`；`defect.writeback` → `-Mode writeback -Artifact …`（推荐显式路径）；无回执不得声称已回写。
7. **报告先写回执**：`【验证回执】` 在完成内容之前；非 READY/有摘要缺失 → 禁用“已定稿/可交开发”。
8. **成本纪律**：P0/普通 P1 轻量；P1↑ 加厚自检不加独立审（除非点名）；P2+ 必问 A/B。详见 `验证/README.md`、`规则/核心/验证规则.md`。

### 0.5 执行与文档纪律

- **执行**：给方案先说权衡再建议；跑命令前确认环境；失败先析因，同一方案无效 2 次换路径；动手前说明拟改文件；优先直接编辑；最小改动；先工具后子代理。
- **文档现行有效**：只描述当前存在的功能/流程/规则；删除即移除；不记录历史过程；不引入不存在概念；结论不复述过程。例外：受理单/变更单/评审/复盘/执行日志/`产品/工作日志.md` 可留痕，但不回流正式产物；**禁止**把工作日志写入根 `CHANGELOG.md`。
- **输出分级**：只读/状态 2～3 行；改文件/过门用完整【任务收尾】；发布/对外/缺陷回写加证据清单。骨架见 `规则/模板/90-交接与收尾/收尾骨架.md`。

### 0.6 协作与交接（硬约束）

1. **交接：内容优先、包按需、内容通用**：默认交自洽主文档；HO 包按需先问后发。**正文不偏科**（多方同收时共享事实全写，角色动作分行）；假定对方无本工作流/无平台也能读懂。禁静默发包。有平台已回写 → 不重复 BUG 整包。多包同仓直读，禁转发。未收回执不得称「已接收」。
2. **三件套**：`00-交接说明` + `01-交接清单` + 必带快照；缺一不发。过门才发（PRD `APPROVED`、原型已评审、UAT READY）。
3. **接收三选一**：接受/有条件/退回；阻断缺口退回，非阻断写条件/责任人/截止；接收后同轮更新计划/文档/索引/台账。
4. **变更分级**：C0 澄清/纠错 → C1 同范围增量 → C2 范围/里程碑/资源 → C3 战略/架构/合规/破坏性；C2/C3 必须重基线过门，禁止拆成 C0/C1 绕过；变更通知发 `CHG` 包。
5. **计划同轮回写**：发送/接收/回执/变更后更新 `交接台账.md` → 产品计划 §0/§10/§12 → 文档索引 → `activeContext.md`；台账是交接真值，`已发送 ≠ 已接收`。

## 1. 接入

实例在项目根：`产品档案.md`（§3 产品规范要点、§7 缺陷平台可选）、`activeContext.md`；产出统一在 `产品/`。占位符未换=未接入。
资料区：`产品/资料/{版本或主题}/` + `_通用/` + `资料/_归档/`（见 `规则/文档治理.md`）；正式产物在 `产品/{版本}/` 等，不进资料。交接：`产品/交接/{HO-ID}/` + `交接台账.md`；多包直读对方发送路径。口令「接入产品规范/重新接入/生成产品档案」→ `onboard.yaml`。本包可独立落地；缺他包一句说明，不阻塞、不强制安装。

## 2. 收尾

触发：工作流末步、产品计划全部阶段结束、点名「收尾/总结」。按 `规则/模板/90-交接与收尾/收尾骨架.md`；中文回执 → 第1点纯执行汇报（代号带中文描述、无待确认指针）→ 第4点假设与待确认表（无则「待你确认：无」）→ 第6点当前/下一步/建议理由/完成标志；专规只填第1点。门3（提交/回写）在骨架后按 YAML `hitl` 单独确认；`wrap` 只写「有 N 个文件待提交」，完整【拟提交】在 commit 步只展示一次。

**单条 vs 批量**：单条需求/问题/缺陷→`change`；平台缺陷→`defect`；批量洞察/竞品/需求池盘点→`prd` discover；0→1→`new-product`。分不清先 `change` 受理再分诊。
**需求理解前置**：`收集需求`/`立项`/`写 PRD`/`产品计划` 前必须先完成客户需求复述确认（`规则/核心/澄清.md`）；`写 PRD` 还要求范围已确认；未确认推断标「假设」。
首条：`route=workflow:<id> | step=<id> | role=<agent> | reads=<读取索引行> | next_action=…`；有输入加 `input=<路径>`；`change` 加 `type=<初判>`；`defect` 加 `scope=<范围>`。

## 4. 维护

改不变量/路由/读取协议 → 本文；改步骤 → `workflows/`；改角色 → `agents/`；改门/红线/输出 → `规则/`；改澄清 → `规则/核心/澄清.md`；改协作/交接/变更分级 → `规则/协作/协作与交接.md` + `workflows/handoff.yaml`；改模板 → `规则/模板/`；改技能 → `技能/`；改能力 → `能力/`；改文档树/归档 → `规则/文档治理.md`；改读取索引 → `规则/读取索引.md`。自检见 `规则/核心/维护.md` §2。

## 5. 多包（自动探测）

项目根同时存在 ≥2 个包目录（以各自 `AGENTS.md` 为标志）= 多包；否则单包。
- 共享 `项目资料/`（首次需要时建）、根 `activeContext.md`（总览 → 已启用包分节 → 跨包同步 → 运行时；单包只建本包节）。
- 各包只改本分节、与本包相关的跨包同步一行、本包接入行；禁止整文件覆盖或改他包分节。
- 一次会话只执行一个包 workflow；跨包交接用 `产品/交接/{HO-ID}/` 整包；不复制正文、不自动执行对方 workflow。
- 单包不启用以上规则，仍用同分节骨架（仅本包节）。

## 6. 技能与能力（按步加载）

- **技能（必用）**：`技能/<name>/SKILL.md`，随包复制、命中步必用；方法见 `技能/README.md`。本包副本可在「体检能力」确认后就地改技能（单包/开源落地无需另有母版仓）。
- **能力（可选）**：`能力/00-能力注册表.md`；已安装即用，未安装降级；能力不替代技能。点名「装配能力」=安装向导；「体检能力」=诊断+优化（含就地改技能/能力表），见 `workflows/skill-audit.yaml`。
- **适度建议（业务会话）**：仅当有证据表明现行技能/能力达不到本任务要求、与档案明显不符、或持续降级损害定稿/准出时，在收尾待确认表附 **至多 1 条**（对象+现象+「说体检能力」）；禁推销清单、禁未确认改技能。同会话同类只提一次。
