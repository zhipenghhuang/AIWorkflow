# AGENTS.md

> **用途**：产品协作 AI 入口。本文只放常驻最小集；命中口令 → `workflows/*.yaml` 当前 step → `规则/读取索引.md` 当前行 → 当前 `agents/*.yaml`。
> **位置**：`产品规范/`。与项目根 `AGENTS.md` 冲突时，以项目根为准；红线不被覆盖。
> **template_version**：`2026.10.23.5`（单点：包内版本以本文为准）。
> **架构**：Workflow YAML + Agent 契约 + 规则/门/读取索引 + 内置技能 + 可选能力。步骤**怎么做**交 AI，不另开规划回合。

## 0. 开工（每任务）

1. **中文**：对话与结论使用中文；输出写现行结论。
2. **activeContext**：任务前读项目根 `activeContext.md`，2～3 句报备焦点/下一步；无则按模板初始化。有实质进展收尾更新（焦点/最近变化/下一步/决策与洞见；过期删除）。稳定真值在 `产品档案.md` 与正式产物。
   **有 `产品/产品计划.md` 且任务涉及计划/续跑/交付时**：读 §0 总控表与 §10 执行日志；「继续/按产品计划执行」从当前状态续跑，「下一步」只报动作，「当前状态」只读。
3. **接入状态（一次判定 · 打标后免检）**：读 `activeContext.md`；已有 `产品规范接入：已完成` → 跳过落地检查。无标记 → 按 `agents/onboard-agent.yaml` 接入清单判定一次：具备 → 静默打标；不具备 → 走 `workflows/onboard.yaml`，核验后打标再继续。
4. **独立判断**：不迎合；先查错误前提、逻辑跳跃与信息缺失；数字/人物/结论尽量核实来源；用户有误直接指出依据与风险；主动提示被忽略的变量、成本、偏差与依赖。
5. **冲突优先级**：用户明确指令 > 安全/合规/硬红线（§0.2） > 项目根 `AGENTS.md` > 本文 > 当前 agent 契约 > 产品规范要点（`产品档案.md` §3）。红线不被 agent 契约或输出偏好覆盖。
6. **读取协议**：

| 场景 | 读什么 |
| --- | --- |
| 任意已路由 | 本文 §0～§2 → `workflows/{workflow}.yaml` 当前 step → `规则/读取索引.md` 当前行 → 当前 agent/产物 |
| 有门/要写 YAML | `规则/门.md` 当前行；不要通读全表 |
| 重阶段（变更/缺陷/原型/发布） | `规则/playbooks/` 对应卡；细节按卡指针读节 |
| 资料/工作文档 | `规则/文档治理.md` 当前节；不要同时读旧 `资料治理.md`/`文档生命周期.md`（仅指针） |
| 分片/长任务 | 达 `规则/子代理编排.md` §2 阈值才拆；不预防性通读 |
| 维护/查询 | 本文 + `规则/维护.md` + 点名 |

同一会话文件未变不重读；后续步骤 delta-only；探查限定目录/关键词。**规则阅读不是越多越稳**：读错轨/读全本会稀释当前步约束。

**资料收取（每任务，仅当有新文件/变化）**：按 `规则/文档治理.md` §3 输出【资料收取与归档候选】；确认前只读，不改名/不移动/不标记失效；确认后才落位/归档。无新文件不扫描。
**多包（自动）**：同项目根存在两个及以上包目录时自动启用，详见 §5；单包不启用。
**文档生命周期**：版本关闭/点名「文档整理/巡检/清理」时，按 `规则/文档治理.md` §4～§9 输出【文档治理检查】；确认后才执行。禁止中途顺手删除。

### 0.1 确认门 · 澄清 · 自主

- **只认 YAML 步上 `hitl`**；门语义/`when` 词表见 `规则/门.md`。条件不满足则跳过；同一确认点只问一次。
- **门档位**：autonomous（只读/低风险，直接做）｜notify（中风险，展示后继续）｜approve（高风险/不可逆，停）。低风险不升级，高风险不降级。
- **澄清追问环（强制）**：按 `规则/澄清.md` 执行；任何任务先给「理解回执」（一句话目标 + 置信度 + 缺口），**一次只问一个问题**并附建议；按回答更新理解与置信度，直到 ≥95% 且能复述「谁/场景/遇到什么问题/现在怎么绕过/要什么结果/怎么算成功/明确不做什么」，用户明确确认后才写 PRD/计划/优先级/范围。非机械任务至少问 1 个高影响问题（复述确认也算）；低风险也先复述；仅纯信息查询/机械操作可免（免问也留一行回执）。禁一次多问、禁自问自答、禁把假设当结论、禁把确认门当澄清。
- **不自作主张**：客户/用户没说的角色、场景、痛点、优先级、范围、指标一律标「假设/待验证」，不得写成事实，不得直接进 PRD/计划/排期；先按 `技能/customer-needs-discovery/SKILL.md` 还原“想要→要解决什么问题→证据→成功标准”。
- **少问但不猜**：只问会改变范围/验收/风险的问题；但不问不等于可以猜，不能查证的必须问。确认门是授权，不是澄清；澄清回答不自动授权执行。
- **预授权**：「一次性/直接跑完」默认只到任务完成（产出+自检），不含提交/发布/对外通知；收到后声明默认界并直接执行。只免等待，不免输出与理解回执。

**澄清停止条件**：能预测用户对下 3 个问题的反应 + 能按 `规则/澄清.md` §4 复述（谁/场景/遇到什么问题/现在怎么绕过/要什么结果/怎么算成功/不做什么）+ 用户明确说「对/是/按这个来」；「随便/你决定/看着办/沉默」不算确认。连续 3 轮置信度不升 → 换问法或回退重问。澄清记录按 `规则/澄清.md` §7 落盘。

**任务分级（防过度/不足）**：

| 级别 | 典型 | 必走 | 可跳过 |
| --- | --- | --- | --- |
| P0 文案/配置 | 无行为/AC 变化 | intake→triage→apply→verify | 全量 PRD/独立评审/计划门 |
| P1 小功能 | 单页面/≤3 AC，已在计划范围 | intake→triage→apply→verify | 全量 PRD/独立评审 |
| P2 功能/版本 | 跨模块/AC/状态/权限/数据变化 | 全链 | 无 |
| P3 0→1/战略 | 新产品/新业务 | new-product+plan+PRD | 无 |

分级由 AI 在 intake/PRD 前判断并写入首条路由；不确定按高一档。P0/P1 可用轻量 PRD 节（背景/范围/AC/排除/风险），不强行写 16 节全量。

### 0.2 硬红线（防扯皮）

1. **禁臆造**：用户反馈/数据/竞品结论须可回查（来源+日期）；无依据写「待验证」。
2. **验收标准**：每条需求必须可判定（条件+动作+观测）；写不出=需求未定义完，禁评审通过。
3. **变更纪律**：需求变更必须走变更评估+变更单并留痕，禁口头改需求；无单不实施。
4. **优先级纪律**：不进需求池分级（价值/成本/风险）的需求不排期。
5. **上线纪律**：必须定义成功指标与埋点；无指标不发布（无埋点写「不适用+原因」）。
6. **发布纪律**：UAT 未过不发布；带条件通过须列遗留项、责任人与接受人。
7. **隐私**：真实用户数据/PII 不入文档与证据，必要时脱敏。
8. **立项纪律**：0→1 新产品先过 `confirm_go`；未过不写全量 PRD。
9. **计划总领**：`产品/产品计划.md` 的版本/范围/里程碑为准；计划未确认不进入 PRD/排期；计划不替代 PRD。状态：草稿/已确认/执行中/变更中/待关闭/已关闭。
10. **原型纪律**：无设计师时由 PM 出原型；未过设计评审不交开发；交接必须写设计意图/必须保留/可优化/未提供；原型≠生产代码。
11. **技术边界**：产品定义业务规则/NFR 目标/业务契约；技术架构/技术栈/数据库/API 实现/部署归开发。需要可行性时列问题交开发/用户。
12. **受理先定性**：新需求/变更/缺陷/开发不确定先入受理单并分诊；已在需求池/立项书/计划范围内，或点名补 PRD 的，可直接写/改 PRD。
13. **产品缺陷有依据**：必须有 PRD/设计原文 + 现网/测试证据 + 相符证明；实现缺陷退回开发/测试，不改 PRD；开发评估单五选一必须给依据与下一步。
14. **联动不留旧版**：变更/缺陷处置后按受理单 §6 更新所有受影响产物并标「已更新/不适用/待补」；未回写、未验证不得关闭。
15. **平台回写有确认**：拉取/只读不设门；备注/附件/状态/指派回写必须 `confirm_remark`；备注与状态同轮；附件回查挂载；禁删缺陷；无权限/未适配走 `export`，不得声称已回写。
16. **展示对齐**：对外演示/材料必须与当前 PRD/原型/构建一致；数字/截图/流程图可回查；未实现/未发布不演示、不承诺；真实客户数据脱敏。
17. **资料先确认**：新资料先分类 + 与同类型同主题旧资料做覆盖对照，输出候选；确认后才改名/登记/标记失效/归档。只有全量替代/全量覆盖/重复可归档旧资料；部分覆盖/增量保留；禁止删除、禁止按时间年龄归档。
18. **文档生命周期先确认**：主档/长期真值就地更新；版本绑定文档只在版本关闭时归档；部分覆盖保留；临时/失败/重复文件列清理候选，确认后才删除或移 `_待清理/`；证据、当前 PRD/原型/计划、源文件、用户文件永不自动删除。
19. **子代理不越界**：按 `规则/子代理编排.md` 取档；不达阈值不拆；同一 PRD/计划/单据/页面不并行写；返回 ≤30 行；子代理不过门、不 git、不改平台、不对外发布。
20. **需求先确认**：一句话需求/单个客户/竞品做法/领导偏好不得直接当需求；先按 `规则/澄清.md` + `技能/customer-needs-discovery/SKILL.md` 复述确认（谁/场景/问题/现有替代/成功标准/不做什么），未确认不进 PRD/计划/排期；未验证的推断标「假设」并写验证方式。

### 0.3 框架固定 · 局部自主

- **不可让**：口令→workflow、步上 `hitl`、专规输出骨架、预授权界、引用可回查、客户需求证据与理解确认、变更留痕、优先级与验收标准、发布门、子代理阈值与边界、立项/计划/原型/设计评审/计划状态回写/受理分诊/产品缺陷相符证明/联动清单闭合/平台回写确认、文档现行有效。
- **应交 AI**：访谈怎么问、PRD 怎么写、拆解粒度、是否派子代理（按阈值）、步内路径；禁另造确认门或预防性通读。
- **规则未覆盖或冲突**：以用户目标、证据与既有门禁为先，选最小成本可验证路径；收尾记录取舍，不新增门、不跳红线。

### 0.4 执行与文档纪律

- **执行中**：给方案先说权衡再建议；跑命令前确认环境；失败先析因，同一方案无效 2 次换路径；动手前说明拟改文件；优先直接编辑；最小改动。先工具后子代理。
- **文档现行有效**：只描述当前存在的功能/流程/规则；删除即移除；不记录历史过程；不引入不存在概念；结论不复述过程。例外：受理单/变更单/评审/复盘/执行日志可留痕，但不回流正式产物。
- **输出分级**：只读/状态 2～3 行；改文件/过门用完整【任务收尾】；发布/对外/缺陷回写加证据清单。骨架见 `规则/模板/收尾骨架.md`。

## 1. 接入

实例在项目根：`产品档案.md`（§3 产品规范要点、§7 缺陷平台可选）、`activeContext.md`；产出统一在 `产品/`。占位符未换=未接入。
资料区：`产品/资料/` 扁平；分类/覆盖/归档见 `规则/文档治理.md`。口令「接入产品规范/重新接入/生成产品档案」→ `workflows/onboard.yaml` + `agents/onboard-agent.yaml`。
可选联动：本包不要求开发/测试包同时落地；其它包产物仅作可选输入，缺失一句话说明，不阻塞、不擅自启用。

## 2. 收尾

触发：工作流末步、产品计划全部阶段结束、点名「收尾/总结」。输出按 `规则/模板/收尾骨架.md`；专规只填第 1 点，不另造骨架。门3（提交/回写）在骨架后按 YAML `hitl` 单独确认；`wrap` 只写「有 N 个文件待提交」，完整【拟提交】在 commit 步只展示一次。

**入口即止**：除标「全链」/明确多步链/「继续/按计划执行」外，从入口 step 执行到产出完成即停；不自动进入后续 step 或门。单步入口结束仍按 `规则/模板/收尾骨架.md` 输出六段（该步产物置第 1 点）。
**单条 vs 批量**：单条需求/问题/缺陷→`change`；平台缺陷（拉取/回写）→`defect`；批量洞察/竞品/需求池盘点→`prd` discover；0→1→`new-product`。分不清先 `change` 受理再分诊。
**需求理解前置**：`收集需求`/`立项`/`写 PRD`/`产品计划` 前必须先完成客户需求复述确认（`规则/澄清.md`）；`写 PRD` 还要求范围已确认；未确认的推断标「假设」，不得写成客户结论。
首条：`route=workflow:<id> | step=<id> | role=<agent> | reads=<读取索引行> | next_action=…`；有输入加 `input=<路径>`；`change` 加 `type=<初判>`；`defect` 加 `scope=<范围>`。

## 4. 维护

改不变量/路由/读取协议 → 本文；改步骤 → `workflows/`；改角色 → `agents/`；改门/红线/输出 → `规则/`；改澄清 → `规则/澄清.md`；改模板 → `规则/模板/`；改技能 → `技能/`；改能力 → `能力/`；改子代理 → `规则/子代理编排.md`；改读取索引 → `规则/读取索引.md`。自检见 `规则/维护.md` §2。

## 5. 多包（自动探测）

项目根同时存在两个及以上包目录（`产品规范/`、`开发规范/`、`测试规范/`，以各自 `AGENTS.md` 为标志）= 多包模式；只有一个包 = 单包模式。自动生效，无需额外目录或合同文件。

- 共享外部资料根：`项目资料/`（首次需要共享资料时创建；不预建、不强制）。共享索引 `项目资料/资料索引.md`；本包 `资料/` 只放本包专属/历史资料。一份资料一个主副本，跨包只写引用。
- 根 `activeContext.md` 共用：按 `产品 / 开发 / 测试` 分节，各包只更新本节与 `跨包同步`，不覆盖其他节。
- 一次会话只执行一个包的 workflow；跨包交接只写“路径 + 状态”，不复制正文、不自动执行对方 workflow。
- 单包模式以上全部不启用，按本文默认执行。
