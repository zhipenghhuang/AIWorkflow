# 测试依据分析（技能 · 随包生效）

> 用于：`testing.analyze`，以及 `plan/generate` 前的轻量分析（主读已点名也不省）。  
> 目标：先回答“**这个需求到底要做什么、怎么算对**”，再回答“怎么测”。  
> 边界：本技能不写测试计划、不写用例、不定测试类型取舍；输出需求模型、可测点、oracle、冲突/歧义清单与追溯种子。

> **影响源 → 命中域**：影响面优先级 提测单（若有）→ CR → 主读 diff → 用户点名；产出命中域候选供计划 §3.7 装填，不默认全库。

## 1. 测试依据盘点

| 依据 | 必看 | 记录 |
| --- | --- | --- |
| PRD / 需求文档 | 目标、范围/非目标、F/R/AC、状态机、权限、字段、NFR、待确认、变更记录 | 路径 + 章节/页码 |
| 迭代方案 | 本期增/改/删、相对上版变化、依赖、验收 | 与 PRD 的对应 |
| 页面原型 / 截图 | 页面、导航、组件、字段、状态、交互、文案、权限可见性 | 页面名/画板号 |
| 接口 / 技术文档 | 接口、字段、错误码、鉴权、时序、限制 | 版本 + 路径 |
| 代码 / diff | 实际实现、改动面、兼容约束、历史包袱 | 分支/commit/文件:行 |
| 历史缺陷 / 工单 | 高发模块、根因、回归锚点 | 单号 + 日期 |
| 现网行为 | 当前口径、边界、异常表现 | 环境 + 构建 + 证据 |

- **主读判定（维度）**：用户路径点名 > 唯一命中正式版 > 当前计划已登记主读 > 否则列候选+建议一问。已点名 → 不重问，仍须产出分析。唯一正式版可拟认，但须在分析表 §0 / 理解门写明路径供确认。
- 依据缺失 → 一句话说明缺口，按现有主读/基线执行；不因缺 PRD 整段不测。
- **多份依据**：定主读与对照；联测多版本须显式「主读 + 对照」。冲突列双方原文，**默认不静默选边**；用户可声明 `冲突SSOT=指定文档|最新一期`，声明后写入 §0/§4 并按 SSOT 执行。
- 大输入（版本级 ≥5 份或长文档）→ 按 `规则/专项/多Agent与输出.md` §1.5 只读扇出，每份返回变更点/AC/影响面候选 ≤30 行，主上下文统一建模。

## 2. 需求模型（十要素 + 证据）

```yaml
requirement_model:
  goal:            # 一句话目标 + 成功标准
  scope:           # 范围内 + 明确非目标
  roles: []        # 角色 → 能做什么/不能做什么/数据域
  inputs: []       # 来源/格式/约束
  outputs: []      # 去向/格式/消费方
  states: []       # 状态A --事件--> 状态B；非法跃迁
  rules: []        # 业务规则/校验/阈值/计算口径
  exceptions: []   # 失败/空值/重复/并发/超时/降级
  dependencies: [] # 上下游/共享数据/时序/外部系统
  open_questions: [] # 未定义/冲突/待裁决 + 用户裁决
```

- 每条 `rules/states/exceptions` 标 `evidence`：文档章节、页面/画板、接口字段、`文件:行`、现网证据。
- 空字段写“已核对，无此类要素”；不要留空。
- 需求点沿用原文编号 `F-xx/R-xx/AC-xx`；没有则建 `RQ-xx/TP-xx` 并记来源，禁止重编号断链。
- 用户裁决写入 `open_questions`，后续不得用代码/实现推翻。

## 3. 五遍分析

### 第一遍：结构与元信息

- 文档类型/版本/状态/owner/日期/适用范围；主读与对照。
- 变更记录：本版相对上版改了什么；旧版是否仍被引用。
- 产出：依据清单 + 主读 + 已读/未读章节。

### 第二遍：需求模型

- 按十要素抽取；先名词（对象/字段）→ 动词（状态变化/动作）→ 规则（约束/阈值/来源）→ 异常（失败/边界/权限）。
- 变更点三问：变了什么、影响谁（邻接）、回归边界在哪。有 GATE/前序依赖 → 回归边界含依赖版 P0-Smoke（禁有界对照替代）；无关跨域默认排除。
- **强制写入分析表 §0**：本期差量表（增/改/删）+ Brief；有产品/开发 Delta → 引用对账；产出：需求模型 + 变更点/影响面候选。

### 第三遍：一致性检查

| 检查 | 要发现 |
| --- | --- |
| 文档内部 | 摘要/正文/附录/FAQ 对同一功能描述不一致 |
| 跨文档 | PRD vs 迭代方案 vs 接口文档 vs 测试报告 |
| 文档 vs 原型 | 页面/字段/状态/权限/文案不一致 |
| 文档 vs 代码/现网 | 规则、状态机、字段、默认值、错误码不一致 |
| 文档 vs 计划 | 范围、版本、里程碑、依赖冲突 |
| 术语 | 同一概念多个名字；同一名字多个含义 |

冲突格式：`{ID}｜{主题}｜A: 原文+位置｜B: 原文+位置｜影响｜建议裁决｜待确认`。默认不裁决；用户裁决后落盘。

### 第四遍：歧义九类扫描（逐类过筛）

| # | 模式 | 扫描问题 |
| --- | --- | --- |
| A | 时间口径 | 每个“X 天/小时/年/每天 N 次”：起算点？自然单位还是滚动窗口？含否当日/时区？ |
| B | 数值边界含否 | 每个“1–20/N 以内/不超过”：端点含否？非整数/取整方向？ |
| C | 规则冲突与叠加 | 同一对象多处规则（正文/活动页/FAQ）：替代还是叠加？冲突以谁为准？ |
| D | 术语一致性 | 同一概念多个名字？同一入口/模块？ |
| E | 异步时限 | 每个异步/延迟/自动行为：多久不发生判失败？无时限即不可测。 |
| F | 部分场景 | 退款/部分支付/部分失败：按比例还是全额？负数/欠额如何处理？ |
| G | 并发与顺序 | 并发到达以谁为准？用户操作与定时任务/自动流程的竞态？ |
| H | 未定义判定口径 | “异常账号/高风险”等判定标准；历史数据保留期限与可查范围。 |
| I | NFR 指标空缺 | 性能/容量/可靠性/兼容性只有定性无指标：吞吐、并发、响应阈值？兼容基线？SLA 与测量方法？ |

- 命中即进 `open_questions`，**不允许跳过**；I 类要么问到数值，要么用户显式裁定“本版不验证”并进范围非目标。
- 另扫：模糊形容词（快/稳定/友好/合理/尽量/等等）、缺失错误路径、缺状态转换、缺权限、AC 不可观测、无非目标。

### 第五遍：可测性与 oracle

- 每条 AC 检查：条件 + 动作 + 可观测结果；不可观测 → 问或标 GAP。
- **oracle 来源**：需求原文 > 验收标准 > 接口契约 > 业务规则 > 用户裁决；现网实现只能作“现状”，不能自动当预期。
- 文档未写死数值 → 仍出行为用例；预期写“以本构建实现值为准”，执行前先读现网口径再断言。
- 异步/延迟 → 必须问出判定时限；无时限写“待确认”，不得拍脑袋。
- 文档未声明权限 → 至少 1 条角色冒烟，或用户显式接受不测（见覆盖三闸）。

## 4. 可测点与追溯种子

- 抽取维度：验收/GATE、主成功路径、状态与非法跃迁、权限/数据域、明确异常与阻断、变更点、影响面（逐邻接点）、负向边界、UI/体验、NFR。
- **显式 vs 隐式**：原文写明的标 `[REQ/F/R/AC]`；推断补出的标 `[IMP-xx]` 并**强制**进 `open_questions` 或「用户确认后升格」——**禁**把推断当规格静默写进断言（对齐市面 qa-skills / test-analysis 纪律）。
- **不变量（Invariants）**：抽「必须始终成立」的约束（如库存≥0、金额守恒、租户隔离）；每条不变量 ≥1 个 TP/用例，缺则覆盖缺口。
- 每个可测点建 `TP-xx`：`TP-xx｜来源｜前置｜动作｜可观测预期｜风险级｜建议测试类型｜去向（用例/不测+理由）`。
- 追溯链：`RQ/AC/F/R → TP → 用例 → 执行结果 → 缺陷`；任一环断开都要显式写缺口。
- 覆盖矩阵：需求点 × 测试点 × 用例；P0/GATE/主链/不变量不得空行；空行=缺口，不得写“已全覆盖”。

## 4.1 章节回执（主读完整性 · 不可让）

- 主读**逐章/逐节**核对：每章「有设计点→已入覆盖单元表」或「无设计点（一句）」；**缺章不得称已理解/已覆盖**（与工作流三闸①同口径）。
- 长文档可扇出分章，但编排合并后回执表必须齐；未读章节标「未读」不得当已覆盖。

## 5. 输出（专门分析表 · 企业惯例）

> **市面做法**：ISTQB Test Analysis 产出 **test conditions**；企业用 **RTM/测试分析工作表** 夹在「原文」与「用例」之间——**不是**直接对着 PRD 写用例。本仓等价物即下表文件。

- **主产物（必落）**：按模板 `规则/模板/10-计划/测试分析表模板.md` 写到项目实例  
  `测试/测试分析表.md`（跨轨共用；勿再默认写到 `功能测试/` 下）  
  必含：**§0 Brief+本期差量表**｜§2 覆盖单元（测试条件，含 Delta ID 列）｜§3 影响面｜§4 歧义冲突｜§6 章节回执；T2/T3 加 §5 追溯矩阵。  
- **兼容**：若实例仅有旧 `测试/功能测试/测试分析表.md` 或「分析短表」→ 迁入 `测试/测试分析表.md` 或头注见新路径并补 §0；下游以新路径为准。  
- **跨轨**：功能/专项双读全文表；接口/发布前/探索式生成或定范围前至少读 §0。  
- **完整叙述（T2/T3 可选加厚）**：另落 `测试/功能测试/需求理解-{范围}-{yyyyMMdd}.md`（十要素长文），仍须有测试分析表中的表结构（含 §0）。  
- **双读纪律**：plan/generate/execute **必须**同时读「主读原文 + 测试分析表」；禁只读原文跳表，禁只读表丢原文证据。  
- 收尾索引：分析表路径 + §0 差量行数 + 未裁决项数 + P0 风险 + **理解是否已确认**。

## 6. 澄清与确认（强制 · 卡住下游）

- **确认门主屏**：§0 Brief + 本期差量表 + 冲突/GAP 计数；附 §1 回执要点。禁止无 §0 宣称已理解（T0 可迷你差量 ≤3 行）。
- 先分析/给建议；只问 0～1 个高影响问题（总≤3），按 `规则/核心/澄清.md`。
- **关键歧义未裁决 → 不得写确定计划范围/用例断言**；草案须标假设与影响。
- `confirm_understanding` 通过前：**禁**计划「已确认」、禁正式 generate、禁把执行结果判整体通过。只确认「理解、本期变化与 oracle」，不替代计划门/门2。
- **准出挂钩**：迭代准出报告须能回指测试分析表 §0/「理解已确认」+ 覆盖矩阵无 P0 空行；理解未确认、无 §0、或关键 GAP 未关闭 → 不得写「功能准出/开发实施已验证」。

## 7. 常见坑（反模式）

- 只读 PRD 不读原型/接口/代码；或只读代码不看需求，把现状当预期。
- 把“文档没写”当“不用测”；不列 GAP。
- 把模糊形容词直接写成用例预期（“正常/正确/快速/稳定”）。
- 先写用例再补需求模型；追溯链断裂。
- 发现文档冲突静默选一个；或按实现改预期。
- 需求点没有编号/来源；覆盖矩阵无法复核。
- 有覆盖单元无 §0 差量表，或「本期=是」无法回溯 Delta ID。
- 无视产品/开发已有 Delta 另造一套 ID。
- 把探索式/接口/发布前的方法混进功能用例；或把测试策略写成用例。
