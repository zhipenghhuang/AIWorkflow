# AGENTS.md

> **用途**：测试规范 AI 入口。常驻最小集；命中口令 → `workflows/*.yaml` 当前 step → `规则/读取索引.md` 当前行 → 当前 `agents/*.yaml`。
> **位置**：`测试规范/`。与项目根 `AGENTS.md` 冲突时，以项目根为准；红线不被覆盖。
> **template_version**：`2026.10.29.16`（单点：包内版本以本文为准）。
> **架构**：Workflow + Agent + 规则/门/读取索引 + 技能/能力 + 验证层（台账/报告/覆盖/评审/回写）；主链分析→计划→生成→**用例评审（先选自行｜AI）**→执行→报告。

## 0. 开工（每任务）

1. **中文**：对话与结论用中文；写现行结论。
2. **activeContext**：任务前读 `activeContext.md` 总览 + `## 测试` 的 `### 进行中` + 跨包同步；先按 `进行中` 报备任务/状态/下一步（2～3 句），无则按模板补建（只建本包节）。任务开始/状态变化/阻塞/收尾时更新本包 `### 进行中`；收尾只改本包分节。多包时禁改他包分节/接入行。
3. **接入状态（一次判定）**：运行时有 `测试规范接入：已完成`（兼容旧 `landing=ok`）→ 禁止再预检，直跑命中 workflow；无标记且命中生成/执行/缺陷类口令 → 仅此一次按 `agents/onboard-agent.yaml` 核验，通过则写标记（删旧 `landing=ok`）静默直跑，未接入则走 `onboard.yaml` 后 resume。
4. **独立判断**：不迎合；先查错误前提/逻辑跳跃/信息缺失；数字/结论与台账/报告同口径并尽量核实来源；用户有误直接指出依据与风险。
5. **冲突优先级**：安全/合规/硬红线（§0.2/§0.4） > 用户明确指令 > 项目根 `AGENTS.md` > 本文 > 当前 agent 契约。红线不被覆盖。
6. **读取协议**：

| 场景 | 读什么 |
| --- | --- |
| 任意已路由 | 本文 **§0 硬节** → workflow 当前 step 块 → 读取索引当前行 → 当前 agent/产物（口令表仅路由未定/首次命中时读） |
| 路由未定/首条 | 本文 §2 口令表或 `规则/核心/入口判定.md` → 再按上行走已路由 |
| 有门/写 YAML | `规则/门.md` 当前行；不通读全表 |
| 生成/执行 | `规则/playbooks/generate.md` 或 `execute.md` + `工作流.md` 当前节 + 当前轨契约；不跨轨通读 |
| 验证/收尾 | `验证/README.md` + `规则/核心/验证规则.md` + 计划/台账/报告 |
| 交接/变更 | `规则/协作/协作与交接.md` 当前节 + 交接包说明模板 + 台账；变更按 C0～C3 |
| 脚本档 | `规则/专项/脚本执行.md` §3/§4 + executor README；失败再按 `playbooks/execute.md` 升级 |
| 维护/查询 | 本文 + `规则/核心/维护.md` + 点名 |

同一会话文件未变不重读；后续 delta-only；同方案无效 2 次换手段。**workflow 只读当前 step 块（当前 `- name:` 到下一个），不整文件通读。** 规则阅读不是越多越稳：读错轨/读全本会稀释约束。**读取预算（目标，非硬上限）：常规单步 ≤3 个来源/≤8k tokens；确需更多只读当前节并在收尾说明，不得为省预算跳过门/证据/红线。**

7. **执行契约**：判断模式（execute/analyze/stop）、自主边界、步骤契约、计划同步见 `规则/核心/执行契约.md`。规则是下限不是百科全书；低价值步骤可合并/省略，但输出/门/证据/红线不可省；跳过与自主取舍写收尾【遵守自检】，不静默偏离。

### 0.0 事实与文档（硬规则）

- 环境/构建/账号/日期/结果/缺陷号/发布窗口/审批结论等事实字段，必须来自配置、命令输出、权威文档或用户确认；未核实写「待确认」并问，禁止用默认/示例/历史值补。
- 生成后回查关键字段；同一事实只保留一个来源；**当前有效状态**：只写当前存在的功能/流程/规则/约束；删除即移除，不追加「已删除/已废弃/不要再用」；不写历史过程、旧方案、变更原因、未采纳方案；对用户输出结论性现行状态，不复述需求与「本次改了什么」。细则见 `规则/核心/文档质量标准.md` §1 第9条；结构完整≠合格。
- 母版只维护通用高标准；项目实例默认不改，但不锁死：发现模板/规则/技能不匹配 → 先出「拟改/原因/影响」，用户确认后只改当前实例并登记；不自动回灌母版。
- 模板是骨架、标准是底线：按项目实际裁剪，不适用写「不适用 + 理由」；产出层能解决的不改母版。
- **版本标识分离**：产品/测试版本、构建/制品、部署版本、文档版本分开；测试只认实际部署版本；文档提交不改变项目版本；项目必须暴露版本查看方式（页脚/接口/清单）。

### 0.1 计划门与三门 · 澄清

- **只认 YAML 步上 `hitl`/`gate_when`**；不满足跳过，专规不另造门。**计划门**：版本级首版/换代或范围·准出·缺陷策略实质变更才停，同会话同载体一次。
- **门1/2/3**：主读未点名一问；执行范围/环境未确认才停；拟入库/交平台/新建缺陷单才停；计划驱动已确认→【已预授权执行：按计划】。
- **澄清**：先读规则/技能/主读/代码/现网，再给「理解+建议+0～1 拍板」；总提问 ≤3（阻塞/安全/合规不受限，仍一次一问）；连续 3 轮无新信息收敛。
- **依据先建模**：PRD/方案/原型/接口先按 `test-basis-analysis` 建需求模型/歧义/oracle；无来源不写断言，不按现网反推。**依赖回归**：前序依赖须含依赖版 P0-Smoke 实测，不重跑归档全量。
- **预授权**：「直接跑完」只到任务完成，不含提交/推送/部署/交平台；计划内执行视为预授权；计划外交平台仍门3。
- **期中/缺陷分流**：新变化→CR+影响分析；A/B 就地更新、C 回计划门、D 缺陷轨；平台提交/查重/回归→`defect.yaml`；修 Bug 代码不在本包。

### 0.2 硬红线（易疏忽）

1. 禁臆造路由/接口/按钮；正式资产只写现行有效。
2. 密钥/凭据不入库/不进提交；基线密码明文仅限授权测试环境；真实 PII 不入证据/平台。
3. 子代理不 git/不交平台/不改他模块；模块档只写本模块台账/证据；拆分档 Worker 仅写 DraftPath；编排核验后结论。
4. 先 UI 再 Network；禁猜未见 API 判失败；禁换验收载体；口径只钉本载体实现值。**用例/方案点名菜单或页面时**：须浏览器 MCP 或脚本档 UI 走完主路径再对同源 Network；禁自造「AI-API」通道、禁纯 API 冒充该条终态（仅接口轨或用例入口本就纯 API 除外）。
5. 阻塞从严：缺数据先造/换；可绕过照跑；产品问题记失败；无菜单无接口→待实现，入口在但 404/500/空壳/假成功→失败；blocked 四问未过不写 blocked；互异手段≥2 总尝试≤3。
6. 禁刷绿：不手改结果表；失败实拍进 `测试/功能测试/证据/{模块}/`；P0 未过不得整体通过。
7. 能脚本不 AI：已脚本化回归走脚本档；脚本失败有界复核后定性；禁直接交平台。
8. 计划驱动不跳轨：按 §9.2 阶段执行，每阶段按轨契约；不跨轨通读/不静默降范围；实质变更回计划门。
9. 依据可追溯：用例/断言指到需求/AC/规则/原型/接口；无来源先问或标“文档未声明”；冲突记失败/待确认，不按实现改预期；弱证据/改题不交平台。
10. 资料：设计输入 `测试/资料/{版本或主题}/` + `_通用/`；入站 T1～T9；采纳后 S1/S2/S3 同批归档；换代/换主题同会话 §7 关账；各轨资产轨内归档；计划/报告/CR/交接→`测试/_归档/`；交平台须回执，无权限 export。
11. 体验验收：UI 减法；资产三维不退化。

### 0.3 执行中（效率）

- 多解先权衡；路径唯一直接做；动手前说明拟改文件；最小改动；过程只落 `.draft/`；本批未终态齐 → 禁【执行收尾】/拟提交。
- 工具点名优先；能脚本不 AI、少全量快照、按 step 读规则（成本见 `多Agent与输出.md` §1.3/§3）。

### 0.4 工程红线

1. 不在生产/未授权环境执行；造数仅授权测试环境；严重度按业务影响（S1–S4），拿不准问。
2. P0 未过不判整体通过；准出对照计划；未测列缺口；有条件通过仅限 P0 全过、缺口非 P0 且用户接受。
3. 子代理/并行隔离账号/数据/profile/写域；同条用例禁并行。

### 0.5 自主与文档

- 判断模式/自主边界/步骤契约/计划同步见 `规则/核心/执行契约.md`；不可让：口令/门/证据/密钥/角色写域/资料形态/单包闭环/覆盖三闸/准出；可自主：拆分/划批/探查/子代理。
- 文档只写现行；删除即移除；例外（变更/CR/复盘/日志/`测试/工作日志.md`）可留痕，不回流正式资产；**禁止**写入根 `CHANGELOG.md`。

### 0.6 验证与汇报（硬约束）

1. **报告只认门**：正文完成后、宣称准出前跑 `-Mode report`，读 `.gate/测试规范/report.json`；无 PASS/CONDITIONAL 只能报不通过/阻塞/未验证；`writeback` 只写 `writeback.json`。
2. **数字/P0 对账**：报告 §4 与台账 §1/§2 一致；P0 必须在台账存在且终态；P0 缺失/未过不得称整体通过；有条件通过仅限 P0 全过、缺口非 P0 且用户接受。
3. **证据可打开**：失败/阻塞/待实现须有证据或恢复条件；路径不存在=FAIL/BLOCKED。
4. **报告先写回执**；非 PASS 禁用“全部通过/可发布”；回写前跑 `-Mode writeback`，无回执不得称已回写。
5. **用例评审先选方式**：T1+ `select_review_mode`（A 自行｜B AI）；B 才跑 `-Mode review` 且写手不得自审；A 须 HUMAN_APPROVED；未放行不进 P2。
6. **成本**：模块批末 `execute -Scope`；准出 `report` 全仓；不全量回归每个补丁；不新增测试文档。

**计划驱动主链**：生成测试计划→**计划/分析 A/B 评审**→计划门确认→生成用例→**多轨资产评审（放行）**→按计划执行→报告/准出。

**执行三态**：「继续」=续跑未完成；「回归/重跑」=重测既有用例（结果就地覆盖、只留最新）；缺陷平台单回归→行 5。
**需求理解前置**：`生成用例/资产`、`测试计划`、`按计划执行` 前必须已有按 `技能/test-basis-analysis/SKILL.md` 产出的需求模型/分析短表；输入含 PRD/原型/方案而未建模 → 先回 analyze，不得直接写用例。
**用例评审前置**：功能全量/专项 T1+ 在进 P2/正式执行前必须经 `review-cases` 放行（或机器门 PASS）；生成写手不得自审自放行；T0 可 SELF_CHECKED 并声明。方法：`技能/testcase-review/SKILL.md`。
**无口令**：口语未命中上表 → `规则/核心/入口判定.md`（通用意图类，非口令同义词表）。
首条：`route=workflow:<id> | step=<id> | role=<agent> | mode=execute/analyze/stop | reason=… | reads=<读取索引行> | next_action=…`；仅无标记预检时加 `preflight=onboard`；有主读/输入时加 `input=<路径>`。

## 3. 实例路径

提交/推送前：拟提交清单 + `.gitignore` 现状 + 当前分支 → 用户确认后执行；禁擅自切主干、force push、开/合并 PR（除非点名）。完整任务收尾检查仓库状态与 `.gitignore`，写入收尾第 2 点。

## 5. 收尾

触发：工作流末步、计划全部阶段结束、点名「收尾/总结」。**对照** `规则/模板/90-交接与收尾/收尾骨架.md` §2（生成/执行用【生成收尾】/【执行收尾】；专规只填第1点）。**必须含【遵守自检】**，缺项=未收尾。门3 在骨架后单独确认；完整【拟提交】在 handoff/commit 只展示一次。

## 6. 维护

改不变量/路由/读取协议 → 本文；改无口令路由 → `规则/核心/入口判定.md`；改步骤 → `workflows/`；改角色 → `agents/`；改红线/门 → `规则/`；改澄清 → `规则/核心/澄清.md`；改协作/交接/变更分级 → `规则/协作/协作与交接.md` + `workflows/handoff.yaml`；改轨边界 → `规则/轨契约/`；改模板/技能/能力 → 对应目录；改计划编排 → 测试计划模板 + `工作流.md` §3.6 + `规则/专项/多Agent与输出.md` §4（三处同步）；改读取索引 → `规则/读取索引.md`。自检见 `规则/核心/维护.md` §2。

## 7. 多包（自动探测）

项目根同时存在 ≥2 个包目录（以各自 `AGENTS.md` 为标志）= 多包；否则单包。
- **单包独立为默认**；多包联动可选，不要求装齐三包、不强制同时启用；跨包同步只登记状态，不等于自动联动。
- 共享 `项目资料/`（首次需要时建）、根 `activeContext.md`（总览 → 已启用包分节 → 跨包同步 → 运行时；单包只建本包节）。
- 各包只改本分节、与本包相关的跨包同步一行、本包接入行；禁止整文件覆盖或改他包分节。
- 一次会话只执行一个包 workflow；跨包交接用 `测试/交接/{HO-ID}/` 整包；不复制正文、不自动执行对方 workflow。
- 单包不启用以上规则，仍用同分节骨架（仅本包节）。

## 8. 技能与能力（按步加载）

- **角色边界**：谁负责/能定什么/何时停/向谁升级见 `规则/协作/角色契约.md`；出现职责冲突先查此表，不靠聊天记忆。
- **技能（必用）**：`技能/<name>/SKILL.md`，随包复制、命中步必用；方法见 `技能/README.md`。本包副本可在「体检能力」确认后就地改技能（单包/开源落地无需另有母版仓）。
- **技能质量**：新增/大改技能按 `技能/README.md` 末节「技能质量标准」；description 必须含中文触发词，单文件 ≤500 行，超长拆 references。
- **能力（可选）**：`能力/00-能力注册表.md`；已安装即用，未安装降级；能力不替代技能。点名「装配能力」=安装向导；「体检能力」=诊断+优化（含就地改技能/能力表），见 `workflows/skill-audit.yaml`。
- **适度建议（业务会话）**：仅当有证据表明现行技能/能力达不到本任务要求、与基线/计划明显不符、或持续降级损害准出时，在收尾待确认表附 **至多 1 条**（对象+现象+「说体检能力」）；禁推销清单、禁未确认改技能。同会话同类只提一次。
