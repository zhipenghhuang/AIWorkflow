### 5.0.0 平台标题前缀（提交时）

> **格式**：`[V{版本}][{测试类型}]{正文}`（无版本标时：`[{测试类型}]{正文}`）。  
> **正文**：= 台账「问题标题」=`{页面/模块}：{动作，偏差，后果}`；**≤56 字**；禁只写 caseId /「有问题」。  
> **顺序固定**：版本标（有则）→ 测试类型标 → 正文；两标均用 `[]` 包裹，紧挨、无空格。

| 前缀 | 何时 | 取值 |
| --- | --- | --- |
| `[V{版本}]` | 本轮测试来源迭代版本**已确认** | 计划 §1「版本/构建」或台账环境「版本·构建」；计划状态=已确认/执行中/待关闭，或本轮用户/提测已点名。写法：去掉多余 `v`/`V` 后统一写成 `V`+号，例 `[V2.6.0]`。**未确认/未知 → 省略，禁猜造** |
| `[{测试类型}]` | **每单必加** | 与台账 §1「测试类型」/本轮轨道对齐：`功能`｜`接口`｜`探索式`｜`随机`｜`性能`｜`安全`｜`兼容`｜`迁移`｜`回归`；专项名收束到上列；拿不准按主轨；禁空括号 |

**示例**：`[V2.6.0][功能]登录页：点击提交无响应，无法登录`；无版本：`[安全]权限页：越权仍可读订单金额`。  
**查重**：按正文关键词/同路径同现象；勿因前缀差异漏判重复。  
**【提交摘要】/§5.2 清单**：写完整平台标题（含前缀）。

## 6. 执行收尾衔接

入口：**计划 §11 预授权** 或 工作流 §4 用户确认交平台。范围：失败 + **待实现（实现缺陷）** + 用户指定；阻塞默认不交。  
流程：查重→§5（十段齐+§5.1 自问）→§5.2。询问句式按策略：发现即提交=不逐条问；按模块批末/阶段末/收尾确认=在对应批次/阶段/收尾出清单后问一次；export=出包。  
**与交接包**：有平台且已交平台 → **不**发 `BUG` 整包（§3.1.1）；无平台/`export`/点名「缺陷交接包」→ **先问后发**自包含详单包（不依赖平台单号）。任何 HO 包禁静默生成。

### 6.1 计划驱动提交策略

- 计划 §11 选择「发现即提交」且计划 §0 状态=已确认/执行中/待关闭 → 执行中查重后**直接提交**，不再逐条问；仍须十段齐+证据+回写台账；收尾列提交清单。**建单不触发 `confirm_remark`；关闭/激活/解决等平台状态回写仍按 §3 确认**。  
- 「按模块批末提交」→ 按计划 §11.2 批次边界执行：功能每模块、接口每域/模块、非功能每专项、探索每章程/会话、回归每修复批次（P0/P1 冒烟缺陷并入当天批次）；批内先落台账，**批末出拟提交清单（失败+待实现+用户指定）→ 用户确认 → 只提交确认项**；批内不逐条问，不跨批累积。  
- 「阶段末提交」→ P2/P3/P4/P5/P6 每阶段末汇总一次；阶段内先落台账，阶段末出清单→确认→提交。  
- 「收尾确认」→ 按门3 一次确认后提交；「仅导出」→ AI 出提交包，用户提交后回填编号。  
- **待实现=实现缺陷**（方案/AC/计划范围内应实现未实现，菜单无入口且无接口）→ 必须进入批次/阶段/收尾提交清单，且须有缺失证据（菜单/接口/方案对照，可非截图）；**入口存在但 404/500/空壳/假成功→`fail`（实现缺陷）**；不得以“未实现”免交；明确范围外/后续池→`不适用`，不标待实现。**阻塞默认不交**；用户点名除外。  
- 未配置平台/未授权 → 默认 `export`，禁猜接口；计划外提交仍按门3。  
- 同因不重复提交；同批修复可合并一次回归。  

### 6.2 产品缺陷直提（不经开发）

- 分类为产品缺陷 → 提交后**直接指派产品负责人**，不指派开发；平台状态按 §13 映射置「待确认/打开」。  
- 【提交摘要】写「缺陷类型：产品缺陷」；平台无类型字段时标题或【提交摘要】首行写「产品缺陷」；【设计对照】必须含 `相符证明` + `证据`；正文明示「请产品确认分类与处置」。  
- 产品回复前，测试不按实现缺陷催开发；产品判定后按 §7.4 分流。  
- 产品判定为实现缺陷 → 产品指派开发，测试等待修复；产品判定为产品缺陷 → 产品改资料/出新文档并指派开发，测试按新 AC 回归；产品判定非问题/重复/信息不足 → 产品指派回测试，按 §8.8 处理。  
- 三包独立：不要求产品包与测试包同目录；以平台单号/备注/附件为准。

## 7. 回归（平台写回一次确认）

复测范围与升级：按 `工作流.md` §3.1「修复后回归（默认口径）」——默认=原单复测+冒烟子集；影响面组建议制（用户点头才跑）；高风险/连环缺陷提示升级。

### 7.0 计划驱动连续回归

- 优先 P0-Smoke 脚本 + 受影响模块用例；每次修复后立即回归，不等批末；范围=原单+冒烟子集+影响面组（计划 §10）。  
- 结果就地覆盖台账/证据，只留最新；报告 §5.2 汇总轮次/通过率/遗留。  
- 高风险/连环缺陷提示升级（模块局部全量/扩大邻接回归），用户确认后执行；同批修复合并一次回归。  
- 平台单回归（本轨）与计划内功能回归分轨：本轨写回平台状态，计划回归写台账/报告，不混用结论。  

### 7.1 拉单范围（先指派，不先过滤已解决）

| 口令 | LIST 默认范围 |
| --- | --- |
| 「指派给我 / 我的 / assigntome」+（回归\|验证\|复测）或仅「回归」+平台未收窄 | **指派给当前账号的未关闭单**（含打开/已解决）；**禁止**仅因「未点已解决」整批丢弃（过滤字段按 §13） |
| 「缺陷变化巡检 / 我提交的 / 看回复」 | **我提交的/我关注的未关闭单**（含指派给开发/产品/测试）；只读变化，不默认回归 |
| 「我关注的单」 | 显式清单；只读变化 |
| 点名「回归已解决」 | 收窄为已解决（可再叠加指派给我） |
| 点名单号 | 仅这些单 |

每条拉单后**先读再动手**：标题、正文/steps、严重度/优先级、状态/处置、指派、验证构建、**历史/备注**、附件、最后编辑时间（字段名按 §13）；按 §7.3 做快照 diff（`solutionChannel=manual` 时备注/附件读不全 → 先请用户补关键备注/附件再分拣）。

### 7.2 分拣（大部分走正常回归；未解决看内容）

> 左侧为**语义信号**；平台枚举经 §13 映射（禅道 resolution 示例见 §4.1）。确认包写语义动作，执行时换成映射取值。

| 信号（状态 ∪ 处置结论 ∪ 最新 actor/备注/附件） | 处置 |
| --- | --- |
| 已解决 + 处置=已修复（多数） | **正常回归**：核验证构建 → 复测 → 拟 `close` / `activate`（§8.1/§8.2） |
| 仍打开，但备注像「已修请验 / 请回归 / 复测」，或疑似忘点解决 | **按回归复测**。通过：拟 `resolve_fixed`+`close`（权限不许 → 备注请有权人补点后再关）；§8.2 并写明「本轮平台仍为打开」。未通过：拟 `activate` 或保持打开 + §8.1 |
| 仍打开 + 最新 actor=product + 新备注/附件（新 AC/文档） | **产品确认/新口径**：暂停回归 → `工作流.md` §2.6 建 CR → 更新资料/计划/用例/脚本 → 按新 AC 再回归；不在缺陷轨直接改用例 |
| 已解决或仍打开 + 处置=无法复现，或备注「无法复现/请补充/看不懂」 | **开发无法复现/需澄清**：补测/补证 → §8.4 → 确认后回写并回派开发；不默认 `close` |
| 已解决或仍打开 + 处置=非修复（设计如此/重复/外部/延期/不修/转需求） | **非修复处置**：按 §8.6 核对；同意则关闭/转需求/纳入遗留，不同意转产品 |
| 回归发现不同失败/新问题 | **新问题**：按 §8.5 另建单并链接原单；原单按原失败是否仍存在决定激活/关闭 |
| 仍打开，无验证/疑问/产品确认意图（纯开发待修误指派等） | LIST 标「非回归候选」+一句依据；一问排除或转开发待修；禁当已解决硬关 |
| 关闭后新备注/附件 | 同因复发/新问题判断；同因按团队口径重开或新单，新问题新单 |
| 读完仍无法判定 | 列入无法判定，一问后再测 |

```text
LIST（指派给我/我提交的·未关闭 + 读 actions/files/lastEditedDate）→ §7.3 快照 diff → §7.2 分拣
→ 产品确认/新文档 → §2.6 CR；开发无法复现 → §8.4；回归 → §8.1/§8.2；新问题 → §8.5；非修复 → §8.6
→ 对内结论 + 备注全文 → 一次 AWAIT_CONFIRM → 按类写回（备注同轮）→ §8.7 回查
```

对内每条：`bugId`、分拣类、`caseId`（或直接回归）、通过/失败/澄清/补充/新问题/非修复/排除、主键、页面/接口依据、建议写回动作。

```text
【缺陷协作·回归结果】
1. **回归结论**：拉单{N}；正常回归{R}；建议关闭{A}；激活{B}；澄清/补充{C}；产品确认/转 CR{P}；新问题{X}；非修复处置{D}；排除{E}；无法判定{U} — {一句}
2. 各单：#{id} → 关/激/解决+关/澄清/补充/新单/转需求/排除/未知（一句+分拣依据）
3. 确认包见 §8.3（备注全文仅此处展示）
```

### 7.3 拉单读取与变化识别（巡检/回归共用）

> 目标：无论单是指派给开发后回测试，还是直接回测试，都能读到最新备注/附件并判断“变了什么、下一步做什么”。巡检只读不写回；产品确认/新文档转 §2.6。读取字段、快照 diff、指派路径以本节为准；§7.2 只定分拣结论。

#### 7.3.1 读取字段（语义；平台字段名按 §13）

| 语义字段 | 用途 |
| --- | --- |
| 状态 / 子状态 / 处置结论 | 判断阶段：待处理/已解决/已关闭/延期/不修 |
| 指派人 / 指派时间 + 最新历史 actor | 判断谁在等谁；避免把产品确认当开发修复 |
| 验证构建 / 解决时间 | 验证构建；没有含修复构建不回归 |
| 历史/备注流（actor/动作/时间/正文/字段 diff） | 读全历史；识别产品/开发/测试意图 |
| 附件列表（id/名/上传者/时间） | 附件读取与分类 |
| 最后编辑者 / 最后编辑时间 | 变化检测；决定是否重读 |
| 重开次数 / 重开时间 | 判断反复（平台无则跳过） |
| 重复主单 / 关联单 | 关联主单/相关单 |
| 创建人 / 创建时间 | 判断是否本人提交 |

#### 7.3.2 附件读取

- 列出附件并下载读全文；不只看文件名。
- 分类：设计文档/PRD/AC → 转 `工作流.md` §2.6；日志/HAR/console/录屏 → 证据；截图 → 对照断言点。
- 记录 id/name/uploader/date/hash；详情附件字段为空时按 §13 回查或页面附件区（禅道见 §4.1）；附件不属于该单 → 不采用。

#### 7.3.3 快照与 diff

- 每条记录 `lastReadAt/lastActionId/lastActionDate/lastEditedDate/lastStatus/lastResolution/lastAssignedTo/lastResolvedBuild/lastAttachmentIds`（台账或 `.draft/`；字段名经 §13）。
- 拉单后比快照：字段变了/有新 action/有新附件 → 标“有变化”；无变化 → 跳过，不重复读。
- 有变化：读 `lastActionId` 之后的全部 action；看字段 old/new；新附件按 §7.3.2 读。

#### 7.3.4 意图与分流

| 信号 | 意图 | 动作 |
| --- | --- | --- |
| 产品 actor + 新备注/附件 + 新 AC/文档 | 产品确认/新口径 | 暂停回归 → §2.6 建 CR → 更新资料/计划/用例/脚本 → 按新 AC 再回归 |
| 开发 actor + 处置=已修复 + 有验证构建 | 修复待验证 | 核构建 → 回归 |
| 开发 actor + 处置=无法复现 / “请补充/看不懂” | 开发无法复现/需澄清 | §8.4；不默认 `close` |
| 开发 actor + 处置=非修复 | 非修复处置 | §8.6 核对依据/关联/风险 |
| 回归发现不同失败 | 新问题 | §8.5 新单链接原单 |
| 关闭后新备注/附件 | 新信息 | 同因复发/新问题判断 |
| 无新变化 | 无 | 跳过 |

#### 7.3.5 指派路径

| 状态/指派（语义） | 含义 | 动作 |
| --- | --- | --- |
| 打开 + 指派=开发 | 开发处理中 | 不抢单；巡检；S1/S2 超时升级 |
| 打开 + 指派=产品 | 产品确认中 | 不抢单；巡检备注/附件 |
| 打开 + 指派=测试 + 最新 actor=product + 新备注/附件 | 产品确认/新口径 | 不是“已修复”；先 §2.6 CR，再决定补测/回归 |
| 打开 + 指派=测试 + 最新 actor=dev + “请澄清/无法复现” | 需测试澄清 | §8.4 |
| 打开 + 指派=测试 + 最新 actor=dev + “已修请验”（忘点已解决） | 修复待验证 | 按回归；通过后 `resolve_fixed`+`close` |
| 已解决 + 已修复 + 指派=测试 | 开发已解决 | 正常回归 |
| 已解决 + 非修复处置 | 非修复处置 | §8.6 |
| 已关闭 + 新备注/附件 | 关闭后新信息 | 同因复发/新问题判断 |

> 产品确认/开发修复超时（S1/S2 当日、S3/S4 按版本）→ 升级产品/开发负责人；测试不静默等待。

#### 7.3.6 读取降级

- `api` 优先；读不全 → `browser`；仍不全 → 请用户补关键备注/附件。
- `solutionChannel=manual` → 先请用户补关键备注/附件，禁只看标题分析。
- 读不到 `actions` 时，至少读详情字段 + 页面历史/备注区；不得把“读不到”当成“无变化”。
- `resolvedBuild` 缺失/不是当前测试构建 → 先问开发/确认含修复构建；不在未知构建上判通过。

### 7.4 产品判定回流

| 产品判定 | 平台动作 | 测试动作 |
| --- | --- | --- |
| 产品缺陷（确认） | 产品改资料/出新文档，指派开发 | 先读新产品文档/AC，按 `工作流.md` §2.6 建 CR/更新资料；等含修复构建后按 §7 回归 |
| 实现缺陷 | 产品说明依据，指派开发 | 等待修复；按 §7 正常回归；不要求产品改 PRD |
| 非问题/设计如此 | 产品说明依据，指派回测试 | 按 §8.8 记录；同意则关闭/纳入遗留，不同意转产品复核 |
| 重复 | 产品/开发关联主单，指派回测试 | 按 §8.6/§8.8 关闭并链接主单 |
| 信息不足 | 产品一次列清缺什么，指派回测试 | 补齐材料后回派产品；不默认关闭 |

- 产品新文档/AC 必须读全文；只读一句备注不算确认。  
- 产品确认“是产品缺陷”不等于“已修复”；测试仍按 §7 回归，不提前关闭。  
- 产品判定与测试判断不一致 → 列事实/证据请产品复核；仍不一致升级产品/测试负责人，留决策记录；不反复回派踢皮球。
