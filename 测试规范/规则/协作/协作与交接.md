# 协作与交接（测试轨）

> **读取级别：参考**（按节读取；按 `读取索引` 只读当前 step 节，禁止通读全本）。

> **目的**：把“产品/开发 → 测试、测试 → 开发/产品、变更 → 所有角色”的交接，从口头约定变成**可复制、可追踪**的交接包（回执可选）。
> **独立性**：本包可单独使用；接收方可以是产品/开发角色、用户本人或外部团队，**不要求对方安装同套包**。交接包自包含（00～04）；对方未装包时按普通文档阅读即可。回执默认可选，仅正式签收时再填模板。
> **单一出处**：交接包结构、回执、变更分级、重规划触发以本文为准；模板见 `规则/模板/90-交接与收尾/交接包说明模板.md`、`规则/模板/90-交接与收尾/交接清单模板.md`、`规则/模板/90-交接与收尾/接收回执模板.md`、`规则/模板/90-交接与收尾/交接台账模板.md`。
> **读取时机**：`handoff.*`、`testing.plan/execute/report`、`defect.*` 的交接/变更节；不需要每次开工通读。

## 1. 角色与决策权

| 角色 | 决策权 | 主要交接责任 |
| --- | --- | --- |
| 测试负责人（A/R） | 测试策略、范围、准出建议 | 测试计划/用例、缺陷、报告、发布后验证 |
| 开发负责人（C） | 实现、修复、构建 | 提测、修复/回归、影响面、构建/环境 |
| 产品负责人（C/A） | 业务范围、AC、优先级、发布 | PRD/AC/原型/变更/验收口径 |
| 用户/业务（A/C） | 目标、预算、风险接受 | 确认范围/准出/发布 |
| 运维/SRE（C/I） | 环境、部署、监控 | 环境/数据/发布/回滚 |

**原则**：一个交付物只有一个 A；R 做、C 咨询、I 知会。测试不替产品改业务口径、不替开发改代码；oracle 必须有来源。

## 2. 协作节奏（什么时候必须拉齐）

| 节点 | 触发 | 参与 | 必须产出 | 门 |
| --- | --- | --- | --- | --- |
| 测试依据澄清（Three Amigos） | 收到 PRD/原型/方案后、计划前 | 测试 + 产品 + 开发（可缺省） | 需求模型、冲突/九类歧义、oracle、TP 追溯、待决 | `confirm_understanding` |
| 测试计划评审 | 计划初稿完成 | 测试 + 产品 + 开发 | 范围/类型/轨道/编排/准入准出/缺陷策略 | 计划门 |
| 提测接收 | 开发提测 | 测试 + 开发 | 准入结论、环境/数据/构建确认、回执 | 门2 |
| 缺陷交接 | 执行失败/发现产品缺陷 | 测试 + 开发/产品 | **有平台→平台单为主**；**无平台/点名发包→BUG 包**（见 §3.1.1） | 门3/计划授权 |
| 测试报告/准出 | 执行完成/报告前 | 测试 + 产品 + 开发 | **自洽测试报告**（默认）；`TEST` 包按需 | 报告门 |
| 发布后验证 | 发布后 | 测试 + 产品/开发 | 验证结果、回滚建议、观察结论 | 无 |

> 产品/开发角色不存在时，由用户本人代收；交接包照常生成，接收回执由用户确认。**不因缺角色阻塞**。

## 3. 交接矩阵（测试轨）

### 3.0 总策略（内容优先 · 包按需 · 与产品/开发同口径）

| 层 | 默认交付（必产、自洽） | HO 交接包（按需） |
| --- | --- | --- |
| 计划 | `测试/测试计划.md` | `PLAN`：多文件附件/正式签收/仓外/点名 |
| 准出 | `测试/测试报告.md`（报告门过） | `TEST`：同上 |
| 缺陷 | **有平台→平台单**；无平台→自包含详单（可先问是否进 BUG 包） | `BUG`/`FIX`：无平台或点名/多文件证据/仓外 |
| 变更 | CR 正文 | `CHG`：C1+ 且需多角色冻结/签收/仓外/点名 |

**包触发（命中才停问建议；未命中不机械每问）**：① 多文件证据 ② 正式签收/回执 ③ 仓外 ZIP ④ 同发多主文档 ⑤ 用户点名。禁止静默发包；禁止「报告完成=必须发包」。

**交付形态**：默认**单文档（主文档 + 必要附件）**，不生成 HO 包；`CLAR/PLAN/DEC/BUG/FIX/TEST/REL/RETRO/CHG` 均按单文档起步；有平台 BUG/FIX 平台优先。只有命中上述触发才升级 `00-04` 标准包。单文档也要有标题、版本/日期、发起/接收、目的/范围、要对方做什么、截止、附件/证据。

**内容通用（硬规则 · 报告/详单与 HO 包同等适用）**

1. **不偏科**：报告同时给产品与开发时，准出/缺口/遗留用业务可懂表述；修复动作给开发、决策给产品可分行，共享事实不两套口径。  
2. **假定对方无工作流**：禁「见测试计划 §16 / 见台账列」代替结论摘要。  
3. **假定对方无平台/无同仓**：缺陷结论写清现象/影响，不单贴单号。  
4. **一份可读**：普通同事只拿报告或详单，也应能决策或认领。

### 3.1 测试发出（适用交接包 · **先问后发**）

> **发包总闸**：凡拟生成任一 `测试/交接/{HO-ID}/`，**先 STOP 出示拟发摘要**；用户确认「要/生成」后才落盘。口令≠已确认内容。业务门过 ≠ 发包已授权。

| 时机 | 类型 | 接收方 | 最小必带（包内） | 前置 |
| --- | --- | --- | --- | --- |
| 依据澄清 | `CLAR` | 产品/开发 | 问题+原文引用+影响+建议+拍板项（正文自洽） | 按需触发 + 用户确认 |
| 计划通报 | `PLAN` | 产品、开发 | 计划关键节快照（范围/准出/缺陷策略等） | 计划门后按需 + 确认 |
| 阶段状态 | `DEC` | 产品、开发 | 阶段/范围/阻塞/预计 | 按需 + 确认 |
| 缺陷（无平台/点名） | `BUG` | 开发/产品 | 十段详单+证据；不依赖平台号 | §3.1.1 + 确认 |
| 回归 | `FIX` | 开发 | 原单/构建/范围/结果/证据 | 有平台写回≠自动发包；按需+确认 |
| 报告/准出 | `TEST` | 产品、开发 | 报告快照+准出摘要 | 报告门过；**默认只交报告**；包按需+确认 |
| 发布后验证 | `REL` | 产品/开发/运维 | 验证结果+证据+回滚建议 | 按需+确认 |
| 复盘 | `RETRO` | 产品、开发 | 复盘+行动项 | 按需+确认 |
| 变更 | `CHG` | 产品/开发 | CR+影响矩阵+截止 | C1+ 按需+确认 |

### 3.1.1 缺陷双通道（互斥 · 禁绑死「先平台后包」）

> **问题背景**：旧规把「交平台」与「发 BUG 交接包」串成先后链——包内写平台单号、又要求提交后才生成 → 有平台则与平台重复且更浅；无平台则永远发不出可用包。以下为现行口径。

| 协作方式 | 主通道 | BUG 交接包 `HO-*-BUG-*` | 台账 |
| --- | --- | --- | --- |
| **有缺陷平台**且本轮走平台提交（api/browser） | **平台单**（十段齐 + 附件 + 指派） | **禁止**再强制生成整包；不得为「走完交接流程」而复制平台正文 | `交接台账` 可记一行「平台已交 #{id} / 本地键 / 模块 / 日期」（可选，非 HO 整包） |
| **无平台** / `export` / 用户点名「缺陷交接包」「发给开发」 | **BUG 交接包** | **适用**；先问后发（§3.1 总闸）；确认后生成，**可先于任何平台建单** | 状态=`已发送`；包内用本地键 `BUG-…` |
| 先包后补平台 | 先 BUG 包，后用户/测试补平台号 | 包已发出后，平台号只回写台账/主台账，**不重发整包**（除非 C2/C3 级内容变更） | 回写平台号到台账备注 |

**硬规则**

1. **互斥**：同一批缺陷不得「平台已交齐」又强制再发一份内容重复的 BUG 整包。
2. **时序**：BUG 包**不得**以「已有平台单号」为生成前置；平台单号不是 BUG 包必填字段。
3. **自包含**：BUG 包读者假定**没有**禅道/Jira 等；正文用业务语言写清复现/预期/实际/证据；禁把「#1644」「fileId=1951」当唯一索引而无详单。
4. **同源**：包内缺陷正文 = 台账问题详情 / 拟交开发文案的**终态十段**（与平台 `steps` 同源模板）；**禁**塞「拟提交」未确认稿；**禁**只拷一份仍写「拟提交」的执行台账充数。
5. **详细度**：无平台时，BUG 包详细度 ≥ 原平台 steps 标准（见 `缺陷协作.md` §5）；有平台时以平台为准，包不重复描述。
6. **口令**：用户说「提交到平台/提交禅道」→ 只走平台 + writeback，**默认不发包**；说「缺陷交接包/发给开发/无平台交接」→ 拟发 BUG 包，**仍先展示摘要等确认**再落盘。
7. **禁自动**：报告完成、计划门通过、批末交平台、回归写回等节点，最多 **建议**「是否发某某交接包」，不得直接生成。

### 3.2 测试接收（读包核对；回执默认可选）

| 时机 | 类型 | 来源 | 测试动作 |
| --- | --- | --- | --- |
| PRD/需求交接 | `REQ` | 产品 | 建需求模型/分析短表；冲突/GAP 发 `CLAR`；回执 |
| 设计交接 | `DES` | 产品/开发 | 核对原型/交互/接口/可测性；补 oracle；回执 |
| 计划/排期 | `PLAN` | 产品/开发 | 核对测试窗口/范围/依赖；更新测试计划；回执 |
| 提测 | `QA` | 开发 | 准入检查（构建/环境/数据/自测证据/已知问题）；接受/有条件/退回；回执 |
| 变更通知 | `CHG` | 产品/开发 | 影响分析/更新计划/用例/脚本；计划门（C2/C3）；回执 |
| 缺陷修复/回归 | `FIX` | 开发 | 回归原单+冒烟+影响面；回执；未通过重开 |
| 澄清/补充 | `CLAR` | 产品/开发 | 补预期/范围/数据；回执 |
| UAT 结论 | `UAT` | 产品 | 更新准出/遗留/发布建议；回执 |
| 发布结果 | `REL` | 开发/运维 | 发布后验证；回执 |

### 3.2.1 提测接收 → 装填（测试侧映射）

- **消费字段**：提测单 §2.6（或等价）**影响面追溯 / 回归范围** → 测试侧写入计划 §3.7 命中域 + `suite`（通常 module；发版可 full）。
- **术语隔离**：不要求开发填写 L0/L1/L2、suite、装填等内部词；业务表述（改了哪些模块/接口/是否需回归）即可。
- **可选加速**：对方在 `activeContext` 同步一行影响面可加速映射，**非必填**；无则测试自填命中域，不阻塞接收。

## 4. 交接包规范

### 4.1 目录与命名

```text
测试/交接/
├─ 交接台账.md                         # 唯一登记（状态/回执/影响）
└─ {HO-ID}/
   ├─ 00-交接说明.md                   # 封面、目的、接收方动作、验收、回执要求
   ├─ 01-交接清单.md                   # 文件清单：版本/来源/包内路径/必读/用途
   ├─ 02-文档/                         # 必带文档快照（按原文件名）
   ├─ 03-证据/                         # 必要证据副本（截图/日志/报告；脱敏）
   └─ 04-回执/
      └─ 接收回执.md                   # 空白模板必带，首行标「空白模板（未签收）」；默认不强制填写，正式签收时再填回传
```

- **确认后才生成**：用户确认发包后写完整包（`00/01/02/03/04`）。**例外**：§3.1.1 有平台已交 → 不强制 `BUG` 整包；未命中 §3.0 触发 → 默认不发包。
- **自包含详实**：读包即懂；`02` 带主文档快照（报告/详单等）；禁只写平台号/「见主副本」。参考 Agent Handoff：Must Satisfy、Scope、Evidence。
- **ID（通用）**：`HO-{yyyyMMdd}-{NN}-{类型}-{发起}2{接收标签}`。单收：`…-TEST-QA2PM`；**多收**：`…-TEST-QA2ALL` 或短拼 `…-QA2PMDEV`。ID 只检索；**禁止**因后缀写成 `2PM` 就把正文做成只给产品。接收人以 `00` 为准。
- **一包多收**：报告可同时给产品+开发；`00` 列全员 + 按角色分行动作；`02` 全体可读。无工作流同事直接发文件夹/ZIP。
- **快照**：`02` 副本；主副本在 `测试/`。
- **BUG 包**：`02` 必含十段详单；禁「拟提交」充数。
- **大文件 / 多包联动**：文本复制；超大可同仓联动；禁拷对方 `资料/交接/`。
- **安全**：密钥/真实 PII 不入包；内部测试演示账号可明文，须标注「仅测试」。
- **00-04 是通用骨架，不新增 05**：校验值写 `01-交接清单`；大包在 `02-文档/`、`03-证据/` 下按类型子目录（需求/设计/接口/数据；截图/日志/样张/报告），小包可平铺；`01` 写清路径即可。

### 4.2 生成步骤（`handoff.send`）

0. **先问（不可跳过）**：按 §3.1 总闸出示【拟发包】类型/接收方/必带/阻断/传递方式 → 等用户确认；未确认 **零写盘**。
1. **冻结来源**：相关业务门已过（计划门/门2/门3/报告门等，按类型）；记录版本/构建/runStamp。
2. **选类型与接收方**：按 §3 选最小必带；缺必带 → 不发送，列缺口与责任人。
3. **复制**：必带文档进 `02-文档/`；证据进 `03-证据/`；保留原文件名，不编辑内容。
4. **写说明与清单**：按模板写 `00-交接说明.md`、`01-交接清单.md`；清单逐项写源路径、版本、包内路径、必读、用途；`04-回执/` 放入空白回执模板（必带文件，默认不要求对方立即填写）。
5. **自检**：运行 `python 测试规范/规则/tools/validate_handoff.py <包路径>`（可用时）；缺件/占位符/版本不符先修。
6. **登记**：更新 `交接台账.md`（状态=`已发送`）、测试计划 §0/§16.1、文档索引、`activeContext.md`。包已生成且状态=`已发送` → 本侧可继续准备，**不得**以「须等回执」阻塞日常工作。
7. **传递模式**（二选一，写进【交接包已生成】）：
   - **多包同仓**（项目根另有对等工作目录 `产品/` 或 `开发/`）：对方**直接读** `测试/交接/{HO-ID}/`；输出「同仓直读：测试/交接/{HO-ID}/」。**禁止**让用户再复制/转发到对方 `资料/交接/`。
   - **单包 / 仓外同事**：用户发送整个 `{HO-ID}` 文件夹；可选在包旁打 ZIP `{HO-ID}.zip`。不假设对方有工作流目录。
8. **告诉用户**：输出【交接包已生成】；**不得写“已接收”**，只写“已生成/已发送”。

```text
【交接包已生成】
- 交接：{HO-ID}｜{类型}｜{发起方} → {接收方}
- 路径：测试/交接/{HO-ID}/
- 传递：多包同仓 → 对方直接读上述路径（禁止再转发/拷到对方资料/交接）；仓外/单包 → 发文件夹或可选 ZIP（{HO-ID}.zip）
- 必带：{…}
- 阻断/待决：{…}
- 回执：默认可选（模板在 04-回执/，首行标「空白模板（未签收）」）；**无平台仅靠 BO 包交付、阻断下游、正式签收、发布/C2/C3 时必须回执**
- 状态：已发送（≠已接收）
```

### 4.3 接收与回执（`handoff.receive`）

1. **定位包**：
   - **多包同仓**：直接打开发送方路径（如 `产品/交接/{HO-ID}/` 或 `开发/交接/{HO-ID}/`），**不要求**拷入本侧 `测试/资料/交接/`。
   - **仓外/单包**：在用户放置处打开文件夹或解压 ZIP；台账可登记实际路径；仅在归档有用时可选复制到 `测试/资料/交接/{HO-ID}/`。
2. 先读 `00`，再按 `01` 核对五件事：清单文件是否齐、版本/构建是否对、是否有阻断缺口、是否有互相矛盾、是否有需测试拍板项。
3. 结论三选一：**接受** / **有条件接受**（列非阻断缺口/假设/责任人/截止） / **退回**（列阻断缺口与需要补什么）。
4. **回执**：默认可选；但**无平台仅靠 BO 包交付、阻断下游、正式签收、发布/重大变更 C2/C3** → 必须填写 `04-回执/接收回执.md` 并回传，台账改为 `已接收`/`有条件接收`/`退回`。无回执时只可声称「已发送」，**不得**声称「已接收」；日常工作不因缺回执阻塞，除非属于上述必须场景或用户点名正式签收。
5. 更新测试计划 §0/§1.1/§9/§14/§16、需求模型/分析短表、文档索引、`activeContext.md`。
6. 若包内是变更通知 → 走 §6；若含实质变更 → 先计划门，不得边执行边改口径。
7. 发送方收到正式回执后更新台账：`已接收`/`有条件接收`/`退回`；退回补件后发新版本，旧包标 `已取代`。**正式签收时不得替对方签收**。

**时限（默认，仅正式签收场景）**：普通交接 1 个工作日；阻断/提测/发布 4 小时。超时由发送方在台账标 `待回执` 并升级给用户。

## 5. 交接完成判定

| 状态 | 含义 | 能否进入下游 |
| --- | --- | --- |
| `草稿` | 包未生成完/未自检 | 否 |
| `已发送` | 已生成并交给对方（回执未填或未收回） | 本侧可继续准备；不得称「已接收」 |
| `已接收` | 正式回执=接受，清单齐 | 是（正式签收完成） |
| `有条件接收` | 正式回执=有条件，非阻断缺口有主/截止 | 是，条件进计划风险 |
| `退回` | 正式回执=退回，阻断缺口未解 | 否；补件后发新版本 |
| `已取代` | 有新版本包 | 否；以新版本为准 |
| `已关闭` | 下游工作完成/验收关闭 | 是（作为历史） |

**硬规则**：日常外发以包生成/`已发送`为准，可继续本侧准备，**不得**用「须等回执」阻塞日常。**正式签收**（用户点名要回执，或发布/重大变更 C2/C3）才要求回执后标 `已接收/有条件接收`；不得用「已接收」冒充未签收。提测包日常以核对清单/准入结论为准开跑；用户点名正式签收时再填回执。

## 6. 变更与计划自适应

### 6.1 变更分级

| 级别 | 判定 | 例子 | 审批 | 计划动作 | 交接 |
| --- | --- | --- | --- | --- | --- |
| `C0` 澄清/纠错 | 不改变范围/AC/准出/资源 | 文案、口径、笔误 | 测试负责人（书面） | 就地更新，不重基线 | `DEC`，受影响才发 |
| `C1` 同范围增量 | 在已批准范围内增/改 AC、用例、回归 | 补边界、补样本、补回归 | 测试负责人 | 更新计划 §0/§2/§3/§15、用例/脚本 | `CHG` + 回执 |
| `C2` 范围/准出/排期变化 | 范围、准出、轮次、窗口、缺陷策略变化 | 加范围、改准出、延期 | 计划门 | 重新基线；更新计划/用例/报告 | `CHG` + 回执 + 计划门 |
| `C3` 高风险/合规/破坏性 | 权限、资金、数据、迁移、安全 | 迁移、合规、破坏性接口 | 计划门 + 专项评审 | 重跑专项/全量/回归；更新准出 | `CHG` + `RISK` + 回执 |

> 不允许把 C2/C3 拆成多个 C0/C1 绕过计划门；A/B 期中变更按 `规则/工作流.md` §2.6 就地更新，C 回计划门。

### 6.2 重规划触发

| 触发 | 默认阈值 | 动作 | 负责人 |
| --- | --- | --- | --- |
| 需求/AC/范围变化 | 出现即触发 | 按 C1/C2/C3 更新计划/用例 | 测试 + 产品 |
| 提测包退回/构建不可用 | 出现即触发 | 暂停准入/退回开发/换构建 | 测试 + 开发 |
| P0 冒烟失败/环境不可用 | 全绿前 | 停轮/环境排查/升级 | 测试 |
| S1/S2 缺陷或准出失败 | 出现即触发 | 停轮/回归/重评准出 | 测试 + 产品 |
| 数据/账号不可用 | > 4 小时 | 造数/换样/暂停 | 测试 + 开发 |
| 产能变化 | > 20% | 降范围/拆轮次/延期 | 测试 + 产品 |
| 发布窗口变化 | 影响准出 | 重排回归/报告/发布验证 | 测试 + 产品 |

**重规划动作**（选一个并写理由）：保持计划+加缓冲｜重排轮次｜降范围/抽样｜拆轮次｜暂停升级｜重新基线。重规划必须在触发后 1 个工作日内完成，并同步计划/台账/索引。

### 6.3 文档同步矩阵（测试侧）

| 变更 | 必更新 | 通知 |
| --- | --- | --- |
| C0 | 需求模型/分析短表、计划 §2/§14.3、文档索引 | 受影响产品/开发（`DEC`） |
| C1 | 计划 §0/§2/§3.1/§3.2/§3.7/§15、用例/脚本、台账 | `CHG` → 产品/开发 |
| C2 | 上述 + 计划 §5/§9.2/§10/§11、报告 §2/§7 | `CHG` + 计划门 + 回执 |
| C3 | 上述 + 专项方案/报告、准出评估、发布前检查 | `CHG` + `RISK` + 回执 + 重过报告门 |

## 7. 计划回写与状态

- **计划是状态唯一入口**：`测试/测试计划.md` §0 写当前阶段/门/下一动作/待回执/健康度；§16.1 写执行日志；交接摘要进计划，详细在台账。
- **每次发送/接收/回执/变更**：更新 `交接台账.md` → 测试计划 §0/§16.1 → 文档索引 → `activeContext.md`。四者同轮，不得只改一处。
- **计划状态**：`草稿` → `已确认` → `执行中` → `变更中` → `待关闭` → `已关闭`。
- **健康度**：绿=无阻断、回执齐；黄=有非阻断缺口/待回执/数据环境风险但可恢复；红=阻断缺口/关键门未过/准出风险。红色必须在 §0 写升级对象与下一步。
- **禁止**：用“已发送”冒充“已接收”；用“计划写了”冒充“已执行”；正式签收场景用聊天结论替代回执/变更单。

## 8. 禁止事项

1. 未过计划门就改范围/准出；清单/准入未核对就开跑。
2. 交接包无清单、无版本；或包内缺 `04-回执/` 空白模板文件（模板必带，不要求默认已填写）。
3. 正式签收场景下发送方替对方签收；用「已接收」冒充未签收。日常外发不以「未写回执」当作阻断。
4. 口头变更、先测后补单、边测边改 oracle。
5. 把密钥/凭据/真实 PII 放进交接包。
6. 用旧版本包继续执行；有新版本仍引用旧包。
7. 交接包内容与主副本不一致；包内文档被接收方修改后当主副本。
8. 变更后不更新计划/台账/索引，导致下一角色按旧口径执行。
9. 多包同仓仍要求用户把包拷/转到对方 `资料/交接/`（应同仓直读）。

## 9. 参考实践（方法参考，非逐字复制）

- Three Amigos / Example Mapping / ATDD：需求、开发、测试在编码前用示例对齐 AC 与 oracle（<https://www.agilealliance.org/glossary/three-amigos/>）。
- Risk-based testing（ISTQB）：按风险选择测试类型/深度/轮次（<https://www.istqb.org/>）。
- ISO/IEC/IEEE 29148：需求规格质量与可测试性（<https://www.iso.org/standard/72089.html>）。
- GitHub Spec Kit：规格 → 计划 → 任务 → 实现，测试依据可追溯（<https://github.com/github/spec-kit>）。
- ADR（Nygard）：架构决策记录，测试可追溯（<https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions>）。
- Team Topologies：团队交互模式与交接边界（<https://teamtopologies.com/>）。
- DORA / Google SRE：变更失败率、MTTR、发布后验证（<https://dora.dev/>、<https://sre.google/>）。
- Scrum/Kanban：Definition of Ready / Definition of Done、WIP 限制与流动效率（<https://scrumguides.org/>）。
