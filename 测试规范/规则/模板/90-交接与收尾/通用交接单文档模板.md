# 跨角色交接 · 单文档写法（择优，非填空卷）

> **用途**：对方结果**无对等专模质量义务**时的跨角色单文档（知会/确认/拍板等）。未命中包触发时禁止升 HO。  
> **本文件不是**必须整份套用的正文骨架；是**择优规则 + 合格线 + 字段菜单**。套全表、把流程元数据印给对方 = 不合格。  
> **专模按目的选用**：交付目的对等既有专模质量义务（范围契约/验收证据/准出结论/变更冻结等）→ 用该专模，字段标准照旧；**不要**用本文件「择优」稀释。无对等专模 → 本文件五问合格线即可；**禁止**因「表上没有场景名」拒写。示例非穷尽。  
> **落盘前**：意图有歧义 → `confirm_intent`；意图已清 → 一行回执即可写（澄清 §0）。禁止含糊口令直接成文。  
> **规范**：`规则/协作/协作与交接.md` §3.0～§3.0.1。

---

## 0. 硬原则

1. **先分析，后落笔**：按接收方、对方动作、情况厚度择形态；禁止「有交接就套统一大表」。  
2. **对方第一**：正文首先回答「情况是什么」和「你要做什么」；工程自检项留给作者，不写进外发文。  
3. **少而准**：确认点尽量少（常见 3～7 条）；只写会改变对方决策的风险/限制。  
4. **回执默认否**：不预置「必须签回执」；要表态用短结论栏即可。  
5. **外发禁内部路径代结论**：禁止「见 `开发|产品|测试/…` / 见计划 §」代替介绍与结论。  
6. **禁止印出的元数据**（可留在作者笔记，勿进对方正文）：意图编码、是否需要回执、HO-ID、包触发说明、合格线自检句、compose/send 字样。

## 1. 落笔前五问（必做 · 只作思考，默认不写入正文）

| # | 问 | 若答不清 |
| ---: | --- | --- |
| 1 | 接收方是谁？用什么语言能懂？（产品/测试/运维/老板） | 先定受众再写 |
| 2 | 对方**必须**做什么？知悉 / 确认几条 / 在选项里拍板？ | 无动作 → 短知会；有动作 → 动作置顶或紧跟介绍 |
| 3 | 对方要无聊天上下文也能懂，最少要哪些事实？ | 缺则补「情况介绍」，勿用表格冒充介绍 |
| 4 | 哪些限制/风险**真的改变**对方是否同意？ | 只留这些；其余运维细节省略或一句带过 |
| 5 | 对方结果是否对等既有专模质量义务？用户是否只要「确认/介绍」？ | 对等 → 专模；否则本文件；确认类优先「一页纸」 |

---

## 2. 形态择优（选一种为主结构，可微调）

| 形态 | 何时选用 | 建议结构（可裁剪） | 典型篇幅 |
| --- | --- | --- | --- |
| **A 知会短讯** | 不要求对方拍板 | 情况几句 → 要点列表 → 「无需你操作」 | 半页内 |
| **B 确认一页纸** | 口径已收敛，要对方同意几条 | **情况介绍** → **已定口径** → **请你确认**（少条）→ **确认后我们做什么** | 一页左右 |
| **C 决策简报** | 仍有选项要拍板 | 背景 → 选项与推荐 → 影响 → 请拍板 | 一～二页 |
| **D 专模** | 目的对等专模质量义务 | 用对应专模（不按文件名白名单） | 按专模 |
| **E HO 包** | 仅命中包触发且用户确认要包 | `00～04` | 按包规 |

**择优冲突时**：接收方是业务/产品且任务是「确认环境/演示/范围」→ 优先 **B**，不要用带满风险矩阵的考卷体。  
**禁止**：把下表「字段菜单」整表粘成正文；禁止为凑「意图扩展块」硬开 NOTE+ENV+ACCEPT 三节。

---

## 3. 结果合格线（看效果，不看是否出现某节标题）

对方只拿本文、无聊天记录时，须同时成立：

| # | 要求 |
| ---: | --- |
| 1 | 知道**背景/现状**（够做判断的介绍，不是元数据表） |
| 2 | 清楚**自己要做什么**（可执行；无动作则写明「仅知悉」） |
| 3 | 掌握关键事实（版本/入口/数据/账号约定等——**按场景需要出现**） |
| 4 | 知道**不做什么 / 非目标**（按需；避免范围误解） |
| 5 | 无密钥明文、无真实 PII；无内部路径代替结论 |
| 6 | 未强迫回执；若需表态，结论方式简单（同意/有条件/不同意） |

缺 1 或 2 = 不合格（即便表格很全）。

---

## 4. 反模式（出现即应改写）

- 整份粘贴「摘要表 + §1～§8 + 多扩展块」却几乎无连贯介绍。  
- 「请你确认」超过约 8 条，或把运维内存/接线细节做成必勾考题。  
- 正文出现：意图类型码、是否需要回执、回传方式枚举、HO-ID、包触发说明。  
- 只有「见某内部方案」而无自洽介绍。  
- 知会类文档仍要求对方填长结论栏。

---

## 5. 字段菜单（按需取用 · 用不上不写）

写正文时从菜单**挑选**，需要才出现；名称可改成对方好懂的小标题。

| 菜单项 | 常见用于 | 写法提示 |
| --- | --- | --- |
| 情况介绍 | 几乎总要 | 连贯段落：现在怎样、为何现在、和测试/正式什么关系 |
| 对方要做什么 | 有动作时必有 | 置顶或紧接介绍；1～3 句或短表 |
| 已定口径 / 关键事实 | 确认、环境、演示 | 入口、版本、数据、账号约定（口令当面/弱口令策略，慎明文） |
| 请你确认 | 形态 B/C | 少而业务化；每条可「同意/改」 |
| 确认后下一步 | 形态 B/C | 开发/测试侧会做什么，减轻对方焦虑 |
| 非目标 | 易误解时 | 不写一长串工程不做项 |
| 须拍板的风险 | 仅改变「批不批」时 | 一条或少数几条，勿工程风险清单化 |
| 选项与推荐 | 形态 C | 推荐写清理由 |
| 附件/样张 | 确有文件外发时 | 业务可读文件名 |

**意图标签**（NOTE/ENV/DEMO/OPS/ACCEPT/CLAR…）仅用于作者路由与台账备注，**默认不印在对方正文标题下当栏目**。

## 6. 与 HO / 专模关系

- 默认：本择优规则 → 落一篇给人看的 md/消息。  
- 有专模 → 专模。  
- 升包 → 把**已写好的自洽正文**快照进 `02`，不要先做空 `00` 再硬凑。

## 7. 作者自检（发出前 · 不对对方展示）

- [ ] 五问已想过；形态选了 A/B/C/D 之一（或等价）  
- [ ] 介绍够不够懂；动作清不清；确认点是否过碎  
- [ ] 正文无流程元数据、无内部路径代结论、无密钥  
- [ ] 未无触发却想建 HO
