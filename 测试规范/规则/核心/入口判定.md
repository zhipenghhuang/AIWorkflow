# 入口判定（无显式口令时）

> **定位**：任意自然语言 → 选**最小可用** workflow/step。不依赖固定口令措辞；靠「信号抽取 + 意图类 + 计划状态」判定。
> **读取时机**：`AGENTS.md` §2 未命中、口令模糊、或用户用描述句提出任务时。
> **与口令表**：明确短命令仍优先；本文只补模糊入口，**不另造 workflow/门**。
> **技能**：路由后只读当前步技能/轨契约；口语不能跳过必用技能。
> **边界**：本包不改业务代码；缺陷记录走台账/`defect`；修代码属开发包。
> **单一出处**：自然语言路由；其它文件只引用。

## 0. 原则

1. **看意图与对象，不抠关键词**。同义说法等价；禁止「必须含某词才路由」。
2. **依据先于资产**：有 PRD/方案/原型要测时，未建模不得直接写用例或宣称执行完成。
3. **有测试计划先续跑**：像继续/跑/测到哪了且计划 §0 可路由 → 按阶段，不另起无关链。
4. **能脚本不 AI、能轻量不完整**：体量用 T0～T3；补丁口语不要默认版本级全量。
5. **首条可纠正**：`reason=` 写清依据。

## 1. 每条消息先抽五元组（必做）

| 轴 | 问什么 | 取值示例（非穷尽） |
| --- | --- | --- |
| **动作** | 建模、编计划、产资产、评审、执行、准出、缺陷协作、还是治理？ | analyze / plan / generate / review / execute / report / defect / govern |
| **对象** | 在处理什么？ | 需求依据(PRD·方案·原型·接口) / 测试计划 / 用例·脚本·轨资产 / 执行结果·台账 / 准出·报告 / 缺陷·平台单 / 交接包 / 环境·资料 |
| **结果** | 结束时要什么？ | 测试分析表（需求模型）/ 计划确认 / 用例·脚本 / 评审放行 / 执行结论·证据 / 准出评估 / 平台提交·回归 / 交接 |
| **连续** | 新开、续跑、回归重测、纠正？ | new / resume / regress / correct |
| **体量** | 补丁/模块/版本/高风险？哪条轨？ | T0～T3；轨=功能/接口/探索/随机/发布前；未知偏高一档 |

**快速启发（可叠加）**：

- 附件=需求类文档 + 要测/计划/用例 → 先看是否已有测试分析表；无则动作=analyze。
- 已有 `测试/测试计划.md` + resume/execute 语义 → 优先按 §0，不拆炉灶。
- 失败证据要入库平台/查重 → defect。
- 「再跑一遍/回归」→ continuous=regress（结果就地覆盖），平台单回归除外走 defect。
- 性能/安全/兼容/探索/接口等字样 → 定轨，仍落在 testing 对应 step。

## 2. 意图类 → workflow（本包）

| 意图类 | 判定要点（通用） | 默认入口 |
| --- | --- | --- |
| A 依据建模 | 要弄清测什么、oracle、歧义、追溯；或有依据文档尚未建模 | `testing.analyze` |
| B 计划编排 | 要版本/轻量测试计划、范围、准出、轨道、期中变更 | `testing.plan`（无 A 产物则先 A） |
| C 资产生成 | 要用例/脚本/专项资产 | `testing.generate`（无 A/B 则先补；小任务可同轮轻量） |
| D 资产评审 | 要计划/分析/用例/接口等评审放行 | `testing.review-cases` 或 plan 内评审 |
| E 执行验证 | 要跑测/冒烟/专题/按计划执行 | `testing.execute`（有计划按阶段；无计划 T0/T1 可 A→轻量 B 后执行） |
| F 回归重测 | 对已有用例再测 | `testing.execute`（regress）；平台指派回归 → `defect` |
| G 准出报告 | 要对台账出报告/准出/能否发 | `testing.report` |
| H 缺陷协作 | 查重、交平台、补充澄清、缺陷巡检 | `defect` |
| I 状态只读 | 测到哪了、下一步、计划状态 | `testing.status` |
| J 协作交接 | 发包/收包/变更通知/重规划 | `handoff` |
| K 仓库治理 | 接入、基线、资料、清理、技能体检 | `onboard` / `skill-audit` |

**动作×对象速查**：

| 动作 ↓ \ 对象 → | 需求依据 | 计划 | 用例资产 | 台账/结果 | 缺陷 |
| --- | --- | --- | --- | --- | --- |
| analyze / understand | A | I 或 B | — | — | H |
| plan / produce 计划 | A→B | B | — | — | — |
| generate | A→B→C | C | C | — | — |
| review | D | D | D | — | — |
| execute / verify | A 前置后 E | E | E/F | E/F | H 或 F |
| report | — | G | — | G | — |
| govern | K | K | K | K | K |

前置硬规则：**generate / plan 前**若对象含需求依据（PRD/原型/方案等）且无测试分析表 → 必须先 A。**execute**：计划 §0 已确认 → 可继续；表缺失仅告警并建议补建，勿强制赶回 analyze（与口令前置一致）。

## 3. 计划与级别修正

1. 有测试计划且 §0 可路由 + resume/execute → **优先计划驱动**。
2. 无计划：T0/T1 允许同轮轻量 A+B；T2/T3/发布列车必须先 B（可同会话）。
3. 轨选择：用户点名或对象暗示 → 对应轨契约；未点名默认功能轨。
4. 随机业务流程 = 计划外独立轨，不进计划准出替代。
5. 无基线/未接入 → §5 摸底；只读向 A/B 草稿可不阻塞。

## 4. 置信度与一问

| 情况 | 做法 |
| --- | --- |
| 唯一意图类 | 直接路由 + `reason=` |
| 只差轻量/完整计划 | 选轻量；可改道 |
| 影响准出范围/是否交平台/是否全量 | 一问 + 推荐 |
| 像修代码而非测试 | 说明边界，推荐开发包或只记缺陷 |
| 缺环境/账号且要 E | 门2；关键事实一问 |
| 连续 3 轮无新信息 | 按推荐或缩到 P0 冒烟 |

## 5. 中途摸底

1. 读 README、`测试/`、预览地址、是否有计划/台账。
2. 能推断被测入口 → 可 A/轻量 B；缺授权环境不执行。
3. 建议事后接入；不阻塞只出分析/计划草稿。

## 6. 首条格式

```text
route=workflow:<id> | step=<id> | role=<agent> | mode=… | reason=<意图类+信号> | next_action=…
```

- 可附 `intent=<A-K>`、`level=T0-T3`、`track=`、`input=`。
- 偶然出现「计划/报告/缺陷」≠ 口令命中。
- 不跳过分析前置、覆盖三闸、P0 准出、证据；交平台仍门3。

## 7. 反模式

- 当口令同义词表做字符串匹配。
- 未建模就写用例或改预期迁就现网。
- 有计划却无视 §0 另起执行。
- 无计划宣称准出或「按计划执行」。
- 把修代码当本包职责。
- 加隐藏门或跳过评审放行/报告门/技能；`reason` 缺失。
