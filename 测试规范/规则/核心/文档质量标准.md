# 文档质量标准（测试轨）

> **定位**：测试轨所有文档的**通用合格线**。模板只提供结构；本文件判断“这份文档能不能用、能不能准出”。
> **适用**：环境基线、测试计划、测试用例、执行台账、测试报告、缺陷详单/文案、评审记录、冒烟清单、交接包、复盘、工作日志。
> **原则**：按文档位置定内容；测试计划不写成测试报告，测试报告不复述计划，缺陷单不写开发方案。

## 0. 冲突优先级

安全/合规/硬红线 > 用户明确指令 > 项目根 AGENTS > 包 AGENTS > 本文件 > 模板结构 > 历史文档。

模板与本文件冲突：**先修母版模板并升版本 → 自检 → 整包分发**；不按旧模板产出，也不在实例里各自改。

## 0.1 母版 / 实例 / 模板的使用方式

- **母版只维护通用高标准**：不写具体项目环境、端口、账号、组织、版本等实例事实。
- **实例默认不改，但可本地适配**：项目里的 `开发规范/产品规范/测试规范` 默认按母版使用；AI 发现模板/规则/技能不匹配或有更好做法，先输出「拟改内容/原因/影响」，用户确认后只改当前实例，不影响母版。
- **本地适配要留痕**：确认后在项目档案或本地适配记录登记（文件/原因/日期/确认人）；母版整包更新前先备份/比对，避免覆盖；本地适配不自动回灌母版。
- **模板是骨架、标准是底线**：按当前项目实际和文档位置裁剪/补充，不要求逐条机械填写；不适用项写「不适用 + 理由」，不为凑模板写空话。
- **不匹配时先改产出**：模板/标准与项目实际不匹配，优先修改当前项目生成的文档（测试计划/报告/缺陷单等），使其贴合实际并可验收。
- **适配建议回母版需确认**：AI 可向用户说明差异/影响/建议；只有用户确认且属于通用改进时，才回母版修改并升版本；项目特化不回灌母版。

## 1. 通用硬门槛（任一不满足 = 不合格）

1. **目的与读者明确**：开头能看出“给谁、解决什么、用来做什么决定”。
2. **事实有来源**：环境 URL/端口/IP、构建/提交、账号、日期、执行结果、通过/失败数、缺陷号、准出结论必须来自配置/台账/证据/用户确认；未验证写「未验证/待确认」，禁止猜测或把假设写成事实。
3. **范围有边界**：in/out、覆盖/未覆盖、依赖/排除分开；out 标来源/理由/确认人。
4. **可执行/可判定**：步骤、数据、预期、判定标准可被他人复现；禁“测试完成/基本正常”等空话。
5. **证据可核对**：命令/截图/日志/报告/执行台账可打开；结论必须能回到证据。
6. **一致与追溯**：需求/AC/用例/执行/缺陷/报告数字同口径；不出现两套统计。
7. **状态与变更**：版本/构建/日期/负责人/状态/变更记录齐；旧版归档。
8. **安全与合规**：无密钥/凭据/真实 PII；测试数据脱敏；环境/权限边界写清。
9. **当前有效状态（硬）**：正式文档以当前最终状态为唯一事实来源。
   1. 只描述当前存在的功能、流程、规则和约束。
   2. 删除后直接移除相关表述；不追加「已删除 / 已废弃 / 不要再用xxx / 禁止xxx（因旧物）」等说明。现行仍生效的约束可写（如安全红线），那是现行规则，不是删后留痕。
   3. 不记录历史修改过程、原因、旧方案和已取消内容。
   4. 不为防误解而引入当前不存在的概念或对照物。
   5. 改完以最终状态落笔，保持简洁准确。
   6. 对用户的文档/结论输出写现行结论，不复述用户需求原文，不写「本次改了什么」。
   7. 禁止在正式正文记录变更原因与废弃史；留痕仅限变更/CR / 工作日志 / 复盘 等允许载体，且不回流正式正文。
   8. 不把未采纳的修改方案、对比草案写入正式文档。
10. **语言克制**：禁辩解式/对比式/冗余括注、未经确认的“应该/可能”。
11. **准出匹配证据**：PASS/CONDITIONAL/FAIL/BLOCKED 有判定依据；不替产品/开发做业务决策。

## 2. 测试文档类型矩阵

| 文档 | 位置/作用 | 必须具备 | 不应包含 | 合格判据 |
| --- | --- | --- | --- | --- |
| 环境基线 | 测试前置事实 | 环境/入口/账号/数据/版本/依赖/访问方式 | 测试结论 | 可复现、可核对 |
| 测试计划 | 版本级测试控制面 | 范围/策略/类型/入口/出口/排期/角色/风险/数据 | 测试结果、缺陷结论 | 测试可按计划执行 |
| 测试用例 | 执行最小单元 | 前置/步骤/预期/优先级/追溯 ID/数据 | 大段方案 | 他人可复现、可判定 |
| 执行台账 | 实际执行事实 | 构建/环境/时间/轮次/结果/证据/缺陷 | 预填“通过” | 实际与证据一致 |
| 测试报告 | 准出评估 | 构建/环境/范围/通过率/P0/P1/缺陷/覆盖/遗留/结论 | 计划复述、猜测数据 | 准出结论可追溯 |
| 缺陷详单/文案 | 缺陷交接 | 复现/预期/实际/环境/构建/证据/严重度/影响 AC | 未确认的技术方案 | 开发可复现、产品可决策 |
| 评审记录 | 文档/用例评审 | 范围/发现/严重度/结论/责任人 | 自我批准 | 结论明确、可关闭 |
| 冒烟清单 | 快速准入 | 关键路径/最少步骤/阈值/证据 | 全量回归 | 可在短时间内判定 |
| 交接包 | 跨角色快照 | 00/01/必带快照/回执可选/版本/缺口 | 密钥、未过门草稿 | 接收方可独立核对 |
| 复盘 | 改进闭环 | 事实/根因/行动项/负责人/截止/验证 | 追责、空泛口号 | 行动项可验收 |
| 工作日志/CHANGELOG | 里程碑/发版史 | 版本/日期/变更/迁移/影响 | 过程流水账 | 可追溯、不过期 |

## 3. 评审清单（交付前逐项过）

- [ ] 目的/读者/范围一句话能说清
- [ ] 环境/构建/账号/数据/执行结果有来源
- [ ] out/未覆盖有来源/理由/确认人
- [ ] 用例/AC 可追溯到需求或提测单
- [ ] 执行结果与台账/证据一致
- [ ] 通过率/P0/P1/缺陷数同口径
- [ ] 已知问题含影响/是否阻塞/规避/计划
- [ ] 状态/版本/负责人/变更记录齐
- [ ] 无密钥/PII；链接/路径可打开
- [ ] 当前有效状态：无「已删除/已废弃/不要再用」留痕；无历史过程/旧方案/未采纳草案；结论只写现行
- [ ] 不替开发/产品下结论

## 5. 版本与构建标识（所有文档）

- **四个标识分开**：产品/测试版本（如 `{版本}`）、构建/制品（tag/commit/构建号/镜像 digest）、部署版本（build-manifest/`.deploy-rev`）、文档版本（文档自身）。**提测单只写实际部署版本**，不写文档版本/commit/tag/`.deploy-rev`；测试只认实际部署版本；代码 commit 是开发内部追溯。
- **版本节奏**：按项目版本策略（A 发布候选/B 连续迭代）；测试只记录版本与构建，不自行升版。
- **项目内可查**：项目/URL 必须提供版本查看方式（页脚、`/version`、`/health`、构建清单）；没有就补，不能靠文档 HEAD。
- **文档提交不改变构建**：禁止把 HEAD、文档 commit、文档 rev 当构建版本；代码不变，文档怎么提交都不影响被测版本。
- **提测单冻结**：起草可滚动；交接冻结为 `提测单-{版本}.md` 或 `releases/{版本}/提测单.md`；交接后改动出下一个版本/候选，不覆盖。
- **构建/发布不可变**：一次构建、同一制品晋级；变更出新版本；参考 12-Factor build/release/run、GitHub immutable releases。
- **证据**：测试报告记录部署版本、环境、版本查看证据；构建/commit 由开发在部署记录中维护，测试无需读取本地文件。

## 6. 维护

- 新增/修改模板时，同步更新本文件 §2 类型矩阵与模板索引。
- 发现“模板有结构但产出不可用” → 先修模板/标准，再修单份文档。
- 版本随包 `template_version` 更新；本文件不单独设版本号。
