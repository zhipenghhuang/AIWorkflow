# 澄清追问环（测试轨）

> **单一出处**：澄清的触发、提问格式、需求理解包、缺口清单、停止条件与落盘。`AGENTS.md` §0.1、workflow 步注、技能只引用本文，不另写一套。
> **与确认门的关系**：确认门=执行授权（`hitl`）；澄清=理解对齐。门不能替代澄清；澄清答复不自动授权执行，仍需按步过门。
> **读取时机**：任务开始、输入含 PRD/原型/方案、测试依据不明、准备写计划或用例前。
>
> **总规则（强制）**：先读规则/技能/主读/代码/现网并做分析，再问用户；**只问影响意图、范围、验收、风险且 AI 无法自行确定的问题**；接口/字段/状态实现/测试技术等由 AI 查规则与技能后给建议，不逐条问用户。首轮通常 0～1 个问题，最多 3 个高影响问题（阻塞/安全/合规/高风险不受限）；用户确认理解/方案后执行。95% 仅参考，不作为停止条件。确认门不是澄清。

## 1. 问什么 / 不问什么

**必须问用户（AI 无法从资料推断，且会影响结果）**：

1. 目标/测试对象、用户与场景、成功标准/准出目标。
2. 范围/非目标、优先级与取舍。
3. 只有用户知道的业务规则、验收差异、风险接受度。
4. 需求/文档/原型/现网冲突需要用户裁决（尤其 oracle 无来源时）。
5. 高风险/不可逆动作的接受度（权限、资金、迁移、安全、发布前）。

**AI 自行分析，不问用户**：

- 接口/字段/状态实现、测试技术、自动化方案、脚本结构、数据准备方式、异常复现手段。
- 先查 `规则/`、`技能/`、主读、计划、基线、代码/现网；能确定就直接给方案/建议。
- 只有技术选择会改变测试范围/AC/准出/风险时，才升级为“需要你拍板”的取舍题，并附推荐。

**可以免问**：纯信息查询、机械操作、已由文件/代码唯一确定且无分支的低风险步骤、已脚本化回归；免问也给一行理解回执。

## 2. 首轮固定动作：先分析，再问 0～1 个关键问题

首轮回复按此顺序，不得先写计划/用例/长清单，也不得先列一串问题：

```text
【我的理解】{测试对象/目标/范围/角色/关键规则/oracle/不做什么，5～8 行}
【我已按规范/技能分析】{依据/风险/测试策略/建议；技术细节不抛给用户}
【需要你拍板】{0～1 个最关键问题；附推荐；没有则写“无阻塞问题”}
【其余假设】{不影响方向的假设；用户不反对即按此执行}
确认后我执行：{下一步}
```

- **首轮最多 1 个问题；常规总提问不超过 3 个高影响问题（阻塞/安全/合规/高风险不受限，仍一次一问）**；不把接口/字段/状态实现/测试技术等细节列成问题。
- **非机械任务至少给一次理解复述，请用户确认**；复述本身算确认，不必额外编问题。
- **先查后问**：能从主读、计划、基线、现网、代码确认的，先查并引用；只问查不到且会改变结论的。
- **问题可回答**：单选/短答/二选一优先；不问“你觉得怎么样”，不问实现细节。
- **附建议**：先给推荐答案 + 一句理由；猜测错了要显式改口。
- **问完就停**：等用户回答；不得自问自答，不得把“我先按 X 测”当已确认。
- **问题顺序**：目标/范围 → 主链 → 验收/oracle → 业务规则/冲突 → 风险取舍；技术细节不进入提问列表。

## 2.1 不确定项分流（防散问）

- **阻塞项**：不决定就无法继续当前步/门/验收 → 即时问（0～1 个），按 §2 格式；收尾第 4 点复述。
- **非阻塞项**：不决定也能按建议/默认推进 → 不即时问；登记 `测试计划` §2.4 假设与约束/§8 风险与应对或 CR；收尾第 4 点一次输出。
- 首轮只列阻塞项；常规总提问 ≤3（阻塞/安全/合规/高风险不受限）；收尾表 ≤5；编号带中文名。禁止散问/重复问；阻塞项不得拖到收尾。
- 回复后更新待决项/决策记录/计划；已确认不重复。

## 3. 回答之后：更新理解，必要时才追问

每轮回答后：

1. 用 1-2 句更新理解与方案（不要重复整段）。
2. 把已回答内容记为“已确认”，不再重问。
3. 只有回答引出新的高影响缺口/冲突才追问；否则更新理解并给方案/建议。
4. 常规总提问不超过 3 个；阻塞/安全/合规/高风险不受限，仍一次一问；超过说明需求本身不清楚，先帮用户收敛范围，不继续盘问。

**禁止**：把用户没说过的话写成预期；把“行业惯例/最佳实践”当需求；把多个问题合并成一段叙述；在用户回答前继续产出下游资产。

## 4. 停止条件（无实质缺口 + 用户确认，不靠感觉）

同时满足才可停：

- [ ] 需求理解包核心项已填；测试策略/oracle 已有 AI 建议；未知项只保留高影响缺口。
- [ ] 能复述：谁 / 在什么场景 / 做什么 / 系统怎么响应 / 怎么算对 / 明确不做什么。
- [ ] 关键冲突已裁决；未决项已标“假设”并有验证方式与责任人。
- [ ] 用户明确说“对/是/按这个来/可以”。
- [ ] 复述中的范围、AC、非目标与用户最后的表述一致。
- [ ] 每条预期（oracle）都能指到来源；无来源的已列 GAP，不用现网实现反推。
- [ ] 剩余缺口只是低影响假设，或已给建议待用户确认，不需要继续盘问。

**不算确认**：“随便/你决定/看着办/应该可以/差不多/沉默/只回一个 OK 但没有对复述表态”；**只回范围选项（如选 A/B）而未对整包理解复述表态**。遇到这些 → 给两个具体选项再问一次，或更新理解后等「对/按这个来」，不要开跑。

### 附录 · 置信度锚点（非停止条件）

> 参考值；**不作为停止条件**。停止仍以 §4 缺口清单 + 用户确认为准；先分析再问（§2）不可砍。

| 区间 | 含义 | 动作 |
| --- | --- | --- |
| <50% | 目标/范围不明 | 只问目标与范围，不产出 |
| 50-70% | 主链大致清楚，规则/oracle 有缺口 | 只问最高影响问题；技术/测试方案自行分析 |
| 70-85% | 主链与主要规则清楚，边界/异常有缺口 | 补关键业务缺口；方案给建议/假设 |
| 85-95% | 可复述，少数低影响项未定 | 复述确认；低影响项标假设 |
| ≥95% | 可复述且用户已确认 | 产出计划/用例/断言 |

连续 3 轮置信度不上升 → 换问法或回退到“目标/范围”重问；仍不上升 → 明确告诉用户“缺一个基础信息”，请其补充或缩小范围。

## 5. 完整复述模板（过门/落盘前）

```text
【理解复述】
- 目标：{解决什么问题/为什么现在测}
- 用户与场景：{谁/什么场景/触发条件}
- 范围：{这次测什么/不测什么}
- 关键规则：{状态/权限/数据口径/异常}
- 验收：{怎么算对；条件+动作+可观测结果}
- 测试依据：{PRD/AC/原型/接口文档/代码；oracle 来源}
- 冲突与缺口：{文档间冲突/未定义项/待探查口径}
- 未决与假设：{待确认项/假设/验证方式}
对 / 不对 / 补充？
```

测试轨另加“风险与建议测试类型”；输入含原型时另加“页面/交互/状态清单”。

## 6. 反迎合、反臆造

- 用户第一句话是“想要什么”，不是“为什么/怎么算成功”；先问后者。
- “应该/惯例/最佳实践/竞品也这样” → 追问具体场景、上次发生时间、代价、不做的后果。
- 用户改口：以最新回答为准；旧结论标作废，不留双真值。
- 不知道就说不知道；无来源写“假设/待验证”，不得写成事实。
- 不为了让用户满意而降低澄清标准；不把“用户没反对”当同意。

## 7. 落盘（单一真值）

| 场景 | 落点 | 最少内容 |
| --- | --- | --- |
| 需求/测试依据分析 | `测试/功能测试/测试分析表.md`（SSOT；理解回执/覆盖单元/歧义节；旧「分析短表」迁入本路径） | 来源、理解复述、Q/A、冲突、GAP、假设、置信度 |
| 版本级/高风险测试（可选加厚） | `测试/功能测试/需求理解-{范围}-{yyyyMMdd}.md` | 长文需求理解（T2/T3 可选）；不替代测试分析表 |
| 计划/用例 | `测试/测试计划.md`、用例文件 | 引用测试分析表（需求模型）/AC/TP；假设与缺口显式 |
| 待确认/决策项 | `测试计划` §2.4 假设与约束/§8 风险与应对或 CR | 编号+中文短名/事项/选项/建议/影响/默认/结论 |

- 记录格式：`Q: … → A: …（来源/日期/裁决人）`。
- 用户裁决优先于代码现状；代码与裁决不一致 → 记差异并回到澄清，不得用代码推翻裁决，也不得把实现当预期。
- 后续会话先读已确认记录，不重复问；有新证据才重开，重开另起一条，不覆盖旧裁决。


## 8. 例外与边界

- **用户点名“直接做/不用问”**：仍先给 3 行理解回执 + 假设清单；高风险/不可逆至少问 1 个最高影响问题。只免等待，不免理解与留痕。
- **执行中异常**：按失败分类处理；无法判断“预期还是缺陷”时用澄清卡问一次，不直接判阻塞。
- **非交互/自动化**：不猜；标 `blocked` + 待确认问题清单，交回人工。
- **确认门**：先澄清后过门；门只确认“是否执行”，不替用户回答“要测什么/怎么算对”。
- **确认门/菜单**：可一次展示多个授权选项，但不得夹带澄清问题。

## 9. 反模式（出现即停）

- 一轮列 3 个以上问题 / 发问卷；首轮把非关键问题也列出来。
- 把接口/字段/状态实现/测试技术等 AI 能查的细节逐条问用户，而不是先查规则/技能/主读给建议。
- 不带猜测的开放盘问。
- 用户答完不更新理解，直接写用例。
- 把“已读文档”当“已理解”；不引用章节/页码/接口。
- 把现网实现当预期；把原型当后端规则；把竞品做法当需求。
- 用“假设”绕过澄清，且不标假设、不写验证方式。
- 把“确认门”当“澄清”，或把“澄清回答”当“执行授权”。
- 置信度虚报 ≥95%，但复述不出“谁/场景/做什么/怎么算对/不做什么”。
