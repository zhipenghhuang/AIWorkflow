## 1. 总则

### 1.1 计划门与三门 · 落盘

见 `../AGENTS.md` §0.1（计划门＋门1～3；条件门：`hitl_when` 不满足则跳过）。正式资产只写现行有效状态（AGENTS §0.0）；落盘按 `规则/模板/`。

### 1.2 测试分级（T0～T3 · 防过度/不足）

| 级别 | 典型 | 计划 | 执行 |
| --- | --- | --- | --- |
| T0 补丁/热修 | 小改、单模块 | 轻量计划（≤1 页） | P0 冒烟 + 影响面 + 已脚本化回归 |
| T1 模块 | 功能/模块 | 轻量计划 | 模块功能 + 接口（如适用） |
| T2 版本 | 发布级 | 完整计划 | P0～P9 按计划 |
| T3 高风险 | 权限/资金/数据/迁移/安全 | 完整计划 + 专项 | 全量 + 性能/安全/兼容 |

T0/T1 不强行填完整模板；范围/类型/轨道/执行矩阵/准出/风险必须写清。发布列车/大版本 ≥1 次功能全量；补丁不强制全量。  
**常青纪律（计划内）**：版本级范围须含本期增量 + 常青/前序足够覆盖（至少依赖版 P0-Smoke 或等价常青冒烟；高风险可升 HighRisk）；准出须**当期通过且常青/前序约定项未崩**，禁止默认「仅新功能通过」。常青靠 Smoke+影响面+必要 HighRisk，不默念归档全量。计划外「随机业务流程」不替代本层、不进计划登记/排期/准出。

### 1.3 产物与过程（相对项目根 · 正式并列轨）

> **产物根：唯一 测试/**——项目根仅 环境基线.md、activeContext.md；设计输入进 测试/资料/{版本或主题}/ 或 _通用/（禁 项目文档/ 层），样本/测试数据进 测试/资料/测试数据/；交接：出站实拷/升包在 测试/交接/出站/{类别}/，入站收件在 测试/交接/入站/{类别}/（台账 测试/交接/交接台账.md；资料/交接不作主入口）；**禁止在项目根新建测试计划/用例/台账/脚本/证据**（原始输入放入原始资料根，推荐 docs/）；下表路径均相对项目根。  
> **资料收取/对照/归档**：以 规则/文档治理.md 为准；新资料先分析分类 + 与同主题/同版本旧文件做覆盖对照，输出候选，**用户确认后**才改名/登记/标记失效/归档。  
> **归档（分轨 · 域常青）**：换代/结项/版本关闭（用户确认后）→ **计划/报告/CR/交接快照**进 测试/_归档/{yyyyMMdd}-{版本}/；**用例主档留下**（功能/接口域常青）。轨内 _归档/ 仅收：下线域、有界重生快照、点名旧轮（探索式/随机）、发布前专项停用包/旧轮报告。失效资料进 测试/资料/_归档/；当前 测试/测试计划.md 不移动；**禁**把各轨用例整包丢进根 _归档/；**禁**关账搬走仍有效的功能/接口主档。多版本并行（罕见）→ 测试/{版本}/ 另起一套、单点随其目录。  
> **常见轨框架**（功能 / 探索式 / 随机业务流程 / 接口 / 发布前，非穷尽）：边界见 规则/轨契约/（随机业务流程为**计划外**独立轨）。新测试种类不强制新轨名 → **就近归轨**，计划/台账写差异与 deviation=；有独立目录需求时再登记。

## 2. 生成

> **资产生命周期（域常青 · 分层库 · AI 增量）**：功能/接口等**域主档跨版本保留**（`…/{NN}-{短名}/*-功能|接口用例.md`），**不**因换迭代整轨搬走。分层：`L0`=Core（`测试/00-稳定冒烟清单.md`，≤12）｜`L1`=域常青主档｜`L2`=本版增量（专项/新条，择优沉淀进 L1）。**索引** = 域注册 + Core + 本轮装填表（计划 §3.7）；**禁**日常通读全库当回归清单。  
> **生成默认**：影响源（提测单影响面**若有优先** → CR → 主读 diff/有界对照 → 用户点名）→ **先打开命中域** → 表 `新增|修改|淘汰|rerun` + 保 `caseId` 增量改；**禁**无分析整版重生；**禁**「继续」隐式全仓 generate。  
> **影响面（测试包自建 · 不依赖提测单）**：无开发提测单/无 HO 时，**测试分析表**仍须写清 **直接/邻接/回归** 影响面并落入 §3.7 装填；**禁**因「没有提测单」跳过邻接影响面或只测变更点本身。提测单只是加速输入，不是影响面的前提。  
> **冷启动**：命中域文件不存在 → **允许按域首生**（非逃生）；有库后默认增量。  
> **有界重生（逃生）**：口令「重写{域}」／半域失效／同域无效合并≥2 次 → 快照入轨内 `_归档/` 后整域重生；须收尾写明域名与原因。  
> **一遍过**：= **本期命中范围/本域变更面** 宁多勿漏（映射无空、影响面落点），**≠** 全仓重生。  
> **脚本**：P0-Smoke 跨版本保留；接口按 depth（迭代 `standard` / 发版 `full` / 补丁 `core`）可执行维须脚本化；一次性不脚本须理由。日常小修 → §2.1.1；续跑 → §3.1。详见 `规则/专项/多轨质量标准.md`。

### 2.1 功能测试资产

- **口令**：生成用例 / 生成测试资产 / 阶段一 等  
- **输入**：已点名主读或门1 选定 + 设计输入 + 可探查现网 + **`测试/测试分析表.md`（必有；模板见 `规则/模板/10-计划/测试分析表模板.md`；主读已点名也不省）** + **现行测试计划**（缺/超范围 → 先轻量补）+ `测试/00-稳定冒烟清单.md`（有则读）+ **命中域现行用例**（有则必读；`_归档` 默认不读）。**生成/计划双读：主读原文 + 测试分析表**。  
- **动作**：轻量分析（可与生成同轮）→ 定命中域 → **增量**产出/更新用例与台账（**计划驱动按 §3.2 + §3.7 装填登记**；结果=未执行；**写法红线见用例模板头**；模块头须有 §1 总览索引供锚点改条）→ **逐条判可脚本化并落 §1.2 清单**（`规则/专项/脚本执行.md` §1）→【生成收尾】写增改删表  
- **大规模生成**：≥3 模块且（预估≥40 条或用户点名）→ 按 `多Agent与输出.md` §1.5 分片（draft 不相交可并行≤3；编排合并+覆盖三闸；超时降级直做）；**禁**并行写同一正式域文件。  
- **能测尽测**：方案未写死数值/细则时，**仍须生成行为与流程用例**；预期可写「以本构建现网实现值为准」。禁止因「文档待冻结 / 交给开发定」而整段不生成或不测。  
- **既有实例**：旧 `{NN}-*.md` 包**视为 L1 现行**；下版起增量；**不强制重编号**。  
- **框架闸**：  
  1. **完稿自检**：按生成代理（testcase-agent）清单逐项过——独立可执行/前置三件套/编号对齐/判定面/负向边界/影响面逐点/视觉基础/映射无空行/引用可回查/冒烟集齐/排序/清理与提示/七维自查/章节回执/引用抽验；缺项先补，禁带缺口落盘。  
  2. 有依据写清；设计来源可回查或标明现网依据。  
  3. 生成期结果列为「未执行」（「待实现」仅作执行终态，且仅限方案/AC/计划范围内未实现——见 §3.0；待实现=实现缺陷，必须计入缺陷并提交）。  
  4. **覆盖（准确度前置 · 三闸）**：落盘前须完成；缺任一项不得称「已覆盖」。细则如下。

#### 2.1.0 覆盖三闸（功能全量 / 功能专项 · 不可让）

> **定位（不可让）**：功能轨是迭代准出主轨——对本期**命中域/变更面**按『**一遍过 · 宁多勿漏**』补齐映射与用例（增量优先）；**影响面（逐邻接点）与视觉/UI 基础必须覆盖**；接口/探索式/发布前为补充轨。**禁**把「一遍过」读成全仓重生。  
> **强制范围**：§2.1 功能全量与 §2.1.1 专项须过覆盖三闸。接口/发布前/探索式（§2.2～§2.4）按 `规则/专项/多轨质量标准.md`：**接口对照禁空+depth 可执行**；**发布前硬映射**；**探索章程目标闭环**——禁止「软覆盖」空话。

| 闸 | 要求 |
| --- | --- |
| **① 可测承诺抽取** | 从主读（+有界对照）及**测试分析表**（覆盖单元/影响面）抽点。须入清单：验收/GATE、主成功路径、状态与非法跃迁、权限/数据域、明确异常与阻断、变更点、邻接影响面、负向边界。有前序/GATE 依赖 → 计划列依赖版 P0-Smoke。未写类 →「文档未声明」≠免测。**章节回执**见分析表 §6；缺章不得称已覆盖。 |
| **② 设计点→用例映射 + 深度档** | 落盘用例文件 `## 3. 设计点覆盖映射`（见用例模板）：每点一行 → 用例 ID（可多对多）或「不适用」+依据；**禁止空映射**。**覆盖单元至少含 `GATE/AC/TP/F/R/§`**（优先级高于 DP/模块名）；P0-Smoke/P0-HighRisk 或 GATE 无对应用例=覆盖缺口，先问用户是否接受不测。阻断主链 / 验收 GATE 标 **P0-Smoke**（冒烟闸判定行，见 `规则/专项/多Agent与输出.md` §1.1.1）；高风险点标 **P0-HighRisk**——均须有对应用例。影响面/变更点行须能指到用例或「不测+理由」。**深度**：仅映射无空行≠已覆盖；P0/高风险点须满足 `技能/testcase-design` §2.2 深度档；**数据链路/可观测性**按 §2.4 检查（幂等落库、窗口守恒、联动字段、点位级诊断、最新值来源、审计、基线对象、`待实现`复测）；**步骤详细度**按 `技能/testcase-design` §5（位置/操作/数据/中间预期四列齐全，禁「同业务详情/按场景数据」）；用例 §4 须有「深度档自检」行（达标/缺口+依据）。禁场景清单 1:1 落条后空喊「宁多勿漏」。 |
| **③ 缺口显式（三分类）** | 收尾「缺口」必须按类写清，**禁**把「方案未写死数字」写成「不测」：① **覆盖缺口**=未映射、深度档未达标或用户接受不测；② **口径待探查**=方案留白、开发已/将落地，**已有用例**，执行时先读现网实现值再断言；③ **环境/交付缺口**=入口不可达或能力未实现（执行期 blocked 或待实现（实现缺陷，计入缺陷））。「覆盖」句须可对照映射表（如「映射 N 点，P0 全覆盖，深度档达标，影响面 i 点全落，视觉基础已含，覆盖缺口 k，口径待探查 m」），**禁**空泛「已全覆盖」。 |


**视觉/UI 基础（生成 + 执行落地 · 单一出处）**

- **生成**：每受影响页面 ≥1 条视觉预期，或并入相邻功能用例的预期/失败判定（布局错位遮挡｜文案数值截断｜按钮/图标态｜空态/加载/错误提示｜明显样式断裂）。不追求像素级（像素级→项目 `visual-reg`/发布前兼容）。§4 须写「视觉基础：已含/并入哪些 ID｜缺口」。
- **执行（浏览器 MCP / AI 直跑）**：凡**为目标页拍截图**（失败留证、定位侦察、或用例要求证据）→ **同帧顺带视觉检**，不另开「纯视觉轮」凑条。检项：①布局错位/重叠/关键控件溢出；②主操作或关键字段被遮挡；③标题/数值/状态截断不可读；④该出现的空态/加载/错误提示缺失或误导；⑤按钮启用/禁用/loading 与业务态明显不符；⑥冗余标语/标签严重妨碍理解（文案减法）。阻断业务或 P0 面 → 本条 `fail`+钉断言截图；非阻断 → `额外发现`/观察项，能复现进缺陷。通过用例不强制额外截图；**已截则必检**。脚本档：有截图断言则同检；无 UI 截图的纯 API 脚本不适用本段。
- **疑似体验/布局不合理（轻量 · 有发现就记）**：读图时顺带看一眼——展开/下钻/弹层后邻接区是否被撑出大块无内容空白、双栏明显一头沉、主内容挤成一团而旁栏空洞等。**默认只记「额外发现/观察项」**（位置+现象+截图），不抬成用例失败、不做设计评审、不追风格偏好；仅当同时挡住主操作或违反已写 AC/设计规范时才升 `fail`。未看见不硬挖。
- **能力**：未装 `vision-ui`/`visual-reg` → 现行「AI 读图/截图人工可读」降级，**不免除**上列检项（含疑似不合理有见则记）。

**权限未声明**：说明列可写「文档未声明」，但须 **≥1 条可用角色冒烟（建议 P1-Core）**，或收尾写明用户接受本轮不测权限——二选一，禁止静默跳过。

设计技法：详版见 `技能/testcase-design` §1～§2.2；写操作与字段级必含负面与边界；P0 按深度档强制，非「可选用可不用」。

**测试分析表**（跨轨共用依据表；企业 RTM/测试条件等价；可与 generate 同轮先产出）：落 **`测试/测试分析表.md`**（模板 `规则/模板/10-计划/测试分析表模板.md`）。含：**§0 Brief+本期差量表**｜理解回执｜**覆盖单元表**（含 Delta ID）｜影响面表｜歧义/冲突/GAP｜追溯摘要｜章节回执。主读已点名**不免除**。**功能/专项**：plan/generate **双读原文+本表**。**接口/发布前/探索式（独立或计划驱动）**：生成或定范围前**至少读 §0**（差量/范围/非目标），契约与指标仍按各轨契约；禁与 §0 本期差量脱节却宣称「本期接口/发布前已对齐」。细则见 `技能/test-basis-analysis`。实例若仍见旧路径/「分析短表」，迁入本路径或头注见新路径。

**【生成收尾】**：对照 `规则/模板/90-交接与收尾/收尾骨架.md` §2（标题可用【生成收尾】）；第1点写生成结果（映射/用例量按实情）；汇报=结论说明体一段（禁子 bullet）。仅生成且有拟入库 → generate 步门3；同会话续执行 → 门3 留到 report。

### 2.5 落地产物评审（主链 · `review-cases` + 计划步内评审）

> **设计说明**：强制问 A/B 的不是「所有文档」，而是**约束执行与准出**的落地产物。选 B 时先【自主分析】再过量规。方法：`技能/test-artifact-review` + `技能/testcase-review`；角色：`agents/testcase-reviewer.yaml`。  
> **评审批次（硬 · 防仪式税）**：默认按**本轮装填/同次生成批次**出评审，**不是**「每个域夹永远强制单独一整套 A/B」。同轨+同主读+同轮可**合卷**；**跨轨不合卷**（功能≠接口≠发布前≠探索）。

- **口令**：用例评审 / 评审用例 / 测试计划评审 / 接口资产评审 → step=`review-cases` 或 plan 步内（**不重生成**）。  
- **主链**：analyze → plan（计划/分析可问 A/B）→ generate → **review-cases** → execute → report。  
- **强制问 A/B**：计划（T1+ 实质）｜分析表（T2/T3 或歧义≥2）｜功能/专项（T1+）｜接口（T1+ 或进准出）｜发布前（T2+ 或发版/计划已列）｜探索（计划纳入且 T2+ 或准出引用）。随机仅点名。见 `多轨质量标准.md` §4。  
- **批次与合卷**：
  | 情形 | 做法 |
  | --- | --- |
  | 单域/单专项本轮大改 | 一范围一评审文档 |
  | 同轮同主读、多邻接功能域（或同轨多接口域）一起生成 | **一份合卷**：范围=本轮装填列表；文内按域分节；可写分域放行/需修 |
  | 功能 vs 接口 vs 发布前 vs 探索 | **分轨分文档**（量规不同） |
  | 孤立大域 / 高风险域 / 用户点名单审 | 可单开，不强制合卷 |
  | T0 小改 / 仅改 ≤3 条 | SELF_CHECKED 或轻量摘要；不必整本评审模板 |
- **落盘命名（C · 自描述）**：
  - 单域：`测试/{轨}/{NN}-{短名}/{NN}-{短名}-评审-{yyyyMMdd-HHmm}.md`
  - 合卷：`测试/{轨}/评审-{本轮范围摘要}-{yyyyMMdd-HHmm}.md`（摘要≤32 字，如 `登录+ASN+邻接`）；§1 必须列全文件路径
  - 计划/分析：`测试/评审-计划-{戳}.md` / `测试/评审-分析-{戳}.md`
- **选 B**：先【自主分析】→ 再量规；用户自定义焦点优先。  
- **功能量规**：A1–A6 / S1–S8 + 三闸 + 评分卡≥18/20；P0 全审。接口 I1–I6；其它轨按契约。合卷时套件轴可整批一次，单条轴按域抽样。  
- **计划驱动**：§9.2 P2 = 冒烟全绿 + 覆盖闸 + **本轮装填对应评审已放行**（合卷或分卷均可，禁未审域混进执行）。  
- **机器门**：功能轨选 B → `-Mode review`；其它轨选 B 留痕即可。  
- **HITL**：`select_review_mode` → `confirm_review`（需修时）。同批合卷只问一次 A/B。  
- **豁免**：T0 SELF_CHECKED；专项轻量追加节不强制计划再审。

### 2.6 期中变更（计划增量 · 用户只给变化）

口令：「本期变更 / 计划变更 / 增量变更 / 新文档更新测试计划 / 产品缺陷已确认 / 产品给新说明或文档 / 同步产品变更」。**不新开整期计划**；在当前 `测试/测试计划.md` 上增量更新。三包独立：产品/开发产物是可选输入；无产品包时用平台备注/附件或用户文档。

1. **建 CR**：`测试/变更/CR-{yyyyMMdd-HHmm}-{主题}.md`（模板 `规则/模板/30-执行与台账/测试变更记录模板.md`）；CR 是唯一变更单，计划 §15 只登记摘要。  
2. **分类**：A 澄清/无范围变化｜B 功能增量/修改（同范围）｜C 实质变更（范围/准出/排期/缺陷策略）｜D 缺陷驱动。产品确认带新 AC/文档 → **D+B**（同范围）或 **D+C**（实质变更）；纯澄清不改 AC → A；不得只算 D 而跳过用例/计划更新。  
3. **影响分析**：按 CR §3 写全：模块/页面、接口、用例、脚本、数据/环境、回归范围、覆盖点、资料/文档、计划/报告、追溯/评审、接口/探索式/发布前资产。  
4. **资料收取/对照**：新文档放入 `测试/资料/{版本或主题}/` 或 `_通用/`（禁 `项目文档/`、禁强制类型前缀），按 `规则/文档治理.md` §3～§4 意图分析 + 覆盖对照；输出候选，**用户确认采纳后同批**才改名/登记/S1～S3 失效归档（落 `测试/资料/_归档/`）；部分覆盖/增量补充保留旧文件；更新 `测试/资料/资料索引.md`；用例/台账/报告的设计指针同步替换；工作产物不回写资料。  
5. **更新计划**：按 CR §4 更新 §0/§1/§2/§3.1/§3.2/§3.7/§5/§7/§8/§9.2/§10/§11/§12/§14.3/§15/§16.1；只改受影响项。  
6. **更新资产**：只改命中域用例/脚本/数据/接口/探索式/发布前资产；**保 caseId/路径**；用唯一锚点增量改；P0-Smoke 变化才更新稳定冒烟清单；不重复建；**禁**无逃生条件整包重生成（半残合并≥2 次 → 有界重生该域）。  
7. **门禁**：C 类 → 计划状态=变更中 + 计划门；A/B 类 → 就地更新，不重开计划门；D 类 → 缺陷轨，范围变化才回计划；D+B/C 按 B/C 门禁。**不新增确认门**。  
8. **执行时机**：默认等计划模块/阶段位；提前仅限 P0/高风险、阻塞后续、独立且数据/入口就绪、有专门含变更构建；P0 冒烟可在构建/阶段边界先跑；执行前核构建含变更；禁一条用例中途切换/旧构建跑新变更/多个变更反复打断。  
9. **执行**：suite=`core` → **命中域+邻接影响面**（suite=`module`，宁多勿漏；影响面组建议制，**禁**为省事只留 Core）；发版/完整项目/点名 → `full`；不默认全库重跑。产品确认新 AC → **按新 AC 回归**。  
10. **收尾**：按 CR §5 逐项标「已更新/不适用/待补+责任人+截止」；未闭合不得标 CR 完成；更新计划 §0（含装填状态）/§16.1、报告 §2/§3/§5/§6/§7/§9/§10、activeContext；用户按计划验收。  

### 2.7 协作交接（提测/报告/缺陷/变更）

- **接收**：提测/需求/报告/变更包先走 `workflows/handoff.yaml` receive：核对清单/版本/构建/阻断缺口 → 接受/有条件/退回 → 填写回执 → 更新计划 §0/§1.1/§16.1 与台账；未签收不得开跑或把结果判为通过。
- **发出（内容优先 · 包按需）**：默认交付自洽主文档——报告→`测试报告.md`；缺陷有平台→平台单；计划→`测试计划.md`；对照发出前合格线。`TEST/BUG/FIX/CHG/REL` **HO 包不默认生成**；仅多文件证据/正式签收/仓外 ZIP/点名时先问后发（见 `协作与交接.md` §3.0）。报告包若发须过报告门 PASS/CONDITIONAL；未回执不得写“产品/开发已接收”。多包同仓直读、禁转发；收件走入站/分析吸收 + 可选签收。
- **变更**：C0 就地更新；C1 更新计划/用例/脚本，**按需**建议 `CHG`（先问后发）；C2/C3 回计划门并重基线；禁止把 C2/C3 拆成 A/B 绕过。
- **状态**：有 HO 时 `交接台账.md` 为包状态真值；无包时以主文档+平台为准。`已发送 ≠ 已接收`。

## 3. 执行

门2 确认后：功能/探索式读 `规则/专项/多Agent与输出.md`（执行形态四档取档，含脚本档）；接口轨单 Agent（见轨契约）。**计划驱动多轨 → §3.6**（计划 §9.2 编排；阶段内仍按轨契约）。

> **装填先行（suite）**：**有文件 ≠ 本轮跑**。开跑必展示装填行（计划 §0/§3.7）：`suite=core|module|full` + 命中域 + 已终态 + next。  
> | 场景 | 装填 |  
> | --- | --- |  
> | 继续/按计划 | Core + §3.7 已登记域；缺资产只补命中域；**不**重新影响分析 unless CR |  
> | 回归 {范围} | 指定条；不扩 |  
> | 发版/点名 full | Core + 范围 Module（±接口 depth=full） |  
> | 缺陷回归 | 原单 + Core 子集 + 影响面组 |  
> **准出门槛（测完才保障发布 · SSOT=`规则/专项/多轨质量标准.md` §3）**：  
> - **迭代/提测准出**：功能 **suite≥module**（命中+邻接宁多勿漏）；范围含接口 → 接口 depth≥**standard**（命中接口全部适用维可执行）；计划已列发布前/探索 → 按 §2.3/§2.4 闭环；分析表 §0 已确认。仅 core **不得**准出。  
> - **发版/完整项目/大版本准出**：功能 suite=**full** + 接口 depth=**full** + 发布前按风险级最小集**硬映射完成**；未跑完不得称可发布，除非用户书面接受缺口（有条件通过）。  
> - **补丁/热修**：可 suite=core + 接口 depth=core，报告须标「补丁口径」；**不得**冒充版本准出。  
> - 安全/P0 **不可**因「精准」静默剔除。报告必声明 suite + 各轨 depth/风险级。

**功能按计划轮次 + 装填执行**（`测试/测试计划.md`；缺则轻量补）：先过「数据准备 → 冒烟」前置——备数据 → P0-Smoke（core）→ §3.7 装填域（**module 为迭代默认**；发版/完整项目 full）。执行中不向用户刷用例级明细（终稿 §4 除外）。

### 3.0 口径探查与结果态（功能全量/专项 · 不可让）

1. **实施后必测**：方案将数值/细则交给项目落地时，执行以**本构建现网实现**（页面说明、配置、接口、计算版本）为断言尺子；与方案意图冲突 → 失败或拉产品确认，**不得**因「方案未写死」跳过。  
2. **口径待探查**：开跑该条前先读出**本载体**实现值（字段名/提示/配置），写入台账摘要或基线增量再判定；**禁止**因难测改测其它功能点/接口。  
3. **`待实现`（pending）**：方案/AC/计划范围内应实现而未实现（菜单无入口且无接口）→ **实现缺陷**；入口存在但 404/500/空壳/假成功→**失败（实现缺陷）**；两者都必须计入缺陷并进入批次/阶段/收尾提交。明确范围外/后续池 → `不适用`，不标 pending。**禁止**「系统已有规则/阈值，仅文档未写」→ pending。  
4. **`阻塞`**：过渡态——穷尽自打通仍不可达（互异手段≥2 且总尝试≤3；缺数据须先造/换，细则见 `规则/专项/多Agent与输出.md` §1.3-4）。**方案/AC 范围内未实现（菜单无入口且无接口）→`待实现（实现缺陷）`；入口存在但页面/接口 404/500/空壳→`fail`；两者都不是阻塞**；与 pending 勿混用。测短路径可通 → 本地消化不开单。需外力 → 按 `缺陷分类.md` §0 / `缺陷协作.md` §6.0 升级**平台盯办**（实机类型与指派，不明问用户），**禁**为交平台改标 fail。**blocked 四问**：能造数/换样？能换入口/角色？是否被测缺陷（→fail）？互异手段≥2 且总尝试≤3？**终态对照**：缺数据/样本→造/换；菜单无入口且无接口→`待实现（实现缺陷）`；菜单有入口但页面/接口 404/500/空壳→`fail`；环境/可测性外责穷尽→`blocked`（可盯办）。  

### 3.1 功能专题 / 专项

口令：执行/跑/专题/阶段二；或执行专项 `S-{数字}…`。

> 「回归」三义：**功能轨回归**（本轨「回归/重跑」＝重测既有用例）｜**平台单回归**（缺陷轨 §7，指派给我/已解决）｜**轮次回归**（R2+ 轮——修复后按轮次复跑，范围见下条默认口径）。

- **续跑（「继续」）**：沿用 `DraftPath`、门2 与计划 §0 **装填状态机**（装填清单/已终态/next）；只续装填，**不**隐式全仓 generate、**不**重做影响分析 unless CR；不重跑已有终态；缺终态先对账再补写/定点重测（**禁未对账重复写操作**，见多Agent §2.1）。  
- **回归执行（「回归 / 重跑 {全量|模块|条目}」）**：按点名范围**重测既有用例**；结果**就地覆盖**台账与证据（执行时间更新为最近一轮）；**只保留最新确认结论，不写过程**；细则见 `规则/专项/多Agent与输出.md` §2.1。  
- **修复后回归（默认口径 · 保留高标准 + 省 token）**：**每次修复后立即回归，不等批末**（计划 §10）。  
  - **默认必跑**：原单复测 + 受影响模块冒烟子集（优先脚本档 0 token）+ **影响面组**（AI 依缺陷改动范围/测试分析表/提测影响面自建 3～8 条；**计划驱动默认纳入**，用户可砍减但须收尾留痕「砍了哪几条+理由」——禁静默省略）。  
  - **无开发回写影响面时**：测试侧仍须自建影响面组，**不**因无提测单/无 FIX 备注而只跑原单。  
  - **升级**：高风险（跨模块/契约/数据/权限/资金/并发）或连环缺陷（同模块短窗口 ≥2）→ 提示升局部 module/扩大邻接，用户确认后执行。  
  - 同批修复合并一次回归（重叠去重）。结果就地覆盖，并入报告 §5.2。平台单同口径（`规则/缺陷/缺陷协作.md` §7）。  
- 与缺陷轨「平台单回归」（指派给我/已解决等，见 `规则/缺陷/缺陷协作.md` §7）不同轨——平台单回归走 `规则/缺陷/缺陷协作.md`。

### 3.6 计划驱动执行（跨轨）

- **执行细则**：并行隔离、回归并行、缺陷提交/闭环、探索式穿插、非功能、外部责任项、停止/恢复/变更 → **`规则/专项/多Agent与输出.md` §4（单一详版）**。

### 4.1 仓库拟提交（`confirm_commit` / handoff·skill-audit commit；≠门3 交平台）

> 与收尾第 2 点「待提交摘要」分工：摘要在收尾；本块仅仓库确认一次。门 ID=`confirm_commit`（≡ 产品/开发同名门）；展示块名可写【拟提交·仓库】以与门3区分。前四字段与产品/开发【拟提交】对齐。

```text
【拟提交·仓库】
- 文件：{清单}
- .gitignore 现状：{一句}
- 当前分支：{名}；跟踪远程：{origin/xxx 或无}
- 本次动作：仅提交（默认）

```

交平台确认（门3=`confirm_platform`，仅一次，置于骨架后；**勿与上块混写**）：「本轮拟提交：缺陷 N（失败 X + 待实现 Y）+ 盯办 M（若有）；类型/指派已按实机匹配或已问清。是否确认提交？」{确认→workflow:defect（可排除）/ 否→结束}
